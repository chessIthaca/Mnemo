+++
title = "Windows pid probes must check the exit code — OpenProcess succeeds on held-open exited processes"
created = "2026-11-01"
+++

On Windows an exited process keeps its kernel object while ANY process still holds a handle to it (for example a launcher's std::process::Child), so OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, pid) succeeds for a DEAD pid. Any "is this pid alive" probe built on OpenProcess alone is wrong: it must follow with GetExitCodeProcess and treat only STILL_ACTIVE (259) as alive, closing the handle on every path. In windows-sys (Win32::Foundation) STILL_ACTIVE is typed NTSTATUS (i32) — compare against the u32 exit code with an `as u32` cast. Implemented in mnemo-app's instance_marker::pid_alive (src-tauri/src/instance_marker.rs) with the regression test an_exited_process_held_open_is_not_alive (spawn cmd /c exit 0, hold the Child, wait, assert !pid_alive — holds through the assertion so the process object stays referenceable). Callers sharing the predicate: conflict_for (mnemo2 project attach + the Mnemo1 backlog root), run_file::prune_stale, mnemo2_mcp's owners_gone, ipc/startup. Accepted residual: a process that really exits with code 259 reads as alive.

Design fact for re-adding a pid-reuse guard in conflict_for (marker.started_at vs GetProcessTimes creation time): a marker {pid: X, started_at: T} whose pid's process was created clearly after T + slack names a recycled pid, not the writer. But mnemo2 project.rs's attach_requires_confirmation_for_a_live_incumbent writes its fixture marker with started_at: 1 while its live child is spawned around now — exactly the recycled-pid shape — so that fixture must be made realistic (spawn the child, then write started_at = current epoch seconds) before such a guard can land.
