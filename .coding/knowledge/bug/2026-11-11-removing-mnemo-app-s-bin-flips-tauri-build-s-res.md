+++

Removing the `[[bin]]` target from src-tauri/Cargo.toml flips how tauri_build's Windows resource is linked. embed-resource 3.0.11 (under tauri-build 2.7.4, pinned in Cargo.lock) picks the directive by a `hasbins` heuristic: Cargo.toml top-level "bin" key OR src/main.rs OR src/bin/ present → package-local `cargo:rustc-link-arg-bins` (inert for a library); none present → PROPAGATING `cargo:rustc-link-lib=dylib=resource`, whose manifest/versioninfo/icon then collide with mnemo2-app's own resources in every downstream binary (rust-lld: "duplicate resource MANIFEST", cargo build -p mnemo2-app fails). Neither can be faked: a top-level `bin = []` restores link-arg-bins but cargo rejects it ("invalid instruction ... does not have a bin target"); cargo also does NOT apply `cargo:rustc-link-arg-tests` to the lib's unit-test target, so the feature-gated #[link] in src-tauri/src/lib.rs is the only manifest path for `cargo test -p mnemo-app --features mnemo2 --lib` (its exe imports TaskDialogIndirect; without the COMCTL32 v6 manifest it dies with STATUS_ENTRYPOINT_NOT_FOUND). Fix shipped in commit 674702df (2026-11-12): src-tauri/build.rs moves the compiled resource.lib to resource-tests.lib and leaves an 8-byte empty archive ("!<arch>\n", the llvm-ar empty form rust-lld parses fine) at the propagated path; lib.rs's #[link] now names "resource-tests". Also: changing Cargo.toml does NOT rerun the build script (tauri_build only declares rerun-if-changed for tauri.conf.json/capabilities) — force with `cargo clean -p mnemo-app` when iterating on link directives.
