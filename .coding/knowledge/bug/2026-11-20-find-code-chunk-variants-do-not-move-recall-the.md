The step-15 eval measured find_code's chunk variants on d3336a8a's 25-question set: a) today's chunk, b) + split name words, c) + enclosing type + body excerpt. Symbol recall@5 was 3/25 for EVERY variant; file recall 11/25 (a), 12/25 (b), 11/25 (c); the fair token-OR search baseline scored 1/25 symbol, 9/25 file. The chunk-text changes did NOT move recall — the differences are within one question (noise) and the cause is unknown: either the jina code model's vectors don't rank these plain-language questions well, or the cosine term's weight (COSINE_WEIGHT in rank()) is too small against the FTS/name terms. The shipped chunk is c (production's Full shape). Diagnosing whether the cosine term itself is effective is a separate follow-up step (the lead's decision, 2027-01-20); do not re-run the three-variant eval for tuning — the questions must not change.
Also learned while diagnosing the eval's stuck drain: `CodeGraph::symbol_embed_pending` returns at-least-one (pending_symbols(model, 1).len() is 0 or 1), NOT an exact count — the eval printed "1 pending" while hundreds were stuck. And the pass's arena-failure mechanism (fixed): one 64-symbol ONNX call per batch grew the arena per distinct padded shape until an allocation failed mid-pass; the embedder's zero-contract answered and the pass's zero guard stopped it with the queue half-drained. The pass now sub-batches at SYMBOL_EMBED_SUB_BATCH=16 like the host.
