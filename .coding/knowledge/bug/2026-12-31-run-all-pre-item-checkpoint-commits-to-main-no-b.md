BUG (security review MEDIUM; verified; fixing under plan a91e71d3, backlog 04bd6977): Run-All's pre-item checkpoint can commit directly to main. Symptom: run_all_dispatch_next (src-tauri/src/ipc/run_all.rs:962-984) calls checkpoint() before dispatching the next backlog item, and checkpoint_impl (src/project/git_ops.rs:104-123) runs git add -A + git commit on whatever branch is checked out — no branch check. The per-directory wt/* auto-fork only happens later inside create_plan (ensure_work_branch, git_ops.rs:588-642), so when the session sits on main — e.g. right after merge_to_main lands a branch — the next Run-All tick commits the dirty tree (typically the .coding/backlog.jsonl status flip) straight to main, violating the never-commit-to-main constitution. Root cause: checkpoint_impl is branch-agnostic and is the ONLY pre-dispatch git step — nothing forks the work branch before it. FIX (plan a91e71d3): a new checkpoint_on_work_branch core (ensure_work_branch_impl → checkpoint_impl) forks/reuses the per-directory wt/* branch before committing (matching create_plan's auto-fork semantics); a refused fork (dirty paths outside .coding/) propagates Err("work-branch fork refused: …") so the dispatch's existing checkpoint-failure path stops the run (item stays Pending, reason in its note) — deliberately stricter than create_plan's Err semantics (which proceed on the current branch), because dispatching while on main with a dirty tree would commit the item's work to main too. Regression tests (git_ops.rs, MockGit): checkpoint_on_main_lands_the_commit_on_the_work_branch (RED: the commit landed while current_branch == "main"), checkpoint_on_the_work_branch_stays_put (pin), checkpoint_refused_fork_commits_nothing (RED: the refused fork committed anyway).
