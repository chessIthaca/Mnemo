Symptom: A 429 on a model served with a 200k-window endpoint never fails over to an endpoint serving the same model id with a 128k cap even when the live conversation is 20k tokens — the turn fails once with "no viable alternate" and later turns keep hammering the rate-limited endpoint. Fails safe (no stall, no data loss) but silently disables failover for mixed-window configurations of the same model id (e.g. a proxy capping context below the direct endpoint). Backlog a117e827; fixed in commit 739c68a on wt/agenticcoding (plan de1f874b).

Root cause: try_429_fallback (src/agent/loop_impl.rs) compared context WINDOWS — `alt_cm.max_tokens() < current CM's max_tokens()` — both static configuration values, not the live conversation size. The exact live count (messages + tools-schema overhead) IS computed every iteration at src/agent/turn.rs:314 (token_accounting.update → token_count) before the request that can 429, but it lived in TurnState, dropped when run_turn returns Err.

Fix (final shape, incl. round-1 review HIGH-1): loop-level stash — AgentLoop.live_token_count: AtomicUsize (0 = none recorded), stored right after the turn.rs:314 accounting update, read by try_429_fallback; viability = alt_window >= live + alt_cm.effective_summarize_at() (the alternate's OWN summarize threshold as headroom — immediate serve plus one growth step fits; the alternate's preflight hard-ceiling + compaction remain the last line of defense) OR alt_window >= the current window — the OR keeps every pre-fix acceptance at any fill rate (with fill_rate > 0.5 the headroom bar alone sits below the incumbent's own operating band and would wrongly reject equal/larger-window alternates). Window comparison alone when live == 0. Regression tests: the mixed-window failover test (fails pre-fix), the genuine-overflow reject test, the live=0 window-fallback unit test, and the high-fill-rate regression (verified red on the headroom-only rule).
