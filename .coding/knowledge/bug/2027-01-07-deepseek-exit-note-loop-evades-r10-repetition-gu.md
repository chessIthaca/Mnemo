BUG (2027-01-11 clean-trace repro, plan b2172228; confirms d492ac45's model-degeneration root cause and pins the harness blind spot). Symptom: deepseek-v4-flash "hello" turn (traces.jsonl record id=3) looped 366× on the 69-char unit "Exit note says 'DeepSeek temporarily disabled — exit notes staged. " — 6,194 completion tokens, 64.5 s, ~1 MB SSE, all in the CONTENT channel (0 reasoning tokens despite reasoning_effort:max), until the user cancelled. Request was clean: 8 messages, HTTP 200, and NONE of the loop text in the payload — "REMAINING THOUGHTS", "[released]", "exit note" exist in no request, no code, no memory (pure model fabrication; the model first echoed the trailing volatile-tail RECALLED MEMORIES block — same echo class as OPEN 5cf5469c). Root cause (harness): the R10 guard detect_repetition (src/provider/stream.rs:447) fires only when the accumulated tail is exactly 200-BYTE-periodic (last 200 bytes repeated 3×); this loop's period is 71 bytes (69 chars + em-dash), 71 ∤ 200, so the guard ran on every delta (~5,244×) and could never fire. Secondary gaps: guard accumulates TextDelta only (reasoning-channel loops invisible — backlog 1f56297a); the cancelled turn's 25,679-char loop was persisted as the assistant message and re-injected into every later request. Fix direction: (1) generalize detect_repetition to any period p ≤ 200 with ≥3 consecutive tail repetitions (per-period slice compare on the ≤2 KB bounded buffer); (2) accumulate reasoning_content into the guard buffer too; (3) cap what a guard-abort/user-cancel persists to history. Regression test: unit test that detect_repetition fires on the 71-byte exit-note unit repeated 10× (fails on current code, passes with fix) and does not fire on normal prose; integration test that a streamed loop aborts with "repetition detected". Evidence: .coding/logs/traces.jsonl line 3 (request+response), line 4 msg[7] (persisted loop).
