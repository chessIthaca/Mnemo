Symptom: during the 2026-12-30 unattended run-all batch (backlog 569b5922, plan 593f4a4e), the user asked mid-run to add a backlog item; the run-all session's tool surface had NO backlog_add (backlog_list and backlog_status were present) — the agent could not comply and had to stash the drafted item in memory for a later interactive session to queue. Root cause (verified): the run-all session rides the MAIN agent's normal state-filtered surface — run_all_dispatch_next (src-tauri/src/ipc/run_all.rs:1289) sends a plain AgentCommand::Prompt with no tool-surface restriction (no run-all tool construction exists). All base states already expose backlog_add (the 2026-12-30 reversal, commit 61cc0ab, itself triggered by this incident — "one silently-lost backlog_add"). The remaining hole — the exact reproduction of the reported symptom (status+list present, add absent) — is the Skill allow-list branch (src/tool/mod.rs:505): under ToolFilter::Skill(allowed), backlog_status + backlog_list ride the always-available set but backlog_add did not (unless the skill's list names it). The 61cc0ab reversal explicitly left this unchanged as a scope guard ("backlog_add stays allow-list-only under skills"); plan 8a16bc91 named this item (66c65db9) as the related follow-up. Reachable from run-all whenever an item invokes a skill mid-run (e.g. merge_to_main after completing work on a branch) and the user steers to queue an item. Fix (plan 274af962): add backlog_add to the Skill allow-list always-available set (the item's option 1, "simply add it" — the filter is state-derived with no run-all special-casing, and the loop-prevention concern is already accepted for every base state); the widening applies uniformly to interactive and run-all skill surfaces; the interactive BASE surface is unchanged; the reviewer ROLE filter stays read-only.
