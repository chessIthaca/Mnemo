BUG (verified 2027-01-08, backlog 1db26c95, plan cc92a5d0; supersedes the 2026-12-24 output-rendering record): files containing LLM special tokens (e.g. the GLM end-of-text token, 13 chars) cannot be read-then-written faithfully — the agent's textual view of tool results shows the token position as an empty string, so read-then-write silently corrupts the file. ROOT CAUSE (verified, three legs): (1) live reproduction — a regex search matched 11 lines in 4 files while every displayed line showed the token stripped (matching is Rust-side on raw bytes; the VIEW strips it); (2) app-side clean — Message::tool_result stores plain text, request serialization is plain json!, the stream guard cuts OUTPUT TextDeltas only, no frontend sanitization; (3) server-side confirmed — an echo test (glm-5.3-flash) showed the model perceiving the token position as "a blank line" (U+000A U+000A): the serving layer strips/maps it from request input. FIX: config-driven escaping of known boundary tokens (stop_boundary_strings, resolved per model) in tool-result messages at the request-building layer (both the chat and Responses paths) — a visible, reversible marker ⟦raw:\uXXXX…⟧ (single-pass longest-match escape; the round trip is identity for any token set) — restored on write by the file tools (file_write content AND its append path / file_append, file_edit old_string + new_string; regex-mode old_string restores to a regex-quoted form so the token's | alternation can't change match semantics). REGRESSION TESTS: build_request_json_escapes_boundary_tokens_in_tool_results + build_responses_request_json_escapes_boundary_tokens_in_tool_results (src/provider/openai/tests.rs), file_write_restores_boundary_markers + append_mode_restores_boundary_markers (src/tool/agent/file_write.rs), append_restores_boundary_markers (src/tool/agent/file_append.rs), file_edit_restores_boundary_markers_in_old_and_new_string + regex_mode_restores_boundary_markers_quoted (src/tool/agent/file_edit.rs).
