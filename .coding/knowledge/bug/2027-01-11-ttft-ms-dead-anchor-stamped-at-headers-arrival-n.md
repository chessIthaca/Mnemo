BUG: ttft_ms dead (0 on 99.2% of rows) — headers-arrived anchor (plan 25e8771c, backlog c60869d8, perf review 2026-09-09 L1 / exec summary BUG 2). Symptom: request_stats.ttft_ms is 0 on 99.2% of rows (28,267/28,506, .coding/analysis/cache-hit-5-aggregates.txt) — the first-token metric is dead, so the "fastest agent" goal has no TTFT signal and the trace graph's Waiting bucket (connect_ms) silently absorbs the server prefill/queue wait. Root cause: the ttft anchor `request_start` is stamped when the POST response HEADERS arrive (src/provider/openai.rs spawn_stream :761, comment :756-760; src/provider/anthropic.rs :1344-1345) — LiteLLM and the direct providers only begin the HTTP response when the first token is ready, so headers and the first SSE chunk arrive in the same burst and the measured window (headers→first chunk, openai/stream.rs :291-294, anthropic :1565-1574) is structurally ~0ms. Fix: stamp a POST-send anchor immediately before the first client.post in both provider paths (openai: PreparedRequest.post_sent stamped in open_stream before the first POST, passed through StreamTask; anthropic: post_sent before .post(&url) :1284) and redefine ttft_ms = first-chunk − post_sent at every ttft site; connect_ms keeps its exact semantics (response-headers − record_created). Regression tests: ttft_measures_post_send_to_first_chunk (src/provider/openai/tests.rs, DelayedFirstChunkSseServer) + anthropic_ttft_measures_post_send_to_first_chunk (src/provider/anthropic.rs tests, DelayedAnthropicSseServer) — both red-confirmed ("got 0ms; the old headers-arrived anchor measured ~0").
