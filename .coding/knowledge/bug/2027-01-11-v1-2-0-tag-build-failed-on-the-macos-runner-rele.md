title = "v1.2.0 tag build failed on the macOS runner — release shipped with no assets (fix 4b0764a)"
created = "2027-01-11"
+++

Symptom — two causes, one asset-less release: the v1.2.0 tag build's macOS runner went red (`state_override_survives_429_fallback` exceeded the 10 s `shutdown_agent` window, `src/runtime/agent.rs:2922`), so the release job did not run on that attempt and the published v1.2.0 GitHub release has 0 assets. Fix one: window widened to 30 s (commit 4b0764a, merged 71e214b) and `gh run rerun 36354666875 --failed`. On that RE-RUN windows and macos both went GREEN and the **release job FAILED** — by then a release for the tag had been published by hand ("Latest release with Anthropic and Laya support", id 398297797), and this repo has GitHub's **immutable releases** setting ON (every release reports immutable:true), so the uploads were rejected:
  `##[error]Cannot upload asset Mnemo_1.2.0_x64_en-US.msi to an immutable release. GitHub only allows asset uploads before a release is published, so upload assets to a draft release before you publish it.`
Immutability makes that unrecoverable: v1.2.0 can never gain installers (its tag is locked to that release too). Fix two (the durable one): the release job now creates the release as a **draft** (`draft: true`), so the assets attach before publication, and a following step publishes it (`gh release edit "${{ github.ref_name }}" --draft=false --latest`). Pinned by `tests/integration/ci_workflow.rs::build_workflow_uploads_installers_to_a_draft_release_first` (draft upload must precede the publish step). Verified end-to-end with a throwaway tag/release: draft + asset upload OK, publish OK (the asset survives), a later upload to the published release returns HTTP 422 "Cannot upload assets to an immutable release" — the negative control proving the order matters. Deleting an immutable release (with `--cleanup-tag`) does work, so no scratch release could get stuck.

Consequence for cutting 1.3.0: it must be the first release with installers since v0.1.1. Do NOT create the v1.3.0 release by hand — a hand-published release blocks the workflow's asset uploads; let CI create it as a draft and publish it, then verify the assets.
