Symptom: Three pre-existing bypasses of Sandbox's path-prefix write protection (found in review rounds 2-4 of plan ee65fd4b, 2027-01-11; BUG memory d7ebe9f9, backlog 1a5bffcf). (1) A hardlink inside .coding/ to a protected file (`.coding/x.toml` hardlinked to `.coding/safety.toml`) is not protected by name — canonicalize cannot see a hardlink (no link to follow; the path IS the file) — so any plan kind can truncate the shared inode; `.coding/x.rs` hardlinked to `src/lib.rs` does the same outside-in. (2) A Win32 8.3 spelling (`.coding/KNOWLE~1/new/x.md`) reads as ordinary — aliases are not symlinks, so the per-component case/trailing-dot trim cannot see them — and validate_for_write's create_dir_all resolves the alias and plants a new subtree inside the real `.coding/knowledge/` (overwriting an EXISTING protected file stays impossible: an alias of an existing file canonicalizes to the long name). (3) validate_for_write's step-5 revalidation failure returns the LEXICAL path (`Err(_) => Ok(validated)`), so a write through a link that escapes the root lands outside it — reachable for implementation/bug_fixing plans (the research route was closed by plan ee65fd4b). · regression test: protected_hardlink_inside_coding_refused
