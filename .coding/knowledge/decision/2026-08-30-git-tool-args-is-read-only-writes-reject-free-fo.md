The `git` tool's `args` parameter (src/tool/agent/git.rs, GitArgs) is READ-ONLY by design: status/diff/log forward validated extra flags (denylist in validate_read_args: --output/-o/--exec/--no-index/--ext-diff/--textconv rejected as unsafe), and `branch list` forwards allowlisted read-only listing flags (validate_branch_list_args — an ALLOWLIST, not a denylist, because `git branch <positional>` CREATES a branch and single-arg flags like --set-upstream-to=/--unset-upstream/--edit-description mutate the current branch; positionals refused; only -v/-vv/--verbose/-a/--all/-r/--remotes/--list/-q/--quiet/--no-color/--color=/--format=/--sort=/--merged/--no-merged/--contains/--no-contains/-i/--ignore-case pass; combined short flags must be split e.g. ["-a","-v"] not "-av"). Every other write subcommand (commit/merge/checkout/stash/branch create/branch delete/push/restore) errors loudly on non-empty args (the "args are not supported for git {sub}" error). Rationale (plan 47472e35, refined 2026-09-19 plan 3f3a188c): (1) read queries are where precision is needed and argv is discrete (no shell); (2) write subcommands have structured params (branch/message/remote/action; restore: paths/source/target) instead — free-form flags there could create branches, overwrite files from any ref, or go interactive; (3) the loud error replaced the original defect where serde silently dropped unknown fields. branch list is a read (it only lists branches), so it joins the read-args surface — but with an allowlist since its positionals are dangerous (a positional creates a branch). WORKAROUND for precise restores: use the tool's structured `restore` subcommand (paths/source/target); the shell tool remains the fallback for exotic git forms.
