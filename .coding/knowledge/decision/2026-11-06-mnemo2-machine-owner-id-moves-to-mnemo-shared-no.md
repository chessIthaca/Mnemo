+++
title = "Mnemo2 machine owner id moves to ~/.mnemo (shared, non-virtualized) with one-time app-data migration"
created = "2026-11-06"
+++

Mnemo2 keeps the machine owner id (state-owner-id) in the Tauri app-data dir, which MSIX AppData virtualization splits into a private per-package copy for processes under an MSIX host (Claude Desktop), producing two ids and alternating project-stamp refusals ("was not created by Mnemo2 on this machine") for state Mnemo2 itself created. Root cause and evidence: .coding/analysis/owner-stamp-divergence.md; option comparison: .coding/analysis/owner-stamp-fix-options.md.

DECISION — chosen: move the owner id to the config dir (~/.mnemo, via resolve_config_dir so MNEMO_HOME is honored) with a one-time, first-wins migration from the legacy app-data file. ~/.mnemo resolves from the profile home, not AppData (src/config/mod.rs config_dir_named), so MSIX does not virtualize it; both views demonstrably share it already (mnemo2-mcp.exe, projects.toml, run files, laya logs). Change surface: project.rs gains machine_owner_id_shared(config_dir, legacy_app_data) (copy legacy id in with create_new when the config-dir id is absent, then machine_owner_id(config_dir)); ipc.rs state_owner resolves resolve_config_dir(None) plus the legacy app_data_dir and calls it; the refusal message additionally names both ids and both file paths. The cloned-repository refusal is preserved unchanged: a clone cannot ship ~/.mnemo/state-owner-id, and the existing test shipped_or_foreign_state_is_refused_never_loaded keeps passing. Regression tests: two_app_data_views_converge_on_one_shared_owner_id (two temp app-data views + one temp config dir; red today because the second view resolves a different id and refuses the first view's stamp) and the_legacy_app_data_owner_id_migrates_once_into_the_config_dir (first-wins, never overwrites).

REJECTED — (a) message-only fix (name both ids and files in the refusal): kept as an adjunct, rejected as the fix because the two-id flip-flop and hand-editing recovery remain; (b) user-confirmed "adopt this folder" dialog: rejected because a cloned repository ships exactly "Mnemo2's own state files", so the offer cannot distinguish my-other-view state from a clone's planted lead.json/team.json — one click resumes untrusted history, the injection the stamp exists to prevent, and it ping-pongs on every view switch; (d) second stamp with a stable project id plus a machine registry: rejected because the registry diverges the same way in app-data, and in ~/.mnemo it is just the chosen option plus a second id, a registry file and a two-branch trust rule; (e1) detect MSIX packaged context and only then relocate: rejected as a detection heuristic for hosts we cannot enumerate; (e2) probe the package LocalCache shadow: rejected as hardcoding a package-family path; (e3) do nothing: rejected — every plugin user is one outside-boundary launch away from losing tool access.

Follow-up: open a bug_fixing plan implementing the chosen option with the named regression tests, plus a one-time manual smoke probe (from outside any MSIX package, read a file an inside-boundary instance wrote under ~/.mnemo) to close the untested sharing direction.
