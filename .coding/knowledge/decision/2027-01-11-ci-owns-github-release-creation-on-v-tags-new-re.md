CI owns GitHub release creation (landed with the v0.1.1 release plan e66f3b75): the build workflow's `release` job (.github/workflows/build.yml) creates the release when a v* tag is pushed — needs windows+macos, gated `if: startsWith(github.ref, 'refs/tags/v')` (manual dispatch builds + uploads artifacts but never publishes), job-scoped `permissions: contents: write`, downloads the windows-installers + macos-bundles-aarch64 artifacts, softprops/action-gh-release@v2 with `fail_on_unmatched_files: true` + `generate_release_notes: true`. NEVER create a release for a v* tag manually — an asset-less manual release blocks the CI one (published releases are immutable).

The new_release skill (.coding/skills/new_release.toml, registered live) encodes the procedure: (1) bump the five manifests (src-tauri/tauri.conf.json, package.json, frontend/package.json, Cargo.toml, src-tauri/Cargo.toml) + the About-dialog fallback literal (frontend/src/components/about/AboutDialog.tsx), refresh locks via `npm install --package-lock-only` + `cargo check`; (2) land on main (merge steps with BOTH build verifications, conflict UNION rule, post-merge memory supersede); (3) annotated tag v<version> on MERGED main, push the tag (approval-gated — triggers the ~30-90 min dual-runner build); (4) verify the run started via the public REST API (Invoke-RestMethod on actions/runs?event=push); (5) report URLs. agent.md's branch policy acknowledges the skill's inline sanctioned merge.
