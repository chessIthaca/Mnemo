title = "tool-schema required lists — strict normalization seam, and Ollama filler vs null"
created = "2026-11-02"

Where tool-schema `required` lists come from, and why Ollama-hosted models fill every file_edit key with filler:

- The ONLY code path that puts all properties in `required` is strict-mode normalization: `normalize_for_strict` (src/provider/strict.rs:76-193; required-list rewrite at :182-192) marks EVERY property required and widens optionals to nullable (:139-180). That is the OpenAI strict contract: required-but-nullable is how "optional" is expressed under strict — OpenAI rejects strict schemas with non-required properties, so optional fields CANNOT be un-required there.
- The seam that decides whether it applies: `ToolRegistry::schemas` (src/tool/mod.rs:1441-1499) calls `strict::apply(&mut schema, caps.supports_strict_schema)` at src/tool/mod.rs:1487 — normalization happens only for STRICT_TOOLS members (file_edit and multi_edit are members, strict.rs:251) on endpoints whose capabilities say strict.
- Capabilities: `EndpointKind::Local` (Ollama) → `ProviderKind::Local` → `Capabilities::local()` → `supports_strict_schema: false` (src/provider/mod.rs:82). A per-endpoint override (`endpoint.supports_strict_schema`) threads through src/provider/client_factory.rs:99 → `capabilities_with_overrides` (src/provider/mod.rs:182-184). The Mnemo2 settings wire passes the tri-state verbatim (`None` = auto = the kind default; src/headless/setup/endpoint_detail.rs:95-97 and :355).
- With the default/auto setting, an Ollama Cloud endpoint receives the schema VERBATIM — file_edit's own schema declares `required: ["path"]` only (src/tool/agent/file_edit.rs:861) — and the OpenAI-compat request builders strip the `strict` flag defensively when caps don't support it (src/provider/openai/request.rs:359-364 and :940-945).
- A model that says "the schema's required list includes all of them, so it filled every field" has seen the strict-normalized form — i.e. that endpoint had supports_strict_schema=true. Under strict the model cannot omit keys; it must send null for unused ones. Weak Ollama models emit filler ("placeholder", "", whitespace, 0, []) instead, which used to die in file_edit's validate_ops mutual-exclusion checks; validate_ops now ignores filler-with-note and only rejects a top-level old_string/new_string pair where BOTH halves look like a real edit (ambiguous intent).
- Tool schemas given to models on strict endpoints should say "leave empty or null", never "omit" — omission is impossible under strict, and the contradiction is what drives placeholder filler. Never "fix" the seam by un-requiring fields: that breaks every strict-enforcing endpoint; the knob for a specific weak endpoint is its supports_strict_schema setting.
