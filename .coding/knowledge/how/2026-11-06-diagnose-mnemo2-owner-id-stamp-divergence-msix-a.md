title = "Diagnose Mnemo2 owner-id/stamp divergence — MSIX AppData virtualization under packaged hosts (Claude Desktop) creates two app-data views"
created = "2026-11-06"
+++

Durable fact about Mnemo2 on Windows: the Claude Desktop plugin chain (claude.exe — the MSIX-packaged Claude Desktop app under WindowsApps, package family Claude_pzs8sxrjxfjjc — spawning mnemo2-mcp.exe serve, which spawns mnemo2.exe --hidden) runs inside the Claude Desktop package boundary, where Windows MSIX AppData virtualization redirects AppData\Roaming\com.mnemo.mnemo2 and AppData\Local\com.mnemo.mnemo2 to private copies under AppData\Local\Packages\Claude_pzs8sxrjxfjjc\LocalCache\... . A Mnemo2 instance started outside that boundary (Explorer, Start Menu, plain terminal) sees the REAL store; the two views can hold DIFFERENT state-owner-id values, so the same machine can stamp a project with an owner id that its own hidden plugin instance then refuses ("was not created by Mnemo2 on this machine"). machine_owner_id (src-tauri/src/mnemo2/project.rs) is NOT at fault: it never regenerates over an existing file (create_new fails AlreadyExists -> Err). Diagnosis technique: from inside the boundary, fsutil hardlink list on the real AppData path reveals the redirection (it resolves to the LocalCache object); to read the true real store, spawn a probe via WMI Win32_Process.Create (WmiPrvSE-hosted, outside the package identity). The same hazard applies to any MSIX-packaged host (e.g., a CLI chain under Windows Terminal would get its own package store). Any fix must reconcile the two views while preserving the cloned-repository refusal in open_state_dir.
