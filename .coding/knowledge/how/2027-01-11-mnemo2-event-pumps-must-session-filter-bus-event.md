+++
title = "Mnemo2 event pumps must session-filter bus events (engine-wide bus)"
created = "2027-01-11"
+++

Mnemo2 (src-tauri/src/mnemo2): the headless engine's session event bus is ENGINE-WIDE — `AgentSession::events()` subscribes the one shared bus, and every SessionEvent is tagged only with the raw `AgentId` (u64); there is no per-session bus and `pump_events`/`pump_worker` perform NO session filtering of their own, so each pump receives every session's events (lead sees worker events and vice versa). Any event-driven recording or state mutation in these pumps must filter with `mnemo2::usage::event_session(&event) == Some(session_id)` (a serde round-trip recovers the comparable SessionId from the AgentId newtype; the engine exposes no accessor). Symptom when forgotten: usage reports double-fold (once per listening pump). Related pre-existing quirk: `pump_worker`'s per-worker telemetry (prompt/completion/cached totals) is NOT session-filtered, so two concurrently-live workers each fold the other's Usage events into their own WorkerRecord — a latent pre-existing defect, intentionally left unchanged by the b952eab4 backend step.

Amended 2027-01-11: the ModelChanged observation arms are ALSO session-filtered now (review finding cross-session-model-attribution, commit 5e15687 on wt/agent-projectU): `pump_worker`'s ModelChanged arm only sets `worker.model_id` and `pump_events`'s ModelChanged arm only updates `observed_model` when `event_session(&event) == Some(session_id)`. Without the filter, a concurrent worker's ModelChanged re-pointed another session's observed model, selecting the wrong accumulator row and vendor price for that session's next Usage event. Two engine facts learned while regression-testing this: (1) the engine emits ModelChanged only when a request's serving model differs from the per-loop `served_effective` seed (seeded at turn entry from `resolved_model()` or the provider's `model()`), so a scripted harness produces ModelChangeds only by switching the provider between a worker's seeded first request and its second; (2) a worker's `message_parent` host-tool call triggers a lead auto-turn that consumes the shared scripted LLM queue — interleaving tests must use kernel tool calls (e.g. `read_file`) to keep worker turns alive instead.
