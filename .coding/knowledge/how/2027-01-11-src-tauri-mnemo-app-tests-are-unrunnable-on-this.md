ENVIRONMENT FACT (observed 2026-09-23, repo C:/Mnemo, during plan e3d0758b step 6). `cargo test -p mnemo-app` (from src-tauri/) and `cargo check -p mnemo-app` cannot run here: cargo fails at "failed to run custom build command for mnemo-app" with "could not execute process C:\Mnemo\target\debug\build\mnemo-app-<hash>\build-script-build (never executed) — An Application Control policy has blocked this file. (os error 4551)". EVIDENCE it is environmental, not the change under test: (a) the blocked file is the FRESHLY built build script (mnemo-app-0fa94cf722ff22f0, written 2026-09-23 15:39); (b) the older ones in the same tree (mnemo-app-56ccaaacdb736a52 from 2026-09-12, mnemo-app-9e4cffb9312e406e from 2026-09-13) execute fine when invoked directly, and so do the root crate's freshly built test binaries; (c) the policy hits the NEW executable, so any rebuild of a build script is blocked. The root crate (`cargo test` at the repo root) and the frontend suite (`frontend/: npx tsc --noEmit` + `npm test`) are unaffected and remain the usable verify surface. Consequence for workflow: a plan step demanding src-tauri tests green must report this block instead of pretending to pass; static cover is available instead (grep src-tauri for the changed root API — e.g. no src-tauri code references ApprovalPreview, so adding a variant there cannot break it). To restore: the user must allow-list/trust the rebuilt binaries (Windows Security → App & browser control / the WDAC or AppLocker policy) — not something the agent can or should bypass.
