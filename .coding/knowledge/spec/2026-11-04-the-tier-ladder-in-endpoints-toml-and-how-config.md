+++
title = "The tier ladder in endpoints.toml and how config writes are serialized"
created = "2026-11-04"
+++

endpoints.toml holds five `[[tier]]` entries in fixed order: trivial, routine, medium, high, escalate (escalate has role "escalate"). Each has an id, a name, a definition, models (an ordered `endpoint/model` list), an optional effort and an optional role. They are read through `TierLadder` in src/config/endpoints.rs: ordered, get, pickable, resolve (an empty tier folds down to the nearest tier below with a model), next_up, escalation, first_model, and convert_old_id (for stored data only). The lowest tier must have a model; validate refuses an empty trivial, and endpoint renames or removals that would empty it are refused. On first load a legacy `[tiers]` table (simple→trivial, average→routine, difficult→high) and Mnemo1's `[general.routing]` lane models (cheap, routine, lane_medium, capable+lane_high, escalate) migrate into the ladder; the original config.toml is kept once in `config.toml.lanes.bak` (staged, fsynced, never overwritten while valid). A cached Config save never writes the ladder; only explicit tier writers do, as a read-modify-write. Every write of config.toml, endpoints.toml, keys.toml and mcp.toml, plus the migration and crash recovery, holds an OS exclusive file lock (std File::try_lock) on `<config>/config.write.lock`, retried every 50 ms with a 5 s timeout; inside the lock the `_unlocked` write variants are used. Crash recovery at load time is best-effort: it skips if it cannot take the lock and runs again on the next load.
