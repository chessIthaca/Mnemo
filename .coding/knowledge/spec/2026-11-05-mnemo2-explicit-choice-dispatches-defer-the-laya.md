title = "Mnemo2 explicit-choice dispatches defer the Laya classification to the background"
created = "2026-11-05"
+++

Mnemo2 dispatch routing (src-tauri/src/mnemo2/team.rs): a dispatch with an explicit lead/user tier or model choice never waits for the Laya classification. route_implementation_dispatch returns immediately with a null Laya label (routed_by "lead"); a background tokio task (spawn_pending_classification, spawned from dispatch_locked after provisioning where the real worker id exists) acquires the same routing_permit, runs classify_dispatch under the same 3s timeout, writes the same corpus rows via the shared helpers dispatch_route_row / dispatch_lead_override_row, and attaches laya_tier/confidence/cleared to the worker's routing record when it lands (persisted best-effort; a record gone to cleanup drops the attach silently). WorkerRouting.cleared is bool (false until the label lands), not Option — only laya_tier/confidence are Option. routed_by resolves at dispatch time and stays "lead" for explicit dispatches even when Laya clears a different tier; the override is corpus-only (the LeadOverride row is still written, so every override remains a training label). The dispatch answer prints "Laya: classifying in the background; the label will land on the routing record." while pending. Skip conditions (too_short/one_tier/no classifier) stay inline. Non-explicit dispatch paths gate on the classification exactly as before. Caveat: a background classification holds the routing permit, so a concurrent drift classification can lose its 3s window.
