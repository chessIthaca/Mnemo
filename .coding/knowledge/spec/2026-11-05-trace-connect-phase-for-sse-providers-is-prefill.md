title = "Trace Connect phase for SSE providers is prefill+TTFT, not network connect"
created = "2026-11-05"
+++

Root cause of "every GLM-5.3 call takes ~5.3s in connect status" (investigated 2026-11-05, run r1793901734063-57164-1, provider Adsk via https://alf.aac.adskeng.net/v1/): the trace's Connect bucket is record_created → response-headers arrival (src/provider/openai/stream.rs:47-55 anchors, computed at :308-315), but SSE providers send response headers only WITH the first chunk — the code itself documents this ("perf review L1: headers arrive with the first chunk for SSE providers", stream.rs:52-55). So connect_ms == ttft_ms exactly on all 19 timed calls of the run (verified in .coding/logs/trace-index.jsonl), and the bucket carries the model's prefill + first reasoning token, NOT network connect. It scales with UNCACHED prompt tokens: ~1.4-2.4s at ≤30k uncached, 4.4-6.9s at 75-119k uncached (the user's "5.3s" cluster), 17.7s outlier with mid-stream stalls. NOT retries: backoff_ms null and http 200 on every row; complete_with_retry (src/agent/dispatch.rs:1262) never fired. Practical lever: keep the provider cache prefix warm (the trace tab's compare mode finds the prefix breaker); rows with cached 0 on 100k+ prompts are what make "connect" slow, and the next call re-warms it (rows 14→15, 17→18 show exactly that). The UI phase label ("connection, upload, and server acknowledgement", mnemo2/src/lib/trace.ts:1292) is technically accurate but reads as network time — for SSE providers the server acknowledgement IS the first token. Secondary anomaly: 3 of 22 index rows (ids 2, 12, 20) show prompt 0 and null timing stamps — unidentified capture path; full trace-to-disk logging was enabled 2026-11-05 to catch the next occurrence.
