What Mnemo2 learns for model choice is the decision log `~/.mnemo/laya/training/dispatch_routing.jsonl`, which the kNN overlay (src/agent/route_knn.rs) votes over; the Laya model never changes (0.3.20 has no fine-tune surface). Thresholds need not ship: the Laya check computes them on each machine from the compiled hand set plus the checkpoint (`eval_fingerprint`). src-tauri/src/mnemo2/laya_learnings.rs: a project that has a `.coding/laya/` folder (the opt-in, no setting) keeps `.coding/laya/dispatch_routing.jsonl`, verbatim log lines whose plan_id names a file in that project's `.coding/plans/`; rows from other projects never leave the machine. Export is a union that never removes a line, run after a merge's outcome row (team/merge.rs), never at project open. `.coding/laya/` is lead bookkeeping and merges with `merge=union`. The Mnemo2 installer ships the file as resource `laya/dispatch_routing.jsonl` (src-tauri/mnemo2-app/tauri.conf.json). After a successful lead_open, `spawn_learnings_check` checks the installer copy then the project copy by exact line text: nothing missing means up to date; missing rows and no local-only rows import silently; both mean an offer, and mnemo2/src/components/LayaLearningsSheet.svelte asks "Update Laya's learnings?". Update appends and removes nothing; Not now records that sha as declined so it does not ask again, and a later version asks instead of importing silently. Import only ever appends: RouteKnn tracks the log by byte length, so rewriting the log would corrupt its index. Each machine embeds imported rows with its own embedder. Per-machine decisions: `~/.mnemo/laya/training/learnings_imports.json`. This repo and its installer are public, so the bundle must hold only rows whose text is already public; the seed was scanned for keys, emails and paths (none) and its brief texts appear in the public plan files.
