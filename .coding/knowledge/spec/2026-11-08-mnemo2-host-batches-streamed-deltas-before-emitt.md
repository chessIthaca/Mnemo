title = "Mnemo2 host batches streamed deltas before emitting them; notifications and blocking IO stay off the forwarders and runtime"
created = "2026-11-08"
+++

src-tauri/src/mnemo2/delta_batch.rs: both Mnemo2 event forwarders (lead LEAD_EVENT_CHANNEL, team TEAM_EVENT_CHANNEL, spawned in ipc.rs lead_open) run `forward_batched`, which merges ADJACENT same-kind deltas (TextDelta, ReasoningDelta, ToolCallArgDelta with the same index) of one stream — lead key (generation, agent), team key (worker_id, generation, agent) — and flushes on the stream's next event, a fixed 16 ms deadline from the first pending delta (DELTA_FLUSH), a 64 KiB cap (DELTA_CAP_BYTES; a single larger delta goes out at once, whole), or channel close. Order inside a stream is exact (unlike Mnemo1's DeltaBatcher in src-tauri/src/ipc/events.rs, which re-sorts by kind and is unreachable from the mnemo2 lib). ToolOutputDelta never merges. The window concatenates deltas, so merged events render the same. Desktop notifications: `wants_notification` (Finished, final Error, ApprovalRequest, UserQuestion) spawns `notify_worker_event` as its own task; nothing awaits it in the forwarder. Blocking work moved to spawn_blocking: TeamRuntime::board_snapshot's PlanBoard::list (and it projects only plan_id/plan_step/BoardWorker under the records lock), start_engine's ignore_project_caches git call, memory_view read_record's knowledge-file read.
