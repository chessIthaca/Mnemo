Workers and audits are checked out into reusable folders `<root>/.worktrees/pool-<n>` (lowest free n reused, else max+1; no cap); only the folder is pooled, each worker still gets its own agent branch. A pool is held while a worker record's `worktree` equals it. Release (merge, recovery, delete, start-screen cleanup, rollback) does not remove the folder itself: it checks the worker's branch and a clean tree, detaches HEAD, and clears the record's `worktree`, so the merged branch can be deleted. A SOFT pool cap then trims the FREE pools above the worker slot count — after a release that frees a pool (merge, audit close, delete, cleanup), at the end of set_slots and once at start — by renaming the folder to `.worktrees/trash-pool-<n>-<ms>` and deleting it on a detached thread; see the amendment below for the mechanics, which pools are kept, and the leftover-trash sweep. Reuse = detach at the base, `git clean -ffdx` excluding /target/, node_modules/ and /.coding/codegraph.db*, then create the new branch, so build caches and the code graph stay warm. A dirty, ownerless-attached or unregistered pool is never reused. Confirmed delete discards uncommitted work (reset --hard + clean -ffd, no -x). Legacy `.worktrees/agent-<id8>` records keep the old remove-folder path. Allocation is serialized by TeamRuntime's checkout_pool_lock. Workers build in the checkout's own target/ and never set CARGO_TARGET_DIR (agent.md). Why: cargo keys workspace crates by absolute source path, so incremental reuse needs a stable path; cold `cargo test --workspace --no-run` 156 s vs about 32 s warm in a pool after touching src/lib.rs. Code: src/app/worktrees.rs (pool primitives); src-tauri/src/mnemo2/team/ spawn.rs, audit.rs, merge.rs, control.rs, deletion.rs; src-tauri/src/mnemo2/workbench.rs.

Amended 2026-11-23: Review fix (trimRemoveInsideLocks, 2026-11-23 soft pool cap): the trim no longer deletes a pool inline. After the claim and the free re-check, `trim_pool_checkouts` RENAMES the folder to `.worktrees/trash-pool-<n>-<ms>` (a metadata operation, so no 10-15 GB delete ever runs under merge_lock / checkout_pool_lock / the app-start path; a failed rename leaves the pool untouched and still registered), prunes the now-dangling registration with `git worktree prune`, and hands the trash to a DETACHED thread running `std::fs::remove_dir_all` — which never follows a symlink or junction, so a link's target outside the pool survives. A part-deleted pool can no longer strand: the pool path and its index are free at once, and every trim sweeps leftover `trash-pool-*` folders on a detached thread even when no pool is above the slot count. This supersedes the earlier "`git worktree remove --force` then `remove_dir_all` in place" mechanics. Tests: trim_removes_free_pools_above_the_keep_count, trim_removes_a_pool_whose_link_points_outside_without_following_it, trim_sweeps_leftover_trash_folders, trim_skips_a_pool_whose_rename_fails (src/app/worktrees.rs), lowering_slots_trims_idle_pools_above_the_new_count (team tests).
