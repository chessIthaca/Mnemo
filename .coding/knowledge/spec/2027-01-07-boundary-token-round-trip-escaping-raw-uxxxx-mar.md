SPEC (2027-01-08, plan cc92a5d0, backlog 1db26c95): boundary-token round-trip escaping — the serving layer strips/maps LLM special tokens (e.g. GLM end-of-text) from request input, so the model's textual view of tool results showed the token position as an empty string (read-then-write corrupted token-containing files; 2026-12-24 incident). Fix: the request builders escape configured stop_boundary_strings (per model, endpoints.toml) in TOOL-RESULT messages only — both the chat path (build_request_json, role==Tool Text arm) and the Responses path (message_to_responses_input's Role::Tool arm) — to a visible, reversible marker ⟦raw:\uXXXX…⟧ (every char as \uXXXX min-4 lowercase hex; SINGLE-PASS longest-match escape — emitted markers are never rescanned, so the round trip is identity for ANY token set). The file tools restore markers to raw tokens on write: file_write content + its append path / file_append, file_edit old_string + new_string (regex-mode old_string restores to a regex-quoted form via regex::escape so the token's | alternation can't change match semantics; new_string is replacement text — plain restore). The assistant raw-echo path, user/system messages, and the Anthropic Messages path are intentionally untouched. Module: src/provider/boundary.rs. Regression tests: build_request_json_escapes_boundary_tokens_in_tool_results + build_responses_request_json_escapes_boundary_tokens_in_tool_results (src/provider/openai/tests.rs), file_write_restores_boundary_markers + append_mode_restores_boundary_markers (file_write.rs), append_restores_boundary_markers (file_append.rs), file_edit_restores_boundary_markers_in_old_and_new_string + regex_mode_restores_boundary_markers_quoted (file_edit.rs).
