SPEC (2027-01-07, user report during plan 28bc06a2's review): chat markdown links route through the sanctioned openers — raw <a> anchors are dead under the webview CSP (default-src 'self'), which was the defect. Message.tsx's Markdown components override `a` with MarkdownLink (frontend/src/components/chat/MarkdownLink.tsx): (1) local file hrefs → normalizeLocalFileHref (frontend/src/lib/markdownLink.ts — percent-decode with raw fallback, backslashes→forward slashes, strip leading ./ and / prefixes, strip trailing #fragment; returns null for scheme forms incl. Windows drive letters, protocol-relative //, pure fragments, empty; traversal segments left for the backend sandbox) → openFileInViewer (the Files-tab deep-link, project-relative forward-slash path — the same sanctioned path the write_review_report tool-card chip uses; .coding/ reads pass the sandbox). (2) external http(s) → openExternal (the Tauri shell open — the webfetch URL chip's pattern). (3) non-openable (mailto:, fragments) → plain span, no dead affordance. Local links render as href-less role="button" anchors (no navigation affordance the webview could dead-end on). Regression test: localFileHrefRoutesThroughRequestFileOpen (MarkdownLink.test.tsx) drives the REAL requestFileOpen store action — pendingFileOpen + rightPanelTab "files". Scope: chat messages only — FileViewer preview / PlanProgress / BacklogView markdown links remain raw anchors (potential follow-up).

The URL travels through the store because the child webview's RECT lives in BrowserView — calling ensure from the chat with a guessed rect would MOVE an already-created child. OS browser kept for ctrl/cmd-click and middle-click (MarkdownLink passes `osBrowser: e.ctrlKey || e.metaKey`, plus an onAuxClick middle-button branch); a `browserWebviewSupported()` REJECTION counts as supported (mirrors BrowserView's optimistic mount probe). Local-file (1) and non-openable-scheme (3) behavior unchanged.
