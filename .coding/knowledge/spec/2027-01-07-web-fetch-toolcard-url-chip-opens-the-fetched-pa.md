How the clickable web_fetch chip works (plan 22001355, commit dcda445 on wt/agenticcoding): a web_fetch ToolCard's header chip (webFetchLabel's 60-char truncation) renders as a button that opens the FULL fetched URL in the user's default browser. frontend/src/lib/openExternal.ts is the shared opener (AboutDialog imports it too) — validates http/https via new URL, opens the parsed URL's normalized href through @tauri-apps/plugin-shell (production CSP blocks plain anchors; shell:allow-open granted), logs+swallows errors. webFetchUrl (frontend/src/lib/toolCardPaths.ts) extracts the full untruncated normalized href from web_fetch args (null for other tools/malformed/blank/non-http(s)); ToolCardChip.url carries it; Message.tsx renders the chip button with stopPropagation + ExternalLink icon, and the header's onKeyDown returns early when e.target !== e.currentTarget so chip keyboard activation doesn't toggle expand (also fixes the file-chip keyboard gap). Tests: webFetchUrl block in toolCardPaths.test.ts (normalization + scheme rejection + untruncated-vs-label decoupling).

Amended 2027-01-11: Amended by plan 92b9d0b7 (user request 2027-01-16): the chip no longer opens the fetched page in the system browser by default — its onClick now routes through `openChatLink(url, { osBrowser: e.ctrlKey || e.metaKey })` (frontend/src/lib/openChatLink.ts), which loads the page in the app's own right-panel Browser tab and falls back to the system browser where that tab cannot exist; ctrl/cmd-click keeps the old behavior. The lucide icon changed ExternalLink → Globe (it opens INSIDE the app now) and the title reads "Open <url> in the Browser tab — ctrl-click for your browser". Message.tsx no longer imports openExternal at all (pinned by the source contract in MarkdownLink.test.tsx: the file must contain `openChatLink(url` and must NOT contain `openExternal`); frontend/src/lib/toolCardPaths.ts ToolCardChip.url doc updated.

Amended 2027-01-11: The chip's escape hatch is no longer read from the click event's flags. User report 2026-10-01: ctrl-click on a chat link behaved like a plain click and loaded the app's Browser tab instead of the OS browser — the engine decides a ctrl/middle-click gesture itself (WebView2 raises NewWindowRequested; wry surfaces it to the host only via `new_window_req_handler`, which this app never registers), so the click can arrive with the modifier already consumed. Plan 8d1b8857 added frontend/src/lib/linkGesture.ts: Message.tsx's chip now wires `onMouseDown={(e) => { if (noteLinkPress(e)) e.preventDefault(); }}` and its onClick reads `takeLinkPress() || e.ctrlKey || e.metaKey` (the click's own flags are the fallback only). MarkdownLink.tsx's anchor was changed identically; middle-click is unchanged — it never read a modifier. Pinned by frontend/src/lib/linkGesture.test.ts plus the `escape-hatch press wiring` source contracts in MarkdownLink.test.tsx.
