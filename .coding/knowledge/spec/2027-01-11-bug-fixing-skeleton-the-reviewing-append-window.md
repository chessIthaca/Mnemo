SPEC: The bug_fixing skeleton lock is state-aware (landed 2027-01-24, plan 5f6e593d, commit ec66d5a on wt/mnemo, backlog 37f8631a): update_plan refuses steps REPLACEMENT in every state, and steps APPEND except in Reviewing — the follow-on window, where a review-surfaced fix becomes a checkable appended step instead of a bare context amendment. Invariants: (1) appended steps stay unchecked through the review (complete_step is hidden mid-review; finish never gates on step completion); (2) the resumability gate applies inside the window — appended steps meet the same path-or-marker bar as every other step (step_issue takes bug_skeleton_exempt: bool; the exemption stands elsewhere since the engine refuses those steps anyway); (3) crash-resumption: load_latest derives Executing from an incomplete plan, so a crash mid-follow-on resumes with the appended step as the ACTIVE step; completing it returns to Reviewing (self-healing — the review is never skipped, reviewed=false). Deliberate characteristic (reviewer design note, on the record): finishing with an unchecked appended step also restarts as Executing (not Complete) — the same semantics implementation plans have had since 2026-12-23 (backlog 24e1c98e); a future refinement could have load_latest consult the reviewed flag before is_complete(), a cross-kind change deserving its own plan. The refusal error keeps the "locked 4-step skeleton" phrase and names the alternatives: the Reviewing window, the mid-Executing context amendment (update_plan append=true with context), the create_plan sub-plan. Security: the window cannot dodge the review — the only path to Complete remains finish() (gated on a reviewer-authored PASS report), and reviewers never see update_plan (plan_mutations_allowed(false)). Tests: update_plan_appends_follow_on_steps_in_reviewing_for_bug_fixing, appended_follow_on_step_survives_restart, update_plan_tool_appends_follow_on_in_reviewing_for_bug_fixing, update_plan_tool_gates_appended_bug_steps_for_resumability.
