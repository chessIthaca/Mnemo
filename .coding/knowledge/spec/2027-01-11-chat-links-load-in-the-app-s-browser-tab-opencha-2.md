SPEC (plan 92b9d0b7, user request 2027-01-16, backlog fc812ffe; MERGED into main at 29825bd (29825bdea1e8b4b24568ee8679bdca43b07ed61c) on 2027-01-16 via the merge_to_main skill — branch wt/mnemo deleted, pre-merge tip 1e2e3df, work commit 07c9ea1). An http(s) link clicked in a chat message — a markdown link (frontend/src/components/chat/MarkdownLink.tsx) or the web_fetch URL chip (frontend/src/components/chat/Message.tsx) — loads in the app's OWN right-panel Browser tab (native child WebView2), no longer in the OS default browser.

ROUTING. frontend/src/lib/openChatLink.ts `openChatLink(url, { osBrowser? })`: `new URL` parse + accept ONLY http:/https: (data:/file: deliberately NOT widened even though the tab's normalize_url (src/browser/mod.rs) accepts them; mailto:/fragments/relative never reach the router), then either `openExternal` (osBrowser flag from ctrl/cmd-click or middle-click via onAuxClick, or `browserWebviewSupported()` false = macOS/Linux, where the tab is a red panel) or `useAgentStore.getState().requestBrowserOpen(parsed.href)`. A REJECTED platform probe counts as SUPPORTED (mirrors BrowserView's optimistic mount probe — the tab degrades visibly instead of surprising with an OS-browser launch).

WHY THE STORE (invariant to preserve). The child webview's RECT lives in frontend/src/components/views/BrowserView.tsx, and src-tauri/src/ipc/browser_webview.rs `browser_webview_ensure` CREATES the child on first call but only MOVES/RESIZES it afterwards — so calling ensure from the chat (no rect there) would drag an existing child to a wrong rect. The URL therefore travels: store action `requestBrowserOpen` (useAgentStore.ts ~:894-904) writes disabledTabs(browser filtered) + rightPanelTab "browser" + rightPanelVisible true + pendingBrowserUrl in ONE set; BrowserView's consume effect (deps [pendingBrowserUrl, supported, loadIntoChild]) calls its own rect-aware `loadIntoChild` (browserNormalizeUrl → browserWebviewEnsure(areaRef rect × devicePixelRatio) → browserWebviewNavigate) and clears the request SYNCHRONOUSLY (single-shot; a re-render cannot replay). This mirrors the requestFileOpen → FileViewer pattern.

EFFECT HYGIENE (both fixes came from review). `loadIntoChild` is `useCallback(…, [])` (stable dep; touches only setters + refs + module imports) and is generation-token guarded (`loadToken` ref: `const token = ++loadToken.current;` + `if (token !== loadToken.current) return;` after every await and in the catch) so two links clicked inside one IPC round-trip cannot settle out of order — only the newest chain navigates or writes loaded/error state. `openUrl` (URL-bar Open/Enter) routes through the same function.

TESTS (vitest is node-env — no DOM harness). frontend/src/lib/openChatLink.test.ts drives the REAL store with mocked ./tauri + ./openExternal (routing, disabled-tab reveal, non-Windows fallback, modifier short-circuit, all non-http(s) targets inert incl. data:/file:, probe-rejection default, href normalization) + `?raw` source contracts pinning BrowserView (`loadIntoChild(pendingBrowserUrl)`, `clearPendingBrowserUrl`, browserWebviewEnsure/Navigate, and areaRef.current + getBoundingClientRect so the rect read itself is pinned) and MarkdownLink.test.tsx pins Message.tsx's chip (`openChatLink(url`, no `openExternal`). Scheme cases must be ASYNC + `await flushRouter()` (the store write lands a microtask after the probe) and assert the TAB channel (pendingBrowserUrl + rightPanelTab), not just pendingFileOpen/openExternal — a wrongly-accepted scheme routes to the tab, which the weaker assertions miss. New test files MUST be added to frontend/vitest.config.ts's include allow-list (src/lib/vitestInclude.test.ts fails the suite otherwise).
