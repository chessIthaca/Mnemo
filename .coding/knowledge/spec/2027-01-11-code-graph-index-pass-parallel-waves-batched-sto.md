SPEC (plan 85368a1f, backlog 5a85e36c, commit 575ba94): the code-graph index pass (src/codegraph/mod.rs index_inner) runs in three stages. (1) ONE Store::stored_file_meta() SELECT loads path → FileMeta{content_hash, mtime, has_content} for the whole tree (replacing 3 SELECTs per file). (2) Waves of ≤512 files (WAVE is a MEMORY knob: each UpsertEntry carries the file's full text, 512 × ~1 MB ≈ ~0.5 GB transient; byte-budget packing ~96 MB is the future-work hardening) run on std::thread::scope workers — worker_count() = available_parallelism clamped [1,8]; an AtomicUsize work index assigns jobs; each worker owns a ParserCache (HashMap<Lang, Parser>, lazy per-language, not Sync) and runs extract_job() (the old per-file mtime-fast-path/read/hash/parse logic, zero store access); per-worker outputs Vec<(job_index, UpsertEntry)>; an mpsc channel pulses the coordinator, which drains it INSIDE the scope closure so the non-Send progress callback stays on the calling thread (count monotonic 1..=total). (3) After the wave joins, outputs are placed by job index (application = the walk's sorted order — determinism) and applied via Store::upsert_files (ONE transaction per wave, prepare_cached throughout; per-file upsert_file fallback on batch failure). INVARIANTS any change must preserve: sorted application order; the progress callback never leaves the coordinator thread; the store lock once per wave (readers responsive between waves); workers never touch the store; the wave size bounds memory. extract_file(rel, source, lang) is a thin wrapper over extract_file_with(..., &mut ParserCache); Ctx carries the cache so visit_html's script-block JS sub-parses reuse it. IndexStats.workers records the wave worker count — the load-immune parallelism observable (a wall-clock bound cannot survive the parallel test harness: contention slowed the 500-file fixture to 2,918 ms, past the 2,547–2,802 ms quiet sequential baseline). Measured: repo cold index 89,235 ms → ~67,500 ms (≈1.3×); 500-file fixture ≈2.2×. Remaining bottleneck (future work): the sequential wave-apply — ~380K SQLite row inserts incl. per-line content + FTS tokenization; next lever multi-row INSERT batching. Regression guard: large_fixture_indexes_on_worker_threads (asserts workers > 1, skipped on 1-core); measurement: #[ignore]d repo_index_timing.
