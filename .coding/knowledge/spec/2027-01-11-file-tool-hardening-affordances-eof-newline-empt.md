Backlog c19ec2ff (plan 7446b6dc, branch wt/mnemo, commits b724769, b5d37e1, 83830c8) landed three file-tool hardening affordances:

1. ensure-final-newline (src/tool/agent/file_edit.rs): append mode with an EMPTY/OMITTED new_string adds the file's detected line ending when missing (LF or CRLF), returns an idempotent "already ends with a newline" note when terminated, and a note for empty files. Invariants: never doubles a newline; byte-exact file ending after the edit (append_empty_new_string_ensures_final_newline + append_empty_restores_missing_eof_newline_byte_exactly). The single-mode splice and r-op paths were verified BYTE-FAITHFUL and pinned (single_mode_trailing_newline_edit_restores_eof_newline, edit_ops replace_op_payload_with_trailing_newline_restores_eof_newline) — the 2027-01-25 restore failures were delivered-args newline loss (model/provider emission), not engine trims; the origin correction (maintenance.rs born newline-less at 322139e) is in BUG 330dd32d.

2. ops_present (file_edit.rs): an empty ops array behaves exactly like an absent one at ALL ops-mode branches — prepare_edit dispatch, prepare_edit_append mutual exclusion, execute no-op guard, large_payload_note — so {old_string, new_string, ops:[]} performs the single edit (empty_ops_array_falls_back_to_single_edit). multi_edit's per-file ops STILL errors on [] (ops is the only edit mechanism per entry — no fallback exists).

3. stringified-sequence repair (src/tool/mod.rs + src/agent/dispatch.rs + src/tool/agent/read_files.rs): repair_stringified_sequences runs at the dispatch seam right after drop_stringified_nulls (one schema binding) and splices a CLEAN JSON-array parse into any schema-declared array-typed property whose value arrived as a String (walk mirrors sanitize_stringified_nulls: anyOf/oneOf/allOf, items single + draft-04 tuple, nested properties — so multi_edit entries' inner arrays repair too). parse_stringified_sequence returns (0-based byte position, serde reason) on failure. read_files' recover_files_from_string adds the layered fallback: clean parse → lenient escape-aware brace scan recovering well-formed {"path": ...} specs (a failed candidate may have swallowed later specs — the scan resumes INSIDE its span) → leading NOTE (survives END-truncation) naming recovered/skipped fragments + parse byte position, or a byte-positional error with the expected native-array shape when nothing recovers. Invariant: the seam never touches non-array props or unparseable strings — the tool's own decode or read_files' layer names them.

Red evidence (pre-fix error strings) recorded in the three commit messages: "new_string is empty — there is nothing to append", "ops is empty — provide at least one op", "an argument must be a sequence, not a string". Gate: cargo test --workspace green (file_edit/edit_ops/multi_edit 138 passed; read_files 35 passed; seam suite 12 + dispatch 2).
