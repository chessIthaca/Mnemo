SPEC: Per-instance WebView2 user data folders + same-project warning (plan 5ce69497, branch wt/mnemo, 2027-01-13 — review .coding/reviews/2026-09-13-5ce69497-webview-udf-per-instance-review.md Verdict PASS).

ARCHITECTURE: (1) UDF isolation — src-tauri/src/webview_udf.rs: `pub fn apply(builder: WebviewBuilder<tauri::Wry>, _label)` wraps ALL THREE builder sites (src-tauri/src/main.rs agent-chat ~259, src-tauri/src/ipc/browser_webview.rs ~336 + ~425) and `pub fn install_default_data_dir(app)` runs inside the window-build block BEFORE any WebviewBuilder. A Windows named mutex `Local\mnemo_webview_udf_{hash}` (helper `mutex_name_for` in src/webview_args.rs; CreateMutexW, Win32_System_Threading already in src-tauri/Cargo.toml) decides: fresh acquire = PRIMARY → builder passes through with no data dir → SDK resolves the persistent default %LOCALAPPDATA%\com.mnemo.app\EBWebView (AUMID-resolved; NOT {exe}.WebView2); ERROR_ALREADY_EXISTS = SECONDARY → every webview gets %LOCALAPPDATA%\com.mnemo.app\WebView2\mnemo-<pid> (`secondary_webview_data_dir`, OnceLock `set_webview_data_dir`/`webview_data_dir` — the primary NEVER calls set, so the static stays None all run, never flipped; apply reads the same static → all webviews of one instance share one profile). Mutex handle deliberately leaked (Box::leak) so later instances observe it; failures degrade to primary/default, never block startup. Non-Windows: apply = pass-through (tauri data_directory maps to WKWebsiteDataStore), install = no-op (underscore params, no warnings under deny(warnings)). (2) Same-project warning — src/instance_marker.rs: each launching instance writes <project>/.coding/instance.json {pid, started_at} last-writer-wins; conflict iff marker pid != own pid AND alive; `conflict_for` excludes absent/own/stale; `instance_pid_alive` (src-tauri/src/startup.rs) probes by EXACT PID only (Windows OpenProcess PROCESS_QUERY_LIMITED_INFORMATION, non-Windows `ps -p <pid>`) — name-less so it can never match the host; access-denied OpenProcess → false (warning suppressed — acceptable for a warning-only feature). Read-before-write ordering in main.rs (incumbent read BEFORE own write). Conflict rides the existing StartupSnapshot (`instance_conflict` in src-tauri/src/ipc/startup.rs, runtime field in src-tauri/src/ipc/state.rs); frontend tolerates older backends (`snap.instance_conflict ?? null`). (3) Frontend: frontend/src/components/projects/InstanceConflictDialog.tsx — [Choose another project] → existing ProjectPicker, [Open it anyway] dismisses; registered in frontend/vitest.config.ts include list.

INVARIANTS TO PRESERVE: primary keeps the persistent default profile (cookies/OS-SSO continuity); every additional instance per-pid; marker writes never block startup; the conflict warning must never match the host process; a second env for an in-use UDF with non-identical browser args must never be attempted (that IS the bug class); all Windows-only pieces cfg(windows)-gated, pure helpers platform-neutral (reviewer-verified).

LIVE EVIDENCE (user-verified "first one is white, second one worked"): while a LEGACY pre-fix release build holds the default UDF, the first NEW fixed instance (primary) still blanks — by design, resolves on host restart. The SECOND instance got its own browser set (msedgewebview2 25→31), own UDF mnemo-<pid> (crashpad-path proof), own CDP port, page http://tauri.localhost/ title 'Mnemo'.
