Gist: `<project>/.coding/instance.json` = {pid, started_at}, written ONLY at launch (src-tauri/src/main.rs:328-344, incumbent read BEFORE own write; sole writer `InstanceMarker::write` src/instance_marker.rs:49 — nothing clears or updates it on project switch or exit). Conflict = stored pid != own pid AND `instance_pid_alive` (src-tauri/src/startup.rs:115 — Windows OpenProcess existence probe on the exact pid; cannot tell whether that process is mnemo at all, nor which project it has open; access-denied -> false). Computed ONCE at startup -> runtime ctx (src-tauri/src/ipc/state.rs:155) -> StartupSnapshot -> frontend state (frontend/src/App.tsx:261); dialog rendered while non-null (App.tsx:731), never re-evaluated, never retracted; [Open it anyway] dismisses. Warns, does not lock.

CONSEQUENCE (live friction, user-reported 2027-01-15: "you warned me another instance was on this project; it had switched away"): switching projects restarts the process (src-tauri/src/ipc/projects.rs:201 `tauri::process::restart` — terminated + relaunched, NEW pid), so the vacated project's marker names a DEAD pid and a later launch reads it stale -> no warning. A warning about an instance that has since left therefore means either (a) timing — it was still here when the dialog fired and the dialog then went stale while staying on screen, or (b) Windows pid recycling handed the dead pid number to another live process — the documented benign residual in .coding/reviews/2026-09-13-5ce69497-webview-udf-per-instance-review.md ("recycled pid ... spurious warning only"). Dialog copy ("is already working on this project") over-claims vs the machine truth ("a process with this pid exists"). No conflict is logged anywhere, so a past warning cannot be reconstructed after the fact.

Fix direction (unfiled): re-check/clear the marker (or re-check liveness in the UI) when an instance switches away, and word the dialog as "launched on this project (PID n, HH:MM)" rather than asserting current occupancy.
