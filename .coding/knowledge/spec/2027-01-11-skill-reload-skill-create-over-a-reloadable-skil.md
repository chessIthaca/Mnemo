Gist: two new skill tools over a reloadable registry. (1) `SkillLibrary` (src/skill/mod.rs) = the `.coding/skills/` dir + a live `RwLock<SkillRegistry>`; `read(|r| …)` is closure-scoped so a std guard can never be held across an await; `reload()` builds the fresh registry OUTSIDE the write lock and returns `SkillReloadReport { total, added, removed, names }` (all name lists sorted); `insert(spec)` hot-adds; `#[cfg(test)] SkillLibrary::from_registry(dir, registry)`. The factory now holds `Option<Arc<SkillLibrary>>` (with_skills / skills_handle), and SKillStartTool + the UI's enter_skill read through it; wired at src-tauri/src/main.rs via `SkillLibrary::load(project.skills_dir.clone())` (was `SkillRegistry::load_dir`). (2) Tools in src/tool/workflow/skill.rs, both AutoRun: `skill_reload` (no args — re-reads the dir, reports added/removed/names; allowed in EVERY workflow state, an active skill included via the Skill arm's always-available set; NOT in the reviewer allow-list) and `skill_create` (EXECUTING-only — validates name [a-z0-9_-], lifecycle-only available_in/target_state, non-empty tools/prompt, refuses `write_review_report` and overwrites without overwrite:true, renders header comment + toml::to_string, parses the text BACK before writing, pre-validates its mkdir with `Sandbox::validate_dir_creation` (round-3 fix), then hot-adds; path = library.dir()/<name>.toml, never user-supplied). (3) Enforcement: `ToolFilter::allows` (src/tool/mod.rs) denies `skill_create` under BOTH constructor-granted filters (Skill, Reviewer) — a skill file naming it cannot widen the Executing-only rule; PlanFrozen carries skill_create + skill_reload because it is the advertised surface whenever a plan is active (advertisement ≠ enforcement: a Reviewing call is dispatch-denied). Regression tests: skill::tests::library_reload_reports_added_removed_and_changes, tool::workflow::skill::tests::create_skill_writes_a_loadable_file_and_hot_adds_it, tool::tests::skill_reload_allowed_in_every_state_and_inside_skills, tool::tests::skill_create_allowed_only_in_the_executing_surfaces. Docs synced: src/agent/prompt.rs (Skill-state line), PLAN.md, docs/FEATURES.md, frontend toolCardPaths.ts (+tests).

Amended 2027-01-11: Post-review fixes (report .coding/reviews/2026-09-17-skill-reload-and-create-review.md, verdict FINDINGS 1 high + 2 low, all fixed before the commit). HIGH 1 — skill_create's write is now sandbox-mediated: SkillCreateTool takes a `Sandbox` (the AGENT's, so a worktree agent cannot author into another tree); it refuses a leaf that `std::fs::symlink_metadata` reports as a symlink (a DANGLING link reads as "free" to `Path::exists`, so the write would CREATE the file it points at, outside the skills dir) and then routes through `Sandbox::validate_for_write` like file_write (link-free ladder + `.coding/**` hardlink guard + protected-target re-check on the canonical result). The skills dir is validated BEFORE the mkdir by `Sandbox::validate_dir_creation` — the mkdir itself is the mutation, so the ladder's step-2/2b judgement runs on the DIRECTORY (round-3 HIGH 1 / LOW 2; see the amendment at the end of this record — an earlier revision created the dir first and judged the caller's spelling, which both reviews superseded). LOW 1 — the always-available enumerations in SKILL_FILE_HEADER and the skill_create description now name skill_reload. LOW 2 — `is_shipped_skill` (new pub fn in src/skill/mod.rs) makes skill_create refuse names in SHIPPED_SKILLS: an AutoRun rewrite of e.g. merge_to_main.toml would be silent and permanent (the file is re-seeded only while missing); editing a shipped skill goes through the approval-gated file tools. New regression tests: create_skill_refuses_a_linked_target (hardlink everywhere, symlink where plantable), create_skill_refuses_a_dangling_symlink_target, create_skill_refuses_to_rewrite_a_shipped_skill, shipped_skill_names_are_recognized; the invalid-args test now asserts the skills dir was never created at all (the old read_dir form could not distinguish "nothing written" from "written elsewhere"). Suites after the fixes: root 2397 passed + 16 integration, src-tauri 299 passed, frontend 83 vitest files + tsc clean.

Amended 2027-01-11: Round-3 fix round (report .coding/reviews/2026-09-17-skill-reload-and-create-review-round3.md — verdict FINDINGS 1 high + 3 low, all fixed before the commit). The directory gate no longer walks every component of the caller's spelling: that walk started at the filesystem root, so a link ABOVE the sandbox root refused a perfectly good "skills dir does not exist yet" directory (macOS spells `/tmp` and `/var` as links into `/private` — three `skill_create` happy-path tests failed there), and it dropped the ladder's lexical containment test, so an out-of-root mkdir whose parent chain was entirely missing was waved through. `validate_dir_creation` now judges the DEEPEST EXISTING ANCESTOR, canonicalized: outside the root → `Error::PathOutsideRoot` (the mkdir would leave the project), inside the root → the ladder's step-2b protected-target re-check; a `validate` `PathOutsideRoot` on the dir itself is still kept (a link whose destination exists elsewhere). Everything below that ancestor is absent, so no component there can be a link. Regression tests: `sandbox::tests::dir_creation_gate_allows_a_link_above_the_root`, `tool::workflow::skill::tests::create_skill_works_under_a_symlinked_ancestor`, and `create_skill_refuses_a_linked_skills_dir` now asserts the DIR gate is what refuses ("refused to create"), so it fails without the gate. The gist's item (2) and the round-1 amendment above are corrected accordingly.
