A worker can re-read its own plan as it stands now (and any capability's current OpenSpec spec) with a read-only plan_read tool, every dispatch header tells it so, and a worker that is working is told when the lead records something new on its plan.

Why: a worker gets its plan once, embedded in its dispatch header (`PlanBoard::brief_for` in src/app/plan_board.rs, pinned as "Your task (pinned)"). It cannot look it up again: plan files live on the lead branch and are often uncommitted, so `.coding/plans/<id>.md` is not in the worker's worktree, and worker file tools are confined to the worktree by `Sandbox::validate` (src/tool/agent/sandbox.rs), so an absolute path to the lead checkout is refused. Decisions, interfaces and acceptance scenarios the lead records after dispatch therefore never reach a running worker unless the lead messages it by hand (it happened on 2026-11-05: a clippy decision had to be sent with team_message). The user asked that workers always have a way to read the plan.

Design (decided):
- Plan board (step 1, src/app): the header text is built by one private function shared by `brief_for` (which keeps its refusals for unknown/closed/abandoned plans, missing steps and done steps) and a new `worker_view(id, step)` that returns the same text for the plan as it stands now and refuses only an unknown plan or a missing step (a worker may re-read after its step was ticked or the plan closed). The header gains, right after the `# Plan:` title block, one line: `Re-read this plan at any time with the plan_read tool: the lead may record decisions or interfaces after you start.` A capability reader `read_capability_spec(openspec_dir, capability) -> Result<Option<String>, String>` moves into src/app/openspec (kebab-case name check `^[a-z0-9]+(-[a-z0-9]+)*$`, refuses a linked capability folder or spec.md, NotFound -> None), and `PlanBoard::capability_spec(capability)` calls it with the board's openspec dir. An edit observer: `PlanBoard::set_edit_observer(observer: Box<dyn Fn(&str, &[&'static str]) + Send + Sync>)`; after a successful `update_with_sections` save it is called with the plan id and the kinds that workers can see and that changed, in this fixed order and spelling: "context", "decision", "interface", "steps", "acceptance", "spec changes", "sections". Progress notes, regression_test and landed_design never trigger it. The observer runs after the board's guard is released (never while holding it).
- Team (step 2, src-tauri/src/mnemo2/team.rs): `worker_host_tools` adds `plan_read` (AutoRun, timeout 10 s) with an optional `capability` string. Without it, it returns `board.worker_view(plan_id, step + 1)` for the calling worker's own plan stamp (audit workers use the plan they audit; a worker without a plan gets an error saying it has no plan). With it, it returns the capability's current spec text, or `No current spec for '<capability>' yet.`, or the error. It never reads another plan. `attach_board` registers an edit observer that, for each worker on that plan whose status is working, dispatching or fixing (never idle, completed, in_review or merged), sends through the existing `message` path (sender Lead) the text `Plan <id> changed: new <kinds joined with ", ">. Call plan_read to re-read it before you continue.` The observer must not block: it spawns the sends on the runtime and holds no team lock while the board calls it.
- src-tauri/src/mnemo2/specs_settings.rs `capability_spec` (the Plan tab command) switches to the shared `read_capability_spec` in step 2, keeping its tests.

This plan creates the OpenSpec capability `worker-brief` through its ADDED spec changes.
