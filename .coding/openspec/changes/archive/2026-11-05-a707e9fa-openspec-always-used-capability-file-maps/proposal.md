OpenSpec becomes enforced, not encouraged: plan_create refuses a plan whose steps touch a capability's governed files unless the plan carries a spec delta for that capability or an explicit no-spec-impact declaration with a reason — with the four existing capabilities' maps authored from evidence, and new capabilities required to declare their governed files at birth.

Why: the user asked (2026-11-05) to make sure OpenSpec is always used. Today spec deltas are encouraged but never required, and the gap is real: the entire LLM trace feature shipped with no capability spec at all (.coding/openspec/specs/ held only dispatch-routing, external-lead, tier-ladder, worker-brief until the llm-trace delta landed with plan fdc334b4). The fix is tooling enforcement in the established refusal style.

Design (decided): (1) A capability-to-files map lives in .coding/openspec/config.yaml under governed_files (the file is seeded and committed — dispatch-routing's map is authored from today's verified work; external-lead, tier-ladder and worker-brief are empty lists the worker fills with per-requirement file evidence). src/app/openspec/schema.rs's OpenSpecConfig already loads config.yaml with unknown-key tolerance — the governed_files field joins it as a parsed field. (2) The plan validation already extracts the file paths a plan's steps name (the "plan too thin" path checks prove it) — the gate intersects those paths with the map: for each hit capability without a spec delta on the plan, plan_create REFUSES with guidance naming the capability and both remedies (attach a delta via plan_create spec_deltas / plan_update, or declare no spec impact explicitly with a reason). The refusal follows the memory-search gate precedent (team.rs:2745-2778 external_plan_create_refusal, wired at mcp_server.rs:1145-1197). (3) The escape hatch: plan_create gains an optional explicit no-spec-impact declaration carrying a reason (the worker designs the exact field shape and updates the tool schema where the plan-board tool definitions live). (4) plan_update add_steps runs the same gate so steps added later cannot bypass it. (5) A spec delta that creates a NEW capability must declare its governed files (the worker adds plan-board's own map entry — dogfooding the rule).

Anchors: src/app/openspec/schema.rs (OpenSpecConfig, config.yaml loading), src/app/openspec/capability_spec.rs (the spec reader), src-tauri/src/mnemo2/mcp_server.rs (the plan_create branch + refusal plumbing), the plan validation site that extracts step file paths (locate via the "plan too thin" message), .coding/openspec/config.yaml (the seeded map).

Constraints: warning-free build (#![deny(warnings)], no #[allow] on rustc warnings); doc comments on public items; PowerShell — read $LASTEXITCODE or the test-result lines, never a piped exit code. The gate must not block plans touching only un-governed files, and empty map lists mean no gating for that capability until filled.
