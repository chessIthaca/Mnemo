Every worker records and is told the lead commit it starts from. An idle worker with no commits follows the lead branch, and one with commits is reported stale and never rewritten. Agent tiers carry a Claude effort. Fix rounds verify with targeted tests while Mnemo runs the full checks once at the reviewed tip, through the machine's heavy-command slots. A model that hits its usage limit is skipped until it resets. Two load-sensitive tests stop failing falsely.

WHY. (1) In a FactoryGame session on 2026-11-22, Claude Code agents started with `isolation: worktree` got a stale base (the session's first commit instead of the lead tip) and bypassed Mnemo's review, checks and merge gate. Mnemo's own pool checkouts already fork from the lead branch tip at every dispatch (src/app/worktrees.rs reuse_pool_checkout: `git switch --detach <lead branch>`, then `git switch -c <branch>`), and since plan e21c4820 agent tiers run Claude agents in those same pool checkouts. What is missing is that the base is neither recorded nor shown, and a worker that waits (for read_back answers, a resume or a fix round) is never brought up to date or flagged. (2) Plan e21c4820 step 1 was slow and expensive. Every fix round reran all four checks (6-8 minutes each, about 6 times), because the shared worker preamble says to run run_checks before every report. The lead's own full-suite runs bypassed the machine heavy slots and failed falsely under load. A provider usage limit (the Ollama Cloud glm-5.3 weekly limit) and a provider overload cost manual reroutes. Five audits ran one after another.

DECISIONS (settled; don't reopen):
1. Base commit: WorkerRecord gains `base_commit: Option<String>` (full sha; serde default None; skipped when None). provision_worker sets it from the `base_tip` it already reads (spawn.rs ~190). After provisioning, the worker's opening prompt ends with the line `You start at <short> (<subject>), the tip of <lead branch> when you were dispatched.`, where short is the first 8 hex digits and subject is `git log -1 --format=%s <sha>`. An agent's prompt embeds the opening prompt, so it carries the line too. When a dispatch has no plan (opening_prompt None), the opening prompt becomes the brief followed by a blank line and that line.
2. Refresh guard: it runs (a) in control.rs message_inner_with_kind, before a prompt reaches the IDLE live session of an implementation worker (it never runs for a steer to a busy session), and (b) in dispatch_locked's re-dispatch path, before `start_worker(existing)`. It fast-forwards only when all of these hold: the worker's branch tip equals base_commit (no commits of its own), its worktree is clean (`git status --porcelain` empty), and the lead branch tip differs from base_commit and descends from it. It then runs `git merge --ff-only <lead branch>` in the worktree, sets base_commit to the new tip, persists, and prefixes the delivered text with `[From Mnemo2] The lead branch moved: your checkout was fast-forwarded to <short> (<subject>).` followed by a newline. In every other case nothing changes. Never rebase, reset or merge non-fast-forward. A git error leaves the worktree as it is, delivers the prompt unchanged, and logs with eprintln.
3. Stale report: stale_base is the count of lead-branch commits missing from the worker branch (`git rev-list --count <worker branch>..<lead branch>`, run in the lead root). It is computed for implementation workers that have a branch and are not Merged, Merging or Cancelled, and shown only when greater than 0. team_status (compact and detail) adds `"stale_base": N`. team_check and team_merge results append the line `stale base: the lead branch has N commit(s) this branch does not; the checks ran without them. Rebase or merge deliberately if they matter.` team_merge still merges with --no-ff exactly as today. Nothing is ever refused because of a stale base.
4. Uncommitted lead files: when the lead checkout has uncommitted paths (modified, added or untracked) under `.coding/`, outside `.coding/plans/`, `.coding/reviews/`, `.coding/knowledge/` and `.coding/laya/`, the dispatch result carries a `warnings` array (in the text JSON `result` and in `data`) with: `The lead checkout has N uncommitted file(s) under .coding/ that this worker's checkout will not contain: <first 5 paths, comma separated>[, ...]. Commit them first if the worker needs them.` Those four folders are excluded because Mnemo serves plans, reviews, knowledge and routing from the lead's own store. This is a warning only; a dispatch is never refused for it.
5. Agent effort: Tier gains `claude_agent_effort: Option<String>`, with values exactly low, medium, high, xhigh or max, allowed only when claude_agent is set. Validation errors: `tier '<id>': claude_agent_effort '<v>' must be one of low, medium, high, xhigh, max` and `tier '<id>': claude_agent_effort needs claude_agent`. TierDto gains the same field (wire key `claude_agent_effort`, null when unset). WorkerRecord gains `claude_agent_effort: Option<String>` (serde default). The dispatch `claude_agent` block gains `effort` (a string, or null). The tier guidance suffix is `; runs as a Claude Code agent (<model>, <effort> effort) when Claude Code leads` when an effort is set, and stays exactly as today when not. The TS preview produces the same line byte for byte. UI: an "Agent effort" select beside Run as, visible only when Run as is a Claude Code agent, with options in this order: "Default" (null), "low", "medium", "high", "xhigh", "max". Choosing "Mnemo models" in Run as clears it.
6. Mnemo-run checks: a new lead tool, `team_run_checks {worker_id?: string}`.
   - With worker_id: refused unless the worker is an implementation worker with no busy live session, no proof and no check run in progress, and is not Merged, Merging or Cancelled.
   - It runs every `.coding/checks.toml` command (the allow-list load_check_commands returns, spawn.rs:63), in order, in the worker's worktree, through the machine heavy slots, on the same path the worker's run_checks tool uses.
   - It records each command as a check on the tip that was current when the run started: name = the exact command; status = passed or failed; detail starts with `run by Mnemo:`, then the exit code, the run time and the failing lines run_checks extracts.
   - If the tip moved before the run finished, it records nothing and says so in the notice.
   - It returns at once. A notice follows: `[TeamManager notice — not the human] worker_id=<id>`, then `Mnemo ran the checks for <id> at <short tip>: N passed, M failed.`, then one line per command, the failing lines, and the next move: `Merge it with team_merge.` when all passed, otherwise `Route the failures with team_route_fix.`
   - Without worker_id: the same run in the lead checkout (an integration check). Nothing is recorded, and the notice names the lead branch and its tip instead of a worker.
   - While a worker's run is in progress, team_merge, review_fix, team_message, team_resume and team_route_fix refuse that worker with `Mnemo is running the checks for <id>; wait for its notice.`
   - Automatic start: when team_review records a review with no open findings at tip T, and T lacks a passed check for at least one checks.toml command, Mnemo starts the run itself, and the team_review result appends `Mnemo is running the missing checks at <short T>; merge after its notice.`
7. Fix rounds verify narrowly: route_fix_brief (nudge.rs:338) replaces its last sentence with `Commit fixes for every finding above. Verify them with the narrowest tests that cover your change (for example the touched crate's tests or the tests the findings name), not with run_checks: Mnemo runs the full checks once at the reviewed tip. Report the commit and the tests you ran for delta review.` The shared worker preamble in src/agent/prompt.rs stays as it is, because Mnemo1 uses it too.
8. Usage limits:
   - Classifier: `pub fn is_usage_limit(error: &str) -> bool` in src/provider/error.rs. Case-insensitive, it is true when the text contains any of "usage limit", "quota", "insufficient_quota", "credit", "billing" or "exceeded your current", and contains neither "overloaded" nor "temporarily".
   - A worker failure whose error is a usage limit marks the model the worker ran on as unavailable for 6 hours. This lives in memory only and is never persisted.
   - current_models() (routing.rs:379) leaves out unavailable models, so tier resolution, fold-down, tier guidance and audits all skip them.
   - The failure notice appends `Mnemo marked <model> unavailable until <HH:MM local time>; the <tier> tier now runs on <fold target spec, or "no model">.`
   - In routing mode auto, Mnemo then resumes the failed worker on its tier, re-resolved so it folds, keeping its transcript (the same path team_resume with a tier takes). It messages the worker `[From Mnemo2] Your previous model <old spec> hit its usage limit; you are now on <new spec>. Run git status and git diff --stat to see where you were, then continue your task.`
   - Outside auto mode, the notice ends with the exact call to make: `team_resume worker_id=<id> tier=<tier>`.
   - A worker whose tier has no fold target stays failed.
9. Load-tolerant tests: cosine_pool_ranks_5000_rows_under_200ms_in_debug (src/memory/tests.rs ~4660) times the best of 5 passes against the same 200 ms budget. slot_wait_is_not_counted_as_silence (src/tool/agent/shell.rs ~1917) keeps proving that a slot wait longer than the silence window is not counted as silence, but its part after the spawn must not depend on how fast PowerShell starts.
10. Tiers: the high tier's only model (Ollama Cloud glm-5.3) is out of its weekly quota until it resets, so this plan names medium, routine or escalate explicitly instead of letting Laya pick high.
