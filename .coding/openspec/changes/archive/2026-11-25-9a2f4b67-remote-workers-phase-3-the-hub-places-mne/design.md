## Decisions

- 2026-11-25: no spec impact: Step 1 is a no-code research step that only reads the governed files. The placement behaviour change is carried by the dispatch-routing delta attached here; external-lead, tier-ladder and worker-brief requirements are unchanged (remote workers keep the same lead attach flow, tier ladder and brief contents). Any further delta is added with plan_update when the implementation steps are recorded.
- 2026-11-25: Phase 3 design from the research step, with lead edits. (1) Typed knowledge on a node: new engine flag worktree_knowledge(true), set only by the node engine, writes typed records into <checkout>/.coding/knowledge so they travel with the branch; hub unchanged. (2) One per-node event demux on the hub via new NodeHandle::events_from/last_event_seq (events() replays from seq 1 today). (3) Hub state lives in <config_dir>/hub/ behind an exclusive hub.lock: one hub per machine; other app instances refuse team_hosts. The project travels per call as a 12-hex project key, not per pairing. Default port 47310 (falls back to an ephemeral port if busy, persisted in hub.json); bind 0.0.0.0 only after the first pairing. (4) src-tauri/Cargo.toml's mnemo dependency gains the remote feature. (5) Counted checks get remote-aware _at variants; old signatures stay as local wrappers. (6) The hub injects no OS/shell text today; decision 7 reduces to running proofs on the node plus a guard test. (7) TeamRuntime::attach_board becomes pub for the e2e. (8) Remote workers do NOT count against the local slot setting; each host has its own slots (mnemo2-node run --slots, default 2). (9) LEAD EDIT: the Windows-only placement rule reads ONLY the project's check commands (powershell/cmd/.ps1/.bat/.cmd), not brief or plan text, because plan context in this project routinely names PowerShell and cfg(windows) and would pin everything to Windows hosts; a lead who knows work is Windows-only pins host. (10) The acceptance text's "team_check" means the tool team_run_checks.
- 2026-11-25: added step 9 (Integration check) because steps 1 and 2 ran in parallel
- 2026-11-25: Step 4 read-back answers: (1) a host's qualification fails only on an environmental failure (command not found and the like); red tests at lead HEAD still qualify it. (2) When synced_tip is missing, the offline-past-budget text falls back to the base commit ("from its starting commit {short} (nothing was synced from {name})"). (3) The reconciler releases a node checkout only when no record names it, it is on a wt/agent-* branch, and it is not a running qualification; release errors are only logged. (4) push_commit asks repo.have for [sha, base_commit, shadow tip]. (5) ShadowSync.dirty is the NODE's uncommitted-path list (FetchStart.dirty or TipAnswer.dirty), which step 6's merge refusal uses; a dirty hub shadow is a hard sync error, not part of the struct. (6) PairOffer.expires_ms is absolute Unix ms; tests override the outage budget through a cfg(test) setter; sync_remote forces the sync.
- 2026-11-25: From the step 4 audits, binding for step 5. (a) Dispatch is unprotected from the reconciler while it prepares a node checkout: the checkout already sits on a wt/agent-* branch, but record.remote is not stored yet. Step 5 must register the checkout before calling prepare_checkout, by adding a RemoteWorkers::reserve(node_id, checkout_branch) / release_reservation pair that the reconciler skips (or by storing record.remote with an empty checkout first and skipping branches named in any record). It must also insert the live entry well within one reconcile period (60 s), because orphan sessions are closed on the second pass. (b) mark_host_restarted and fail_lost_host must re-check the record's status under the records lock and leave terminal states (Completed, Merged, Failed, Stopped) untouched. Step 5 owns this edit in team.rs. (c) requires_windows: add "pwsh.exe" to WINDOWS_SHELLS, and match .bat/.cmd/.ps1 only as a whole-token suffix, so that `bats tests/e2e.bats` is not Windows-only. Step 5 may make this one edit in team/remote.rs plus its test.
- 2026-11-25: Refines the step 4 audit decision (b): when a host restarts or stays away past the budget, only a worker in an active state (running a turn) is moved to Interrupted or Failed. A worker that is Completed (waiting for review), in review, merged, failed, stopped or already interrupted keeps its status and error, so a finished worker stays reviewable and mergeable from its shadow. In every case the live entry is removed and the pump aborted, because the host session is gone, which frees the host slot.
- 2026-11-25: For the integration check (step 9): the step 8 e2e saw the hub's WorkerRecord.transcript empty ({"messages":[]}) for the remote worker right after it became Idle or Completed. Local workers get it from the pump's post-turn snapshot refresh (pump.rs ~:1655, session.snapshot()); a remote worker's snapshot travels over NodeHandle::snapshot. Step 9 must find out whether the refresh simply had not landed (test timing) or the remote snapshot is empty (a product gap: team_resume host:"local" and resumes on the node would start without the conversation). If it is a gap, fix it with its own step and a test that waits for the refresh and asserts a non-empty transcript on the hub record.
- 2026-11-25: Empty-transcript investigation: not a product gap. The remote snapshot carries the transcript: SessionSnapshot.transcript has no serde skip, the node's session.snapshot serializes the engine snapshot, and src/remote/node.rs snapshot_and_close_and_wait_over_link asserts a non-empty transcript over the real link. The pump fills WorkerRecord.transcript from session.snapshot() in its tracked post-turn refresh task, so the step 8 e2e read the record before that task landed. Step 11 adds a guard to the e2e that waits for the hub record's transcript to become non-empty.
