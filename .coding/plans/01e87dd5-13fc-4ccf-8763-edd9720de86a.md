# Plan: git commit respects existing staging (no blanket add -A)

## Goal
Make the `git` tool's `commit` subcommand respect existing staging: only auto-stage (`git add -A`) when nothing is already staged, so a deliberate selective `git add <files>` via `shell` is not overridden. Backward-compatible (common case still auto-stages).

## Kind
implementation

## Context
Root cause (documented in HOW memory + .coding/knowledge/how/2026-08-26-git-tool-commit-auto-stages-everything-use-shell.md): the `git` tool's `commit` subcommand (src/tool/agent/git.rs, commit arm ~line 520) runs `git add -A` UNCONDITIONALLY before `git commit -m`. This silently overrides selective staging — when an agent (or skill) deliberately stages a subset via `shell` (`git add <specific files>`), then calls the `git` tool to commit, it re-stages EVERYTHING (all untracked + modified files), sweeping in stray files from other branches. This caused the toolcard-dedupe commit-hygiene bug (stray branch-policy .coding/ files swept into the wrong commit). Fix: only auto-stage when nothing is already staged (`git diff --cached --quiet` exits 0 → nothing staged → auto-add; exits non-zero → something staged → commit only what's staged). Backward-compatible: the common case (agent calls `git commit` with nothing staged) still auto-stages everything. Frontend test: `npm test` (vitest run) in frontend/ is N/A — this is Rust. Test command: `cargo test` (root, unpiped, read $LASTEXITCODE per project rules). The git tool tests are in src/tool/agent/git.rs mod tests (~line 662+).
