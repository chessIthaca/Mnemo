# Plan: Window rendering cost: throttled streaming markdown, windowed conversation lists, lazy Graph and Trace views

## Goal
A streaming reply no longer re-parses its whole markdown on every chunk, long lead and worker conversations render only their newest entries until asked for more, and the Graph and Trace views (with d3-force and the trace code) load when first opened instead of at startup.

## Kind
implementation

## Context
WHY. The 2026-11-07 Mnemo2 performance review found: PERF-4 — every streamed `TextDelta` appends to the entry body and `Markdown.svelte` re-runs `renderMarkdown` (markdown-it + DOMPurify + highlight.js over the whole text, mnemo2/src/lib/markdown.ts) on every change, so a long reply costs O(n^2) on the webview's main thread; PERF-9 — `LeadChat.svelte` and `WorkerThread.svelte` render every entry with a keyed `{#each}` and no windowing, so a 6-hour session's DOM and per-update diff grow without bound; PERF-10 — the production bundle is one ~920 KB JS chunk because App.svelte statically imports every view.

WHERE.
- mnemo2/src/components/Markdown.svelte: `source` prop, `$derived.by` html with a one-entry cache, a `$effect` that re-decorates repo paths after each render. Used by LeadChat (lead replies, team messages, reviews), WorkerThread, PendingPrompt, PlanTab, MemoryView, TraceResponse, WorkerDetail, WorkerInbox. Tests: mnemo2/src/components/Markdown.test.ts.
- mnemo2/src/components/LeadChat.svelte: `const entries = $derived(...)`, `{#each entries as entry, index (entry.id)}` inside `.lead-entries`, uses `entries[index + 1]` for neighbour classes; scrolling via `createStickToBottom` (mnemo2/src/lib/stickToBottom.ts). Tests: LeadChat.test.ts.
- mnemo2/src/components/WorkerThread.svelte: snippet `threadMessages` with `{#each worker.messages as entry (entry.id)}`; an `$effect` resets per-worker state when `worker.id` changes (`lastWorkerId`). Tests: WorkerThread.test.ts.
- mnemo2/src/App.svelte: static imports of CostView, GraphView, MemoryView, TraceView (lines ~5-15) rendered per tab (~47-55). Tests: App.navigation.test.ts, App.openWorker.test.ts, GraphView.test.ts, TraceView.test.ts.

DECISIONS.
- Streaming throttle lives in Markdown.svelte itself, keyed on "the new source extends the shown one" (pure appends): appends re-render at most every 150 ms (the last one within 150 ms of the final chunk); any other change renders at once. No per-call-site streaming flag.
- Windowing is a simple tail window (newest 200 entries) with a "Show earlier messages" button that grows it by 200 — no virtual scroller, so stick-to-bottom and the keyed `{#each}` keep working unchanged.
- No `manualChunks`: the bundle is served from local files inside the app, so splitting statically imported vendors adds files without deferring any parse work; only lazy-loading a view defers its code.

VERIFY (in `<worktree>\mnemo2`): `npx vitest run`; svelte-check through the main checkout's shim: `& C:\mnemo\mnemo2\node_modules\.bin\svelte-check.cmd` (read $LASTEXITCODE; npx cannot resolve svelte-check in a worktree); `git diff --check`. Step 3 also runs `npx vite build` (not `npm run build`, whose svelte-check step fails in worktrees) and lists the produced assets.

## Acceptance scenarios
- While a long reply streams, its markdown is re-rendered at most about every 150 ms and the final text appears within 150 ms of the last chunk; a replaced (non-append) text renders at once.
- A lead chat or worker thread with more than 200 entries renders the newest 200 plus a 'Show earlier messages (N hidden)' button that reveals 200 more per click; switching workers resets the worker thread to 200.
- npx vite build emits TraceView and GraphView as their own chunks, loaded only when their tab is opened, and the main chunk is smaller than the previous ~941 KB.
- npx vitest run and svelte-check pass.

In Markdown.svelte's script (keep the props, `container`, `decoratePaths`, `handleClick` and the decorate `$effect` as they are): ```ts import { onDestroy, onMount, untrack } from "svelte"; /** Streamed text grows by appends; re-render it at most this often. */ const STREAM_RENDER_MS = 150; let shown = $state(untrack(() => source)); // the source the html was rendered from let lastShownAt = 0; // Date.now() of the last `shown` change; 0 so the first change renders at once let pending: ReturnType<typeof setTimeout> | null = null; function show(next: string): void { shown = next; lastShownAt = Date.now(); } function cancelPending(): void { if (pending !== null) { clearTimeout(pending); pending = null; } } $effect(() => { const next = source; untrack(() => { if (next === shown) return; const appended = shown.length > 0 && next.startsWith(shown); const since = Date.now() - lastShownAt; if (!appended || since >= STREAM_RENDER_MS) { cancelPending(); show(next); return; } if (pending === null) { pending = setTimeout(() => { pending = null; show(source); }, STREAM_RENDER_MS - since); } }); }); onDestroy(cancelPending); ``` and the existing `html` derivation reads `shown` instead of `source` (keep its one-entry `cachedSource`/`cachedHtml` cache). Use `Date.now()` (faked by `vi.useFakeTimers()`), not `performance.now()`.
