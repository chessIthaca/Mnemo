# Plan: Plan-only default tools + cleanup inactive subagents on new plan from Complete

## Goal
(1) All right-panel tools start disabled except Plan; right panel opens on Plan. (DONE in frontend. (2) On Complete→Planning (a fresh plan from Complete), clean up only INACTIVE subagents — cancel each non-running subagent so it exits and its tab disappears; never touch running subagents.

## Context
CORRECTION to requirement 2: on the Complete→Planning transition, only INACTIVE subagents are cleaned up — never stop/cancel a subagent that is currently running. Active (running) subagents are left untouched; they finish on their own and are removed later via the existing `Exited` forwarder path. So cleanup = send AgentCommand::Cancel to each registered subagent whose is_running() == false (and is not the main agent). Running subagents stay.

Mechanics confirmed from exploration: AgentManager has list()/get()/parent_id()/remove()/set_running(); AgentHandle.is_running() and parent_id exist. AgentCommand::Cancel makes the AgentTask emit Finished{Stop} then break → Exited → the forwarder (events.rs Exited case) calls mgr.remove(agent_id) + agent_loops.remove + pending_approvals cleanup + emits the Exited event to the frontend. So if I send Cancel to inactive subagents, the existing Exited machinery removes them from the manager and the frontend sees Exited and should drop their tab.

The Complete→Planning transition is detected in the event forwarder: when a `create_plan` tool result lands and the agent's new WorkflowState is Planning while it was Complete before. But the forwarder doesn't currently track prior state per agent. Simpler + cleaner: detect the transition at the source — in src/agent/mod.rs where WorkflowStateChanged is emitted after create_plan — but mod.rs is core lib with no AgentManager access. Best place: the forwarder (events.rs) since it has the manager_arc and sees WorkflowStateChanged. Need a per-agent "previous state" map to detect Complete→Planning (or Complete→Executing since create_plan goes to Executing... wait: create_plan transitions to Executing, not Planning). Re-check: WorkflowState::create_plan sets state = Executing. So the transition on a fresh plan from Complete is Complete→Executing, not Complete→Planning. The user said "switching from complete into plan mode" — meaning starting a new plan after Complete. So detect: prior state was Complete and the new event is WorkflowStateChanged with state Executing AND it came from a create_plan tool (not a step completion). Distinguishing create_plan's Executing from a sub-plan-pop-to-parent's Executing: a fresh root plan clears the stack (state was Complete/Planning, not Executing). So: if previous workflow state for this agent was Complete and now Executing → it's a fresh plan from Complete → clean up inactive subagents. Keep a prev_state HashMap<AgentId, WorkflowState> in the forwarder.

Frontend (requirement 1, already done): disabledTabs = all except plan; rightPanelVisible = true; rightPanelTab = "plan". Frontend (requirement 2): handle the Exited event for subagents — drop the agent from agents/agentNames/agentParents/workflowStates; if it was activeAgent, switch to main agent. Check the current Exited handler in useAgentStore.ts.
