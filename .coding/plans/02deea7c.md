# Plan: Laya failure triage — classified retries without model roundtrip + startup fine-tune

## Goal
At every failure-handling site (tool-execution cap src/agent/turn.rs:828, bad-JSON repair loop :3199, provider turn-attempt loops — BOTH the inner complete_with_retry in src/agent/dispatch.rs:997 and the outer run_turn_attempt in src/runtime/agent.rs:514), classify the error text with the item-1 Laya Classifier as a choice question (transient / permanent / needs_user / flaky_test) and HARNESS-ACT on confident classifications: auto-retry re-runnable read-only tool calls without a model roundtrip, feed classified guidance otherwise, escalate/park immediately for needs-user/permanent provider errors (marker in the error text so both retry layers skip), and name the class in abort messages — all confidence-gated (≥0.80) behind a new opt-in LayaConfig flag `failure_triage`. Log every classified failure with its true disposition (did the retry succeed?) to a JSONL training log (one row per failure, resolved when the outcome is observable). On startup (managed mode + new opt-in `auto_finetune`), check the accumulated labeled rows against the last-fine-tune marker and, when ≥50 new rows accrued, run the Laya fine-tune via the managed venv and hot-swap the served checkpoint (runner probes for the training surface — laya 0.3.20 ships none, so an ineligible run exports the dataset + skips cleanly). With Laya disabled or the flags off: byte-identical behavior.

STEP 4 FINDING (measured 2027-01-25, plan 02deea7c): there are TWO provider retry layers, and a classifier skip must cover BOTH. (1) INNER — `dispatch::complete_with_retry` (src/agent/dispatch.rs:997, `for attempt in 0..3`, called from `request_stream` src/agent/turn.rs:2572): retries retryable errors 3× with jittered backoff; skips serialization bugs / is_non_retryable / is_rate_limited. (2) OUTER — `run_turn_attempt` (src/runtime/agent.rs:514): 3 attempts. Live measurement: an always-failing 502 provider cost 9 provider calls (3 inner × 3 outer); a needs_user skip wired ONLY at the outer layer still cost 3 (the inner burned its ladder). LANDED DESIGN: the classification lives at the INNER layer (complete_with_retry), placed after the is_non_retryable/is_rate_limited early-returns (so a 429 is never classified) and before the retry sleep; a confident needs_user/permanent → log the row (site provider_turn, action skip_retry, disposition escalated — ONE row per failure) and return `Error::Provider(format!("{e} — classified {label}: retrying cannot help ({hint})"))`. The marker text carries the classifier's CANONICAL label (`needs_user`, underscore — a hyphenated needle silently failed to match, causing a duplicate second row; the test caught it). `Error::is_classified_skip()` (src/error.rs) detects the marker and `is_non_retryable()` returns true for it, so the OUTER layer skips via its existing arm WITHOUT re-classifying (no duplicate row) and the terminal note's qualifier (runtime/agent.rs, order: is_rate_limited → is_classified_skip → skip_triage(outer classification) → is_non_retryable → exhausted) reads "classified failure-triage skip (retrying cannot help)". `failure_triage::skip_hint(class)` is the shared hint text. The OUTER layer still owns: the transient/flaky `ladder` row (action ladder, disposition retry_failed when the ladder dies) and its own skip path (reachable only when the inner classify failed but the outer succeeded). MEASURED COUNTS (pinned by tests): needs_user skip = 1 provider call, 0 retrying notes, 1 row; transient = 9 calls / 8 retrying notes (6 inner + 2 outer) / 1 ladder row; disabled = 9 calls / 8 notes / 0 rows. Test harness note: `AgentTask::run`'s auto-continue loop multiplies everything (3 rounds) — the provider-site tests drive `task.run_turn_attempt(...)` DIRECTLY (one attempt) and assert the qualifier on the in-context note (`terminal_note`), NOT the terminal event text (which carries the raw error unless 429/skip).
