# Plan: Pin one Rust version for local builds and CI (rust-toolchain.toml)

## Goal
A committed rust-toolchain.toml pins Rust 1.99.1 (with clippy and rustfmt) for every local cargo command in this repo and for every CI job. A new Rust release can no longer turn the PR check red without a commit. Bumping becomes a deliberate one-line change, made with its lint fixes in the same PR.

## Kind
implementation

## Context
WHY: CI installs whatever stable Rust is current (dtolnay/rust-toolchain@stable), while the user's machine had 1.95. New clippy lints under #![deny(warnings)] broke CI three times: the fetch_update deprecation in build run 42067076616, the 1.95 lint storm, and the 1.99.1 lints on PR #118, fixed in 1a61e96d. The user asked (2026-11-11) for one pinned version shared by local and CI.

CURRENT SETUP: every workflow job installs Rust with dtolnay/rust-toolchain@stable:
- .github/workflows/ci.yml job `check` (~line 35, `with: components: clippy`);
- .github/workflows/build.yml windows job (~59), macos job (~122, `with: targets: aarch64-apple-darwin`) and examples job on ubuntu (~284).
codeql.yml does not install Rust (its Rust extraction is no-build); only its header comment mentions dtolnay.

The macOS job builds `npx tauri build --target aarch64-apple-darwin` (twice), so the pinned toolchain needs that target there. Do NOT put `targets` in rust-toolchain.toml: rustup would then download Apple std libraries on every Windows dev machine and runner. Add the target in the macOS job only.

DECISIONS:
- rust-toolchain.toml at the repo root: channel "1.99.1", components ["clippy", "rustfmt"], profile "minimal". 1.99.1 is what CI ran green on 2026-11-11, and it is already installed locally.
- Every workflow's dtolnay step is replaced by a plain step that runs `rustup toolchain install`. With no arguments, rustup (>= 1.28) installs the toolchain and components named in rust-toolchain.toml. GitHub's windows, macos and ubuntu runners ship rustup.
- The macOS step also runs `rustup target add aarch64-apple-darwin`. Run from the repo directory, that adds the target to the pinned toolchain.
- With dtolnay gone, every `uses:` in the workflows is a full SHA. The guard `workflows_pin_actions_to_full_shas` (tests/integration/ci_workflow.rs ~474) loses its only exception, and its doc comment drops the exception paragraph. That makes the repo's "require SHA pinning" Actions setting possible; the lead will offer it to the user, so the worker does not change GitHub settings.
- Dependabot cannot bump rust-toolchain.toml, so the file carries a comment saying how to bump it.

VERIFY:
- `rustup toolchain install` run in the worktree root picks up 1.99.1 and adds the components;
- `rustc --version` in the worktree prints 1.99.1;
- `cargo test --test integration ci_workflow` (all ci_workflow tests);
- `cargo clippy --workspace --all-targets` and `cargo clippy -p mnemo-app --all-targets --features mnemo2`, plain cargo, which now resolves to 1.99.1 through the file;
- the four workflow files still parse as YAML: `python -c "import yaml,sys; [yaml.safe_load(open(p, encoding='utf-8')) for p in sys.argv[1:]]" .github/workflows/*.yml`.

## Acceptance scenarios
- rust-toolchain.toml at the repo root pins channel "1.99.1" with clippy and rustfmt; `rustc --version` in the repo prints 1.99.1
- No file under .github/workflows contains `dtolnay/rust-toolchain`; every job that runs cargo has a step running `rustup toolchain install` before its first cargo command
- The macOS job adds aarch64-apple-darwin to the pinned toolchain before `npx tauri build --target aarch64-apple-darwin`
- `workflows_pin_actions_to_full_shas` has no allowed exceptions and passes; a new guard test fails if rust-toolchain.toml is missing, unpinned (e.g. "stable"), lacks clippy, or any workflow reintroduces dtolnay or runs cargo without the rustup install step
- `cargo test --test integration ci_workflow` and both clippy runs exit 0
