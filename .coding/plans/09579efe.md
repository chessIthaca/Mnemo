# Plan: Attribute connect/backoff/stall to "waiting"; fail-fast non-retryable errors

## Goal
Make the inflight bar and trace honest about where time goes: (1) move Phase::Waiting to before the provider request so connect timeouts + retry backoff show as "waiting" not "sending"; (2) stamp ttft_ms on error records (connect failure, stream stall, HTTP error) so the elapsed time is attributed to the waiting bucket in the trace; (3) classify context-overflow/auth/not-found errors as non-retryable so they fail immediately instead of burning 3×3 retries.

## Kind
implementation

## Context
From the provider-errors.jsonl analysis + code reading:

PHASE EMISSION (turn.rs): Phase::Sending is emitted at the top of the request loop; Phase::Waiting is emitted at turn.rs:1009 AFTER `stream_result?` (line 1006) — i.e. only after 200 headers arrive. So the 30s connect timeout (CONNECT_TIMEOUT, openai.rs:103) and the 1s/2s retry backoff sleeps (dispatch.rs:630, agent.rs:319) all show as "sending" in the live bar. The user wants these to be "waiting": "sending" = local prep only (<250ms, already measured as prep_ms), "waiting" = everything network-bound (connect, POST, TTFT, retry backoff).

TRACE TIMING (openai.rs + trace.rs): record_created (openai.rs:715) is set after log.start() but before the POST. request_start (openai.rs:826) is set after headers arrive. send_ms = request_start - record_created (record creation → headers). ttft_ms = first_chunk - request_start (headers → first byte). On ALL error paths, log.fail() is called but NO timing is stamped — send_ms/ttft_ms stay null. The error log confirms: every error record has "send_ms":null, "ttft_ms":null. So the 30s connect timeout and 90s stream stall (READ_TIMEOUT=90s, openai.rs:110) are completely lost from the trace. Fix: stamp ttft_ms (= record_created/request_start → error) on error records before log.fail().

RETRY (dispatch.rs + agent.rs): complete_with_retry (dispatch.rs:602-645) retries ALL errors 3× with 1s/2s backoff. run_turn_attempt (agent.rs:282-361) retries ALL provider errors 3× with 1s/2s backoff. No retryability classification exists. The 502 context-overflow (error body contains "maximum context length" + "input_tokens"), 401 auth, and 404 not-found are all retried 9 times pointlessly. Fix: add is_non_retryable() check; skip retries for these classes.

Error type: crate::error::Error::Provider(String). The error string from the gateway contains the markers ("maximum context length", "max_completion_tokens", "max_model_len", "auth_error", "NotFoundError").

Phase-sequence tests at src/agent/tests.rs:757-769 assert [Sending, Waiting, Streaming, RunningTools, Sending, Waiting, Streaming] — this sequence is UNCHANGED by moving Waiting earlier (Waiting is still emitted once per request, just before the network call instead of after). The reasoning-then-answering test at :780+ is similarly unaffected. But a NEW regression test is needed: assert Phase::Waiting fires on the ERROR path (old code skipped it; new code emits it before complete_with_retry).

Anthropic provider (src/provider/anthropic.rs) has a parallel complete()+stream-loop structure — mirror the trace-timing changes there.

No frontend changes needed: the phase wire strings ("sending"/"waiting") are unchanged; the trace DTO already has ttft_ms. Only backend Rust + tests + docs.
