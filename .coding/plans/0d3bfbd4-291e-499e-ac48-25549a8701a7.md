# Plan: Fix file_edit CRLF/LF line-ending mismatch

## Goal
Make `file_edit`'s string matching line-ending-agnostic: detect the file's line-ending style (CRLF vs LF) and normalize `old_string`/`new_string` to match before find/replace, so edits succeed regardless of whether the caller used LF or CRLF.

## Context
The `prepare_edit` function in `src/tool/agent/file_edit.rs` uses `content.find(&args.old_string)` and `content.replace(...)` for byte-exact matching. On Windows, files commonly have CRLF (`\r\n`) line endings, but the LLM emits `old_string`/`new_string` with LF (`\n`). This mismatch causes "old_string not found in file" errors. The fix: detect the file's dominant line-ending style and normalize the old/new strings to match it before matching. This preserves the file's existing line-ending style (CRLF files stay CRLF) while making matching line-ending-agnostic.

## Steps
- [x] 1. Add `detect_line_ending` + `normalize_line_endings` helper functions to `src/tool/agent/file_edit.rs`
- [x] 2. Update `prepare_edit` to normalize old_string/new_string to the file's line-ending style before matching, and move the identical-strings check after normalization
- [x] 3. Add tests: CRLF file + LF old_string matches; LF file + CRLF old_string matches; CRLF file preserves CRLF after edit
- [x] 4. Run `cargo test` to verify
