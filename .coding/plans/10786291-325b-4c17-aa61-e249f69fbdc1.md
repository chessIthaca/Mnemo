# Plan: Spike: does iced_webview render + expose CDP for agent inspection?

## Goal
De-risk the iced + iced_webview path with a minimal throwaway spike app. Answer two questions: (1) does iced_webview render sites including framing-refusers (google.com)? (2) DECISIVE — does its webview expose a CDP debug port the agent can attach to (enumerate targets, eval, screenshot)? If both YES → iced is viable; a real port is a follow-up implementation plan. If CDP is NO → iced does not solve the inspection problem and we revisit the Tauri separate-window option.

research

## Steps
- [x] 1. **Scaffold the spike + learn the iced_webview API** — `cargo new spike/iced-webview-poc` (binary) inside the project root. Add deps: `cargo add iced iced_webview` (confirm both publish + resolve; if iced_webview needs a git dep, use the docs.rs-published version). After fetch, read the iced_webview source from the cargo registry (~/.cargo/registry/src/.../iced_webview-*/) to pin the EXACT widget API: how to create a webview widget, load a URL, and whether it uses wry under the hood (grep its Cargo.toml for `wry`/`webview2-com`). Write a minimal `main.rs`: an iced window whose content is a webview widget loading `https://google.com`. Run `cargo build` in the spike dir; fix until it compiles warning-free. If iced_webview does NOT use wry/WebView2 (e.g. it's a different backend), record that — it changes the CDP story in step 3.
- [x] 2. **Run it + verify visual rendering (manual)** — Launch the spike in the background so it stays open for probing: `Start-Process -FilePath "target\debug\iced-webview-poc.exe" -PassThru` (build first with `cargo build`, then run the exe so it doesn't block on cargo). Ask the user: does google.com render in the iced window? (This is the framing-refuser test — the original motivation for leaving the iframe.) Record render=yes/no. Keep the process running for step 3.
- [x] 3. **Test CDP attach (the decisive question)** — iced_webview likely uses wry, which reads `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` at env-var time. Set it to a DIFFERENT port (9223, to avoid clashing with the running Tauri app on 9222) BEFORE launching the spike: `$env:WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--remote-debugging-port=9223"` then relaunch the spike exe. Probe `Invoke-RestMethod http://localhost:9223/json` — does it return targets including the webview page? If YES: confirm agent-style attach by eval'ing against the target (either a quick chromiumoxide one-liner in a tiny test, or raw CDP via the HTTP endpoint + a websocket eval of `document.title`). If NO targets: iced_webview's webview does NOT expose CDP → iced does not solve the inspection problem. Record the exact result (targets count, URLs, whether eval worked). This step's finding IS the go/no-go.
- [x] 4. **Record go/no-go + cleanup** — memory_write (semantic) the verdict: (a) does iced_webview render framing-refusers, (b) does it expose CDP for agent inspection (with the exact mechanism — wry env var, port, target shape), (c) the recommendation: if both YES → iced is viable, next step is a real implementation plan to port the Browser tab (and eventually the app); if CDP NO → iced does not solve the inspection problem, revisit the Tauri separate-window option (A) which is compile-proven to share the env. Kill the spike process. Optionally keep the spike dir for reference or delete it (`Remove-Item spike/iced-webview-poc -Recurse`). Update the prior iced fallback memory with the concrete finding.
