# Plan: Lead-facing Mnemo tools are lean and honest about the lead

## Goal
team_status answers in a compact form by default and says whether Claude Code is attached, idle or gone; memory_supersede picks the right tier itself; and an idled-out Claude Code session gets its lead role back on its own next tool call without other sessions stealing it.

## Kind
implementation

## Context
WHY: in a long Claude Code lead session (2026-11-01) three frictions showed up. (1) team_status returned the full brief, the whole opening prompt (plan text), review evidence and inbox for every worker: about 6 KB for one finished worker, growing with every worker, which burns the lead's context. (2) No Mnemo tool reports whether the external lead is attached; the lead had to read ~/.mnemo/run/*.json and call POST /lead/notices with the bearer token to find out. (3) memory_supersede refused a call with tier "procedural" for a file-backed record ("lives in a file — the successor must be semantic") instead of using semantic itself. (4) After 10 silent minutes the external lead is released (now shown as "Lead: Claude Code (idle)"); it only re-attaches on a Mnemo tool call or the waiter, although the PostToolUse hook already calls the helper after every tool call of that session.

FINDINGS (probed while planning):
- verified: team_status is answered in src-tauri/src/mnemo2/team.rs (the `if name == "team_status"` branch near line 1724, returning worker_result(result, "team_status")); worker_result serialises the whole record minus transcripts (without_transcripts). The tool schema is declared near line 1498.
- verified: the external lead state lives in TeamRuntime's ExternalLead (team.rs): since_ms, idle_since_ms (new, set by the idle sweep), last_activity_ms, waiters; accessors external_lead_since_ms, external_lead_idle_since_ms.
- verified: the supersede tier error is raised in src/tool/memory/mod.rs around line 1334.
- verified: hooks run `mnemo2-mcp notices --drain` after every tool call (mnemo2/plugin/hooks/hooks.json; src-tauri/src/bin/mnemo2_mcp/hooks.rs `notices`), which posts to /lead/notices; McpServer::notices in src-tauri/src/mnemo2/mcp_server.rs touches the lead only while attached and never attaches.
- verified: attach happens only on MCP tools/call and /lead/wait (McpServer::attach); a comment there explains why initialize/tools/list must not attach: opening Claude Code in the project must not take notices from the in-app lead.

DECISIONS:
- team_status default output per worker: id, name, status, kind, tier, model, plan_id, plan_step, branch, worktree, error, pending (as is), open findings (id, title, severity, file, line), checks as name + status + tip prefix, review summary and tip if reviewed, merge commit if merged, cost_micros, last_activity_ms. A `detail: true` argument returns today's full record. A `worker_id` filter keeps working with both.
- team_status adds a top-level `lead` object next to `result`: {"kind": "external"|"in_app", "attached": bool, "since_ms", "idle_since_ms"}. Existing consumers that read `result` must keep working.
- memory_supersede: when the old record is file-backed and the requested tier is not semantic, use semantic and say so in the success text; never refuse for that reason.
- Re-attach from hooks only for the SAME Claude Code session that idled out. Another Claude session in the project (the user often runs several) must never take the lead through a hook. If the helper cannot establish that identity reliably (the hook gets session_id on stdin; MCP tool calls may not carry it), the worker stops and reports to the lead instead of guessing.

## Acceptance scenarios
- team_status without arguments returns per-worker entries without brief, opening_prompt, inbox or review evidence, and a top-level `lead` object.
- team_status with detail true returns the full worker record as before.
- memory_supersede with tier procedural on a file-backed record succeeds and the result says the successor was stored as semantic.
- After an idle release, a hook call carrying the idled session's id re-attaches the lead; a hook call from a different session id does not.
