# Plan: Settings dialog: standard OK/Cancel buttons (OK saves all + closes, Cancel closes without saving)

## Goal
Replace the per-section Save/Reset buttons in the Settings dialog with standard dialog-level OK and Cancel buttons. OK saves all dirty sections and closes; Cancel closes without saving. Make this the dialog convention.

## Context
Architecture findings:
- SettingsDialog.tsx (the shell) renders 7 sections. Providers + Appearance are always-mounted (CSS-hidden when inactive); Safety/Vision/Pricing/Models/Advanced are conditionally mounted (only when active). The shell tracks a `dirtyMap` (per-section dirty) via `onDirtyChange` callbacks, and its footer has a single Done/Close button that confirms discard on close.
- Each section owns its save logic: handleSave() calls saveSettings / saveEndpoints / saveSafetyRules, updates its snapshot, shows an ok toast. Each has a Reset + Save button at its bottom. Save is disabled when !dirty || saving.
- Section prop shape: { active: boolean; onDirtyChange?: (dirty:boolean)=>void }. ProvidersSection requires onDirtyChange (non-optional).
- The dialog UI (ui/dialog.tsx) is a thin Radix wrapper; SafetyToggleDialog is a separate confirm dialog with Cancel/Confirm buttons (a good style reference for the new footer).
- No existing settings-section unit tests (frontend tests are the ipc-contract suite + useAgentStore reducer tests). types.ts has pure helpers (serializeAppearance, serializeProviders) but no section components.

Design (user chose "keep all sections mounted"):
1. Define a `SettingsSectionHandle` interface in types.ts: `{ save: () => Promise<void> }`.
2. Each section: wrap in forwardRef + useImperativeHandle exposing `save()` (the existing handleSave, but returning a Promise that resolves true on success / false on failure, and only updates snapshot on success). Remove the per-section Reset+Save button block. Keep the ok/error toasts (they now reflect the dialog-level OK result). Keep `onDirtyChange`.
3. Shell: always-mount all 7 sections (CSS-hidden like Providers/Appearance). Collect a ref per section into a `Record<SettingsSectionId, RefObject>`. Replace the footer Done/Close button with Cancel + OK. OK: for each dirty section, call ref.save(); collect results; if all succeeded, clear dirtyMap + close; if any failed, stay open and surface a toast. Cancel: if anyDirty, confirm discard; then close (sections restore snapshots via their existing deactivate logic — but since always-mounted now, the AppearanceSection's `active`-driven restore still fires on close because `active` = `open`).
4. The `active` prop semantics: currently sections get `active={open && section===X}`. With always-mount, keep passing `active={open}` for Providers/Appearance (already so) and switch the conditionally-mounted ones to always-mount with `active={open}` too — so their load() runs on open and their deactivate-restore runs on close. The `section===X` part of `active` was only relevant for load-on-nav; with always-mount we still want load on open. Keep nav switching purely CSS (no remount), so draft state persists across tab switches (matches Providers/Appearance behavior).

Risk: AppearanceSection's useEffect restores CSS on `active` false — with always-mount + active={open}, that fires on dialog close (good). ProvidersSection clears secrets on !active (good). The conditionally-mounted sections' load() runs on `active` true (open) — fine.

Tests: add a vitest for the shell's OK/Cancel behavior is hard (needs Tauri mocks). Instead add a pure helper in types.ts: `collectDirtySections(dirtyMap)` returning the list, + a `SettingsSectionHandle` type, and test the helper. Keep it lightweight.
