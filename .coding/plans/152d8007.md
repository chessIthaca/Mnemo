# Plan: web_fetch: re-validate the SSRF blocklist on every redirect hop

## Goal
Close the SSRF redirect bypass in web_fetch: replace reqwest's auto-following redirect policy with a manual redirect loop that re-runs the full gate (http/https scheme + internal-host blocklist, fail-closed) on every hop's Location before requesting it, caps at 5 follows with a clear too-many-redirects error, and preserves all other behavior (scheme filtering, size caps, HTML stripping, output format). Regression-tested against a local stub HTTP server.

## Kind
bug_fixing

## Context
Verified by code read (src/tool/agent/web_fetch.rs, 473 lines): scheme check on raw string → extract_host + hostname_resolves_to_internal via spawn_blocking (fail-closed) ONCE → client with Policy::limited(5) → single send() auto-follows redirects unchecked. Test infrastructure: repo pattern is a hand-rolled tokio TcpListener stub server (src/provider/openai/tests.rs StubServer ~2493; no mock crates; tokio full + test-util available). Testability design: production gate blocks 127.0.0.1, so a local stub server is unreachable through execute()'s initial gate — extract the redirect loop as a private fn taking the hostname gate as fn(&str) -> bool (production: hostname_resolves_to_internal; tests: stubs). IP-literal targets (169.254.169.254) resolve without DNS → deterministic tests. reqwest parity decisions: follow only 301/302/303/307/308 with a Location header (else return the 3xx as-is, matching reqwest); 5 follows max (old Policy::limited(5)); GET stays GET. Deliberate minor behavior notes: unparseable-but-http-prefixed URLs now error "fetch failed: invalid URL: ..." (was reqwest builder error; untested edge); whitespace-padded URLs now parse (trim, consistent with the scheme check); exceeding 5 hops returns a clear too-many-redirects error.

## Bug
web_fetch follows up to 5 HTTP redirects automatically (reqwest redirect::Policy::limited(5), src/tool/agent/web_fetch.rs:186) without re-running the SSRF internal-address blocklist on redirect targets — the gate runs exactly once, on the initial URL (lines 161-177). A public URL answering 302 → http://169.254.169.254/... (cloud metadata or any internal host) is fetched, bypassing SSRF protection; the inline comment documents this as a known residual.
