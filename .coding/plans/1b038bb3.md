# Plan: Launch Mnemo-decided Claude agents without a permission prompt

## Goal
When Mnemo has decided that a step runs as a Claude Code agent, the lead's Agent launch for it runs without a human permission prompt. A misfired launch is corrected by the lead model at once, instead of waiting on the user.

## Kind
implementation

## Context
WHY: the user does not want to approve agent launches that Mnemo itself decided on. In another project (2026-11-24) an agent-worker launch sat behind a permission prompt for about 35 minutes, and Mnemo meanwhile handed the worker back (plan ee73bd2f fixes the hand-back side).

How the gate works today:
- The plugin's PreToolUse hook for Agent|Task|Workflow runs `mnemo2-mcp gate-agent` (src-tauri/mnemo2-app/src/mnemo2_mcp/hooks.rs gate_agent, ~line 242). It posts to `/lead/gate-agent`, served by McpServer::gate_agent (src-tauri/src/mnemo2/mcp_server.rs ~1108).
- The server already decides "allow" while a Claude Code agent worker is Working/Fixing (claude_agent_working, team/external_lead.rs:566), with the reason "runs Mnemo worker <id> (<tier> tier) as a Claude Code agent".
- But the hook only ever emits a hookSpecificOutput for "ask". On "allow" it prints nothing, so Claude Code falls back to its own permission rules and may still prompt.
- When a worker waits for its agent and the launch lacks isolation "worktree", the server answers "ask" (WORKTREE_GATE_REASON). That parks a question on the human when the lead model could simply relaunch correctly.

DECISIONS:
1. The server marks its agent-worker allows: gate_agent adds `"auto_approve": true` to the reply ONLY when it allows because a Claude Code agent worker is waiting for its launch or Working/Fixing (the claude_agent_working branch, and the waiting-worker branch below). The other allows never carry it: no external lead attached, or a subagent_type listed in agents_without_prompt. Those keep today's behaviour, where Claude Code's own permission rules decide.
2. The hook passes it on: when the reply has decision "allow" and auto_approve true, gate_agent prints `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow","permissionDecisionReason":<reason>}}`. With auto_approve missing or false it prints nothing, as today. "ask" is unchanged.
3. Waiting worker, non-isolated launch: instead of "ask", the server answers `"decision": "deny"` with a reason the model can act on: "Mnemo worker <id> waits for its agent: relaunch with isolation \"worktree\" (the hook then hands the agent its warm checkout), or, if the worktree hook cannot place it, launch without isolation with a prompt that names its checkout <worktree path>." The hook emits permissionDecision "deny" with that reason. EXCEPTION: when the Agent prompt names the waiting worker's worktree path (case-insensitive, either slash style), it is a deliberate manual launch into that checkout; allow it with auto_approve true. The hook must pass `tool_input.prompt` in the body for this (capped at, say, 64 KiB). The isolated launch for a waiting worker is allowed with auto_approve true.
4. Never auto-approve anything else. A general-purpose agent the lead starts for its own work while no agent worker is in play still asks (GATE_REASON), as today.

VERIFY: the exact .coding/checks.toml commands from the checkout root. Test temp folders live in <checkout>/target.

## Acceptance scenarios
- With Claude Code leading and an agent worker waiting, the lead's Agent launch with isolation "worktree" runs with no permission prompt: the hook prints permissionDecision "allow".
- A launch without isolation while a worker waits is denied at once, with a reason telling the model how to relaunch; no human prompt appears. A launch whose prompt names the waiting worker's checkout is allowed.
- A general-purpose agent the lead starts while no agent worker is waiting or running still asks the user, as before.

## Decisions
- 2026-11-24: no spec impact: Gate decision plumbing between the plugin hook and the external-lead server plus skill wording; the external-lead capability's requirements are unchanged (the gate already allowed agent-worker launches; this makes the allow effective).
- 2026-11-24: added step 3 (Integration check) because steps 1 and 2 ran in parallel
- 2026-11-24: 2026-11-24 (step 1 review): narrowing decision 1. A Working/Fixing agent worker does not make every Agent launch auto-approvable. auto_approve is set only for (a) the isolated launch while a worker waits for its agent, (b) a non-isolated launch whose prompt names the waiting worker's checkout, and (c) a launch whose prompt names the worktree path or wt/agent-* branch of a Working/Fixing agent worker. Any other agent while workers run gets the plain allow, which leaves the decision to Claude Code's own permission rules.
- 2026-11-24: 2026-11-24 (step 1 audit): the waiting-worker branch of the gate applies only to launches of the agent type the claude_agent block uses: subagent_type "general-purpose", or no type. Any other type (Explore, claude-code-guide, a custom agent) or a Workflow call while a worker waits is neither auto-approved nor denied by that branch: it falls through to the normal path (the agents_without_prompt allow, or ask), as before this plan. That way an isolated Explore can never be auto-approved into the waiting worker's checkout. The checkout matcher gets the same boundary guard as the branch matcher (no further path characters after the match). The gate decides from worker records only (a records-only team method under one lock), never from a full snapshot.
