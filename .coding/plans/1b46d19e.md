# Plan: A typed knowledge row can no longer drift from its file

## Goal
No writer can change a derived (file-backed) row without its source file, and any row that has drifted from its file is repaired by the next targeted or full reindex and by the startup staleness check.

## Kind
bug_fixing

## Context
ROOT CAUSE (confirmed on the live DB C:\Mnemo\.coding\memory.db, read-only): the writer is SESSION-END CONSOLIDATION, not memory_update. `extract_semantic_facts` in src/memory/consolidation.rs (about lines 391-487) lists ALL semantic-tier rows via `store.list_by_tier(MemoryTier::Semantic)` — derived knowledge rows included, because the indexer writes every derived row with tier Semantic (`write_derived` in src/memory/indexer.rs) — and tells the LLM "set 'id' when an entry refines one of these". When the LLM answers with a knowledge row's id, the code does `prior.clone()` (so record_class stays Derived), sets `title` to the fact's first 60 chars (untyped, so `MemoryRecordType::from_title` yields None inside `store.write`), `content` to the fact, `data` to `SemanticData{fact,confidence}` (rel_path and links lost), appends the session id, and `store.write` INSERT-OR-REPLACEs the row. The knowledge FILE is never touched. Evidence: row d82acb4a-b2d8-5ce7-8bcc-777c9370742a has title 'Mnemo2 automatically attempts merged-worker branch cleanup: ' (60 chars), data {"confidence":0.99,"fact":...}, record_class derived, record_type none, source_session_ids ["47dbf145-..."], and its derived_index_state hash still matches the file. The same drift sits on 105 knowledge-keyed rows in that DB (record_type none + non-empty source_session_ids; 20 bug, 14 decision, 37 how, 34 spec): `index_derived`'s post-loop `set_derived_metadata` pass later restored their data/rel_path, but nothing restores title/content/record_type. WHY IT NEVER HEALS: both `index_derived` (src/memory/indexer.rs ~line 137) and `reindex_knowledge_files` (src/memory/indexer/knowledge.rs ~line 163) skip a source when the stored content hash equals the file's hash; the hash lives in derived_index_state and never sees the row; `corpus_is_stale` (indexer.rs ~line 322) uses the same hash-only test, so the startup reconcile stays silent. SECOND PATH: `MemoryUpdateTool::execute` (src/tool/memory/mod.rs ~lines 1067-1084) and `repair_by_id` (~lines 899-927) call `self.store.update_memory(...)` database-only whenever the tool has no knowledge backing or `knowledge_for_id` (line ~494) finds nothing — which is also what happens to a clobbered row whose data.rel_path was lost — so a DB-only edit of a derived row is possible there too. DECISIONS: (1) consolidation owns only AUTHORED facts: derived rows are neither listed to the LLM nor rewritten; an id naming one finds no match and the fact is written as a new authored memory. (2) memory_update on a Derived row that has no working file path is refused with a clear error naming the source (not silently routed), because derived rows are rebuilt from their source. (3) The indexer compares the stored row against the file, not only the hash: a row is 'unchanged' only if the hash matches AND the row is Derived, tier Semantic, title and content equal the source's, and record_type equals `MemoryRecordType::from_title(title)`; a drifted or missing row falls into the existing 'changed' path (update_memory + post-loop metadata reconcile restores data/rel_path/links; a missing row is re-written by `write_derived`). Same check in `corpus_is_stale`. No settings knob, no new report field. REGRESSION TEST: `semantic_extraction_leaves_derived_knowledge_rows_alone` in src/memory/consolidation.rs (tests module). Without the fix it FAILS: the knowledge row's title becomes the fact's first 60 chars, record_type becomes none, data becomes SemanticData with no rel_path, and source_session_ids gains the session id. Supporting regressions: `full_reindex_repairs_a_row_that_drifted_from_its_file` (src/memory/indexer/tests/knowledge.rs, fails today: second run skips the drifted row) and `update_refuses_a_database_only_edit_of_a_derived_knowledge_row` (src/tool/memory/mod.rs tests, fails today: the DB-only update succeeds). VERIFY: `cargo test -p mnemo-app --lib` and `cargo clippy -p mnemo-app --all-targets -- -D warnings` (no src-tauri file is touched, so `--features mnemo2` is not needed). Do NOT rebuild or restart Mnemo2, and do not touch .coding/memory.db: the live drifted rows heal on the next startup reconcile after the lead rebuilds with the user's yes.

## Acceptance scenarios
- Session-end consolidation whose LLM names a knowledge row's id leaves that row unchanged (title with its typed prefix, content, record_type, data incl. rel_path, empty source_session_ids), keeps the id out of the extraction prompt, and stores the fact as a NEW authored semantic memory.
- memory_update (with or without the knowledge backing) on a Derived row that has no working file path is refused with an error saying it is a derived record and naming the fix, for title/content updates and for find+replace_with repairs; the row is unchanged afterwards. Authored DB-only rows still update as before.
- After a row drifted from its file (file and index hash unchanged), a full index_derived run and a targeted reindex_knowledge_files run each rewrite the row from the file (typed title, digest content, record_type, rel_path and links data); a further run skips it.
- corpus_is_stale returns true while any derived row has drifted from its source (so the startup reconcile runs) and false once repaired.
- A derived row deleted while its derived_index_state entry remains is recreated by the next reindex.
