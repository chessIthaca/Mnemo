# Plan: Worker output side panel beside the lead

## Goal
Clicking a worker name in the lead's "Waiting on …" line opens a right-side panel that streams that worker's output, as Mission Control does, while the lead chat stays visible. The panel has a dropdown to switch between active workers, shows the worker's model and status, and has a text box to steer it.

## Kind
implementation

## Context
Why: the user likes the lead's status line "Waiting on A, B. The lead picks up when one finishes." They want to click a worker there and watch its LLM output stream, the same way they watch the lead, without leaving the Lead view. Today the only worker view is Mission Control (route "team"), which hides the lead. The user clarified they want the worker's normal output (its messages and tool calls), NOT model reasoning.

Findings from planning (verified by reading the code):
- verified: mnemo2/src/components/LeadChat.svelte:175-180 renders the waiting line from `runningWorkers` (status dispatching/working/fixing), as one plain text span.
- verified: mnemo2/src/components/WorkerDetail.svelte:196-224 is the Thread tab: it loops over worker.messages, shows ToolActivity cards for tool entries, Markdown/Collapsible bodies for messages, and screenshot links, then a reply textarea. Enter calls sendReply -> actions.replyWorker(worker.id, reply).
- verified: mnemo2/src/lib/store.ts:1319-1328 replyWorker trims the text and calls transport.message(workerId, text), which is IPC team_message (teamEngine.ts:95); a busy worker receives it as a steer.
- verified: mnemo2/src/lib/store.ts:1849-1867 streamWorkerEvent folds each TeamEvent through workerThread.ts::applyWorkerLiveEvent (text_delta appends to a streaming message; tool_call_start adds a tool card; tool_output_delta and tool_result update it). It then writes composeThread() (saved thread + live entries) into worker.messages. So worker.messages already streams live; the panel must not add a second streaming path.
- verified: mnemo2/src/lib/store.ts:712-723 selectWorker switches route to "team" (Mission Control). The panel needs a new action that stays on "lead".
- verified: mnemo2/src/App.svelte:24-28 puts LeadChat and the optional Workbench (a resizable right aside, width $app.workbenchWidth, mobile overlay at <=760px per Workbench.svelte:84-97) inside .lead-column.
- verified: WorkerDetail.svelte:96-100 shows model info via ModelBadge(worker.model), worker.reasoningEffort, worker.tier, and workerStatusText(worker).

Decisions:
- Extract the Thread section of WorkerDetail.svelte into a reusable mnemo2/src/components/WorkerThread.svelte (props: worker; optional compact). It holds the message list, screenshot links, and reply composer. WorkerDetail must render it, so Mission Control behaviour and the existing WorkerDetail/ControlRoom/ReviewEvidence/WorkerModel tests stay unchanged and green.
- New mnemo2/src/components/WorkerPanel.svelte: a right-side aside inside .lead-column (App.svelte), placed and styled like Workbench (reuse its width/resizer pattern and its mobile overlay). The worker panel and the Workbench share the right side: opening one closes the other.
- Store (store.ts plus AppState in lib/types.ts):
  - New `workerPanelId: string | null` (initially null) and actions `openWorkerPanel(workerId)` (route stays "lead"; unknown ids ignored; also closes the Workbench) and `closeWorkerPanel()`.
  - Opening the Workbench sets workerPanelId to null.
  - Reset to null on project switch and when a team sync no longer contains that worker.
  - selectWorker is unchanged.
- Panel header:
  - A native select (aria-label "Choose worker") listing active workers: status dispatching, working, fixing, idle, needs_you, paused, interrupted. Always include the currently shown worker, even after it finishes, so the panel never jumps away by itself.
  - The worker's status text, ModelBadge, effort and tier pills, and its plan label (boardState.ts workerPlanLabel).
  - An "Open in Mission Control" button (calls actions.selectWorker) and a close button (aria-label "Close worker panel").
- Panel body: WorkerThread. Auto-scroll to the bottom while the user is within 48px of the bottom (same rule as LeadChat's STICK_TO_BOTTOM_PX). Never move the scroll position while the user has scrolled up to read.
- LeadChat waiting line: render each running worker's name as a small inline button (aria-label "Show <name>'s output") that calls openWorkerPanel. Keep the sentence wording identical. Update LeadChat.test.ts:564's text assertion only if the button markup splits the text node.
- No Rust or backend changes. Do not touch frontend/** (the Mnemo1 UI, owned by plan 2c26d533).

Verification: in mnemo2/ run `npm test`, `npm run check` (0 errors, 0 warnings), and `npm run build`.

\## Acceptance scenarios
- With two workers running and the lead idle, clicking a worker name in the "Waiting on …" line opens the worker panel on the right. $app.route stays "lead" and the lead chat stays rendered.
- A text_delta TeamEvent for that worker makes new text appear in the panel. A tool_call_start event shows a tool card there.
- The "Choose worker" select lists the active workers. Choosing another one switches the panel's thread, model badge, and status text to that worker.
- Typing in the panel's text box and pressing Enter invokes team_message with that worker's id and the text, then clears the box.
- Opening the Workbench closes the worker panel, and vice versa. Switching project resets workerPanelId to null.
- Mission Control's WorkerDetail still shows the same Thread content and reply box; the existing WorkerDetail and ControlRoom tests pass unchanged.

Needs-attention status in the Lead view (added 2026-10-31, same step):
- LeadChat shows a second status line whenever any worker has needsYou true (the same predicate as store.ts needsYouCount). Example: "Needs you: Audit auditCom (failed)." Each worker name is an inline button (aria-label "Open <name>") that calls openWorkerPanel. The line shows whether or not the lead is busy, and is hidden when the count is 0.
- WorkerPanel: when the shown worker is failed, conflict, stopped, or interrupted, show a clear status banner with its error text (worker.error, if present) and actions that reuse existing store actions only:
  - "Continue" (resumeWorker, then a replyWorker nudge is not required; resume alone)
  - "Delete" (requestDeleteWorkers([id]), which opens the existing confirmation)
  - "Open in Mission Control"
- The "Choose worker" select also includes needsYou workers.
- Never add UI for answering worker questions: workers cannot ask them.
Acceptance additions:
- A failed worker makes the Lead view show the "Needs you" line; clicking its name opens the panel on that worker with Continue and Delete visible.
- Delete opens the existing worker-deletion confirmation.
