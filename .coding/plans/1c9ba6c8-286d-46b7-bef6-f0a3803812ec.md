# Plan: Semantic memory system — 4-phase orchestrator

## Goal
Implement the endorsed 4-phase semantic memory system (typed memory records + hygiene tools; indexer + bootstrap + config-dialog Memory section; retrieval tools + prompt enforcement; bug_fixing plan kind + finish-step auto-capture) on one branch, each phase executed as a sub-plan with its own detailed implementation and verification, followed by end-to-end integration verification.

## Kind
implementation

## Context
Design endorsed by user across 3 chat rounds (2026-08-22); full decisions in semantic memories "DECISION: semantic memory system for plans/reviews/bugs — endorsed design" and "DECISION: semantic memory system — round 3". Hard constraints: (a) ALL phases on the single branch feat/semantic-memory-system — sub-plans must NOT create branches; (b) scale is a hard requirement — 1000s of bug records, 100s of plan/feature records over time: recency decay, per-class/per-query caps, indexed storage, incremental indexing, config knobs; (c) prompt enforcement ships in the SAME phase as each tool; (d) digests are pointer-first with app-enforced budgets (PLAN ≤400, BUG ≤600, SPEC ≤500, DECISION ≤300 chars); (e) merge hygiene is OUT OF SCOPE — backlogged as item #87; (f) semantic-memory capture happens in the finish step. Each phase step below = push ONE sub-plan that works out detailed implementation + tests; the phase descriptions here are feature-level by design. cargo test must be green and warning-free per constitution; reviewer report at root completion covers the whole feature.

- [x] 1. **Phase 1 sub-plan: typed memory records + hygiene tools** — Push ONE sub-plan (no new branch — stay on feat/semantic-memory-system) that designs and implements Phase 1 features: (1) typed memory title prefixes SPEC:/DECISION:/BUG:/PLAN:/HOW: with content templates; (2) app-enforced length budgets in memory_write (PLAN ≤400, BUG ≤600, SPEC ≤500, DECISION ≤300 chars — reject or truncate over-budget); (3) new bookkeeping tools memory_update, memory_supersede, memory_delete, memory_list(tier, prefix filter); (4) stable memory IDs returned by memory_recall/memory_list so supersede can address records; (5) supersede-not-delete semantics: supersede writes new record + marks old superseded-by:<new-id>, superseded records excluded from default recall but retrievable via an explicit history option; (6) store schema gains an authored-vs-derived record-class flag plus tag/date/class indexing sized for 1000s of records (no full scans); (7) per-class ranking weights (authored > derived on ties, superseded downranked).
