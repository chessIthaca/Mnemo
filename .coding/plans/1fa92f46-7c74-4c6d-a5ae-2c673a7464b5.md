# Plan: Diagnose time spent in the "sending" phase (network vs our code)

## Goal
Determine what the inflight bar's "sending…" phase actually includes, and whether the observed time there is network latency (upload/TLS/connect) or our own processing (prompt build, model resolution, retries), using the existing per-phase trace timings and code reading. Produce a verdict + any concrete findings, no source changes.

## Kind
research

## Context
User observes most of each turn's wall time in the "sending" inflight-bar phase. Known: PhaseKind::Sending is emitted at the top of the request loop in src/agent/turn.rs and PhaseKind::Waiting right after the stream is established (plan f3739d61); the phase docs in src/runtime/channels.rs say Sending = building/retrying the provider request, Waiting = POST sent awaiting first byte. trace.rs records send_ms / ttft_ms / generation_ms per request (LlmRequestSummary), and the LLM trace view shows them. provider-errors.jsonl shows retry-style errors for some providers but that's a separate concern.

## Steps
- [x] 1. **Map the Sending→Waiting window in turn.rs** — read src/agent/turn.rs around the request loop top and the stream establishment (Phase::Sending / Phase::Waiting emissions, per plan f3739d61: loop top ~line 150-170 and stream_result ~line 720). List every operation between the two emissions: prompt/message building, model resolution, provider capabilities checks, retry/backoff loops, and anything awaited there. Also read the phase doc comments in src/runtime/channels.rs (~254-311, 1059) to confirm the intended semantics.
- [x] 2. **Read the timing instrumentation** — read src/provider/trace.rs (start(), set_usage with send_ms/ttft_ms/generation_ms, LlmRequestSummary) and find where send_ms starts/stops in src/provider/openai.rs (the caller). Determine exactly which part of the request path send_ms covers and whether it overlaps or excludes what the UI calls 'sending'.
- [x] 3. **Check retry/backoff behavior** — search for retry loops / sleep / backoff in src/provider/ and src/agent/turn.rs that run inside the Sending window (e.g. 429 handling, model resolution fallback, connection retries). Quantify worst-case time a retry path can add to the 'sending' phase.
- [x] 4. **Check what the frontend actually displays** — read frontend/src/components/chat/InflightBar.tsx (phase label map) and frontend/src/hooks/agentEventReducer.ts phase handling to confirm the UI's 'sending' maps 1:1 to PhaseKind::Sending and nothing else (e.g. whether a stuck phase lingers after stream start).
- [x] 5. **Inspect live trace data if available** — look in .coding/logs/ (and any trace log files the app writes, e.g. llm trace jsonl) for recent LlmRequestSummary rows: compare send_ms vs ttft_ms vs generation_ms across requests/providers to see whether most wall time is inside the local send window or after the bytes hit the wire.
- [x] 6. **Write the verdict** — summarize: (a) what 'sending' includes in code, (b) whether the data shows network vs local processing dominates, (c) concrete suspects if our code contributes (prompt build cost, retries, model resolution) with file/line refs. Report in chat; no source changes.
