# Plan: A merged worker's branch is deleted automatically

## Goal
After team_merge lands a worker cleanly, Mnemo2 deletes that worker's branch itself with a safe delete, retries the delete for earlier merged workers at the next merge, and the lead rules say so, so no merged branch lingers and no lead deletes one by hand.

## Kind
implementation

## Context
WHY. The user asked (2026-11-06): branches that are successfully merged should be deleted automatically, and Mnemo2 must know it, in the merge rules. Today `TeamRuntime::merge_locked` (src-tauri/src/mnemo2/team.rs, after the `git merge --no-ff` succeeds) marks the worker Merged, closes its live session and removes its checkout with `cleanup_agent_worktree`, but never touches the branch `wt/agent-<shortId>`. After one release cycle there were 7 merged worker branches and a leftover worktree to clean by hand. mnemo2/README.md (about line 416) even documents "keeps the branch for audit".

WHY DELETING LOSES NOTHING. The merge is `--no-ff`, so the merge commit's second parent is the worker's reviewed tip, and `MergeRecord.worker_tip` records it. The Diff tab (`worker_diff` in src-tauri/src/mnemo2/workbench.rs) already reads a merged worker through `commit^1` and `commit^2`, never through the branch ref. `revert_locked` in team.rs reverts by `merge.commit` and does not need the branch either. So the "kept for audit" claim is replaced by "the merge commit keeps the worker tip as its second parent".

DECISIONS ALREADY TAKEN.
- Delete with `git branch -d`, never `-D`. `-d` refuses a branch that is not fully merged into the checked-out lead branch and a branch a worktree still uses, which is the safety net. A refusal is not a merge failure: the merge already landed.
- The immediate delete runs only after `cleanup_agent_worktree` returned Ok (or found no checkout). If the checkout cleanup failed, keep the branch; the existing error text stays.
- A failed delete sets `worker.error` to `"merged, but branch cleanup needs attention: <git error>"` (the same pattern as the existing "merged, but worktree cleanup needs attention"). It never turns the merge into an Err.
- A small sweep inside `merge_locked` (holding the merge lock) retries the branch delete for OTHER workers that are `ledger::merged` (status Merged, a merge record, no revert), own their branch (`owns_its_branch`), share it with no other record, and have no checkout folder left. This cleans leftovers from before this change and from transient failures. It is best effort and silent: a refusal just means the branch stays until the next merge. It does not retry worktree removal (that is a separate known residual).
- Never touched: branches of Cancelled, Stopped, Failed, conflict or audit workers (they keep their branch for audit and resume), a merged record whose merge was reverted (the lead may want to re-land it), `main`, and the lead branch `wt/mnemo`.
- No setting, no knob: the app decides (the user's standing preference).
- Not in scope: the Mnemo1 app code under src/app/worktrees.rs and src-tauri/src/ipc/run_all.rs (they keep PR branches on purpose); startup sweeps; retrying a stuck worktree removal.

FILE OWNERSHIP. Step 1 owns src-tauri/src/mnemo2/team.rs and src-tauri/src/mnemo2/runtime.rs. Step 2 owns mnemo2/plugin/skills/mnemo-lead/SKILL.md, mnemo2/plugin/skills/mnemo-review/SKILL.md and mnemo2/README.md. They share no file, so they can run in parallel.

KNOWN TEST IMPACT. src-tauri/src/mnemo2/runtime.rs test `merge_requires_tip_checks_and_supports_local_revert` (about line 5689) runs `git show-ref --verify refs/heads/<worker.branch>` after the merge. That now must assert the branch is GONE; the revert half of that test must still pass, which proves revert does not need the branch. Any other test that asserts a merged worker's branch survives must be changed the same way, and no other assertion may be weakened.

## Acceptance scenarios
- After `team_merge` of a clean, reviewed worker, `git branch --list 'wt/agent-*'` no longer lists that worker's branch and its `.worktrees/agent-*` folder is gone, while the merge commit's second parent still equals the reviewed worker tip (unit test `merge_deletes_the_merged_branch_and_keeps_the_work`).
- A worker branch that is not fully merged into the lead branch is never deleted: `delete_merged_branch` returns an error and the branch still exists (test `delete_merged_branch_refuses_a_branch_that_is_not_fully_merged`).
- When the session close fails and the merge is retried, the branch survives the failed attempt and is deleted by the successful retry (extended `merge_close_error_returns_to_review_and_retries_cleanup`).
- `team_revert_merge` still works after the worker branch is deleted: the runtime test `merge_requires_tip_checks_and_supports_local_revert` asserts the branch is gone and still reverts the merge.
- A later merge deletes the leftover branch of an earlier merged worker whose checkout is gone, but keeps the branch of a reverted merge, of a worker whose checkout folder still exists, and of a branch with commits not in the lead branch (tests `a_later_merge_sweeps_an_earlier_merged_workers_leftover_branch` and `the_sweep_keeps_reverted_held_and_unmerged_branches`).
- The `team_merge` tool description, the mnemo-lead and mnemo-review skills and mnemo2/README.md all say that the merge deletes the worker's branch and that the merge commit keeps the work; no file under mnemo2/ or docs/ still says a merged branch is kept for audit.
