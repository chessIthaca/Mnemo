# Plan: Strict tool schemas + sanitized tool errors for OpenAI-compatible providers

## Goal
Make tool calls robust for OpenAI-compatible providers (DeepSeek in particular) by (1) enabling provider strict-schema mode — `"strict": true` — for the file-mutation, plan, and finish tools on endpoints that support it, with schemas automatically NORMALIZED to be strict-legal so the tools' existing forgiving argument forms keep working; and (2) sanitizing tool-failure feedback so the model receives a clean, instructive message naming the offending parameter and the expected type instead of a raw serde/JSON stack trace. Strict mode must be capability-gated per endpoint (litellm/vertex reject the field), never blanket-on.

## Context
## Findings from exploration

**Strict mode is plumbed but never enabled.** `ToolSchema` (`src/provider/mod.rs:690`) has `pub strict: Option<bool>` with `#[serde(default, skip_serializing_if = "Option::is_none")]`. Both OpenAI request builders already emit the field correctly and only when `Some`:
- chat-completions path: `src/provider/openai/request.rs:686-707` (`function["strict"] = true`)
- Responses API path: `src/provider/openai/request.rs:934-952` (`tool["strict"] = true`)

But `ToolSchema::new` (`src/provider/mod.rs:807-817`) hardcodes `strict: None`, and no call site ever assigns it. Existing tests `build_request_json_omits_strict_when_none` / `build_request_json_includes_strict_when_some` (`src/provider/openai/tests.rs:774-820`) cover serialization only.

**Why blanket `strict: true` would break things.** OpenAI strict mode requires, for every object in the schema: `additionalProperties: false`, and every property listed in `required`. Several repo schemas are deliberately FORGIVING and violate both:
- `git` (`src/tool/agent/git.rs:457-505`): only `subcommand` is required, while `message`/`branch`/`action`/`source`/`paths`/`target` are accepted interchangeably — doc comment at `src/tool/agent/git.rs:43-52` documents the forgiving resolution (`resolve_git_subcommand`, `resolve_git_action`).
- `complete_step` accepts integer OR whitespace-padded numeric string (`src/agent/dispatch.rs:325-332` mirrors `StepNumber::parse`).
- `file_edit` has multiple modes (exact / regex / counted / line-range / fuzzy-whitespace).
So the schema must be NORMALIZED to be strict-legal while preserving acceptance: nullable optionals (`anyOf: [{type: X}, {type: "null"}]`), all properties in `required`, `additionalProperties: false`.

**Not all OpenAI-compatible endpoints support strict.** The existing comment at `src/provider/openai/request.rs:689-693` says litellm/vertex REJECT the field (`"Input should be a valid boolean"`), which is why it is omitted when `None`. So strict must be CAPABILITY-GATED per endpoint, never blanket-on.

**Tool errors reach the model raw** (the sanitizer's target):
- dispatch arg-parse failure: `src/agent/dispatch.rs:189-200` returns `"malformed arguments JSON: {e} (raw: {})` with the full serde error + raw arguments string.
- tools do `format!("invalid arguments: {e}")` with a full serde error, e.g. `src/tool/agent/image_tools/tools.rs:239`, `:319`, `:396`.
- `ToolResult::error` (`src/tool/mod.rs:77-83`) is a pass-through with no sanitizing.
The target shape is `"Error: The tool 'X' failed because parameter 'Y' must be an integer, not a string. Please try again with the correct type."` — i.e. extract the field name + expected/actual type from the serde error rather than echoing the trace.

**Prior art to reuse, not reinvent.** The repeat-failure circuit breaker (plan a9875b73, merged 8b2ee81) already lives in `src/agent/turn.rs` (`repeated_tool_failure` history scan) and injects the schema for a tool whose call failed identically twice. The sanitizer should feed that path clean text, and the schema injection should carry the normalized schema. Read that code before editing.

**Verification:** `cargo test` at the repo root (`C:"C:/AgenticCoder/AgenticCoder`); run it UNPIPED and read `$LASTEXITCODE` per the project constitution (a piped exit code is the pipe's). Build must be warning-free (`#![deny(warnings)]` at both crate roots) — never add `#[allow(...)]`.

**Config anchor:** endpoint definitions live in `endpoints.toml` and per-endpoint capability flags are consumed via `Capabilities` (`src/provider/mod.rs`); follow the existing per-endpoint config pattern rather than inventing a new one.
