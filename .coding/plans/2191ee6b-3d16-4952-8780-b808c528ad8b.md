# Plan: Fix: share parent WebView2 environment with the child (with_environment)

## Goal
Make the child WebView2 share the parent's WebView2 environment so it registers as a 2nd CDP target on port 9222, letting the agent's game_* tools attach. Root cause (source-confirmed in research plan 08710212): Tauri Window::add_child builds the child WITHOUT with_environment, so wry creates a fresh CoreWebView2Environment whose --remote-debugging-port=9222 fails to bind (parent already holds it) → child never appears on CDP. Fix: pass the parent main webview's environment to the child builder via WebviewBuilder::with_environment.

## Kind
implementation

## Context
Research plan 08710212 (Complete) confirmed: (1) live probe of localhost:9222/json shows ONE target (app page) even after opening Browser tab + loading google.com — child is absent from CDP; (2) Tauri add_child (tauri-2.11.5/src/window/mod.rs:1129) does not call with_environment; (3) wry (wry-0.55.1/src/webview2/mod.rs:133-136) reuses parent env ONLY when pl_attrs.environment is Some, else create_environment (line 283) makes a fresh env with its own additional_browser_arguments (line 327); (4) wry docs (lib.rs:470) explicitly say 'The webview must use the same environment as the caller webview. See with_environment.' The fix APIs: app.get_webview('main') -> Option<Webview> (Manager trait, lib.rs:671); Webview::environment() -> ICoreWebView2Environment (#[cfg(windows)], webview/mod.rs:189); WebviewBuilder::with_environment(env) -> Self (#[cfg(all(feature='wry', windows))], webview/mod.rs:1256). The 'unstable' feature is already enabled in src-tauri/Cargo.toml. Project is Windows-only. The about:blank cleanup in is_app_url is a separate latent-bug nice-to-have, NOT the active cause — leave it for now to keep this fix focused. Regression-test caveat: the with_environment path uses Tauri's add_child runtime API, which cannot be unit-tested without a running Tauri app/window; the standing verification is the live probe (rebuild + restart + Invoke-RestMethod localhost:9222/json shows TWO targets + game_snapshot succeeds). Existing cargo tests verify no regression in the rest of the browser code.
