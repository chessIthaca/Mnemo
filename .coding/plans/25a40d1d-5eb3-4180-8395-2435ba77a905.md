# Plan: Evaluate craby.rs for path (b) native shell

## Goal
Evaluate craby.rs (and the broader path-b native-shell option) against path (a)'s known-good baseline, to decide whether path (b) offers enough strategic upside to justify its M/L effort — or whether path (a) should just ship.

## Kind
research

## Context
Architecture decision in flight (2026-12). Path (a) — bare Tauri WindowBuilder + two ordered add_child webviews (game browser first→9222→CDP; agent chat second→React, no CDP) — is fully de-risked by spike fa099902 (draw order, tab switching, crash isolation all proven). Path (b) — non-Tauri native shell — is the unknown. The memory flagged "React Native/craby.rs (unknown, needs web_fetch)" as the blocker; web_fetch (plan 64ab0050) has now shipped, so the research is unblocked. The payoff of path (b) per the scoping memo (.coding/scoping-native-mix-architecture.md §3, §5) is eliminating the 83-command IPC serialization layer via direct Rust API calls into the myharness brain. The make-or-break requirements any path-(b) candidate must meet: (1) WebView2 on Windows with CDP attach for the game browser, (2) host a second webview rendering React without CDP, (3) creation-order control so the first webview grabs port 9222, (4) production maturity on Windows. craby.rs is the specific candidate to evaluate; its category (React Native binding? native shell? webview host?) is itself unknown.

## Steps
- [x] 1. **Locate + identify craby.rs** — fetch candidate URLs to find the project: try https://crates.io/crates/craby , https://docs.rs/craby , and a web search (https://html.duckduckgo.com/html/?q=craby.rs+rust). Determine its category: React Native Rust binding? native window shell? webview host? something else? Record the canonical repo/docs URL and a one-paragraph description of what it actually is.
- [x] 2. **Evaluate CDP + WebView2 on Windows** — the make-or-break for the game browser. From craby.rs's docs/source/readme, determine: does it use WebView2 on Windows? Does it expose a CDP debug port (9222) the agent's game_* tools can attach to? If it uses a non-WebView2 engine (Ultralight/WebKit like iced_webview — already NO-GO), flag it immediately. This single requirement can short-circuit the whole evaluation.
- [x] 3. **Evaluate multi-webview hosting + creation order** — can craby.rs host TWO sibling webviews in one window: a game-browser webview (created first, grabs 9222, gets CDP) and an agent-chat webview (created second, renders the existing React bundle, no CDP)? Does it expose creation-order / env control? Compare to path (a)'s confirmed add_child ordering.
- [x] 4. **Evaluate the IPC story** — path (b)'s stated payoff is eliminating the 83-command Tauri IPC layer via direct Rust API calls into the myharness brain. Does craby.rs enable that (Rust↔JS without a command serialization layer), or does it reintroduce its own IPC bridge? If it still needs a JS↔Rust bridge, the payoff shrinks and path (b) loses its main advantage over (a).
- [x] 5. **Assess maturity + Windows readiness** — is craby.rs production-ready or experimental? Last commit/release date, stars/activity, Windows testing evidence, known Windows blockers. A path-(b) candidate that isn't Windows-mature is a non-starter regardless of architecture fit.
- [x] 6. **Write go/no-go memo** — synthesize findings into .coding/craby-evaluation.md: what craby.rs is, how it scores on the four make-or-breaks (CDP/WebView2, multi-webview+ordering, IPC, maturity), a direct comparison vs path (a) (effort S vs M/L, what each keeps/loses), and a clear recommendation: ship path (a), or invest in path (b) via craby.rs. Update the in-flight architecture memory with the verdict.
