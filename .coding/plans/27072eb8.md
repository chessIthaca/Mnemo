# Plan: Worker tabs show why a worker failed

## Goal
When a worker fails, for example on a provider 429 or after tool errors, its thread in mission control and in the lead's side worker panel shows the error text as a clear failure block, with a hint that the lead can resume it. A provider error the worker is retrying shows as a transient note.

## Kind
implementation

## Context
The user reported on 2026-11-02 that two workers failed on an Ollama 429 ("you have reached your session usage limit ...") and the error was not visible in either worker tab. Today the backend stores the failure in the worker record's `error` field (src-tauri/src/mnemo2/team.rs, `fail_worker`), and team_status shows it. The UI does three things with it:
- `workerFromRecord` in mnemo2/src/lib/store.ts (around line 2261) copies `record.error` only into `summary`;
- `WorkerThread.svelte`, which both WorkerDetail.svelte and WorkerPanel.svelte render, shows no error;
- `applyWorkerLiveEvent` in mnemo2/src/lib/workerThread.ts has no case for the agent event kind "error". It carries `error` / `message` and `retrying` (see LeadAgentEvent in mnemo2/src/lib/types.ts and SerializableAgentEvent::Error in src-tauri/src/mnemo2/runtime.rs), so the event is silently dropped.

Decisions:
- Add an explicit `error: string | null` to the UI `Worker` type (mnemo2/src/lib/types.ts), filled from the record. Keep `summary` behaviour as it is, so the list rows don't change.
- WorkerThread shows a failure block at the end of the thread when `worker.status === "failed"` and `error` is set. It uses the danger token, the full error text (wrapped, selectable, no truncation) and the line "The lead can resume this worker on another model." Mnemo2 has no user-facing resume button here, and none is added.
- In applyWorkerLiveEvent, an "error" event with retrying true becomes a muted transient note ("Provider error, retrying: ...") that is replaced or cleared when streaming resumes. With retrying false it becomes a thread entry of a new kind, error, rendered in the danger colour. Follow how the lead chat (mnemo2/src/lib/leadState.ts and LeadChat.svelte) already shows lead errors and retries, and reuse its wording and styles where it has them.
- File ownership: plan 966429b4 is in flight and owns ToolActivity.svelte, LeadChat.test.ts and mnemo2/src/test/previewScenes.ts. This plan must not touch those three files. It adds no preview scene.

Verification, from mnemo2/: `npx svelte-check --tsconfig ./tsconfig.json`, `npx vitest run src/lib src/components`, `npm run check:no-mock`.

## Acceptance scenarios
- A worker whose record has status failed and error "provider error: ... 429 ... usage limit" shows that full text in a red failure block at the end of its thread, in mission control and in the lead's side panel.
- A live "error" event with retrying=true shows a muted "retrying" note that disappears when text streams again; retrying=false adds a red error entry.
- A working or completed worker shows no failure block; mission-control list rows look as before.
- svelte-check is clean, and vitest over src/lib and src/components passes.
