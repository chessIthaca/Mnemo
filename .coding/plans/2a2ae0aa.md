# Plan: Watcher root cause: .coding artifacts indexed but never watched

## Goal
Fix the watcher's indexed-but-never-watched asymmetry so a write to any `.coding/` artifact the content index covers (knowledge, plans, reviews, skills, backlog.jsonl) triggers a debounced incremental pass instead of leaving those FTS rows permanently stale. The trigger set must be made EQUAL to the index's coverage set by construction: introduce one shared `pub(crate)` predicate for the app's own SQLite store family (codegraph.db + memory.db and their -wal/-shm/-journal sidecars) and use it from BOTH `should_search` (what gets indexed) and `is_indexable_path` (what triggers a pass), so the two sets cannot drift apart again. That family is the only exclusion the self-trigger-loop argument actually requires, since those are the only files an index pass writes itself. The motivating defect, its two mechanisms, the exact code anchors and the regression-test design are in the context field; this is deliberately NOT a contained one-line fix (it adds shared cross-module surface), hence kind=implementation.

## Context
MOTIVATING DEFECT (live 2027-01-25, user report: "there is no one else changing files, other than mnemo, so it is a bug"): files under `.coding/` are indexed by the content index but never watched. Writing `.coding/knowledge/*.md`, `.coding/plans/*.md`, `.coding/reviews/*.md` or `.coding/backlog.jsonl` fires NO watcher event, so those FTS rows stay stale until an unrelated non-.coding file happens to change, the app restarts, or someone rebuilds manually. Observable symptom: a `search` reports "content index stale for N file(s) - serving tree-walk results" with nobody else editing the tree, and the very next query is clean only because an unrelated edit triggered a pass. In an artifact-heavy session (plans, memories, reviews) the staleness is permanent, not a lag. Diagnosed and recorded in BUG memory / .coding/knowledge/bug/2027-01-11-content-index-staleness-root-causes-coding-index.md.

THE DEFECT IS ONE OF TWO MECHANISMS (the other is NOT this plan's scope). Mechanism 1 (transient, by design): the 800 ms watcher debounce — src-tauri/src/main.rs:2066 spawns GraphWatcher::spawn(graph, root, Duration::from_millis(800)), and watcher.rs debounce_loop (:201-213) sleeps that quiet period before running a pass; the adaptive inline repair shipped under plan 90fab97e (commits 06276aa + d8152f7) covers that window. Mechanism 2 (PERMANENT — what this plan fixes): an ASYMMETRY between the index's coverage and the watcher's trigger set.

THE ASYMMETRY, exactly:
- Index side: `should_search` (src/tool/agent/search.rs:85-132) accepts every `.coding/` file EXCEPT the app's SQLite stores, which it excludes deterministically via a local `const DATA_FILES` (search.rs:109-118): codegraph.db, codegraph.db-wal, codegraph.db-shm, codegraph.db-journal, memory.db, memory.db-wal, memory.db-shm, memory.db-journal. Its own comment (:100-107) states the exclusion is loop-safety, not searchability: the graph DB "changes during every pass, so it would re-index forever". So `.coding/knowledge/*.md`, `.coding/plans/*.md`, `.coding/reviews/*.md`, `.coding/plans/stack.json`, `.coding/instance.json`, `.coding/skills/*.toml` and `.coding/backlog.jsonl` ALL get content rows + cg_files mtime rows.
- Watch side: `is_indexable_path` (src/codegraph/watcher.rs:52-82) rejects ANY path with a `.coding` component — a BLANKET rule at line 61: `if crate::tool::agent::search::is_ignored_component(name) || name == ".coding" { return false; }`. Its doc (:34-46) admits the consequence verbatim: "Those files' content rows simply refresh on the next pass."
- Net: files the index covers can never trigger the pass that would refresh them — the indexed-but-never-watched class itself. It also contradicts the watcher module doc's own stated contract (:17-19, :35-38) that it "Mirrors walk_searchable's coverage".

WHY THE BLANKET RULE IS OVER-BROAD: it existed for ONE reason — the codegraph DB is written DURING an index pass, so watching it self-triggers a reindex loop (watcher.rs:40-46). That reason is satisfied exactly by the DATA_FILES set the search tool already uses. The doc's second stated worry (per-step bookkeeping "would churn passes all session") does not survive inspection: `instance.json` is written ONLY on launch (src/instance_marker.rs:47-55 — last-writer-wins, no heartbeat, no periodic refresh), and `stack.json` only on plan-step transitions; both are debounced into one pass per burst, and passes are incremental (content-hash gated). Nothing an index pass writes lives outside the DATA_FILES family, so the narrowed exclusion is provably loop-free.

FIX DIRECTION (make the two sets equal by construction — no index-coverage change): extract search.rs's `.coding` store exclusion into ONE shared `pub(crate)` predicate taking a ROOT-RELATIVE path, e.g. `pub(crate) fn is_coding_data_file(rel: &Path) -> bool` (same semantics: first component `.coding` AND file name in DATA_FILES). `should_search` calls it (pure refactor — behaviour-preserving). `is_indexable_path`'s `under_base` keeps the `is_ignored_component` loop for the search ignore rules and then returns `!is_coding_data_file(rel)` instead of rejecting `.coding` wholesale. Keep the canonical-form fallback (:71-81) intact — it shares `under_base`, so it inherits the fix automatically.

REGRESSION-TEST DESIGN (must fail on the current code and pass after): (a) a LIVE watcher test in src/codegraph/watcher.rs mirroring `watcher_reindexes_on_new_source_file` (:378-408) — tempdir root, write `a.rs`, `CodeGraph::open_in_memory(root)`, `index(None)`, `GraphWatcher::spawn(graph, root, Duration::from_millis(100))`, then write `.coding/knowledge/live-artifact.md` containing a unique marker and poll `graph.search_content(marker, 10)` for 200 x 50 ms, asserting a hit. On the CURRENT code no event fires, no pass runs, the marker never reaches the content index → the test fails; after the fix it passes. It must use the existing 200 x 50 ms poll pattern (FSEvents on macOS delivers events after a latency window — the macOS CI leg has burned this project twice, run 35521221353). (b) unit assertions on `is_indexable_path`: `.coding/knowledge/x.md`, `.coding/reviews/r.md`, `.coding/plans/90fab97e.md`, `.coding/backlog.jsonl` → true; `.coding/codegraph.db`, `.coding/memory.db-wal` → false (the first group also fails today).
