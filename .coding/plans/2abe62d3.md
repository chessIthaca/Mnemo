# Plan: Profile appendStreamingText per-flush concat (mem-perf LOW 5) — gate the array-chunks fix on real numbers

## Goal
Profile the appendStreamingText per-flush string-concatenation cost at realistic sizes/cadences and decide by a pre-registered gate whether the array-chunks+join-on-finalize fix is worth implementing — closing LOW 5 either as "profiled, not worth it" (documented numbers) or via an implementation sub-plan.

## Kind
research

## Context
Mem-perf review LOW 5 (.coding/reviews/2027-01-06-full-review-memory-perf.md:60-67) is explicitly profiling-gated: "Only if profiling ever shows it: accumulate chunks in an array and join on finalize... Do not do this speculatively." Facts gathered: appendStreamingText (useAgentStore.ts:1020) does `streamingText + text` per rAF flush (V8 rope concat — O(1) alloc, no copy) plus an activity-log mirror (appendAnswerEntry, agentEventReducer.ts:242 — same concat + ≤300-entry array copy); appendStreamingReasoning has two more accumulation sites; the rAF buffer concats per delta (useAgentEvents.ts:381-390). The streaming display renders PLAIN text (Message.tsx:362-378 — markdown re-parse already avoided), so the per-frame O(n) work is the DOM text-node update (flatten+copy) that ANY full-text display needs. Bounds: SANE_MAX_OUTPUT_TOKENS=32K tokens (≈128 KB response), 64 KiB rAF-buffer cap, review reference 100 KB/~60 flushes. The fix would touch 4 accumulation sites + 2 display paths + the buffer — wide change for bounded churn. tsconfig includes only src/, so frontend/bench/ is inert to tsc/vite/vitest. Node's V8 ≈ WebView2's V8 (primary platform); JSC (macOS) also uses rope strings — directionally valid, noted as caveat.
