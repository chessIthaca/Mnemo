# Plan: Laya routes once: Mnemo2 workers at dispatch, Mnemo1 sessions at their first prompt

## Goal
Laya classifies a Mnemo2 worker's step spec once at dispatch, and a Mnemo1 session's first prompt once, with a shared three-label question and a calibrated gate. It never switches a running session by itself, only nudges. Every route, override (lead or user), nudge and outcome is logged as calibration and training data.

## Kind
implementation

## Context
The full design is .coding/design/mnemo2-laya-routing.md (committed 661fe04b), written after marcreichel/laya-router. Every step below is a spec taken from that doc's §5. When a step cites "design §4.x", read that section of the doc: it holds the exact rules (question §4.3, gate §4.4, modes §4.5, overrides and nudges §4.6, log rows §4.7, outcome labels and eval §4.8, config §4.9, surfaces §4.10, failure modes §4.11, Mnemo1 §4.12). The DispatchRoutingDecision struct is in §4.4.

Why: Mnemo1's per-turn gate (src/agent/turn.rs route_turn_start ~1243) currently also runs on every Mnemo2 worker turn, because workers are top-level sessions on the lead's engine, not subagents. It classifies the wrong text (plan headers, now the fixed KICKOFF) with a two-label question (model_routing.rs routing_question ~109) at a guessed 0.80 gate. All 94 logged decisions are 'architectural', with mean confidence 0.42 and none cleared. With enforce on it would switch a worker's model every turn, overriding the lead's tier and dropping the prompt cache. Mnemo1's own sessions have the same design weaknesses. Model choice today is the lead's tier per dispatch (team.rs lead_model_choice ~930, tier required ~1660). Manual changes (mission control change_model ~3268, team_resume) teach nothing.

Decisions already taken:
- Route ONCE: Mnemo2 at team_dispatch, on the step text + brief (never the plan boilerplate); Mnemo1 on a session's first prompt of at least 3 words.
- Never switch automatically afterwards; only nudge (one per worker or session).
- A manual model choice always wins and is logged.
- Shared kernel question in src/agent/route_question.rs: neutral labels trivial/routine/hard, keyword descriptions, folding of un-offered labels, default gates 0.475 for 3 labels and 0.60 for 2 (provisional until the step 9 eval).
- Mnemo2 modes off/shadow/suggest/auto, default off.
- Mnemo2 sessions opt out of the per-turn gate via SpawnOptions.skip_turn_routing.
- Mnemo1's step-lane ladder and reflex are out of scope.
- Logs are append-only JSONL under ~/.mnemo/laya/training/: dispatch_routing.jsonl (Mnemo2) and session_routing.jsonl (Mnemo1). routing.jsonl keeps its row shapes.

Order: steps 1 and 2 in parallel. Step 3 after 2. Step 4 after 1 and 3 (high risk). Step 5 after 4, step 6 after 5. Step 7 after 1 and 2 (high risk), parallel with 3-6; it shares team.rs and runtime.rs only for one ignoring RoutingNotice match arm each (record an interface before parallel dispatch). Step 8 after 6 and 7. Step 9 is the lead's verification.

Verification for every step:
- root: cargo clippy --all-targets -- -D warnings; cargo test --lib.
- src-tauri: cargo clippy --manifest-path src-tauri/Cargo.toml --features mnemo2 --lib --tests --bins -- -D warnings; cargo test --manifest-path src-tauri/Cargo.toml --features mnemo2 --lib --bins; cargo build --manifest-path src-tauri/Cargo.toml --bins.

- No new #[allow(...)] anywhere.

## Acceptance scenarios
- With Mnemo2 routing mode off, team_dispatch behaves exactly as today: no classifier call, no log row, and `tier` is required.
- With mode shadow, every implementation dispatch appends one `route` row to dispatch_routing.jsonl with Laya's tier, confidence and the lead's tier; the worker runs on the lead's tier, and the dispatch result says what Laya would pick.
- With mode suggest, `tier: "auto"` runs on Laya's tier when it clears the gate, and is refused with "Laya is unsure (x.xx); pass a tier" when it does not.
- No Mnemo2 worker, audit or lead session is classified per turn or writes routing.jsonl rows; Mnemo1 sessions with routing on still are classified (first prompt only after step 7).
- A user's model change in mission control appends a `user_reroute` row, and a lead `team_resume` onto another tier appends a `lead_reroute` row.
- Three failing or repeated tool calls in a row produce exactly one nudge notice and never change the model, in both Mnemo2 (to the lead) and Mnemo1 (in chat).
- A merged worker's `outcome` row carries a derived label, and the plan's review report shows Laya and Routed-by columns in the Effort table.
- A dispatch never waits more than 3 s on Laya.
- Mnemo1 with routing on classifies only a session's first prompt, switches the model at most once (enforce on), and afterwards only suggests; a manual pick turns routing off for that session and is logged; a resumed session is never routed; with routing off Mnemo1 behaves exactly as today.
- Mnemo1 and Mnemo2 ask Laya byte-identical questions for the same offered labels.
