# Plan: Command-class safety rules + safety.toml cleanup

## Goal
Add a "command-class" safety rule kind that auto-approves a shell command based on its normalized operation (primary commands, ignoring cosmetic output filtering like Select-String patterns and redirections) while still prompting for command-chaining (`&&`, `;`, `||`) or unknown commands. Add a "Mark Safe (same operation)" approval button that saves such a rule. Then consolidate the ~15 near-duplicate literal shell rules in `.coding/safety.toml` into a few command-class rules.

## Context
PROBLEM: safety.toml has ~15 near-duplicate `shell` rules that differ only in cosmetic output filtering (Select-String patterns, Out-String, 2>&1, etc.). The "Mark Safe" button (add_rule) writes an exact escaped literal `^shell:<full command>$`, so every variant gets its own rule. The only alternative, "Allow for project" (add_rule_broad → `^shell:`), is far too wide. There's no middle ground.

DESIGN (agreed with user): A command-class rule normalizes a shell command into a "safety class" = the set of PRIMARY commands across all pipeline segments, ignoring filter cmdlets and redirections. Two commands with the same class are equivalent (auto-approve). Command-chaining operators (`&&`, `;`, `||`, `&`) split into multiple statements; if ANY statement's primary is unknown/unapproved, the whole command prompts (fail-safe). This closes the chained-command hole that pure prefix-regex can't (`^shell:cargo test` would match `cargo test && rm -rf x`; the classifier splits on `&&`, sees `rm` unknown → prompt).

ARCHITECTURE:
- src/safety_rules.rs: `Rule` struct {tool, pattern, regex} + `SafetyRules` (file-backed, mtime-checked). `is_safe(tool, args)` iterates rules: `r.tool == tool && r.matches(signature)`. signature = `<tool>:<key_argument>`; for shell, key_argument = the full `command` string. `add_rule` writes literal `^<sig>$`; `add_rule_broad` writes `^<tool>:`. Rules serialize as `[[rule]] tool=... pattern=...`. `RuleEntry` is the TOML shape. FILE_HEADER is prepended on persist.
- src/agent/dispatch.rs:163 calls `sr.is_safe(&tc.name, &parsed_call.arguments)`.
- src-tauri/src/ipc/agent.rs: `add_safety_rule` (→add_rule), `add_safety_rule_broad` (→add_rule_broad), `save_safety_rules` (→write_raw). Registered in main.rs invoke_handler.
- frontend: ApprovalPrompt.tsx has "Mark Safe" (addSafetyRule) + "Allow for project" (addSafetyRuleBroad) buttons. SafetyRules.tsx is a raw TOML editor. tauri.ts has addSafetyRule/addSafetyRuleBroad bindings.

KEY DESIGN DECISIONS:
1. New rule kind via a `kind` field on RuleEntry: `"literal"` (default, current behavior — exact regex match) or `"command_class"` (shell-only; pattern stores the approved safety-class string, e.g. "cargo test" or "cd;npm run build"). Backward compat: missing `kind` = literal.
2. The classifier lives in a new module `src/safety_rules/cmd_class.rs` (or inline). It tokenizes PowerShell-ish command strings: split on `;` `&&` `||` `&` (respecting quotes), then within each statement split on `|` into stages; the FIRST stage of each pipeline is the primary (external command), classified by command+first-arg (subcommand) only; subsequent stages are filters (Select-String, Out-String, Select-Object, Where-Object, Sort-Object, ForEach-Object, Out-Null, Out-Default, Out-Host, Tee-Object, Group-Object, Measure-Object) → ignored. Redirections `2>&1` `2>$null` `>file` `n>file` stripped. `cd <dir>;` prefixes are kept as primaries (so `cd frontend; npm run build` class = "cd;npm run build"). Unknown primaries → the whole command is unclassifiable (returns None → never auto-approved by a class rule).
3. A command_class rule matches when: tool=="shell" AND classify(command) == Some(rule.pattern). is_safe checks class rules by computing the class and comparing; literal rules keep using regex.
4. New button "Mark Safe (same operation)" → add_safety_rule_class IPC → add_rule_class(tool, args): classifies the command; if Some(class), saves a command_class rule with pattern=class; if None, returns an error so the UI can fall back / inform the user it can't be classified.
5. safety.toml cleanup: replace the ~15 cargo/npm/tsc/git literal shell rules with ~5 command_class rules (cargo test, cargo build, cargo check, cd frontend; npm run build, cd frontend; npx tsc, git diff, git branch, git log). Keep the spawn_agent and git:merge literal rules (not shell, not applicable).

SAFETY PROPERTIES TO PRESERVE: never_auto tools still always prompt (dispatch.rs:159 force_prompt gate unchanged). Unknown/unclassifiable commands always prompt. Chained commands with any unknown segment always prompt. Non-shell tools unaffected (class rules only apply to shell).

## Steps
- [x] 1. **Add the command classifier module** — Create `src/safety_rules/cmd_class.rs`. Implement `pub fn classify(command: &str) -> Option<String>` returning the normalized safety class (semicolon-joined primaries) or `None` when unclassifiable. Algorithm: (1) tokenize into statements by splitting on `;`, `&&`, `||`, `&` at top level (NOT inside single/double quotes — track a simple quote state machine; treat backtick as a quote char for PowerShell); (2) for each statement, strip leading/trailing whitespace and skip empty; (3) strip redirection tokens via regex before splitting pipeline: `\d*>&\d*`, `\d*>\S+`, `\d*>\$null`, `2>&1` etc. — remove them; (4) split the statement on `|` at top level (quote-aware) into stages; (5) the FIRST non-empty stage is the primary — parse its first 1-2 tokens (command + optional subcommand like `test`/`build`/`diff`/`run`/`clippy`); if the first token is `cd`, the primary is just `cd` (drop the dir); (6) stages 2..N are filters — verify each starts with a known filter cmdlet (Select-String, Out-String, Select-Object, Where-Object, Sort-Object, ForEach-Object, Out-Null, Out-Default, Out-Host, Tee-Object, Group-Object, Measure-Object); if a non-first stage is NOT a known filter, return None (unclassifiable → prompt); (7) collect primaries, join with `;`. Return None if any primary's command is unknown (not in a SAFE_COMMANDS set: cargo, rustc, npm, npx, node, git, Get-ChildItem, Get-Location, Get-Item, ls, dir, echo, Write-Output) OR if a pipeline has a non-filter non-primary stage. Add a `#[cfg(test)] mod tests` block with: `cargo test 2>&1 | Select-String -Pattern x` → Some("cargo test"); `cargo test` and `cargo test 2>&1 | Select-String -Pattern y` → same class; `cd frontend; npm run build | Select-Object -Last 5` → Some("cd;npm run build"); `cargo test && rm -rf x` → None; `cargo test123` → None (unknown command); `git diff a.ts` and `git diff b.ts` → Some("git diff"); quoted semicolon `"a;b"` not split; `(Get-Item x).LastWriteTime = Get-Date; cargo build` → None (the assignment statement is unclassifiable).
