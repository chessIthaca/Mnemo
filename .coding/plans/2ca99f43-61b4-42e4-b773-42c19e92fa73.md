# Plan: Slim the volatile tail: header-first CURRENT STEP + memory cap

## Goal
Shrink the volatile system tail so each complete_step/new-turn cache reprocess costs fewer tokens: render CURRENT STEP from the step's bold header (with a truncated fallback for headerless steps) instead of the full body, and cap recalled-memory content at 160 chars per entry instead of 300.

## Kind
implementation

## Context
Post-R5 state: the provider request now ends with byte-stable CONTEXT_FOOTER (feat/prompt-cache-context-footer, committed 31319a3), so per-complete_step/new-turn the ONLY reprocessed bytes are the volatile tail message (workflow state + memories). The tail is still fat: CURRENT STEP renders the FULL step body (prompt.rs:260-264 — bodies in this codebase are 200-700 chars vs headers ~40-60), and recall entries cap content at 300 chars each (prompt.rs:210). The Step struct (src/workflow/plan_file.rs:98-107) already carries `header: Option<String>` (the bold **Header** punchline, extracted by plan_file) and `text` (full body). Existing tests use headerless short steps ("step 1") so the truncate fallback keeps them green (executing_prompt_shows_plan asserts contains("step 1"), volatile_tail_includes_workflow_and_memories asserts contains("memory text") + "CURRENT STEP"). GOAL stays full (rarely changes, only on update_plan). The constant instruction paragraphs in the tail are reprocessed per change too — a possible follow-up is splitting the tail into [volatile progress] + [stable instructions] messages (the 28→29 trace precedent shows prefix reuse when only the tail-changed message differs), but THIS plan is the user-chosen minimal shrink: header-first CURRENT STEP + 160-char memory cap.
