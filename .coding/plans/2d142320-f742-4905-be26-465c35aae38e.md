# Plan: Diagnose memory cleanup stuck at 100%

## Goal
Determine whether the user's stuck-at-100% memory cleanup is still running or wedged, explain the 100% display, and produce a diagnosis with concrete live checks + fix options. Research only — no source changes.

## Kind
research

## Context
User reports Settings → Memory "Clean up memory" appears stuck at 100% (with a provider configured in config). Code read so far: engine src/memory/maintenance.rs ticks (Consolidating, i+1, total) AFTER each session's consolidate_session returns, then a label-only (Vacuuming, 0, 0) tick, then store.vacuum(). IPC layer src-tauri/src/ipc/memory_maintenance.rs is fire-and-forget with a module-level BUSY AtomicBool (second invocation errors "a memory maintenance operation is already running"), best-effort emits on channel memory://maintenance. Frontend MemorySection.tsx computes pct = Math.round(done/total*100) when total>0 (so total≥200 makes done=total-1 render as "100%"), and renders total==0 phases as a full-width pulsing bar (no number) with caption like "vacuuming…" — visually indistinguishable from a bar stuck at 100%. Cleanup with a configured default provider makes LLM calls per consolidated session (summarize + extract), so the leading hypotheses are: (a) still running — stuck inside the last session's LLM call (slow or hung endpoint, timeout unknown) while the rounded bar reads 100%; (b) in the VACUUM tail (full-width pulse looks like 100%); (c) genuinely wedged (lost events / dead task).
