# Plan: Idle worker pools above the slot count are removed (soft pool cap)

## Goal
Pool checkouts (.worktrees/pool-<n>) stop accumulating: whenever a pool is given back, when the slot count is lowered, and at Mnemo2 start, every FREE pool whose index is above the worker slot count is deleted, so at rest the pool count is at most the slot count. Dispatch is never refused because of pools; the cap is soft.

## Kind
implementation

## Context
WHY: each pool keeps its target/ and node_modules/ (10-15 GB each in this repo). Pools are never removed today (spec .coding/knowledge/spec/2026-11-23-worker-checkouts-are-reused-pool-folders-that-ke.md: "Release ... never removes the folder"), and a pool is held by ANY unmerged worker record (in review, conflict, failed), not only running ones, so the folder count rises to the historic peak of held checkouts and stays there. On 2026-11-23 the user found 5 pools (~52 GB) with 3 slots. The user chose a SOFT cap over a hard cap: a hard cap (pools <= slots) would block new dispatches while workers sit waiting for review, because slots count only running workers (TeamRuntime::active_workers_for_slots, src-tauri/src/mnemo2/team.rs:913) while pools are held by every record whose `worktree` is set (held_checkouts, team.rs:431).

DECISIONS:
1. Allocation is unchanged (src/app/worktrees.rs provision_pool_checkout_impl: lowest free pool reused, else max+1). Dispatch never fails for a pool count reason; a pool above the slot count may be created while lower ones are held.
2. Trim rule: a pool `pool-<n>` is removed only when ALL hold: n > keep (keep = current slot count); not in the `held` list (same_checkout_path comparison); passes the same `free` test provision uses (ensure_registered_pool_checkout guard, HEAD detached, `git status --porcelain -uall` empty); its cross-instance claim (acquire_pool_claim) is obtained and the free test passes again after claiming. Anything else is skipped with an eprintln and never touched. Uncommitted work is never deleted. Pools at or below keep are never removed, even if idle (they are the warm caches).
3. Removal: with the claim held, `git worktree remove --force <pool>` run from main_root (--force because ignored caches are present; the free test already proved no tracked/untracked work). If the folder still exists afterwards (Windows: npm workspace junctions such as node_modules/mnemo2 survive git's removal, seen on 2026-11-23), delete it with std::fs::remove_dir_all, which does NOT follow symlinks/junctions (Rust std guarantee since 1.58.1) — a link's target outside the pool must survive. Then `git worktree prune`. A removal failure is reported (eprintln) and the trim continues with the next pool; the function returns the removed paths. Highest index first.
4. Lock order is merge_lock -> checkout_pool_lock (dispatch and audit already take them in that order). The team-level trim takes checkout_pool_lock itself, so it may be called while merge_lock is held but must never be called while checkout_pool_lock is already held. It reads `held` from the records after taking the lock.
5. Call sites (team runtime): (a) after a successful merge's checkout cleanup (merge.rs, where cleanup_agent_worktree released the pool and the record's worktree was cleared/persisted); (b) after release_audit_checkout (audit.rs:550) releases a pool — call AFTER its checkout_pool_lock guard is dropped; (c) after deletion releases a pool (deletion.rs release paths); (d) at the end of set_slots after the new value is persisted (team.rs:931); (e) once in TeamRuntime::open after recovery. Trim errors never fail the caller's operation.
6. Multiple Mnemo instances may share a repo: another instance's held pool is on a branch (not detached) so the free test skips it; the claim file prevents racing a concurrent provision.

VERIFY: cargo test -p mnemo --lib app::worktrees; cargo test -p mnemo-app mnemo2::team; cargo clippy --workspace --all-targets -- -D warnings. The full .coding/checks.toml set before committing.

## Acceptance scenarios
- With 3 slots and free released pools pool-1..pool-5, after any merge (or Mnemo2 start) only pool-1..pool-3 remain on disk and in `git worktree list`; pool-4 and pool-5 folders are gone including leftover junction folders.
- A pool above the slot count that is held by a worker record, is on a branch, has uncommitted or untracked work, or has a live claim file is never removed.
- Removing a pool whose node_modules contains a junction/symlink to a directory outside the pool leaves that outside directory and its files intact.
- Lowering the slot count from 3 to 1 removes the free pools pool-2 and pool-3 right away and keeps pool-1 with its target/.
- A dispatch while every pool up to the slot count is held still succeeds by creating the next pool index (no refusal).

## Decisions
- 2026-11-23: no spec impact: Internal pool housekeeping; no OpenSpec capability covers pool folder lifetime (it is recorded in the .coding/knowledge spec record, which the step updates).
- 2026-11-23: 2026-11-23 (after audit auditTrimPools01): removal no longer deletes inside the locks. Replaces decision 3's removal mechanics: with the claim held and the free test re-passed, RENAME the pool folder to `<main_root>/.worktrees/trash-pool-<n>-<unix_ms>` (std::fs::rename, same volume, instant; a failed rename — locked file, a shell sitting in the folder — skips the pool with nothing touched), then `git worktree prune` (the registration goes because its folder is gone), then delete the trash folder OFF the caller's thread: `std::thread::spawn(move || std::fs::remove_dir_all(trash))`, detached, eprintln on failure. Every trim also sweeps leftover `.worktrees/trash-pool-*` folders (a crash or failed delete) the same way in the background — that is the retry path, so no pool can become a permanent half-deleted zombie. `trash-pool-*` names never match pool_index, so allocation ignores them. remove_dir_all never follows links (std guarantee). The trim still returns the pool paths it renamed away (they are no longer pools). This makes the trim fast under merge_lock/checkout_pool_lock/save_lock, which also answers the audit's latency and cleanup-under-save_lock points. The cleanup call site (sixth, team.rs cleanup) is accepted. Cross-instance release racing a trim (audit finding 3) is accepted: post-merge only, no work at risk.
