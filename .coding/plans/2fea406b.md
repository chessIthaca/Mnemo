# Plan: Fix missing pasted-image preview in Mnemo2

## Goal
Reproduce and fix the missing Mnemo2 pasted-image preview, with a regression test exercising the real conversion and composer path.

## Kind
bug_fixing

## Context
The user reported that pasting an image into Mnemo2 chat shows no preview, and confirmed Ctrl+V. Verified: Composer.svelte has `onpaste={handlePaste}`, converts clipboard files with the shared fileToAttachedDataUrl, appends them through actions.addLeadDraftImage, and renders `draft.images` as 52px `<img>` thumbnails. The Mnemo2 CSP allows `img-src data: blob:`. Existing Composer tests mock the converter, so the real clipboard→FileReader→data URL→store→`<img>` path is not covered. The running app's CDP endpoint at localhost:9222 is unavailable, so the symptom has not been reproduced in the live app; do not assume a root cause or make speculative UI changes. Work in mnemo2/. First add a faithful regression in mnemo2/src/components/Composer.test.ts named `a real pasted PNG renders its thumbnail before sending`: use a real PNG File and the real frontend/src/lib/attachImages.ts converter (no converter mock), dispatch a real paste, then assert the image is in the store and the rendered thumbnail has the same data:image URL. Run it against the unchanged component. If red, diagnose and fix that path, keeping ordinary text paste unaffected; if green, investigate the remaining live-only boundary (actual WebView2 clipboard behavior or stale running build), and report precisely what is and is not reproduced rather than inventing a fix. Add a regression test for any defect found; it must fail before and pass after. Verification: mnemo2 npm test, npm run check (0/0), npm run build. Do not touch Rust or the spawn code; a separate plan owns that.

User clarification: the failing paste was Ctrl+C on an image FILE in Explorer, then Ctrl+V in chat, not copied pixels. This explains why the real image/* item regression was green. Reproduce the Explorer-shaped clipboard: DataTransfer.items contains a file item whose type is empty (or otherwise not image/*), while DataTransfer.files contains the actual File with type image/png. Current imageFiles() only scans items and filters item.type.startsWith('image/'), so it ignores this clipboard. Fix by falling back to clipboardData.files when no image item is found, filtering File.type for image/*; deduplicate so ordinary image-item pastes are not attached twice. Add regression `an Explorer-copied PNG file renders its thumbnail before sending`: empty-type item plus image/png File in files must fail on the current filter (no attachment/thumbnail) and pass after. Keep the real-converter test and text-only paste behavior. The earlier test-only commit f5e9c9c remains useful coverage but is not the fix.
