# Plan: Audit UI freeze candidates: locks, blocking I/O, wait conditions

## Goal
Enumerate every code path reachable from the UI that can block the main thread or wait on a lock/file/database/subprocess/channel, verify past freeze fixes are still in place, and produce a ranked findings report with concrete fix recommendations.

## Kind
research

## Context
User reports the app freezes too often. Past diagnoses fixed: F1 blocking git-branch poll, F3 unbounded transcript, R1 main-thread set_size, R2 rAF buffering, N1–N6 perf findings — all merged. This is a NEW comprehensive sweep, not a re-diagnosis. Codebase: Tauri app, 96 #[tauri::command] handlers across src-tauri/src/ipc/*.rs, heavy lock usage (tokio Mutex on manager/agent_loops/config/workflow; std Mutex in approval.rs + browser_webview.rs), IPC files read/write sessions, traces, memory index, settings. Tauri v2 semantics: non-async commands run on the main thread → any blocking work there freezes the UI instantly. Deliverable: ranked report in .coding/reviews/.

## Steps
- [x] 1. **Enumerate sync vs async Tauri commands** — In src-tauri/src/ipc/*.rs, classify each #[tauri::command] as sync `fn` vs `async fn` (sync commands run on the Tauri MAIN thread in v2). For every sync command, check whether its body does file I/O, locking, subprocess, or webview interaction. Output: table of sync commands with blocking-body severity.
- [x] 2. **Audit std::sync locks for blocking + lock-order cycles** — Find std::sync::Mutex / RwLock / parking_lot locks taken on command or main-thread paths (known: ipc/approval.rs pending-approvals map, ipc/browser_webview.rs deferred_rect/state). Check: guard held across blocking work? std Mutex locked from a context where a tokio Mutex guard is already held (lock-order inversion vs manager→workflow→config chains in ipc/agent.rs)? Poisoning behavior?
- [x] 3. **Audit blocking file/DB I/O on IPC paths** — Check command handlers and event emitters for synchronous fs reads/writes (sessions, traces, memory index JSON/SQLite, settings.toml, backlog.json, .coding files) and any rusqlite/sqlx calls — flag any not behind async command + spawn_blocking, and any file written without atomic-rename that a reader could lock-contend on. Search: fs::read_to_string|fs::write|File::create|rusqlite|Connection::open in src-tauri/src.
- [x] 4. **Audit subprocess calls + channel waits for unbounded waits** — Verify the F1 git-poll fix is still intact (find the current git branch/status polling — search for Command::new("git") and interval/poll in src-tauri/src and frontend). Check every Command::output()/spawn in command handlers for main-thread execution. Check every oneshot/mpsc .recv().await reachable from a command (e.g. ipc/browser.rs ~line 44) for missing timeouts — a webview that never replies = permanent hang.
- [x] 5. **Audit WebView2/native calls + large event payloads** — Verify R1 (set_size off main thread) and R2 (rAF event buffering) fixes still present in ipc/browser_webview.rs + frontend. Look for large payloads emitted via app.emit (session lists, memory items, transcripts, trace events) that force big JSON parse/stringify on the webview main thread; check frontend for synchronous heavy work in event handlers (search frontend for listen( then JSON.parse / big array spreads).
- [x] 6. **Write ranked findings report** — Write .coding/reviews/ui-freeze-lock-audit.md: every candidate freeze site ranked by (likelihood × user-visible frequency), cross-referenced against past fixed items (F1/F3/R1/R2/N1–N6) with verified-still-fixed or regressed status, plus a concrete fix recommendation per finding. Write a semantic memory summarizing top findings + report path.
