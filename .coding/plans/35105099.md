# Plan: Keep test temp folders inside the dev tree and stop them leaking

## Goal
Every temp folder a cargo-run test (or anything else cargo runs from this workspace) creates lives under the checkout's own `target/tmp`, and a full `cargo test --workspace` leaves no new folders behind.

## Kind
bug_fixing

## Context
WHY: the user does not want build/test output outside the dev tree and its drive, and the leaked folders grow without bound (each review runs the full battery in every pool checkout and in the main checkout). tempfile's TempDir ignores delete errors on drop; on Windows an open handle (SQLite connection, a child process's cwd, a background thread still deleting) makes the delete fail silently.

DECISIONS:
1. Redirect, don't rewrite: set TMP, TEMP and TMPDIR for every process cargo starts via the workspace `.cargo/config.toml` `[env]` table, with `relative = true` (resolved against the folder holding `.cargo`, so each pool checkout gets its own `target/tmp`) and `force = true` (Windows always has TMP/TEMP set, so without force the entry is ignored). `std::env::temp_dir()` reads TMP first on Windows (GetTempPath2W) and TMPDIR on Unix, so the ~2,600 `TempDir::new()`/`tempdir()` call sites and the `std::env::temp_dir()` users follow without edits. Child processes the tests spawn (git, workers) inherit it.
2. Target folder: `target/tmp` (cargo's own CARGO_TARGET_TMPDIR location; `cargo clean` and the Mnemo2 pool trim remove it with the checkout). Installed/release builds are unaffected because [env] applies only to processes cargo launches; a dev `cargo run`/`tauri dev` app also uses it, which is intended.
3. No sweeper and no settings knob: fix the leaks at the source instead (step 2).
4. npm/vitest tests are out of scope.

REGRESSION TEST: `temp_dir_is_inside_the_checkouts_target_dir` in tests/integration/ci_workflow.rs (or the integration file that already hosts workspace-config guards). It asserts `std::env::temp_dir()` canonicalizes to a path under `<CARGO_MANIFEST_DIR>/target/tmp` (compare canonicalized, case-insensitive on Windows). Without the [env] entry it fails because temp_dir() is the user's system temp folder.

VERIFY: the exact `.coding/checks.toml` commands from the checkout root (cargo test --workspace; cargo clippy --workspace --all-targets; npm test --workspace mnemo2; npm run check --workspace mnemo2).

## Acceptance scenarios
- `cargo test --workspace` from the checkout root creates no new `.tmp*` folder in the user's system temp folder (count before/after equal).
- `std::env::temp_dir()` inside a cargo-run test resolves under `<checkout>/target/tmp`; the regression test `temp_dir_is_inside_the_checkouts_target_dir` passes and fails if the [env] entries are removed.
- From an empty `target/tmp`, a full `cargo test --workspace` leaves zero `.tmp*` folders in `target/tmp`.
- A pool checkout's tests use that pool's own `target/tmp`, not the main checkout's.
- `npm test --workspace mnemo2` and `node --test scripts/*.test.mjs` create their temp folders under `<checkout>/target/tmp`, not in the system temp folder; the guard tests `keeps os.tmpdir() inside the repo target/tmp` and `script tests keep os.tmpdir() inside the repo target/tmp` pass.

## Bug
Rust tests create their temp folders in the user's system temp dir (C:\Users\<user>\AppData\Local\Temp on this machine — outside the repo and on another drive) and many are never deleted: about 31,000 `.tmpXXXXXX` folders built up in two days (an earlier cleanup removed about 120,000 more). Measured on 2026-11-24: one `cargo test --lib` run of the root crate (3,761 tests) left 12 folders, two still holding `.coding/memory.db` with its `-wal` and `-shm` files and ten empty. Older leftovers also hold `.worktrees`, `team.json` and `transcripts`, so the mnemo-app/mnemo2 team tests and the integration tests leak too.
