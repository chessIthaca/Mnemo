# Plan: Right-panel width as a window fraction — fix 80% cap pinning + resize non-tracking

## Goal
Make the right-panel width a fraction of the window width — persisted, rendered, and dragged as a fraction with a sane clamp band and a guaranteed chat-column minimum — so it can never pin at a cap on a small window and always tracks window resizes.

## Kind
bug_fixing

## Context
Root cause (diagnosed 2027-01-16; BUG memory 97200cbc, knowledge file .coding/knowledge/bug/2027-01-11-plan-panel-pins-at-its-80-cap-on-startup-persist.md): the width is persisted as ABSOLUTE px — localStorage mh.rightPanelWidth (frontend/src/hooks/appearance.ts:30) read at store init (frontend/src/hooks/useAgentStore.ts:664), written by the px setter (:814-821), live-updated in-memory (:828) — and rendered as px with a render-time clamp [300, window.innerWidth×0.8] (frontend/src/components/layout/RightPanel.tsx:31-39). The drag path (frontend/src/App.tsx ResizeHandle :823-917) clamps px at commit against the window AT DRAG TIME, so the stored value reflects a past, larger window and is never re-normalized; the chat column is the flex-1 sibling (App.tsx:745) and absorbs every resize delta. FIX DESIGN: store + render a FRACTION — new localStorage key (e.g. mh.rightPanelWidthFrac in appearance.ts); render width as a percentage (style width `${frac*100}%`) so the browser tracks window resizes with no JS listener; ResizeHandle computes frac = clampedPx/innerWidth live and commits the frac; clamp band: min = max(300/innerWidth, 0.15), max = min(0.5, (innerWidth−480)/innerWidth) — the 480px chat-column minimum replaces the 0.8 ceiling; the legacy px value seeds the fraction on read (frac = clamp(legacyPx/innerWidth)) with no migration write. REGRESSION-TEST DESIGN: frontend/src/components/layout/RightPanel.width.test.tsx (vitest) — (a) legacy persisted px 831 + innerWidth 800 → the rendered panel width must NOT be 640 (the 0.8 cap); it must be ≤ the band max; (b) the panel width must change when innerWidth changes (resize tracking). Must fail against current code and pass with the fix. VERIFICATION: cd frontend; npm test and npm run build; cargo test at the root UNPIPED (read its test result: lines — agent.md). Docs: check docs/FEATURES.md for a right-panel resize description to sync.

Review round 1 (.coding/reviews/2026-09-18-right-panel-fraction-width-review.md): FINDINGS (0 high, 1 low) — L1: the band clamp was render-time-only, so a window shrink below ~960px could leave a band-violating percentage (up to 50% where the band at 800px wants ≤40%) until the panel next re-rendered. Fixed by rendering the width with the band caps INLINE — min(pct%, 50%, calc(100% - 480px)) — so the CSS layout engine re-clamps at every viewport (no listener, no stale clamp); the band constants are exported from appearance.ts (CHAT_MIN_PX=480, PANEL_MAX_FRAC=0.5) and shared by clampPanelFraction and the RightPanel style; the regression test now asserts the inline caps. Re-verified after the fix: full vitest suite green, tsc+vite build clean, cargo test 2410+16 green.

## Bug
On app open the right panel (Plan tab — the startup default) fills as much of the app as it can: the persisted absolute-px width (localStorage mh.rightPanelWidth; 831px on this box) pins at the render clamp's 80% ceiling whenever the restored window is ≤ ~1040px wide — the startup geometry clamp (plan 9ff59133, commit c9da825) now restores small windows (min 800×560), so the old px width dominates and the chat column is squeezed to a sliver. Second face of the same report: resizing the overall window keeps the tools panel at its px width while the flex-1 chat column absorbs the entire delta — the panel should track the window instead.
