# Plan: Harness-run deterministic verify at plan-step boundaries (backlog: costsaving verification section)

## Goal
Ship the harness-run deterministic verify layer at plan-step boundaries: (1) `[general.verify]` config — opt-in enabled flag + test_command (string, empty = the feature is inert) + timeout_secs (default 300); (2) a StepVerifyHandle that runs the configured command directly at each plan-step boundary (a successful skeleton complete_step) through the shell tool's multi-platform spawn idiom with a clean-cancel timeout, compresses output via the existing lever-2 compressor (output_compactor::compress) and feeds back a compact evidence note — exit status, failing test names, distinct error lines, counts — appended to the complete_step tool result, never full logs; (3) the item-1 reflex wiring — action=verify re-runs the checks at the lane-classification boundary with the note riding the volatile tail; retry/escalate already feed the shipped lane ladder; (4) the timeout path cancels cleanly (kill-on-drop) and surfaces as a normal triage-able failure-shaped note. Invariants: flag off = byte-identical behavior with zero process spawns; detailed sub-step ticks never verify; a failing verification keeps the tick's success (the note carries the failure signal); multi-platform neutral; no new dependencies; docs/costsaving.md is a gitignored LOCAL-ONLY draft — never stage or commit it.

DESIGN DECISIONS (decided, rationale):
- The evidence note appends to the complete_step tool RESULT (not a synthetic extra turn): the tick and its verification land in ONE fed-back result — the model reads the evidence in the same roundtrip, zero model decisions spent. Tool-side hook (the tool parsed `has_step` exactly — no stringly arg re-detection in the batch layer), mirroring how the shell tool result carries its own compacted output.
- result.success stays TRUE when checks fail: the step DID tick (a false result would drive tier-1 auto-retry re-ticking a completed step and tier-2 misclassification of a successful action). The failure signal lives in the note text ("FAILED, exit N" / "timed out and was killed"), which is exactly the 'triage-able failure' shape: failure-shaped evidence in context, addressed by the model's next action, and any later real failure triages normally. Document this in the module doc.
- New module src/agent/step_verify.rs (one decision layer per module — model_routing/step_lanes precedent): StepVerifyHandle { cfg: Arc<RwLock<VerifyConfig>>, optimizer: Arc<RwLock<OptimizerConfig>>, root: PathBuf } — the factory builds ONE handle, cloned into the tool (with_step_verify) AND the loop (with_step_verify): both consumers read one live config.
- run_checks is inert by construction: disabled flag or empty test_command → None, ZERO process spawns (flag off = byte-identical, testable without spawning).
- Note builder: header line (command, exit status or 'timed out after Ns and was killed'), body = output_compactor::compress().text when the family matches, else a local fallback (first N DISTINCT non-empty lines, redacted via redact_secrets, with repeat counts), capped at a fixed char budget — the conciseness assertion feeds a huge synthetic output and asserts the note stays under the cap.
- action=verify wiring: in step_lane_target's DECIDED branch, decision.action == Verify → run_checks + stash the note in a per-loop `verify_note: Mutex<Option<String>>`; the request seam drains it via append_nudge beside the lever-7 note (verified anchor (6)) — one-shot (take), rides the volatile tail, popped after the request. Fires regardless of shadow/enforce (evidence, not routing). The reflex + routing flags must already be on for the classification to happen (the ladder's own gates) — the wiring composes both features; retry/escalate already feed the ladder (escalate action override + epoch re-classification, shipped in ad56c7bd) — documented, no new code.
- Multi-platform: the powershell/sh cfg! branches both implemented (the shell.rs precedent — not a Windows-only API). No new dependencies. No Settings UI (the item lists none; a config.toml surface like [shell_filter] — documented in README/PLAN).

ACCEPTANCE (from the item): cargo test green; flag off = exactly today's behavior (byte-identical outputs, zero spawns); a failing suite produces a compact evidence note (conciseness asserted in a unit test); the timeout path cancels cleanly and surfaces as a normal triage-able failure.
