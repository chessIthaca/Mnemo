# Plan: Diagnose app freeze / resource exhaustion during a session

## Goal
Identify likely causes of the app freezing mid-session (memory growth, unbounded buffers, blocked async runtimes, runaway subprocesses) and deliver a concrete, evidence-backed fix plan. No source-code changes — investigation only.

## Kind
research

## Context
User reports the app freezes again ("crashed again... freezes... maybe exhaust resources like memory somewhere within a session"). Project is a Tauri v2 + Rust backend + TS frontend app (myharness) with three browser surfaces (headless Chromium, native child WebView2, WebView2 Browser tab), an agent loop with LLM streaming, memory subsystem (working/episodic/semantic/procedural), console forwarding per page, file watcher for config, SQLite stores. Prior knowledge: 2026-04-18 deep review found a "forwarder stall" issue and maintainability backlog; there is a standing rule against wait-timers. Initial grep showed src/browser/mod.rs keeps per-page state maps (console, pages, console_tasks) that may never be cleaned, and agent turn.rs grows message vectors per turn.

## Steps
- [x] 1. **Map the resource-growth suspects** — Read src/browser/mod.rs (console buffer lifecycle, console_tasks, pages map cleanup on page close), src/memory/mod.rs + src/memory/consolidation.rs (working-memory event accumulation), src/agent/turn.rs (message vec growth, tool_output truncation limits), and any IPC channels between Rust and the frontend. List every in-memory collection that can grow during a session and whether it has a bound/eviction.
- [x] 2. **Check for blocked-runtime freeze patterns** — Search for std::sync::Mutex held across .await, blocking calls (std::fs, reqwest::blocking, rusqlite) on the tokio runtime, sync IPC handlers that call block_on, and unbounded mpsc channels (channel(0) vs unbounded). A single blocking call on a tokio worker can freeze ALL async work including UI event handling.
- [x] 3. **Check frontend + WebView2 growth** — Look at ui/src for unbounded state (event logs, streamed token buffers never reset), WebView2 child-process accumulation (game_navigate creating new processes without disposing old), and any JS-side timers/listeners added per session without removal. Check src-tauri for window/webview lifecycle.
- [x] 4. **Gather runtime evidence** — If the app or logs are inspectable: check .coding/logs or app-data logs for memory/CPU clues, look for recent crash/panic entries, and note the session length vs. tool-call volume pattern from working-memory DB size (.coding/*.db file sizes on disk).
- [x] 5. **Write findings + fix plan** — Produce a ranked list of freeze causes (most likely first) each with: evidence (file:line), mechanism (how it freezes the app), and a concrete fix. Write the report to .coding/reviews/2026-04-19-freeze-diagnosis.md and write a semantic memory summarizing the diagnosis for future sessions.
