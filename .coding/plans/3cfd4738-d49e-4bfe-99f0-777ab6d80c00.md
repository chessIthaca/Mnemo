# Plan: Wire vision fallback: auto-describe attachments + describe_image tool

## Goal
Make image attachments work for non-multimodal providers (e.g. Kimi): when a prompt carries images and the main LLM is text-only, describe each image via the configured vision model and inject the description as text. Also add a `describe_image` agent tool so the model can analyze image files on demand. Both paths share the same VisionClient plumbing.

## Context
The user configured `[general.vision_model]` (gemini/gemini-3-flash-preview) as a vision fallback, but images never reach any model: the OpenAI request builder strips image blocks for non-multimodal providers (src/provider/openai.rs:376-391), and the `AgentLoop::describe_image` fallback (src/agent/mod.rs:284) is dead code — nothing in production calls it. The VisionClient (src/provider/vision.rs) is already built in src-tauri/src/main.rs and threaded into the AgentLoopFactory (src/agent/factory.rs) and each AgentLoop.

Design (shared plumbing per user suggestion):
- New module src/tool/agent/describe_image.rs holds shared helpers: `mime_from_ext()` (png/jpg/jpeg/gif/webp/bmp), `load_image_data_url()` (sandbox-validate path, read bytes, base64-encode into a data URL), `describe_image_data_url()` (call VisionClient with an optional question, default prompt "Describe this image in detail."), and `describe_image_file()` (load + describe). These are used by both the new tool and the agent task fallback. Needs the `base64` crate added to Cargo.toml.
- New `DescribeImageTool` (agent tool, AutoRun since read-only, category Agent so it's available in all workflow states): args `{ path, question? }`, validates via Sandbox, loads the file as a data URL, calls VisionClient::describe_image. Registered in AgentLoopFactory::build_registry only when `self.vision` is Some.
- AgentTask Prompt arm (src/runtime/agent.rs:106-142): when images are non-empty AND `!self.agent_loop.is_multimodal()` AND a vision client is configured, replace image parts with per-image text descriptions (calling describe_image per data URL; failures become inline notes like "[image 1: description unavailable: ...]" so the turn still proceeds). Multimodal providers keep the existing multipart path unchanged. Images are described in order, prefixed `[image N description: ...]` and joined after the user's text.
