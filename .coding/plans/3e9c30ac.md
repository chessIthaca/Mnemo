# Plan: Repetition guard: per-interaction error accounting — same-batch calls don't abort, repair attempts don't count as repetition

## Goal
Make the turn-level repetition guard and MAX_RETRIES interaction-aware: a batch of identical failing calls is ONE error interaction (no same-time abort), any error in the previous batch resets the repetition ring (repair attempts never count as repetition), and the guard trips only on success-outcome pattern loops — per the user's semantics: same-time calls must not break the loop; the break for error loops belongs to MAX_RETRIES at the same error across three different LLM interactions.

## Bug
Turn aborted with "repetition guard: 3 identical consecutive responses — breaking the tool loop" (src/agent/turn.rs:777) while the model was re-emitting identical tool calls after receiving error feedback — repair attempts were counted as repetition. Root cause: tool_error_count (src/agent/turn.rs:1464-1474) is per-CALL and reset by ANY success within a batch, so a mixed [fail, success] batch leaves the counter at 0 and the repetition ring (clear keyed on tool_error_count > 0 at :758) counts error-following responses as repetition; separately, a single batch of 3 identical failing calls increments the counter 0→3 in ONE interaction, so the post-batch MAX_RETRIES check (:876) aborts the turn without the model ever getting a repair chance ("if all three were called at the same time it shouldn't break").
