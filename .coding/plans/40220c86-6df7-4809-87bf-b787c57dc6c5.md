# Plan: Forgiving git action/subcommand resolution

## Goal
Make the git tool's action/subcommand API forgiving: accept the subcommand name in either the `subcommand` or `action` field, map branch/stash action names (list/delete/create/push/pop/drop) from the `subcommand` value, make `subcommand` optional (no more "missing field `subcommand`" hard failure), and make error messages list the valid values. Keep every consumer (execute, never_auto_for, is_git_read_only, is_durable_tool, safety-rule signature) consistent via shared resolvers.

## Kind
implementation

## Context
src/tool/agent/git.rs is the git tool. Reported failures: (1) subcommand=branch + action=branch → "unknown branch action 'branch'"; (2) action=delete + subcommand=delete → "unknown git subcommand 'delete'"; (3) missing subcommand → serde hard-fails "invalid arguments: missing field `subcommand`" (GitArgs.subcommand is a required String, schema has required:["subcommand"]). Consumers that read the git args: GitTool::execute (git.rs:297), GitTool::never_auto_for (git.rs:275, core-op gating for merge/push), is_git_read_only (src/agent/approval.rs:153, AutoApproveProject auto-approval), is_durable_tool (src/agent/turn.rs:1662, working-memory recording), key_argument (src/safety_rules.rs:420, safety-rule signature "git:<subcommand>"). Design: add pub(crate) resolve_git_subcommand(args:&Value)->Option<String> and resolve_git_action(subcommand:&str,args:&Value)->Option<String> in git.rs. Resolution rules: a known subcommand in either field wins; branch action names (list/delete/create) in either field → "branch"; stash action names (push/pop/drop/list) in either field → "stash" ("push" is a subcommand first); subcommand field takes precedence over action; when the subcommand field carried an action name it wins as the action (handles swapped calls like subcommand="delete" + action="branch"); action field repeating the subcommand name (action="branch" with subcommand="branch") → default action (list for branch, push for stash); empty action → default. execute resolves from the raw Value BEFORE deserializing GitArgs (subcommand becomes Option<String>), so a missing subcommand yields a helpful "git requires a 'subcommand' field (…valid values…) — or an 'action' naming one of them" instead of a serde error. never_auto_for/is_git_read_only/is_durable_tool/key_argument switch to the resolvers (safety: subcommand="create"/"delete"/"pop" must NOT be auto-approved; action="push" must still force the core-op prompt). Schema: drop required:["subcommand"], document the interchangeability. Update module doc + README. Regression tests for every reported failure mode + swapped-field cases + resolver unit tests. NOTE: existing test invalid_args_error (git.rs:508) asserts json!({}) errors with "invalid arguments" — that behavior changes to the new missing-subcommand message; update it and add a separate genuine-serde-error test (e.g. {"subcommand":"status","branch":42}).
