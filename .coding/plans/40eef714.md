# Plan: Specs survive, get questioned, and are measured

## Goal
A worker's task, meaning the plan, its step's spec and the lead's brief, stays verbatim in its instructions for the whole session, through compaction, resumes and model switches. A worker can be asked to read back its spec and raise questions before coding. The plan board notes thin steps without refusing them. Each plan's review report shows how many review and fix rounds each step needed, on which models.

## Acceptance scenarios
- A worker dispatched on a plan step sends its first request with the plan, its step spec and the lead's brief inside the system message under '## Your task (pinned)', and its first user message is the short kickoff.
- After a compaction, or a switch to a smaller-context model that summarizes, the worker's next request still carries the full pinned task text byte-for-byte.
- A worker dispatched with read_back true first messages the lead with numbered questions or 'No questions.' and changes no file before the lead replies.
- plan_create with thin steps succeeds and lists 'Spec notes (advisory; nothing was refused)' per thin step; full-spec steps and no-code steps get no notes.
- A closed plan's review report has an '## Effort' table with per-task models, review rounds, fix rounds, findings (high) and audits, and a total line.
- Mnemo1 behaviour is unchanged (no pinned task, same head bytes); all root, src-tauri and mnemo2 checks pass.
