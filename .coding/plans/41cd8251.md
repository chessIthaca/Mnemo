# Plan: plan_read with a wrong capability sends the worker back to its plan

## Goal
plan_read without arguments is clearly the way to read the plan; a capability that names no OpenSpec capability fails with the list of real capabilities and tells the worker to call plan_read with no arguments for its plan.

## Kind
bug_fixing

## Context
ROOT CAUSE: src-tauri/src/mnemo2/team/pump.rs `worker_host_tool_result` (~65-90): with `capability` it returns `board.capability_spec(capability)`; `Ok(None)` becomes `ToolResult::success("No current spec for '<x>' yet.")`. The worker host tool spec (src-tauri/src/mnemo2/team/lead_tools.rs ~257, name "plan_read") says "Re-read your plan as it stands now ..., or with capability, that capability's current OpenSpec spec." with a `capability` property "Optional kebab-case capability name, e.g. tier-ladder". PlanBoard (src/app/plan_board.rs ~692) has `capability_spec` reading `<openspec_dir>/specs/<capability>/spec.md` via crate::app::openspec::read_capability_spec; the capability folders live under `.coding/openspec/specs/` (today: dispatch-routing, external-lead, llm-trace, plan-board, settings-dialog, tier-ladder, worker-brief).

DECISIONS:
- Add `PlanBoard::capability_names() -> Result<Vec<String>, String>`: sorted names of the folders under the openspec specs directory (none when it does not exist).
- In worker_host_tool_result: when `capability` is given and is NOT one of capability_names, return `ToolResult::error(format!("There is no OpenSpec capability named '{capability}'. Known capabilities: {list}. To re-read your plan, call plan_read with no arguments."))` where list is the comma-separated names, or "none" when there are none. A known capability whose spec.md does not exist yet keeps a success answer, now ending with " To re-read your plan, call plan_read with no arguments."
- Tool description (lead_tools.rs plan_read spec): "Re-read your plan as it stands now, including decisions and interfaces the lead added after you started: call it with no arguments. Pass `capability` only to read one OpenSpec capability's current spec (the folder names under .coding/openspec/specs, e.g. tier-ladder)." The `capability` property description: "Only to read an OpenSpec capability's spec instead of your plan; omit it to read your plan."
- Doc comment on worker_host_tool_result updated to match.

REGRESSION TEST: in src-tauri/src/mnemo2/team/tests.rs (or the pump's own test module), `plan_read_with_an_unknown_capability_names_the_real_ones`: a board whose openspec specs dir holds `tier-ladder/spec.md`; calling worker_host_tool_result with {"capability":"worker-checks-current-plan"} returns success == false and an output containing "Known capabilities: tier-ladder" and "call plan_read with no arguments". It fails on today's code (success answer "No current spec ..."). Also keep/extend a test that {"capability":"tier-ladder"} returns the spec and {} returns the plan view.

VERIFY: the regression test red then green; `cargo test --workspace`, `cargo clippy --workspace --all-targets` as plain commands. Prompt text (the tool description) is reviewed by the lead word by word.
