# Plan: Fix stale workflow state hiding the Merge-to-main button

## Goal
Fix the stale-workflow-state bug that hides the "Merge to main" button: bump `planVersion` on the `finished` event so StatusBar's `refreshPlan()` re-fetches the true backend workflow state when the agent goes idle, correcting any stale `workflowStates` value left by workflow mutations that didn't emit a `WorkflowStateChanged` event (e.g. harness/outer-agent `complete_step` calls outside the agent loop's run_turn).

## Context
Bug: the "Merge to main" button (StatusBar.tsx:606) is gated on `workflowState === "complete" || "planning"`. The frontend's `workflowStates[agentId]` is updated by the `workflow_state_changed` event (reduceWorkflowStateChanged, agentEventReducer.ts:360) and re-fetched by StatusBar's `refreshPlan()` (StatusBar.tsx:141) which is keyed on `planVersion` (StatusBar.tsx:154-160). `planVersion` bumps on `workflow_state_changed` + `step_completed` events (agentEventReducer.ts:366,373).

ROOT CAUSE: `WorkflowStateChanged` is emitted ONLY inside `src/agent/turn.rs:780-809` after the AGENT dispatches a workflow tool during `run_turn`. When the harness/outer-agent calls `complete_step`/`create_plan`/`update_plan`/`abandon_plan` through its own dispatch path (NOT the inner agent loop's run_turn), no `WorkflowStateChanged` event fires, so `planVersion` never bumps, so `refreshPlan()` never re-fetches, so the UI's `workflowStates` stays stale (e.g. stuck at "executing" after the last step completes → merge button missing). On app restart `load_latest` (workflow/mod.rs:552-556) correctly derives Complete from the on-disk checkboxes, so the bug is session-only.

FIX: bump `planVersion` on the `finished` event too (reduceFinished, agentEventReducer.ts:439). When the agent goes idle (turn done), the StatusBar re-fetches `getWorkflowState(activeAgent)` which reads the TRUE backend workflow state, correcting any stale value — covering both the harness-tool path and any other path that mutates the workflow without an event. This is a one-line change in a pure reducer (already table-tested), so it's low-risk and unit-testable. The existing `refreshPlan()` already calls `setWorkflowState(activeAgent, wf.state)` (StatusBar.tsx:146), so the re-fetch propagates the true state into the store + the button visibility re-evaluates.

Alternative considered + rejected: emit WorkflowStateChanged from the workflow tools themselves (brain crate) — rejected because the tools have no access to fanin_tx/AgentManager (the event channel is wired in the agent loop / IPC layer, not the brain). Emitting from the IPC layer for harness-tool calls would require threading the emitter into every harness tool-call site — larger, riskier. The finished-bump is the minimal, robust fix that also covers any future state-mutation path.
