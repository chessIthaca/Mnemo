# Plan: Between-items auto-compact respects the fill-rate dial

## Goal
Gate the run-all between-items auto-compact (auto_compact_on_plan_complete) on the same effective fill-rate threshold the fill-rate summarization path uses — summarize_at_fill_rate × window, proxy-ceiling cap included: compact only when the post-item context is at/above it; below, skip the summarization LLM call and dispatch the next item directly. Off (default) stays byte-identical. Also surface the knob→mechanism relationship in the Advanced settings help text and the README config paragraph.

## Kind
implementation

## Context
Findings: compact_then_dispatch_next (run_all.rs:2640) sends AgentCommand::Compact unconditionally — the only compaction mechanism ignoring the dial (by design: "every item starts clean overnight"). The dial: summarize_at_fill_rate ([context], default 0.3, validated 0.05..0.95); the effective threshold = min(rate × window, proxy_cache_ceiling_tokens − PROXY_CACHE_PRESSURE_MARGIN_TOKENS) via ContextManager::effective_summarize_at (src/agent/context.rs:129). The app has NO context-usage source today: the forwarder (events.rs) sees every SerializableAgentEvent::ContextUsage { used, max, .. } but only forwards it (no dedicated arm — it falls through the `_ => {}` bookkeeping matches). The AgentLoop holds the LIVE fill_rate (loop_impl.rs:180, threaded via with_fill_rate :988) but has no accessor. Config access pattern: state.project.config.lock().await (settings.rs). The compact signal: events.rs:499-534 (CompactStarted/Compacted/Error → compact_signal for the main agent). Existing source-contract test compact_then_dispatch_next_orders_compact_wait_dispatch (~run_all.rs:2352) pins the compact→wait→dispatch ordering — the gate must not change the compact path's ordering.

Design decisions (documented for review): (a) STRICT ≥ the effective threshold — "same dial" semantics, the task's primary proposal; the fraction-of-threshold and absolute-floor alternatives were rejected (two knobs for one concept, less predictable). (b) The fill rate is read from the LIVE loop (what the engine's fill-rate path actually uses — stays correct even if the config changed after the loop was built); the ceiling from the current config. (c) No usage data or max==0 → compact (conservative — today's behavior when blind). (d) The threshold formula is SHARED, not duplicated — a pub helper on ContextManager that effective_summarize_at delegates to, so the gate can never drift from the fill-rate path. (e) The gate sits BEFORE the compacting flag is set, so a skip never flashes the "compacting…" UI state.
