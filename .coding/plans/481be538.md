# Plan: Break the malformed-JSON retry loop: strategy-changing correction + literal escape hatch

## Goal
Break the malformed-JSON retry loop: when a tool call's arguments fail to emit as valid JSON and the SAME failure repeats for the same tool, the harness must stop re-injecting identical schema guidance and instead deliver a strategy-changing correction that names a different formulation (for search: use literal:true, or a metacharacter-free pattern) — and the search tool's advertised description must present literal:true as the remedy for metacharacter-dense patterns rather than an advisory tip. Fixes the live 5-consecutive-failure incident from plan 263a9e31.

## Kind
bug_fixing

## Context
INVESTIGATION (code-verified, not assumed):

1. THE LOOP: src/agent/turn.rs::handle_bad_json (line 3229) is the bad-JSON retry handler. Line 3248 increments state.bad_json_count; line 3249 aborts at MAX_BAD_JSON_RETRIES (src/agent/mod.rs:59, value 8). The retry arm (lines 3290-3354) pushes, per failed call, a FIXED user-facing error string (line 3342): "arguments JSON was malformed or truncated — please retry with valid, complete JSON. An empty argument object is a mistake … re-read the tool's schema, rewrite the COMPLETE call with every required field present and non-blank … never resend the broken call unchanged." That text is CONSTANT — it does not vary by attempt and does not diagnose WHY the emission failed. For escaping fragility the model already knows the schema; it needs a DIFFERENT FORMULATION. So attempts 1..8 are identical → the observed 5-in-a-row loop.

2. THE EXISTING STRATEGY-CHANGING LAYER: src/agent/turn.rs::tool_call_correction (line 3506) builds a harness-attributed corrective USER message (HARNESS_CORRECTION_PREFIX) that today says "the earlier malformed call is still steering your output … re-emit the COMPLETE call … do not resend the previous arguments unchanged" PLUS the tool's rendered schema (render_correction_schema, line 3525). It is delivered via the pending_correction slot consumed at turn.rs:1644 (which also applies the strict-schema normalization at 1652). repeated_tool_failure (line 3470) detects the repeat by scanning REPEAT_FAILURE_SCAN_WINDOW history messages for the SAME (tool name, byte-identical error text). CRITICAL GAP: the bad-JSON path never consults repeated_tool_failure nor sets pending_correction — so this whole mechanism is bypassed for exactly the failure class in this item.

3. THE CHEAP COMPLEMENT: src/tool/agent/search.rs — SearchArgs (line 358) has `pattern: String`, `glob: Option<String>`, `literal: bool` (line 367, #[serde(default)]). The module doc (lines 35-40) documents a LITERAL TIP as an ADVISORY output note ("for next time"), never as the remedy for a pattern that is hard to JSON-encode. So the model is never told that literal:true sidesteps backslash escaping entirely — the escape hatch exists and is undiscoverable.

WHY bug_fixing (scope decision): a contained defect — a retry loop that burns turns and makes no progress. The reproducer is concrete, the root cause is located to specific lines, and the fix is bounded to the correction path + tool descriptions. It adds no new capability surface and no new dependency (the item's own option (2), a pattern_literal parameter, is NOT needed — `literal` already exists; the gap is documentation).

DESIGN DECISIONS:
(a) Distinguish the two failure classes rather than replacing the existing message. The FIRST bad-JSON failure should keep today's schema-oriented guidance (it IS right for the dropped-required-field class that plan 4fa222cc addressed). From the SECOND identical bad-JSON failure onward, the guidance must name a DIFFERENT FORMULATION.
(b) Detection keyed on the same (tool name, error text) signature the existing circuit breaker uses — reuse, do not invent a parallel mechanism.
(c) Keep the correction harness-attributed (HARNESS_CORRECTION_PREFIX) so it never masquerades as user input, and keep it context-only (no Error event — per plan 995436c2/5a86e9d the correction must not render as a red error box or extend the UI doom streak).

TEST SURFACE: src/agent/tests.rs already holds repeat_failure_injects_schema_correction_on_second_identical_error, repeat_failure_across_an_intervening_success_still_fires, distinct_tool_errors_do_not_fire_the_correction, bad_json_retries_continue_past_three, bad_json_aborts_at_higher_cap, bad_json_tool_call_emits_tool_result_event — extend these rather than adding a parallel test module. The search description assertions live with the search tool's tests in src/tool/agent/search.rs.

VERIFICATION: cargo test --workspace (unpiped, read $LASTEXITCODE per agent.md — a piped exit code is the pipe's, not cargo's). The build must stay warning-free under #![deny(warnings)].

## Bug
A tool call whose arguments need backslash escaping in JSON (e.g. search with pattern "\\(\\?<" to match the literal `(?<`) is rejected with "arguments malformed or truncated — not run; retrying" and the retry re-emits the identical broken call. Observed live 2026-09-21 (plan 263a9e31): FIVE consecutive identical failures on one search pattern before a hand-found paren-free reformulation ([(][?]) succeeded. Root cause located: handle_bad_json (src/agent/turn.rs:3229) pushes a FIXED retry message (line 3342 — "re-read the tool's schema, rewrite the COMPLETE call") on every attempt up to MAX_BAD_JSON_RETRIES=8. For a content-EMISSION failure the schema is not the missing information, so every retry is identical and the loop cannot self-break. The strategy-changing correction machinery already exists — tool_call_correction (turn.rs:3506) via pending_correction (turn.rs:1644) — but the bad-JSON path never sets it.
