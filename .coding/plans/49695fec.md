# Plan: Separate installers for Mnemo and Mnemo2 (2.0.0 release)

## Goal
The release ships two installers per platform: the Mnemo installer (Mnemo.exe/.msi/.dmg, unchanged in content from 1.3) and a new Mnemo2 installer that installs Mnemo2 with its mnemo2-mcp helper beside it, both built by the tag workflow and attached to the v2.0.0 release.

## Kind
implementation

## Context
Why: the v2.0.0 tag build fails at the Mnemo MSI step ("cannot find target/release/mnemo2_mcp.exe") because the Tauri bundler packages every [[bin]] of the mnemo-app package, and src-tauri/Cargo.toml now declares three feature-gated Mnemo2 bins (mnemo2, mnemo2-mcp, mnemo2_route_eval) that `npx tauri build` does not compile. The user decided (2026-11-05): Mnemo and Mnemo2 get DIFFERENT installers.

Current layout (read before changing):
- Root Cargo.toml: [workspace] members = ["src-tauri"], exclude vendor; [patch.crates-io] vendored wry. Targets land in <repo>/target.
- src-tauri/Cargo.toml: package mnemo-app (lib mnemo_app + main bin src/main.rs = Mnemo), default-run = "mnemo-app", features custom-protocol = ["tauri/custom-protocol"] and mnemo2 = []; [[bin]] mnemo2 (src/bin/mnemo2.rs, calls mnemo_app::mnemo2::run()), mnemo2-mcp (src/bin/mnemo2_mcp.rs with module dir src/bin/mnemo2_mcp/), mnemo2_route_eval (src/bin/mnemo2_route_eval.rs), all required-features = ["mnemo2"].
- src-tauri/mnemo2-app/tauri.conf.json: productName Mnemo2, version 2.0.0, identifier com.mnemo.mnemo2, frontendDist ../../target/mnemo2-dist (mnemo2/vite.config outDir ../target/mnemo2-dist), bundle icons ../icons/*, capabilities ["mnemo2"]. The Mnemo2 Tauri context is generated INSIDE the mnemo-app lib: src-tauri/src/mnemo2/mod.rs:680 `tauri::generate_context!("mnemo2-app/tauri.conf.json")` (and a test one at :865); generate_context only loads a file literally named tauri.conf.json in that directory (BUG record: Tauri generate_context ignores a custom config filename) — keep that.
- src-tauri/build.rs runs tauri_build and adds rerun-if-changed for mnemo2-app/tauri.conf.json.
- package.json scripts: dev:mnemo2:native = `cargo run --manifest-path src-tauri/Cargo.toml --features mnemo2 --bin mnemo2`; build:mnemo2:native = `npm run build:mnemo2 && cargo build --manifest-path src-tauri/Cargo.toml --features mnemo2,custom-protocol --bin mnemo2 --bin mnemo2-mcp --release && node scripts/install-mnemo2-mcp.mjs`; scripts/rebuild-mnemo2.mjs wraps it; scripts/install-mnemo2-mcp.mjs copies target/release/mnemo2-mcp(.exe) into mnemo2/plugin/bin and ~/.mnemo/bin.
- .github/workflows/build.yml: windows job runs `npx tauri build` (from repo root, src-tauri/tauri.conf.json, beforeBuildCommand npm run build) and uploads target/release/bundle/msi/*.msi + nsis/*.exe as artifact windows-installers; its "Build + test Mnemo2 host (feature-enabled)" step runs `cargo build -p mnemo-app --features mnemo2 --bin mnemo2` (+ tests). macos job runs `npx tauri build --target aarch64-apple-darwin`, zips target/aarch64-apple-darwin/release/bundle/macos/*.app with ditto into mnemo.app.zip and uploads it with bundle/dmg/*.dmg as macos-bundles-aarch64; its Mnemo2 step mirrors Windows. The release job (tags only) downloads both artifacts and attaches **/*.msi, **/*.exe, **/*.dmg, **/*.zip to a draft release, then publishes. tests/integration/ci_workflow.rs parses build.yml (secret-free ifs, clap-bool CI env, no node20 actions, scoped permissions, draft-first upload, SHA-pinned actions, the Cargo.lock vendored-patch guard) — keep all of them passing.

Design (decided by the lead):
1. New Cargo package `mnemo2-app` in the EXISTING directory src-tauri/mnemo2-app (it already holds tauri.conf.json): src-tauri/mnemo2-app/Cargo.toml with name "mnemo2-app", version "2.0.0", edition 2021, license MIT, description "The Mnemo2 desktop app (lead + team)", default-run = "mnemo2"; dependencies `mnemo-app = { path = "..", features = ["mnemo2"] }` and whatever the bins import directly (check the use lines of mnemo2.rs, mnemo2_mcp.rs + its modules, mnemo2_route_eval.rs, and add each crate with the SAME version spec as src-tauri/Cargo.toml so versions unify; tauri-build as a build-dependency); features `custom-protocol = ["mnemo-app/custom-protocol"]` (tauri build passes --features custom-protocol to the package it builds). Bins: `mnemo2` (path = "../src/bin/mnemo2.rs") and `mnemo2-mcp` (path = "../src/bin/mnemo2_mcp.rs"; its `mod` children resolve relative to that file, so the module dir stays where it is). `mnemo2_route_eval` becomes an [[example]] of mnemo2-app (path = "../src/bin/mnemo2_route_eval.rs") so it is never bundled; update its doc-comment run line to `cargo run -p mnemo2-app --example mnemo2_route_eval -- ...` and the two comments in src-tauri/src/mnemo2/mod.rs:31 and route_eval.rs:11-12 that name the bin path. Move nothing else. If any bin source uses `crate::` paths that only worked inside mnemo-app, switch them to `mnemo_app::` (the lib's pub API); make only the visibility changes that requires, and list them.
2. src-tauri/mnemo2-app/build.rs: `fn main() { tauri_build::build() }` so mnemo2.exe gets its own Windows resources (icon from mnemo2-app/tauri.conf.json bundle.icon, version info, common-controls manifest). If tauri_build requires a capabilities directory or the frontendDist to exist at build time, satisfy it the smallest way (e.g. an empty or copied capabilities dir, or `tauri_build::try_build(Attributes::new())` with the needed options) and explain why. The runtime Tauri context still comes from mnemo-app's generate_context!.
3. src-tauri/Cargo.toml: delete the three [[bin]] sections and their comments; keep `default-run = "mnemo-app"` and the `mnemo2` feature (the lib's mnemo2 module stays gated behind it); fix the default-run comment to say the app is the only bin. Root Cargo.toml: members = ["src-tauri", "src-tauri/mnemo2-app"].
4. src-tauri/mnemo2-app/tauri.conf.json: add `"build": { "beforeBuildCommand": "npm run build:mnemo2", ... }` only if tauri runs it from the repo root when invoked from src-tauri/mnemo2-app (verify; otherwise leave it out and the CI/scripts build the frontend first). Add `"mainBinaryName": "Mnemo2"` only if needed for a sensible installed exe name (check what tauri names it by default from productName).
5. Scripts: package.json dev:mnemo2:native -> `cargo run -p mnemo2-app --bin mnemo2`; build:mnemo2:native -> `npm run build:mnemo2 && cargo build -p mnemo2-app --features custom-protocol --bins --release && node scripts/install-mnemo2-mcp.mjs`; add `"bundle:mnemo2": "npm run build:mnemo2 && cd src-tauri/mnemo2-app && npx tauri build"` (adjust to however tauri must be invoked for the nested config, verified). install-mnemo2-mcp.mjs: update the "build it with --bin mnemo2-mcp" hint to `cargo build -p mnemo2-app --bin mnemo2-mcp`. rebuild-mnemo2.mjs keeps working through build:mnemo2:native (target paths unchanged).
6. CI (.github/workflows/build.yml): windows job: replace the Mnemo2 step's `cargo build -p mnemo-app --features mnemo2 --bin mnemo2` with `cargo build -p mnemo2-app` (+ keep its test command, adding `cargo test -p mnemo2-app` for the mnemo2-mcp bin's tests); after the Mnemo `npx tauri build`, add "Build the Mnemo2 frontend" (`npm run build:mnemo2`) and "Tauri build Mnemo2 (unsigned installers)" running the verified Mnemo2 bundle command; the windows-installers artifact already globs target/release/bundle/msi/*.msi and nsis/*.exe, which now holds both apps' installers (distinct names Mnemo_… and Mnemo2_…) — keep the glob. macos job: same Mnemo2 frontend + bundle steps with `--target aarch64-apple-darwin` after the Mnemo bundle step (same signing env), and replace the single-.app ditto with one zip per app (`ditto ... Mnemo.app mnemo.app.zip` and `ditto ... Mnemo2.app mnemo2.app.zip`, using the real .app names), uploading both zips plus bundle/dmg/*.dmg. The release job needs no change if its globs already match. Keep every ci_workflow.rs guard passing; add one guard test `build_workflow_bundles_both_apps` asserting both jobs run a Mnemo2 bundle step.
7. Out of scope (note in the report, do not build): first-run setup that copies mnemo2-mcp into ~/.mnemo/bin for the Claude Code plugin from an installed Mnemo2, and code signing differences.

Verification: `cargo build -p mnemo-app --release` then `npx tauri build` from the repo root must bundle ONLY Mnemo (no mnemo2 exe in target/release/bundle/msi/*.msi content list: check the generated target/release/wix/x64/main.wxs mentions no mnemo2); the Mnemo2 bundle command must produce Mnemo2 MSI/NSIS installers whose main.wxs lists mnemo2 and mnemo2-mcp; `cargo test --lib`, `cargo test --test integration ci_workflow`, `cargo test --test boundary`, `cargo test -p mnemo-app --features mnemo2 --lib`, `cargo test -p mnemo2-app`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo clippy -p mnemo-app --all-targets --features mnemo2 -- -D warnings`, `npm run rebuild:mnemo2` is NOT run by workers (it quits the user's Mnemo2); instead `npm run build:mnemo2:native` must succeed only if no Mnemo2 is running — workers run `cargo build -p mnemo2-app --features custom-protocol --bins --release` instead.

## Acceptance scenarios
- npx tauri build from the repo root bundles Mnemo only; its WiX main.wxs references no mnemo2 binary
- Running npx tauri build in src-tauri/mnemo2-app produces Mnemo2 MSI and NSIS installers containing mnemo2.exe and mnemo2-mcp.exe
- npm run build:mnemo2:native still produces target/release/mnemo2.exe and mnemo2-mcp.exe and installs the helper
- build.yml builds and uploads both apps' installers on Windows and macOS; the v2.0.0 release lists Mnemo and Mnemo2 installers
