# Plan: Safety UX: rule-based "Allow for project", mode-change re-evaluates pending approvals, hide no-op core-op buttons

## Goal
Three coupled fixes to the safety/approval UX:
(1) "Allow for project" adds a tool-level safety rule (broad, e.g. ^file_edit:) instead of flipping the global safety mode — additive, persistent, no desync.
(2) Changing the safety mode re-evaluates any pending approval: if the new mode would auto-run the call, resolve it as Approved (except core ops like git merge/push, which always stay gated).
(3) Hide the "Mark Safe" and "Allow for project" buttons for core operations (git merge/push) since both are no-ops there (never_auto_for bypasses safety rules AND safety modes).
A shared `core_operation: bool` flag (the existing `force_prompt` from dispatch) threads through the event → IPC → TS → store → UI, and also feeds the re-evaluation skip-logic.

## Context
User observation: git merge/push always prompt even in Unsafe/Autonomous mode (correct, via Tool::never_auto_for). But the approval prompt offers 4 buttons, two of which are silently no-ops for core ops: "Mark Safe" (writes a safety rule, but dispatch.rs:148 ignores rules when force_prompt) and "Allow for project" (flips to AutoApproveProject mode, but never_auto_for overrides all modes). Additionally, "Allow for project" changes the GLOBAL mode without persisting to disk → desync on next configVersion bump (StatusBar resync reads disk, resets store label while runtime stays AutoApproveProject). And changing the mode while an approval is pending does nothing to resolve it — the oneshot just sits there.

Verified mechanism:
- src/agent/dispatch.rs:140 force_prompt = tool.never_auto() || tool.never_auto_for(&args) — true for git merge/push
- src/agent/dispatch.rs:148 auto_approved = !force_prompt && ... — safety rules ignored when force_prompt
- src/agent/dispatch.rs:169 AgentEvent::ApprovalRequest { tool_call_id, tool_name, args, preview, responder } — NO core_operation flag sent
- src/runtime/channels.rs:66/186 AgentEvent::ApprovalRequest + SerializableAgentEvent::ApprovalRequest — both lack the flag
- src-tauri/src/ipc/approval.rs:21 PendingApprovals stores only (agent_id, tool_call_id) → oneshot::Sender — NO tool_name/args/core_op, so can't re-evaluate
- src-tauri/src/ipc/agent.rs:194 set_safety_mode — updates runtime mode, does NOT re-evaluate pending approvals
- src-tauri/src/ipc/settings.rs:966-970 save_settings — also updates runtime mode when safety patched, also does NOT re-evaluate
- src/safety_rules.rs:187 add_rule — creates narrow literal pattern ^<escaped_sig>$; no broad variant exists
- src/agent/approval.rs:62 needs_approval + is_project_scoped — PUBLIC, callable from IPC layer
- frontend/src/components/chat/ApprovalPrompt.tsx:145 handleAllowForProject — calls setSafetyMode("auto-approve-project") (the bug)
- frontend/src/components/layout/StatusBar.tsx:349-354 selectSafetyMode — setSafetyMode + saveSettings fire-and-forget (separate desync risk, pre-existing)

Design:
- core_operation flag = force_prompt from dispatch. Threaded through event → serializable event → PendingApprovals entry → TS type → PendingApproval → ApprovalPrompt.
- PendingApprovals extended to store {sender, tool_name, args, core_operation} per entry. New re_evaluate(mode, sandbox) method resolves entries where !core_operation && !needs_approval(NeedsApproval, mode, tool_name, args, sandbox).
- set_safety_mode + save_settings call re_evaluate after mode update.
- New SafetyRules::add_rule_broad(tool) creates pattern ^<tool>: (matches any call of that tool). New IPC add_safety_rule_broad. Frontend "Allow for project" calls it instead of setSafetyMode.
- ApprovalPrompt hides "Mark Safe" + "Allow for project" when core_operation=true.
