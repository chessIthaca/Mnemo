# Plan: Transport stringifies explicit null for string/enum params — central defense + nullable victim schemas (backlog 9118714a)

## Goal
Kill the null-stringify transport failure class: a central dispatch-level defense drops the literal string "null" from OPTIONAL tool-call properties (keyed on the advertised schema's required list, recursive into nested objects/array items/union branches), and the four victims' optional string/enum params advertise nullable so JSON null is legal end-to-end — pinned by per-field regression tests (explicit "null" → unset, omitted → unset, real value → passes) plus a dispatch-seam integration test.

## Kind
implementation

## Context
Backlog 9118714a (observed live 2026-09-19, plans 995436c2 + 04a195de): explicit JSON null for string/enum tool params arrives as the literal string "null" — the transport stringifies (ints/arrays/bools pass null cleanly). Four live failures: (1) backlog_status(status="null") → enum rejection, note-only updates forced through a done→pending→done requeue dance; (2) update_plan(title="null", goal="null") → title/goal REPLACED with "null" (data corruption, repaired manually); (3) create_plan(branch="null") → "git checkout null failed"; (4) file_edit(edits=[…] + old_string="null"/new_string="null") → false "edits is mutually exclusive with old_string" — batch mode unusable. ROOT CAUSE: the model/transport emits the string "null" for optional string/enum params (it cannot express JSON null for non-nullable-advertised fields); nothing between the provider parse and tool deserialization normalizes it. Verified deserialization side: ALL victim fields already accept JSON null — BacklogStatusArgs.status Option<BacklogStatus> (src/tool/workflow/backlog.rs:238-257), UpdatePlanArgs.title/goal/context/regression_test Option<String> (src/tool/workflow/plan.rs:438-466), CreatePlanArgs.bug/branch/base Option<String> + context/kind null_to_default (src/tool/workflow/plan.rs:75-110), file_edit old_string/new_string Option<String>. Reference fix: spawn_agent.model (src/tool/agent/spawn_agent.rs:177 — advertised ["string","null"] + "null"-string-counts-as-unset at :242-268, backlog 3e6f7887). DESIGN DECISIONS: (a) the central defense keys on OPTIONAL (absent from the schema's `required` list), not on advertised nullability — the model's intent with "null" is always unset, no tool param legitimately wants the literal string, and this covers every tool incl. unfixed schemas; required fields keep "null" as a genuine error (circuit-breaker territory). (b) Defense handles the STRING "null" only — JSON null already works for every victim field (Option/null_to_default); the observed transport converts JSON null → string anyway. (c) Scope of advertised nullability = the four victims' named fields (+ create_plan.kind, same enum shape) — NOT a full ~50-field sweep across ~20 tool files: the central defense makes advertised nullability hardening rather than correctness, and a blind sweep risks advertising null for plain #[serde(default)] String fields whose deserializers reject it. Seam: src/agent/dispatch.rs execute_tool_call — args parsed :192, ParsedToolCall built :205, tool lookup :212 (reorder lookup first, then sanitize, so approval/safety/preview/steering all see clean args; the raw tc.arguments string keeps UI fidelity). Verify: cargo test green + warning-free (#![deny(warnings)]); budget ceilings in src/agent/factory.rs may need a documented dated raise (~90 chars of ["string","null"] growth across 13 fields).
