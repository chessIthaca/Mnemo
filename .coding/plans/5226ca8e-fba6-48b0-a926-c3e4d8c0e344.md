# Plan: Cache-hit analysis round 2: measure R1-R3 improvement + further optimization

## Goal
Analyze the current LLM trace log (.coding/logs/traces.jsonl) to measure the cache-hit rate after the R1–R3 prompt-management fixes, compare it to the 2026-08-13 baseline (80.7%, 15 resets), identify any remaining cache-breakers, and produce a findings report with concrete further-optimization recommendations.

## Kind
research

## Context
Baseline report at .coding/analysis/cache-hit-analysis.md (2026-08-13): 82 requests, 80.7% overall hit, ~15 full cache-reset requests (hit<50%) wasting ~2.0M tokens (17.8% of prompt), every reset was firstDiff=0 (system message changed), stable head ≈2,176 tokens survived across sessions. Root cause: volatile WORKFLOW STATE + RECALLED MEMORIES embedded mid-message[0]. Recommendations R1 (split stable head from volatile tail — message[0] stable, volatile block appended at the END after history), R2 (deterministic tool-schema ordering — sort by name), R3 (stabilize memories block ordering) were subsequently implemented (commits 54b76dd "perf: split stable head from volatile tail for prompt cache-hit (R1-R3)", 6dc36d2 "Strengthen system-preamble workflow guidance", b080f9b merge). The user asks: (1) is the cache hit rate more efficient NOW, and (2) can we optimize further. Trace log: .coding/logs/traces.jsonl (live-appending, one JSON line per request, fields: id, ts_ms, model, base_url, request_json{messages[],tools[],...}, usage{prompt,completion,reasoning,cached}, finish_reason, ttft_ms, generation_ms, error, response_truncated). Previous analysis used PowerShell ConvertFrom-Json + JSON.stringify equality per message index (mirroring LlmTraceView compareMessages) with outputs .coding/analysis/traces-summary.txt + traces-diff.txt. ANALYSIS ONLY — no source changes (research plan).
