# Plan: Fix Mnemo2 native host WebView2 startup hang

## Goal
Make the native Mnemo2 host open a working window with its own WebView2 identity/profile instead of hanging before the frontend loads, and lock the fix with a regression test and a launch smoke check.

## Kind
bug_fixing

## Context
Verified from the live process: mnemo2.exe PID 84820 has a visible top-level window, 2 wait-state threads, 184 handles, no msedgewebview2 child, no WebView2 DLLs, and no C:\Users\carst\AppData\Local\com.mnemo.mnemo2 profile. Verified from the build output: src-tauri/build.rs runs tauri_build::build() against the default tauri.conf.json, and every target/debug/build/mnemo-app-*/output only tracks C:\Mnemo\src-tauri\tauri.conf.json, never mnemo2.conf.json. Verified (read src-tauri/src/mnemo2/mod.rs:47): the host calls tauri::generate_context!("mnemo2.conf.json"), and mnemo2.conf.json declares identifier com.mnemo.mnemo2. Verified (read src-tauri/src/webview_udf.rs): Mnemo1 documents that a second process sharing the default WebView2 profile produces a blank window because its session never initializes; Mnemo1 currently owns C:\Users\carst\AppData\Local\com.mnemo.desktop\EBWebView. Hypothesis to confirm in step 1: the Mnemo2 context actually resolves to Mnemo1's identifier or profile, so its WebView2 environment collides with the running Mnemo1 app. Regression-test design: a unit test for a pure Mnemo2 identity/profile helper asserting com.mnemo.mnemo2 and a WebView2 data directory distinct from com.mnemo.desktop; plus a host smoke check that launches the native binary and waits for a msedgewebview2 child or the com.mnemo.mnemo2 profile directory, failing on timeout.

Root cause CONFIRMED (2026-10-24, plan 52d7bb81): `tauri::generate_context!("mnemo2.conf.json")` does not load that filename. The macro resolves it under CARGO_MANIFEST_DIR and validates the filename, but `tauri-codegen::get_config` passes only the path's PARENT to `tauri-utils::config::parse::read_from`, which always loads `<dir>/tauri.conf.json`. So the Mnemo2 host compiled Mnemo1's `com.mnemo.desktop` context and collided with Mnemo1's live WebView2 profile. Proof: `cargo test -p mnemo-app --lib mnemo2::tests::context_uses_mnemo2_identifier` failed with `left: "com.mnemo.desktop"`, `right: "com.mnemo.mnemo2"`. Fix: move the alternate config to `src-tauri/mnemo2-app/tauri.conf.json` and pass that path; adjust relative paths (`frontendDist` -> `../../target/mnemo2-dist`, icons -> `../icons/...`, npm commands -> `npm --prefix ../.. ...`), add the new config to build.rs rerun tracking, update live docs, and keep the context-identifier test as the regression guard. After the fix, run a real launch smoke to confirm WebView2 creates the `com.mnemo.mnemo2` profile and the window loads.

Launch verification (2026-10-24): after moving the config to `src-tauri/mnemo2-app/tauri.conf.json`, `cargo build -p mnemo-app --bin mnemo2` succeeded; `target/debug/mnemo2.exe` opened a titled Mnemo2 window (43 threads) with a WebView2 child using `--user-data-dir=C:\Users\carst\AppData\Local\com.mnemo.mnemo2\EBWebView`, and that profile exists. The host also clears inherited `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`, so it never reuses Mnemo1's CDP port 9222. The visible team/delegation cards are `mnemo2/src/lib/mock.ts`; no LLM is called until a lead prompt is sent. Regression test: `mnemo2::tests::context_uses_mnemo2_identifier`.

## Bug
Native Mnemo2 host hangs before WebView2 initialization: it creates a visible untitled window (Win32 handle 1642316), the process stays alive with only two idle threads and no WebView2 modules, and no %LOCALAPPDATA%\com.mnemo.mnemo2 WebView2 profile is created. Reproduced 2026-10-24 by launching cargo run -p mnemo-app --bin mnemo2 (process 84820); the frontend never appears.
