# Plan: Fix R14 cache-break: hysteresis tool-result compaction (no-op below a 20-result high-water mark)

## Goal
Make compact_old_tool_results stop mutating conversation history on every tool batch: add a hysteresis window (no-op while the intact tool-result window is <= 20, then one cut back to 10) so consecutive requests share a byte-identical prefix and the provider's prefix cache holds — measured cache hit goes from ~46% to ~95% on stable requests (~90% amortized).

## Kind
bug_fixing

## Context
Design: hysteresis (high-water mark) compaction. Today compact_old_tool_results(messages, 10, 500) runs unconditionally after every tool batch and truncates all but the last 10 tool results in place — the sliding window mutates one more message every request, breaking the prefix cache every time (BUG memory 5bbc7d3a, knowledge file .coding/knowledge/bug/2026-12-31-cache-hit-terrible-at-any-context-size-r14-per-b.md). Fix: only compact when the INTACT window (tool results without the COMPACTED_MARKER "[… truncated for context efficiency]") exceeds keep_high=20, then cut back to keep=10 in ONE pass. Between cuts nothing is mutated → consecutive requests byte-identical on shared prefix → ~95% hit on 10 of 11 requests, one cut request at ~40-60% → ~90% amortized (vs 46% measured). Tradeoff: intact window can reach 20 fat results (2x today) between cuts; pathological growth is still bounded by summarization at fill_rate 0.3. keep_high=20 is a call-site constant, tunable later. The function should return the number of truncated results so the turn loop only resets token accounting when messages actually changed.
