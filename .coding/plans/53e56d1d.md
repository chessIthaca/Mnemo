# Plan: Quit from the tray ends Mnemo2

## Goal
Quit (tray menu, and any other app exit) always ends the Mnemo2 process promptly after an orderly shutdown, and a shutdown step that cannot finish never keeps the process alive.

## Kind
bug_fixing

## Context
WHY: the user quit Mnemo2 from the tray to rebuild it; the process never exited and had to be force-killed, which risks the open SQLite stores (memory.db, codegraph.db) and leaves stale run files. Since Mnemo2 now outlives Claude Desktop restarts, quitting it cleanly is the normal way to stop it.

WHERE:
- verified: `grep -n` -> src-tauri/src/mnemo2/mod.rs:102 `fn request_quit(` (tray Quit; with no running workers it calls `app.exit(0)` at :109) and :384 `if let tauri::RunEvent::Exit = event {` with `tauri::async_runtime::block_on(async {` at :390.
- verified: reading mod.rs:383-398 -> the Exit handler calls `state.shutdown_endpoint()`, then inside `block_on` on the event-loop (main) thread: `state.save_cached_preferences(&owner).await`, `state.shutdown().await`, `browser.close().await`.
- verified: reading src-tauri/src/mnemo2/ipc.rs:192-215 -> `Mnemo2State::shutdown` aborts forwarders, takes the runtime and awaits `runtime.shutdown()` (src-tauri/src/mnemo2/runtime.rs:875, which interrupts the live lead session and awaits `engine.shutdown()`), then detaches the project and syncs the run file; team teardown is `TeamRuntime::shutdown` (src-tauri/src/mnemo2/team.rs:3788).
- verified: reading src-tauri/src/mnemo2/browser.rs:426-445 -> `BrowserController::close` hides and closes a child webview (`webview.close()`).
- assumption: the likeliest causes are (a) main-thread work (webview hide/close, window operations, events) requested from inside `block_on` on the main thread during RunEvent::Exit, which can never be serviced (deadlock), or (b) an await in runtime/team/engine shutdown that never completes (e.g. waiting on a session, pump or lock). Neither is confirmed; find the actual stall first.

DECISIONS:
- Find and fix the real stall. Do the async teardown where it cannot deadlock the event loop: for example, on RunEvent::ExitRequested prevent the exit, run the async shutdown on the async runtime (not blocking the main thread), then call exit again; and run main-thread-only steps (webview close) on the main thread without blocking it.
- Add a bounded overall shutdown deadline as a safety net in addition to the root-cause fix (not instead of it): if orderly shutdown has not finished within it, log what was still pending and exit anyway, so Quit always ends the process. Keep the run file removal and project detach on the normal path.
- Keep the existing quit confirmation when workers are running (request_quit's dialog) unchanged.
- Do not touch the mnemo2-mcp helper or the frontend.

REGRESSION TEST: add `shutdown_completes_with_an_open_project_and_team` to the test module of src-tauri/src/mnemo2/ipc.rs (or runtime.rs if the state fixture lives there): open a real LeadRuntime/team as the existing tests do (ScriptedLlm), optionally with a live idle worker session, then assert `Mnemo2State::shutdown()` (and `LeadRuntime::shutdown()`) completes within a few seconds. If the stall turns out to be in the Exit/event-loop sequencing rather than in an awaited future, also extract that sequencing into a testable function and test that it does not block on main-thread work. State in the report which cause you proved and how.

VERIFY:
- `cargo test --manifest-path src-tauri/Cargo.toml --features mnemo2 --lib mnemo2::`
- `cargo clippy --manifest-path src-tauri/Cargo.toml --features mnemo2 --lib --tests` (no new warnings in touched files)
- The lead will verify the real app: build with `npm run build:mnemo2:native`, start Mnemo2, open a project, choose Quit in the tray, and confirm mnemo2.exe exits within seconds and its run file is removed.

## Acceptance scenarios
- `shutdown_completes_with_an_open_project_and_team` passes: Mnemo2State::shutdown with an open project, lead and team completes within a few seconds.
- In the built app, choosing Quit in the tray with a project open and no workers running makes mnemo2.exe exit within seconds and removes its ~/.mnemo/run/mnemo2-<pid>.json run file.
- If a shutdown step cannot finish, the process still exits after the bounded deadline and logs which step was pending.
- The quit confirmation dialog still appears when workers are running, and `cargo test --features mnemo2 --lib mnemo2::` passes.

## Bug
Choosing Quit in Mnemo2's tray menu (no workers running) does not end the process: the window disappears but mnemo2.exe stays alive indefinitely, keeps its run file and project claim, ignores a normal close request (taskkill without /F), and keeps target\release\mnemo2.exe locked so rebuilds fail until it is force-killed. Observed 2026-11-01 with the build from 2026-10-31.
