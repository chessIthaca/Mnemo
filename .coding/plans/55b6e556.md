# Plan: Cross-platform npm start launcher — scripts/start.mjs (mac-readiness LOW 1+2)

## Goal
Make `npm start` work identically on macOS and Windows: a cross-platform node launcher (scripts/start.mjs) encoding the .bat workflow knowledge — npm-install sync before CLI use, the Tauri CLI invoked as node <root>/node_modules/@tauri-apps/cli/tauri.js with src-tauri/ as cwd, --no-bundle default vs bundle opt-in, exit-code plumbing, Windows taskkill of the locked exe — with modes dev/build/bundle/default(build+run), plus README quick-start updates for both platforms.

## Context
Mac-readiness review LOW 1+2 (.coding/reviews/2027-01-06-full-review-mac-readiness.md): package.json:10 wires "npm start" to start.bat — a batch file sh can't run, so a macOS developer's most instinctive entry point fails. start.bat (53 lines) + build.bat (33 lines) encode real workflow knowledge (npm sync before CLI use, tauri runs from src-tauri/ as cwd, --no-bundle default vs bundle opt-in, exit-code plumbing, Windows taskkill of the locked exe) with no macOS counterpart. The README documents the manual sequence for both platforms but never mentions npm start. SURVEY FACTS: (1) @tauri-apps/cli v2.11.4's bin entry is ./tauri.js (node_modules/@tauri-apps/cli/package.json:52-54) — the launcher can spawn `node <root>/node_modules/@tauri-apps/cli/tauri.js <args>` with cwd src-tauri, avoiding ALL .cmd/.sh shim issues (pure node→JS spawn, identical on every platform); (2) the cargo workspace root is the repo root (README:107 "workspace: library + app") so builds land in root/target/release/ — start.bat:51 runs target\release\mnemo-app.exe from the root after popd, confirming; (3) start.bat modes: "dev" → tauri dev from src-tauri; default → taskkill mnemo-app.exe (Windows, locked-exe "Access is denied" guard) → tauri build --no-bundle → run target\release\mnemo-app.exe; build.bat modes: default → build --no-bundle; "bundle" → tauri build (installers); (4) npm appends positionals after the script name to the command (the repo's own convention: start.bat checks %1=="dev" and is only ever invoked via npm start — `npm start dev` is the established usage); (5) on Windows, spawning npm needs the explicit 'npm.cmd' name (libuv routes .cmd through cmd.exe; bare 'npm' gives ENOENT); taskkill.exe is a real executable (PATH-resolvable, no shell needed); on Unix a running binary can be replaced (unlink+create), so no kill is needed on macOS. DECISIONS: (1) option (a) — the cross-platform launcher scripts/start.mjs — over .sh counterparts (duplicates knowledge, doesn't fix npm start) or README-only (leaves macOS second-class); (2) start.bat/build.bat are KEPT unchanged — Windows-native conveniences (double-click pause UX); no removal in an unattended run; the README documents npm start as the canonical cross-platform entry (drift risk accepted + noted for the reviewer); (3) the launcher is STRICT about modes (unknown arg → usage error, exit 1) instead of the .bat's lenient fall-through-to-default (a typo shouldn't trigger a full build+launch); (4) taskkill only in the default (build+run) mode — matching start.bat; the 'build' mode matches build.bat (no kill, matching its no-kill precedent); (5) verification without launching the app in unattended mode: node --check, --help + bad-mode paths, `npm start -- --help` (the -- form is safe — plain `npm start --help` is intercepted by npm itself), spawn probes, then the full `node scripts/start.mjs build` (incremental release build — the definitive flow check; the default mode's final app-launch step is NOT run unattended); (6) no Rust/TS code changes — both suites are the constitutional regression net.
