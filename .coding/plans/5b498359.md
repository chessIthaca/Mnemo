# Plan: One simple `job` tool that starts and waits; jobs shown like shell calls

## Goal
A worker runs a long build or test with a single call, `job`, which starts it and waits for the result. The Mnemo2 window shows every job call like a shell call, titled with the job's purpose (for example "job · build game") and its state.

## Kind
implementation

## Context
WHY (user, 2026-11-21): today a worker needs two calls for every long command, `job_start` (returns an id) and then `job_wait` (blocks until it ends), and the worker prompt spells out that sequence. The user wants one simple tool called `job`, and wants the window to show job calls like shell calls with the job's label ("job · build game") instead of raw JSON. job_start already requires a `purpose` label; the window ignores it.

DECISIONS:
- Rename `job_start` to `job`. Keep job_wait, job_tail and job_kill as they are (names unchanged): they act on a job by id.
- `job` WAITS BY DEFAULT: args {command, purpose, cwd?, wait_s?, pattern?}. wait_s defaults to DEFAULT_WAIT_S (600) and is clamped to MAX_WAIT_S (1800); wait_s 0 returns at once with the id (for a dev server, or work in parallel). With a wait, the call blocks server-side exactly like job_wait and returns the same result shape: the job ended (exit status plus the output tail), a NEW line matched `pattern`, or 'still running', in which case the id is returned for job_wait. The job's ownership, 3-hour cap, no silence limit and log are unchanged.
- The old name `job_start` is NOT kept as an alias: a single tool list stays short. Old transcripts that contain job_start calls must still render in the window (the display step handles both names).
- New worker prompt bullet (both variants and the sync copy, verbatim): "- For a build or test that may run longer than a few minutes, run it with job: it waits for the result (wait_s, default 600). If it is still running when the wait ends, job_wait on its id; to keep working while it runs, start it with wait_s 0. Never poll with sleep or Start-Sleep, and never start detached processes."
- New `job` tool description (verbatim): "Run a long build or test as a background job with no silence limit (3-hour cap) and wait for its result in this call. If it is still running when wait_s ends, you get its id for job_wait; wait_s 0 returns the id at once so you can work while it runs. purpose is a short label shown in the window, for example 'build game'."
- Shell's silence-timeout hint becomes '... or run it with job'.

VERIFY (each alone): `cargo test --workspace`; `cargo clippy --workspace --all-targets`; `npm test --workspace mnemo2`; `npm run check --workspace mnemo2`.

## Acceptance scenarios
- A worker runs `job {command: "cargo build", purpose: "build game"}` and gets the build's result in that one call; with wait_s 0 it gets the id at once.
- The window shows that call collapsed as 'job · build game — exited 0', and expanded like a shell call (purpose, command, output); a later job_wait on the same id shows 'job · build game — …'.
- An executor worker's `job` call running `git push` or `git stash pop` is refused exactly as job_start's was.
