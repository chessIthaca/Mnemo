# Plan: Long commands without polling: silence timeout, job tools, run_checks, neutral gate redirects

## Goal
Workers run long builds and tests in one tool call instead of detaching them and polling with sleep: the shell kills only silent or very long commands, job tools wait server-side, run_checks runs and records the project checks with structured results, and stale-read redirects no longer count as strikes.

## Kind
implementation

## Context
WHY: a worker on a Windows Bevy repo (FactoryGame, glm-5.3 / deepseek-v4.1-flash) can't finish `cargo build/clippy/test --workspace` inside the shell tool's fixed 5-minute limit (src/tool/agent/shell.rs:74 DEFAULT_TIMEOUT, enforced around :739; not configurable). Background processes are killed on purpose (TreeKillGuard, plan bfe2b09f: no process outlives its call, so workers can't leave dev servers behind). So workers launch builds as detached WMI processes and poll them with sleep and log reads. That costs one model round trip per poll, and the sleep is always too long or too short. Memory HOW 640bc134 and the procedural record 'Long Cargo validation under worker shell limits' describe the workaround; they go stale with this plan.

DECISIONS:
- The tree-ownership rule stays: nothing a call starts outlives what owns it. A job is owned by the session's job registry instead of a single call. The registry kills every job's tree when it is dropped (session end, merge, stop) and on job_kill. A job is never a way to leave a dev server running after the session.
- Timeouts become a silence timeout plus a hard cap: a command is killed after 5 minutes with no output on stdout or stderr, or after 60 minutes in total, whichever comes first. Cargo prints a line per crate and per test, so a long healthy build keeps running. Jobs get a 3-hour hard cap and no silence limit (they are watched with job_wait).
- run_checks is the structured way to run `.coding/checks.toml` `commands`. Its runs are recorded against the tip by the same rules as a counted shell run: an exact allow-listed command, run in the checkout root, exit 0, and a content tree unchanged by the run (pump.rs counted_check, review.rs record_worker_checks).
- A stale-read redirect (EDIT INTERCEPTED from the edit gate in src/agent/dispatch.rs) and an unknown read receipt error (src/tool/agent/read_registry.rs:188) are steering, not failures. They count neither as a strike nor as a success toward the escalation nudge (src/agent/route_question.rs Strikes, src-tauri/src/mnemo2/team/pump.rs ~727, src-tauri/src/mnemo2/team/nudge.rs). An exact repeat of the previous call still counts as a strike, as today.
- Build caches (shared CARGO_TARGET_DIR, sccache) are out of scope. Pool checkouts already keep target/ between dispatches (src/app/worktrees.rs:629-652); slow first-use builds get measured on FactoryGame first.

CONSTRAINTS: Windows PowerShell 5.1 and Unix sh are both supported, like shell.rs (cfg!(windows) branches; the macOS CI leg runs the tests). Reuse shell.rs pieces instead of copying them: TreeKillGuard, translate_powershell_chaining, the core-operation guard (`git merge|push` approval), shell_filter::filter_shell_output, cap_tool_output (src/tool/agent/mod.rs:72). New tools get the same SafetyLevel and approval treatment as `shell`. No #[allow] attributes. Docs that describe the shell limit (docs/FEATURES.md, the worker prompt in src/agent/prompt.rs if it names the limit, tool schemas) are updated in the step that changes the behaviour.

VERIFY (each alone on its line): `cargo test --workspace`; `cargo clippy --workspace --all-targets`. Focused: `cargo test -p mnemo --lib tool::agent::shell` (adjust the package name to the root crate's).

## Acceptance scenarios
- A worker shell command that prints a line at least every minute and runs 7 minutes finishes with its exit code; it is not killed at 5 minutes.
- A worker shell command that prints nothing for 5 minutes is killed with an error that names the silence timeout; one that keeps printing past 60 minutes is killed with an error that names the hard cap. Either way no process from its tree survives.
- job_start on a 7-minute build returns a job id at once; one job_wait call then returns the exit code, the run time and a filtered tail with the errors and summary, with no sleep calls in between.
- Ending or merging a worker session that has a running job kills the job's whole process tree; no process holds the worktree afterwards.
- run_checks on a clean worker checkout runs every .coding/checks.toml command, returns pass/fail per command with the first compiler errors (file:line) and failing test names, and each passing run is recorded as a passed check against the tip exactly like a counted shell run.
- A worker whose edit is intercepted by the stale-read gate, then re-reads and edits, gets no escalation nudge from those calls.

## Spec changes

### dispatch-routing

#### ADDED Requirements

##### Requirement: Stale-read redirects are not strikes
The system SHALL NOT count a failed tool result that is a stale-read gate redirect (EDIT INTERCEPTED) or an unknown read receipt error toward a worker's strike streak, and SHALL NOT let it reset the streak either. An exact repeat of the previous call SHALL still count as a strike.

###### Scenario: Intercepted edit followed by a re-read
- **WHEN** a worker's edit is intercepted by the stale-read gate
- **WHEN** the worker re-reads the file and edits again
- **THEN** no strike nudge is sent for those calls

###### Scenario: Repeated identical intercepted call
- **WHEN** a worker sends the same intercepted edit call three times in a row
- **THEN** the repeats count as strikes as before
