# Plan: Run-All done-orphan guard — detect landed work at the drain/adoption

## Goal
Stop run-all from re-dispatching items whose work already landed: when the main-agent-exit drain or the run-start adoption sweep handles an orphaned InFlight item, first check for landed-work evidence — the item's plan file (.coding/plans/<plan_id>.md) shows all steps checked AND at least one commit exists on the branch after the pre-item checkpoint sha — and if both hold, auto-resolve the item Done with an explanatory note (checkpoint sha preserved at the note head) instead of requeueing it to Pending for duplicate re-execution.

## Kind
bug_fixing

## Context
Root cause confirmed by code reading: drain_run_all_on_main_exit (src-tauri/src/ipc/run_all.rs:2567) and adopt_orphaned_in_flight (run_all.rs:2632) both requeue orphaned InFlight items to Pending unconditionally — neither checks whether the dead session's work already landed. Evidence available at requeue time: (a) the item's plan_id → .coding/plans/<plan_id>.md (mnemo::workflow::PlanFile::parse, steps have .done flags — the live case's plan 225e0dad shows all steps checked); (b) the pre-item checkpoint sha stamped in the item's note at dispatch (run_all_dispatch_next → set_note), parseable via extract_checkpoint_sha (run_all.rs:1627). DESIGN DECISIONS: (1) Landed = plan file all steps checked AND ≥1 commit after the checkpoint sha — the plan gate alone is too weak (steps checked before review/commit), the commit alone is too weak (mid-work commits); together they exactly match the died-between-commit-and-finish window. (2) "Any commit after the checkpoint" (git log sha..HEAD non-empty), NOT "commits referencing the item id": agent commits don't reliably carry the id, and commit_success is a no-op on a clean tree — exactly the died-after-commit case; during an item's flight its session is the only committer (the next item's checkpoint runs only after this item resolves). (3) No separate "work landed" marker: the death window sits between the agent's own commit and its finish call — no harness-controlled point exists inside it; the commit anchored by the per-item checkpoint IS the marker. (4) Safe default = requeue (today's behavior) when evidence is unverifiable (no plan_id, plan missing/incomplete/stepless, no sha, git error). (5) Lock discipline: run the git check WITHOUT the backlog store lock (clone the project root first, mirroring run_all_dispatch_next's checkpoint pattern), then re-take the lock and re-verify the item is still InFlight (+ still unowned, for adoption) before transitioning. InFlight→Done is a legal guarded transition (backlog.rs:229).

## Bug
Run-All re-dispatches items whose work already landed: a session that dies between committing and finishing leaves its item orphaned InFlight (only finish marks done), so the main-exit drain / run-start adoption sweep requeues it to Pending and run-all re-executes the fully-landed task. Live case 2027-01-07: item 35b94671 (plan 225e0dad, commit eac25dc, since merged to main) was re-dispatched — caught by the user before duplicate edits.
