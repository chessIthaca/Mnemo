# Plan: Finish half-removed worker checkouts on merge and delete

## Goal
A merged or deleted worker's checkout is fully removed even when git deregisters it before the folder is gone, and a leftover, unregistered agent checkout never blocks deleting its worker; nothing outside that worker's own `.worktrees/agent-<id>` folder is ever removed.

## Kind
bug_fixing

## Context
WHY: workers became undeletable from mission control. On 2026-10-31 the lead found 11 such leftovers: 9 folders whose `.git` file points to worktree admin data git had already pruned (git there says "not a git repository"), and 2 fragments with no `.git` at all, where git walks up to the main checkout on `wt/mnemo`. The lead removed those 11 folders by hand; the code still produces new ones (the merge of workerSummaryUI31 on 2026-10-31 left one).

DECISIONS:
- Registration is decided from the main repository, never by running git inside the folder: a checkout counts as registered only if `git worktree list --porcelain` run in the workspace root lists that exact path (normalize case and separators on Windows). Running git inside an unregistered folder is forbidden because a fragment without `.git` resolves to the main checkout.
- A folder at `worker_checkout(root, id)` that is not registered is a "leftover": it holds no git state of its own (its work is either merged or lives on the `wt/agent-*` branch, which is judged separately as today). Leftovers are removed with a filesystem removal (retrying briefly for Windows locks), strictly limited to that exact path: canonicalize it, require it to be a direct child of `<root>/.worktrees` named `agent-<short id>` of a record that owns its branch (`owns_its_branch`), and refuse symlinks/junctions at that path. Never remove anything else.
- `cleanup_agent_worktree`: if the worktree is registered, keep today's clean check and `git worktree remove`; once it is no longer registered (including right after a remove that deregistered it), remove the leftover folder instead of calling `require_clean` again. Success means the folder is gone.
- `inspect_deletion`: a leftover is not blocked; report it (e.g. a `leftover` flag on `WorkerDeletion`, shown or ignored by the UI as the existing fields are) and keep the unmerged-commits check on the branch. `delete_one` removes a leftover with the same guarded filesystem removal.
- `cleanup_workspace` (the project Clean up action) also removes leftovers of records that own their branch, with the same guard, and still never touches Mnemo1 run-all worktrees.
- Registered checkouts keep every existing protection (branch check, dirty-work confirmation). No frontend change is required; if `WorkerDeletion` gains a field, keep the TS type in `mnemo2/src/lib/types.ts` in sync only if the frontend reads that type.

## Acceptance scenarios
- A merge whose `git worktree remove` deregisters the worktree but leaves the folder ends with the folder gone and no "worktree cleanup needs attention" error (regression test a_half_removed_checkout_is_finished_after_merge).
- Deleting a worker whose checkout is a leftover (dangling .git file, or fragments without .git) succeeds and removes that folder; today it is refused (regression test a_leftover_checkout_does_not_block_deleting_its_worker).
- Leftover removal touches only `<root>/.worktrees/agent-<short id>` of that worker: the main checkout, sibling folders and a symlink/junction at the path are never deleted (regression test leftover_removal_never_leaves_the_worker_folder).
- Registered checkouts keep today's protections: a dirty or wrong-branch registered checkout still blocks or asks for confirmation, and the whole mnemo2 lib suite passes, including the existing cleanup tests.

## Bug
After a merge, a worker's checkout under .worktrees/agent-* can be left half-removed: git deregisters the worktree but the folder stays (Windows file locks), and the merge reports "merged, but worktree cleanup needs attention: git status --porcelain failed: fatal: not a git repository". Such workers can then never be deleted in Mnemo2: delete refuses with "its checkout could not be read" or, when only fragments without .git remain, "its checkout is on 'wt/mnemo', not wt/agent-…" because git resolves the folder to the main repo. The user had 11 undeletable workers this way.

## Decisions
- 2026-11-01: Checkout removal must wait for every worktree-bound user, not just the parent AgentLoop: descendants and the consolidation corpus digest are included in the release boundary.
- 2026-11-01: Family cleanup must use stable lineage that survives intermediate exits, and cancellation must be idempotent per agent rather than repeated on every release poll.
- 2026-11-01: Distinguish closed cancellation channels from full queues during close; Closed is normal exit progress, Full remains a real cancellation failure.
- 2026-11-01: A failed-close retained LiveWorker must never accept new work without a functioning event pump; either preserve/restart the pump or make the handle retry-only.
- 2026-11-01: Cleanup-retry-only must be enforced centrally for every non-cleanup worker command, and the recovery test must use a genuinely active pump before the failed close.
