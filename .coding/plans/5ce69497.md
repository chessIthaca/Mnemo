# Plan: Second mnemo instance shows blank white window — per-instance WebView2 user data folder

## Goal
Fix the second (and any further) production mnemo instance showing a blank white window: give each additional instance its own WebView2 user data folder (per-pid, under the app-local-data dir) so it initializes its own browser process instead of colliding with the first instance's in-use default UDF, while the first instance keeps the persistent default profile unchanged. Contained bug fix with a fails-without-fix regression test, a BUG memory, and a green warning-free suite.

## Context
STATIC ANALYSIS (2027-01-13, before the reproduce step — verify against live evidence): both instances create their WebView2 environments with an EMPTY user data folder. No `data_directory` anywhere in app code: agent-chat builder at src-tauri/src/main.rs:248-252, both browser-child builders at src-tauri/src/ipc/browser_webview.rs:330-337 and :411-418 are plain `WebviewBuilder::new(...)`. wry's create_environment passes `&data_directory.unwrap_or_default()` (vendor/wry/src/webview2/mod.rs:287-291, :348) → WebView2 resolves the Win32 DEFAULT UDF = the exe path + ".WebView2" (MS Learn "Manage user data folders": "The default UDF is the executable path of your app + .WebView2", e.g. target\release\mnemo-app.exe.WebView2; "A UDF can only have at most one WebView2 session at a time"). MS Learn "Process model for WebView2 apps": an environment for a user data folder another environment already uses, if not configured identically, "will fail to create WebView2 objects" — true across processes. The window is built BEFORE the webview (main.rs:240-245 then :248-252), so instance B shows a live-but-blank white frame. Prior repo evidence of the same collision class: backlog 55ba23b1 — a second env with a different CDP port "renders but gets no CDP" (silent attach to the first browser process). The CDP-port fix (plan 89daef6f, DECISION memory 1d20f353) gave each instance its own PORT but both still resolve one shared UDF → one browser process — the white-frame root cause is untouched by it.

FIX DESIGN (user-confirmed on 2027-01-13: "it should create its own, right?"): per-instance WebView2 user data folder — the FIRST instance keeps the persistent default profile (zero behavior change: cookies/OS-SSO persistence across restarts survive), every ADDITIONAL instance gets a private per-pid profile → its own browser process → no UDF collision, no white frame. Decision via a Windows named mutex keyed on the resolved default UDF path (first = primary; subsequent = secondary). windows-sys 0.59 already a target.`cfg(windows)` dependency at src-tauri/Cargo.toml:48-49 (extend its feature list, e.g. Win32_System_Threading for CreateMutexW, rather than adding a crate).
