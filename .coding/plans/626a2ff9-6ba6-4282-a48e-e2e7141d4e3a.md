## Spec-driven development

Mnemo turns software development into a disciplined spec loop: the human and the AI iterate on a spec until it is precise enough to execute, then Mnemo pins that spec into a step-by-step plan and enforces it through the state machine described above.

1. **Iterate on the spec, together.** Each session starts in Planning, where the agent explores the codebase and the two of you converge on what exactly will be built — goal, constraints, context, and an ordered list of steps. The spec lives on disk (`.coding/plans/`) where you can read it, edit it, and revisit it later.
2. **The spec becomes the execution plan.** `create_plan` writes that agreed spec as the plan of record. Its steps are the contract: the agent may not touch the project until the spec exists, and it must complete steps one at a time, checking each off on disk. Sub-plans nest and pop back to the parent, so even mid-plan detours stay inside the spec.
3. **The spec is written for low-capability models.** Steps are deliberately detailed and self-contained: explicit file paths, exact actions, one-line context — 'a step must not assume the model remembers an earlier step.' Because the reasoning has already been done in the human↔AI design loop, the plan can be executed by a small, cheap, fast model that simply reads each step and does exactly what it says.
4. **Different models for different jobs.** Mnemo routes models per workflow state: a strong model for Planning (reasoning about the spec), a cheap fast model for Executing (following the detailed steps), and a fresh model for Reviewing (an independent read-only pass that audits the diff, and whose findings must all be fixed before commit). Configure each via the [models] section of config.toml — planning, executing, reviewing, complete, subagent, and per-skill overrides. Result: you pay for expensive reasoning where it matters (spec design, review) and spend pennies on the mechanical execution — cutting both cost and wall-clock time.
4. **The loop closes.** Every completed implementation plan is reviewed, fixed, and committed; research plans stay read-only. Then the cycle starts again — the next spec builds on the memory of the last.
