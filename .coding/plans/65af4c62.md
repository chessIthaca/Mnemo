# Plan: Guard compaction against runaway tool output — budgeted summarizer prompt, mechanical fallback, per-result caps

## Goal
Make compaction always able to recover a context bloated by runaway tool output (images/base64 dumps, huge reads): (L1) budget the summarizer's request against the summarizer model's real window — advancing the cut so more recent messages stay verbatim (no data loss) and truncating per-message with a marker when the region alone is over budget, with byte-identical prompt output whenever the region fits; (L2) fall back to a mechanical compaction (drop the summarized region into a note + aggressive tool-result truncation with re-run pointers) when the provider rejects with a context-size error, so manual /compact and auto-compaction never fail on size; (L3) bound individual tool results — a TOOL_RESULT_MAX_CHARS=100_000 ingestion cap at tool-feedback time and an oversize truncation rule inside compact_old_tool_results's hysteresis keep window — so no single result can wedge the context. All paths covered by regression tests that fail without the fix.

## Context

Secondary: compact_old_tool_results (src/agent/context.rs:689, called turn.rs:1571 keep=10 keep_high=20 summary_chars=500) is hysteresis-gated and keeps the newest intact results — a single monster result survives all compactions. Third gap (found while reading): MessageContent::Parts (image blocks, src/provider/mod.rs:587/632 ImageUrl) are (a) INVISIBLE to token accounting — count_message_tokens (context.rs:1283) uses content.as_text(), which drops image parts, so an image-heavy context is undercounted and compaction may never fire — and (b) skipped by compact_old_tool_results (Parts => continue at context.rs:758), so they can never shrink. Fourth gap: marching the summary cut back keeps more recent messages VERBATIM, so on a 7.2M-token history the compaction result is still ~6M tokens — the compaction "succeeds" and the next request still 400s. Size-error classification already exists: Error::is_non_retryable (src/error.rs:102) covered "maximum context length" etc. but NOT DeepSeek's "longer than the limit" wording from the screenshot; Capabilities.max_context is on every client (src/provider/mod.rs:44). Fix design: (L1) `pub fn context_budget(max_context, max_output_tokens)` = window − (max(4096, output) + 2048), floor 8192; `budgeted_cut_index(messages, cut, budget)` marches the cut BACKWARD (never forward — the region messages[1..cut] must shrink) with an incremental per-message token sum (not O(n²) re-tokenization) keeping the boundary off Role::Tool; `build_summary_prompt(messages, to_summarize, budget_tokens)` is byte-identical to today when the region fits, and truncates per-message with SUMMARY_BUDGET_TRUNCATION + SUMMARY_BUDGET_NOTE when not (backstop for direct callers). Constants SUMMARY_PROMPT_HEAD/UPDATE_HEAD/UPDATE_MID/UPDATE_TAIL split SUMMARY_FORMAT so frame tokens are measurable. (L1b) count_message_tokens must price Parts (text parts + ImageUrl byte length) so image-heavy contexts are visible to the trigger and the ceiling checks. (L1c) POST-CONDITION: after assembling system+summary+recent, if the result exceeds the SENDABLE budget (the turn model's window, threaded as a new `sendable_budget` param since the summarizer may be a smaller model), shrink it recoverably: aggressive compact_old_tool_results(result, keep=0, keep_high=0, summary_chars=AGGRESSIVE) with re-run pointers, then — last resort — drop the oldest tail messages on a non-Tool boundary keeping system+summary+newest. (L2) is_context_overflow() → mechanical_compaction(messages, cut) = note system message + aggressive tool-result truncation, returned Ok (recovery); non-size errors still Err. (L3) pub const TOOL_RESULT_MAX_CHARS = 100_000 (~25K tokens): ingestion cap at the tool-feedback Message::tool_result site (turn.rs:1516) via a shared cap_tool_result_text helper, plus an oversize rule inside compact_old_tool_results that truncates monsters EVEN when the hysteresis gate is a no-op and EVEN in the keep window, and drops image Parts from OLD results (replace with a text marker + re-run pointer) since Parts can otherwise never shrink. (1) MEASUREMENT WAS THE REAL O(n²): the incremental cut march was O(n) as designed, but tokenizing a single unbroken run is not — tiktoken-rs byte_pair_encode is O(n²) in PRETOKEN length (cl100k's `\p{L}+` matches a base64 blob / "x".repeat(N) as ONE piece). Measured raw: 4K=33ms, 16K=541ms, 32K=2.06s, 64K=8.32s (4x per doubling) ⇒ 128K≈33s, 400K≈5min; mixed text is fine (200K chars of "word " = 167ms). This made the whole agent::context suite un-runnable (one test spun CPU forever). Fix: TOKEN_MEASURE_CHUNK_CHARS=2048 (+floor_char_boundary); prompt_text_tokens measures strings longer than the cap CHUNK-WISE and sums — linear cost, and the sum is a documented CONSERVATIVE UPPER BOUND (no BPE merge spans a chunk split), which is the safe direction for budget guards. count_message_tokens now routes content/reasoning/tool-args through prompt_text_tokens so turn accounting and the summarization budget share ONE measure (was: direct encode_with_special_tokens calls). The slack absorbs tokens that merge across the frame/block junctions, so "the built prompt fits its budget" is strict instead of landing a token or two over.

Also normalizes the INCOMING cut off Role::Tool so the bail-out return cannot orphan a tool result.
