# Plan: Add op="status" to git_read — a read-only home for "is the tree clean?"

## Goal
Give git_read a read-only op="status" so "is the tree clean?" has a home on the read-only surface: implemented as `git status --short` plus a one-line summary (clean tree → "(working tree clean…)", dirty → "(N changed, U untracked)"), with the unknown-op error sharpened to name the `git` tool as the write-ops alternative, the schema description documenting the new op, regression tests for dirty/clean/unknown-op, and the docs + budget ceilings synced. Fixes the tool-surface gap observed live during plan 263a9e31 (op:"status" rejected with no substitute pointer → read-loop before falling back to the approval-gated `git` tool).

implementation

DESIGN DECISIONS:
(a) ADD the op to git_read (the item's fix direction 1), NOT route to the `git` tool: the `git` tool is NeedsApproval and hidden in the read-only Planning/Complete states — exactly where "is the tree clean?" is asked most (pre-commit/pre-dispatch checks) — so routing would leave the check unavailable precisely when needed. git_read is AutoRun and visible everywhere.
(b) GitStatusTool as a full Tool-impl delegate in git_read.rs (pattern-consistent with GitLogTool/GitShowTool; dispatched via self.status.execute(args).await like the siblings). It is NOT registered standalone, so its schema never rides the tools array (no budget cost).
(c) Implementation: `git status --short` via run_git_read, then a one-line summary appended to result.output computed from result.data["stdout"]: empty → "(working tree clean — no changes, nothing untracked)"; else "(N changed, U untracked)" with `?? `-prefixed lines counted as untracked. Interpretation of the item's "(plus an untracked/ignored summary)": count untracked explicitly; ignored files are excluded by --short by design (that is the point — they are not tree dirt). Read-only: `git status` is the same command is_git_read_only already classifies read-only for the `git` tool; no staging, no fetch, no optional-locks flags.
(d) Unknown-op error sharpened to: "unknown op '{other}' — valid: diff, log, show, status; for write operations (commit/merge/push/…) use the `git` tool" — names the working alternative for the remaining confusion class (write ops tried on the read-only tool), which is what let the original read-loop persist.
(e) Tests live in git_read_tool.rs's tests module (it already spawns git via the repo() fixture — lines 122-140 — unlike git_read.rs's tests which are pure validation). Clean-tree case needs the fixture's edit committed first.

CLASSIFICATION: kind=implementation — the item adds a capability (a new op + sharpened error), and its own text says "this is a schema/ergonomics gap, not a bug in an existing op". The observed read-loop (plan 263a9e31, 2026-09-21: op:"status" rejected, agent re-emitted the invalid call repeatedly before falling back to the `git` tool) is the motivation, documented here.
