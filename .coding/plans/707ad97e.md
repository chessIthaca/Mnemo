# Plan: Fix flaky second_heavy_command_waits_for_the_slot (wait shorter than the 2 s note threshold under load)

## Goal
The test proves the same behavior (a queued heavy command waits for the only machine slot, announces the wait once on the live view, still runs, and its result carries the "NOTE: waited …" line) deterministically on a loaded machine, without changing product code.

## Kind
bug_fixing

## Context
ROOT CAUSE (lead-verified by reading the code): the result note is emitted only when the slot wait reaches REPORT_WAIT_AFTER = 2 s (src/host/machine_slots.rs:40, wait_note at :258-261). The test (src/tool/agent/shell.rs:1876-1950) lets a FIRST heavy command, `Start-Sleep -Milliseconds 3000` / `sleep 3` (slow_heavy_command, :1833), hold the only slot. wait_until_slot_is_held (:1859, polling every 100 ms) returns only after it sees the slot held, and only then does the second command start acquiring. acquire polls every 500 ms (POLL_INTERVAL, machine_slots.rs:35). Under load, the detection delay, the second call's own setup and the 500 ms poll eat more than 1 s of the first command's 3 s hold, so the second command waits less than 2 s and correctly gets no note. Start-Sleep prints nothing, so the output is "" (the observed failure). The `elapsed >= 700ms` assert passes trivially because elapsed includes the second command's own 3 s run. The product behavior is right; the test's timing is not.

FIX (test only, the pattern the sibling test slot_wait_is_not_counted_as_silence at shell.rs:1952 already uses): the TEST holds the only slot itself with `HeavySlots::new(slots, 1).try_take().guard().expect(..)` instead of a first command. It starts the second command in a spawned task with a live OutputSink. It waits on the EVENT (the live sink receives "waiting for a build slot (1 in use on this machine)"), polling the shared Vec with a generous 120 s deadline. Only then does it keep holding for REPORT_WAIT_AFTER + 1 s (3 s, measured from that moment) before dropping the guard. The second command's slot wait is therefore at least 3 s by construction, however slow the machine is. See the HOW memory "write tests that stay green under a loaded machine (wait on the event, not on the clock)".

FILES: src/tool/agent/shell.rs (only the test second_heavy_command_waits_for_the_slot and, if they become unused, the helpers slow_heavy_command / wait_until_slot_is_held; keep any helper another test still uses). No product code changes, no #[allow], no cfg(windows) (cfg!(target_os) inside the existing helper is already accepted). Temp dirs come from the existing tempdir() helpers the module uses.

VERIFY: `cargo test -p mnemo --lib tool::agent::shell` (repeat the single test 5 times: `cargo test -p mnemo --lib second_heavy_command_waits_for_the_slot`), then `cargo clippy --workspace --all-targets`. Do not run `cargo test --workspace`; Mnemo runs the full checks.
