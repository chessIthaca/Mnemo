# Plan: Multi-platform build: macOS support + GitHub Actions + game_* gating

## Goal
Make myharness buildable/distributable for macOS alongside Windows: gate the Windows-only live-webview stack off on macOS (game_* agent tools unregistered; Browser tab shows a red explanation panel), add the macOS runtime must-fixes ($PATH inheritance, cfg-gated WebView2 env var), bundle.macOS config, and a GitHub Actions workflow that tests + builds Windows and macOS artifacts (secrets-driven signing, ad-hoc fallback).

## Kind
implementation

## Context
Follow-up to the 2026-08-20 macOS research (.coding/analysis/2026-08-20-macos-port-research.md, plan de68c811): user wants macOS as a build target with a GitHub Actions pipeline, game_* live-inspection tools disabled on macOS, and the Browser tab showing a red explanation panel there instead of trying to create a child webview. Key facts verified this session: (1) game_* tools (GameScreenshot/Eval/Snapshot/Navigate/Click/TypeTool) are registered unconditionally as one block at src/agent/factory.rs:658-663, right after the headless browser_* tools (:643-652) which share the same `ctx` closure — so cfg-gating just the game_* block cannot orphan `ctx`; the agent's system prompt is built from the registry, so unregistered tools vanish from it automatically. (2) The child webview is created ONLY in browser_webview_ensure (src-tauri/src/ipc/browser_webview.rs:201-248); set_rect/navigate/set_tab_visible/overlay_* already tolerate webview=None (no-op), so a guard in ensure is the single choke point. (3) BrowserView.tsx (frontend/src/components/views/BrowserView.tsx) is the whole Browser tab UI: URL bar + openUrl() → browserWebviewEnsure + placeholder div; it already renders red error boxes (style: border-red-900 bg-red-950/40 text-red-300, line 100-104). useBrowserRect (frontend/src/hooks/useBrowserRect.ts:56) reports rects unconditionally. (4) main.rs sets WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS unconditionally at main.rs:89-95; helper browser_inspection_enabled (main.rs:44-49) is used only there — both must be cfg(windows)-gated together or deny(warnings) fails the macOS build (dead fn). (5) No platform detection exists anywhere in the frontend (searched); no @tauri-apps/plugin-os dep. (6) src-tauri/Cargo.toml has no target-specific deps yet; root Cargo.toml already demonstrates the [target.'cfg(windows)'.dependencies] pattern. (7) tauri.conf.json: bundle.targets="all", icons include icon.icns; no bundle.macOS section. (8) No .github/ exists. (9) macOS gotcha from research: GUI apps don't inherit shell $PATH — adopt fix-path-env crate (tauri-apps) at startup on unix, or the agent's `sh -c cargo/npm` fails in a shipped .app. (10) Repo conventions: unpiped cargo test reading test-result lines + $LASTEXITCODE (PowerShell, Windows dev machine), #![deny(warnings)] both crates, doc comments on pub fns, vitest in node env (no DOM/component harness — static JSX ships without new tests, precedent b33b4b95), pure-helper + both-branch unit tests pattern for gates. macOS CI cannot sign without Apple secrets → workflow must be secrets-driven (signs when APPLE_* present, ad-hoc otherwise). This is a feature plan (not a defect fix): regression tests focus on the gate helpers; the macOS compile itself is validated by the new CI job.
