# Plan: External lead follows Mnemo2's memory, bug and spec workflow

## Goal
When Claude Code leads through the mnemo plugin, Mnemo2 makes it follow the same memory workflow as the built-in lead: search memory before planning, file bugs as bug_fixing plans, and record durable SPEC:/DECISION:/HOW: learnings before a plan closes. The server enforces this, and the plugin's instructions and skills describe it.

## Kind
implementation

## Context
WHY: the user found that Claude Code, leading Mnemo2 over MCP, skips Mnemo2's memory/bug/spec workflow. It planned without memory_search, ran bug fixes as implementation plans, and recorded learnings only when reminded. The built-in lead is bound by its compiled prompt (src/agent/prompt.rs TOOL_STRATEGY: memory_search MANDATORY before planning and before diagnosing a bug with record_type "bug", memory_write the moment something durable is learned; MEMORY_RECORDS: SPEC:/DECISION:/BUG:/HOW: typed records, supersede instead of delete; STATE text: bugs ALWAYS kind bug_fixing, except bug-triggered FEATURES that add capabilities or span modules). The external lead only gets the soft "Project memory" section of the mnemo-lead skill and nothing in the MCP initialize instructions. The user's requirement: "when you use the mnemo2 mcp you always have to use the memory, bug and spec workflow of mnemo2". So it must be enforced, not only described. This is a feature-scale change motivated by that report, so it is an implementation plan.

DECISIONS:
1. The gates apply only while an external lead is attached to the project's team. The built-in lead keeps its prompt-based behaviour and must never be blocked by them.
2. Recall gate: an MCP plan_create is refused unless this external-lead attachment ran memory_search since its previous plan_create (or since attaching). A bug_fixing plan_create additionally needs a memory_search with record_type "bug" in that window. The refusal names the exact call to make. Passive recall in the result stays.
3. Bug-kind reminder (not a refusal): an MCP plan_create with kind implementation or research whose title or goal reads like a defect fix (fix, bug, crash, hang, broken, regression, case-insensitive whole words) gets one appended line. It says bugs use kind bug_fixing unless the fix adds capabilities or spans modules.
4. Knowledge gate at close: while an external lead is attached, an implementation or research plan cannot close until at least one durable knowledge record exists that was written, amended or superseded at or after the plan was created. Durable means a live record of type spec, decision or how (bug also counts), not plan-scoped and not an automatic PLAN:/REVIEW: digest. bug_fixing plans are exempt because their BUG: record is captured automatically at close. The blocked reason tells the lead to record what the plan established with memory_write (a SPEC:/DECISION:/HOW: title, no plan IDs, branches or commit hashes), then call plan_step_done on the last step to close. The gate is a CloseOutcome::Blocked reason like the others, so the existing "cannot close yet" notice and retry path carry it.
5. Reminders: a successful team_merge result, and the "Plan X is closed" notice, for an external lead end with a one-line reminder to record durable SPEC:/DECISION:/HOW: learnings and supersede stale records.
6. LEAD_INSTRUCTIONS gains one mandatory memory-workflow line (search before planning and before a bug, bug_fixing for bugs, record durable learnings before close, details in the mnemo-lead skill). It names only listed tools.
7. Skills mirror the built-in rules as MANDATORY triggers, adapted to the MCP tool names (memory_search, memory_write, memory_amend, memory_update, memory_supersede, plan_create kind bug_fixing, plan_update regression_test). No new tools.

## Acceptance scenarios
- With an external lead attached, an MCP plan_create before any memory_search is refused with a message naming memory_search; after a memory_search it succeeds.
- With an external lead attached, an MCP plan_create of kind bug_fixing is refused until a memory_search with record_type "bug" has run.
- With an external lead attached, an implementation plan whose steps are done and whose review passed reports 'cannot close yet' naming memory_write until a durable SPEC:/DECISION:/HOW: record is written; then plan_step_done closes it. Plan-scoped notes do not satisfy the gate; bug_fixing plans close without it.
- Without an external lead (built-in lead), plan_create and plan close behave exactly as before.
- The MCP initialize instructions and the mnemo-lead, mnemo-plan and mnemo-review skills state the mandatory memory workflow, and `cargo test --features mnemo2 --lib mnemo2::` passes.
