## Goal
Close the permanent-staleness half of the content-index staleness defect by making the watcher's trigger set EQUAL to the content index's coverage set instead of a blanket `.coding/` exclusion. A write to any `.coding/` artifact the index covers (knowledge, plans, reviews, skills, backlog.jsonl) must trigger a debounced incremental pass, while the app's own SQLite store family (codegraph.db + memory.db and their -wal/-shm/-journal sidecars) stays excluded — the only exclusion the self-trigger-loop argument actually requires, since those are the only files an index pass writes. Achieved by extracting search.rs's existing `.coding` store exclusion into one shared `pub(crate)` predicate used by BOTH `should_search` (what gets indexed) and `is_indexable_path` (what triggers a pass), so the two sets cannot drift apart again — with a live watcher regression test that fails on the current code.

## Context
ROOT CAUSE (diagnosed 2027-01-25, recorded in BUG memory/.coding/knowledge/bug/2027-01-11-content-index-staleness-root-causes-coding-index.md). Two mechanisms make the content index stale, both from Mnemo's own writes. Mechanism 1 (transient, by design, NOT this plan): the 800 ms watcher debounce — src-tauri/src/main.rs:2066 spawns GraphWatcher::spawn(graph, root, Duration::from_millis(800)), and watcher.rs debounce_loop (:201-213) sleeps that quiet period before running a pass; the just-shipped adaptive inline repair (plan 90fab97e, commits 06276aa + d8152f7) covers that window. Mechanism 2 (PERMANENT — the defect this plan fixes): an ASYMMETRY between the index's coverage and the watcher's trigger set.

THE ASYMMETRY, exactly:
- Index side: `should_search` (src/tool/agent/search.rs:85-132) accepts every `.coding/` file EXCEPT the app's SQLite stores, which it excludes deterministically via a local `const DATA_FILES` (search.rs:109-118): codegraph.db, codegraph.db-wal, codegraph.db-shm, codegraph.db-journal, memory.db, memory.db-wal, memory.db-shm, memory.db-journal. Its own comment (:100-107) explains the exclusion is loop-safety, not searchability: the graph DB "changes during every pass, so it would re-index forever". So `.coding/knowledge/*.md`, `.coding/plans/*.md`, `.coding/reviews/*.md`, `.coding/plans/stack.json`, `.coding/instance.json`, `.coding/skills/*.toml` and `.coding/backlog.jsonl` ALL get content rows + cg_files mtime rows.
- Watch side: `is_indexable_path` (src/codegraph/watcher.rs:52-82) rejects ANY path with a `.coding` component — a BLANKET rule at line 61: `if crate::tool::agent::search::is_ignored_component(name) || name == ".coding" { return false; }`. Its doc (:34-46) admits the consequence verbatim: "Those files' content rows simply refresh on the next pass."
- Net: files the index covers can never trigger the pass that would refresh them. That is the bug class itself (indexed-but-never-watched), and it contradicts the watcher module doc's own stated contract (:17-19, :35-38) that it "Mirrors walk_searchable's coverage".

WHY THE BLANKET RULE IS OVER-BROAD: it existed for ONE reason — the codegraph DB is written DURING an index pass, so watching it self-triggers a reindex loop (watcher.rs:40-46). That reason is satisfied exactly by the DATA_FILES set the search tool already uses. The doc's second stated worry (per-step bookkeeping "would churn passes all session") does not survive inspection: `instance.json` is written ONLY on launch (src/instance_marker.rs:47-55 — last-writer-wins, no heartbeat, no periodic refresh), and `stack.json` only on plan-step transitions; both are debounced into one pass per burst, and passes are incremental (content-hash gated). Nothing an index pass writes lives outside the DATA_FILES family, so the narrowed exclusion is provably loop-free.

FIX DIRECTION (make the two sets equal by construction — no index-coverage change): extract search.rs's `.coding` store exclusion into ONE shared `pub(crate)` predicate taking a ROOT-RELATIVE path, e.g. `pub(crate) fn is_coding_data_file(rel: &Path) -> bool` (same semantics: first component `.coding` AND file name in DATA_FILES). `should_search` calls it (pure refactor — behaviour-preserving). `is_indexable_path`'s `under_base` keeps the `is_ignored_component` loop for the search ignore rules and then returns `!is_coding_data_file(rel)` instead of rejecting `.coding` wholesale. Keep the canonical-form fallback (:71-81) intact — it shares `under_base`, so it inherits the fix automatically.

REGRESSION-TEST DESIGN (must fail on the current code and pass after): (a) a LIVE watcher test in src/codegraph/watcher.rs mirroring `watcher_reindexes_on_new_source_file` (:378-408) — tempdir root, write `a.rs`, `CodeGraph::open_in_memory(root)`, `index(None)`, `GraphWatcher::spawn(graph, root, Duration::from_millis(100))`, then write `.coding/knowledge/live-artifact.md` containing a unique marker and poll `graph.search_content(marker, 10)` for 200 x 50 ms, asserting a hit. It must use the existing 200 x 50 ms poll pattern (FSEvents on macOS delivers events after a latency window — the macOS CI leg has burned this project twice, run 35521221353). (b) unit assertions on `is_indexable_path`: `.coding/knowledge/x.md`, `.coding/reviews/r.md`, `.coding/plans/90fab97e.md`, `.coding/backlog.jsonl` → true; `.coding/codegraph.db`, `.coding/memory.db-wal` → false (also fail today for the first group).

## Bug
Files under `.coding/` are indexed by the content index but never watched: writing .coding/knowledge/*.md, .coding/plans/*.md, .coding/reviews/*.md or .coding/backlog.jsonl fires NO watcher event, so those FTS rows stay stale until an unrelated non-.coding file happens to change, the app restarts, or someone rebuilds manually. Observable symptom (live 2027-01-25): a `search` reports "content index stale for N file(s)" with nobody else editing the tree, and the very next query is clean only because an unrelated edit triggered a pass. In an artifact-heavy session (plans, memories, reviews) the staleness is permanent, not a lag.
