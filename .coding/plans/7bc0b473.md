# Plan: Finer LLM trace: split Connect into upload + server wait, richer live statuses

## Goal
Split the trace's ambiguous Connect bucket into non-overlapping segments — prep → upload → server wait → generation — via a stamping body wrapper in both providers, fix the connect/ttft double-count in the phase bar, and replace the coarse "connect" live status with a finer state set (uploading, waiting for first token, streaming, stalled), end to end: kernel record → Tauri DTO → Mnemo2 Trace UI, with tests at every layer.

## Kind
implementation

## Context
Why: the 2026-11-05 investigation (SPEC memory record "Trace Connect phase for SSE providers is prefill+TTFT, not network connect") showed the ADSK gateway serving GLM-5.3 sends response headers only WITH the first chunk, so connect_ms == ttft_ms on all 22 timed calls of run r1793901734063-57164-1 — the Connect phase silently absorbs the model's prefill, the phase bar double-counts the same window (connect and ttft segments overlap), and the live status collapses everything before the first token into one opaque "connect" the user watched for ~5.3s. The user asked for a finer trace with more status.

Current anchors: connect_ms = record_created → headers (anchors src/provider/openai/stream.rs:47-55; stamped at :308-315 plus ~8 more sites incl. stall/error paths); ttft_ms = post_sent → first chunk; prep_ms covers body build; the request body is pre-serialized and attached via reqwest .body() (src/provider/openai.rs:456, :666, :752; post_sent stamped at :660; a second send site is the reasoning_effort fallback retry). Frontend: phases pushed around mnemo2/src/lib/trace.ts:654, MetricTerm glossary union at :1223-1244, phase descriptions ~:1290. Tauri serving: src-tauri/src/mnemo2/trace_view.rs (index row ~:1829). Design doc: .coding/design/mnemo2-llm-trace.md.

Decisions taken: (1) new record fields upload_ms (post_sent → body fully written, stamped by a wrapping body stream — reqwest Body::wrap_stream over the pre-serialized bytes; share the instant into the stream task the way pending_backoff_ms is shared, src/provider/openai.rs:215/:399) and server_ms (upload done → headers), plus chunks (SSE byte-chunks read). (2) connect_ms and ttft_ms stay unchanged for compatibility; connect = prep-sliver + upload + server. (3) The phase bar draws NON-OVERLAPPING segments only — prep | upload | server wait | generation (reasoning/content split retained, stall overlay retained); ttft becomes a metric chip, not a bar segment, fixing the double-count. (4) Live status is derived client-side from stamped fields (no new kernel enum): preparing → uploading → waiting for first token → streaming → stalled → done/error; the worker follows whatever mechanism trace.ts currently uses for the live "connect" state. (5) Both providers (openai + anthropic) get identical stamps — the trace is shared. (6) Backward compat: old rows lack the new fields → null; absent segments collapse, no NaN. (7) DNS/TCP/TLS split is OUT of scope: reqwest pools connections (keep-alive + TLS resumption), handshake is ~0 on reuse and not exposed by reqwest's API.

Known edge case: 3 of 22 rows in the current run (ids 2, 12, 20) have prompt 0 and null stream timings — cause unidentified (full trace-to-disk logging was enabled 2026-11-05 to catch the next one). The new status model must render such rows as complete calls with absent segments, not break.

Constraints: warning-free build (#![deny(warnings)] at both crate roots — no #[allow]); doc comments on public functions; Mnemo2-side cargo checks need --features mnemo2 (project memory); no screenshots for UI verification — source and tests only (standing user correction); PowerShell — never trust a piped exit code, read $LASTEXITCODE or the test-result lines.
