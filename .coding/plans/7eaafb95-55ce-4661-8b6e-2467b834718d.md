# Plan: Spike: prove CDP attach-to-running-browser (chromiumoxide Browser::connect + Tauri WebView2)

## Goal
Prove the chromiumoxide Browser::connect API + CDP target-enumeration/attach flow works end-to-end, and verify Tauri WebView2 exposes a CDP debug port — de-risking the iframe+CDP-attach architecture before the full build.

## Kind
implementation

## Context
Architecture (saved to memory): iframe + CDP attach. Human plays the game in an <iframe> (shares Tauri WebView2's GPU/WebGPU). Agent attaches to that SAME WebView2 via its CDP debug port and inspects the human's live game state. BrowserManager gains a connect mode alongside its existing launch mode.

THREE MAKE-OR-BREAK UNKNOWNS the spike must prove before the full build:
1. Does chromiumoxide::Browser::connect(ws_url) exist in 0.7? (attach to already-running browser, vs Browser::launch which spawns)
2. Does the connect flow work end-to-end? (launch Chromium exposing a debug port → fetch wsUrl from http://localhost:PORT/json/version → Browser::connect → enumerate targets → attach → screenshot/eval)
3. Does Tauri 2 forward --remote-debugging-port to WebView2 and expose a CDP WebSocket? (manual verify — needs running Tauri app)

SPIKE STRATEGY: prove #1+#2 with an automated test using a launched-Chromium stand-in (launch with --remote-debugging-port → connect to it separately → enumerate → attach). This mirrors exactly what attaching to the Tauri WebView2 will require. #3 is a manual config check.

chromiumoxide source is at %CARGO_HOME%\registry\src\index.crates.io-1949cf8c6b5b557f\chromiumoxide-0.7.0\src\browser.rs (read via shell — file_read is sandboxed to project root). reqwest is already a dep (Cargo.toml:47) for fetching the /json/version endpoint. The existing BrowserManager (src/browser/mod.rs) uses Browser::launch + BrowserConfig builder (.headless_mode, .user_data_dir, .args).

If #1 fails (no connect API) → pivot options: raw tungstenite WebSocket to CDP (chromiumoxide depends on async-tungstenite already), or a different crate. Report + abandon + re-plan.

- [x] 2. **Write the connect-flow spike test** — In src/browser/mod.rs `#[cfg(test)] mod tests`, add `#[tokio::test] async fn browser_connect_attaches_to_running_chromium()`. Steps inside: (a) launch a Chromium via `Browser::launch(BrowserConfig::builder().headless_mode(HeadlessMode::New).user_data_dir(tempdir).args(["--remote-debugging-port=9333".into()]).build())` — this is the 'already-running browser' stand-in for the Tauri WebView2; (b) navigate it to `data:text/html,<title>spike</title><h1 id=x>hello</h1>`; (c) fetch `http://localhost:9333/json/version` with reqwest (the lib already depends on reqwest), parse the JSON `webSocketDebuggerUrl` field (a ws://localhost:9333/.../devtools/... Clean up: drop the connected browser + the launched browser (kill the process). Use a generous timeout (30s) on the reqwest fetch + connect since Chromium startup varies. If the connect signature differs from expected, adapt to the real one from step 1.
- [x] 3. **Run the spike + confirm green** — Run `cargo test --lib browser_connect_attaches_to_running_chromium` (unpiped, read $LASTEXITCODE + the test result line). If RED: read the error carefully — if it's a fundamental API gap (connect doesn't actually attach, or target enumeration isn't exposed), report the finding and abandon the plan for a re-plan; if it's a fixable issue (wrong port, parse shape, timeout), fix and re-run.
