# Plan: Per-agent workflow + remove steer feature

## Goal
Make multi-agent truly safe for concurrent implementation by giving each agent its own workflow/plan state (instead of the shared singleton), and remove the now-unneeded steer/suggestion feature entirely (UI, IPC command, channel variant, agent-loop injection logic, and frontend store state).

## Context
Two independent changes requested together:

**1. Per-agent workflow (multi-agent readiness).** Currently all agents share one `Arc<AgentLoop>`, which shares one `Arc<tokio::sync::Mutex<Workflow>>` (src/agent/mod.rs:42, src-tauri/src/ipc/state.rs:26). The `spawn_agent` command (src-tauri/src/ipc/commands.rs:211) clones the shared AgentLoop, so every spawned agent sees the same plan. Reviews (reviews/01-architecture.md:117, reviews/03-prd.md:359, reviews/fix-plan.md:164) flag this as M5 — "multi-agent workflow is a singleton." The fix: each agent gets its own `Workflow` + its own `ToolRegistry` (since the workflow tools — CreatePlanTool/CompleteStepTool — hold an `Arc<Mutex<Workflow>>`). The provider, constitution source, memory store, sandbox, and safety rules can remain shared (they're stateless or concurrency-safe). 

Key design decision: introduce an `AgentLoopFactory` (or similar) that holds the shared, stateless deps (provider, constitution source, memory store, sandbox, safety rules, safety mode, context manager) and can build a fresh `AgentLoop` with a NEW `Workflow` + NEW `ToolRegistry` per spawn. The factory is stored in `IpcState` instead of a single `Arc<AgentLoop>`. `spawn_agent` calls `factory.build()` to get a per-agent loop. The first ("main") agent is also built via the factory at startup.

The `get_workflow_state` command currently reads the single shared workflow. With per-agent workflows, it must take an `agent_id` and read THAT agent's workflow. The AgentLoop needs a `workflow_handle()` accessor (returns `Arc<Mutex<Workflow>>`) so the IPC layer can read a specific agent's plan. The StatusBar/PlanProgress frontend fetches workflow state for the active agent.

**2. Remove steer/suggestion.** The steer feature spans:
- Frontend: InputBar.tsx (steer mode, backlog UI, Compass icon, addSteer/clearSteers), useAgentStore.ts (SteerEntry, steers[], addSteer, clearSteers, nextSteerId, STEER_LANDED_TTL_MS, suggestion_injected handler, steer transcript kind), Message.tsx (steer case + Compass import), types.ts (suggestion_injected event variant, steer TranscriptEntry), tauri.ts (sendSuggestion).
- Rust IPC: send_suggestion command (commands.rs:103), registered in main.rs:138.
- Rust channels: AgentCommand::Suggestion variant (channels.rs:31), AgentEvent::SuggestionInjected + SerializableAgentEvent::SuggestionInjected (channels.rs:96,158).
- Rust agent loop: suggestion buffering/injection in run_turn (mod.rs:231-256, 340, 423-453, 601-627), AgentTask::Suggestion handling (agent.rs:105-120).
- Rust approval/context: suggestion buffering in await_approval (approval.rs:73) and summarize_with_interrupt (context.rs:136,205-208).

After removal, while the agent is running, the input should just be disabled (or send as a normal prompt that queues — but simplest is disable send while running, keep the Stop button). The user can still interrupt via the Stop button.

Files that construct AgentLoop (must switch to factory): src-tauri/src/main.rs (build_brain + spawn), tests/workflow_integration.rs, src/agent/mod.rs tests, src/runtime/agent.rs tests. The factory must be in the library (src/) so both main.rs and tests can use it.
