# Plan: Interactive shared browser (live screencast + input passthrough)

## Goal
Make the right-panel Browser tab a live, interactive view of the single shared headless Chromium — the human can click, scroll, and type — while the agent keeps debugging the same pages via the existing browser_* tools (unchanged).

## Kind
implementation

## Context
DECISION (with user): ONE shared browser — the right-panel Browser tab becomes interactive on the SAME headless Chromium the agent debugs. The agent's browser_* tools are unchanged (same BrowserManager); we only upgrade the UI's view of the shared browser from a static pull-screenshot to a live interactive view.

ARCHITECTURE: mirror the existing console-forwarder pattern exactly (src/browser/mod.rs forward_console_events → broadcast::Sender → src-tauri/src/ipc/browser.rs spawn_console_forwarder → Tauri event → frontend/src/components/views/BrowserView.tsx listener). The frame stream replaces the pull screenshot; new input-dispatch surface lets the human click/scroll/type by coordinates (the agent keeps selector-based click/type).

KEY FILES: src/browser/mod.rs (BrowserManager + State), src-tauri/src/ipc/browser.rs (commands + forwarder), src-tauri/src/main.rs (register commands + spawn forwarder in all 3 setup branches at lines ~170/220/280), frontend/src/lib/tauri.ts + types.ts (wrappers + types), frontend/src/components/views/BrowserView.tsx (live img + input handlers).

RISK: chromiumoxide 0.7's exact screencast/input CDP type names (StartScreencastParams, ScreencastFrame event, ScreencastFrameAckParams, DispatchMouseEventParams, DispatchKeyEventParams, MouseButton, MouseEventType, KeyEventType) must be confirmed before building on them. Step 1 is a go/no-go spike; fallback is a polled-screenshot forwarder (~10fps, reuses BrowserManager::screenshot) which only needs the already-proven screenshot path.
