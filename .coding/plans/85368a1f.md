# Plan: Code-graph indexing: parallel waves + parser reuse

## Goal
Cut initial code-graph index time substantially by parallelizing the per-file work (read + hash + parse + extract across scoped worker threads in waves) with batched store round-trips (one meta SELECT, one transaction per wave with hoisted prepared statements) and per-worker parser caches (including the HTML script-block sub-parser), while keeping results deterministic (sorted application order), progress live (per-file callback on the coordinator thread), and the incremental/watcher/seed semantics unchanged.

## Context
Root cause (verified in code): the whole per-file pipeline is sequential — store round-trips (3 SELECTs), file reads, parser construction, parse, and a per-file transaction with fresh statement preparation all happen one file at a time on one thread; with WAL already enabled (schema.rs apply_pragmas — journal_mode=WAL, synchronous=NORMAL, busy timeout; .gitignore already covers codegraph.db-*), the remaining cost is round-trips + I/O waits + per-file parser setup, hence 3% CPU. DESIGN (decided, per the user's direction — parallelism + single-file speed): (1) store.rs — new stored_file_meta() batch SELECT (path → hash/mtime/has_content in ONE query, replacing 3×N round-trips) + refactor upsert_file's body into upsert_entry(tx, ...) with new upsert_files(batch) applying a whole wave in ONE transaction with prepared statements hoisted (upsert_file keeps its signature for the single-file callers). (2) extract.rs — new ParserCache (HashMap<Lang, tree_sitter::Parser>) + extract_file_with(rel, source, lang, &mut ParserCache); the cache threads through Ctx so visit_html's per-script-block JS parser (:1078) reuses it too; extract_file keeps its signature (fresh cache) for tests/small callers. (3) mod.rs — index_inner becomes WAVE-BASED PARALLEL: load the batch meta map once (one store lock), then waves of ~512 files: std::thread::scope with min(available_parallelism, 8) workers, an AtomicUsize work index over the wave, per-worker ParserCache + per-worker output Vec<(usize, WaveEntry)>, and an mpsc channel the CALLING thread drains to fire the progress callback per completed file (the &dyn Fn callback is not Send — it stays on the coordinator; the count sequence stays 1..=n monotonic); after the wave joins, outputs are placed by index (deterministic, sorted order preserved) and applied via upsert_files (one store lock per wave); mtime fast-path + hash check run in the worker against the batch map; prune_missing + rebuild_edges + the indexing-flag lifecycle + the seeded pass (trust_mtime=false) unchanged; reindex_one / reindex_stale_files / reindex_files_containing stay sequential (small-N, already WAL-cheap). REGRESSION TEST DESIGN: large_fixture_indexes_within_budget — a ~500-file mixed-language fixture in a tempdir, asserting stats.elapsed_ms < BOUND where BOUND is calibrated in step 1 from the measured sequential baseline (~50-60% of it; the parallel pass should land 4-10x under); RED today (sequential), GREEN after. Plus the #[ignore]d repo_index_timing measurement test (indexes the actual repo root into a temp-DB Store, prints elapsed_ms — run before AND after, both numbers recorded for the acceptance). Verification: cargo test large_fixture + cargo test codegraph + full cargo test --workspace green, warning-free under #![deny(warnings)] (read `test result:` lines, not the pipe exit code).

LANDED DESIGN AMENDMENT (step 3, post-implementation — the truth for crash resumption and review; the sketch above describes the intent, this describes what shipped):

Architecture (src/codegraph/mod.rs index_inner): (1) ONE stored_file_meta() SELECT up front (store.rs — path → FileMeta{content_hash, mtime, has_content}) replaces the 3 per-file SELECTs; (2) waves of 512 files: std::thread::scope, worker_count() = available_parallelism clamped to [1,8], an AtomicUsize work index over the wave's jobs; each worker owns a ParserCache (extract.rs — HashMap<Lang, Parser>, lazy per-language, deliberately not Sync) and runs extract_job() (mod.rs — the old per-file mtime-fast-path/read/hash/parse logic verbatim, minus all store access; returns Option<UpsertEntry>); per-worker outputs Vec<(job_index, UpsertEntry)>; an mpsc channel pulses the coordinator, which drains it INSIDE the scope closure so the non-Send progress callback stays on the calling thread (count monotonic 1..=total; outside-root files pulse from the coordinator); (3) after the wave joins, outputs are placed by job index (application order = the walk's sorted order — determinism) and applied via Store::upsert_files (ONE transaction per wave; on batch failure it falls back to per-file upsert_file so one bad file cannot lose the wave). reindex_one / reindex_stale_files / reindex_files_containing stay sequential (small-N callers).

extract.rs: extract_file(rel, source, lang) is a thin wrapper over extract_file_with(rel, source, lang, &mut ParserCache); Ctx carries parsers: &'a mut ParserCache so visit_html's per-script-block JS sub-parse reuses the cached JS parser (one construction per worker, not per block). store.rs: upsert_file's body became the associated fn Store::upsert_entry(&Transaction, …); upsert_file = tx + entry + commit; upsert_files = tx + loop(entry) + commit.

Deviations from the sketch (all resolved in code): Lang needed Hash added (walk.rs derive) for the HashMap key; upsert_entry is an associated fn (Self:: scope); String::from_utf8_lossy returns Cow — the source arm converts via .into_owned(); ParserCache::parser uses contains_key + get_mut (the early-return borrow blocked the later insert — NLL).

Behavioral notes: binary content-only files are no longer counted in files_reindexed (the old loop counted them via Ok(()); they never had rows written — the new count is honest). The seeded pass (trust_mtime=false), the mtime/hash fast paths, the indexing-flag lifecycle (incl. panic-unwind clear), prune_missing + rebuild_edges are unchanged.

MEASURED (this machine, debug build): 500-file fixture: 2,547–2,802 ms sequential → 1,174 ms parallel (budget 1,500 ms, green). Repo cold index: 89,235 ms / 2,913 files → 57,537 ms / 2,914 scanned / 2,670 reindexed (≈1.55×). Invariants any future change must preserve: sorted application order (determinism); the progress callback never leaves the coordinator thread; the store lock is taken once per wave (readers stay responsive between waves); workers never touch the store (the meta map is read-only shared); the wave size bounds memory for extracted results.

## Bug
Code-graph indexing has become really slow (2027-01-11 user report): project opens and re-indexes take noticeably longer than before, and CPU sits at ~3% during indexing — the pass is I/O- and round-trip-bound, not CPU-bound. The index loop (src/codegraph/mod.rs index_inner :355-487) is fully SEQUENTIAL: per file, 3 separate SQLite SELECTs (file_hash/file_mtime/has_content under the store lock), a blocking std::fs::read, a fresh tree_sitter::Parser::new + set_language per file (src/codegraph/extract.rs :188-204, plus a fresh JS parser per HTML script block at :1078), and a per-file upsert transaction that re-prepares ~6 statements each call (src/codegraph/store.rs upsert_file :196-283). Regression source: the all-language coverage work (plan c87093c1) added 10 grammars + 7 visitors + HTML script-block sub-parsing to this path.
