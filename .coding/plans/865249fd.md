# Plan: Tool-error guard: abort at 5 consecutive failing batches, nudge the model after 2

## Goal
An agent turn aborts after 5 consecutive failing tool batches instead of 3, and after the 2nd consecutive failing batch the harness adds one corrective nudge message so the model changes approach before it is cut off.

## Kind
implementation

## Context
WHY: the 3-batch cap (`MAX_RETRIES = 3`, src/agent/mod.rs:92) kills background workers that are still exploring; Mnemo's own memory records 5 occurrences in two days (workers traceUiStatus01, boundaryFix01, specGate01, traceLeadScope01 and sharedIdProjectRs01), each recovered by a manual team_resume and re-brief with the same guidance (see the HOW record 'recover a Mnemo2 worker that dies on 3 consecutive tool errors'). The user decided: raise the cap to 5 and add a nudge after 2.

CURRENT STATE (verified in the code): `MAX_RETRIES` is documented at src/agent/mod.rs:77-92: it counts tool-EXECUTION error batches, one per batch however many calls failed, resets to 0 on a batch with no failure and at least one success, ignores user denials and bad-JSON arguments (the separate MAX_BAD_JSON_RETRIES = 8). In src/agent/turn.rs, `state.tool_error_count` (field at line ~166) is updated once per batch at lines ~3059-3072 (`+= 1` on a failing batch, `= 0` on a clean successful batch); the cap check and the abort (`Aborting turn: {MAX_RETRIES} consecutive tool errors (the model may be stuck).`) are at lines ~1184-1222; the message text uses the constant so it will read 5 automatically. A harness-attributed corrective message already exists for IDENTICAL repeated failures: `pending_correction` is set at lines ~2880-2887, then after the batch (lines ~3085-3108) the harness pushes `Message::user_text(correction)` as a plain user-role tail message, with no event emitted (so no red box in the transcript and no extension of the UI doom streak), and `HARNESS_CORRECTION_PREFIX` (line ~108, `[harness tool-call correction`) is skipped by `last_user_query` (lines ~5895-5908) so a harness message never becomes the auto-recall query. The nudge must follow that same pattern.

DESIGN (decided; do not redesign): (1) src/agent/mod.rs: change `MAX_RETRIES` from 3 to 5 and update its doc comment; add `pub(crate) const TOOL_ERROR_NUDGE_AT: u32 = 2;` with a doc comment saying the harness nudges once per error streak when `tool_error_count` first reaches it. (2) src/agent/turn.rs: add `pub(crate) const HARNESS_ERROR_NUDGE_PREFIX: &str = "[harness tool-error nudge";` beside HARNESS_CORRECTION_PREFIX; collect the distinct names of tools that failed in the current batch (a small Vec<String> filled where a result with `!result.success`, not a user denial, is handled, around lines ~2880-2887); after the per-batch accounting, when the batch had a (non-denial) error and `state.tool_error_count == TOOL_ERROR_NUDGE_AT` (exactly, so it fires once per streak, not at 3, 4 and 5) and no corrective message was queued this batch (`pending_correction` was None: one corrective message per batch, the repeat-failure correction wins), push after the batch (after the correction block, so every tool result precedes it and the Anthropic tool_result ordering holds) `Message::user_text(tool_error_nudge(&failed_tools, state.tool_error_count))`. Add `fn tool_error_nudge(failed_tools: &[String], streak: u32) -> String` returning exactly: `{HARNESS_ERROR_NUDGE_PREFIX} — not the user]\n{streak} tool-call batches in a row have failed (latest: {tools}). Read the error text in the failed results, fix the cause in the arguments or choose a different approach; do not resend the same call. If the next batch fails too, change tactics completely, and if it still fails stop and report what failed instead of retrying.` where {tools} is the failed tool names joined with ', ' (at most 3, then '…'). No event is emitted for the nudge. The streak resets as before, so a new streak nudges again. (3) `last_user_query` also skips messages starting with HARNESS_ERROR_NUDGE_PREFIX (extract a tiny helper `is_harness_message(text: &str) -> bool` covering both prefixes). (4) NOT changed: `REVIEW_REPORT_MAX_FAILURES`, `MAX_BAD_JSON_RETRIES`, Laya's strike limit (`Strikes::new(3)` at src/agent/loop_impl.rs:1259 and `NUDGE_STRIKE_LIMIT = 3` at src-tauri/src/mnemo2/team.rs:1183: a stuck-worker nudge to the lead still fires at the 3rd strike, but the worker now keeps running to the 5th), the frontend's `DOOM_ERROR_STREAK = 3` (a lower bound for the doom sound).

FOLLOW-UP (a later step, added by the lead after step 1 merges): the Mnemo2 team tests in src-tauri/src/mnemo2/team.rs and a few comments (src/config/general.rs `sound_stopped_errors`, frontend/src/lib/sounds.ts, frontend/src/hooks/agentEventReducer.ts) assume 3; they are updated in that step. Step 1 must not touch them.

RISKS: many tests in src/agent/tests.rs encode the number 3 (scripted MockProvider sequences of 3 or 4 failing calls and assertions like `tool_msgs.len() == 3` at ~1491-1575, ~14340-14450, ~15112-15250). Update them to the new behaviour without weakening any assertion: derive counts from `MAX_RETRIES` where possible, otherwise script the right number of failures. The user-visible abort text changes from 3 to 5.

VERIFY (each once; stop after 3 failed fix attempts): `cargo test -p mnemo` and `cargo test -p mnemo --features browser,embeddings`; `cargo clippy -p mnemo --all-targets` judging only findings in the three files this step edits (the workspace has pre-existing clippy findings elsewhere that must not be fixed here). ## Acceptance scenarios
- A scripted agent turn whose tool calls fail 4 batches in a row and then succeeds finishes normally and is not aborted; the same turn with 5 failing batches in a row ends with the final Error 'Aborting turn: 5 consecutive tool errors (the model may be stuck).' and no trailing Finished event.
- After exactly the 2nd consecutive failing batch the provider-facing message list gains ONE user-role message starting with '[harness tool-error nudge' that names the failed tool(s), placed after that batch's tool results; the 3rd, 4th and 5th failing batches add no further nudge; no AgentEvent is emitted for it.
- A failing batch that also triggers the identical-failure correction ('[harness tool-call correction') gets only the correction, not the nudge; a clean successful batch resets the streak so a later streak nudges again at its own 2nd failure.
- A user denial or interrupt counts neither toward the cap nor toward the nudge; bad-JSON arguments are still governed only by MAX_BAD_JSON_RETRIES.
- `last_user_query` skips both harness message kinds, so a nudge never becomes the auto-recall query.
- `cargo test -p mnemo` and `cargo test -p mnemo --features browser,embeddings` pass.
