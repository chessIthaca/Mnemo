# Plan: Unified tiers: one five-tier ladder for Mnemo1 and Mnemo2, on one Tiers page

## Goal
Mnemo2's three tiers and Mnemo1's six routing lanes become one ordered ladder (trivial, routine, medium, high, escalate) with written definitions, defined once on a single Settings > Tiers page that also holds who picks the tier (Laya or the lead) and all Laya settings; Laya picks among the four non-escalate tiers, empty tiers use the tier below, and escalation works the same in both apps.

## Kind
implementation

## Context
\## Source of truth
The full design is `.coding/design/unified-tiers.md` (committed on the lead branch as 0cc97317). **Every worker reads it first**; this context only summarises it and lists the decisions the user took on 2026-11-04, which override anything older.

\## Decisions (user, 2026-11-04)
1. Five fixed tiers, cheapest first: `trivial`, `routine`, `medium`, `high`, `escalate`. Names, definitions, models and effort are editable; the set and order are not (no custom tiers).
2. The old ids `simple`, `average`, `difficult` go away with **no aliases**: tools and settings refuse them. Stored data is converted once (endpoints.toml, team.json records); old routing-log rows keep their bytes and are mapped when read (simple→trivial, average→routine, difficult→high).
3. The lowest tier (`trivial`) must have a model: it is the default model; Settings refuses to save it empty; migration fills it from `simple` or, failing that, the configured default model.
4. Empty tiers fold **down** to the nearest tier below with a model (so every tier resolves). The dispatch result and Settings say so ("medium has no model; ran on routine").
5. `escalate` is never a first pick (not offered to Laya or the kNN); only escalation paths and an explicit lead choice use it.
6. Laya picks among the four non-escalate tiers with four neutral, byte-stable labels: `trivial`→trivial, `routine`→routine, `involved`→medium, `hard`→high. Question text stays fixed in code (never built from user-edited definitions). A `min_confidence_4` gate (provisional 0.40) joins the 3/2-label gates; the eval corpus is relabelled to four labels; a labelled dataset is exported for retraining (laya 0.3.20 has no fine-tune module; the startup fine-tune hook in src-tauri/src/ipc/finetune.rs picks it up when one exists). The kNN overlay (src/agent/route_knn.rs) learns tier ids.
7. Auto mode may escalate an idle worker without asking, and tells the lead in a notice.
8. One Settings > Tiers page: at the top "Does Laya help pick the tier?" (No: the lead picks / Watch only / Suggest / Auto) driving both apps, showing Laya's readiness in place (not installed → install button; off → turn on; failed → retry/log; ready → checkpoint + kNN rows); then the ladder editor; then collapsed routing details incl. the eval; then a Laya section with its non-routing settings. **The Decisions tab is removed**; links to it point to Settings > Tiers.

## Acceptance scenarios
- After the upgrade, endpoints.toml holds five [[tier]] entries: trivial = the old simple models, routine = average, high = difficult, medium and escalate empty; config.toml has no lane fields and a config.toml.bak exists if any lane was set.
- team_dispatch with tier "medium" while medium has no model runs on routine's first model and the result says so; tier "average" is refused with the list of the five tier ids.
- Settings refuses to save a ladder whose trivial tier has no model.
- A Laya answer "involved" maps to tier medium; escalate is never offered to Laya or the kNN.
- With Laya not installed, the top of Settings > Tiers shows the Laya choices disabled with an Install button, and 'No: the lead picks' selected; the Decisions tab no longer exists.
- In auto mode, a worker whose second review round fails on the same finding is moved one tier up while idle, a reroute row with source escalation is logged, and the lead gets a notice.

## Decisions
- 2026-11-04: User suggestion (2026-11-04): fix rounds may step DOWN to a cheaper tier. Step 6 also adds an optional `tier` to team_route_fix (explicit, or `auto` = the routing question classifies the findings' text); the fix runs in the same session on that tier's model; a high-severity or shared-contract finding never steps down automatically; if the finding stays open after the stepped-down round, the next round returns to the previous tier; logged as a reroute row with source fix_downshift plus whether the finding closed. Design §6.1 (commit 54050eec).
- 2026-11-04: User request (2026-11-04): audits run on a tier. Step 3 also covers: team_audit_dispatch takes an optional `tier` (default `high`, fold-down like dispatch); the audit record stores its resolved model and tier at dispatch so team_status/mission control show them at once; an audit that has not reported yet may be switched (user in mission control, lead via team_resume + tier); a finished audit stays locked; audits are never routed by Laya/kNN and their switches are not training labels. Design §5.2 "Audits run on a tier".
- 2026-11-04: added step 9 (Integration check) because steps 3 and 4 ran in parallel
