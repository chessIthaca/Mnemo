DESIGN DECISIONS:
(a) Detection: UP-FRONT via `gh api repos/<owner>/<repo>/rulesets` (owner/repo from `gh repo view --json nameWithOwner` or parsing `git remote get-url origin`) — deterministic, side-effect-free; PLUS GH013 recovery on the direct path's push as the fallback (covers gh-missing/unauthed/no-remote). `git push --dry-run` rejected as primary (its ruleset evaluation is not guaranteed across git/GitHub versions).
(b) Two paths: ruleset present → PR flow (build the branch, push it, gh pr create, report URL, STOP); absent → the existing direct flow unchanged (acceptance c — the skill ships to other repos, mostly unprotected).
(c) NO BYPASS ever: no force-push, no admin override, no ruleset edits (the item's hard rule).
(d) PR-path build gate: run BOTH builds on the branch tip before pushing (build.yml has no PR trigger; the branch-tip build catches the historical break classes — TS-only and bin-crate compile errors are branch properties, not merge artifacts). The PR body reports build status + review verdicts.
(e) PR title/body: title = the branch's latest commit subject; body = `git log main..<branch> --oneline` + review verdicts + build status.
(f) Memory supersede on the PR path: successors recording "PR #N OPENED against main (head <branch>, tip <sha>), awaiting human review" — the MERGED-at-<sha> supersede happens after the human merges (a later session). Branch deletion likewise documented as post-human-merge.
(g) new_release step 2 gets the same ruleset-aware landing; on re-run after the human merge, main already carries the bump → continue to step 3 (tag). The tag push (step 3) is NOT blocked (branch-targeting ruleset) — verified live and documented in the skill's comments.
(h) The existing PR-already-exists case (live on wt/macos-fix: PR #3) is handled: gh pr create errors with the existing PR's URL → report it.
