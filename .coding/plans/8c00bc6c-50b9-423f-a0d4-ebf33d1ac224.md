# Plan: Fix stale recalled memories: decay strength on recall + register memory_consolidate

## Goal
Fix stale working-tier memories surfacing in recall by decaying strength on recall (the root cause), and register memory_consolidate so the agent can prune.

## Kind
implementation

## Context
Root cause (investigated + documented in semantic memory "Stale recalled memories — root cause + remediation"): recall ranking (src/memory/mod.rs:584) uses `score = sim*0.7 + strength*0.3 + keyword_boost`. The `strength` field is frozen at write time (1.0 for new memories) and NEVER decayed on recall. Working-tier memories are raw tool-output snapshots (git diffs, search results) whose content matches common FTS keywords, earning +0.2 keyword_boost. Combined with frozen-high strength×0.3, stale entries outscore relevant semantic ones. HashEmbedder makes `sim` (cosine) essentially noise, so the score is dominated by `strength*0.3 + 0.2` for keyword-matching entries.

The fix: apply `strength::decay(m.strength, now - m.last_accessed_at)` in the recall scoring loop instead of using `m.strength` directly. This is in-memory only (no persistence side effect) — old, never-re-accessed memories naturally sink in ranking. The `decay()` function already exists in src/memory/strength.rs:44 (Ebbinghaus curve, 7-day tau). The MemoryStore has a clock (`now: Arc<dyn Fn() -> i64>`) accessible in recall. The Memory struct (types.rs:55) has `last_accessed_at: i64`.

Secondary: register `memory_consolidate` in the factory (factory.rs:538 register_memory_tools only registers memory_write + memory_recall) so the agent can prune working-tier → episodic per session.
