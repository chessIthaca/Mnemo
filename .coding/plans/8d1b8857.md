# Plan: Ctrl/cmd-click must reach the OS browser: decide the link escape hatch at press time

## Goal
Make ctrl/cmd-click (and middle-click) on a chat http link reliably open the OS default browser instead of the app's built-in Browser tab, by deciding the escape hatch at press time (mousedown, where modifiers are reliable and preventDefault suppresses the engine's native new-window gesture) instead of trusting the click event's modifier flags — shared by both link surfaces (MarkdownLink's anchor and Message's web_fetch chip), with node-env regression coverage pinning the reported symptom.

## Bug

Plain click correctly opens the app tab, and both surfaces advertise the hatch in their tooltips ("...ctrl-click for your browser"). Middle-click is NOT reported broken. Symptom-implied root cause: the built-in tab is reachable only when osBrowser is falsy — verified: requestBrowserOpen has exactly one non-test caller (src/lib/openChatLink.ts:83), after the osBrowser early-return at :62-65 — so the click handler ran with the modifier flags false. The escape hatch is decided SOLELY from the click event's flags (verified: MarkdownLink.tsx:88 and Message.tsx:645 both pass `{ osBrowser: e.ctrlKey || e.metaKey }`), whereas the engine decides a ctrl+click gesture itself: verified: wry only acts on NewWindowRequested when the host registers `new_window_req_handler` (vendor/wry/src/webview2/mod.rs:766-778) and verified: 0 such registrations exist under src-tauri/. Middle-click survives because it never reads a modifier: verified: MarkdownLink.tsx:90-96 hardcodes `osBrowser: true` in onAuxClick.
