# Plan: Content index: adaptive-budget inline stale reindex (backlog 9201704f)

## Goal
Replace the content index's hard 8-file inline-repair cap with an adaptive bound, so a 9-32 file staleness (the live 2027-01-25 symptom) is repaired inline and the query re-served from the fresh index instead of falling back to the tree walk. Design: keep a COUNT CEILING as the adaptive upper bound (STALE_REINDEX_CAP 8 -> 32) and add a LATENCY BUDGET (~500 ms) inside CodeGraph::reindex_stale_files, which holds the atomic indexing-flag claim for the whole pass and stops early once the budget is spent (the caller then re-queries, still sees staleness, and walks with the note). Preserve every existing guard: the compare_exchange flag claim / IndexFlagGuard (never overlap the watcher), the out-of-root containment check, the single re-query, and the prune-vanished / content-only-upsert / source-reparse branches. Sync the docs and re-pin the boundary tests.

## Context
SYMPTOM (live 2027-01-25, backlog item 9201704f): a `search` for "AgentLoop {" returned "note: content index stale for 9 file(s) — serving tree-walk results" — NINE stale hit files, exactly one over the inline-repair cap, so the query fell back to the walk. The next search returned "reindexed 2 stale file(s) — serving fresh index results" (the watcher had caught up). The staleness came from the ordinary edit→watcher lag (file tools edited several files moments earlier); multi_edit is not special.

CURRENT MECHANISM (DECISION 2027-01-04, plan a00d05fc, commit 60f508d): src/tool/agent/search.rs `try_index` (:966) calls the private `fts_page`, which collects `stale_paths` (on-disk mtime != as-of-index mtime, vanished, or no cg_files row). Attempt 0: if `stale_paths.len() <= STALE_REINDEX_CAP` (const = 8, :348) AND `graph.reindex_stale_files(&page.stale_paths).is_ok_and(|n| n > 0)`, set `reindexed` and `continue` → ONE re-query from the fresh index → `FtsOutcome::Hits` (+ the "reindexed N stale file(s) — serving fresh index results" note). Anything else (above the cap, busy pass, failed reindex, re-edited during the retry) → `FtsOutcome::Stale { files }` → the caller walks with the "content index stale for N file(s) — serving tree-walk results" note. Call sites of the Stale arm: src/tool/agent/search.rs:1413 and src/tool/agent/search_read.rs:294; the Hits-arm disclosure: search.rs:1400 and search_read.rs:281.

FIX DIRECTION: an adaptive bound, not a hard count. Keep the count ceiling (it is what makes the boundary deterministically testable — a pure time budget cannot be pinned by tiny-file tests) but raise it 8 -> 32, and bound the pass itself by a latency budget (~500 ms) checked between files inside CodeGraph::reindex_stale_files, which already holds the atomic indexing-flag claim via compare_exchange + IndexFlagGuard for the entire pass (holding it for the whole budgeted pass is exactly why the budget goes INSIDE that method rather than as batched re-calls, which would drop and re-claim the flag between batches). A budget that runs out leaves the remainder stale; the caller's single re-query then finds staleness and walks with the note — the same graceful degradation as today.

GUARDS TO PRESERVE (all covered by existing tests): the atomic flag claim (a busy claim returns Ok(0) without touching someone else's flag) and IndexFlagGuard; the canonicalized-root containment check (a crafted out-of-root DB key is skipped, never indexed/read); the single re-query (the 2-attempt loop); the vanished���prune, source→reindex_one (with edge rebuild), text→content-only-upsert, and became-non-UTF-8→prune branches.

BLAST RADIUS of the signature change (`reindex_stale_files(&[String])` -> `(&[String], Duration)`): src/tool/agent/search.rs::try_index (real caller), src/tool/agent/codegraph.rs::execute — the graph_search staleness sweep (~line 340, inside execute::303-418) (real caller), and four tests in src/codegraph/mod.rs (reindex_stale_files_refreshes_the_given_files ~1343, _prunes_vanished_files ~1385, _busy_returns_zero_and_leaves_the_flag ~1406, _skips_out_of_root_keys ~1435).
