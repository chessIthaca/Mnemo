# Plan: Chat links open in Mnemo's Browser tab, not the OS browser

## Goal
Clicking an http(s) link in a chat message — a markdown link or the web_fetch URL chip — foregrounds the right-panel Browser tab and loads the URL in the child WebView2 instead of shelling out to the OS default browser. The OS browser stays the fallback where the Browser tab cannot exist (non-Windows: browser_webview_supported false / UNSUPPORTED_BROWSER_TAB_MSG) and for an explicit escape hatch (ctrl/cmd-click and middle-click keep the old behavior). Scheme rules are NOT widened: chat still routes only http(s) (mailto:/fragments stay non-openable text, data:/file: are not added).

WHY THE RECT DECIDES THE DESIGN. The child webview's rect is owned by frontend/src/components/views/BrowserView.tsx, which reports it via useBrowserRect and computes it at call time in openUrl() (:88-115: browserNormalizeUrl → getBoundingClientRect × devicePixelRatio → browserWebviewEnsure → browserWebviewNavigate). The chat has NO rect, and calling ensure with a guessed rect would MOVE an already-created child webview to the wrong place. So the URL must reach BrowserView, which owns the rect — mirroring the repo's proven pattern for exactly this: a STORE-HELD request consumed by the view on mount/change. frontend/src/lib/openFile.ts:5-19 states the rationale (a CustomEvent was dropped whenever the viewer was not mounted — the default, since the Files tab starts disabled). Precedent to copy: `requestFileOpen` (useAgentStore.ts:864-874) + `clearPendingFileOpen` (:874) + the consume effect in frontend/src/components/views/FileViewer.tsx:215-225 (reads `pendingFileOpen` via selector, loads, then clears). `revealRightPanelTab` (useAgentStore.ts:856-863) enables-if-disabled + selects + reveals and NEVER disables — the reveal used by the agent's browser://reveal handler (frontend/src/hooks/browserReveal.ts:23-25).

DESIGN. New frontend/src/lib/openChatLink.ts: `openChatLink(url, opts?: { osBrowser?: boolean })` — parse + accept only http(s) (mirror openExternal.ts), `opts.osBrowser` → openExternal, else `browserWebviewSupported()` (a REJECTION assumes supported, mirroring BrowserView's deliberately optimistic default :50-68) → false ⇒ openExternal (the documented non-Windows fallback), true ⇒ `requestBrowserOpen(url)` (new store action: holds `pendingBrowserUrl` + reveals/selects the Browser tab). BrowserView consumes it through the same shape as FileViewer. Consequence: on Windows a chat click never launches the OS browser; on macOS/Linux the click still opens the OS browser (the tab is a red panel there).

TEST STRATEGY (vitest is node-env — no DOM/component harness; precedent: pure helpers + store tests + `?raw` source-contract pins, e.g. MarkdownLink.test.tsx:199-203). New frontend/src/lib/openChatLink.test.ts (mock ../lib/tauri + ./openExternal) drives the real store: browser-supported → store holds the URL + Browser tab revealed + openExternal NOT called; unsupported → openExternal called, store untouched; osBrowser → openExternal, store untouched; mailto:/ftp:/relative → NO side effect at all; supported() rejection → browser path.
