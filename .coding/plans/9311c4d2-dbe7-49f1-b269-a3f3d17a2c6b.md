# Plan: Configurable accent + border + text colors in the config dialog

## Goal
Make the accent color, border color, text-primary color, and text-muted color configurable via the ConfigDialog, persisted to localStorage, applied live via CSS variables.

## Context
The color scheme is currently hardcoded in globals.css as CSS custom properties (--bg-primary, --bg-secondary, --bg-tertiary, --border-color, --text-primary, --text-muted) for dark/light themes. The accent color (cyan #22d3ee / cyan-600) is hardcoded in Tailwind utility classes throughout every component — it's not a CSS variable at all.

The ConfigDialog (frontend/src/components/layout/ConfigDialog.tsx) currently offers: theme (dark/light), font family, font size. It persists to localStorage via the store setters.

The store (frontend/src/hooks/useAgentStore.ts) holds fontFamily, fontSize, theme. It has applyFontVars() and applyTheme() helpers that write CSS custom properties / toggle the .light class.

The user wants to make these configurable in the config dialog:
1. Accent color (the cyan used for buttons, links, active states) — currently hardcoded as Tailwind cyan-* classes everywhere
2. Border color (--border-color)
3. Text primary (--text-primary)
4. Text muted (--text-muted)

Design:
- Add CSS variables: --accent-color (default #22d3ee), and the three requested are already variables (--border-color, --text-primary, --text-muted).
- Add store state: accentColor, borderColor, textPrimaryColor, textMutedColor (all strings, hex). Persist to localStorage (mh.accentColor, mh.borderColor, etc.). Defaults match the current dark theme values.
- Add applyColors() helper that writes all four CSS variables onto :root.
- The accent color is the tricky part — it's used as Tailwind cyan-* classes (bg-cyan-600, text-cyan-400, border-cyan-500, etc.) in ~30+ places across all components. Replacing every cyan-* class with a CSS variable would be a massive, error-prone change. Instead, use a CSS override approach: define --accent-color and override the specific Tailwind cyan shades used (cyan-400, cyan-500, cyan-600) via CSS custom properties that Tailwind generates. Actually, the cleanest approach: define a set of accent CSS variables (--accent, --accent-hover, --accent-text, --accent-bg) and add a small set of utility classes in globals.css (.accent-bg, .accent-text, .accent-border, .accent-hover) that use them. Then do a find-replace of the most common cyan-* patterns. But that's still a lot of churn.

Better approach for the accent: Override Tailwind's cyan color palette at runtime by setting CSS variables that Tailwind's cyan-* utilities reference. Tailwind v3 with the default config generates cyan utilities from a fixed palette — they don't use CSS variables. So we can't override them via CSS variables alone.

Simplest robust approach: Add a <style> block (or globals.css rules) that overrides the specific cyan shades used, keyed off a --accent-color variable. E.g.:
  .bg-cyan-600 { background-color: var(--accent-color) !important; }
  .hover\:bg-cyan-500:hover { background-color: var(--accent-hover) !important; }
  .text-cyan-400 { color: var(--accent-text) !important; }
  .border-cyan-500 { border-color: var(--accent-border) !important; }
  etc.
This is a small, contained set of overrides in globals.css that makes ALL existing cyan-* classes respond to the accent color variable. The user changes one color and the whole UI updates. The !important is needed because Tailwind's generated rules have equal specificity.

For border/text colors: --border-color, --text-primary, --text-muted are already CSS variables used via Tailwind's bg-bg-primary etc. (mapped in tailwind.config.ts). Wait — let me check: the components use classes like bg-bg-primary, text-slate-200, border-border. The tailwind.config.ts maps these to the CSS variables. So --border-color is already wired. --text-primary and --text-muted are used via the CSS variables in globals.css but the components use hardcoded slate-* classes for text (text-slate-200, text-slate-400, text-slate-500). So text-primary/text-muted overrides would need the same !important override approach for the specific slate shades.

Actually, let me reconsider. The user asked for border-color, text-primary, text-muted to be configurable. These are already CSS variables. The components use them in two ways:
1. Via Tailwind classes mapped in tailwind.config.ts (bg-bg-primary → var(--bg-primary), border-border → var(--border-color))
2. Via hardcoded slate-* classes (text-slate-200, text-slate-400, text-slate-500)

For #1, changing the CSS variable already works. For #2, we'd need overrides. But the user specifically asked for these three colors. Let me check tailwind.config.ts to see what's mapped.

Plan:
1. Add the four color settings to the store + applyColors() helper + localStorage persistence.
2. Add CSS overrides in globals.css for the accent color (cyan-* shades) and optionally for text colors (slate-* shades used for primary/muted text).
3. Add color pickers to the ConfigDialog.
4. Wire up App.tsx to call applyColors() on mount.
5. Test.
