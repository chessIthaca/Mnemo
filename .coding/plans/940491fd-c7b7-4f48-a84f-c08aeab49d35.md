# Plan: Scoped one-shot merge-to-main action

## Goal
Add a scoped, user-initiated, always-approval-gated "merge to main" capability: a `merge_to_main` workflow tool that performs the full merge as one atomic action (verify clean tree → record current branch → checkout main → merge --no-ff the current/feature branch → checkout back to the original branch → report), plus a UI affordance (a "Merge to main" button shown when the workflow is Complete). It must never be auto-run (always NeedsApproval regardless of safety mode), must leave the repo on the original branch even on failure, and must respect the "never commit to main" constitution rule by being an explicit user-sanctioned action rather than a standing agent capability.

## Context
Design facts (verified this session): The `git` tool (src/tool/agent/git.rs) is sandboxed to project_root and supports only status/diff/log/commit — NO checkout/merge, so merging to main is impossible today by design. WorkflowState (Planning/Executing/Complete) is derived from disk plan files (src/workflow/mod.rs: load_latest, state at :77); ToolFilter (src/tool/mod.rs:104-172) maps each state to allowed tools; the git tool is ToolCategory::Agent + SafetyLevel::NeedsApproval. Workflow tools live in src/tool/workflow/plan.rs (create_plan/update_plan/complete_step/abandon_plan), each holding Arc<Mutex<Workflow>>. The agent's available tools are built per-agent by AgentLoopFactory::build_registry (src/agent/factory.rs:253-300). SafetyMode toggle (approve-each vs auto-approve) governs the approval gate. The constitution hard rule "never commit directly to main" (agent.md) + a standing memory (never override the user's safety choice) mean a merge-to-main must be explicit, user-initiated, and always approval-gated — never auto-run.

Key design decision: implement merge-to-main as a dedicated `merge_to_main` workflow tool that is USER-INITIATED (via a UI affordance / explicit ask) and ALWAYS NeedsApproval regardless of safety mode — NOT a standing WorkflowState the agent can wander into. This preserves plan-first (the tool itself does not bypass planning; it's a single sanctioned action the user explicitly invokes after a plan completes) and the never-touch-main rule (the merge is one atomic, approval-gated, user-sanctioned action that also returns to the original branch). The tool performs: verify clean tree → record current branch → checkout main → merge --no-ff the feature branch → optionally push → checkout the original branch → report. On any failure it checks out the original branch and reports (no half-merged state).

The user's phrasing "a special state merge that is only active for that one action" maps to: the tool is only *available* in the Complete state (i.e., a plan has finished and there's something to merge) and/or gated behind an explicit UI button, and it runs as a single self-contained action. I'll implement it as a workflow tool available in Complete (and Executing) state, always approval-gated, plus surface it in the UI (a "Merge to main" button that appears when the workflow is Complete). The one-shot nature: the tool executes the whole merge in one call and returns; there's no persistent merge mode.
