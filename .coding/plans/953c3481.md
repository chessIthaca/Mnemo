# Plan: Files saved with a UTF-8 byte-order mark are not indexed

## Goal
Every .coding/ source Mnemo parses (OpenSpec specs, knowledge records, plans, reviews, backlog) reads the same with or without a leading UTF-8 byte-order mark.

## Kind
bug_fixing

## Context
ROOT CAUSE: `std::fs::read_to_string` keeps a leading U+FEFF. `Spec::parse` (src/openspec/spec.rs:88) finds the capability title with `line.text.starts_with("# ")`, so the first line `\u{feff}# Live check` never matches and parsing fails with `SpecError::MissingCapability`. `scan_openspec` (src/memory/indexer/openspec.rs) pushes that error into the report's `errors`, which nobody shows. Live repro (2026-11-17): a spec written with a BOM was not found by memory_search; after rewriting it without the BOM it was found within 6 s. Windows tools write BOMs routinely (PowerShell 5 `Set-Content`/`Out-File -Encoding utf8`, some editors), and agents on this machine run PowerShell 5.

Same class, same fix: `knowledge::parse_file` (src/memory/knowledge.rs:289) passes `contents` to `split_front_matter`. A BOM in front of the front-matter fence makes it unrecognized, so the record silently loses its title and type. `PlanFile::parse` (src/memory/plan_format.rs:217) reads the `# ` title line the same way. Reviews (src/memory/indexer/reviews.rs) and the backlog (src/memory/indexer/backlog.rs, one JSON object per line, so a BOM breaks line 1) are read with read_to_string as well.

DECISION: strip one leading U+FEFF at the top of each PARSER, as `let text = text.strip_prefix('\u{feff}').unwrap_or(text);`, not at each read site. Every caller (indexer, plan board, archive, Settings > Specs, plan_read) then gets the fix. Byte offsets inside Spec::parse are then relative to the stripped text, which is the text the function works on, so they stay consistent. Writers are unchanged: Mnemo never writes a BOM, and a re-rendered file simply loses it.

REGRESSION TEST: `parse_accepts_a_leading_byte_order_mark` in the `#[cfg(test)]` module of src/openspec/spec.rs. It parses a valid spec prefixed with "\u{feff}" and asserts Ok with the right capability and requirement. Without the fix it fails with Err(MissingCapability).

VERIFY (each alone on its line, nothing piped or appended): `cargo test -p mnemo byte_order_mark`; `cargo test --workspace`; `cargo clippy --workspace --all-targets`.

## Acceptance scenarios
- A spec.md starting with EF BB BF is indexed by index_derived with no error, and memory_search finds its requirement.
- A knowledge record, plan or review file starting with EF BB BF parses to the same title and type as the same file without it.

## Bug
A `.coding/openspec/specs/<cap>/spec.md` written by PowerShell 5's `Set-Content -Encoding utf8` starts with a UTF-8 byte-order mark (EF BB BF). Memory search never indexes it, and nothing reports why. The same file without the mark indexes at once.
