# Plan: Reuse worker checkouts so builds stay warm; trim the duplicate checks

## Goal
New workers and audits get a reused checkout folder (`.worktrees/pool-<n>`) whose `target/`, `node_modules/` and code graph survive from the previous worker, so a worker's cargo builds are incremental instead of cold; and the check battery (agent.md, CI) stops running two commands that repeat the workspace runs.

## Kind
implementation

## Context
WHY (measured 2026-11-16, knowledge record how/2026-11-16-worker-build-cost-measured-2026-11-16-fresh-chec.md): every worker gets a brand-new checkout `.worktrees/agent-<id8>` that is deleted at merge. Cargo keys the workspace's own crates (mnemo 244k lines, mnemo-app, vendored wry) by their source path, so each new checkout compiles them from scratch even when deps come from a shared target dir: `cargo test --workspace --no-run` takes 156 s cold vs 21-47 s in a reused checkout after a one-file edit; the first `cargo clippy --workspace --all-targets` adds another 126 s cold. Workers also guess at CARGO_TARGET_DIR: without it a checkout compiles every dependency too (~10 min); with the shared C:\Mnemo\target, concurrent workers block on its lock and the dir grew to 203 GB. Incremental reuse only works when the checkout keeps the SAME absolute path, so the fix is a pool of fixed folders that new worker branches are checked out into, each with its own `target/` (no CARGO_TARGET_DIR).

DECISIONS (taken):
- Pool folders are `<main_root>/.worktrees/pool-<n>`, n = 1, 2, 3 … (decimal, no leading zeros). The pool grows on demand (lowest free n is reused; a new one is `max n + 1`); no setting, no cap, no pruning in this plan.
- Branch names stay `wt/agent-<id8>` (agent_branch). Only the folder changes.
- Occupancy rule: a pool checkout is HELD while any worker record's `worktree` equals it (path compare like deletion.rs `same_checkout_path`). Releasing a checkout sets that record's `worktree` to `PathBuf::new()` (persisted; the field already allows empty — cleanup_workspace does it today; no persistence format change). A pool checkout is FREE when no record holds it AND Git lists it as a registered worktree AND its HEAD is detached AND `git status --porcelain -uall` is empty. Anything else (on a branch with no record, dirty, unregistered) is never reused; it is skipped and logged with eprintln.
- Release (merge, recovery, deletion, start-screen cleanup, rollback): never delete the folder. Check the checkout is on the worker's branch and clean, then `git -C <pool> switch --detach` (HEAD stays at the tip, files untouched) so `git branch -d` can delete the branch.
- Reuse: `git -C <pool> switch --detach <base_ref>`, then `git -C <pool> clean -ffdx -e /target/ -e node_modules/ -e /.coding/codegraph.db*` (removes the previous worker's ignored leftovers such as .coding/tmp/, .coding/logs/, *.log, but keeps the warm build caches and code graph), then `git -C <pool> switch -c <branch>`. If the switch or the clean fails, leave that pool detached, log it, and try the next free pool or create a new one.
- Legacy: records whose `worktree` is a `.worktrees/agent-<id8>` folder (dispatched before this change) keep today's code path exactly (remove the folder, trash rename, holders probe). Every place that derives `agent-<id8>` from the id must branch on the recorded path instead: pool path → pool logic, legacy path → today's logic.
- Safety guards keep their strength: a pool path is accepted only when it canonicalizes to a direct child of the canonical `<main_root>/.worktrees`, its file name matches `pool-<n>`, it is not a symlink/junction, and no OTHER record holds the same path. Never remove a pool folder; never run `git clean` or `reset --hard` on a checkout that a live record holds, except the confirmed-discard deletion path.
- Concurrency: dispatches and audits can run at once. TeamRuntime gets one `tokio::sync::Mutex<()>` (e.g. `checkout_pool_lock`) held from computing the held set through pushing the new record into `records`, so two provisions can never pick the same pool.
- Workers build in their checkout's own `target/` and never set CARGO_TARGET_DIR (agent.md says so after step 2 lands).
- `--workspace` already enables `mnemo-app`'s `mnemo2` feature through `mnemo2-app` (`cargo tree --workspace -e features -i mnemo-app`; the `-p mnemo-app --features mnemo2 --lib` run and the workspace run produce the identical `mnemo_app-<hash>.exe`), so `cargo clippy -p mnemo-app --all-targets --features mnemo2` and `cargo test -p mnemo-app --features mnemo2 --lib` only repeat the workspace commands.

VERIFY: `cargo test --workspace` and `cargo clippy --workspace --all-targets` (both warning-free under #![deny(warnings)]); the real-git tests named in each step.

## Acceptance scenarios
- After worker A is merged, the next dispatched worker B is given the same `.worktrees/pool-1` folder; files A's builds left under `target/` and `node_modules/` are still there, while A's ignored leftovers such as `.coding/tmp/` are gone, and B's HEAD is `wt/agent-<B>` at the lead tip.
- Two workers alive at the same time always have different pool checkouts, including when both are dispatched concurrently; a third concurrent worker gets a new `pool-3`.
- After a merge the worker's branch is deleted with `git branch -d`, its record's `worktree` is empty, and the pool folder still exists with a detached HEAD.
- A pool checkout with uncommitted changes, or still on a branch no record owns, is never handed to a new worker; its contents are left untouched.
- Deleting a failed worker (confirmed) discards its pool checkout's uncommitted changes, frees the pool and the next dispatch reuses it.
- Workers dispatched before the change, whose checkouts are `.worktrees/agent-<id8>`, still merge and delete exactly as before (folder removed).
- In a reused pool checkout, `cargo test --workspace --no-run` after a one-file change finishes far below the 156 s cold build measured on 2026-11-16.
