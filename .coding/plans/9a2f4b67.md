# Plan: Remote workers, phase 3: the hub places Mnemo workers on paired nodes

## Goal
A dispatched Mnemo-model worker can run on a paired Windows or Mac worker node: the hub places it there automatically, syncs its code there and back as git bundles, runs its checks and proofs on the node, and reviews and merges it from a local shadow checkout, exactly like a local worker from the lead's point of view.

## Context
WHY: roadmap phase 3 of remote workers (design and roadmap: plan c8a1a6f5; node runtime and wire protocol: plan a040713f). The user wants workers and builds off the main PC with "same plugin, same everything". Remote hosts are Windows or Mac only, never Linux. No GitHub login and no API keys on a node.

SETTLED DESIGN FOR THIS PHASE (lead decisions):
1. Hub in the app: the Mnemo2 app runs one HubServer per app instance (not per project), with HubServices backed by the app's tiers/endpoints, the project's memory store and its catalog. Remoting is OFF until the user pairs a first node: no listener before that. Pairing and host management in this phase go through ONE new lead MCP tool `team_hosts` (actions: list, pair -> shows a pairing code and the `mnemo2-node pair` command to run, revoke). The Settings → Worker hosts UI is phase 5. The research step decides whether the project travels per spawn or per pairing (a hub may serve several projects).
2. Placement is automatic (no settings knob): a Mnemo-model worker goes to a connected node that has a free slot and whose OS can run the project's checks; otherwise it runs locally exactly as today. The lead may pin a host with an optional `host` parameter on team_dispatch ("local" or a node name). Claude-agent-tier workers always stay local in this phase (remote Claude workers are phase 4). Audits follow the same placement. A node's OS suitability comes from check runs measured on that host (a project whose checks fail for environmental reasons on a host is not placed there again until a check passes there); Windows-only work (cfg(windows) policy, PowerShell-only commands) goes to Windows hosts.
3. Code sync by git bundles only: the hub sends the node a bundle of the worker's base commit (incremental against what the node already has), the node keeps one clone per project under its home plus pool checkouts `<home>/checkouts/<name>` with warm target/ caches; the worker commits on its `wt/agent-*` branch on the node; the hub pulls the branch back as a bundle into a SHADOW checkout on the hub (a normal local checkout, e.g. a hub pool folder) whenever the hub needs the code (check, review, diff, merge, team_status tip), so review.rs/merge.rs/workbench.rs git code keeps working locally. Bundles travel over the link in chunks (MAX_FRAME 16 MiB); the link's MAX_MESSAGE is not raised.
4. Checks and proofs run on the node in the worker's node checkout (warm build cache, right OS); results come back in the same report shapes check_run.rs and proving.rs use today. Lead-branch checks stay local.
5. Must-dos recorded in phase 2: (a) the node refuses session.spawn with bad_params when the pinned endpoint/model is not in its applied catalog, and the hub pushes the catalog and waits for the node's catalog_revision (node.status) before dispatching on a changed tier; (b) spend/savings rows produced on the node are mirrored to the hub so plan spend and budgets see them; (c) typed knowledge files (.coding/knowledge/*) written on the node travel with the branch bundle and are indexed on the hub after merge (prove it in the e2e).
6. `[machine]` knowledge stays with its host: a node's sessions see the node's own machine corpus, never the hub's; hub-routed recall/list for a node excludes the hub's machine-sourced rows; `memory_write scope=machine` on a node writes the node's corpus.
7. Worker shell and OS guidance matches the host: anything the hub injects into a worker's prompt (brief, kickoff, pinned task, guardrails, check commands text) that names the hub's OS or shell is built for the node's OS when the worker is remote.
8. Link loss: a remote worker whose node is disconnected shows a clear state (not Failed) and resumes when the node is back within the outage budget; past it the worker fails with a resumable error naming the host. Full link-loss UI is phase 5.
9. Test hygiene: test temp folders and caches stay inside the checkout (tempfile under target/ via .cargo/config.toml [env]), never %TEMP%. Never delete target\.tmp* while a cargo build runs.

VERIFY: the four .coding/checks.toml commands from the checkout root: `cargo test --workspace`, `cargo clippy --workspace --all-targets`, `npm test --workspace mnemo2`, `npm run check --workspace mnemo2`. The team tests in src-tauri/src/mnemo2/team/tests.rs prove local behaviour is unchanged; none may be weakened or deleted. A remote e2e (hub = the real TeamRuntime in a test, node = the mnemo2-node child process, as in src-tauri/mnemo2-app/tests/node_e2e.rs) is the proof for remote behaviour.

## Acceptance scenarios
- With a node paired and connected, a team_dispatch without a host places the Mnemo worker on the node; team_status shows the host, and the worker's model calls are served by the hub.
- The remote worker's commits reach a hub shadow checkout as a git bundle; team_check runs the project's checks on the node, team_review and team_merge then work exactly as for a local worker, and the merged commit is on the lead branch.
- With no node connected, dispatch behaves exactly as before (the existing team test suite passes unchanged).
- A node never receives an API key, and a session pinned to a model the node's catalog does not know is refused instead of silently running on the default model.
- A typed knowledge file written by a remote worker arrives on the hub with its branch and is indexed after merge; the hub's [machine] records never appear in a node session's recall.

## Spec changes

### dispatch-routing

#### ADDED Requirements

##### Requirement: Workers are placed on a host after the tier is chosen
After the tier is chosen, dispatch SHALL place a Mnemo-model worker on a connected paired worker node that has a free slot and whose operating system can run the project's checks, and SHALL run it locally otherwise. A lead-supplied host MUST win over automatic placement. Claude-agent-tier workers MUST stay local.

###### Scenario: No node connected
- **WHEN** the lead dispatches a Mnemo-model worker
- **WHEN** no worker node is connected
- **THEN** the worker runs locally exactly as before

###### Scenario: Idle suitable node
- **WHEN** the lead dispatches a Mnemo-model worker without a host
- **WHEN** a connected node has a free slot and passed the project's checks
- **THEN** the worker runs on that node
- **AND** team_status shows the node as the worker's host

###### Scenario: Lead pins local
- **WHEN** the lead dispatches with host "local"
- **THEN** the worker runs locally even when a node is idle
