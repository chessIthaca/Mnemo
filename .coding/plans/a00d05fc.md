# Plan: Content-index staleness: inline reindex instead of warn + single "note:" prefix

## Goal
When the FTS content index is stale for a small number of hit files, search/search_read reindex those files inline and serve fresh index results instead of warning + walking; the tree-walk fallback stays for large staleness (above a small-N cap) and while an index pass runs; and the doubled "note: note:" prefix on the staleness note is fixed to a single "note: ".

## Kind
implementation

## Context
Findings: try_index (src/tool/agent/search.rs:842) returns FtsOutcome::Stale{files} when any glob-passing hit file's on-disk mtime differs from the stored one (or the file vanished / lacks a cg_files row); both search.rs (line 1307) and search_read.rs (line 274) then walk with a staleness note. The doubled prefix: with_note (search.rs:928) prepends "note: " while the staleness strings (search.rs:1309, search_read.rs:276) already start with "note: ". Reindex machinery that exists: CodeGraph::index mtime fast-path (mod.rs:271), private reindex_one (mod.rs:372), Store::upsert_file (content+symbols, one transaction) / remove_file, IndexFlagGuard (mod.rs:90, clears on every exit incl. panic unwind), watcher debounce loop waits on is_indexing() before its pass (watcher.rs:202). Design decisions weighed: (1) reindex inside try_index so BOTH tools (incl. search_read's auto-read) get it; (2) STALE_REINDEX_CAP=8 — above it, or while a pass runs, walk (bounded latency; a git-checkout-scale staleness must not parse inside a tool call); (3) ONE retry — re-query after reindex, still-stale → walk; (4) success note "reindexed N stale file(s) — serving fresh index results" (a read tool mutated the index DB — disclose the side effect; alternative "silent" rejected for transparency); (5) watcher coordination: reindex_stale_files claims the indexing flag via compare_exchange(false→true) + IndexFlagGuard — the watcher waits on it, so passes never overlap; busy claim → Ok(0) → walk.
