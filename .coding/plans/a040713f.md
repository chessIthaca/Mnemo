# Plan: Remote workers, phase 2: a headless worker node that runs sessions for the hub

## Goal
The mnemo2 binary can run as a headless worker node on another Windows or Mac machine: it pairs with the hub once, dials it over one authenticated link, and runs worker sessions whose model calls, shared memory and host tools are served by the hub. Proven end to end with a hub and a node as two processes on one machine.

## Kind
implementation

## Context
WHY and SETTLED DESIGN: see plan c8a1a6f5 (phase 1) for the hub/node design and roadmap; this plan is roadmap phase 2. Summary: the hub is the user's PC (Mnemo2 app, plugin, lead, memory, tiers, review, merge). The node runs the headless engine (`mnemo::headless::Engine`) and executes worker sessions locally (tools, checkout, builds). Remote hosts are Windows or Mac only.

DECIDED FOR THIS PHASE:
- Transport: the node dials the hub (no inbound port on the node). One long-lived authenticated connection, multiplexed: request/response calls in both directions plus server-push event streams. The link runs inside Tailscale or an SSH tunnel chosen by the user; Mnemo does not build its own TLS, but every frame is authenticated by a per-node secret established at pairing (a one-time pairing code shown by the hub, exchanged for a long-lived node token stored in the node's config dir and in the hub's state dir).
- Models: the node holds no API keys. Every model call goes through a hub-proxied `LlmClient` (trait in src/provider/mod.rs:1038): the hub resolves the tier/model from its Settings → Tiers and its endpoints, streams `LlmEvent`s back, and keeps trace/cost attribution in one place. Model/reasoning changes resolve per request (see the SPEC memory "Model/reasoning changes land on the next request"), so the proxy must work per request.
- Memory: the node keeps its own local store for session-local data (session stats, tool-result archive, working memory, savings/spend rows), and routes the shared-knowledge methods of `MemoryStoreTrait` (src/memory/mod.rs:360: write, recall, recall_peek, access, batch_access, update_memory, supersede_memory, quarantine_memory, delete_memory, get_memory, list_filtered, version, primer_records) to the hub, so there is one shared memory.
- Host tools (`message_parent`, `plan_read`, later others) are answered by the hub's TeamRuntime; the node relays the call and the result.
- The node session is driven from the hub through the phase-1 `WorkerSession` trait (src-tauri/src/mnemo2/team/worker_session.rs): send, events, snapshot, set_model, close, close_and_wait travel over the link. The hub-side remote implementation of that trait belongs to phase 3; this phase provides the node side and the wire protocol it needs.
- Code: the node's project clone and pool checkouts are fed by git bundles from the hub (phase 3 implements the sync); for this phase's end-to-end test the node may be given a local clone directly.
- Test hygiene: test temp folders and caches stay inside the checkout (target/), never %TEMP%.

VERIFY: the four .coding/checks.toml commands (cargo test --workspace, cargo clippy --workspace --all-targets, npm test --workspace mnemo2, npm run check --workspace mnemo2).

## Acceptance scenarios
- A node process paired with a hub process on the same machine runs a worker session whose model calls are served by the hub and whose memory_write lands in the hub's store.
- Killing and restarting the hub mid-turn pauses the node's model call and the turn resumes when the link is back, within the bounded wait.
- The node's config dir holds no API key; the only secret it stores is its node token.
