# Plan: Remote workers, phase 2: a headless worker node that runs sessions for the hub

## Goal
The mnemo2 binary can run as a headless worker node on another Windows or Mac machine: it pairs with the hub once, dials it over one authenticated link, and runs worker sessions whose model calls, shared memory and host tools are served by the hub. Proven end to end with a hub and a node as two processes on one machine.

## Kind
implementation

## Context
WHY and SETTLED DESIGN: see plan c8a1a6f5 (phase 1) for the hub/node design and roadmap; this plan is roadmap phase 2. Summary: the hub is the user's PC (Mnemo2 app, plugin, lead, memory, tiers, review, merge). The node runs the headless engine (`mnemo::headless::Engine`) and executes worker sessions locally (tools, checkout, builds). Remote hosts are Windows or Mac only.

DECIDED FOR THIS PHASE:
- Transport: the node dials the hub (no inbound port on the node). One long-lived authenticated connection, multiplexed: request/response calls in both directions plus server-push event streams. The link runs inside Tailscale or an SSH tunnel chosen by the user; Mnemo does not build its own TLS, but every frame is authenticated by a per-node secret established at pairing (a one-time pairing code shown by the hub, exchanged for a long-lived node token stored in the node's config dir and in the hub's state dir).
- Models: the node holds no API keys. Every model call goes through a hub-proxied `LlmClient` (trait in src/provider/mod.rs:1038): the hub resolves the tier/model from its Settings → Tiers and its endpoints, streams `LlmEvent`s back, and keeps trace/cost attribution in one place. Model/reasoning changes resolve per request (see the SPEC memory "Model/reasoning changes land on the next request"), so the proxy must work per request.
- Memory: the node keeps its own local store for session-local data (session stats, tool-result archive, working memory, savings/spend rows), and routes the shared-knowledge methods of `MemoryStoreTrait` (src/memory/mod.rs:360: write, recall, recall_peek, access, batch_access, update_memory, supersede_memory, quarantine_memory, delete_memory, get_memory, list_filtered, version, primer_records) to the hub, so there is one shared memory.
- Host tools (`message_parent`, `plan_read`, later others) are answered by the hub's TeamRuntime; the node relays the call and the result.
- The node session is driven from the hub through the phase-1 `WorkerSession` trait (src-tauri/src/mnemo2/team/worker_session.rs): send, events, snapshot, set_model, close, close_and_wait travel over the link. The hub-side remote implementation of that trait belongs to phase 3; this phase provides the node side and the wire protocol it needs.
- Code: the node's project clone and pool checkouts are fed by git bundles from the hub (phase 3 implements the sync); for this phase's end-to-end test the node may be given a local clone directly.
- Test hygiene: test temp folders and caches stay inside the checkout (target/), never %TEMP%.

VERIFY: the four .coding/checks.toml commands (cargo test --workspace, cargo clippy --workspace --all-targets, npm test --workspace mnemo2, npm run check --workspace mnemo2).

## Acceptance scenarios
- A node process paired with a hub process on the same machine runs a worker session whose model calls are served by the hub and whose memory_write lands in the hub's store.
- Killing and restarting the hub mid-turn pauses the node's model call and the turn resumes when the link is back, within the bounded wait.
- The node's config dir holds no API key; the only secret it stores is its node token.

## Decisions
- 2026-11-25: no spec impact: Phase 2 adds a new node runtime and protocol; it changes no specified behaviour of existing capabilities. Spec deltas for a new remote-workers capability are added when the implementation steps are recorded.
- 2026-11-25: Phase 2 design settled from the research step (2026-11-25): WebSocket link (async-tungstenite 0.32 + hmac 0.13, both already in Cargo.lock) with HMAC-SHA256 per-frame MACs and per-direction sequence numbers, a challenge/response handshake with mutual proofs, JSON-RPC-style envelopes (req/res/item/end/cancel/note); protocol, hub server and node runtime in a new lib module src/remote/ behind feature `remote`; the node's model calls go through a `ModelTransport` seam inside the per-request resolver (never EngineBuilder::provider, which drops spawn model pins); shared memory routed to the hub, session-local memory on the node; host tools need no new mechanism (HostToolCall event + HostToolResult command over the link). Lead decisions on the open points: (1) the node gets its own CONSOLE binary `mnemo2-node` (a [[bin]] in src-tauri/mnemo2-app) instead of a `node` mode of the GUI-subsystem `mnemo2` binary, so pairing over SSH prints its result; (2) an in-test-process hub restarted behind the TCP cutter proxy is an acceptable stand-in for restarting the hub process, the node being a real child process; (3) spend/savings rows stay on the node in this phase; mirroring them to the hub is a phase-3 item; (4) MCP servers, vision tools, semantic find_code and the local classifier are not available on a node in this phase.
- 2026-11-25: added step 7 (Integration check) because steps 1 and 3 ran in parallel
- 2026-11-25: Constraints from the link audits, for steps 4 and 5. (1) Every Link::call_stream must be wrapped in the caller's timeout (RemoteLlmClient's outage budget, hub handlers' per-call timeout), because a busy answer is best effort and may be dropped. (2) Step 4 rewords src/remote/mod.rs's MAX_INFLIGHT doc: excess requests get a best-effort `busy` err, dropped when the outbound queue is full, and the requester then times out. (3) Step 5 hardening: a stream item arriving before its res is a protocol violation, not a silent drop; a panicking inbound handler must still free its inbound slot; HubServer fails a revoked node's live link when its registry file is deleted.
- 2026-11-25: From the lib-seams audit: with a transport set, build_provider_via falls back to a local HTTP build when client_for returns None. That fails closed on a node (hub.invalid base_urls, no keys) but as a RETRYABLE error. So step 4's RemoteTransport::client_for must return Some for every endpoint present in the mirrored catalog, and only None for an unknown endpoint, where the fallback also returns None. Step 4 also adds an openai request golden for ToolChoice::Function { name }.
- 2026-11-25: From the relay audit, for step 5: HubServer runs a periodic CallLog sweep (every 60 s) and also sweeps when a node's link attaches, so ended calls whose ack never arrived are dropped 600 s after their end even if that node never calls again. Step 5 may also fold memory.rs's duplicate CODE_MEMORY into remote::CODE_MEMORY. If the tight-margin relay tests (hub restart and per-outage budget) flake, widen their margins.
- 2026-11-25: From the hub/node delta audit, for step 6: (1) serve_connection selects the hub's shutdown signal alongside link.closed(), and attach refuses while shutdown is set, so an attach racing halt cannot escape the close. (2) follow_events tasks are tracked by HubServer and aborted in halt, and wait_link checks the current shutdown value before subscribing, so no task parks holding HubState after shutdown. The e2e harness exercises hub shutdown with a node attached.
- 2026-11-25: Found while fixing the catalog test: a session pinned to a model whose endpoint the node's catalog does not know silently runs on the default model. Engine::spawn only parses "endpoint/model"; resolve_turn_provider_routed falls back to the default provider when build_turn_provider returns None. On a remote node, a dispatch racing a tier change could then run on the wrong model without notice. Phase 3 must make the node refuse session.spawn with bad_params when the pinned endpoint/model is not in its applied catalog, and the hub must push the catalog and wait for catalog_revision (node.status) before dispatching on a changed tier. Local behaviour stays unchanged.
- 2026-11-25: A typed memory_write on a node (DECISION:/SPEC:/HOW: titles) writes a .coding/knowledge file into the node's checkout plus a node-local Derived row; it does not reach the hub store directly. This matches local workers, whose typed records travel with their branch, so it is intended: in phase 3 the file reaches the hub with the worker's git bundle and is indexed there after merge. Untyped shared writes route to the hub directly. The e2e therefore uses an untyped title.
