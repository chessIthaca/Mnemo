# Plan: Runtime agent tests stop flaking under full-suite load

## Goal
The agent-runtime tests in src/runtime/agent.rs wait for the turn's outcome up to their overall deadline instead of giving up after 500 ms without an event, so they pass reliably under full parallel `cargo test --lib` load.

## Kind
bug_fixing

## Context
\## Cause
The tests in `src/runtime/agent.rs` drive an `AgentTask` and read events with
`match tokio::time::timeout(Duration::from_millis(500), fanin_rx.recv()).await { ...; _ => break }`
inside a `while Instant::now() < deadline` loop (deadline 5 s). The `_ => break` arm treats any 500 ms quiet gap as "done". Under full-suite parallel load (3000+ tests), work between two events (e.g. counting tokens of the 60k-token prompt in rate_limit_429_high_fill_rate_does_not_regress_window_viability) can exceed 500 ms, so the loop exits early, `saw_finished` stays false and the test fails; run alone it passes. The same pattern sits at ~1742, ~1887, ~2211, ~2361, ~2516, ~2638, ~2769, ~2983, ~3105, ~3269.

\## Fix
- Add one small test helper in the tests module, e.g. `async fn next_event(rx: &mut mpsc::Receiver<(u64, AgentEvent)>, deadline: tokio::time::Instant) -> Option<AgentEvent>` that waits until the overall deadline (`tokio::time::timeout_at`) and returns None only on deadline or channel close.
- Replace every `timeout(500ms, recv)` + `_ => break` loop in this file with the helper, keeping each test's own exit conditions (Finished, Exited, specific events). Where a test intentionally checks that NO further event arrives (a quiet period), keep a short explicit quiet-wait for that check only and name it.
- Raise the overall deadlines from 5 s to 30 s (they are upper bounds; passing tests finish as soon as their terminal event arrives).
- Do not change production code.

\## Regression test
The regression test is `rate_limit_429_high_fill_rate_does_not_regress_window_viability` itself under load: it must pass in a full `cargo test --lib` run and in a stress run `cargo test --lib runtime::agent -- --test-threads=32` repeated 5 times. Add a unit test of the helper: a sender that waits 800 ms before sending still delivers the event (the old 500 ms idle break would have returned early).

\## Verification
- cargo clippy --all-targets -- -D warnings
- cargo test --lib (full root suite)
- for i in 1 2 3 4 5; do cargo test --lib runtime::agent -- --test-threads=32 || break; done

## Acceptance scenarios
- A full `cargo test --lib` run passes, including rate_limit_429_high_fill_rate_does_not_regress_window_viability.
- `cargo test --lib runtime::agent -- --test-threads=32` passes five times in a row.
- An event that arrives 800 ms after the previous one is still received by the test helper.
