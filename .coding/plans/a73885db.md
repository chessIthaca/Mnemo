# Plan: Research: project state owner stamp diverged from the machine owner id

## Goal
Find out why a project's .coding/mnemo2/owner stamp stopped matching this machine's owner id, which made Mnemo2 refuse to open a project it created itself, and decide what the fix should be.

## Kind
research

## Context
Symptom (2026-11-06, Windows 11, C:\mnemo, Mnemo2 2.0.0 built from origin/main 1de3e9a): the Mnemo2 instance that mnemo2-mcp started hidden at 03:23 refused to open the project, and the Claude Code plugin lost its tools. The error was: "C:\mnemo\.coding\mnemo2 was not created by Mnemo2 on this machine (it may have come with the repository), so its conversation and worker history are not loaded. Delete or rename that folder to start a fresh session here."

Facts (checked on disk): the folder holds this machine's own state (team.json 7.7 MB, lead.json 3.1 MB, preferences.json) and was stamped at 2026-11-05 13:02 when the user first opened the project in Mnemo2. The stamp file .coding/mnemo2/owner held 3d688e9fa6e04281a772a41376afdbea. The machine id file C:\Users\hessc\AppData\Roaming\com.mnemo.mnemo2\state-owner-id held b7bc55c152c542298dba58dc70877540, last written 2026-11-05 07:19:42, which is about six hours BEFORE the stamp. No other state-owner-id exists under C:\Users\hessc (searched to depth 5). A normal run reads the id file if it exists, so the 13:02 instance should have stamped b7bc..., not 3d68.... Nothing explains the second id yet.

Code anchors: src-tauri/src/mnemo2/project.rs — OWNER_FILE ("owner") and OWNER_ID_FILE ("state-owner-id") at lines 226 and 232, machine_owner_id (line 243, creates the id with create_new if the file is missing or not 32 hex chars), open_state_dir (line 315, returns the quoted error at line 344 when the stamp does not match and the folder holds any file other than .gitignore). src-tauri/src/mnemo2/ipc.rs — state_owner (line 272) resolves app_data_dir through Tauri.

Hypotheses (NOT verified, reject any that the evidence contradicts): (1) the instance started by the user and the instance started hidden by mnemo2-mcp resolve different app-data dirs (different environment, sandbox redirection, a dev versus release identifier); (2) the id file was deleted and recreated by something and its modified time was not updated; (3) machine_owner_id's 'not 32 hex chars' branch regenerated a valid id after a read failure (for example a lock or partial write); (4) the stamp was written by a different build or a test run. Do not assume the user did anything wrong.

Workaround already applied by hand: the owner file was rewritten to b7bc55c152c542298dba58dc70877540; the original is saved at C:\Users\hessc\AppData\Local\Temp\claude\58110815b969ccf5\19006164-0901-430a-a6a0-c66944e09d9e\scratchpad\owner.bak. After that the plugin server connected again.

Constraints: this is research only, so do not change production code. A restart of Mnemo2 is normal and must not delete the stamp, because the stamp exists to refuse state that arrived with a cloned repository. A fix must keep that protection. Another team is already fixing the unrelated tests/boundary.rs failure (plan 843cb384); do not touch it.

Verification: every claim in the finding comes with the command or file read that supports it; any reproduction is done in a temporary project folder and a temporary app-data dir, never in C:\mnemo.
