# Plan: Tool-call robustness: repeat-failure circuit breaker + schema injection

## Goal
Break the self-reinforcing malformed-tool-call loop (dropped required fields under long context) with three aligned layers: (1) a harness circuit breaker that detects a repeated identical tool-execution failure and injects the tool's actual parameter schema into the retry context as a fresh, harness-attributed user-role corrective message — the empirically proven loop-breaker (a fresh user turn), automatic, on attempt 2 instead of attempt 15; (2) expected-shape error enrichment so per-subcommand/mode validation errors (git commit message, file_edit line-range) carry the exact argument shape the tool expects; (3) a cheap git schema tightening (required: ["subcommand"] + a per-subcommand requirements map in the description). The full git tool split is deliberately deferred as a measured follow-up.

## Kind
implementation

## Context
Live-observed failure (user report, long flash-model session): 15 consecutive `git` commit calls missing `message` (one carried a stray restore-only `target`), plus 5 consecutive file_edit line-range errors (start_line without end_line). Root cause confirmed in code: (a) the git tool (src/tool/agent/git.rs:456-505) has a 15-value subcommand enum and NO `required` array — conditionality is prose-only, runtime-enforced ("commit requires a 'message' field", git.rs:672; merge :707, checkout :728, restore :750, branch :837/:852, no-subcommand :565); (b) file_edit.rs:497 "start_line and end_line must both be set" is prose-only (required: ["path"] exists at :1287); (c) the turn loop (src/agent/turn.rs) feeds failed results back as bare `[tool error]` tool_result messages (:1536-1543) with NO repeat detection and NO schema injection — the only teach-back is the bad-JSON path (handle_bad_json :3149, MAX_BAD_JSON_RETRIES=8), and the repetition guard (:747) clears its ring on any tool error (:740) so the re-emit loop evades it. MAX_RETRIES=3 consecutive abort (:858) stays. DESIGN REASONING: the breaker is the core fix — a harness-attributed USER-ROLE corrective message (the empirically proven pattern-breaker: the user's hint worked as a fresh user turn; error-as-tool-result repeated 15x with no effect) injected when a failure's (tool name, normalized error text) matches a prior identical one in recent history (history-scan: no new session state, works across turn boundaries = the observed loop's span, compaction ages old failures out naturally). Tool-result-content enrichment alone was REJECTED as primary (live evidence: error text repetition did not break the pattern). The full git tool SPLIT was deferred: high churn (never_auto_for + runtime-mutable core_operations config keyed by subcommand names, deliberately-built forgiving action resolution, system-prompt references, 1571-line git.rs tests) for narrow payoff — it fixes one tool while file_edit/search/spawn_agent keep the failure mode, and adds tools to a 53-tool registry; breaker covers the class; split = measured follow-up if field data persists. Model routing + compaction tuning are out of scope (config-level / already exists; the injected message is a plain user message so it compacts normally). Verification: cargo test at repo root (warning-free under deny(warnings)) + cargo test in src-tauri; no frontend TS touched. NOTE: no automated schema-parity test exists today (the 2026-08-26 HOW record's accuracy check was manual) — this plan adds real test coverage for the schema changes.

Review round 1 (report: .coding/reviews/2026-09-18-repeat-failure-circuit-breaker-review.md, FINDINGS 0 high / 3 low) — all three fixed. LOW-1: the corrective user message hijacked the auto-recall query (turn.rs built it from the last User-role message); fixed by extracting last_user_query (skips HARNESS_CORRECTION_PREFIX-prefixed messages, shared const with the correction builder) + regression test last_user_query_skips_harness_corrections. LOW-2: stale git.rs module doc ("subcommand is not required") corrected to "the schema marks `subcommand` required, but the runtime still forgives an `action`-only call". LOW-3 (README): README.md carries no git-tool section by design — it is the lean tour (README.md:46: "The feature reference (docs/FEATURES.md) has the exhaustive detail; this is the tour"); the step-5 doc deliverable lands in docs/FEATURES.md (git tool bullet) + PLAN.md (error-recovery section), so no README change is warranted — recorded here per the reviewer's suggested resolution instead of adding an off-style bullet.

## Steps
- [x] 1. **Repeat-failure detector + schema injection in the turn loop** — In src/agent/turn.rs, at the execute_tool_batch result-feedback site (~:1441-1566, where failed results are pushed as `[tool error] {capped}` tool_result messages at :1536-1543): after pushing a FAILED result, scan the provider-facing `messages` backwards over a bounded window (last ~50 messages) for a PRIOR tool_result message of the same tool name with identical normalized error text (skip the message just pushed; compare trimmed text). On a match, push ONE corrective user-role Message after the tool results, content prefixed `[harness tool-call correction — not the user]`, carrying: the tool name, the error verbatim, the tool's parameter schema looked up from the registry via Tool::schema() (src/tool/mod.rs:1018 schemas(); thread registry/schema access into run_turn via src/agent/dispatch.rs which already holds the tools), size-capped (past ~1.5 KiB degrade to property names + required list), and an explicit rewrite-the-COMPLETE-call / never-resend-unchanged instruction. Emit an AgentEvent (Error, retrying: true) so the UI shows the correction. Do NOT change MAX_RETRIES (:858) or the repetition guard (:747/:740) semantics — the breaker is additive. Two identical failures within one batch fire one injection.
- [x] 2. **Breaker tests in the agent harness suite** — In src/agent/tests.rs, model of max_retries_aborts_after_consecutive_tool_errors (:1334) and error_recovery_malformed_json (:1131): (a) stub tool failing identically twice → assert the corrective user-role message sits in `messages` after the second failure, before the next provider request, is harness-attributed and carries the schema snippet; (b) two DISTINCT errors for the same tool → no injection; (c) a failure matching an older identical failure that predates an intervening SUCCESS of another tool → injection still fires (intended: the pattern-poison stays in context); (d) 3 consecutive failures still abort the turn (MAX_RETRIES unchanged); (e) the injected message survives as a normal user message (no special compaction handling).
- [x] 3. **Expected-shape error enrichment (git + file_edit)** — src/tool/agent/git.rs: enrich each per-subcommand required-field error with the exact expected-args JSON for that subcommand plus which sibling fields are rejected there — commit (:672), merge (:707), checkout (:728), restore (:750), branch delete/create (:837/:852), and the no-subcommand error (:565).
