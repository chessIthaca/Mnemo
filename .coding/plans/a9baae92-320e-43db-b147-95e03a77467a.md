# Plan: Working-branch architecture: mergeable .coding state across Mnemo instances

## Goal
Research how .coding/ side-car state (memory DB, embeddings, code graph, plans, reviews, backlog) is stored and written today, survey merge strategies for such state, and propose an architecture for working branches shared by multiple Mnemo instances with mergeable side-car state.

## Kind
research

## Context
User wants to change branch strategy: keep "never commit to main directly" but move from branch-per-plan to long-lived working branches, with several Mnemo instances working the same code base in different directories (git worktrees). Blocker: side-car state in .coding/ must survive/merge across working copies and branch merges. Facts known: .coding/memory.db and .coding/codegraph.db are gitignored SQLite stores; .coding/plans|reviews|backlog.json|skills are tracked text; merge_to_main skill currently only supersedes branch-status memories post-merge. MemoryStore lives in src/memory/mod.rs.

## Steps
- [x] 1. **Inventory .coding/ state formats + writers** — Read src/memory/mod.rs (MemoryStore: schema, tables, embeddings), the codegraph indexer/store (search src/ for codegraph.db creation + schema), and how .coding/ paths are resolved (project root detection). Record for each artifact: format, git-tracked or ignored, writers, mutable vs append-only.
- [x] 2. **Classify merge semantics per subsystem** — For each artifact from step 1 (memories, embeddings, graph index, plans/stack.json, reviews, backlog.json, skills), determine what 'merging' means: union-append, record-level rebase (supersede chains), rebuild-from-canonical, or last-writer-wins. Note id schemes (UUIDs?) and whether concurrent writes can conflict.
- [x] 3. **Survey prior art for mergeable side-car state** — web_fetch research: git merge drivers / union drivers, git worktree workflows, CRDT append-only logs, event-sourced rebuild patterns, how tools like Dolt/Turso/LiteSync handle SQLite sync, and how other agent side-cars (e.g. Aider, Claude Code memory) treat state across branches.
- [x] 4. **Design + present architecture** — Write the proposal: branching model (working branches, worktrees, one .coding/ per worktree), canonical-vs-derived split (text records in git as truth, DBs+embeddings+graph as rebuildable caches), merge ceremony (extend merge_to_main), and open trade-offs. Present to user for decision.
