# Plan: Close web_fetch DNS-rebinding TOCTOU (pin the validated IP)

## Goal
A rebinding DNS server cannot swap the address between web_fetch's SSRF gate check and the actual connection: the gate resolves once, validates every address, and PINS the connection to the validated address (reqwest ClientBuilder::resolve — SNI/TLS/Host stay on the hostname), per hop including redirects; resolution failure is fail-closed. cargo test green; the existing SSRF/redirect tests stay green.

## Kind
bug_fixing

## Context
Verified by code read (src/tool/agent/web_fetch.rs, 882 lines): `execute` (135-247) gates via `ensure_public_http_url(&url, hostname_resolves_to_internal)` then builds ONE client (redirect::Policy::none()) and calls `fetch_following_redirects(&client, url, gate)` which re-gates every hop (the 2027-01-05 redirect fix, plan 152d8007). The gate is a predicate `fn(&str) -> bool` (true = internal); `hostname_resolves_to_internal` (406-414) resolves via blocking ToSocketAddrs and rejects if ANY address is internal; resolution FAILURE is fail-open (returns false — the request then fails at connect). reqwest is 0.12 (Cargo.toml:79, rustls-tls) — `ClientBuilder::resolve(domain, addr)` is available: it pins a domain to a specific SocketAddr while TLS SNI/cert validation and the Host header keep using the hostname (exactly the preferred fix's mechanism, no manual SNI fiddling).

Fix design (instruction 1 — pin the validated IP, per hop): (1) the gate fn type becomes `fn(&str, u16) -> Result<Option<(String, SocketAddr)>, String>` (host, port → validate → pin; None = IP-literal host, no DNS, nothing to pin). Production gate `resolve_and_gate_host`: strip brackets + parse the host as IpAddr → literal branch (validate the literal, Ok(None)); else resolve ONCE via ToSocketAddrs — resolution error or zero addresses → Err (FAIL-CLOSED, new: previously fail-open, letting an attacker serve SERVFAIL to the gate and a private address to the connector); ANY internal address → Err (current behavior preserved); else Ok(Some((host, first public addr:port))). (2) `fetch_following_redirects(start, gate)` — the client moves INTO the loop: per hop, gate → pin → `build_fetch_client(pin)` (the current builder + `.resolve(&host, addr)` when Some) → send. Per-hop clients are fine for a research fetch tool (≤6 requests, no pool reuse needed across hosts); the pin is keyed to that hop's host so a redirect to another host gets its own validated pin. (3) `execute` drops its pre-flight gate call + client build (the loop gates `start` — self-contained by design, already documented). (4) The "Known limitation" TOCTOU comment (171-177) is replaced by the fix description; the module doc updated. (5) The internal-address error message is factored into a helper (returned from two branches now).

Tests: the 5 redirect tests + the gate test update to the new signatures (stubs: `|_, _| Ok(None)` = public/no-pin — reqwest resolves normally so the 127.0.0.1 stub server stays reachable; `|_, _| Err(...)` = internal; `loopback_exempt_gate` reshaped to delegate to `resolve_and_gate_host` for non-loopback hosts). NEW regression `connection_uses_the_gate_validated_address`: URL host `rebind.invalid.` (RFC 2606-reserved TLD, trailing dot = no search-suffix rewriting — deterministic NXDOMAIN) with the gate stub PINNING it to the local stub server → the fetch SUCCEEDS, proving the connection used the gate's validated address rather than a fresh resolution (today it fails with a DNS error — the red state). NEW `resolve_and_gate_host` unit tests: internal literal → Err(SSRF), public literal → Ok(None), unresolvable host → Err (fail-closed). The acceptance's live rebinding scenario (attacker DNS) is not reproducible in unit tests — the pin test proves the mechanism (the connection cannot deviate from the gate's answer).

## Bug
web_fetch's SSRF gate validates the resolved IP (rejecting private ranges, link-local 169.254.169.254 — commit 8957b12), but reqwest re-resolves the hostname at connect time: a rebinding DNS server can return a public IP for the gate check, then 127.0.0.1/169.254.169.254 for the actual connection — bypassing the gate (time-of-check to time-of-use). The gap is documented as a known limitation in src/tool/agent/web_fetch.rs (lines 171-177): "the hostname is resolved once per gate check, then again by reqwest when it connects". Root cause: resolve-then-connect — the gate runs on one DNS answer, the connection uses another.
