# Plan: IPC event volume and blocking host calls: batched streamed deltas, notifications off the forwarder, no blocking IO on the runtime

## Goal
Streamed token deltas reach the window in batches (at most one emit per stream per ~16 ms) instead of one IPC event per chunk, desktop notifications never stall event forwarding, and the board snapshot, project open and memory read paths no longer run blocking file or git work on a tokio worker.

## Kind
implementation

## Context
WHY. The 2026-11-07 Mnemo2 performance review found (PERF-3) that every per-chunk `TextDelta`, `ReasoningDelta` and `ToolCallArgDelta` of the lead and of every worker becomes its own `app.emit` (JSON serialization plus a webview IPC crossing per chunk). Mnemo1 batched these with a `DeltaBatcher` (src-tauri/src/ipc/events.rs, ~line 170: buckets per agent and kind, flushed on a structural event, a 16 ms timer or a 64 KiB cap); it did not make the Mnemo2 port. Mnemo1's file is in the Mnemo1-binary-only `ipc` module tree, which the mnemo2 library code cannot import (the `ipc` tree is declared only in src-tauri/src/main.rs), so Mnemo2 gets its own batcher; read Mnemo1's as a reference only. The team forwarder in src-tauri/src/mnemo2/ipc.rs also awaits `notify_worker_event` inline after each emit, so a slow notification delays every later event and can lag the 1024-slot team broadcast (lagged events are skipped).
The review also found blocking work on async paths: `board_snapshot` (src-tauri/src/mnemo2/team.rs) calls `PlanBoard::list()` (src/app/plan_board.rs: takes the board guard, loads board.json and every plan file with std::fs) directly on the async thread and clones every worker record (PERF-5); `start_engine` (src-tauri/src/mnemo2/runtime.rs) runs `ignore_project_caches`, a synchronous `std::process::Command::new("git")` plus file reads/writes, on the async open path (PERF-11); `read_record` (src-tauri/src/mnemo2/memory_view.rs, used by the async `memory_read` command) does a blocking `std::fs::read_to_string`.

WHERE.
- Forwarders: `lead_open`-path code in src-tauri/src/mnemo2/ipc.rs that spawns `forwarder` (lead events, `LEAD_EVENT_CHANNEL`) and `team_forwarder` (team events, `TEAM_EVENT_CHANNEL`, then `notify_worker_event`); `notify_worker_event` itself in ipc.rs. Event envelopes: `LeadEvent { generation, event: SessionEvent }` (src-tauri/src/mnemo2/runtime.rs), `TeamEvent { worker_id, generation, event: SessionEvent }` (src-tauri/src/mnemo2/team.rs), `SessionEvent { agent: AgentId /* u64 */, event: SerializableAgentEvent, rates }` (src/headless/types.rs), `SerializableAgentEvent::{TextDelta { text }, ReasoningDelta { text }, ToolCallArgDelta { index, fragment }, ToolOutputDelta { tool_call_id, stream, text }, ..}` (src/runtime/channels.rs).
- Window consumers append deltas (mnemo2/src/lib/leadState.ts, workerThread.ts, teamState.ts) and only use their kind for activity phases (workerActivity.ts), so merging ADJACENT same-kind deltas of one stream is invisible to the window. Order within a stream must be preserved exactly.

DECISIONS.
- Merge only adjacent deltas of the same kind (and, for tool-call arguments, the same index) within one stream; any other event of that stream first flushes the pending delta, then passes through. This keeps per-stream order exact (unlike Mnemo1, which re-sorted buckets by kind).
- `ToolOutputDelta` is not merged (the tool already throttles its own stream), as in Mnemo1.
- Stream key: lead = (generation, agent); team = (worker_id, generation, agent).
- Flush deadline 16 ms from the first pending delta (not extended), cap 64 KiB per pending delta, flush everything when the channel closes.
- Desktop notifications are spawned as their own task only for the event kinds `notify_worker_event` acts on (Finished, final Error, ApprovalRequest, UserQuestion).

VERIFY (run in your worktree; a fresh worktree first needs `npm ci --no-audit --no-fund` then `npm run build` at the worktree root; the shell tool stops commands at 300 s, so run long cargo builds detached with Start-Process, logs under .coding/tmp/, and poll):
- `cargo test --manifest-path src-tauri/Cargo.toml --features mnemo2 --lib`
- `cargo clippy --manifest-path src-tauri/Cargo.toml --features mnemo2 --all-targets -- -D warnings -A clippy::redundant_guards -A clippy::nonminimal_bool`

## Acceptance scenarios
- While the lead or a worker streams text, the window receives merged delta events (at most one per stream about every 16 ms, or when 64 KiB accumulate) and the rendered threads read exactly as before, in the same order.
- A slow desktop notification never delays the next team event: notify_worker_event runs in its own task, only for finished, final-error, approval and question events.
- board_snapshot, project open (the git info/exclude update) and memory_read run their file and git work on the blocking pool; their results are unchanged.
- cargo test (lib), clippy with -D warnings and the boundary test pass.

## Decisions
- 2026-11-08: no spec impact: Performance-only: event payloads merge adjacent same-kind deltas the window concatenates anyway, and the board/memory/open paths return identical results. No team.rs specified behavior (dispatch routing, external lead, tiers, worker briefs) changes.
- 2026-11-08: Correction to step 1's `the_byte_cap_flushes_a_long_delta`: with the push rules (merge only while the merged text stays <= DELTA_CAP_BYTES, otherwise flush the pending delta and start a new one), 4,000-byte chunks flush at 64,000 bytes, not at 64 KiB or more. The test asserts instead: some push before the final flush returns a delta; no emitted delta's text exceeds DELTA_CAP_BYTES; and concatenating every emitted text (pushes plus the final flush_all) equals the 80,000 input bytes in order.
- 2026-11-08: added step 3 (Integration check) because steps 1 and 2 ran in parallel
- 2026-11-08: Step 1 read-back answers (2026-11-08): (1) a single delta whose text is strictly larger than DELTA_CAP_BYTES is emitted at once, whole (never split); a delta of exactly the cap pends like any other. (2) `notify_worker_event` starts with `if !wants_notification(event) { return; }` so the four kinds live in one private fn in ipc.rs. (3) The deadline test interleaves send, `yield_now`, `advance(20ms)`, `yield_now`, then asserts exactly one merged event. (4) Notification tasks are spawned detached and their handles are not stored; a notification that outlives a closed team only reads `team.worker()` (an Err on a stale team) and app state, which is harmless.
