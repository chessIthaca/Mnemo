# Plan: Use actual execution start for Mnemo2 tool timers

## Goal
Make every Mnemo2 tool-card suffix measure that call's own execution duration rather than time accumulated since the model announced the batch.

## Kind
bug_fixing

## Context
verified: src/agent/turn.rs:2139-2184 loops over tool_calls sequentially and calls execute_tool_call one at a time; streaming emits AgentEvent::ToolCallStart earlier at src/agent/turn.rs:4558-4574. verified: mnemo2/src/lib/leadState.ts:330-348 and mnemo2/src/lib/workerThread.ts:185-220 stamp startedAtMs with Date.now() when tool_call_start is reduced, so batched announcements include queue time in later calls. Add a separate ToolExecutionStart event immediately before the first execute_tool_call for each logical call, after the between-call stop gate. Do not emit it again for failure-triage retries: one card measures the whole logical call including approval/execution/retry, but excludes time queued behind earlier calls. Preserve ToolCallStart for streaming/card creation and use its timestamp only as a compatibility fallback until execution-start arrives or for old histories. Engine regression test: `sequential_tool_calls_time_from_execution_not_announcement` in src/agent/tests.rs must fail without the new event and prove first result precedes second execution-start. Frontend regression coverage must announce two calls at the same timestamp, start/finish them at distinct later timestamps, and assert independent durations in both lead and worker reducers; component coverage must show the per-call suffix rather than cumulative time. Public event enums require exhaustive serialization updates and warning-free builds. Verification: cargo test --workspace and, in mnemo2, npm test plus npm run check. Preserve all unrelated uncommitted changes.
