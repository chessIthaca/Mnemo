# Plan: Investigate + remediate stale recalled memories

## Goal
Determine the root cause of stale working-tier memories outranking relevant semantic ones in recall, and apply the best available remediation (consolidation, deprecation notes, or a recall-ranking fix).

## Kind
research

## Context
The memory_recall tool keeps surfacing stale working-tier snapshots from before `.claude/` was deleted (e.g. `tool: git` / `tool: search` entries whose bodies reference `.claude/plans/...` paths that no longer exist). There is no `memory_delete` tool visible in the tool set. The constitution's bookkeeping-tools clause mentions `memory_consolidate` alongside `memory_write`/`memory_recall` as AutoRun bookkeeping tools — need to verify whether it exists and whether it can prune stale entries. The memory store implementation lives at `src/memory/mod.rs`. This is investigation first; if it turns out source-code changes to the recall logic are needed, abandon this research plan and re-plan as implementation.

## Steps
- [x] 1. **Investigate available memory tools + store implementation** — Check whether a `memory_consolidate` tool exists (try recalling it / search the tool registry in `src/tool/`). Read `src/memory/mod.rs` to understand: (a) how recall ranking works (semantic + keyword relevance + strength), (b) why stale working-tier entries (raw tool-output snapshots) outrank relevant semantic entries — is it a strength/recency issue, or does the working tier get a fixed boost? (c) whether there's any TTL/decay/eviction for working-tier entries. Note the exact ranking formula + any tier weighting.
- [ ] 2. **Determine remediation path + apply** — Based on the investigation: if `memory_consolidate` exists and can prune/merge stale working-tier entries, run it. If no deletion/consolidation exists, determine whether writing stronger semantic-tier deprecation notes (already started with the `.claude/ deleted` note) is the only lever, and write any additional ones needed to outrank the stale entries. If the root cause is a recall-ranking bug (e.g. working-tier entries with high strength never decay), document it as a finding for a follow-up implementation plan — do NOT change source code in this research plan (abandon + re-plan as implementation if a code fix is warranted).
