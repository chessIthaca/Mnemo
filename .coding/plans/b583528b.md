# Plan: file_edit ops calls tolerate placeholder single-edit fields

## Goal
A file_edit call that carries real `ops` applies them even when the model also fills the top-level single-edit fields with filler, and models stop believing those fields are required.

## Kind
bug_fixing

## Context
Why: Mnemo2 worker graphView69 (deepseek-v4.1-flash and glm-5.3 via Ollama Cloud) failed twice with 3 consecutive tool errors. Its raw calls (recorded in `.coding/mnemo2/team.json`) sent `ops` together with top-level `old_string`/`new_string` set to JSON null, `""`, or the literal `"placeholder"`, plus `from_read: null`/`fuzzy_whitespace: null` inside op items. The model's own reasoning said "the schema's required list includes all of them", so it filled every field. The `""` and null forms pass; `"placeholder"` hits `validate_ops` in `src/tool/agent/file_edit.rs` (around lines 687-745): "ops is mutually exclusive with old_string — the anchor items carry their own old_string". `crate::tool::drop_stringified_nulls` (called in `src/agent/dispatch.rs` around line 270) already drops the literal "null" from optional properties; it does not cover other filler.

Required behaviour:
1. In ops mode (non-empty `ops`), top-level `old_string`/`new_string` that cannot be a real single edit are ignored instead of rejected: decide the rule from the code, but at minimum whitespace-only values, `"placeholder"`, and any top-level old_string/new_string pair where the other half is empty. A top-level old_string AND new_string that both look like a real edit stay an error (ambiguous intent). Likewise ignore `false`/0/null-equivalent values of use_regex/replace_all/count/lines/append when ops is given. When something is ignored, add a one-line note to the result so the model learns.
2. Find why the models think every field is required. Check how the file_edit schema reaches Ollama-hosted models (the provider request builder, any strict-mode/`required` rewriting of tool schemas, `src/provider/` and the tool schema in `file_edit.rs` around line 850). If the schema sent marks all properties required, fix it at that seam for optional fields; if not, make the `ops` and single-edit field descriptions say plainly to omit the single-edit fields when using ops. Note the finding in your report.
3. Do not change behaviour for single-edit, append or line-range modes.

Regression test: `ops_with_placeholder_top_level_old_string_applies_the_ops` in the test module of `src/tool/agent/file_edit.rs`. It calls the tool with two valid ops plus `"old_string":"placeholder","new_string":""` (and one variant with whitespace-only), and asserts both ops are applied and the result carries the ignore note. Without the fix it fails with "ops is mutually exclusive with old_string". The existing test asserting that error (around line 2873) must be updated to a genuinely ambiguous case, not deleted.

Verification: `cargo test --lib tool::agent::file_edit`, `cargo test --lib`, `cargo clippy --lib --tests -- -D warnings` (root crate, repo root). Do not start dev servers or any command that does not exit on its own.

## Acceptance scenarios
- file_edit with two valid ops plus top-level old_string "placeholder" applies both ops and says it ignored the placeholder.
- file_edit with ops plus a top-level old_string and new_string that both look like a real edit is still rejected as ambiguous.
- Single-edit, append and line-range calls behave exactly as before.
