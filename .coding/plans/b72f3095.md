# Plan: Investigate remaining build + test bottlenecks (round 2)

## Goal
Identify the biggest remaining build + test bottlenecks after the lld + line-tables-only + git-test-removal round, and produce concrete ranked recommendations for the next optimization round. Output is an analysis report, not source changes.

## Kind
research

## Context


## Steps
- [x] 1. **Measure the current cold + warm build breakdown (lib + src-tauri). Run `cargo clean` then `cargo build --lib --timings` (cold, captures per-crate compile times) and record total + the timing report path. Then `cd src-tauri; cargo build --timings` (cold) and record total. This establishes the cold-build baseline (the ~70s src-tauri pain) and the per-crate timing data needed for step 3. Also measure the warm incremental rebuild (touch src/lib.rs → cargo build --lib; touch src-tauri/src/main.rs → cd src-tauri; cargo build) to confirm the 7.2s post-optimization number holds.**
- [x] 2. **Measure the test-execution breakdown — which tests are slowest. Run `cargo test --lib -- --test-threads=1` won't help isolate; instead run `cargo test --lib` and capture per-test timings. Use `cargo test --lib -- --report-time` (or `--nocapture` with timing) to get per-test wall times, OR run `cargo test --lib -- --list` to count tests then run with `--test-threads=1` and `--report-time` to find the slowest individual tests. Identify the top 10 slowest tests by wall time. Suspects: tests that spawn subprocesses (git_ops/plan orchestration tests), tests that do heavy setup (tempfile + git init), tests that exercise embeddings/tiktoken, tests with real network (shouldn't exist but verify), tests with sleeps/timers. Record the top 10 + their categories.**
- [x] 3. **Identify the heaviest dependencies by compile time from the cold-build timing reports. Read the cargo-timings HTML reports generated in step 1 (target/cargo-timings/cargo-timing-*.html) — extract the per-crate durations and rank the top 10. Cross-reference with the dependency list (fastembed/ONNX, rusqlite/bundled C SQLite, chromiumoxide, tree-sitter+grammars, tauri, tiktoken-rs, image, reqwest, notify). For each heavy dep, note: is it always-compiled (in the lib) or behind a feature gate? Could it be feature-gated or made optional? Is there a lighter alternative? Record the top 10 with compile times + assessment.**
- [x] 4. **Assess cargo-nextest as a test-execution lever. Check if cargo-nextest is installed (`cargo nextest --version` or `where.exe cargo-nextest`). If installed, run `cargo nextest run --lib` and compare wall time to `cargo test --lib` (17.1s baseline). If not installed, note that `cargo install cargo-nextest` is the prerequisite and estimate the expected speedup (nextest runs tests in parallel by default and has lower per-test overhead; for a 1664-test suite the win is typically 1.5-2x). Also check: how many test binaries are there (cargo test --lib compiles one binary; nextest can shard across cores better). Record the measured or estimated impact.**
- [x] 5. **Synthesize findings + ranked recommendations. Compile the measurements into a ranked list of the next optimization levers by impact/effort: (a) cargo-nextest for test parallelism (if the suite is serial-bound), (b) feature-gating or trimming heavy deps (fastembed/chromiumoxide/tree-sitter) if they're a large fraction of cold compile, (c) splitting the lib test binary or marking slow tests #[ignore] with a separate slow-test runner, (d) incremental compilation tuning, (e) any per-test slowness found in step 2. Write the analysis to a memory record (HOW) with the post-round-2 baseline + recommendations, and present a concise summary to the user. No source changes (research plan).**
