# Plan: De-risk embedded child-webview browser (replace iframe)

## Goal
Confirm whether a native child WebView2 can be embedded inside the existing "main" Tauri window (positioned over the Browser tab area) to replace the iframe — so sites that refuse framing (Google, YouTube) load normally — and produce a concrete implementation design + go/no-go risk register. No source changes; this is investigation that gates the follow-up implementation plan.

## Kind
research

## Context
User wants sites that refuse to frame (X-Frame-Options / CSP frame-ancestors, e.g. Google) to load in the Browser tab. Decided approach: replace the iframe in frontend/src/components/views/BrowserView.tsx with a native child WebView2 embedded in the existing "main" window (NOT a separate window — user chose embedded). A top-level/child WebView2 is never "framed," so framing headers don't apply. All WebView2 instances in the process share the one CDP debug port (9222, debug-only, set in src-tauri/src/main.rs:42-46), so the agent's game_* tools should still attach to the child webview as a new CDP page target.

CURRENT ARCHITECTURE (read, don't assume):
- BrowserView.tsx renders an <iframe> with sandbox attrs; URL bar calls browserNormalizeUrl (IPC browser_normalize_url) then sets iframe.src.
- src/browser/mod.rs BrowserManager has TWO modes: launch-mode (headless Chromium, browser_* tools) and connect-mode (webview_* fns: webview_screenshot/eval/snapshot/navigate/click/type, game_* tools). Connect-mode attaches to http://localhost:9222 and operates on the app's main WebView2 page + its iframe (via CDP frame API). State.webview: Option<Arc<Browser>>, webview_handler: Option<JoinHandle>. webview_page() returns the first page target.
- src-tauri/tauri.conf.json: one window "main" (1200x720); CSP has frame-src 'self' http://localhost:* http://127.0.0.1:* https://* (only needed for the iframe — can be dropped if iframe goes away).
- Tauri 2 (src-tauri/Cargo.toml: tauri = "2"). Only one webview exists today (the main window's); no child-webview usage anywhere (search found only app.get_webview_window("main")).
- Prior CDP-attach spike (plan 7eaafb95, review .coding/reviews/2026-11-22-cdp-attach-spike-review.md) PROVED: Browser::connect works, the main WebView2 exposes CDP on 9222, target enumeration works. A child webview would be an ADDITIONAL target on the same port — needs confirming.

KEY RISKS TO RESOLVE (go/no-go):
1. Does Tauri 2 (this version) support a CHILD webview inside an existing window on Windows/WebView2? (WebviewBuilder / window.add_webview or equivalent.) If NO → approach dead, fall back to separate-window option.
2. Z-order: a child WebView2 is a separate HWND composited by the OS — it renders ABOVE the parent's HTML. Any HTML overlay crossing the browser rect (modal, dropdown, even the URL bar if it overlaps) won't show on top. Must design layout so overlays never cross the browser rect, or document the hard limit.
3. Positioning/resize: must track the Browser tab's rect (active tab + panel layout + window resize) and reposition the child webview. Find the Tauri API (Webview::set_position/set_size) + the IPC path for React to report screen coords.
4. CDP target selection: BrowserManager.webview_page() currently grabs the FIRST target (the main app page). With a child webview there are 2+ targets — must select the child webview's target specifically (by URL/title/parent-frame), not the app page.

## Steps
- [x] 1. **Confirm Tauri 2 child-webview API surface** — Verify the pinned Tauri 2 version (src-tauri/Cargo.toml) exposes a child-webview primitive: `tauri::webview::WebviewBuilder` + `WebviewWindow::add_webview` (or `WebviewWindowBuilder` vs `WebviewBuilder` distinction). Check the Tauri 2 API: a `WebviewWindow` is a window+webview combo; a bare `Webview` can be a child of an existing window. Look in the cargo registry cache (~/.cargo/registry/src/.../tauri-2.x/) for `WebviewBuilder`, `add_webview`, `Webview::set_position`/`set_size`/`set_focus`. Record the EXACT API signatures + the call to create a child webview inside the existing "main" window from a Tauri command (needs an AppHandle/WebviewWindow handle). If the primitive is absent or Windows/WebView2-unsupported in this version → STOP, mark approach dead, recommend the separate-window fallback.
- [x] 2. **Map positioning + resize + lifecycle** — Find how to (a) create the child webview positioned over a specific screen rect, (b) move/resize it when the Browser tab's rect changes (panel resize, tab switch, window resize), (c) hide/show it when the Browser tab is inactive, (d) destroy it on app exit. Determine the IPC contract: a Tauri command the React BrowserView calls with the browser-area's screen-space bounding rect (getBoundingClientRect + window.screenX/screenY) so Rust can call Webview::set_position/set_size. Note whether Tauri emits window-resize events the Rust side can listen for to re-sync. Record exact API names.
- [x] 3. **Assess z-order + overlay constraint** — Determine from Tauri/WebView2 docs + behavior whether a child WebView2 HWND renders above the parent window's HTML on Windows, and whether ANY mechanism lets HTML render above the child webview over the same rect (it almost certainly cannot). Enumerate every HTML overlay in the app that could cross the browser rect: the URL bar (currently ABOVE the iframe — safe if the child webview starts below it), modals/dialogs, dropdown menus, tooltips, the approval/question popups, the right-panel tab bar. Design the constraint: the child webview's rect must be a strict sub-rect with no HTML overlay ever crossing it; document which existing overlays would break and how to avoid them (e.g. render overlays in a separate non-overlapping region, or accept the URL bar is the only thing above the webview).
- [x] 4. **Confirm CDP-target story for the child webview** — From the prior spike evidence (.coding/reviews/2026-11-22-cdp-attach-spike-review.md, memory 'Tauri WebView2 CDP attach confirmed working') + WebView2 behavior, confirm a child webview appears as an ADDITIONAL page target on the shared debug port 9222 (separate from the main app page). Determine how BrowserManager (src/browser/mod.rs webview_page() ~line 718) would select the CHILD webview's target specifically instead of grabbing the first target — by target URL (the navigated URL), title, or CDP target type/parent-frame-id. Identify the exact change to webview_page()/iframe_context() so game_* tools drive the child webview, not the app page. Note: with a child webview there is no iframe in the app DOM, so the current iframe_context (frames.get(1)) approach is obsolete — game_click/game_type would dispatch directly against the child webview's main frame.
- [x] 5. **Draft implementation design + go/no-go risk register** — Produce a concrete design doc (write to .coding/reviews/ via the report path is NOT available in research; instead record in the plan step result + a memory_write): (1) BrowserView.tsx becomes a URL bar + a rect-reporting placeholder div (no iframe); on mount/resize/tab-activate it IPC-reports its screen rect; on Open it IPC-navigates the child webview. (2) main.rs / a new ipc::browser_webview module creates the child webview on first Browser-tab activation, positions it, listens for rect updates + window resize, destroys on exit. (3) BrowserManager gains a child-webview CDP target mode (select the child target by URL/title); webview_navigate drives the child webview directly (no iframe.src set); game_click/game_type dispatch against the child webview's main frame (no iframe offset bug — resolves review H1). (4) tauri.conf.json: drop frame-src from both CSPs (no iframe). (5) List the go/no-go risks + the step-1 runtime spike for the follow-up implementation plan (create child webview, position it, confirm it loads google.com, confirm it appears as a CDP target the agent can screenshot).
