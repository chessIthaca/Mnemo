# Plan: Team ledger hot paths: shared transcripts, coalesced off-thread saves, per-worker transcript files, transcript-free team syncs

## Goal
Worker state changes and LLM usage reports stop rewriting and re-sending every worker's whole conversation: team.json saves are small, coalesced and off the async runtime, transcripts live in their own files, and the window's team syncs carry only transcripts it does not already hold.

## Kind
implementation

## Context
WHY. The 2026-11-07 Mnemo2 performance review (findings PERF-1, PERF-2, PERF-7) found that the team ledger dominates cost at scale: `WorkerRecord` embeds the full `transcript`, `save_workers` clones every record and `TeamPersistence::save` pretty-serializes the whole ledger with blocking std::fs on a tokio worker, and the pump saves on EVERY `Usage` and `ContextUsage` event (one per LLM request per worker), and the lead's `record_usage` saves on every lead request too. The window re-fetches `team_snapshot` (all workers with full transcripts) after every non-stream event, debounced 120 ms. Re-verification on 2026-11-08 also found that the pump calls `engine.session(..).snapshot()` on every `Usage` event just to read the model id — `AgentSession::snapshot` (src/headless/session.rs) exports the whole conversation from the agent loop each time.

WHERE (the review's line numbers predate the team.rs split; these are the current homes):
- `WorkerRecord` (field `transcript`): src-tauri/src/mnemo2/team/record.rs
- `PersistedTeam`, `TeamPersistence::{new, load, save, decode}`: src-tauri/src/mnemo2/team/persistence.rs
- `save_workers` and `pump_worker` (Usage/ContextUsage branches, the `if terminal || changed` save, the `terminal || refresh` transcript refresh task): src-tauri/src/mnemo2/team/pump.rs
- `TeamSnapshot`, `TeamRuntime` struct and its initializer in `open`, `snapshot()`, `record_usage()`, `worker()`, `board_snapshot()`, `shutdown()`: src-tauri/src/mnemo2/team.rs
- the `team_snapshot` Tauri command: src-tauri/src/mnemo2/ipc.rs
- MCP-side transcript stripping (`without_transcripts`): src-tauri/src/mnemo2/team/lead_tools.rs
- frontend: `syncTeam`/`disconnectTeam` in mnemo2/src/lib/store/team.ts, the transport in mnemo2/src/lib/teamEngine.ts, wire types in mnemo2/src/lib/teamState.ts.
- tests: src-tauri/src/mnemo2/team/tests.rs (child module of `team`, so it can touch private fields; fixtures `worker(root, id)`, `open_test_team(root, state, workers)`); messages for test transcripts: `mnemo::provider::Message::text(mnemo::provider::Role::User, "hello")`.

CONSTRAINTS.
- No behavior change visible to the user or the lead tools other than speed: the frontend still shows every worker's full thread, `team_resume` still resumes from the saved transcript, team_status output is unchanged.
- team.json written by the previous version (transcripts embedded) must load with every transcript intact and migrate on the next save. A crash may lose at most the last second of usage/context counters; status transitions (Started, Completed, Failed, NeedsYou, tool failures, model changes) are still persisted immediately.
- `save_lock` keeps serializing every ledger write; never hold the records lock across file IO.

DECISIONS ALREADY TAKEN.
- `WorkerRecord.transcript` becomes `Arc<Transcript>` (serde `rc` feature: same JSON). A transcript change always assigns a NEW Arc; nothing mutates through it. Later steps rely on `Arc::ptr_eq` as the "unchanged" test (safe because whoever compares also holds the Arc, so the allocation cannot be reused).
- Telemetry-only changes (Usage, ContextUsage, the lead's record_usage) schedule one coalesced save after 1 s (`LEDGER_FLUSH_DELAY`); everything else saves immediately as today. team.json becomes compact JSON (`serde_json::to_vec`).
- Transcripts move to `transcripts/<worker_id>.json` beside team.json, rewritten only when that worker's transcript Arc changed; team.json keeps an empty transcript placeholder per worker. On load a transcript file wins over the embedded one.
- The window learns a per-worker transcript revision (process-global counter, cached per worker with the Arc it described) and sends back the revisions it holds; the host leaves those transcripts out.
- Out of scope (deferred by the lead, see plan decisions): PERF-6 (narrowing merge_lock around worktree provisioning) and PERF-8 (lead snapshot transcript paging).

VERIFY (run in your worktree; a fresh worktree first needs `npm ci --no-audit --no-fund` then `npm run build` at the worktree root, because tauri's generate_context! needs the frontend dist; the shell tool stops commands at 300 s, so run long cargo builds detached with Start-Process, logs under .coding/tmp/, and poll):

## Acceptance scenarios
- While workers stream, usage and context-size updates rewrite team.json at most about once per second, and status changes (started, finished, failed, needs you, tool failures, model changes) are still written immediately.
- team.json no longer embeds conversations: each worker's transcript lives in transcripts/<worker_id>.json beside it and is rewritten only when that worker's transcript changes.
- A team.json written by the previous version (transcripts embedded) loads with every worker thread intact, and the next save moves the transcripts into their files.
- After restarting Mnemo2 every worker thread shows its full conversation and team_resume continues from it.
- A team_snapshot call that passes the window's known transcript revisions returns empty transcripts for unchanged workers, and the worker threads in mission control still show every message.
- cargo test (lib), clippy with -D warnings and the boundary test pass; npx vitest run and svelte-check pass.

- 2026-11-08: Correction after the independent audit (2026-11-08): the earlier statement that no production path runs a second saver is WRONG. 'Open anyway' (project::attach(root, true)) lets two live instances share a project. team.json between them stays last-writer-wins, as it always was. Transcript files therefore follow two rules. (1) A save only deletes the file of a worker this instance recorded and then removed; it never deletes by scanning. - 2026-11-08: Second audit adjudicated (2026-11-08). An empty transcript writes no new file, and a record that ran but has no conversation shows a visible `worker.error` on every load. A failed move-aside of a damaged file fails the load. A failed removal stays in `written` for retry. Accepted limits, stated in the module doc: driving the same worker from two instances means the last replaced transcript wins, and deleting a worker in one instance during another's save can leave that record with no file (flagged). The old format was worse on both, because any stale save replaced every worker's transcript. Sharing needs the user's 'Open anyway' confirmation.
