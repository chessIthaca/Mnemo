# Plan: Worker panel Plan tab: the full plan and the current specs it changes

## Goal
Every worker's detail panel gets a Plan tab that shows the whole plan the worker works from (goal, context, spec changes, acceptance scenarios, steps with the worker's own step marked) and, for each capability the plan's spec changes touch, the current OpenSpec spec folded below it.

## Kind
implementation

## Context
Why: the user looks at a worker in mission control and sees only the lead's brief. The worker actually receives far more (the whole plan, including OpenSpec `## Spec changes` and acceptance scenarios), but the panel offers no way to see it without leaving for the Plans route. The user asked: "each worker, as a tab, should show the full openspec spec/plan".

Existing pieces:
- mnemo2/src/components/WorkerDetail.svelte has tabs `let tab = $state<"review" | "thread" | "timeline">("thread")` rendered in `<nav class="detail-tabs">` (around line 221) with `{#if tab === "review"} ... {:else if tab === "thread"} ...` blocks below. `worker.planId` (string | null) and `worker.planStep` (0-based index, number | null) are on the `Worker` type (mnemo2/src/lib/types.ts).
- Plan documents: `createBoardTransport()` from mnemo2/src/lib/boardEngine.ts returns a `BoardTransport` (or null outside Tauri) whose `document(planId): Promise<string>` reads `.coding/plans/<id>.md` (Tauri command `board_plan_document`), and `onChanged(handler)` fires on board changes. `seedBoardPreview(transport)` plants a stand-in transport when there is no Tauri runtime; tests use it. PlanTab.svelte shows the pattern (loadDetails, errorText).
- mnemo2/src/lib/planDocument.ts has `splitSections` (private) and `planDetailMarkdown`; its tests are mnemo2/src/lib/planDocument.test.ts.
- Plan files render spec changes as `## Spec changes`, then one `### <capability>` heading per capability (kebab-case), then `#### ADDED|MODIFIED|REMOVED|RENAMED Requirements`, `##### Requirement: ...`, `###### Scenario: ...`.
- Current specs live at `<project>/.coding/openspec/specs/<capability>/spec.md`. src-tauri/src/mnemo2/specs_settings.rs holds the Specs page commands (`project_root(&state)`, `openspec_dir(root)`), registered in src-tauri/src/mnemo2/mod.rs (the `specs_settings::...` list near line 562). There is no command yet that returns one capability's spec text.
- `actions.openPlanDocument(planId)` (mnemo2/src/lib/store.ts) opens the Plans route on that plan.
- `<Markdown source onOpenLink={actions.openBrowser} onOpenPath={actions.openRepoPath} />` renders markdown with clickable links and repo paths.

Decisions: the tab is read-only; it re-reads the plan when the board changes (like PlanTab); it is shown only for workers with a planId; an audit worker shows its target's plan the same way (it has a planId too). The tab label is "Plan".

Verification: backend `cargo test -p mnemo-app --lib mnemo2::specs_settings` and `cargo clippy -p mnemo-app --all-targets -- -D warnings`; UI (in mnemo2/) `npx vitest run src/lib/planDocument.test.ts src/components/WorkerDetail.test.ts src/components/WorkerPlanTab.test.ts` and `npx svelte-check --threshold error`.

## Acceptance scenarios
- Opening a worker in mission control shows a Plan tab next to Thread, Review and Timeline; it shows the whole plan document including Goal, Spec changes, Acceptance scenarios and Steps, with the worker's step number in the header
- For a plan with spec changes on tier-ladder, the Plan tab lists 'Current spec: tier-ladder', and opening it shows .coding/openspec/specs/tier-ladder/spec.md
- read_capability_spec refuses names like '../x' and returns nothing for a capability without a spec
- A worker without a plan shows no Plan tab
