# Plan: Fix model switch not applied on next turn (kimi→deepseek stuck)

## Goal
Fix model switching: after the user stops the agent and switches its model (e.g. kimi → deepseek), the agent's next turn must run on the newly selected model.

## Kind
implementation

## Context
User report: "we broke the switching of models somehow. I stopped you and set it to deepseek but it you continue in kimi." — i.e. after the user stopped the agent, set the model to deepseek (per-agent model picker), and continued, the agent's NEXT TURN still ran on the OLD model (kimi).

Facts from prior exploration:
- setModel IPC (frontend/src/lib/tauri.ts:972-984): `setModel(agentId, endpointName, model, reasoningEffort)` → backend rebuilds provider "for that agent's loop only; takes effect on its next turn".
- Per-agent model overrides were shipped 2026-08-22 ("models are agent-specific, user decision 2026-08-22" — from tauri.ts doc comments).
- model_resolver has a cached provider per agent: tests mention `build_turn_provider_caches_provider_across_turns` and `set_config_invalidates_the_provider_cache`. If the per-agent set_model path only swaps the agent loop's CURRENT provider but the resolver re-builds from config each turn WITHOUT consulting the per-agent override, the next turn would re-resolve to the OLD endpoint/model (kimi) — exactly the reported symptom. The resolver test list shows: `state_override_resolves`, `executing_and_complete_states_resolve`, `skill_override_beats_subagent_and_state`, `subagent_override_beats_state_override`, `model_override...` — the OVERRIDES are state/skill/subagent overrides from config `[models]`; the per-agent runtime override may live elsewhere (an in-memory map in the factory or a per-agent field).
- The switch path to inspect: frontend model picker → setModel IPC → src-tauri ipc handler → AgentFactory / runtime per-agent provider swap; then next-turn resolution in src/model_resolver or src/agent turn provider construction (resolve_turn_provider tests exist in agent::tests: resolve_turn_provider_uses_override_when_configured / forced_model_beats_state_override).
- Also plausible: the frontend sends the WRONG agentId (active agent id vs main agent id), or a stopped agent's runtime is replaced/rebuilt at restart losing the per-agent override, or the set_model handler swaps the provider but turn.rs re-resolves the provider from scratch each turn.

The plan: first READ the full path (frontend picker → IPC → backend handler → runtime → next-turn resolution) to pin the exact break, then fix with a regression test (per constitution, every defect needs a regression test that fails without the fix).

## Steps
- [x] 1. **Diagnose the model-switch break** — Trace the per-agent model-switch path end to end. Read: (1) the frontend model picker component (search for setModel( usage in frontend/src — likely a ModelPicker in the top tab bar) to see WHICH agentId it sends; (2) src-tauri IPC set_model handler (search src-tauri/src/ipc for set_model) — what it does to the runtime (per-agent provider swap, and whether it persists the override anywhere); (3) next-turn provider resolution: src/model_resolver (build_turn_provider / resolve for an agent) + src/agent/turn.rs resolve_turn_provider + agent runtime per-agent state; (4) how the runtime stores/replaces providers per agent (runtime::agent or loop impl). Identify the exact break: does the per-agent override survive to the next turn? Is the cached provider invalidated? Is the IPC handler even reached with the right agent id? Note: the user stopped the agent BEFORE switching — check whether Stop/restart of the runtime drops the override. Write findings into the plan as a short diagnosis note (update_plan), no code changes yet.
- [x] 2. **Fix + regression test** — Implement the fix based on the diagnosis. If the per-agent override is dropped/lost between set_model and the next turn (e.g. the override lives only in the swapped provider and turn.rs re-resolves from config each turn), store the per-agent override in the runtime/agent state and make next-turn resolution prefer it. If the frontend sends the wrong agent id (e.g. active tab vs main agent), fix the picker. Keep the existing set_model IPC contract. Add a regression test that reproduces the defect: set override for agent A to endpoint X/model deepseek, simulate next-turn provider resolution, assert the resolved provider is deepseek (must fail without the fix, pass with it). Run `cargo test`.
- [x] 3. **Verify + docs** — Verify end to end: run the full matrix — `cargo test` at root, `cd src-tauri && cargo test`, `npm test` + `npm run build` in frontend/ if the frontend changed. Update docs if the behavior/contract of set_model or the model picker changed (README.md model-switch bullet, PLAN.md if it claims per-agent switching, module doc comments). Then report to the user what was wrong and that a rebuild/restart shows the fix.
