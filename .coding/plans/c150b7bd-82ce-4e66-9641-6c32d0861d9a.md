# Plan: Fix child-WebView2 CDP target selection (about:blank misclassification)

## Goal
Make the agent's game_* tools attach to the Browser tab's child WebView2. Root cause (confirmed by reading code + reproducing with game_snapshot/game_screenshot): is_app_url (src/browser/mod.rs:812) treats about:blank + chrome:// as the app's own page, so select_child_target skips a child webview that is sitting on about:blank (freshly created / navigation pending or failed) and returns None → "no page target to attach to". That same blank child HWND overlays the app (eats events) while showing nothing. Fix the misclassification, add diagnostics, update tests.

## Kind
implementation

## Context
Reproduced live: game_snapshot + game_screenshot both fail with "the child WebView2 has no page target to attach to — is the Browser tab open?". That error means Browser::connect to localhost:9222 SUCCEEDED and browser.pages() returned targets, but select_child_target found no non-app page. The child webview exists as an HWND (user reports it eats events + shows blank), so it should be a CDP target — its URL is almost certainly about:blank, which is_app_url wrongly classifies as the app page. The about:blank/chrome:// matchers were added only so launched-Chromium test stand-ins (whose default page is about:blank) resolve; in production the app page is never about:blank, and the child CAN be (pending/failed navigation). Review findings C1/C2/C3 from .coding/reviews/2026-12-child-webview-browser-review.md are already fixed in the current code (PhysicalPosition in use, is_app_url matches only port 5179, no pages.first() fallback). This is a NEW defect not in that review. iced+iced_webview is a deferred fallback (memory written); this fix is in-place in the current React/Tauri architecture.
