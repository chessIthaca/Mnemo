# Plan: LLM trace in Mnemo2: every model call in detail, redesigned

## Goal
Mnemo2 gets a full LLM trace, ported from Mnemo1's Trace view and redesigned to be friendlier: every model call by the lead and every worker, with who made it, its full context, reasoning, response, tool calls, timing phases, tokens, cache reuse and cost, plus charts and persistent logging for later analysis.

## Kind
implementation

## Context
Why: the user: "the one feature mnemo1 has that we are still missing from mnemo2 is the LLM debugging where i can trace each and every call to the LLMs, see the context, reasoning, etc in detail. That truly helps a lot in understanding cost and behavior. Also good for logging so we can make mnemo better. Can we port this over too? but also review the design with Kimi here and make it better and more user friendly. Then have Opus review it in this thread to make it consistent with the rest of the new Mnemo2."

Process (decided by the user): step 1 is a DESIGN written by a worker on Kimi (kimi-k3.1-pro); step 2 is the lead's (Claude Opus, in the user's session) review of that design for consistency with Mnemo2; only then are build steps added (plan_update add_steps) and dispatched.

Verified facts:
- verified: Mnemo1's trace UI is `frontend/src/components/views/LlmTraceView.tsx` (1281 lines: RequestRow with rowBadges for error/http_status/cancelled and a CacheBadge, UsageCard with ttft/generation/reasoning/connect/stall/tools/prep/compact/backoff phases and prefix reuse, MessageRow for each context message, TopLevelChips, RequestSection, ResponseSection, DeliveredToolCallsSection, DiffBadge/PrefixLine for prompt-prefix reuse vs the previous request, polling rules shouldStopPolling/shouldSkipRefetch, a resizable stats strip) and `frontend/src/components/views/TraceStats.tsx` (588 lines: PhaseChart and TokenChart over the request list).
- verified: the data source is `mnemo::provider::trace::LlmRequestLog` (`src/provider/trace.rs`): `LlmRequestSummary`/`LlmRequestDetail` with id, ts_ms, model, base_url, provider, http_status, usage, finish_reason, is_complete, version, ttft_ms, generation_ms, reasoning_ms, connect_ms and more; an in-memory ring with a memory budget and request-body cap (`[trace]` config); optional "Log to file" mirroring to `.coding/logs/traces.jsonl` (off by default because bodies may be sensitive); failed requests always mirrored with secrets redacted; `.coding/logs/cancels.jsonl` (always on) and `.coding/logs/traces-history.jsonl` (append-only archive with rotation).
- verified: Mnemo2 already has a basic Trace tab in the lead's side panel: `mnemo2/src/components/TraceTab.svelte` (398 lines), `mnemo2/src/lib/trace.ts`, `src-tauri/src/mnemo2/trace_view.rs` (list/detail/clear over `Engine::trace()`). Mnemo2 runs ONE engine, so the log holds the lead's and every worker's requests, but records carry NO agent/session attribution.
- verified: Mnemo2's UI conventions: top-level routes Lead · Team · Cost · Graph · Plans · Memory (`mnemo2/src/lib/types.ts` Route, `TopBar.svelte`), lead side panel tabs Browser · Diff · Plan · Files · Trace · Git, colour tokens only with a dark theme (`mnemo2/src/app.css`), type tokens `--text-meta/--text-body/--text-title/--text-page`, Inter, Markdown via `Markdown.svelte`, preview scenes in `mnemo2/src/test/previewScenes.ts` with dev-only seed seams, the Cost tab's pricing (`src-tauri/src/mnemo2/insights.rs`) for dollar figures.

Step 1 (design, Kimi) must produce `.coding/design/mnemo2-llm-trace.md` covering at least:
1. Where it lives: a full top-level "Trace" route vs. growing the side-panel tab (or both: a compact side tab plus a full page) — with a recommendation and why.
2. Attribution: how each call is tied to the lead or a specific worker (and its plan step), which kernel change that needs (e.g. an agent/session label stamped on each `LlmRequestLog` record via the provider factory or turn context), and how Mnemo1 stays unaffected.
3. The information hierarchy for one call: what is visible at a glance (who, model, purpose, tokens in/out, cache hit %, cost, duration, status) vs. one click (timing phases, context messages, reasoning, response, tool calls, prefix reuse vs the previous call of the same agent) vs. raw (request/response JSON).
4. The list: filters (agent, model, status, errors, cancelled, time range), grouping by turn or by agent, search across content, and live updates while streaming.
5. Charts: which of Mnemo1's phase and token charts to keep, change or drop, plus cost over time; how they relate to the Cost tab without duplicating it.
6. Persistence and logging for improving Mnemo: what is kept across restarts, the privacy default (bodies on disk opt-in), export (e.g. a JSONL bundle of selected calls), and size limits.
7. Friendlier than Mnemo1: plain-language labels for every metric, explanations on hover, sensible defaults, empty and error states, and what to drop from Mnemo1 as noise.
8. The proposed build steps (files, backend/frontend split, which can run in parallel) and acceptance scenarios.
The design is a document only: no production code in step 1. Keep it concrete (field names, component names, wireframe-like text sketches) and within Mnemo2's existing conventions above.

## Acceptance scenarios
- A design document exists that answers placement, attribution, the per-call information hierarchy, list filters, charts, persistence/privacy/export, friendliness, and proposes build steps.
- The lead's review decisions are recorded on the plan before any build step is dispatched.
- Running the lead and two workers concurrently, every trace row and export line names the correct actor, worker, plan/step, turn and purpose; nothing is cross-labelled.
- For a known pricing fixture the Trace cost estimate equals the Cost tab's pricing rule; an unpriced model shows a dash, never $0.
- After restarting Mnemo2 with default settings, retained calls still list with metadata, and no prompt or response text was written to the metadata journal.
- Mnemo1's trace view still lists and inspects records, and the existing provider/trace tests pass.

## Decisions
- 2026-11-02: Lead review of .coding/design/mnemo2-llm-trace.md (2026-11-02): adopted as written except: (1) keep the kernel's failed-request body mirroring ON in Mnemo2 (redacted) — no new persist_failed_bodies option; the user wants logging to improve Mnemo and failed calls are the most valuable. (2) Mnemo2's live ring capacity is 128 (not 256): request bodies are capped per call but not in aggregate; the metadata journal covers older history. Mnemo1 keeps 32. (3) Export writes to <project>/.coding/logs/trace-exports/trace-<YYYYMMDD-HHMMSS>.jsonl (gitignored folder) and the UI shows the path with Copy and Reveal; no save-file dialog (Mnemo2 has none). (4) Add entry points: a 'Model calls' link on a worker in mission control (WorkerDetail) and the lead's side worker panel, and on a lead turn, opening the Trace route filtered to that worker/turn. (5) Open questions answered: Trace sits between Cost and Graph and all seven top-bar items stay visible; the metadata journal is on by default; history deletion uses a normal confirmation stating size and count; the five purposes are enough; cross-project analysis is out of scope. (6) Step A is review_risk high with an independent audit.
- 2026-11-02: added step 9 (Integration check) because steps 3 and 5 ran in parallel
- 2026-11-02: trace_export with scope "filtered" exports every call that matches query's filters. Step B ignores query.limit and query.cursor for export (the UI passes the list's page query, limit 200), and states the exported count in the result. The per-turn "Model calls" link on a lead turn in LeadChat is deferred: LeadEntry carries no turn_id, so a lead turn cannot name its calls yet. That needs the lead runtime to expose a turn id per lead turn first, and is a follow-up outside this plan.

## Interfaces
- 2026-11-02: Trace wire contract (frozen before parallel steps; Rust serde snake_case, TS mirror in mnemo2/src/lib/trace.ts owned by step C). Kernel (step A, src/provider/trace.rs): `TraceAttribution { actor_kind: "lead"|"worker"|"subagent"|"system", agent_id: String, session_id: String, agent_name: String, worker_id: Option<String>, plan_id: Option<String>, plan_step: Option<u32>, turn_id: Option<String>, purpose: "turn"|"compaction"|"memory_consolidation"|"routing"|"other" }`; `LlmRequestSummary` and detail gain `run_id: String` and `attribution: Option<TraceAttribution>` (additive; Mnemo1 ignores them). Mnemo2 view (step B, src-tauri/src/mnemo2/trace_view.rs): `TraceRow = LlmRequestSummary + { cost_micros: Option<u64>, priced: bool, retained: bool /* metadata-only from the journal */ }`; `TraceListQuery { agent: Option<String> /* "lead" | worker_id | agent_id | "unattributed" */, model: Option<String>, status: Option<"complete"|"in_progress"|"failed"|"cancelled"|"guard_cut">, purpose: Option<String>, from_ms: Option<u64>, to_ms: Option<u64>, turn_id: Option<String>, search: Option<String>, search_scope: Option<"all"|"request"|"response"|"reasoning"|"tools"|"metadata">, cursor: Option<String>, limit: u32 /* <=200 */ }`; `TraceListPage { rows: Vec<TraceRow>, total: u64, unpriced: u64, has_more: bool, next_cursor: Option<String>, capped: bool }`. Commands: `trace_list(query) -> TraceListPage`; `trace_detail(run_id, id) -> Option<LlmRequestDetail + {cost_micros, priced}>`; `trace_settings() -> { log_bodies: bool, ring_capacity: u32, journal_bytes: u64, history_bytes: u64 }`; `trace_set_log_bodies(on: bool)`; `trace_clear_live()`; `trace_delete_history() -> { deleted_files: u32, bytes: u64 }`; `trace_export({ scope: "call"|"selected"|"filtered", keys: Option<Vec<String>> /* "run_id:id" */, query: Option<TraceListQuery> }) -> { path: String, count: u32, includes_bodies: bool }`. The existing `trace_list_requests`/`trace_detail`/`trace_clear` stay until step E switches the side tab. Charts (step D, mnemo2/src/lib/traceCharts.ts) consume `TraceRow[]` only.
