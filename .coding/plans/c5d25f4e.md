# Plan: Mnemo2 advertises on-screen browser_* tools it can never connect

## Goal
Mnemo2 (every agent built through the headless engine) never advertises the on-screen `browser_*` tools, whatever `enable_browser_inspection` says. Mnemo1's behaviour and the `offscreen_browser_*` tools are unchanged.

## Kind
bug_fixing

## Context
ROOT CAUSE (lead-verified by reading the code, 2026-11-11). The on-screen gate is shared wiring that runs for both apps:
- src/host/brain.rs ~1011: in a release build with the flag on, `browser.set_webview_enabled(true)` turns on the WebView2 CDP attach.
- src/host/brain.rs ~1289: `factory.set_browser_inspection(config.general.general.enable_browser_inspection)` seeds the shared AtomicBool that `Tool::available()` of the six on-screen tools reads (src/tool/browser/mod.rs `Ctx.inspection`, ~33; tool impls ~872-1100).
- Mnemo2 builds every agent through the headless engine. src/headless/engine.rs calls `wire_brain(...)` at ~871 and ~1081.
- `Setup::patch_settings` (src/headless/setup.rs ~597) re-mirrors the flag into the live factory on every settings save.
So the user's `enable_browser_inspection = true` (set for Mnemo1) advertises the tools in Mnemo2. Mnemo1 builds through src/host/brain.rs ~251 (a non-headless caller) and src-tauri/src/ipc/settings.rs, which have a real WebView2 Browser tab with CDP when opted in.

FIX DIRECTION:
- The headless engine is the host without an on-screen WebView2. It must hold the on-screen gate off on both paths: at engine start (both wire_brain call sites) and on every `Setup::patch_settings`.
- Prefer an explicit input over a post-hoc override. For example, a `wire_brain` parameter or brain option such as `on_screen_browser: bool` that the Mnemo1 caller sets from config and the headless engine sets to false. Then neither `set_webview_enabled(true)` nor `set_browser_inspection(true)` happens on the headless path. setup.rs ~597 then stops mirroring the flag.
- If threading a parameter through `wire_brain` touches too many call sites, a headless-only override right after each `wire_brain` call is acceptable, PROVIDED setup.rs ~597 is fixed too and the regression tests cover both paths.

CONSTRAINTS:
- Mnemo1 unchanged: src-tauri/src/main.rs, src-tauri/src/ipc/settings.rs and the brain.rs ~251 caller keep reading the config flag.
- `offscreen_browser_*` tools are unaffected.
- Do not remove the config key, its Settings UI in Mnemo1, or the factory's AtomicBool.
- Root-crate browser tests need `--features browser` (the feature is off by default in the root crate; mnemo2-app enables it).

VERIFY:
- `cargo test --features browser --lib headless` (and the new tests by name)
- `cargo test --features browser --lib browser`
- `cargo test -p mnemo-app --features mnemo2 --lib`
- `cargo test --workspace --no-fail-fast`. Known timing flakes: runtime::agent::tests::cancel_during_approval_exits_agent and interrupt_during_approval_stops_turn; re-run them alone if they fail.
- `cargo +1.99.1 clippy --workspace --all-targets` and `cargo +1.99.1 clippy -p mnemo-app --all-targets --features mnemo2`

## Acceptance scenarios
- A headless Engine started with a config holding `enable_browser_inspection = true` has `factory.browser_inspection_enabled() == false`, and a spawned session's advertised tool names contain no `browser_*` name (the `offscreen_browser_*` names are still present when the browser feature is on)
- After `Setup::patch_settings` saves `enable_browser_inspection = true` on a live headless engine, the gate is still off
- Mnemo1's path (brain.rs non-headless caller) still advertises `browser_*` when the flag is on and hides them when it is off: the existing factory test (~src/agent/factory.rs 3182-3240) still passes
- `cargo test --workspace --no-fail-fast` and both `cargo +1.99.1 clippy` runs exit 0

## Bug
With `[general] enable_browser_inspection = true` (the user's config), Mnemo2's lead and its workers get the six on-screen `browser_*` tools in their tools array. But Mnemo2 removes WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS at startup (src-tauri/src/mnemo2/mod.rs:584), and its Browser pane exposes no CDP endpoint, so every browser_* call can only fail. The model wastes turns on them, and each request carries ~800 tokens of tool schema for nothing.

## Decisions
- 2026-11-11: no spec impact: Hides tools that can only fail in Mnemo2; no specified capability (settings-dialog, plan-board, dispatch-routing, worker-brief, ...) describes the browser tool set.
