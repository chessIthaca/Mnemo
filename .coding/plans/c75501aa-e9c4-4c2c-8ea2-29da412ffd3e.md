# Plan: file_edit line-range mode (start_line/end_line)

## Goal
Add a line-range edit mode to file_edit: optional start_line + end_line (1-indexed, inclusive) that replaces those lines with new_string, no string matching required. Coexists with the existing old_string/new_string mode (mutually exclusive). Eliminates the whitespace-mismatch failures that are the real cause of file_edit failing.

## Context
file_edit currently uses exact substring matching (content.find(&old_string)), which fails when the model reproduces indentation/whitespace slightly wrong — the #1 real-world failure mode (line endings are already handled via normalize_line_endings, so \n is NOT the culprit). The model already sees 1-indexed line numbers from file_read (file_read.rs:131: `format!("{:>4}: {}", start + i + 1, line)`), so a line-range edit mode lets it replace lines by number with zero string matching.

Design: add optional `start_line` + `end_line` (1-indexed, inclusive) to FileEditArgs. When BOTH are present, the tool replaces those lines (by line number) with `new_string` — no old_string needed. When absent, the existing old_string/new_string path runs unchanged. The two modes are mutually exclusive: line-range mode requires start_line+end_line+new_string (old_string ignored/forbidden), string mode requires old_string+new_string. This keeps the existing API fully backward-compatible.

Line semantics: Rust's str::lines() splits on \n (dropping the terminator) and does NOT yield a trailing empty element for a trailing newline. So a file "a\nb\nc\n" has lines [a,b,c] (3 lines). start_line=2,end_line=3 → replace "b\nc" with new_string, preserving the file's line-ending style (normalize new_string to the file's LE, like the literal path does). Must handle: end_line beyond file length (clamp), start_line > end_line (error), start_line=0 or negative (error — 1-indexed), empty file (error: no lines to replace).

Implementation lives in file_edit.rs: new fn prepare_edit_lines(args, content) dispatched from prepare_edit when start_line.is_some() || end_line.is_some(). Reuses detect_line_ending + normalize_line_endings + compute_diff. The execute() path and approval_preview path both go through prepare_edit, so both get it for free.

Schema: add start_line/end_line as optional integers with descriptions noting 1-indexed inclusive + that they're an alternative to old_string. Update the tool description + the prompt.rs guidance (lines 21-23) to mention the line-range mode.

Tests: add to the existing #[cfg(test)] mod in file_edit.rs — line-range replace, end_line clamped, start>end errors, start=0 errors, empty file errors, CRLF file preserves endings, line-range + diff renders, and that old_string mode still works unchanged. Also a tokio::test end-to-end via execute().

Project: Windows 11, npm workspace at C:\myHarness. Rust tests via `cargo test`, frontend unaffected (no frontend change). This is plan 1 of 4 (line-range mode); the others (whitespace-tolerant matching, replace_in_files, batch read) follow as separate plans.

- [x] 2. **Implement prepare_edit_lines** — In `src/tool/agent/file_edit.rs`, add `fn prepare_edit_lines(args: &FileEditArgs, content: &str) -> Result<PreparedEdit>`. Validate: start_line >= 1 and end_line >= start_line (else InvalidInput). Split content into lines via `content.lines()` collecting into a Vec<&str>. If the vec is empty → NotFound 'no lines to replace'. Clamp end_line to vec.len(). Build new_content: take lines [0..start-1), push normalize_line_endings(&args.new_string, le) where le = detect_line_ending(content), then take lines [end..] joined with the file's LE. Reuse compute_diff(&args.path, content, &new_content). Return PreparedEdit. Mirror the literal path's line-ending handling (normalize new_string to the file's LE so CRLF is preserved).

Update the top description string to mention the line-range mode. Keep required as [path, old_string, new_string] for backward compat BUT note in descriptions that old_string is ignored when start_line/end_line are set.
