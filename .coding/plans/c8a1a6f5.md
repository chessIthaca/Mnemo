# Plan: Remote workers, phase 1: workers talk to their session through a WorkerSession handle

## Goal
Every place the team runtime drives a worker's live session goes through one `WorkerSession` trait object instead of the concrete engine `AgentSession` or `engine.session(id)` lookups, so a later phase can plug in a session that runs on a remote worker node. Behaviour is unchanged.

## Kind
implementation

## Context
WHY: the user wants Mnemo workers to run on another computer (Windows or Mac, never Linux) with the same plugin and the same lead flow. Settled design (2026-11-25): the user's PC stays the HUB (Mnemo2 app, plugin, Claude Code lead, plan board, memory, tiers, review, merge). A remote machine runs the same Mnemo engine headless as a WORKER NODE: the session loop, file/shell tools, pool checkouts, builds and check runs run there. Model calls and shared memory are proxied to the hub over one authenticated link the node dials (Tailscale/SSH, no inbound ports, no API keys and no GitHub login on the node). Code moves only between hub and node as git bundles; the hub keeps a shadow checkout of each remote worker branch so review/merge git code stays local. Claude-tier workers on a node are Claude Code sessions the lead starts over the desktop app's SSH sessions; Mnemo never launches `claude` itself.

ROADMAP (one board plan per phase, each planned when the previous one lands, because its specs depend on that code):
1. THIS PLAN: the WorkerSession seam (pure refactor, no behaviour change).
2. Node runtime: node mode of the mnemo2 binary, wire protocol, a hub-proxied LlmClient, a memory store that routes shared-knowledge calls to the hub, host-tool relay, pairing; end-to-end with two processes on one machine.
3. Remote workers on the hub: RemoteHost spawning sessions on a node, git-bundle sync with shadow checkouts, remote check and prove runs, OS-aware placement from per-host check results, `[machine]` memories kept to their host, worker shell guidance per host OS.
4. Remote Claude workers: dispatch answer with an SSH launch on the node, plugin on the node relaying to the hub, transcript watching on the node.
5. Settings → Worker hosts, pairing UI, host shown in team_status and Mission Control, link-loss states and resync.
