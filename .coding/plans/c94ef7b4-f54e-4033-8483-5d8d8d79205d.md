# Plan: file_edit whitespace-tolerant matching (fuzzy_whitespace)

## Goal
Add whitespace-tolerant matching to file_edit's literal mode: a fuzzy_whitespace flag that locates old_string by normalizing whitespace (collapse runs, strip trailing) for matching only, while splicing the replacement into the original content verbatim. Catches the tab-vs-space / off-by-one-space failures that are the #1 cause of file_edit failing in string-matching mode.

## Context
file_edit's literal path (file_edit.rs:208-247 prepare_edit_literal) uses raw content.find(&old_string) — byte-exact substring match. The #1 real failure mode is whitespace/indentation mismatch: the model reproduces the indentation slightly wrong (tabs vs spaces, a space off, trailing whitespace it can't see). Line endings are already handled (normalize_line_endings). The line-range mode (just shipped) avoids this entirely, but string-matching mode is still brittle for cases where the model doesn't have exact line numbers or wants a surgical in-line replacement.

Design: add a `fuzzy_whitespace: bool` field (#[serde(default)], default false) to FileEditArgs. When true, the LITERAL path (only — regex mode is already pattern-based) locates old_string via a whitespace-normalized comparison instead of byte-exact find. Specifically: define a helper `normalize_ws(s: &str) -> String` that (a) strips trailing whitespace from each line, (b) collapses runs of whitespace (spaces/tabs) within a line to a single space. Then to locate+replace: normalize both the file content and old_string, find the normalized old_string in the normalized content to get a char-range, map that range back to the ORIGINAL content's byte offsets, and splice new_string (verbatim, line-ending-normalized as today) into the original. This preserves the file's exact original whitespace outside the match (only the matched region is replaced) while tolerating whitespace differences in the anchor.

Mapping normalized→original offsets is the tricky part. Approach: build a parallel Vec of (original_byte_idx, normalized_char_idx) as we normalize, so a normalized match range maps back to original byte offsets. Concretely, iterate original content char-by-char, emitting normalized chars and recording original_offset for each emitted char; then str::find on the normalized haystack gives a normalized byte range; binary-search the offset map to get original byte start/end; splice.

Edge cases: multiple matches under fuzzy mode — respect count/replace_all the same way (first N or all). No match → same NotFound error. The identical-strings guard: compare normalized old vs normalized new (if they normalize equal, it's a no-op). Protected by the existing empty-old_string guard in prepare_edit (already shipped). CRLF: normalize_line_endings runs first (as today), so fuzzy works on top of LE-normalized strings.

Schema: add fuzzy_whitespace boolean property. Update tool description + prompt.rs guidance. Tests: fuzzy matches with tab-vs-space, extra trailing space, collapsed runs; fuzzy + count; fuzzy no-match errors; fuzzy identical-strings errors; fuzzy preserves surrounding original whitespace; CRLF + fuzzy; regex mode ignores fuzzy (or errors if both set — prefer: regex mode ignores fuzzy silently, document it).

Project: Windows 11, npm workspace at C:\myHarness. Rust tests via cargo test. This is plan 2 of the sequence (after line-range mode, before batch read).
