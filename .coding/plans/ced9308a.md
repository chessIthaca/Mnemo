# Plan: Land the bookkeeping before the commit: stop merge_to_main's post-landing dangling writes

## Goal
Make the landing skills write ALL memory/knowledge bookkeeping BEFORE the branch's final commit, so it lands with the merge and nothing is ever written after the push. Concretely: reorder `.coding/skills/merge_to_main.toml`'s prompt (and `new_release.toml`'s inline landing) so the records step precedes the commit step; rephrase the landing records onto pre-landing facts (branch + date + work tip — no merge sha, no PR number, both unknowable while the branch is frozen); add an explicit "no memory or knowledge write after the landing" rule plus a clean-tree check before skill_end; pin the order with prompt-contract tests that are red before the fix; document the new record house style in agent.md.

## Kind
bug_fixing

## Context
ROOT CAUSE. `.coding/skills/merge_to_main.toml` prompt: step 1 `Commit ALL uncommitted work on that branch`, step 3/4 land the branch (merge+push, or push+`gh pr create`), step 5 `Supersede this branch's stale status memories with successors recording "MERGED into main at <sha>" ... / "PR #N OPENED ... awaiting human review"`. Step 5 therefore runs on a tree whose branch is already merged and pushed — on the direct path after `git branch -d` has deleted it, and on protected main (ruleset 23755694) any such write can never be pushed. It rides the next plan's wt/* branch instead, and the merge it belongs to is long closed.

WHY IT CANNOT JUST BE MOVED (the circularity that forces a phrasing change too): a record transported BY the merge cannot contain that merge's sha — a commit cannot contain its own hash, and the merge commit is created after the branch content is frozen. The PR number is equally unknowable: it exists only after `gh pr create`, i.e. after the push. So "write it earlier" requires the record to be phrased on facts knowable pre-landing.

FIX DIRECTION. Landing records are written pre-landing and are true-by-construction: title tail `— MERGED into main (branch <name>, <YYYY-MM-DD>)`, body naming the branch's work tip (the tip BEFORE the bookkeeping commit) — the merge commit is then one `git log main --merges` / ancestry-path away. On the PR path the record ships inside the PR, so it becomes live in main exactly when the human merges; a rejected PR means the record never lands (self-consistent). Same reorder for `new_release.toml` step 2, which carries the identical supersede clause after its push/merge. This also subsumes the closeout-plan pattern: with nothing written post-landing, no follow-up closeout is needed.
