## Steps
- [x] 1. **Inventory the trace log + provider-error log** — PowerShell (project root C:\AgenticCoder\AgenticCoder): (1) Get-ChildItem .coding\logs\traces.jsonl | Select Length,LastWriteTime — report size + recency. (2) Count lines (Get-Content | Measure-Object -Line). (3) Read the FIRST line, ConvertFrom-Json, print the top-level keys (id, ts_ms, model, base_url, request_json, usage, finish_reason, etc.) to confirm shape. (4) Parse ts_ms from first + last line, format as HH:mm:ss yyyy-MM-dd — report the date span. (5) Distinct model + base_url values across all lines. (6) Same inventory for .coding\logs\provider-errors.jsonl (line count, date span, distinct models, HTTP status distribution). Save a one-line summary to .coding\analysis\cache-hit-4-inventory.txt (New-Item -Force the dir). Do NOT pipe through Select-String and trust exit code — read $LASTEXITCODE directly. If traces.jsonl is empty or has <3 lines with usage, note that and pivot to provider-errors.jsonl as the primary signal.
- [x] 2. **Per-request summary table + cache-hit aggregates** — PowerShell: read .coding\logs\traces.jsonl line by line, ConvertFrom-Json each, and for requests that have usage (usage.prompt present and > 0): emit a row {id, ts HH:mm:ss, model, prompt, cached, hitPct=round(100*cached/prompt,1), completion, reasoning, finish_reason, nMessages (request_json.messages.Count), nTools (request_json.tools.Count), sysLen (messages[0].content length), tailLen (last system message content length before footer, or the footer itself), max_completion_tokens}. Save the table to .coding\analysis\cache-hit-4-summary.txt. Then compute and append aggregates to the same file: total prompt, total cached, OVERALL HIT %, count of requests with hit >=95%, count of reset requests (hit <50%), tokens wasted on resets (sum of prompt-cached for those), projected hit if resets eliminated, and the median + p90 prompt token count (context size distribution). Mirror the round-2/round-3 table format so the snapshots are comparable. Handle large files: process line-by-line with a foreach, do NOT load the whole file into a single variable.
- [x] 3. **Diff consecutive requests to classify cache-breakers** — PowerShell: for each adjacent pair (i, i+1) in traces.jsonl that both have usage, compare request_json.messages index-by-index (JSON.stringify equality per message, mirroring LlmTraceView compareMessages). Print: k = length of identical leading prefix, first changed index + role, whether system message [0] is byte-identical (sysEq), whether the tools array is byte-identical (toolsEq), whether the LAST message is byte-identical (the R5 footer should make this True unless the footer itself changed), and any top-level request_json field differences (stream, max_completion_tokens, model). Classify each reset (hit <50%) by cause: TAIL-CHANGE (volatile tail content changed but head+tools stable), TOOLS-CHANGE (tool set swapped — workflow state transition), MODEL-SWITCH (different model/base_url), SUMMARIZE (conversation rewritten), PRIMER-CHANGE (session primer differs), HEAD-CHANGE (stable head bytes differ — should be rare post-R1). Write results to .coding\analysis\cache-hit-4-diffs.txt. Key question: is the R5 CONTEXT_FOOTER keeping the last message byte-stable across tail changes? If resets still correlate with tail changes, the footer may not be working as expected on the current provider.
- [x] 4. **Context waste + compaction opportunity scan** — From the per-request summary + diffs, identify context-size waste: (1) Stable head size trend — is sysLen growing across the session (primer re-fetch, tool-group disclosure churn)? (2) Volatile tail size — is tailLen staying compact (~600 tokens) or bloating? (3) Conversation growth rate — how fast does nMessages grow, and does summarization keep it bounded? (4) Tool-result bloat — sample the largest tool-result messages (search request_json for long Tool-role content); are file reads / search outputs oversized? (5) max_completion_tokens — is it being capped correctly (R9), or still sending 131072? (6) Repetition/stuck-loop evidence — any request with completion > 10K tokens (R10 detector should have caught these)? (7) Provider errors from provider-errors.jsonl — are there still max_completion_tokens failures (R9 should have fixed these), or new error patterns? Record findings inline in the report.
- [x] 5. **Write findings report + memorize** — Write .coding\analysis\cache-hit-4-report.md with: (1) Headline — current overall hit %, comparison to baselines (80.7% → 87.2% → 98.5% → now), reset count + waste. (2) Cache-breaker classification table (cause → pairs → waste share), with verdict on whether R5 footer is holding. (3) Context waste findings (head growth, tail bloat, tool-result sizes, summarization frequency). (4) Recommendations ranked by impact/effort — each with a concrete code reference (file:line) and expected token savings. Only recommend changes with real evidence; if the system is already near-optimal, say so and explain why. (5) Caveats (sample size, provider-specific cache semantics). Then write a semantic memory (SPEC or PLAN tier) summarizing the findings + top recommendations, and respond to the user with the headline in ≤3 lines.
