# Plan: Laya sidecar dies with Mnemo, however Mnemo ends

## Goal
The managed laya-serve process tree (laya-serve.exe and its python.exe descendants) always ends when its Mnemo host stops: orderly, force-ended or crashed. No orphaned Laya keeps the checkpoint in RAM.

## Kind
bug_fixing

## Context
Root causes, read 2026-11-03:
1. LayaManager (src/host/laya.rs) spawns `laya-serve` with std::process::Command (~458-470) and stops it with kill_child (~478-482: `child.kill(); child.wait()`). On Windows that kills only laya-serve.exe; its python.exe descendants survive, so even an orderly stop can leave the interpreter holding the checkpoint.
2. When the host process (Mnemo2 or Mnemo1) is force-ended or crashes, neither the RunEvent::Exit stop nor `impl Drop for LayaManager` (~486-490) runs, and Windows does not end child processes with their parent. The whole tree is orphaned.

An existing pattern solves exactly this: src/tool/agent/shell.rs ~825-935 TreeKillGuard (plan bfe2b09f) assigns a spawned child to a Windows Job Object with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE. Descendants inherit the job, and when the last handle to the job closes (including when the owning process dies, because the OS closes its handles) the whole tree is terminated. On Unix it uses a process group. windows-sys already has the Win32_System_JobObjects feature (Cargo.toml ~147-156).

Decisions:
- Factor the Windows job logic out of shell.rs into a small shared module, src/process_tree.rs (new; registered in src/lib.rs), exposing an owned `KillOnCloseJob`. shell.rs's TreeKillGuard then uses it with no behaviour change.
- LayaManager keeps the job alongside the child for the child's lifetime. Stop or replace closes the job (killing the whole tree) and then kills and reaps the root child. Because the job handle lives in the host process, a crash or force-kill of Mnemo closes it and Windows kills the Laya tree.
- On Unix, spawn laya-serve in its own process group (`process_group(0)`) and stop by killing the group (as shell.rs does). Parent-death on Unix is out of scope (documented).
- If job creation or assignment fails, fall back to today's behaviour (only kill_child) and log a warning. Never fail the Laya start.

Regression tests (bug_fixing): `stopping_the_manager_kills_the_server_tree` in src/host/laya.rs and `kill_on_close_job_ends_the_whole_tree` in src/process_tree.rs. Without the fix, the first fails because the grandchild (ping, standing in for python.exe) survives stop(). Known trap (bug record 'A test-spawned process that outlives the test delays the whole test binary's teardown'): tests must always end their spawned trees, even on assertion failure, for example with a guard that kills the job in Drop.

Verification:
- `cargo clippy --all-targets -- -D warnings`, `cargo test --lib` (root);
- `cargo clippy --manifest-path src-tauri/Cargo.toml --features mnemo2 --lib --tests --bins -- -D warnings`;
- `cargo build --manifest-path src-tauri/Cargo.toml --bins`.
- No new #[allow(...)] beyond the existing `unsafe impl Send` pattern in shell.rs.

## Acceptance scenarios
- Force-ending the Mnemo2 process leaves no laya-serve or python.exe process from its Laya tree running.
- An orderly stop of the Laya manager (quit, project switch, settings disable) ends laya-serve and all its python.exe descendants, not just laya-serve.exe.
- The shell tool's tree-kill behaviour is unchanged (its existing tests pass) after the job logic moves to the shared module.

## Bug
Orphaned laya-serve process trees pile up and hold the Laya checkpoint in RAM. On 2026-11-03 there were 8 orphan trees (about 17 GB) left from Mnemo2 processes that had been force-ended or had exited abnormally. Each tree is laya-serve.exe, then python.exe, then python.exe.
