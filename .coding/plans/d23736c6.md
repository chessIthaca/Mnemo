# Plan: A stopped Mnemo2 no longer blocks the project as "in use"

## Goal
When a Mnemo2 process has exited, its leftover project marker no longer makes the next Mnemo2 refuse the project with "another Mnemo2 process (pid N) is using the project".

## Kind
bug_fixing

## Context
SYMPTOM (2026-11-01): see bug. The old Mnemo2 was ended with Stop-Process (no orderly shutdown), so its marker .coding/instance.json {pid 48684, started_at 1793568358} stayed. The new instance's project::attach (src-tauri/src/mnemo2/project.rs line ~153) calls instance_marker::conflict_for(root, own_pid, instance_marker::pid_alive) and treated 48684 as alive.

ROOT CAUSE (probed while planning):
- verified: src-tauri/src/instance_marker.rs pid_alive (line ~71) on Windows returns true whenever OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, pid) yields a handle; it never checks the exit code.
- verified: `tasklist /FI "PID eq 48684"` printed "No tasks are running which match the specified criteria" while the marker blocked the open.
- assumption: OpenProcess still succeeded because the mnemo2-mcp helper that launched Mnemo2 (spawn_app in src-tauri/src/bin/mnemo2_mcp/instance.rs, ~line 895) keeps the Child and so the exited process object; the regression test below proves or refutes this.
- The marker also stores started_at (seconds); a reused pid of an unrelated process would also look alive today.

DECISIONS:
- pid_alive on Windows: after OpenProcess succeeds, call GetExitCodeProcess and report alive only when the code is STILL_ACTIVE (259). windows-sys Win32_System_Threading is already enabled.
- Guard against pid reuse where cheap: if the process's creation time (GetProcessTimes) is later than the marker's started_at plus a small slack, treat the marker as stale. Best effort; failure to read times falls back to the exit-code answer.
- Do not change the conflict prompt or the allow_instance_conflict flow.

REGRESSION TEST: src-tauri/src/instance_marker.rs tests, `an_exited_process_held_open_is_not_alive` (Windows only): spawn a short-lived child (cmd /c exit 0), keep its Child, wait for it to exit, assert pid_alive(child.id()) is false. assumption: it fails before the fix; the worker must run it before fixing and report the result.

VERIFY:
- cargo test --manifest-path src-tauri/Cargo.toml --features mnemo2 --lib instance_marker
- cargo test --manifest-path src-tauri/Cargo.toml --features mnemo2 --lib mnemo2::
- cargo clippy --manifest-path src-tauri/Cargo.toml --features mnemo2 --lib --tests --bins (clean)
- Fresh worker worktrees need `npm ci --no-audit --no-fund` at the worktree root first.

## Acceptance scenarios
- A marker naming a process that has exited, even while another process still holds its handle, does not block opening the project.
- A marker naming a running Mnemo2 still produces the in-use conflict.

## Steps
- [x] 1. **Exited processes are not alive** — `src-tauri/src/instance_marker.rs` (pid_alive and its tests): GetExitCodeProcess == STILL_ACTIVE, optional creation-time check against started_at, regression test an_exited_process_held_open_is_not_alive.

## Bug
After stopping Mnemo2 (pid 48684) for a rebuild and starting the new build, open_mission_control failed: "Mnemo2 could not open the project C:\Mnemo: another Mnemo2 process (pid 48684) is using the project." tasklist showed no process 48684; .coding/instance.json still named it. Removing that file by hand fixed it.
