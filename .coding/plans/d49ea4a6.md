# Plan: Memory tab shows that it is loading, and loads fast

## Goal
While the Memory tab waits for its first page, it says so: a spinner with what it is waiting for (the project engine starting, or the records loading) and the elapsed time. The slow part of that first load is measured and removed, or made as short as the engine allows.

## Kind
implementation

## Context
The user reported on 2026-11-02, right after Mnemo2 was rebuilt and reopened, that the Memory tab showed no memories for a while with no wait indicator and no reason. The records were there all along: memory.db is 224 MB and the Mnemo MCP tools listed today's records from it.

Findings from the lead's probe:
- verified: `sed -n 315,330p src-tauri/src/mnemo2/memory_view.rs`. Every memory command goes through `store(state)` → `engine(state)` → `lead.engine_handle().await`, so the first call waits until the project engine has started. Just after an app start that can take a while (brain start, code-graph open, the 224 MB memory.db with a 34 MB WAL).
- verified: `sed -n 75,100p mnemo2/src/components/MemoryView.svelte`. loadList sets `loadingList`, but the template only uses it to hide the empty message and to label "Load more" (lines 238, 264). On the first load the list area is simply blank: no spinner, no text.
- verified: list_page in memory_view.rs (around line 397) calls `store.list_filtered(&filter)` with a limit of offset+limit+1 (OTHER_SCAN_LIMIT for the "other" group). Whether that query itself is slow on this DB is not measured yet.

Decisions:
- UI (mnemo2/src/components/MemoryView.svelte):
  - The first load of the list, the overview and the reader each show a clear loading state: a spinner with "Loading the project's memory…" and an elapsed-seconds counter after 1 s.
  - When the backend reports that the engine is still starting, the text says "Waiting for the project engine to start…" instead.
  - Errors stay as they are.
  - Reuse the app's existing spinner and elapsed-time components (ElapsedTime.svelte, the LoaderCircle spin used elsewhere); don't invent new ones.
- Backend: measure where the time goes, then fix the slow part.
  - Add timing (tracing debug spans) around the engine wait and around list_filtered/overview in memory_view.rs, and measure a cold first call on this repository's real memory.db, a copy in a temp dir is fine.
  - If the store query itself takes more than about 300 ms, make it fast (an index or a cheaper query for the first page) without changing results.
  - If the engine wait dominates, check whether the memory store can be opened and served before the full engine start finishes. If it can, do it, keeping the "memory is off" and "nothing open" errors exact. If it can't without large changes, report the numbers and keep the UI explanation.
  - Report the measured numbers before and after in the commit message and the report.
- Do not touch files of plan f302cc0e (src/tool/agent/edit_ops.rs, file_edit.rs, multi_edit.rs) or plan 1238e0de (src/agent/*, src/runtime/channels.rs, src/headless/session.rs).

Verification:
- `cargo clippy --manifest-path src-tauri/Cargo.toml --features mnemo2 --lib --tests --bins -- -D warnings` and `cargo test --manifest-path src-tauri/Cargo.toml --features mnemo2 --lib --bins`. Root `cargo clippy --all-targets -- -D warnings` and `cargo test --lib` if src/memory changes.
- From mnemo2/: `npx svelte-check --tsconfig ./tsconfig.json` and `npx vitest run src/lib src/components src/preview`.

## Acceptance scenarios
- Opening the Memory tab right after Mnemo2 starts shows a spinner with "Waiting for the project engine to start…" or "Loading the project's memory…" and an elapsed counter, never a blank list.
- Once loaded, the list, the overview and the newest record appear exactly as before.
- The report states the measured first-load time before and after on this repository's memory.db, and names what was slow.
- All listed checks pass.
