# Plan: Laya managed runtime — download in Settings, Mnemo auto-starts it

## Goal
Give Laya embedding-parity UX: the Settings → Classifier section downloads a self-contained Laya runtime (uv + venv + laya[serve] + checkpoint) with live progress, and when Laya is enabled Mnemo automatically starts, monitors, and stops the local laya-serve sidecar on 127.0.0.1 — no command line, no Python prerequisites. External-endpoint mode remains as an advanced option; the opt-in default (absent [general.laya] ⇒ nothing exists) is unchanged.

## Kind
implementation

## Context
Symptom: the Laya classifier integration requires the user to run `pip install "laya[serve]"` and keep a `laya-serve` process alive by hand; the Classifier settings section documents this ("Mnemo never installs, downloads, or starts it for you"). The user wants embedding-parity: download in the config dialog, and Mnemo auto-starts it when enabled.

Embedding pattern to mirror (all in tree): catalog + download command with progress events in src-tauri/src/ipc/embeddings.rs (`EmbedderStatus::Downloading{model,progress}` emitted on `embedder://status`, progress = cache-dir size sampling); startup hooks `spawn_startup_download`/`spawn_startup_load` (+ console twins) wired in src-tauri/src/main.rs (~592-617); save-driven rewire in src-tauri/src/ipc/rewire.rs; UI in frontend/src/components/settings/sections/EmbeddingSection.tsx.

Laya facts (HF convaiinnovations/laya + github.com/NandhaKishorM/laya, checked 2027-01-11): Python >=3.10 package, core deps torch/transformers/huggingface_hub; `laya-serve` extra (fastapi+uvicorn) serves POST /v1/systemone; env config LAYA_HOST, LAYA_PORT, LAYA_PRELOAD, LAYA_MODELS, LAYA_THREADS; POST with empty `questions` returns 200 with answers:{} (readiness probe); checkpoints convaiinnovations/laya english (repo root, ~808 MB) and multilingual (subfolder, ~647 MB); HF_HOME redirects the model cache. An in-process Rust port was rejected: the scoring head (option [MASK] markers, head-budget splitting, temperature calibration, router language detection) ships no ONNX export — porting risks silent miscalibration.

Chosen architecture — managed uv sidecar: download the uv single-file binary on demand (GitHub releases, asset per target triple) into <global_config_dir()>/laya/bin; `uv venv --python 3.12` at <config>/laya/venv (uv fetches standalone CPython); `uv pip install "laya[serve]"`; pre-download the checkpoint via the venv python (`laya.load`) with HF_HOME=<config>/laya/hf, progress by dir-size sampling (embeddings trick). Runtime: spawn venv's laya-serve (Windows venv\Scripts\laya-serve.exe, unix venv/bin/laya-serve) with LAYA_HOST=127.0.0.1, LAYA_PORT=<free port bound from 127.0.0.1:0>, LAYA_MODELS=<checkpoint>, LAYA_PRELOAD=1, LAYA_THREADS=physical cores; probe /v1/systemone empty-questions until 200 (~120s cold budget); kill the child on app exit (RunEvent::Exit, main.rs:917), on disable, and on reconfigure. Preserve the foundation gate (SPEC 06c1eb9a): absent/disabled [general.laya] ⇒ no client, no server, no downloads. Surface honest sizes in the UI (~0.8-1 GB runtime + 0.65-0.8 GB checkpoint).

Verification: cargo test at repo root (lib + src-tauri, warning-free by #![deny(warnings)]); cd frontend && npm test (vitest run). Tests stay offline — no real uv/PyPI/HF network in unit tests; network-facing fns get thin pure cores that are unit-tested.
