# Plan: Track whether merged work holds up, per model and tier

## Goal
Mnemo2 shows, per model and per tier, how often merged work needed fixing, was reverted, or was followed by a bug fix in the same files. Tier and model choice, and the state of the codebase, are then judged on evidence.

## Kind
implementation

## Context
WHY: the routing log already records each worker's outcome: `outcome` rows in `.coding/laya/dispatch_routing.jsonl` with status, final_tier, models_used, review_rounds, fix_rounds, findings, findings_high, audits, cost_micros. Nobody sees them in aggregate. Two signals are missing:
- a merge that was later reverted;
- a merge followed soon by a bug fix in the same files.
That second one is the earliest sign that work only looked done, and that the codebase is degrading.

DATA SOURCE (decided): the routing log, not the team ledger. The log is committed and union-merged across computers (.gitattributes); the ledger in .coding/mnemo2/ is per machine. Two additions:
1. The `outcome` row gains `merge_commit: Option<String>` (serde default, skipped when None), set when status is merged.
2. A new row kind `reverted` `{event:"reverted", ts, worker_id, plan_id, step, revert_commit}`, appended when `team_revert_merge` succeeds (TeamRuntime::revert_merge, src-tauri/src/mnemo2/team/merge.rs:666).
Rows are the `DispatchRoutingRow` enum in src-tauri/src/mnemo2/dispatch_routing.rs. Every reader of the log (Laya training, route_eval, kNN, laya_settings) must ignore `reverted` rows. Verify each reader and add tests.

METRICS (decided), over a window (default 30 days by outcome ts), grouped by final model (last of models_used) and by final_tier. Only `merged` outcomes count as tasks; audit workers have no outcome rows.
- merged: count.
- first_pass: merged with fix_rounds == 0 and findings_high == 0 (share, 0-1).
- avg_fix_rounds, avg_findings, high_findings (sum).
- reverted: merged tasks with a later `reverted` row for the same worker_id.
- bugfix_followups: merged tasks with merge_commit M whose changed files (`git diff --name-only M^1 M`) overlap the changed files of a LATER merged task, within 14 days, whose plan is kind bug_fixing (plan kind read from `.coding/plans/<plan_id>.md` with the existing plan parser). A task never counts as its own follow-up, nor do tasks of the same plan.
- cost_per_merged: total cost_micros of merged tasks / merged.
Plus `categories`: the top 10 finding categories from `.coding/reviews/findings.jsonl` (written by plan 3c2ec71c) in the window, as (category, distinct workers). Empty when the file is absent.
Rows without merge_commit (older ones) count for everything except bugfix_followups. The report says how many tasks lacked it.

VERIFY (each alone on its line): `cargo test --workspace`; `cargo clippy --workspace --all-targets`; for UI steps also `npm test --workspace mnemo2` and `npm run check --workspace mnemo2`.

## Acceptance scenarios
- After a merge, the outcome row in dispatch_routing.jsonl carries merge_commit; after team_revert_merge, a reverted row is appended, and Laya's eval results are unchanged by it.
- team_quality returns per-tier and per-model rows whose merged/first-pass/fix-round numbers match a hand count over the log.
- A task whose files a bug_fixing plan's merge touched within 14 days counts once under 'Bug fix followed'.
- The Quality tab in the side panel shows both tables, the recurring finding categories, and the empty state when the window has no merges.
