# Plan: skill_end/abandon_skill always available during a skill

## Goal
Make the skill exits — skill_end and abandon_skill — always available while a skill is active, regardless of the skill's allow-list, so a skill file that forgets to list them can never trap the agent.

## Kind
bug_fixing

## Context
Root cause: the ToolFilter::Skill arm (src/tool/mod.rs:829-857) auto-grants only memory tools, ask_user, current_plan, skill_reload, backlog_add/backlog_status/backlog_list — the skill's exits (skill_end, abandon_skill) fall through to `allowed.iter().any(|n| n == name)`, so an allow-list that omits them hides the only way out. The same "never stuck" principle is already documented for abandon_plan in the Reviewing arm (src/tool/mod.rs:401-402). Fix: add both exits to the always-available set (the user asked for skill_end; abandon_skill is the paired rollback exit the skill prompt also names — without it a failing skill can only exit forward). Anchors: (1) src/tool/mod.rs:829-857 the Skill arm — add `|| name == "skill_end" || name == "abandon_skill"` with a comment citing the never-stuck rule; (2) src/tool/mod.rs:468-474 the Skill variant doc — add the exits to the always-available set description; (3) src/tool/mod.rs:806-808 the Complete arm comment "(the Skill filter exposes them via the allow-list)" → "(the Skill filter always exposes them)"; (4) src/agent/factory.rs:1056-1058 register_skill_tools doc "exposed via the Skill filter's allow-list" → "exposed by the Skill filter unconditionally"; (5) src/tool/workflow/skill.rs:299-314 SKILL_FILE_HEADER — add skill_end/abandon_skill to the "always available and need not be listed here" list (this header is written into every skill_create-generated file). Regression tests: (a) src/tool/mod.rs tests (near skill_create_allowed_only_in_the_executing_surfaces, ~2350): new test skill_exits_are_always_available_inside_a_skill — skill_end + abandon_skill allowed under ToolFilter::Skill(vec![]) (EMPTY allow-list — fails pre-fix), hidden under Planning/Executing/Reviewing/Complete (only meaningful mid-skill), and not granted to ToolFilter::Reviewer implicitly; (b) src/agent/tests.rs: new dispatch test modeled on dispatch_denies_tool_outside_skill_allow_list (line 6047): wf.start_skill("narrow", "do the skill", WorkflowState::Planning, vec!["file_read".into()]) — allow-list WITHOUT skill_end — then execute a skill_end tool call and assert result.success (pre-fix it fails with "not allowed ... Skill"). Check make_dispatch_fixture registers SkillEndTool; if not, register it the way the ~10550 test registers SkillStartTool (registry.register(Box::new(SkillEndTool::new(workflow.clone(), ...)))) — read src/tool/workflow/skill.rs:184+ for the constructor. Existing tests that list skill_end in allow-lists (src/agent/tests.rs:10560, src/tool/mod.rs:2490, src/workflow/mod.rs:3206) keep passing — listing the exits stays legal, just redundant. Verification: cargo test (canonical root run; deny(warnings) means green = zero warnings).

## Bug
During an active skill, `skill_end` (and `abandon_skill`) are only visible if the skill's allow-list names them — a skill file that omits them traps the agent in the skill with no exit and no rollback, while the injected skill prompt (src/agent/prompt.rs:770: "Goal achieved → skill_end (exits to {target}); rollback → abandon_skill") advertises both. User report 2027-01-24: "skill_end is always allowed during a skill. Not having that is silly."
