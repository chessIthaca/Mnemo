# Plan: Phase 6b — Safety hardening leftovers (Quality M5/M6/M4-strict)

## Goal
Fix the three remaining safety-hardening findings from the 2026-04-08 architecture quality review: (M5) expand `Sandbox::is_protected_write_target` beyond just `memory.db` to also block `stack.json`, `safety.toml`, `backlog.json`, and plan markdown files from the file agent tools; (M6) enforce restrictive filesystem permissions on `keys.toml` after write (Unix chmod 0600, Windows user-only DACL) instead of leaving it world-readable; (M4-strict, optional) add an opt-in `run_all_strict_success` config flag that gates Run-All `commit_success` on the main agent's workflow reaching `Complete`/`Planning` (rejecting mid-plan `Executing`/`Skill` turns). ## Context
Parent: Architecture review remediation, step 26 (Phase 6b). Three findings from .coding/reviews/2026-04-08-architecture-quality.md:

M5 (line 144): `Sandbox::is_protected_write_target` (src/tool/agent/sandbox.rs:148) only blocks `.coding/memory.db` + wal/shm. Approved file_write can corrupt `.coding/plans/stack.json`, plan markdown, `safety.toml`, backlog files — restart/resume and safety rules become model-writable. Recommendation: "At minimum protect stack.json, safety.toml, memory.db*." The dedicated workflow tools (create_plan/complete_step/update_plan/abandon_plan in src/tool/workflow/plan.rs) write `.coding/plans/` via their OWN std::fs paths — they do NOT go through is_protected_write_target, so expanding the protected set only blocks the file AGENT tools (file_write/edit/append), not the dedicated tools. The reviewer subagent writes to `.coding/reviews/` via file tools — must remain writable. GAP: the current protected check (file_write.rs:84 `if let Ok(validated) = sandbox.validate(path)`) only fires for EXISTING paths; a non-existent protected path (creating a fresh stack.json) slips through validate_for_creation. Must close this creation gap too.

M6 (line 151): PLAN.md claims ACL-restricted keys; `src/config/keys.rs` `save` (line 94) uses `write_atomic` only — no permission tightening. KeyStore correctly redacts Debug (good). keys.toml lives in the GLOBAL config dir (~/.myharness/), not the project. Recommendation: "On Windows, set user-only DACL after write; document permissions for other OS." Unix can use std::os::unix::fs::PermissionsExt::set_mode(0o600) — no new dep. Windows needs the windows-sys crate (raw FFI) for SetFileSecurityW/SetNamedSecurityInfoW with a user-only DACL — CHECK Cargo.lock first for transitive availability (Tauri likely pulls windows-sys). No windows deps in Cargo.toml currently.

M4-strict (line 137, optional): Success criterion for Run-All is "Finished without final Error," not "plan Complete." `on_main_turn_resolved` (src-tauri/src/ipc/run_all.rs:470) calls commit_success whenever success=true. Agent can stop mid-plan (MAX_RETRIES, model stops early) and still "succeed." Recommendation: "Optional strict mode: require workflow Complete before commit_success." Design: opt-in `run_all_strict_success: bool` (default false) in GeneralSection (src/config/general.rs). Pure helper `strict_success_allows_commit(WorkflowState) -> bool`: Complete|Planning → true (plan done, or freeform no-plan prompt); Executing|Skill → false (plan/skill incomplete). on_main_turn_resolved reads main agent's workflow state via state.runtime.agent_loops + state.runtime.manager.main_agent_id() when strict_success && success; if not allowed, rollback + CantResolve("strict mode: workflow not Complete") instead of commit_success + Done. The pure helper is unit-testable without a Tauri AppHandle.

Existing tests to keep green: file_write.rs `refuses_to_write_memory_db` (line 329), file_append.rs protected test (line 212). cargo 508+ tests, vitest 78, tsc green at start. Branch: feat/bookkeeping-tools-autorun.
