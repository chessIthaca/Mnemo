# Plan: Multimodal flag + vision model fallback for image-to-text

## Goal
Add a `multimodal` flag to endpoint config and an optional `vision_model` config (endpoint name + model) so that when the chosen LLM is not multimodal, a separate vision model (possibly from a different OpenAI-compatible source) can be used for image-to-text. Add a `VisionClient` that wraps an `OpenAiClient` configured for the vision model, and a `describe_image` method on the agent loop that uses the vision model when available.

## Context
The user's scenario: GLM-5.2 (a reasoning model) is not multimodal, but Qwen-VL is configured in the same portal (or a different OpenAI-compatible source). When the agent encounters an image it can't process (because the main LLM is text-only), it should fall back to the vision model for image-to-text.

Current architecture:
- `Capabilities` (src/provider/mod.rs:22) has no `multimodal` field.
- `Endpoint` (src/config/endpoints.rs:18) has name, kind, base_url, models, max_context, max_output_tokens — no multimodal flag.
- `GeneralConfig` / `GeneralSection` (src/config/general.rs) has default_provider, default_model, safety — no vision model config.
- `OpenAiClient` (src/provider/openai.rs) takes an `OpenAiClientConfig` (base_url, api_key, model, kind, max_context, max_output_tokens).
- `build_brain` (src-tauri/src/main.rs:174) resolves the endpoint + model from config, builds an `OpenAiClient`, and passes it to the `AgentLoopFactory`.
- The `AgentLoopFactory` (src/agent/factory.rs) holds the provider as `Arc<dyn LlmClient>`.
- `MessageContent` already supports `Parts(Vec<ContentPart>)` with `ImageUrl` blocks (src/provider/mod.rs:135-188), but `build_request_json` in openai.rs always serializes content as plain text via `m.content.as_text()` (line 291) — it doesn't send image blocks.

Design decisions:
1. **`multimodal` flag on `Endpoint`** — a per-endpoint boolean (default false). Set true for endpoints whose models accept image inputs (e.g. OpenAI gpt-4o, Qwen-VL). This is an endpoint-level property because all models at an endpoint typically share multimodal capability.
2. **`vision_model` in `GeneralSection`** — an optional struct `{ endpoint: String, model: String }` naming a separate endpoint + model to use for image-to-text when the main LLM is not multimodal. The vision endpoint can be a different OpenAI-compatible source (different base_url + api_key). This is general — not hardcoded to Qwen-VL.
3. **`Capabilities.multimodal`** — a boolean on the capability set, derived from the endpoint's `multimodal` flag. The agent loop checks this to decide whether to use the vision fallback.
4. **`VisionClient`** — a new struct wrapping an `OpenAiClient` configured for the vision model. It has a `describe_image(image_url: &str, prompt: &str) -> Result<String>` method that does a non-streaming completion (simpler than streaming — we just need the text back). It implements a new `VisionClient` trait or is just a concrete struct held by the factory.
5. **`AgentLoopFactory`** — gains an optional `vision: Option<Arc<VisionClient>>` field. `build()` passes it to the `AgentLoop`.
6. **`AgentLoop`** — gains an optional `vision: Option<Arc<VisionClient>>` field + a `describe_image` method. When the agent needs to process an image and the main provider is not multimodal, it calls the vision client.
7. **`build_brain`** — resolves the vision endpoint + model from config, builds a `VisionClient` if configured, and passes it to the factory.
8. **`build_request_json`** — updated to send image blocks when `MessageContent::Parts` contains `ImageUrl` blocks AND the provider is multimodal. When not multimodal, image blocks are stripped (the vision client handles them separately).

The vision model might come from a different OpenAI source than the LLM — the config is general (endpoint name + model), and `build_brain` resolves the endpoint's base_url + api_key independently from the main provider.
