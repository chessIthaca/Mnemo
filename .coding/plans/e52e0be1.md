# Plan: The lead sees and follows the live tier setup

## Goal
A Claude Code lead can always read the current tier setup (models in order, effort, run as, each model's health). Its tool descriptions refresh when tiers change or Mnemo2 restarts, a pinned model that bypasses a Claude Code agent tier is flagged, and escalation or a resume onto an agent tier hands the step to the lead's agent instead of switching models.

## Kind
implementation

## Context
WHY (FactoryGame, 2026-11-22). The High tier was set to "Run as: Claude Code agent — Opus" in Settings > Tiers, but the lead never knew. Its team_dispatch schema still described high as "Ollama Cloud/glm-5.3" with no agent note: Claude Code fetches tool descriptions once per MCP session, and Mnemo2 had been rebuilt mid-session. The lead pinned `model: deepseek/deepseek-flash` to dodge glm's weekly 429, which silently bypassed the Claude setting. Mnemo's auto-escalation kept moving workers onto glm-5.3, which was out of credits. The same staleness hit the Mnemo lead today: after a rebuild added team_agent_done, the session never saw the tool.

RELATION TO PLAN e5d93df3. Its step 5 already marks usage-limited models unavailable for 6 hours (in memory, read through current_models()) and skips them in tier resolution, fold-down, tier guidance and audits, which is item 5 of the request. This plan builds on it and never duplicates it. Its steps 1 and 3 dispatch only after e5d93df3's steps 2, 4 and 5 have merged, because they share routing.rs, lead_tools.rs, dispatch.rs, control.rs, escalation.rs, pump.rs and tests.rs. Step 2 (src-tauri/src/mnemo2/mcp_server.rs and the helper) can run at once.

DECISIONS (settled):
1. team_tiers. A new lead tool `team_tiers {}` (no arguments; read-only; SafetyLevel::AutoRun). It returns, in tier order, one entry per tier:
   - id, name, definition;
   - `models`: an array in configured order, each `{spec, health}`. health is "available"; "unavailable until <HH:MM local> (usage limit)" from e5d93df3 step 5's map; or "not configured" when the spec names no model in the catalog;
   - effort;
   - `run_as`: `{"kind": "claude_agent", "model": <m>, "effort": <e or null>}` or `{"kind": "mnemo"}`;
   - `resolves_to`: the tier and model a dispatch would run on now, after skipping unavailable models and folding down.
   It also returns `tiers_changed_at` (local HH:MM, or null when unchanged since Mnemo2 started) and `lead: "claude_code" | "in_app"`. In the text JSON, "run_as" applies only when Claude Code leads; with the in-app lead the entry still shows it, with `"applies": false`.
2. Tier change tracking. TeamRuntime keeps `tiers_revision: u64` and `tiers_changed_at_ms`, bumped by set_tiers when the ladder (including claude_agent and effort) actually changes, and by e5d93df3's mark_model_unavailable. It also keeps `lead_seen_tiers_revision`, updated whenever the external lead calls team_tiers, and set to the current revision when the external lead attaches. When the current revision differs from lead_seen, every team_dispatch, team_resume and team_route_fix result carries the line `Tiers changed at <HH:MM> since you last read them; call team_tiers for the live setup.` (in `warnings`).
3. Live tool list. mcp_server.rs computes `tools_revision`, a stable hash of the exact tools/list JSON for the connection's target. It declares `capabilities.tools.listChanged: true` in initialize, and carries tools_revision on every reply the helper receives, in a field the helper strips before writing to stdout. The helper (src-tauri/mnemo2-app/src/mnemo2_mcp/serve.rs) remembers the revision of the last tools/list it answered. When a later reply carries a different revision, it writes `{"jsonrpc":"2.0","method":"notifications/tools/list_changed"}` to stdout right after that reply. It also writes it after reconnecting to a restarted Mnemo2 whose revision differs (the rebuild case). A missing revision (an older app) never triggers a notification.
4. Bypass warning. When team_dispatch from the external lead passes `model`:
   (a) if it also passes `tier` and that tier has claude_agent, or
   (b) if it passes no tier and the model is listed in a tier that has claude_agent,
   the result's `warnings` carry `model <spec> bypasses tier <tier>'s Claude Code agent (<agent model>); dispatch by tier to use the agent.` (for (b), name the first such tier). When the deferred Laya classification of a model-pinned dispatch later lands on a tier with claude_agent, push a notice to the external lead: `Laya reads <id>'s step as <tier>, which runs as a Claude Code agent (<agent model>); the pinned model <spec> bypassed it.` Dispatch behaviour doesn't change: an explicit model still starts a Mnemo worker on it.
5. Escalation honours run as. When an implementation worker (not an audit) is moved onto a tier whose claude_agent is set, and Claude Code is the attached external lead, the move hands the step to the lead's agent instead of switching models. This applies to team_resume with that tier, auto escalation, and e5d93df3 step 5's usage-limit auto-resume.
   - Stop the worker's Mnemo session, keeping its record, branch, worktree and commits.
   - Set claude_agent and claude_agent_effort from the tier, set record.tier, set status Working, and persist.
   - Build the claude_agent block as dispatch does (claude_agent_block). Its prompt is agent_prompt(record) followed by: `A Mnemo worker on <previous model spec> already worked on this step in this checkout. Before you change anything, run git status, git log --oneline <base_commit>..HEAD and git diff to see where it stopped, then finish the step.`
   - team_resume returns the block in its result (result.claude_agent and data). Auto escalation and auto-resume push a notice to the external lead: `<id> moved to tier <tier>, which runs as a Claude Code agent: launch your Agent with this block, then call team_agent_done.`, followed by the block as JSON.
   - Without an attached external lead, the move switches models exactly as today. Audits never take this path.
6. Tier choice: e5d93df3 decision 10 applies (the high tier's model is out of quota). Name tiers explicitly.

ANCHORS (verify): tier_guidance, current_models, resolve_tier_choice, tier_models in routing.rs; set_tiers on TeamRuntime (routing.rs ~365); lead_host_tools in lead_tools.rs; dispatch_result and claude_agent_block in dispatch.rs; the resume-with-tier path in control.rs (resume, resume_inner) and escalation.rs (auto escalation switch); spawn_pending_classification and the label landing in routing.rs (~923); push_external_notice in external_lead.rs; agent_prompt in record.rs; initialize and tools/list in mcp_server.rs (~1154-1210, tool_list); the helper's serve in src-tauri/mnemo2-app/src/mnemo2_mcp/serve.rs and http.rs.

VERIFY: the four .coding/checks.toml commands.

## Acceptance scenarios
- With Claude Code leading, setting High to 'Claude Code agent — Opus' in Settings refreshes the lead's team_dispatch description without a restart (a tools/list_changed notification), and the next dispatch says the tiers changed until the lead calls team_tiers.
- team_tiers lists every tier's models in order with their health, effort, run as, and the tier and model a dispatch would run on now; a usage-limited model shows 'unavailable until HH:MM (usage limit)'.
- A team_dispatch that pins a model on a tier which runs as a Claude Code agent warns that the model bypasses the agent, and still starts the Mnemo worker.
- team_resume or auto escalation onto a tier that runs as a Claude Code agent stops the Mnemo session and gives the lead a claude_agent block whose prompt says where the previous worker stopped.
- After a Mnemo2 rebuild that adds a tool, the running Claude Code session gets a tools/list_changed notification and sees the new tool.

## Spec changes

### external-lead

#### ADDED Requirements

##### Requirement: The lead can read the live tier setup
The lead tool team_tiers SHALL return every tier's models in order with their health, effort, run as and current resolution. Mnemo SHALL tell the external lead when the tiers changed since it last read them, and its tool descriptions SHALL refresh through a tools/list_changed notification when the tool list changes, including after Mnemo2 restarts.

###### Scenario: Tier change reaches the lead
- **WHEN** Claude Code leads
- **WHEN** the user sets High to run as a Claude Code agent and saves
- **THEN** the lead receives tools/list_changed
- **AND** the next dispatch result says the tiers changed

###### Scenario: Health is visible
- **WHEN** a model hit its usage limit
- **THEN** team_tiers shows it unavailable until a time

### dispatch-routing

#### ADDED Requirements

##### Requirement: Pinned models that bypass an agent tier are flagged
A dispatch from the external lead that pins a model on a tier which runs as a Claude Code agent SHALL warn that the model bypasses the agent, and SHALL still start the Mnemo worker.

###### Scenario: Pinned model on an agent tier
- **WHEN** high runs as a Claude Code agent opus
- **WHEN** the lead dispatches with tier high and an explicit model
- **THEN** the result warns that the model bypasses the agent
- **AND** a Mnemo worker starts on the pinned model

##### Requirement: Escalation honours run as
When Claude Code leads, moving an implementation worker onto a tier that runs as a Claude Code agent, by team_resume, auto escalation or usage-limit auto-resume, SHALL stop its Mnemo session and hand the step to the lead's agent with a claude_agent block. Without an external lead the move SHALL switch models as before.

###### Scenario: Resume onto an agent tier
- **WHEN** Claude Code leads
- **WHEN** the lead resumes a worker on a tier that runs as a Claude Code agent
- **THEN** the result carries a claude_agent block
- **AND** the worker has no Mnemo session

###### Scenario: In-app lead
- **WHEN** no external lead is attached
- **WHEN** a worker is resumed on that tier
- **THEN** it switches to the tier's model

### tier-ladder

#### ADDED Requirements

##### Requirement: Tier model health is reported
For each tier, Mnemo SHALL report each configured model as available, unavailable until a time after a usage limit, or not configured, and the tier and model a dispatch would resolve to now.

###### Scenario: Unavailable first model
- **WHEN** a tier's first model is unavailable after a usage limit
- **THEN** the tier resolves to its next available model, or folds down
- **AND** team_tiers shows the first model unavailable until its time

### worker-brief

#### ADDED Requirements

##### Requirement: A worker handed to an agent mid-step continues from its checkout
When a worker moves to a Claude Code agent tier mid-step, the agent prompt SHALL carry the worker brief plus where the previous worker left off: its previous model, and the instruction to read git status, the log since the base commit and the diff before changing anything.

###### Scenario: Continuation prompt
- **WHEN** a worker on a Mnemo model is resumed onto an agent tier
- **THEN** the agent prompt names the previous model and the base commit

### settings-dialog

#### ADDED Requirements

##### Requirement: Saving tiers updates what the lead sees
Saving a changed tier ladder in Settings SHALL bump the tier revision, so an attached Claude Code lead's tool descriptions refresh and its next dispatch says the tiers changed.

###### Scenario: Save tiers
- **WHEN** the user changes a tier and clicks Save tiers
- **WHEN** Claude Code leads
- **THEN** the lead's next dispatch says the tiers changed
