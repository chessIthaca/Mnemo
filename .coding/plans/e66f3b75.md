# Plan: v0.1.1 release: CI release job + new_release skill + version bump

## Goal
Create the v0.1.1 GitHub release with CI-built installers and make the release process a reusable skill: a CI-native release job in the build workflow, the 0.1.0 → 0.1.1 version bump, and a new_release skill that encodes bump → merge → tag → push → verify.

## Kind
implementation

## Context
User request: create a new GitHub release + make a reusable skill of the release process. User chose tag v0.1.1 (bump from 0.1.0; the existing "First release" — tag WindowsRelease, 2026-09-13, no assets — claimed the 0.1.0 era). Repo: github.com/chessIthaca/Mnemo (public — the REST API works unauthenticated for verification reads).

DESIGN — CI-native release creation: .github/workflows/build.yml already triggers on v* tag pushes and uploads artifacts (windows-installers: msi/nsis under target/release/bundle/; macos-bundles-aarch64: mnemo.app.zip + dmg), but nothing creates the GitHub release (the existing release was made manually, no assets). Add a `release:` job: `if: startsWith(github.ref, 'refs/tags/v')` (tag pushes only — manual dispatch builds but never publishes; github context IS allowed in jobs.if, secrets is not), `needs: [windows, macos]`, runs-on ubuntu-latest, `permissions: contents: write`, steps: actions/checkout@v4, actions/download-artifact@v4 (windows-installers → dist/windows, macos-bundles-aarch64 → dist/macos), softprops/action-gh-release@v2 with files globs (dist/windows/**/*.msi, *.exe, dist/macos/**/*.dmg, *.zip) + generate_release_notes: true. The regression test tests/integration/ci_workflow.rs::build_workflow_step_ifs_never_reference_secrets must stay green (the new job-level if uses github, not secrets).

VERSION BUMP 0.1.0 → 0.1.1 in ALL FIVE files together: src-tauri/tauri.conf.json (drives the installer version), package.json, frontend/package.json, Cargo.toml (root lib), src-tauri/Cargo.toml (bin); then cargo check to refresh Cargo.lock (mnemo + mnemo-app entries) and commit it.

SKILL: author .coding/skills/new_release.toml matching the merge_to_main.toml format (comment header with rationale + name/available_in = ["complete","planning"]/target_state = "planning"/tools allow-list/prompt = terse checklist). The prompt encodes: (1) bump the version in all five files + cargo check + commit; (2) land on main (merge_to_main steps inline: commit all, checkout main, shell git fetch/pull, git merge --no-ff, verify BOTH builds — npm run build in frontend/ AND cd src-tauri && cargo build, branch -d, push); (3) annotated tag v<version> on the MERGED main commit (never a branch tip), push the tag via shell (approval-gated — triggers the ~30-90 min dual-runner build); (4) verify the run started via Invoke-RestMethod on https://api.github.com/repos/chessIthaca/Mnemo/actions/runs?event=push; (5) report run + expected release URLs — NEVER create the release manually (the CI release job owns it; a manual asset-less release would block the CI one). Then skill_reload to register it live.

VALIDATION: PyYAML parse of build.yml (the L52-class guard); actionlint if downloadable (temp dir, single Go binary from github.com/rhysd/actionlint/releases — catches expression/context errors PyYAML cannot; fix any findings); cargo test full suite (includes the ci_workflow guard over the new job).

POST-FINISH RELEASE EXECUTION (Complete state, after the plan lands): run merge_to_main to land the workflow + bump + skill on main, then start the new_release skill and execute it for v0.1.1 (bump already landed — continue at the tag step): git tag -a v0.1.1 on merged main, push the tag (approval-gated), verify the workflow run started, report. The release with .msi/.exe/.dmg/mnemo.app.zip assets + generated notes appears when CI completes.
