# Plan: Show the automatic memory re-embed as a progress line, and resume it instead of restarting

## Goal
When the memory embedding model changes (Settings save, startup with a different model, or stale rows from another machine), the window's status line shows "Re-embedding memories · 3,200/12,444 memories" with a bar, then "Memories re-embedded" for a moment. A re-embed interrupted by closing the window continues with only the rows still on the old model.

## Kind
implementation

## Context
WHY: the user switched Settings → Models → memory embedding model from bge-base-en-v1.5 to jina-embeddings-v2-base-code. The re-embed ran silently, so they thought nothing happened. FactoryGame (1,335 memories) finished. C:\Mnemo (12,444) stopped at 362 when the window closed, and on reopen it started again from row 1. The user's rule: background work must be visible.

HOW THE RE-EMBED RUNS TODAY: every automatic path calls `crate::memory::reembed_if_needed(store, embedder)` (src/memory/mod.rs:72). Call sites:
- src/host/brain.rs:816 (startup);
- src/host/brain.rs:1369 and :1401 (the deferred model load, remote and in-process);
- src/host/rewire.rs:178 (Settings save).

It reads `stored_model_fingerprints()` and, when the set is not exactly {(model, dim)}, calls `MemoryStoreTrait::reembed_all(embedder, progress)` (src/memory/mod.rs:2840). That re-embeds EVERY row one at a time (about 18 rows/s over the models host) and ticks `progress(done, total)` after each row. The manual Memory tab "Rebuild search" (src-tauri/src/mnemo2/memory_maintenance.rs, `rebuild_search` in src/memory/maintenance.rs) also uses reembed_all and has its own progress UI; leave it unchanged.

HOW THE STATUS LINE WORKS: src-tauri/src/mnemo2/indexing.rs, `IndexingTracker`:
- It folds pass events (JSON tagged "type": started | progress{done,total} | done{summary} | failed{error}) into an `IndexingSnapshot { revision, first_run, code, memory, laya }` with `apply_pass_event`.
- It broadcasts the snapshot on "mnemo2://indexing". `watch(engine)` starts the forwarding tasks.
- The frontend: mnemo2/src/lib/indexingEngine.ts (types, `runningPasses`, `PassKind`) and mnemo2/src/components/IndexingStatus.svelte. The latter keeps per-kind text tables (RUNNING_TEXT, UNIT_TEXT, PROGRESS_LABEL, FINISHED_TEXT, FAILED_TEXT) and iterates the kinds `["code","memory","laya"]` in two places.

DECISIONS TAKEN:
1. The re-embed state lives on the MemoryStore as a `tokio::sync::watch` channel holding the LAST event. Why: the startup re-embed starts inside brain construction, before the window's tracker subscribes. A watch channel gives a late subscriber the current state, and one store serves every path (startup, deferred load, rewire). No HostEvent plumbing.
2. Progress ticks are throttled in core with the existing `crate::host::maintenance::should_forward_progress(done, total, PROGRESS_EVERY)` (src/host/maintenance.rs:112), the same throttle the manual rebuild uses. Started, the final tick (done == total) and the terminal events are always sent. If the core memory module cannot depend on crate::host, move nothing: re-implement the same rule locally in a private fn with a comment pointing at the original.
3. reembed_if_needed re-embeds only stale rows: `embedding IS NULL OR embed_model IS NOT ?model OR embed_dim IS NOT ?dim`. A restart then continues where it stopped. reembed_all keeps its every-row behaviour for the manual rebuild.
4. A new fourth pass, `embeddings`, joins the snapshot after `laya`. It never touches first_run (it never blocks the project).

WORDING (the status line, final):
- running: "Re-embedding memories" with unit "memories" (so "Re-embedding memories · 3,200/12,444 memories");
- progress bar label: "Memory re-embed progress";
- finished: "Memories re-embedded";
- failed: "Memory re-embed failed".
- The done summary (tooltip): "<n> memories re-embedded for <model>".

VERIFY: cargo test -p mnemo --lib memory; cargo test -p mnemo-app indexing; npm test --workspace mnemo2; npm run check --workspace mnemo2. Workers must never use git stash.

## Acceptance scenarios
- With a store whose rows carry fingerprint bge-base-en-v1.5/768 and an embedder whose model_id is jina-embeddings-v2-base-code, reembed_if_needed publishes Started, then Progress ticks ending with done == total, then Done whose summary names the count and the model; a receiver taken BEFORE the call sees the final Done; a receiver taken AFTER sees Done as its current value.
- A store with 10 rows where 4 already carry the new fingerprint: reembed_if_needed re-embeds exactly the 6 stale rows (Progress total == 6) and afterwards stored_model_fingerprints is exactly [(new model, dim)].
- A store already uniform on the expected fingerprint: reembed_if_needed publishes nothing (the watch value stays None) and touches no rows.
- IndexingTracker folding a Started then Progress{done:3200,total:12444} from the store's watch yields snapshot.embeddings = Running 3200/12444; a Done yields state Done with the summary as detail; first_run is unchanged throughout.
- In the window, while a re-embed runs, the status line reads "Re-embedding memories · 3,200/12,444 memories" with a progress bar labelled "Memory re-embed progress"; when it ends, "Memories re-embedded" shows briefly; a failure shows "Memory re-embed failed" with the error as tooltip.
