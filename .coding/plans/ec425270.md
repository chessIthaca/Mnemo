# Plan: Self-healing wedged offscreen browser (CDP timeouts + force-reap + watchdog probe)

## Goal
Make the offscreen (launch-mode headless Chromium) browser self-healing: every CDP command is bounded by a timeout, a timed-out (wedged) browser is force-reaped and transparently respawned on the next command, and the watchdog proactively detects and reaps an idle-wedged browser — so "the offscreen browser is wedged" becomes a bounded error + automatic restart instead of an infinite hang.

## Kind
bug_fixing

## Context
Root cause (verified by code read, 2027-02-05): (1) No timeout on any launch-mode CDP round-trip in src/browser/mod.rs — navigate (browser.new_page + event_listener + page_info, :566-637), list_pages (:641), close_page (:678), switch_page (:703), screenshot (:718), snapshot (:755), eval (:765), click (:781), type_text (:793) all await chromiumoxide futures with no tokio::time::timeout; a wedged browser never responds → the tool call hangs forever. (2) watchdog_loop (:547) → reap_dead_browser (:420) only reaps browsers whose handler task is_finished() (process death / dropped connection) — a wedged browser keeps the handler alive, so it is never reaped. No tool-layer timeout exists either (src/tool/browser/mod.rs has none).

Fix design: per-command timeout + force-reap + watchdog liveness probe, all in src/browser/mod.rs (chromiumoxide 0.7 API verified via docs.rs: Browser::version() is a cheap browser-level CDP round-trip; Browser::kill() already used by kill_browser :882). Key invariants: CDP round-trips run OUTSIDE the state lock (Review C1 — keep it); the kill runs off-lock on a background task (Review B1 — keep it); kill_browser needs Arc::try_unwrap sole ownership — the timeout dropping the inner future releases the op's Arc<Browser> clone, and the existing 50×100ms retry loop covers stragglers (worst case: kill gives up, child left + profile skipped — same as today's dead-browser path). Scope: launch-mode (offscreen) browser ONLY — the webview attach mode (browser_* tools on the app's own WebView2) is out of scope (RDP-freeze class, handled separately).

Regression-test design: eval("while(true){}") blocks the renderer main thread → the Runtime.evaluate response never arrives → the op hangs (the defect, reproducible). With the fix + a shortened test timeout (set_cdp_timeout), the eval returns an Err mentioning "unresponsive" + "restart", and a subsequent navigate succeeds on a freshly spawned browser (self-heal). Pre-fix the test fails via a 5s outer guard (demonstrating the hang); post-fix it passes in <1s.

Verification (Windows/PowerShell, unpiped + $LASTEXITCODE per agent.md): cargo test (normal suite, warning-free under #![deny(warnings)]); cargo test browser -- --ignored (integration tests that spawn Chromium: the new wedge test + no-false-positive probe test + existing navigate/console tests). Package: root crate "mnemo" (lib mnemo; browser feature is default-on for tests via src-tauri dev-deps — the existing browser tests already run under plain cargo test for the non-ignored ones).

## Bug
offscreen_browser_* tool calls hang forever when the shared headless Chromium is wedged (alive process, open CDP connection, unresponsive renderer — e.g. a page stuck in an infinite JS loop). The watchdog never reaps it (the handler task is still running, and reap_dead_browser only fires on a finished handler), so the wedge persists until an app restart.
