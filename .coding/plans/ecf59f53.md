# Plan: Knowledge records carry today's date, not a copied future date

## Goal
A knowledge record written today is named and stamped with today's date from the wall clock. A future-dated file already on disk no longer pins the date of every new record.

## Kind
bug_fixing

## Context
SYMPTOM: memory_write and memory_supersede on 2026-11-01 produced .coding/knowledge/spec/2027-01-11-mnemo2-type-scale-has-four-sizes-meta-body-title.md, .coding/knowledge/how/2027-01-11-review-mnemo2-ui-changes-with-the-preview-page.md and others, all dated 2027-01-11. The user confirmed 2026-11-01 is the real date; some earlier session ran with a clock set to January 2027 and wrote files with that date.

ROOT CAUSE (probed while planning):
- verified: KnowledgeStore::stamped_date in src/memory/knowledge.rs (around line 610) returns max(wall clock, artifact_date_floor()). artifact_date_floor scans the newest YYYY-MM-DD prefix across .coding/knowledge/{spec,decision,bug,how} and .coding/reviews, ignoring only dates more than ~400 days past the wall clock (ceiling = now + 400 days). 2027-01-11 is within that window, so it wins over the correct 2026-11-01 for every new record.
- verified: the floor was added for an earlier symptom (BUG "knowledge exports back-dated by stale OS clock", backlog d7b2e722): every export carried filename date and created = "2026-09-01" regardless of the record's real date. That was attributed to a stale OS clock. A single constant date across many sessions suggests a pinned clock in code instead (for example a fixed test clock or a cached timestamp in a different write path); the worker must check that before deciding the floor is unneeded.
- verified: ls .coding/knowledge/*/ shows prefixes from 2026-08-22 to 2027-01-11, with 336 files on 2027-01-11 and 109 on 2027-01-07.

DECISIONS:
- New records are stamped with the wall clock date. Files on disk never move the date of a new record forward. Remove the artifact floor (stamped_date, artifact_date_floor, scan_dir_max_date, valid_floor_date if unused) unless the investigation finds a real need; if it finds a code path with a pinned clock (the 2026-09-01 symptom), fix that path instead and say so in the report.
- Do NOT rename or re-date existing files: slugs are referenced by supersedes links and plan/review notes. Existing misdated files stay as history.
- Replace the tests that encode the floor (write_dates_from_artifact_floor_when_clock_stale, clock_ahead_of_artifact_floor_wins, supersede_successor_never_backdates_below_floor) with tests of the new rule.

REGRESSION TEST: in src/memory/knowledge.rs tests, `write_uses_the_wall_clock_even_when_a_future_dated_file_exists`: create .coding/knowledge/spec/2027-01-11-old.md, build KnowledgeStore::with_clock pinned to 2026-11-01 (1_793_491_200), write a record, assert the rel path starts with the 2026-11-01 date and created = "2026-11-01". Today it fails (gets 2027-01-11).
