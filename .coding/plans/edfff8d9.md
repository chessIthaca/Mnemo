# Plan: Interrupted turns must not silently drop in-flight tool calls

## Goal
Eliminate the app-runtime bug where a user message or Stop arriving while a turn's tool calls are in flight silently drops calls (no result block, no error, nothing in the agent's context — observed instances in .coding/knowledge/bug/2026-12-30-interrupted-turns-silently-drop-in-flight-tool-c.md). After the fix: every tool call ends in an explicit result (success, error, or recorded cancellation) in BOTH the UI and the conversation history; bookkeeping mutations (memory_*, backlog_*, complete_step, file_write) either complete or visibly fail; a user message never cancels a tool batch (drain), and hard stops cancel with visible, context-recorded results.

## Kind
implementation

## Context
Audit 2026-12-30 (files read: turn.rs, dispatch.rs, loop_impl.rs, context.rs, turn_resolve.rs, ipc/agent.rs, ipc/events.rs, InputBar.tsx, useAgentEvents.ts, agentEventReducer.ts):

- Root cause A (primary): src/agent/turn.rs post-stream block (~:1336) ends the turn for ANY stop_reason BEFORE the tool batch executes. A regular user message (AgentCommand::Prompt -> StopReason::Steer via StopReason::fold, loop_impl.rs:409) arriving mid-stream therefore silently cancels the complete batch, while the same message arriving after stream-end drains it (the between-call safe point ~:1680 breaks only for hard stops). That sub-second timing asymmetry = the observed nondeterminism (instance 2: shell ran, sibling backlog_add didn't; instance 5: whole batch never ran).
- Root cause B: the same block handles orphaned calls with UI-ONLY synthetic "not run" ToolResult events (backlog 63cbc20f) and pushes the assistant message with tool_calls: vec![] — the model's context never records the cancelled calls, so it cannot know to re-issue them (violates "context must reflect what actually ran").
- Root cause C: src/agent/dispatch.rs dispatch_with_interrupt (~:481-530) DROPS the tool future on Interrupt/Cancel mid-execution — bookkeeping mutations (backlog_add, complete_step, file_write) can end half-applied or unapplied (instances 1-3); spawn_blocking work completes untracked in the background.
- Correct precedent to extend: the between-call safe point + post-call hard_stop (turn.rs ~:1680, ~:2009) already push "interrupted: not run" tool_results into messages; summarize_with_interrupt_aborts_on_interrupt (context.rs:1318) is the select!-with-cmd_rx pattern.
- Frontend instance 4 (call text echoed into the user's follow-up message): mechanism unconfirmed — candidates: transcript assembly on interrupt (frontend/src/hooks/agentEventReducer.ts, useAgentEvents.ts streaming buffers, InputBar.tsx handleSend ~:205-337) or model-side repetition of unrecorded calls via the raw echo (acc.take_raw()). Pin down in step 1.
- TurnResolveLatch (src/runtime/turn_resolve.rs) audited: resolves backlog items, not tool results — not implicated.
- Design decision (recorded in step 2): hybrid — steers drain (never cancel a batch); hard stops cancel visibly with context-recorded results; mid-execution interrupts grace-drain fast calls (2s) and cancel slow ones with explicit results.
- Test infrastructure exists: src/agent/tests.rs has mid-stream command-injection patterns (ask_user_interrupt_returns_error ~:4989, deny_all_latches_and_skips_remaining_tool_calls ~:4389); frontend vitest suites in frontend/src/hooks/*.test.ts.
