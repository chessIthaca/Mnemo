# Plan: Anthropic conversation-history caching (3rd breakpoint)

## Goal
Make direct-Anthropic sessions cache the growing conversation history: relocate the volatile system tail into the final message and add the 3rd cache_control breakpoint on the conversation prefix, so cache_read_input_tokens grows with the conversation and input cost per turn drops (~0.1x on cached history).

## Kind
implementation

## Context
Source: .coding/reviews/2026-09-09-provider-comms-review.md finding 3 (LOW). Symptom: direct-Anthropic sessions re-bill the growing conversation history at full input price every request (cache reads bill at ~0.1x) — only 2 of 4 breakpoint slots used (system head + last tool).

ROOT CAUSE (verified by reading src/provider/anthropic.rs build_request_json :228-362): the turn loop pushes the volatile tail (workflow state/progress/memories, src/agent/turn.rs :2295) + the byte-stable CONTEXT_FOOTER (:2296) as trailing SYSTEM messages; build_request_json hoists them into system[1..]. Anthropic's cache-prefix order is tools -> system -> messages, so the per-turn-mutating tail invalidates EVERY message-history breakpoint on every turn (the design note at :319-325 documents this deliberately). A naive 3rd breakpoint would miss every turn + pay the 25% write premium.

FIX DESIGN (verified against docs.anthropic.com/en/docs/build-with-claude/prompt-caching, fetched 2027-01-10):
1. RELOCATE the post-head system blocks into the FINAL message's content as trailing text blocks (after its real blocks). system becomes [head] only (fully stable, breakpoint 1 unchanged). The final message may be a user-text message OR a tool-result carrier — appending text blocks after tool_result blocks is valid Messages-API shape.
2. Breakpoint 3 = cache_control {"type":"ephemeral"} on the LAST REAL block of the final message (the block just before the relocated tail blocks). This is the docs' "static prefix + varying suffix" pattern: the cached prefix covers tools+head+history+current real content; the volatile tail is the uncached varying suffix. The docs' multi-turn example marks the final block; ours sits just before the varying tail.
3. 20-block lookback (docs): the next request's breakpoint walks back at most 20 positions; a run of consecutive tool_use blocks counts as ONE position, likewise tool_result runs — so our loop's requests (assistant reply + coalesced tool runs + new content + tail = a few positions) always find the previous write. Tests assert the breakpoint sits on the final message's last real block (never 20+ blocks back).
4. Thinking blocks cannot be directly marked with cache_control (docs) — walk back past thinking/redacted_thinking blocks when stamping; skip breakpoint 3 if no markable block.
5. AUTOMATIC CACHING (top-level cache_control) EVALUATED AND REJECTED: the docs' "Common mistake" section states it places the breakpoint on the last cacheable block — with our shape that is the varying volatile-tail block, i.e. a fresh write every turn and never a read. Explicit placement before the varying suffix is the documented fix. Record as DECISION.
6. 4th breakpoint NOT added: post-relocation the final block IS the varying tail — a breakpoint there hits the same trap; breakpoint 3 already covers the current turn's content.
7. Minimum cacheable size (512-4096 tokens by model) is a silent no-op below the threshold — no size guard needed; breakpoints cost nothing extra (docs).

Acceptance: multi-turn direct-Anthropic sessions show cache_read_input_tokens > 0 growing with the conversation — runtime verification depends on the separate 'Parse Anthropic cache usage fields' backlog item (NOT landed; no cache_read_input_tokens handling in anthropic.rs today). This plan's verification = request-body tests asserting breakpoint placement + cargo test --workspace green.

Test anchors: existing tests pinning current shape — messages_do_not_carry_cache_control_when_system_has_volatile_tail (:2182, replaced by new-behavior test), the system-hoisting test asserting body["system"] (:1979), last_tool_has_ephemeral_cache_control (:2152, unchanged). 43 tests in the module (1753-2857) — run the suite and fix any assertion broken by the new final-message shape.
