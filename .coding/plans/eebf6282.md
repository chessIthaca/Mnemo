# Plan: Inventory the Mnemo1-only code and settings left in the core

## Goal
An evidence-backed inventory (.coding/analysis/2026-11-11-mnemo1-only-core-code.md) that says, for every candidate in the core library and the Mnemo2 settings surface, whether it is Mnemo1-only and can go, a kernel feature that stays, or a settings key that now does nothing — so removal steps can be written from evidence.

## Kind
research

## Context
WHY: Mnemo1 (frontend/ and the mnemo-app binary with src-tauri/src/ipc/) was deleted on 2026-11-11 (commit 674702df, merged as 6748f8c4 on wt/mnemo). Code in the core crate `mnemo` (src/) that only the Mnemo1 shell called is now dead weight, and some settings Mnemo2 still shows no longer do anything. The user asked to plan this cleanup. This plan only INVENTORIES; it changes no code. The removal plan is written from its report.

THE HARD RULE — the core is a public library, not just Mnemo2's engine: README "Embedding the kernel" documents the `kernel`/`headless`/`app` feature slices and examples/second_consumer.rs; tests/boundary.rs keeps src-tauri on the public surface. "Mnemo2 does not use it" is NOT enough to remove something. Classify with these criteria:
- REMOVE: reachable only from the deleted Mnemo1 shell — no caller in src-tauri/**, src/headless/**, examples/**, the `app`/`headless` public API or another live core path; only its own unit tests use it. Also Mnemo1-UI-only shapes (DTO fields only the React UI read).
- RETIRE-SETTING: a config key or settings field that nothing live reads or enforces any more, or that Mnemo2's UI shows but no code path acts on. Note every place to remove it: src/config/*, src/config/settings_dto.rs, src-tauri/src/mnemo2/*_settings.rs, and the Mnemo2 page in mnemo2/src/components/*. The config files do not use deny_unknown_fields, so removed keys in users' existing config.toml are ignored on load.
- KEEP: reachable from the Mnemo2 host (src-tauri/src/mnemo2/**, src-tauri/mnemo2-app/**), the headless engine, examples, or a general kernel feature an embedder could use (for example per-turn model routing, which Mnemo2 turns off with skip_turn_routing but is still a kernel feature). Say why in one line.
- UNSURE: the evidence does not settle it; state the exact question for the lead.
