# Plan: Backlog items silently deleted after the Mnemo2 rebuild

## Goal
Find what deleted 78 backlog items, make sure nothing in Mnemo2 or the engine can drop pending or in-flight backlog items again, and protect the file against whole-file rewrites that lose entries.

## Kind
bug_fixing

## Context
Why: the lead found `.coding/backlog.jsonl` with 78 deletions while merging. The lead restored it from git (nothing had been added since the last commit) and kept the 09:38 version at `C:/Users/carst/AppData/Local/Temp/claude/C--Mnemo/35c96c7c-c02f-47e2-872b-8e33eed626ea/scratchpad/backlog-0938.jsonl` for comparison; the committed version is `git show HEAD:.coding/backlog.jsonl` (104 lines).

Verified facts:
- verified: the 09:38 file kept 26 items (5 done, 16 in_flight, 5 pending) byte-identical and removed 78 (60 done, 11 pending, 7 in_flight); the removed items are not the first or last lines (not a truncation) and statuses alone do not separate them.
- verified: Mnemo2 had just gained a Backlog section in the Plans tab: `src-tauri/src/mnemo2/backlog.rs` (commands backlog_items/add/edit/remove/reorder/set_deferred/clear_finished, each opening `mnemo::app::backlog::BacklogStore` fresh on `<project>/.coding/backlog.jsonl`) and `mnemo2/src/components/BacklogSection.svelte` + `mnemo2/src/lib/backlog.ts`. The section shows pending items and offers reorder (drag or up/down) and "Clear finished".
- verified: `BacklogStore` (`src/app/backlog.rs`): `reorder(&[ids])` (~line 578), `clear_finished()` (~882), `remove`, `set_status`, and `reload_from_disk` before mutations; other engine code also uses the store (`src/app/tool/workflow/backlog.rs` — the workflow's backlog tools — and `src/app/workflow/mod.rs`).
- verified: a previous bug of the same class: `.coding/knowledge/bug/2026-08-31-backlog-jsonl-clobbered-to-empty-by-stale-in-mem.md` (stale in-memory state persisted over committed entries).
- assumption: the likely culprits are (a) `backlog_reorder` sending only the items the section shows and `BacklogStore::reorder` dropping ids it was not given, (b) `clear_finished` treating more statuses as finished than intended, or (c) an engine path (workflow backlog tool or run-all/linkage reconcile) rewriting from a partial in-memory list. Verify each against the 09:38 file before changing code.

Required behaviour:
1. Reproduce: find the operation that, applied to the committed 104-line file, yields exactly the 09:38 file (compare item ids). Record the root cause with file:line in your report.
2. Fix it so that no UI or engine operation can remove a pending or in-flight item except an explicit single-item remove; `reorder` with a subset of ids must keep every item it was not given, in their relative order; `clear_finished` removes only finished (done/failed/cancelled) items.
3. Guard: `BacklogStore`'s save refuses (and logs) a write that would drop a pending or in-flight item that is not an explicit removal, so a future bug fails loudly instead of losing work.

Regression test: `reorder_with_a_subset_keeps_every_other_item` in the test module of `src/app/backlog.rs` (or, if the root cause is elsewhere, `<root-cause>_never_drops_pending_items` next to the culprit): start from a store with done, pending and in-flight items, run the culprit operation as the UI or engine calls it, and assert every pending and in-flight item survives. It must fail before the fix. Add a test for the save guard.

Verification: `cargo test --lib app::backlog` and `cargo test --lib`, `cargo test --manifest-path src-tauri/Cargo.toml --features mnemo2 --lib mnemo2::backlog`, both clippy runs, and in `mnemo2/` `npx vitest run` if the frontend changes. Never start a dev server or any command that does not exit on its own. Do not modify the real `.coding/backlog.jsonl`.
