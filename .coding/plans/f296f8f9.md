# Plan: Worker git gate: refuse git stash on the shared stack

## Goal
Executor workers cannot push, pop or drop entries on the shared stash stack, through either the git tool or the shell. Recovering a known stash commit by its SHA stays possible, and the refusal tells the worker what to do instead.

## Kind
bug_fixing

## Context
WHY: `refs/stash` is shared by every worktree of a repository. Workers run in parallel worktrees (.worktrees/pool-N) of the same repo, so a worker's stash pop takes whatever is on top: another worker's WIP, or a months-old stash in the lead checkout. Memory record: BUG d210f28c "workers' git stash is shared across all worktrees" (2026-11-20), and the rule "never use git stash; park work as WIP commits". The user asked for the gate to block stash without a SHA.

WHERE: src-tauri/src/mnemo2/team/guardrails.rs:
- `executor_gate_rules()` (~:184). Today it explicitly ALLOWS `"subcommand":"stash"` on the structured `git` tool (an Allow rule placed before the action deny), and its shell/job_start loop has no stash rule.
- `EXECUTOR_GIT_DENY` (~:148) is the refusal text for integration commands.
- `executor_prompt()` (~:14) is the executor identity text.
The structured git tool (src/tool/agent/git.rs, STASH_ACTIONS push/pop/drop/list ~:116) runs `git stash push|pop|drop|list` with no ref argument, so on the shared stack every pop and drop is unsafe.
Existing tests: src-tauri/src/mnemo2/team/tests.rs, `executor_gate_denies_*` (~:240-300) through the `executor_denies(tool, args)` helper. One current assertion expects `{"subcommand":"stash","action":"push"}` to be ALLOWED; it must flip to denied.

DECISIONS:
- Structured git tool: deny stash push, pop and drop for executors (any carrier: subcommand "stash" with action push/pop/drop or no action, which defaults to push; subcommand "pop"/"drop"; action "pop"/"drop"). Keep `stash list` allowed. The tool has no ref parameter, so there is no safe pop or drop through it.
- shell and job_start: deny `git stash` when bare, and `git stash push|save|pop|drop|clear|store|branch`. Deny `git stash apply` UNLESS its argument is a full or abbreviated commit SHA (7 to 40 hex characters), the recovery path for a known dangling commit. Allow `git stash list`, `git stash show ...` and `git stash create`, which are read-only or create no stack entry. Reuse the SHELL_CMD_PREFIX / SHELL_GIT machinery, so `git -C dir stash pop`, chained commands (`cargo test && git stash pop`), escaped newlines and the like are all caught.
- A separate refusal text for stash (not EXECUTOR_GIT_DENY): "The git stash stack is shared by every worker checkout of this repository, so a stash can be popped by another worker. Park work as a WIP commit on your branch instead (git commit -m \"wip\"), and to prove a test red, edit the fix out temporarily. To recover a known stash commit, use git stash apply <sha>."
- Executor prompt: one added sentence, "Never use git stash: the stash stack is shared with other workers; park work as a WIP commit." The audit guardrails already exclude git and shell entirely, so they need nothing.
- Only executor workers are gated. The lead and the user are unaffected.

REGRESSION TEST: `executor_gate_refuses_the_shared_stash_stack` in src-tauri/src/mnemo2/team/tests.rs. Without the fix it fails, because `{"subcommand":"stash","action":"pop"}` and the shell command `git stash pop` are both allowed today. It asserts denial for every refused form above (structured and shell, including `git -C x stash pop`, `cargo test && git stash`, `git stash apply` with no argument, `git stash apply stash@{0}`), allowance for `git stash list`, `git stash show -p`, `git stash apply 78b29bbd` and `git stash apply` with a 40-hex SHA, and that the refusal message names the WIP-commit alternative.

VERIFY (each alone): `cargo test --workspace`; `cargo clippy --workspace --all-targets`; `npm test --workspace mnemo2`; `npm run check --workspace mnemo2`.

## Acceptance scenarios
- An executor worker's git tool call {subcommand: stash, action: pop} is refused with the shared-stash message naming the WIP-commit alternative.
- An executor worker's shell command `cargo test && git stash pop` is refused; `git stash list` and `git stash apply 78b29bbd` run.
- The lead's own git stash use in its checkout is unaffected.

## Bug
Parallel workers share one git stash stack (every worker checkout is a worktree of the same repo, so refs/stash is global). On 2026-11-20, symVec01's `git stash pop` applied hostToken01's stash in the wrong checkout; hostToken01's work survived only as a dangling commit, and its next pop would have applied an unrelated Oct 31 stash with about 59 conflicted paths. The executor gate allows stash through the structured git tool and does not cover `git stash` in shell/job_start at all.
