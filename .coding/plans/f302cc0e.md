# Plan: file_edit read-receipt cites land on the lines they cite

## Goal
A from_read cite always edits exactly the lines it cited from that read, however many ops come before it in the array. A cite whose cited lines were already changed by an earlier op in the same array is refused with a re-read steer, and nothing is written.

## Kind
bug_fixing

## Context
Reported on 2026-11-02. Worker memoryPaths122 hit it on deepseek-flash: a batched file_edit with several read-receipt cites into one file briefly corrupted store.ts, MemoryView, PlanTab and FilesTab. For example, new store actions landed inside openTrace's object literal, according to the memory record "Stale read-receipt cites in a batched store.ts edit". The worker noticed only through a svelte-check cascade and repaired the files by hand. The user asked for it to be fixed. A procedural memory "Read-receipt freshness check for batched file edits" records the current workaround; supersede it once this lands. No existing BUG record covers this (searched record_type bug).

Root cause, probed by the lead:
- verified: `sed -n 1246,1290p src/tool/agent/edit_ops.rs`. resolve_read_anchors validates each from_read cite against the CURRENT (pre-op) bytes with read_registry::resolve, then swaps it for `EditOp::Line(LineOp { verb: Replace, start: lines[0], span: Through(lines[1]), .. })` that still carries the ORIGINAL line numbers.
- verified: the apply_ops doc comment (edit_ops.rs, just below) says "Line ops are matched against the content AS LEFT by the preceding ops". So a cite after any op that changes the line count replaces the wrong lines, and its validation already passed on the original content, so nothing fails.
- verified: `sed -n 538,547p src/tool/agent/file_edit.rs`. prepare_edit_ops calls resolve_read_anchors once on the whole array before apply_ops.
- verified: multi_edit already refuses the same file twice in its files array (src/tool/agent/multi_edit.rs ~line 175: "appears twice — merge its ops into one entry"). The repeated-file problem is within one file's ops array.
- The tool schema (file_edit.rs ~line 908) documents that compact line ops use the coordinates left by preceding ops. That contract stays. Only from_read cites are in the coordinates of the read they cite.

Decisions:
- Cite ranges are interpreted in the cited read's coordinates, which are the file as it was before this call's ops. While applying the array in order, translate each cite's [start, end] through the line-count changes that earlier ops made above it, so it lands on the lines it validated. Anchors and compact line ops keep their current semantics, and the call stays atomic.
- If an earlier op in the same array already changed any of a cite's lines (overlap), refuse the whole call. The message names the cite and tells the model to re-read or split the edit.
- Several disjoint cites into one file in one array remain allowed.
- The tool description gets one sentence saying from_read ranges are in the cited read's line numbers, unlike compact line ops.
- Regression test (required to close): in src/tool/agent/file_edit.rs tests, mint one receipt for a file. Then send one ops array: first an op that inserts 3 lines near the top, then a from_read cite of a lower range. Assert the cited lines are replaced and nothing else changed. It fails today because the replacement lands 3 lines too high. Add tests for the overlap refusal and for two disjoint cites with a deletion between them.

Verification: from the repo root, `cargo clippy --all-targets -- -D warnings` and `cargo test --lib`; and `cargo build --manifest-path src-tauri/Cargo.toml --bins`.

## Acceptance scenarios
- An ops array that inserts lines near the top and then cites a lower range from an earlier read replaces exactly the cited lines; the rest of the file is unchanged.
- A cite whose lines were already changed by an earlier op in the same array is refused with a re-read steer, and the file is untouched.
- Two disjoint cites plus a deletion between them in one array all land correctly.
- Compact line ops and verbatim anchors behave exactly as before; root clippy and lib tests pass, including the new regression test.

## Bug
A file_edit ops array that cites several read-receipt ranges of one file (from_read + lines) applies later cites to the wrong lines once an earlier op in the same array has added or removed lines. It silently corrupts the file while every check passes.
