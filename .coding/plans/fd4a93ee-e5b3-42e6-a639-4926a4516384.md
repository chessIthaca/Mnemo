# Plan: Phase 6a — Structural perf: spawn_blocking for FS/search/sandbox (Perf H1)

## Goal
Fix Performance H1 (structural/multi-agent scalability): offload all synchronous file-system I/O in the async agent tools onto tokio's blocking thread pool via tokio::task::spawn_blocking, so concurrent multi-agent tool use cannot stall the async runtime. Affected tools: file_read, file_edit, file_write, file_append, search, describe_image, and the sandbox validate/validate_for_creation calls each invokes. Each tool's blocking work (sandbox validate + the std::fs op) runs inside a single spawn_blocking closure that owns its inputs and returns the ToolResult, preserving identical behavior (same validation, errors, caps, line-ending handling). The two optional items in the step (Rust delta coalesce, memory read pool) are explicitly deferred with written justification (coalesce is a larger cross-cutting change to the just-hardened event contract; read-pool is "if needed" with no measured contention today). cargo test + npm test + tsc --noEmit must stay green; existing per-tool unit tests must pass unchanged.

## Context
Parent: Architecture review remediation, step 25 (Phase 6a). Finding = Performance H1 (structural/multi-agent scalability): blocking FS/search on the async runtime. Tools run as `async fn execute` but do SYNCHRONOUS disk I/O (std::fs::{read_to_string,read,write,create_dir_all,metadata}), blocking tokio workers under concurrent multi-agent tool use. Shell/git already use tokio::process::Command (async). No spawn_blocking anywhere in the codebase today (confirmed via search). 

Affected production paths (non-test std::fs calls inside async execute):
- file_read.rs:101 read_to_string
- file_edit.rs:234 read_to_string, :245 write
- file_write.rs:105 create_dir_all, :128 write, :174 read_to_string (post-write diff)
- file_append.rs:114 OpenOptions, :130 metadata
- search.rs:52 metadata, :167 read_to_string (per matched file)
- describe_image.rs:67 std::fs::read
- sandbox.rs:50 validate() / :93 validate_for_creation() are pub fn (sync) doing canonicalize on every call, invoked from inside each tool's async execute. Cheap (one canonicalize) but still a syscall on the async runtime.

The tool execute signatures: `async fn execute(&self, args: serde_json::Value) -> ToolResult` (impls of the Tool trait). Each returns ToolResult. The blocking work is validate(path) + the fs op.

Scope decision (the plan step gates the extras): CORE = spawn_blocking for all FS tools + search + sandbox validate (H1 fix). DEFERRED with written justification = (a) Rust delta coalesce before fan-in — the step says "optional"; it's a bigger change to events.rs/turn.rs with ordering/backpressure subtleties and cross-cuts the event contract just hardened in Phase 5c, so defer to a dedicated pass; (b) memory read-connection pool — step says "if needed"; current memory uses a single connection with WAL (read/write split already noted as a strength), N is modest, no measured contention, so defer until a pool is shown necessary. Both deferrals are explicit, justified, and within the step's wording.

Approach for the core: wrap each tool's blocking work (validate + the std::fs op together, returning the result) in tokio::task::spawn_blocking. Pattern: move the owned inputs (args, self-clone of immutable config, sandbox Arc) into the closure, do validate+fs, return (ToolResult). Avoid spawning for the cheap-but-async parts. Keep behavior identical (same validation, same errors, same caps). Tests are sync (call execute().await in #[tokio::test] or via the existing test harness) — spawn_blocking works under the multi-thread runtime the tests already use (need to confirm the test runtime flavor). Existing per-tool unit tests must stay green.

Risk: spawn_blocking closures must be 'static + Send; the Sandbox is held by the tool (likely Arc<Sandbox>) and is Send+Sync, so cloning the Arc into the closure is fine. Args are serde_json::Value (Send). Need to confirm the Tool trait's execute is called on a multi-thread runtime (it is — AgentLoop runs on tokio). Verify tests use #[tokio::test] (multi-thread) or that spawn_blocking works on current-thread (it does — spawn_blocking runs on the blocking pool regardless of runtime flavor, but current-thread runtime has a blocking pool too; default 512 threads).

cargo test (508+), npm test (78), tsc green at start. On branch feat/bookkeeping-tools-autorun.
