# Plan: Split mnemo2/src/lib/store.ts (3,019 lines) into per-concern modules behind an unchanged facade

## Goal
`mnemo2/src/lib/store.ts` stops being a god module: core state, pure layout math and worker view mapping, preferences, browser, workbench, navigation, board, indexing, team sync, lead connection, team/worker actions, project lifecycle, external lead and open-worker each live in their own module under `mnemo2/src/lib/store/`, `store.ts` keeps every public export and the same `actions` object, no component or existing test changes, and `npm test` (vitest) and svelte-check stay green.

## Kind
implementation

## Context
WHY. Architecture review finding ARCH-3 (Medium): `mnemo2/src/lib/store.ts` is one 3,019-line module (verified unchanged at ba6c266f) mixing one global `writable<AppState>` (`app`), about 40 module-level mutable singletons (leadTransport/leadUnlisten/leadSessionToken, teamTransport/teamUnlisten/teamToken/teamSyncTimer, boardTransport/boardToken/boardSyncTimer, indexingTransport/indexingToken, externalLead*/openWorker* listeners and tokens, workbenchTransport/diffRequest/diffSyncTimer, browser* state, preferenceSave/preferenceTimer, deletionFlow/deletionUnlisten, the worker thread/activity maps), lead-pane layout math, toasts, project lifecycle, and 95 actions. leadState.ts (809 lines) and teamState.ts (688 lines) already prove the pure-reducer pattern; this plan applies it and gives every stateful concern its own module.

WHAT EXISTS TODAY (verified). store.ts exports exactly: SESSION_START_MS, createInitialState, app, currentProject, selectedWorker, needsYouCount, MIN_LEAD_WIDTH, MIN_WORKBENCH_WIDTH, maxWorkbenchWidth, clampWorkbenchWidth, MIN_BOARD_WIDTH, MIN_BOARD_OUTPUT_WIDTH, BOARD_DIVIDER_WIDTH, maxBoardWidth, clampBoardWidth, defaultBoardWidth, OLD_WORKER_STATUSES, isOldWorker, actions. 94 files import from it (components import `actions`/`app`/`currentProject`/`needsYouCount`/`SESSION_START_MS`/`selectedWorker`; 16 `store.*.test.ts` files plus leadState.test.ts import `actions`, `app`, `createInitialState`, the width functions). Tests mock the engine modules by relative path (`vi.mock("./leadEngine")`, `./teamEngine`, `./projectEngine`, `./boardEngine`, `./workbenchEngine`, `./runtime`, `./sounds`, `./uiLog`, ...). Two import-time side effects exist and must still run exactly once when store.ts is imported: `void loadSoundToggles();` right after `app` is created, and the `app.subscribe(...)` that hides/shows the native browser pane (it reads browserTransport/browserTabWantsPane/browserPaneShown). `resetDemo()` (an action used by tests) resets all module state and must keep doing so. `actions.initTheme` is `applyStoredTheme` imported from ./theme.

RULES (non-negotiable).
S1 NO behavior change. Move code; do not rewrite it. Keep the order of awaits, `app.update` calls and timers inside every function, the same debounce delays (25 ms, 200 ms, ...), the same texts. Do not fix anything you notice; list it in your report.
S2 Public surface frozen: the list of store.ts exports above and the set of keys of `actions` stay identical (step 1 adds a characterization test that pins both); no component (.svelte) and no existing test file changes.
S3 State ownership: a module-level `let` is private to the ONE module that owns it and is never exported or imported (an ES `let` export is a read-only binding for importers). Other modules reach it through small exported functions. Named accessors used by this plan: `bumpLeadSession(): number` in lead.ts (does `leadSessionToken += 1`, returns the new value; replaces every `leadSessionToken += 1` in openProject, closeProjectNow, retryLead and resetDemo), `getTeamTransport(): TeamTransport | null` in team.ts (replaces the direct `teamTransport` read in confirmCloseProject), `hasPendingPreferences(): boolean` and `discardPendingPreferences(): void` in preferences.ts (replace `if (preferenceSave)` and the `preferenceSave = null; clear preferenceTimer` pair), `disconnectBrowser(): Promise<void>` in browser.ts (the browser half of today's disconnectWorkbench in the same order: `browserToken += 1`, unlisten all, clear the transport and the two flags, then `await browser.close().catch(() => {})`; workbench.ts's disconnectWorkbench keeps the diff half and calls it).
S4 Imports are acyclic. Layers, lowest first, a module may import only from lower layers or the same layer's earlier entries: L0 layout, workerView, core; L1 preferences, board, indexing, browser; L2 workbench; L3 team, navigation; L4 lead, teamActions; L5 externalLead; L6 project; L7 store.ts. If a cycle seems unavoidable, break it by moving the smaller function down a layer or by passing a function parameter, and say so in a one-line comment. Check by reading the import lines; no tool is installed for it.
S5 vi.mock compatibility: new modules import the engine/helper modules from the same files (`../leadEngine`, `../teamEngine`, `../projectEngine`, `../boardEngine`, `../indexingEngine`, `../workbenchEngine`, `../browserEngine`, `../externalLeadEngine`, `../runtime`, `../sounds`, `../uiLog`, `../workerSelection`, ...) and never re-wrap or re-export them, so every existing `vi.mock` keeps applying.
S6 Import-time side effects run exactly once when store.ts is imported, in this order: `app` creation, then `void loadSoundToggles();` (core.ts), then the browser visibility subscription (browser.ts). store.ts must import browser.ts so the subscription is installed.
S7 Types: reuse the existing types from `../types`, `../teamState`, etc.; add no new exported type except where a step names one. No `any`.

HOW TO VERIFY (every step). Worker worktrees have no mnemo2/node_modules (known; see the HOW records on svelte-check in worktrees): run vitest with `npx vitest run` from `<your checkout>\mnemo2` (it resolves the hoisted `C:\Mnemo\node_modules`), and svelte-check with the main checkout's shim from `<your checkout>\mnemo2`: PowerShell `& C:\Mnemo\mnemo2\node_modules\.bin\svelte-check.cmd --tsconfig ./tsconfig.json`. Also run `node scripts/assert-no-production-mock.mjs` from `mnemo2`. The shell tool may kill commands after about 300 s: run long commands detached or in smaller pieces. `git diff --check` must be clean. No Rust file changes in this plan. Keep scratch files under an absolute path outside every checkout (never inside C:\Mnemo or your worktree).

ORDER. The four steps all rewrite store.ts, so they run strictly one after another (the lead dispatches the next only after the previous merged). Each new module file is created by exactly one step.

OUT OF SCOPE: behavior changes; new features; splitting leadState/teamState; touching components; ARCH-8 (large Svelte components); the five other findings of the review.
