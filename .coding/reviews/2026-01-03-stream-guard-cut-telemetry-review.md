### Findings

**Low 1 — `chars_before` underreports once the repetition-guard buffer is trimmed (src/provider/openai.rs:1171).**
The call site passes `response_text.chars().count()`, but `response_text` is the R10 repetition-guard buffer, not an accumulator: after every text delta it is re-bounded by `bound_repetition_buffer` (openai.rs:1427-1432; `REPETITION_BUFFER_CAP = 2048` bytes, trimmed to the last 600 bytes once over — src/provider/stream.rs:390-425). For any guard cut firing after ~2KB of answer text has streamed, `chars_before` therefore reads ≈≤600 instead of the true count — a cut 20K chars into an answer is misreported as an early one, actively misleading for exactly the post-hoc diagnosis this field exists for (the plan step itself says "accumulated answer chars", and the Rust/TS doc comments promise "answer characters streamed before the triggering delta"). The primary motivating scenario (invisible cut at delta start, `chars_before = 0`) is unaffected. Fix: pass `est_completion_chars` (openai.rs:1051, maintained at :1183-1184, unbounded, TextDelta-only — precisely the accumulated answer chars, already in scope at the call site) instead of `response_text.chars().count()`. No unit-test change required; optionally note the source in the `chars_before` doc comments.

**Low 2 — misindented fixture line (frontend/src/components/views/LlmTraceView.test.ts:45).**
The added `guard_cut: null,` uses 2-space indentation; every sibling property in the `detail()` fixture uses 4. (Adjacent, pre-existing and NOT introduced by this change — optional cleanup while touching the constructor: src/provider/trace.rs:531 `raw_tool_calls: None,` is indented 4 spaces against 12-space siblings; the new `guard_cut: None,` on the next line is correct.)
