## Verified fixes

### LOW 1 — status map invalidated on Settings save — FIXED
`replace_servers` (src/mcp/mod.rs:448-458) clears the status map after clearing connections: `self.connections.lock().await.clear();` then `self.status.lock().await.clear();`. The Settings page can never render "connected" for a connection the manager no longer holds, and a removed server's row cannot resurface. Lock order is clean: the connections guard is a temporary dropped at the end of its statement, then status is taken ALONE — no nesting, no inversion. Regression test `replace_servers_invalidates_the_status_map` (mod.rs:950-980) pins the exact contract: connect → save → `statuses().await.is_empty()` → reconnect → `connected && restarts == 0` (a save is correctly NOT a restart). The test fails without the fix (stale row survives the save).

### LOW 2 — connect failures record `last_error` — FIXED
`ensure()` (mod.rs:504-528) wraps the connect block (factory spawn → `initialize` → `tools/list`) in an async block; on failure it acquires the status lock, records `connected = false` + `last_error = Some(e.to_string())` (the transport error text, audited in round 1 (c) as free of env values/headers/args), drops the guard, and propagates the error. The success path (mod.rs:539-554) still clears `last_error`, so the lifecycle stays consistent — the Settings card's "error: …" line now renders for a DOWN server, not just failed calls. Regression test `failed_connect_records_last_error_for_the_status_line` (mod.rs:912-947): down at handshake → `last_error` contains the failure text, `connected == false`, `restarts == 0`; up → success clears the error, `restarts` still 0. Fails without the fix (no status entry exists → `find().unwrap()` panics).

### Semantic refinement — `ever_connected` (first success after failed connects is NOT a restart) — CORRECT
Verified all four sub-points:
- **(a) Private + off the wire.** `ever_connected: bool` (mod.rs:363) has no `pub`. `ServerStatus` derives only `Debug, Clone, Default` — no `Serialize`, so it cannot be serialized directly. The IPC wire type `McpServerStatusWire` (src-tauri/src/ipc/mcp.rs:89-97) maps only the four pub fields plus `name` and `idle_timeout_secs` (the latter from the def via `server_def`), copied field-by-field in `mcp_status` (:118-125). A repo-wide search shows `ever_connected` appears in exactly 4 places, all inside src/mcp/mod.rs (:363, :543, :547, :549) — never in src-tauri or frontend. The frontend `McpServerStatus` interface has exactly the 6 wire fields. No leak.
- **(b) Restart semantics preserved.** `status_tracks_connections_failures_and_restarts` (mod.rs:879-909) still asserts `restarts == 1` after a call failure then reconnect (`reestablished = entry.ever_connected && !entry.connected` — first connect set `ever_connected`, the failure set `connected = false`, so the next success counts exactly once), and `idle_timeout_expires_stale_connections_lazily` (mod.rs:849-876) still asserts `restarts == 1` after idle expiry. The refinement itself is pinned by the LOW 2 regression: a first-ever connect failure then success keeps `restarts == 0` — under the round-1 suggested `!entry.connected` logic the `or_default` entry would have made `reestablished == true` and the test's `assert_eq!(s.restarts, 0)` (mod.rs:946) would fail. The "restarted after a crash" agent-window note therefore never fires for a server that never ran.
- **(c) Lock discipline.** Every nested acquisition in the changed code is connections→status: ensure expired branch (:497-498), ensure error path (:521-525), ensure success path (:539-554), call_with_info gap path (:656-658), call_with_info success/error paths (:664-676). `replace_servers` takes connections then status sequentially (temporary guard); `statuses()` takes status alone. No path acquires status→connections, so no inversion is possible. No awaits occur while holding the status lock — all status-lock holds are pure field sets/reads followed by a drop. (The connections lock held across the connect block remains pre-existing, per-manager serialization, documented at mod.rs:366-375.)
- **(d) Doc comments accurate.** `ServerStatus` doc (:343-346) describes exactly the four public semantics; `ever_connected` doc (:357-362) states it is private, not part of the wire surface, and explains the re-establishment vs. first-ever-connect distinction. `call_with_info` doc (:627-636) correctly describes the vanish-retry/gap path and the restart-note surface.
