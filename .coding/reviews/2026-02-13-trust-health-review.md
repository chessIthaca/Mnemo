## Findings

### LOW 1 — Stale status after a Settings save: `replace_servers` drops connections but leaves `connected=true` in the status map
- **Where:** src/mcp/mod.rs:441-444 (`replace_servers`)
- **What:** `replace_servers` clears the connections map but never touches the status map. The Settings page refreshes status immediately after Save (`refreshStatus()` in McpSection.tsx), so it will render "connected · N tools" for a connection the manager no longer holds — until the next agent call to that server happens to refresh `last_used`/state. A server *removed* from the config keeps its status row forever, and if the same name is re-added later, the stale row (old `tool_count`, old `last_error`, possibly `connected=true`) resurfaces instantly, contradicting the `mcp_status` doc ("Entries appear only for servers the manager has seen traffic for this session" — the entry persists across the save that invalidated it).
- **Fix:** in `replace_servers`, after clearing connections, set `connected = false` on every status entry (or clear the whole status map — it is session-scoped and a save invalidates every connection it describes). A one-line loop under the status lock; no new lock-ordering concern (status alone, no nested acquisition).
- **Severity rationale:** LOW — cosmetic/UX-only, self-heals on the next call, no correctness impact on calls or restart counting (a save is correctly NOT counted as a restart).

### LOW 2 — A failed connect (e.g. the Settings Test button against a down server) never records `last_error`, so the card's "error: …" line cannot appear for connect failures
- **Where:** src/mcp/mod.rs:490-492 (`ensure` connect path)
- **What:** `ensure()` writes to the status map only on connect *success* (:503-514); connect failures (factory spawn error, `initialize`/`list_tools` errors) propagate without touching status. `mcp_test` connects through `server_tools` → `ensure`, so a failed Test leaves the status entry absent (never-connected server → no line at all) or stale ("connected" from before). The plan/PLAN.md promise a per-card "error: …" line; today it can only ever show *call* failures (`call_with_info`'s error path), which is a smaller audience than the docs imply.
- **Fix:** in `ensure()`, wrap the connect block so a failure records `connected = false` + `last_error` (the same transport error text — audited in (c): server name, command, URL/status, server-controlled messages; no env values/headers/args) before propagating. The success path already clears `last_error` (:511), so the lifecycle stays consistent.
- **Severity rationale:** LOW — the error is still surfaced prominently in the Test result area; only the new status line misses it.
