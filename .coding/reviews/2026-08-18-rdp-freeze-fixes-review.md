## Findings

### F1 — [bugs · MEDIUM] The 2s exit timeout is shorter than `BrowserManager::close()`'s *normal* budget → spurious timeouts orphan the headless Chromium process

`src-tauri/src/main.rs:614-616` bounds the whole teardown in `run_with_timeout(2s)`. But `BrowserManager::close()` (`src/browser/mod.rs:555-592`) legitimately needs more than 2s in ordinary (non-wedged) conditions:

1. `close()` first awaits `self.state.lock()` (`src/browser/mod.rs:560`) — which can be held for an entire headless-Chromium **launch** (`ensure_browser`, "Callers hold the state lock", `src/browser/mod.rs:204-208`). Exiting while an agent is mid-`browser_open` parks the teardown behind a multi-second spawn.
2. `kill_browser` (`src/browser/mod.rs:612-625`) retries `Arc::try_unwrap` up to **50 × 100 ms = 5 s** while an in-flight CDP op holds a browser clone, then `owned.kill().await` waits for process exit — Chromium shutdown alone can exceed 2 s with pages open. The doc comment itself says "the kill can take up to ~5s" (`src/browser/mod.rs:556-558`).

So the timeout fires not only on a wedged compositor but on plausible *normal* exits (agent actively using the browser). On timeout the main thread proceeds, the process exits, and the detached teardown thread is killed mid-flight — if it is still in the `Arc::try_unwrap` loop (or the kill was issued but the thread died before it mattered), **the Chromium child is never killed**: chromiumoxide 0.7 never sets `kill_on_drop` (per the repo's own verified Review L2 note, `src/browser/mod.rs:597-599`) and Windows does not reap children on parent exit. That reintroduces exactly the L2 leak (live Chromium holding locks on its throwaway profile dir) that this teardown exists to prevent. The `eprintln!` at `src-tauri/src/main.rs:618-621` ("the OS reaps the browser/WebView2 processes") is wrong for the separate headless Chromium *process* — the OS reaps the app's own HWNDs, not an independent child process.

Note the tradeoff itself (bounded exit vs. guaranteed kill) is the intended one from the diagnosis (R5) and is right — a wedged exit must not hang forever. The problem is the constant and the missing kill fallback.

**Fix (pick one or both):**
- Raise the bound above `close()`'s documented worst case (e.g. 10 s covers lock-behind-launch + 5 s retry + kill).
- On timeout, still guarantee the kill: fire a best-effort synchronous terminate of the child (kill via the process handle / `taskkill` by pid if `BrowserManager` exposes it) before returning from the `RunEvent::Exit` handler.

### F2 — [bugs · LOW] `env_flag_enabled` treats `"false"`, `"no"`, `"off"` as ENABLED

`src/webview_args.rs:35-40` — only `None`, `""`, and `"0"` are falsy. An RDP user who naturally writes `MYHARNESS_DISABLE_WIN_OCCLUSION=false` (or `no`/`off`) silently gets the flag **on**: the renderer stays unthrottled while occluded and burns background CPU/GPU — the exact opposite of the intent. The test at `src/webview_args.rs:64-71` covers `"yes"` but never a negative word. Suggest a case-insensitive falsy set `{"", "0", "false", "no", "off"}` + tests for `"false"`/`"FALSE"`. (Truthy-anything-else is fine for an opt-in flag.)

### F3 — [correctness · LOW] A `Busy`-dropped rect update has no guaranteed re-send (stale child-webview layout)

`src-tauri/src/ipc/browser_webview.rs:193-206` drops the update when `try_lock` contends (`RectOutcome::Busy`), on the stated assumption "the next ResizeObserver tick re-sends the current rect" (`:176-178`, `:210-212`). That re-send is not guaranteed: `ResizeObserver` fires only on *size* change and the window listener only on window resize — a *position* change fires neither, and after occlusion the single pending coalesced rAF (`frontend/src/hooks/useBrowserRect.ts:83-96`) fires once on restore. If that one restore-time report lands `Busy` (e.g. it races the previous wedged controller call unwedging and releasing the lock), no further report is ever sent: the child webview sits at a stale rect until the next window resize, panel resize, or tab remount (`browser_webview_ensure` re-applies the rect, `src-tauri/src/ipc/browser_webview.rs:156-165`). Narrow window — the RDP switch-back usually ships a resize storm that re-reports — but when it hits there is no self-heal. Cheap hardening: on `Busy`, stash the desired rect in a lock-free side slot that the next command to acquire the mutex applies before doing its own work (apply-on-unlock), or have the frontend retry a dropped report once on a ~100 ms timer.

Related (accepted-by-design, no action): `ensure`/`navigate`/`set_tab_visible`/overlay commands still `lock().await` and can queue behind a wedge — the diagnosis scoped the try_lock change to `set_rect` only, and those are one-shot user-initiated calls, not a per-frame stream.

### F4 — [correctness · LOW] A panic in the worker's `sink` permanently disables resize handling

`src/thread_util.rs:71` — `sink(v)` runs bare in the worker loop; the (correct) care taken to never hold the slot lock across user code means a *panic* in `sink` unwinds out of `loop` and kills the thread. After that, `submit` keeps overwriting the slot (`thread_util.rs:34-37`) with no consumer: the agent-chat webview silently stops tracking window resizes for the rest of the session (no crash, no log). Today's sink is `let _ = resize_sink.set_size(size)` (`src-tauri/src/main.rs:124-128`) — Result errors are swallowed, so a panic requires a bug inside tauri/wry — unlikely, but the failure mode is silent permanent degradation of the very fix. Suggest `std::panic::catch_unwind(AssertUnwindSafe(|| sink(v)))` (log + continue) in the worker loop. Conversely the `expect("slot poisoned")` in `submit` is unreachable-by-construction (the lock is never held across `sink`, so the worker cannot poison it) — fine as defense, just noting it would panic on the event loop if ever hit.

### F5 — [constitution · LOW] `useBrowserRect`'s doc comment is orphaned — the exported hook is now undocumented

`frontend/src/hooks/useBrowserRect.ts:4-25` (the hook's original JSDoc, including `@param areaRef`) is immediately followed by the new `rafCoalesce` JSDoc (`:26-32`) and then `rafCoalesce` (`:33`). TypeScript attaches only the *last* preceding doc block, so the hook's JSDoc dangles and the exported `useBrowserRect` (`:56`) carries no doc comment — against the project rule that all public functions have doc comments. Fix: move `rafCoalesce` (+ its doc) above the hook's doc block, so the hook's JSDoc sits directly above `useBrowserRect` again.

### F6 — [constitution · LOW] R2 regression test never exercises the wiring; the defect can silently reappear

`frontend/src/hooks/deltaFlush.test.ts` tests only the pure `shouldFlushSync` predicate. Deleting any `flushNowIfOverCap(next.length)` call from the three delta branches (`frontend/src/hooks/useAgentEvents.ts:233,240,252`) — i.e. reverting the actual R2 fix — leaves all 199 tests green, as does removing the `cancelAnimationFrame` branch (`:199-202`). Constitution: every fixed defect needs a regression test that fails without the fix. The wiring is testable without a DOM: mock `../lib/tauri` (`onAgentEvent` handler capture), stub `requestAnimationFrame`/`cancelAnimationFrame` like `useBrowserRect.test.ts`'s `makeRaf`, dispatch a synthetic `text_delta` payload >64 KiB, and assert the store received the append *without* a frame firing (and that a pending frame id gets canceled). Same gap class, smaller: `rafCoalesce`'s tests are behavioral and good; `useBrowserRect`'s effect wiring (immediate mount report, cleanup cancel) is untested but lower-risk.

## Security — no findings

- **No env→Chromium-args injection.** `MYHARNESS_DISABLE_WIN_OCCLUSION`'s *value* is never interpolated into the args string — only its truthiness selects a fixed constant (`src/webview_args.rs:23-32`, `src-tauri/src/main.rs:71-77`). An attacker who can set env vars gains only the occlusion-disable flag (a performance/behavior flag, no security impact), and `std::env::set_var` still clobbers any pre-set `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`, so the direct injection vector stays closed.
- **CDP gate unchanged.** `--remote-debugging-port=9222` is appended iff `cfg!(debug_assertions) || browser_inspection_enabled()` (`src-tauri/src/main.rs:71-72`), and `browser_inspection_enabled` still fails closed (`src-tauri/src/main.rs:43-48`). Release builds without the opt-in get `--disable-extensions` (+ optionally the occlusion flag) only.
- Nit (no action): a second `--disable-features=` flag added later would silently override rather than merge with `CalculateNativeWinOcclusion` (Chromium keeps the last) — fine while there is exactly one.

## Verified correct (review-focus items with no finding)

- **Latest-wins worker (`src/thread_util.rs:45-74`)** — textbook condvar slot: predicate re-checked under the lock before `wait` (no lost wakeup: a notify landing while the consumer is mid-`sink` is harmless because the consumer re-loops into `take()`); `submit` releases the lock before `notify_one`; the lock is never held across `sink` (poison cannot originate in the worker); latest value always survives (submit overwrites unconditionally, consumer always drains before waiting again — the final size after a storm is never lost). Behavior tests `delivers_values_in_order` + `coalesces_to_latest_while_sink_is_busy` are genuine (would fail on a queueing or lost-wakeup implementation).
- **R2 flush state machine (`frontend/src/hooks/useAgentEvents.ts:197-207`)** — over-cap path cancels the pending frame *then* flushes, so no stale frame leaks; `flushBuffers` sets `rafIdRef.current = 0` first and clears all three maps in one synchronous pass (single-threaded JS, no reentrancy into the buffers via the store actions), so no double-flush; below-cap calls `scheduleFlush()` identical to the old code. The pre-existing quirk where the *non-delta* branch (`:257`) flushes without canceling a pending frame (stale frame later fires an empty flush and clobbers the newest id → one extra no-op frame) is unchanged by this diff and harmless (data is never lost; unmount re-flushes). **No remaining unbounded buffer path:** every buffer (per-agent text/reasoning, per-(agent, tool-index) args) is checked on each of its own appends; each is capped at 64 KiB + max single fragment, and every flush clears all buffers.
- **R5 ordering** — trace flush stays outside and before the timed teardown (`src-tauri/src/main.rs:560-568` vs `:590-622`); `agent_chat.try_lock` (`:610-612`) cannot block exit; the detached-thread semantics of `run_with_timeout` (`src/thread_util.rs:82-92`) are correct (silent `tx.send` failure when the receiver is gone, `recv_timeout` distinguishes completion). Only the constant vs. `close()`'s budget is wrong (F1).
- **One-frame resize latency (R1)** — by design: during an interactive drag the webview bounds lag the window by ~a frame (possible brief edge artifact), self-correcting, newest size never lost. The event-loop handler now only does `submit` — no controller call on the UI thread (`src-tauri/src/main.rs:131-135`).
- **`try_apply_rect` (`src-tauri/src/ipc/browser_webview.rs:189-206`)** — behavior-preserving vs. the old lock-and-compare on the uncontended path (`Applied`/`Noop` semantics identical, stored rect updates even with no webview handle); both new `#[tokio::test]`s are real regressions for the Busy/Noop paths. The `Busy` drop-recovery hole is F3.
- **`rafCoalesce` (`frontend/src/hooks/useBrowserRect.ts:33-54`)** — mount report stays immediate (`:80`), cleanup cancels the pending frame (`:101`), resize listener removed via a stable named handler (`:95-96,100`); the `pending = 0` sentinel is safe (browser rAF ids start at 1; the injected test raf does too). Behavioral tests cover coalescing, cancel, and re-arm.
- **Doc comments / warnings (Rust)** — every new public item is documented (`thread_util` module/struct/methods, `webview_args` module/functions, `RectOutcome` + variants, private `try_apply_rect` too); no `#[allow(...)]` added anywhere; `RectOutcome`'s derives and the non-`must_use` `let _ =` discard cannot warn. (Per the implementer's green `cargo test` under `#![deny(warnings)]`.)
- **vitest include completeness (task item 6)** — enumerated every `*.test.ts` under `frontend/` (18 files, via `^import .*vitest` search): all 18 are matched by the include patterns — `src/components/settings/**/*.test.ts` covers `AdvancedSection` + `types`; the hooks entries cover `useAgentStore`, `useAgentStore.preview`, `deltaFlush`, `useBrowserRect`, `rightPanelViews`; the rest are listed verbatim. **No `*.test.ts` file is missing from the list**, and no `*.test.tsx` / `*.spec.ts` files exist anywhere in the repo.
