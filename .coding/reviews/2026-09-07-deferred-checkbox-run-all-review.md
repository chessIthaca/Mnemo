### Finding

**LOW 1 — `run_all.rs` module doc overstates the adoption semantics (src-tauri/src/ipc/run_all.rs:12-13).**

The doc says deferred items "are NEVER selected, **adopted**, or counted by a run". The *adopted* leg is false for the shipped behavior: `adopt_orphaned_in_flight` (called from `backlog_run_all` at src-tauri/src/ipc/backlog_cmds.rs:450, before the total count) requeues **all** orphaned `InFlight` items to `Pending` regardless of the flag — deliberately, per the plan's stated rationale (skipping adoption would strand a deferred orphan `InFlight` with no recovery; the flag survives the requeue — `transition` only mutates status/note — and then excludes the item from selection). The same sentence's "a `deferred` item stays `Pending`" is also a simplification: the tool and the UI checkbox can defer an `InFlight` or terminal item, and the flag never changes status (the `backlog.rs` field doc and the tool schema describe this correctly).

Risk: a future reader trusting the module doc "fixes" `adopt_orphaned_in_flight` to skip deferred items — reintroducing the stranding the deliberate non-change avoids. Fix is doc-only: reword to "never selected or counted", and note that orphan adoption still requeues deferred items (the flag survives and excludes them from selection). Note the README paragraph and the `run_all_dispatch_next` doc comment are already accurate ("never selects or counts") — only the module header carries the overstated wording.

### Verification detail (all eight review-focus areas)

The store test `deferral_survives_status_transitions_and_requeue` pins the flag surviving transition + requeue.

**2. Run-start edge — correct, no spin possible.** `backlog_run_all` (backlog_cmds.rs:437) counts `total` over `items()` (live items only — soft-deleted excluded) with the filter `Pending && !deferred`; the error fires only when `total == 0 && no live pending item exists`. An all-deferred backlog creates the run state with `total: 0`, then `run_all_dispatch_next` → `next_pending_eligible()` → `None` → the pre-existing `end_run` arm (run_all.rs:1618-1622) clears the run state and emits `backlog://changed`. No spin: `run_all_dispatch_next` is invoked exactly once from `backlog_run_all`; every later invocation is event-driven from a resolved turn, and an all-deferred run has no turn. Auto-feed is force-disabled at run start (backlog_cmds.rs:466), so the two loops cannot fight.
