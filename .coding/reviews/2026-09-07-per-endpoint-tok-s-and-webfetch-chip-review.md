### Findings

**LOW 1 — Documentation sync: README.md:77 doesn't mention the new web_fetch URL chip.**
The ToolCard bullet reads "Tool-card file links open the file in the Files tab — except `file_edit` chips, which open that file's diff in the Diff tab" — the natural home for the new user-facing behavior (a `web_fetch` chip now opens the fetched URL in the system browser via shell open). PLAN.md was updated for feature B, but feature A has no README coverage. Fix: extend the line-77 bullet, e.g. "…; a `web_fetch` chip opens the fetched URL in the system browser".

**LOW 2 — StatsView.tsx:128: React row key `mb.model + (mb.endpoint ?? "")` can collide across distinct rows.**
Concatenation without a separator: model `"glm"` + endpoint `"5.3"` and model `"glm5.3"` + NULL endpoint both yield `"glm5.3"`. The SQL GROUP BY guarantees (model, endpoint) pairs are unique, but the derived key is not — colliding rows make React warn and can mis-diff rows on re-render. Fix: a collision-free key, e.g. `JSON.stringify([mb.model, mb.endpoint])` (rows are stable per query, so the array index also works).

**LOW 3 — openExternal.ts:35 / toolCardPaths.ts:582: the raw URL string, not the normalized href, reaches the OS opener.**
Both `webFetchUrl` and `openExternal` validate with `new URL(...)` but pass/return the ORIGINAL string. Inputs that parse to http(s) yet differ from their normalized form — `http:example.com` (no slashes), embedded tabs/newlines (stripped by the URL parser), `https:\\example.com` (backslashes) — reach explorer/open/xdg-open verbatim and may fail to open or resolve differently than the browser would. Not exploitable: the Tauri shell plugin passes the URL as a single argv element (no shell parsing → no command injection), and the http(s)-only check blocks dangerous custom protocol handlers (zoommtg:, ms-*, steam:, …). In practice web_fetch only fetches literal `http(s)://`-prefixed URLs (web_fetch.rs:144-151), so chips over successful fetches are well-formed; the gap only shows on chips over failed/rejected fetch args. Hardening: return/pass `parsedUrl.href`.

**LOW 4 — Message.tsx:536-541: keyboard activation of the URL chip is suppressed by the header's keydown handler (pre-existing pattern, extended).**
The ToolCard header is a `<span role="button">` whose onKeyDown (Enter/Space → `preventDefault()` + toggle expand) also fires for keydowns bubbling up from the nested chip `<button>`s. Pressing Enter on a focused URL chip therefore toggles the card's expand instead of opening the link — preventDefault on the bubbled keydown cancels the button's default click activation. The new chip mirrors the existing file-link chips (consistent), but keyboard users cannot activate any chip. Fix: in the span's onKeyDown, return early when `e.target !== e.currentTarget` (repairs file chips and URL chips together).
