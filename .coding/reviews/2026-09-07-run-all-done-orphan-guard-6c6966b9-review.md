### Design decisions — validated, not just accepted
- **(a) "Any commit after the checkpoint"** — sound. The single-committer invariant holds: the per-item checkpoint runs in `run_all_dispatch_next` before the item is stamped InFlight, and the next dispatch happens only from `on_main_turn_resolved` after the current item resolves; the harness's own `commit_success` runs at resolution (after which the item is no longer InFlight), and reviewer subagents are read-only. `commit_success_impl` no-ops on a clean tree — the died-after-commit case leaves exactly one commit after the checkpoint. The plan gate (steps checked) + commit gate together match the died-between-commit-and-finish window; either alone would be too weak (steps check before review/commit; mid-work commits exist). The alternative ("commits referencing the item id") is correctly rejected — agent commits don't reliably carry the id.
- **(b) No separate marker** — correct: the death window (agent's own commit → finish) contains no harness-controlled point; the commit anchored by the per-item checkpoint IS the evidence.
- **(c) Safe default = requeue** — implemented on every failure path (see above). Research-plan orphans (no commits) still requeue — the commit gate cannot verify commit-less work; conservative and documented in the helper's doc comment.
- **(d) Lock discipline** — verified below.

### Lock discipline (review check 3)
- Drain: run_all lock released → store lock held only for the `(note, plan_id)` snapshot (block-scoped) → `orphan_work_landed` with NO locks held (the project-root lock is held only for the `root.clone()` — the guard temporary drops at the end of the `let` statement; the git subprocess runs via `spawn_blocking` with zero locks) → store lock re-taken, still-InFlight re-verified → transition. The drain's re-verify checks only InFlight (not ownership) — correct by construction: its item is the ending run's own `current_item`, same shape as pre-change.
- Adoption: 3 phases. `main_agent_top_plan_id` (manager/agent_loops/workflow locks) is taken BEFORE the store lock in both phases — same ordering as pre-change. `single_in_flight` (std Mutex) is read under the store lock — same as pre-change and required by the prior review's TOCTOU pin (pointer read after the store lock). Phase 2 (git evidence) holds no locks. Phase 3 re-verifies still-InFlight AND still-unowned (fresh single pointer + active plan re-read) under the lock before each transition.
- No lock is held across the git subprocess anywhere; no new lock-ordering edge exists (the store lock never nests with the manager/agent_loops locks; the root lock is only ever held for a PathBuf clone). Residual TOCTOU windows (a manual resume flipping `top_plan_id` during Phase 3's held store lock; a single-pointer set mid-loop) are unchanged from pre-change and benign — dispatch only picks Pending items and the store lock serializes item reads.

### MockGit log arm vs commit arm (review check 4)
The commit arm does `commits.push(msg); head_sha = format!("sha{}", commits.len())` — a commit landing at index k gets sha `sha{k+1}`; the initial commit is `abc123` at index 0; `sha1` never exists (the first push from the 1-commit initial mock yields `sha2`). The unit test's sequence (checkpoint on clean tree → `abc123` → false; commit → head `sha2`; `abc123..HEAD` → true; `sha2..HEAD` → false; `deadbee` → Err) is consistent with the mapping. The comment block documenting the mapping is accurate.
