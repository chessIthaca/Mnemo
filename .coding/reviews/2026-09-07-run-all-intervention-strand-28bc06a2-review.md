**2. LOW — Stale-latch edge: the keep-InFlight disposition doesn't verify the run still holds the item.**
`from_run_all` is derived from the latch id alone (run_all.rs:2168). If the run is drained between the halt and the resolution — steer lands → the main agent is cancelled/crashes before the soft-stop turn resolves → `drain_run_all_on_main_exit` ends the run (events.rs:677–679) → a later main-agent turn consumes the lingering latch — the handler keeps the item InFlight with the note "the plan stays active, resume to continue", but there is no run and no pointer: requeue refuses InFlight and dispatch requires Pending, so the item closes only via the agent's `backlog_status` tool or a manual stamp. Pre-fix, this same edge requeued to Pending (auto-recoverable). The identity check exists later in the function (2253–2266) but doesn't feed back into the disposition. Suggested hardening: keep InFlight only when the identity-matched run is still active; otherwise requeue (the pointer is gone — exactly the single-dispatch rationale the code itself documents). Narrow window, the end state matches the already-accepted drain design ("item left in flight; work kept in tree; run ended"), and reachability additionally requires a main-agent turn after the exit — hence LOW.

**3. LOW — Hardening: the stop-flag set re-acquires the run_all lock after the identity check.**
`handle_user_intervention` checks identity under one run_all acquisition (2253–2266), drops it, then re-acquires to set the flag (2271–2276). In the microscopic window between the two awaits, the matched run could end and a new run start, and the flag would then stop the new run (which would end after its first item resolves — recoverable, not a strand). The old code had the identical shape (identity check → `end_run` re-acquiring), so this is not a regression; setting the flag under the same guard as the identity check would close it.
