## 2. HIGH — the new regression test retains a select!-order race: the mock stream can exhaust before the Prompt is polled (~12.5% flake per run)

`buffered_prompt_during_compaction_rederives_unattended` (src/runtime/agent.rs:6425-6513) pins the takeover Prompt into the inbox before the summarization returns — that half of the determinism argument is sound (the gate holds `complete()` open until after `cmd_tx.send`, and `Notify` permit semantics make neither wakeup losable; the 10-message setup also clears both noop guards in `summarize_with_interrupt`, context.rs:300-311, so `entered.notified()` cannot hang). But the buffering itself happens in `summarize_with_interrupt`'s select! loop (src/agent/context.rs:328-365), which only STARTS after `complete()` returns — i.e. after the gate opens. From that point on, BOTH branches are ready in every iteration:

- `stream.next()` — the GatedMockProvider returns an already-materialized `futures::stream::iter` (TextDelta, Finish; agent.rs:6414-6421), always `Poll::Ready`;
- `cmd_rx.recv()` — the Prompt sits in the channel.

tokio::select! (unbiased) picks randomly among ready branches each iteration. The loop breaks only when the stream returns `None` — three stream-branch picks (TextDelta → Finish → None→break); the cmd branch never breaks the loop. The Prompt is therefore buffered unless select! picks the stream branch in ALL of iterations 1-3 while the Prompt waits unpolled: **P(fail) = (1/2)^3 = 12.5%**. In the miss case the Prompt stays in cmd_rx, the re-injection loop is empty, and `assert!(!task.unattended)` fails (unattended stayed true) — a clean intermittent failure, not a hang.

Why the round-2 claim doesn't hold: "the takeover prompt is the only ready branch while the provider pends" describes the window BEFORE the select! loop exists — while `complete()` pends, nothing polls anything. The race is entirely post-gate, inside the loop. The gate fixed the first version's race (a prompt landing after the window closes is never buffered); it did not fix the in-loop branch selection.

Impact: production is unaffected — a Prompt that misses the buffering stays in cmd_rx and is handled by run()'s Prompt arm (between-turn Compact path, agent.rs:679-698) with the same re-derivations, or folds into the follow-up turn as a steer (mid-turn path — the documented pre-existing steer semantics). The defect is the test: it is the committed regression test for LOW 2, and the constitution's regression-test contract requires it to pass WITH the fix. At ~12.5% it will red the root gate within a handful of suite runs, and a spurious failure of THIS test reads as "the LOW 2 fix regressed" — a false alarm costing a debugging session. The reported green gate (2083 passed) does not contradict this: one run passes with probability 87.5%.

Fix direction (either):
- Truly deterministic: keep the provider gate, but also gate the STREAM's first event behind a second Notify, released only once the Prompt is provably buffered — e.g. signal the test from the stream's first poll (a third Notify fired from `poll_next`/the first `next()`), then release. While the stream pends, cmd_rx is the only ready branch, so iteration 1 deterministically buffers the Prompt; the short-circuit subtlety (select! may skip polling the stream in the picking iteration) is covered because the poll-signal fires by the following iteration at the latest, by which time the Prompt is already buffered.
- Pragmatic: make the mock stream long (e.g. 64+ TextDeltas before Finish) so P(exhaust-before-cmd) = 2^-65 — effectively zero with the current structure; document that it is probabilistically, not structurally, deterministic.
