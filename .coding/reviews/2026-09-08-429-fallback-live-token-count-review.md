## Findings

### HIGH-1: the headroom rule regresses failover for `fill_rate > 0.5` — including equal-window and much-larger-window alternates

**Derivation.** With no proxy ceiling, `effective_summarize_at = window × fill_rate` (context.rs:156), so the new rule is viable ⟺ `alt ≥ live + alt×fill` ⟺ **live ≤ alt×(1−fill)**. The old rule was viable ⟺ `alt ≥ cur`. The regression slice is `alt ≥ cur AND live > alt×(1−fill)` — non-empty for any fill, and it widens as fill grows:

- **fill 0.6, cur = alt = 128k**: an **equal-window** alternate is rejected once live > 51.2k — but the current endpoint's own operating band runs to 76.8k (its threshold). A 60k conversation: 60k + 76.8k = 136.8k > 128k → rejected. The alternate is held to a stricter bar than the incumbent serving the same conversation.
- **fill 0.75** (valid — settings_dto.rs:279 validates 0.05–0.95; general.rs:738 shows 0.75 in config tests), **cur 128k, alt 200k, live 60k**: old → failover; new → 60k + 150k = 210k > 200k → rejected. The band (50k, 96k] — most of the current endpoint's normal band — loses failover to a 1.56× larger alternate.
- **fill 0.95, alt 1M, live 60k**: 60k + 950k = 1010k > 1M → a one-million-token alternate rejected for a 60k conversation.
- Even at the default 0.5 the slice exists for over-threshold tool-loop conversations (Rule 4 blocks compaction, requests still go out — the 84b5ed69 bug class): alt = cur = 128k, live ∈ (64k, 128k] → rejected where old accepted.

The rejected alternates are all servable: their own compaction fires at their threshold — normal operation, exactly as the incumbent's does. The "one growth step" guarantee is a preference, not a correctness need (the minimal requirement is the immediate serve). The failure mode is the exact symptom class of the bug being fixed: the turn fails once with "no alternate provider found" and later turns keep hammering the rate-limited endpoint. Fails safe (no stall, no data loss), but the feature is silently disabled for valid configurations that previously worked.

**Fix (one line, strictly dominant — accepts everything the old rule accepted AND the mixed-window cases this fix targets):**

```rust
let cur_window = self.context_manager.read().expect("context manager lock").max_tokens();
let viable = if live > 0 {
    alt_cm.max_tokens() >= live + alt_cm.effective_summarize_at()
        || alt_cm.max_tokens() >= cur_window
} else {
    alt_cm.max_tokens() >= cur_window
};
```

plus a regression test (fill 0.75, equal-or-larger alternate, live in the affected band → must fail over) and a doc-comment touch-up (method doc + inline comment). Evidence: loop_impl.rs:1717-1731; context.rs:151-163; settings_dto.rs:279.

### LOW-1: the stored count excludes the per-request system scaffolding — over-accept direction on a first-iteration 429

The store (turn.rs:321) records the top-of-iteration accounting basis (messages + tools overhead), but the request that 429s additionally carries the system scaffolding installed AFTER the store: the stable system head (first iteration only — context.rs:810-816: "the turn loop will INSERT the head at index 0"; counted from iteration 2 via the head-swap path, context.rs:775-786) and the volatile tail + CONTEXT_FOOTER (every iteration — pushed at turn.rs:376-383, popped at :401-404). So a first-iteration 429 under-counts the actual request by the system-prompt block (constitution, workflow state, session primer, memory context — not measured here, but the same scaffolding every request carries). Direction: over-accept (anti-conservative), bounded by the headroom (the alternate's full summarize threshold), and backstopped by the alternate's own preflight/compaction — worst case a clean non-retryable context-overflow error, strictly better than the old always-reject. The store-site comment's "the request built from THIS count" slightly overclaims exactness. **Suggested fix:** extend the field doc (loop_impl.rs:103-110) and the store-site comment (turn.rs:316-320) to state the basis (excludes the per-request head/tail scaffolding; the headroom absorbs it; the alternate's preflight is the backstop). A code change isn't warranted — the basis is the harness's canonical live count (the same basis the summarize trigger uses).

### LOW-2 (pre-existing, adjacent): README.md:60 "only when no other endpoint serves the model"

The 429 sentence says the actionable error surfaces "only when no other endpoint serves the model". Both pre-fix (smaller-window alternate rejected) and post-fix (alternate that can't hold the live conversation rejected), the error can also fire when another endpoint DOES serve the model. Not introduced by this diff, but this change is the natural place for the one-clause touch-up (e.g., "…or when no viable alternate can hold the live conversation"). Evidence: README.md:60; runtime/agent.rs:633-634.

## Bottom line

The mechanism is right and well-tested: the live count is stored at exactly the right point with correct Relaxed ordering, the sticky semantics are preserved, the window fallback is kept, and all three regression tests exercise the changed path with real margins (test (a) verified red pre-fix). The one real problem is the headroom rule's shape: demanding a full growth step of headroom makes the viability bar — live ≤ (1−fill)×alt — stricter than the incumbent's own operating band whenever fill > 0.5, silently disabling failover for configurations the old code served (including equal-window alternates). OR-ing in the old window comparison restores every pre-fix acceptance at zero cost to the fix's target case. With HIGH-1 addressed (plus the two doc LOWs), this is a clean, well-scoped bug fix.
