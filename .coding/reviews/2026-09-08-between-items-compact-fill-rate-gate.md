### Finding LOW-1 — the gate's ceiling provenance (current config) can diverge from the engine's (factory snapshot) after a mid-session settings edit

**Where:** `src-tauri/src/ipc/run_all.rs`, `between_items_compact_gate` (the `state.project.config → general.context.proxy_cache_ceiling_tokens` read).

The gate reads `fill_rate` from the **live loop** and `max` from the **usage event** — both provably the same values the engine's fill-rate path uses (the factory derives `fill_rate` from the CM at `summarize_at()/max_tokens()` and threads the identical value into every loop via `with_fill_rate`, factory.rs:757, and into every rebuilt CM via `context_manager_for`/`set_provider`; the usage event's `max` is the live per-iteration CM's `max_tokens`, turn.rs:344/1709). But the **ceiling** comes from the current config, while the engine's no-override path uses the CM's ceiling — the factory's **startup snapshot** (main.rs:1432; CM rebuilds use `self.proxy_cache_ceiling`, and no settings-save path updates the factory's stored ceiling). After a mid-session `proxy_cache_ceiling_tokens` edit without a restart, the gate computes `min(product, new_ceiling − 32k)` while the engine's in-item path applies `min(product, old_ceiling − 32k)` — the between-items gate fires at a different threshold than the dial the engine actually applies, contradicting the "SAME effective threshold" invariant in that window. (The per-context-override path is the exception: the resolver reads the live config per turn, so per-iteration CMs carry the new ceiling and the gate matches there.)

Impact is bounded: it self-heals on restart, the divergence magnitude is capped by the ceiling delta, and the preflight backstop (window − 32k) still guards the window — the gate is an optimization, never a blocker. But the provenance is mixed (live loop for fill_rate, live config for ceiling), which is exactly the drift class the shared helper exists to prevent.

**Suggested fix (either):**
- (a) Read the ceiling from the same live source the engine used — the main loop's context manager exposes `proxy_cache_ceiling()` — matching the fill_rate provenance; or
- (b) Keep the config read and extend the gate's doc comment to note the mid-session-edit divergence window (the comment currently documents WHAT is read, not that it can diverge from the engine's snapshot).
