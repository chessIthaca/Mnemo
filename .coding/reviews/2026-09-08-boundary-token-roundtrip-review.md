### HIGH

**H1. `file_write` mode="append" bypasses the marker restore — the documented chunked-write path silently corrupts token-containing files.**

- `src/tool/agent/file_write.rs:110-112` — `execute` checks `is_append` and returns `self.append.execute(args).await` BEFORE the restore at `src/tool/agent/file_write.rs:117-125`, so mode="append" never reaches `restore_boundary_tokens`.
- `src/tool/agent/file_append.rs:78-82` — `FileAppendTool::execute` deserializes `FileAppendArgs { path, content }` and writes `content` with no restore (only line-ending normalization).
- Reachability is by design, not an edge case: `file_write`'s schema (`src/tool/agent/file_write.rs:77-81`) instructs "To write a large file, overwrite the first section then append the rest in chunks of under ~5000 characters", and `file_append`'s schema (`src/tool/agent/file_append.rs:53-56`) says the same. Any token-containing file larger than ~5000 chars written via the prescribed chunked workflow lands literal `⟦raw:\uXXXX…⟧` markers in chunks 2+ — read-then-write is NOT unchanged, violating the plan's acceptance ("a fixture containing the token round-trips read → write unchanged") and the review task's explicit check ("verify no path bypasses it (append mode, …)").
- Fix: restore in `FileAppendTool::execute` after deserialization (mirroring file_write/file_edit — covers the mode="append" delegation and any future direct registration), and add a regression test (append a marker-carrying chunk → disk carries the raw token). Also update the FIX wording in `.coding/knowledge/bug/2027-01-07-serving-layer-strips-special-tokens-from-request.md:11` and PLAN.md item 8 ("the file tools (file_write content, …) restore the marker"), which currently read as if all of file_write were covered.

### LOW

**L1. The Responses-API escape has no regression test.** The new request test covers only the chat path (`build_request_json_escapes_boundary_tokens_in_tool_results`, `src/provider/openai/tests.rs:1161+`). The responses path (`message_to_responses_input`'s `Role::Tool` arm, `src/provider/openai/request.rs:548-563`) applies the same escape but is untested — a future refactor of that path could silently drop the escape while the chat-path test stays green. Suggest a `build_responses_request_json` test asserting `function_call_output.output` carries the marker and not the raw token.

**L2. The marker-invariant claim is an overclaim; pathological tokens can nest markers.** `src/provider/boundary.rs:26-27` claims the marker "never contains the raw token (or any configured token) as a substring". The full `\uXXXX` rendering guarantees that only for the escaped payload — the fixed wrapper `⟦raw:` / `⟧` and the hex alphabet can themselves contain a configured token (e.g. a token `raw:`, `a`, or the literal text `\u003c`). Because the escape is a sequential per-token `replace` (`src/provider/boundary.rs:69-80`), such a token would be escaped INSIDE a previously emitted marker, nesting markers and breaking round-trip identity. Realistic boundary tokens (GLM role tags, newline cascades) never overlap the wrapper, so this is theoretical — but either guard it (skip tokens that occur in the wrapper/hex alphabet, or escape single-pass longest-match-at-position) or soften the module-doc/PLAN.md claim to "tokens that don't overlap the marker alphabet".

**L3. The restore accepts hex groups the escape can never emit (mirror-exactness deviation).** `unescape_marker_inner` (`src/provider/boundary.rs:139`) accepts 4..=8-digit groups, but the escape (`{:04x}` over chars ≤ U+10FFFF, `src/provider/boundary.rs:75`) emits at most 6 digits. A hand-written `⟦raw:\u00000041⟧` (8-digit group) is restored to `A` where the stated contract ("the parser must mirror the escape's format exactly") says leave untouched. Impact stays inside the documented collision caveat, so this is strictness-cosmetic — tighten the cap to 6, and fix the function doc at `src/provider/boundary.rs:123` ("1..=8 hex digits each" — the code actually enforces ≥4). Verified safe along the way: 9+-digit runs fail the group parse and are left untouched; surrogate/out-of-range values fail `char::from_u32` and are left untouched; all restore slicing is char-boundary-safe (indices from `find`), no panic paths.

**L4. Regex-mode `old_string` restore changes pattern semantics.** The restore runs before mode dispatch (`src/tool/agent/file_edit.rs:855-859`), so in `use_regex` mode the restored raw token lands in the pattern unescaped (`src/tool/agent/file_edit.rs:768-770` compiles it). The GLM token `<|endoftext|>` as a regex is alternation — an agent that copies the marker from its view into a regex (single-backslash form, which the strict parser restores) gets a pattern that can match a tiny wrong substring (e.g. just `endoftext`) and silently splice `new_string` there — the same silent-corruption class this plan fixes. Literal/line-range/fuzzy modes are correct (verified). Suggest: in regex mode restore to a regex-quoted form of the raw token, or document the limitation in the `use_regex` schema description (`src/tool/agent/file_edit.rs:823`).

**L5. README sync: the `stop_boundary_strings` paragraph predates the round-trip escaping.** `README.md:127` documents the config's stop-list + stream-guard effects but not the new tool-result escaping/restore behavior of the same knob. PLAN.md item 8 is updated; a one-clause addition to the README paragraph would keep the config docs complete.
