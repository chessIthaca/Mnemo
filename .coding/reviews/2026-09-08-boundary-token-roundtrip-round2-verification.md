### L2 — single-pass escape: FIXED
- `escape_boundary_tokens` (src/provider/boundary.rs:67-96) is a single scan over the original content: non-empty tokens sorted longest-first (`sort_by_key(Reverse(t.len()))` :80); at each position the first — hence longest — token with `rest.starts_with(*t)` wins (:84); otherwise ONE char is emitted and the scan advances by `ch.len_utf8()` (:90-92). Emitted markers are never rescanned: `out` is append-only and `rest` only advances over original content, so no configured token can be escaped inside a previously emitted marker.
- UTF-8 safety: `rest[token.len()..]` is char-boundary-safe (guaranteed by the preceding `starts_with` match); the fallback advances by the char's UTF-8 length; all restore slicing uses `find`-derived byte indices at char boundaries. No panic paths.
- Realistic-token behavior unchanged vs the round-1 sequential version: longest-first ordering preserved, and for tokens that don't occur inside marker text, single-pass and sequential replace produce identical output (the existing round-trip / longest-first / multiple-token tests pin this).
- Pathological identity verified by reasoning and tests: `pathological_tokens_do_not_nest_markers` (tokens [endoftext, "a"] — under the OLD sequential replace, the 'a' in the emitted marker's own `raw:` wrapper would be re-escaped, nesting markers and breaking identity; the test asserts the endoftext marker stays intact and the round trip is identity — a genuine red-without-fix test) and `pathological_single_tokens_round_trip` ("a", "raw:", "⟧", "\\u003c", "0f"). The module doc (:24-33) now claims exactly this — "identity for ANY token set, even pathological tokens that overlap the marker's own alphabet" — accurate for the escape→restore round trip, with the pre-existing marker-shaped-text collision caveat still documented separately (:35-37).

### L3 — hex-group cap tightened to 6: FIXED

A 7+-digit run stops the digit loop at 6 and then fails the `\`-check at the next byte, so the whole marker is left untouched.
- Test `groups_longer_than_six_digits_are_malformed` (:366-384) pins the 8-digit case (`⟦raw:\u00000041⟧` untouched) plus the valid 4/5/6-digit range (U+0041, U+1F600, U+10FFFF). The function doc (:173-177) states the 4..=6 mirror-exactness — the round-1 "1..=8" doc error is gone.

### Notes (no action required)
1. **Approval-preview paths don't restore**: `file_write`'s and `file_edit`'s `approval_preview` → `prepare_for_approval` deserialize raw args without a restore, so a token-containing edit's diff preview fails to match (marker `old_string` vs. raw token on disk) and falls back to the raw-args prompt, and a file_write overwrite preview shows the marker where the write lands the raw token. 2. **Residual mirror-exactness nuance** (inside the documented collision caveat): a hand-written 5-6-digit group with leading zeros (e.g. `⟦raw:\u00041⟧`) parses although the escape never emits one (`{:04x}` is minimal-width-padded-to-4). Round-1's prescribed cap-to-6 fix is implemented and pinned; the leading-zero case stays within the accepted "legitimate marker-shaped text is rewritten" caveat.
3. **Escape idempotence** holds for realistic tokens (pinned by `escape_is_idempotent`) but not for pathological tokens that prefix the marker wrapper itself (e.g. a configured token `raw:` re-escaped inside previously escaped output would double-escape). Unreachable in practice — the request layer always escapes the raw stored `Message`, never previously-escaped content; the module doc's "never rescanning emitted markers" claim is accurate for a single pass.
4. **Scope observation**: `memory_write` (knowledge files) also persists agent-authored content without a restore — same class as round-1's accepted scope (the file tools only); knowledge files are agent-authored summaries, not verbatim file round-trips.
