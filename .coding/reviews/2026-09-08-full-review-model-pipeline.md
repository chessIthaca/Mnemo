## Findings

### LOW-1 — 429-fallback viability check compares context windows, not the live conversation size

**Location**: `src/agent/loop_impl.rs:1701–1710` (`try_429_fallback`).

**Symptom**: the check rejects an alternate endpoint whenever `alt_cm.max_tokens() < current_cm.max_tokens()` — the alternate's context *window* vs the current model's *window* — regardless of how many tokens the live conversation actually holds. A 429 on a model served with a 200k window never fails over to an endpoint serving the same model with a 128k cap, even when the live conversation is 20k tokens. The turn then fails once with the "no viable alternate" message and later turns keep hammering the rate-limited endpoint.

**Why it matters**: the doc comment (lines 1660–1663, 1690–1700) justifies the check as "the alternate's context window is smaller than the live conversation" — but the code compares against the *budget* (the current CM's `max_tokens`), not the live token count. The stated failure mode ("would overflow on EVERY later turn for this model id, because the sticky entry persists") does not actually hold: `resolve_turn_provider` rebuilds the alternate's context manager every turn (loop_impl.rs:1193–1204, 1277–1287), so the alternate's own fill-rate summarization fires before overflow on later turns. The only real risk is the *immediate* sticky serve exceeding the alternate's window — which the precise check (`alt_window < live_tokens`) would catch exactly. The current check is a safe over-approximation that silently disables failover for any mixed-window configuration of the same model id (e.g. a proxy capping context below the direct endpoint's). It fails safe (no stall, no data loss — one actionable turn failure, no sticky entry recorded), hence LOW.

**Fix direction**: thread the turn's live token count (from the `TokenAccounting`/turn state, or a `current_tokens()` accessor on the CM) into `try_429_fallback` and accept the alternate when `alt_window >= live_tokens + headroom` (headroom ≈ the alternate's summarize threshold, so the immediate serve plus one growth step fits). Keep the window comparison as the fallback when the live count is unavailable.

## Improvement suggestions (prioritized — nothing broken, concrete gains)

1. **Precise 429-fallback viability (fixes LOW-1, top robustness win).** Thread the live token count into `try_429_fallback` and accept an alternate whose window covers `live_tokens + headroom`. This unblocks failover for mixed-window configurations of the same model id (proxy-capped endpoints), which today degrade to repeated turn failures under a sustained rate limit. Small, test-covered change; the count is already available in the turn's `TokenAccounting`.

2. **Sticky-endpoint expiry / recovery probe** (`loop_impl.rs` `fallback_endpoints`). Once a 429 sticks a model to its alternate, the original endpoint is never retried for the rest of the session — traffic (and cost) stays on the alternate indefinitely, even after the rate limit clears. The flip-back path only triggers when the *alternate* also 429s. Add a TTL (10–15 min) or clear the sticky entry after N successful turns on the alternate, then let the next 429 (if any) re-stick. Cheap: a timestamp/count on the map entry.

3. **Seed spawned-worktree codegraphs from the main graph DB** (`spawn.rs` `spawn_run_all_agent`, lines ~153–155). Every spawned parallel run-all agent pays a cold full code-graph index pass (seconds on a large tree) before its first turn. The worktree is a fresh checkout of `main` — the same content the main tree's graph just indexed. Cloning the main tree's `codegraph.db` into the worktree and running the (content-hash) incremental index would catch the usually-empty delta in milliseconds. Biggest win for parallel run-all dispatch latency; also reduces per-item token spend (the agent's early `graph_search` calls stop falling back to tree walks while the cold index runs).

4. **Dedicated summarization model slot** (`model_resolver.rs` + `context.rs`). Auto-compaction summaries ride the turn's model — often the premium per-state model. The between-items compact in run-all adds one summary LLM call per item, unattended, all night. A `[models.summarize]` slot (defaulting to current behavior — no config, no change) would let users route compaction summaries to a cheaper model. The summary prompt is model-agnostic (structured handoff format), so quality risk is low.

5. **(Minor) Recall-block gist could surface the record's path pointer** (`run_all.rs` `format_recalled_context`, RECALL_BLOCK_GIST_CHARS = 300). Typed titles carry path/commit pointers, but episodic hits' pointers live in the content body — a 300-char gist can cut off before them. Emitting the record's file path (when the record has one) as a fourth field on the `- [tier] title — gist` line would make every hit actionable for the dispatched (possibly lesser-reasoning) model without raising the gist budget.
