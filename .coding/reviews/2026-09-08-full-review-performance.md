## Findings

### LOW 1 — `reindex_files_containing` byte-scans non-source files it can never re-parse (finish-gate escalation path)

- **Location:** `src/codegraph/mod.rs:525-597` (the walk + `std::fs::read` + `bytes.windows(needle.len()).any(...)` scan); caller `src/tool/workflow/plan.rs:1458` (the finish-gate escalation, commit 3d13884 / backlog 648e0ad5).
- **Symptom:** the escalation walks ALL searchable files and reads every one's full bytes to scan for the needle — but only files with a parseable source extension (`extension(rel).is_some()`) are ever re-parsed (`reindex_one`). `should_search` covers `.coding/**/*.md` (only the SQLite DBs are excluded), and this repo alone carries ~2,700 such files. A needle match in a `.md` file leads nowhere: the scan result is discarded for non-source files. On this tree that is the majority of the walk's read volume — pure wasted I/O and scan time on a path that stalls the dispatched agent's turn (the gate runs inside the finish tool call; `spawn_blocking` keeps the executor free, but the agent waits for the result).
- **Why it matters:** the escalation is the last-chance path before a hard finish-gate error that historically sent agents chasing phantom renames (the exact bug 648e0ad5 fixed). Every second it spends reading knowledge/review markdown it cannot act on delays the gate — and the path also runs inside the run-all DISPATCH_LOCK window when a spawned lane's bug_fixing plan finishes (see LOW 2), compounding the serialization.
- **Fix direction:** gate the read+scan on `extension(rel).is_some()` BEFORE `std::fs::read` — the needle is a Rust/TS test-function name; a match in a non-source file is unactionable by construction. Secondarily, the naive `windows().any(|w| w == needle.as_bytes())` scan is O(n·m) per file; `str::find` (Two-Way algorithm, via `std::str::from_utf8(bytes).map(|s| s.find(needle))`) or the `memchr` crate is substantially faster on the 1 MB-capped files that remain. Both are ~5-line changes; the existing regression test (`reindex_files_containing_reparses_despite_fresh_meta`, mod.rs:746) pins the behavior and stays green.

### LOW 2 — parallel run-all fill serializes per-item provisioning under DISPATCH_LOCK; each lane pays a full cold code-graph parse

- **Location:** `src-tauri/src/ipc/run_all.rs:3263-3268` (`run_all_dispatch_next` takes `DISPATCH_LOCK`), `:3540+` (`fill_spawned_window` loops `dispatch_spawned_item` — worktree checkout + checkpoint + `recalled_context_block` + `spawn_run_all_agent` cold index + record + prompt — all inside the guard); cold index at `src-tauri/src/ipc/spawn.rs:140-185` (documented "a cold graph index over the worktree tree").
- **Symptom:** with concurrency N, the fill provisions items strictly one at a time — the lock's own comment prices the selection→record window at "tens of seconds (a worktree checkout + a checkpoint commit + an agent spawn + a cold graph index)" per item. Lane k cannot start until lanes 1..k-1 have each completed their full provisioning, so the "parallel" run's lanes come up serially: with concurrency 4 on a repo this size, the last lane starts minutes after the first. Each spawned agent also rebuilds the entire code graph from scratch (fresh worktree checkout → no gitignored codegraph.db → every source file read+hashed+tree-sitter-parsed), repeating work the main tree's DB already represents for every file unchanged between main and the worktree branch.
- **Why it matters:** this is throughput waste on the headline parallel-run-all feature (48a35ad), not a stall — all heavy steps are `spawn_blocking`'d (UI stays responsive), nothing re-enters the lock (no deadlock; verified the call tree), and for overnight marathons items run long enough that the serialization is a modest wall-time fraction. But it is exactly the "resource contention / serialization points / redundant work" the axis asks about, and it compounds with LOW 1 (a spawned lane's bug_fixing finish gate runs its escalation inside this same lock window).
- **Fix direction (two independent levers):** (a) split selection from provisioning — snapshot/record all N item selections under DISPATCH_LOCK, then run the per-item provisioning (checkout + checkpoint + spawn) concurrently outside it, re-verifying eligibility under the lock before each record if strictness must be preserved; (b) seed each worktree's `codegraph.db` by copying the main tree's DB at provision time — the store is content-hash keyed, so files unchanged between the main tree's branch and the worktree's `main` checkout skip the tree-sitter parse entirely (hash-mismatched files just re-parse; never worse than cold). (b) alone cuts per-item provisioning from a full parse to a read+hash sweep. Neither changes the serialized-landing correctness design (LANDING_LOCK stays).

## Improvement suggestions (prioritized; nothing else broken)

1. **Seed worktree codegraph.db (LOW 2 lever b)** — biggest single win for run-all marathons: eliminates the redundant full tree-sitter parse per spawned item. Content-hash keying makes it safe by construction; measure with a timing log on `spawn_run_all_agent`'s index pass before/after.
2. **Concurrent provisioning (LOW 2 lever a)** — removes the serial lane-startup; matters most for short items and high concurrency (8).
3. **`reindex_files_containing` scan hardening (LOW 1)** — extension gate + `str::find`; also consider capping the escalation's total re-parse count with a note in the gate error (it currently re-parses every source file containing the needle — usually 1-2, but a common identifier like `run_all_dispatch_next` would re-parse many).
4. **Startup (already good; small residual):** first paint is not blocked by indexing (background `spawn_blocking` index, hash-embedder-first with ONNX load off-thread, watcher started after). Optional polish: defer the watcher's initial full-tree debounce pass until after the first background index completes (they coordinate via the indexing flag today — correct, just double-walks the tree on a cold open).
5. **Delta pipeline (already excellent):** Rust-side DeltaBatcher (16ms deadline armed once, 64KiB cap, structural flush, per-agent buckets) + frontend rAF buffering (64KiB cap, 250ms max latency, hybrid flush policy, name-resolution guard) are well-tuned and symmetric. No change proposed; the LOW 5 chunk-list accumulation stays closed per the profile.
6. **Trace/telemetry:** 16 MiB rotating budget with 256 KiB per-entry cap is appropriate; per-request stats writes go through the shared store with brief locks. No action.
