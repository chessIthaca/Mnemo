Exactly the specified placement, mirroring the drain's R2 clear.
- **The assumption holds on every path**: `finish_captured_item_done` (5011-5034) transitions the item Done unconditionally (a commit failure only eprintlns — the plan-loop gate already passed at the caller) and never touches `current_item`, so the pointer is stale by definition when the ours arm runs.
- **The sequential path (no spawned lanes) is unchanged**: `spawned_in_flight = false` → `end_run` — the pre-fix behavior; the clear is redundant-but-harmless there (end_run drops the state anyway).
- **Lock usage**: `as_mut` on the tokio run-state guard is sound (the inner std Mutexes are scoped, no awaits inside the hold); `current_item` BEFORE `spawned` matches the documented invariant (R8). The stop-flag set is a separate, later acquisition — safe (if the run state vanished in between, `as_ref()` → None → no-op; if a lane resolved in between, the next stop-check terminates).
- **The wrong comment is gone**: the arm now carries the correct rationale ("The steered item was just resolved Done above — clear the main lane's pointer BEFORE the wind-down"); the "stays InFlight by design" rationale lives only in `handle_user_intervention`'s arm, where it belongs.
- **The pin**: `end_run_is_gated_on_lanes_in_flight_everywhere` asserts `body.contains("R3-H1: the steered item was just resolved")` — the marker exists verbatim at run_all.rs:3863. The R2 gap (nothing pinned the ours arm's clear) is closed.
- **Termination re-audited with the fix**: the steered item Done + pointer cleared → each lane's terminal resolution/exit reads stop → `any_lane_in_flight` (current_item None + spawned empty after the last entry's removal) → `end_run`. The R3-H1 hang (stale `Some` keeping every end-of-run check true forever) is gone. A second steer doesn't regress (the item is already Done; the latch path re-runs harmlessly).

### R3-L1 — a spawned lane's deferred turn resolution has no flush path → **fix complete ✓**

events.rs:1154-1229 (`try_flush_deferred_spawned_resolutions`) + the two wiring sites:
- **The ordering at both sites**: the Finished arm's child else-branch (738-745: spawned flush, then main flush) and the Exited arm's unconditional flush (783-789: spawned flush, then main flush). Correct — post-main-exit `main_agent_id()` resolves to a lane (verified: `main_agent_id` is the smallest parentless id, src/runtime/mod.rs:137), so a main-flush-first ordering would mis-consume a lane's latch.
- **The Complete gate mirrors the main flush** (1199-1224 vs the main's 1123-1148): failures deliver unconditionally (a failure is terminal); successes deliver only when the lane's OWN workflow is Complete (`agent_workflow_state(&state, lane_id)` — the per-agent sibling, never the main's), else the consumed entry is re-marked via the pre-existing `remark_pending_finished` (turn_resolve.rs:200-205 — undoes exactly the flush's `resolved` insert + `pending_finished` removal). Same API (`flush_deferred_main_failure`, keyed by agent id), same semantics.
- **No deadlock with DISPATCH_LOCK**: the flush sites hold no locks upward (the manager guard is dropped at 663/768; the agent_loops guard at 769 is a statement temporary); the flush's per-lane manager/agent_loops acquisitions are scoped; its deliveries (`on_spawned_turn_resolved` → `run_all_dispatch_next` → DISPATCH_LOCK) wait at most for a concurrent dispatch holder, and dispatch holders never wait on the forwarder (sends are channel sends processed asynchronously, emits are synchronous UI events) — no cycle, no self-deadlock (the forwarder never holds DISPATCH_LOCK at the flush sites; its dispatch_next calls complete before returning).
- **Interaction with the R1 ownership routing**: a lane's own Finished/Error goes through the ownership branch directly (677-706 / 603-632) — the flush only consumes DEFERRED latches (`flush_deferred_main_failure` returns `None` when nothing is deferred), runs in the child else-branch + the Exited arm, and iterates a snapshot of lane ids (no iterator invalidation when a delivery removes entries). A lane removed after the snapshot: its latch was already consumed by its own terminal resolution, or the drain took the entry and the delivery's `on_spawned_turn_resolved` early-returns on the missing entry (the agent is gone; `on_exited` cleared its latch anyway) — benign.
- **The post-main-exit pre-drain window** (the flushes run after `mgr.remove` at 767 but before `drain_run_all_on_main_exit` at 807 sets the stop flag — any delivery reaching `dispatch_next` there would dispatch to a lane, since `main_agent_id()` is now a lane): analyzed **closed on every constructible path**. A lane's deferred latch only becomes deliverable when its descendants clear, and every descendant-clearing event (the reviewer's Finished else-branch, any Exited) runs the lane flush itself, consuming the latch then — failure → delivered; success+Complete → delivered; success+not-Complete → re-marked, and the main flush's own Complete gate re-marks rather than delivers (so even the main flush mis-consuming a re-marked latch post-main-exit is benign churn). The stop flag then gates every post-drain `dispatch_next` caller (all four re-drive tails check stopped first). Note: round 3's claim that the inverse edge "no-ops because the R2 clear guarantees current_item is None post-main-exit" was imprecise about timing — the R2 clear runs in the drain, AFTER the flushes; what actually closes the window is the lane-flush-first ordering plus the Complete gates. That is exactly why the ordering is load-bearing (see LOW-2).

### R3-L2 — `remove_item_worktree`'s early-return ordering could skip the branch delete → **fix complete ✓**

worktrees.rs:104-131:
- **Prune first** (122, best-effort `let _ =`): clears the stale worktree metadata that makes the branch delete refuse ("cannot delete branch used by worktree").
- **Both ops run independently** (123-126): `removed` and `deleted` are BOTH computed before either `?` — the branch delete always runs; the remove's error still surfaces (via `removed?`) but never skips the delete. All callers are best-effort (`let _ =`), so the surfaced error is logged/ignored — correct.
- **The prune does not affect the normal remove path**: `git worktree prune` removes metadata only for worktrees whose directories are gone — a live item worktree and the landing worktree are untouched (`remove_cleans_up_worktree_and_branch` covers the live path; the landing worktree re-provisions itself if its dir ever vanished, worktrees.rs:174-181). Theoretical prune-vs-`worktree add` race (a lane's terminal remove pruning while another lane's dispatch provisions — provision runs under DISPATCH_LOCK, removes don't): a pruned mid-add fails loudly → the fill's skip arm → the item is skipped this pass and re-dispatchable later; self-healing, not corruption.
- **The test exercises the path** (`remove_still_deletes_the_branch_when_the_worktree_is_already_gone`, 259-281): provisions a REAL worktree (real-git tempdir), deletes the worktree directory manually (`remove_dir_all` — the metadata stays), removes, asserts `branch --list` is empty. It fails BOTH without the prune (git refuses `branch -D` on a branch used by a worktree with stale metadata) AND without the independent-ops reorder (the old `?` after the remove returns early, skipping the delete) — the test proves both halves of the fix are required, and passes with them.

## Round-4 findings

### LOW-1. The ours arm's wind-down is not serialized against DISPATCH_LOCK

run_all.rs:3835-3880. The ours determination (3835-3847), the clear (3859-3872), and the wind-down decision are separate run-state holds with no DISPATCH_LOCK — while every dispatch decision (which mutates `current_item` at 2814 and records `SpawnedRun`s in the fill) runs UNDER DISPATCH_LOCK (R4). Two interleavings orphan state:

- **(a)** a concurrent dispatch's `current_item` write lands between the ours check and the clear → the clear wipes the NEW item's pointer: the item is worked by the main agent with no run pointer; its resolution reads `current_item == None` and cannot stamp it Done; it strands InFlight until the next run start's adoption sweep requeues it.
- **(b)** a concurrent fill's `SpawnedRun` record lands between the spawned-read (empty) and `end_run` → end_run drops the run state with the lane's entry in it: the lane's resolution finds no run state and no-ops, its item stays Pending with a stale `wt/runall-*` branch + worktree (the R3-L2 class — the branch blocks every later spawned-lane dispatch of the item; the adoption sweep only cleans requeued InFlight orphans, not Pending items with stale worktrees).

Both windows are microseconds wide and need a between-items compact task or a lane resolution's re-drive to land exactly inside them — not demonstrably reachable in a concrete interleaving (the forwarder is single-tasked, so forwarder-triggered dispatches cannot interleave; the realistic concurrent dispatchers are the compact task and the IPC start task, and the latter refuses while a run is active). But the class is exactly what DISPATCH_LOCK exists to close (R4), and the ours arm is the ONE wind-down that runs while the main agent is alive and dispatchable — `drain_run_all_on_main_exit`'s equivalent clear is safe post-main-exit because `main_agent_id()` is then None/a-lane, so no concurrent dispatch can set `current_item`.

**Fix**: hold DISPATCH_LOCK across the ours-arm wind-down (nothing in the arm calls dispatch_next, so no re-entrancy), or at minimum merge the ours determination into the clear's single run-state hold (read `current_item`, compare against the interrupted id, clear, read `spawned` — one acquisition), which closes (a); closing (b) needs the lock.

### LOW-2. The R3-L1 pin does not pin the load-bearing ordering

run_all.rs, `end_run_is_gated_on_lanes_in_flight_everywhere`: the R3-L1 arm asserts `events.matches("try_flush_deferred_spawned_resolutions(").count() >= 3` — existence of the definition + the two call sites — while the comment above it claims "running BEFORE the main flush". The ordering is the load-bearing part of the fix: post-main-exit `main_agent_id()` resolves to a lane, and a main-flush-first ordering would consume a lane's deferred FAILURE and deliver it through `on_main_turn_resolved` — the main path — while `current_item` is still `Some` (the R2 clear runs later, in the drain at events.rs:807, AFTER the flushes) → the main's item is cross-stamped with the lane's failure disposition (or annotated with it), exactly the R1 defect class the fix exists to prevent. A future reorder of the two flush calls stays green and silently reintroduces the mis-consumption.

**Fix**: pin the ordering at both sites — e.g. within each arm's body, assert the spawned-flush call's index is strictly less than the main-flush call's index (mirroring the existing was_main-before-`mgr.remove` ordering pin in `main_agent_exit_drains_an_active_run_all`).
