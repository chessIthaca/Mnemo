### LOW-2 — Note wording "lane wrote N…" misattributes the common case

`src-tauri/src/ipc/run_all.rs` `end_run` formats `"lane wrote {n} knowledge record(s) — uncommitted in the main tree"`. `KNOWLEDGE_WRITES` is process-global and the store is factory-shared, so the run-window diff counts **main-agent** writes too — and the main agent is the primary writer on the default path: sequential run-all works every item on the main agent, and parallel run-all gives item 1 to the main agent (README:81). A user finishing a sequential run that wrote 3 records reads "lane wrote 3" and looks for lane worktrees that don't exist. The actionable half (records are uncommitted in the main tree) is accurate in every case, and the frontend tooltip is already attribution-neutral — only the note string misleads. Flagged per the review brief; cosmetic, no functional harm.

**Fix:** attribution-neutral wording, e.g. `"wrote {n} knowledge record(s) during this run — uncommitted in the main tree"` (update the doc comments on `RunAllProgress.note`, `run_completion_note`, `knowledge_writes_at_start`, and the `types.ts` doc to match).

### LOW-3 — Version-stamp race can pin stale recall results for the rest of a turn

`src/agent/turn.rs` stamps `state.last_recall_store_version = store.version()` **after** the recall returns, while `MemoryStore::write` bumps the counter at the **top** — before the row is visible (the embed + insert happen between). Interleaving with a concurrent writer (cross-agent — the store is factory-shared): the recall's DB snapshot lands inside the writer's bump→visible window (misses the row), then the stamp reads the post-bump version → the stale results are pinned as current, and every later same-query recall this turn cache-hits and never sees the write — exactly the bug this feature fixes, in a narrow window (the writer's embed duration; sub-ms with the local embedder, real with a slow one). Self-heals at turn end/summarize; pre-fix behavior was strictly worse (never visible within the turn), so this is a residual, not a regression.

**Fix (airtight):** bump the counter at the **end** of each mutating op (after the row is committed/visible) **and** capture the version *before* the recall for stamping (`let v = store.version();` before the recall call; stamp `v`). With bump-after-visibility + pre-read stamp, any write invisible to the snapshot necessarily bumps above the stamped version → forced fresh recall. (Either half alone still leaves a window.)

## Observations (non-findings)

- `end_run`'s doc comment says "Shared by the 5 exit points" but there are 9 call sites — pre-existing staleness outside this delta (the diff didn't touch that comment).
- The tick's piggybacked `void loadList()` uses the default no-op cancellation guard while the tier-filter path passes `() => cancelled` — a fetch resolving after unmount setStates harmlessly (React 18 no-op, no leak beyond one closure). Consistency nit only; the source test pins the current shape.
- `end_run`'s lock-drop window between the diff read and the `= None` clear marginally widens a pre-existing interleaving hazard (a concurrently armed run's state could be wiped by the clear) — unchanged in kind by this diff, and starting a run while one is ending is already UI-gated.
- `update_memory` bumps the version even on a no-op update (`Ok(false)`) — over-invalidation, harmless (one extra recall).
- `KNOWLEDGE_WRITES` counts every agent process-wide, including main-agent writes outside any run — inherent to the process-global design; the run-window diff bounds the count to the run's lifetime. Accepted per plan ("no store-behavior changes beyond the counter").
