## Verdict: FINDINGS (2 high, 6 low)

Performance + data-loss review of the agent communication pipeline (axis 2 of the 2027-01-09 round). Full-tree review at HEAD c18b5d0 (wt/agenticcoding), clean tree. Scope: src/agent/ (turn.rs, context.rs), src/provider/ (openai/ stream + request, anthropic.rs, trace.rs, sse_util.rs), src-tauri/src/ipc/ (state.rs, events.rs, run_all.rs, backlog_cmds.rs), frontend (useAgentStore.ts, polling views). Section 1 ranks latency bottlenecks by end-to-end turn-loop impact; section 2 ranks data/message-loss paths by severity.

### The three data signals, explained up front

1. **ttft_ms=0 for 28,267 of 28,506 rows (99.2%)** — TTFT *is* recorded, but it measures a degenerate window: response-headers→first-chunk. On every LiteLLM-fronted backend (and direct OpenAI/Anthropic) the server only begins the HTTP response when the first token is ready, so headers and the first SSE chunk arrive in the same TCP burst — the window is structurally <1ms. The real first-token wait (upload + prefill + queue) lands entirely inside connect_ms. The extract script's "(0 = unrecorded)" gloss is a misreading: these are genuine 0ms measurements of a useless window. → Finding L1 (HIGH, measurement bug).

2. **"stream aborted — consumer dropped" (45+ occurrences)** — the user-interrupt path working as designed: a hard stop (Interrupt/Cancel/Compact/Clear) mid-stream makes `consume_stream` drop the event receiver; the SSE pump task's next channel send fails and logs the message. No *generated* data is lost (partial text + tool calls are preserved); what is lost is measurement completeness (no request_stats row for cancelled requests) and error-signal hygiene (user cancels logged as provider errors). → Finding D1 (LOW, BUG).

3. **send_ms 47-86s for ~1.4MB request bodies** — send_ms was renamed connect_ms; it spans record-created→response-headers, which includes the 1.4MB upload *and* the server's prefill of the ~340K-token prompt (headers only start when the first token is ready — same root cause as signal 1). The client-side share (build + clone + serialize) is ~25-60ms plus raw upload time; the dominant cost is server prefill on the uncached prefix. → Findings L3/L4.

### Section 1 — Latency bottlenecks (ranked by end-to-end turn-loop impact)

**L1. HIGH — TTFT is a dead metric: the anchor measures headers→first-chunk, which is ~0ms on all current backends.**
- Location: src/provider/openai/stream.rs:86-88 (window definition) and the Usage arm ~278-330 (`ttft_ms = first_chunk − request_start`); src/provider/anthropic.rs:~1460-1529 (same design, same boundary); the anchor `request_start` is stamped in spawn_stream (src/provider/openai.rs:683-757) when the POST response *headers* arrive — the documented "connect/ttft boundary".
- Symptom: request_stats.ttft_ms=0 for 99.2% of rows; ttft50 = 0-7ms across all 18 models. The metric cannot rank models or endpoints by first-token latency, and the trace graph's Waiting bucket (connect_ms) conflates network upload with server prefill/queue time.
- Root cause (BUG): `request_start` is stamped at response-headers arrival. LiteLLM (and the direct providers) only start the HTTP response when the first token is ready, so headers and the first SSE chunk arrive together — the measured window is structurally ~0. The user-perceived first-token wait (request-sent→first-chunk) is never recorded as its own bucket; it is buried in connect_ms.
- Estimated impact: zero runtime cost; blinds the round's core latency measurement (model ranking, endpoint comparison, latency regression detection — the "fastest agent" goal has no TTFT signal).
- Suggested fix: stamp ttft_ms from POST-send initiation (practically: `record_created`, or immediately before the `client.post`) → first chunk; keep connect_ms as the network/upload bucket. One anchor change per stream loop (openai/stream.rs, anthropic.rs) plus test updates. This also makes the aggregates' "(0 = unrecorded)" gloss unnecessary.

**L2. HIGH (run-all scoped) — the event forwarder awaits run-all dispatch/landing work inline: multi-second event-delivery blackouts for ALL agents while DISPATCH_LOCK/LANDING_LOCK work runs.**
- Location: src-tauri/src/ipc/events.rs:709-760 (`on_spawned_turn_resolved` / `on_main_turn_resolved` awaited inline inside the forwarder's single event loop; the error arm :640-684 does the same). The awaited work: src-tauri/src/ipc/run_all.rs:3758 (DISPATCH_LOCK acquired) held across `checkpoint_run_all_item` (git commit, :3857), `recalled_context_block` (embedder round-trip, :3877), `dispatch_run_all_to_main` (:3881), and `fill_spawned_window` (:3848; def :4100-4170 → `dispatch_spawned_item` :4177+ — worktree checkout + branch fork per lane, looped until the concurrency window is full). Landings (LANDING_LOCK — serialized --no-ff merges into main) run on the same inline path via `on_spawned_turn_resolved`.
- Symptom: when a lane or main turn resolves during a parallel run-all, the forwarder stops recv()-ing from the fan-in channel for the duration of git checkpoint + embedder recall + worktree provisioning — seconds, or tens of seconds when multiple lanes provision. The bounded fan-in channel (capacity 256, src/runtime/mod.rs:38, wired via AgentManager::new(256) in src-tauri/src/main.rs and console.rs:824) then fills; every agent's `fanin_tx.send(...).await` blocks; mid-stream lanes stall (TCP backpressure, stall_ms accumulates); the UI shows nothing app-wide. No data is lost — but every agent in the app freezes for the dispatch duration.
- Root cause (BUG): the single event-forwarder task is also the run-all dispatch driver; multi-second git/embedder/worktree work runs inline on the event-delivery critical path under global locks. The locks themselves are correct (they prevent double-dispatch and serialized landings); the defect is *who* awaits them — the one task that must keep pumping events.
- Estimated impact: seconds-to-tens-of-seconds full-app event blackout per dispatch/landing during run-all; invisible in single-agent interactive use (the ▶-button path, `dispatch_item` in backlog_cmds.rs:462-523, is lightweight and takes neither lock).
- Suggested fix: `tokio::spawn` the resolution→dispatch continuation instead of awaiting it inline in the forwarder loop — the forwarder only needs the turn-resolve latch result, not the dispatch completion. Same for the landing path.

**L3. LOW — per-iteration O(history) request-rebuild costs on every provider call.**
- Location: src/provider/openai/request.rs:103 (`let mut echoed = raw.clone()` — deep clone of every assistant message's raw JSON on every request, even when the reasoning-retention policy makes no mutation); src/provider/mod.rs:710-725 (`estimate_prompt_tokens` re-walks all message content + tool schemas per request); the full ~1.4MB body is re-serialized by reqwest `.json()` per request; the trace body capture re-clones and truncation-walks the body again.
- Symptom/math: for the 503-message conversations in the data (~1.4MB bodies): raw-echo clone ~5-15ms + token re-estimate ~2-5ms + full JSON serialization ~15-40ms ≈ 25-60ms per iteration, growing linearly with history length. Negligible against the 47-86s prefill turns, but 3-8% overhead on fast cached turns — the turns that define the "fastest agent" feel.
- Root cause: the request body is rebuilt from scratch each iteration with no incremental reuse, although history is append-mostly and TokenAccounting (src/agent/context.rs:709+) already maintains an incremental estimate.
- Suggested fix: (a) borrow instead of clone when the policy does not mutate the raw echo; (b) cache the serialized message prefix across iterations; (c) feed TokenAccounting's incremental estimate into the max-token cap instead of re-walking all content.

**L4. LOW as a comms-pipeline finding (nothing defective client-side) — but the #1 end-to-end latency lever: the 1.4MB request body itself.**
- The 47-86s connect_ms for ~1.4MB bodies is dominated by server-side prefill of the ~340K-token prompt (headers start only at first token — see L1) plus the upload itself. Client-side build+serialize is the ~25-60ms of L3 plus raw upload time. Every turn re-pays prefill on the uncached prefix; the prefix-cache levers are axis 3's scope. Within this axis, the in-app mitigations are compaction aggressiveness (summarize_at, keep_recent) and tool-result truncation (keep_high=20, summary_chars) — which trade the information loss of D2 against this latency.
- Suggested fix directions (cross-axis): raise compaction frequency for long sessions; consider pruning the tool-schema list to the tools the active plan needs (25 schemas re-sent on every request); keep the CONTEXT_FOOTER stable-prefix discipline (already present) to maximize prefix-cache hits.

**L5. LOW — LlmTraceView re-fetches the full trace record every 1.5s while a request is streaming.**
- Location: frontend/src/components/views/LlmTraceView.tsx:743 (POLL_MS=1500; four timers at :837/:857/:901/:941); the detail fetch returns the full record including raw response (up to MAX_RAW_RESPONSE_BYTES = 2MiB, src/provider/trace.rs:70-73) and the capped request body.
- Symptom: Trace tab open during a 60s generation → ~40 × up-to-2MiB JSON serialize + IPC transfer. The code comments acknowledge the cost (review N1+L1) and bound it with an is_complete stop predicate.
- Suggested fix: skip the fetch when the record's dirty-version is unchanged (cheap integer compare), or serve a stream-truncated detail during streaming and fetch the full body once on completion.

**L6. LOW — the trace file-writer rewrites the entire mirror file per coalesced batch during streaming.**
- Location: src/provider/trace.rs:1155-1259 (writer_main — drains and coalesces Msg::Dirty, then one full rewrite) and :1324-1395 (write_records_to_file — redacted clone of every record, whole-file rewrite; the mirror is capped at 8MiB).
- Symptom: per-chunk record updates during a long generation wake the writer repeatedly; each drain pays a full redact + serialize + write of up to 8MiB — sustained background disk/CPU churn during every long stream. It runs on a dedicated thread (off the agent's critical path), hence LOW.
- Suggested fix: debounce mirror writes to end-of-stream (the in-memory ring already serves the UI/IPC path), or write per-record files so a dirty record costs one record, not the whole file.

### Section 2 — Data/message-loss paths (ranked by severity)

**D1. LOW (BUG) — "stream aborted — consumer dropped" is the user-interrupt path, but it is misclassified as a provider error and leaves no request_stats row.**
- Location: drop sites src/provider/openai/stream.rs:414-446 and src/provider/anthropic.rs:1608-1640 (the `tx.send(event).await.is_err()` arm); trigger src/agent/turn.rs:2254-2547 (`consume_stream`'s command fold — a hard stop breaks the loop and drops the ReceiverStream, so the pump task's next send fails).
- Symptom: 45+ rows in .coding/logs/provider-errors.jsonl carry "stream aborted — consumer dropped"; the trace records are marked failed (log.fail) even though the HTTP response was healthy; the corresponding requests have no request_stats row (no Usage event ever arrives after the drop), so cancelled requests are invisible to latency/token accounting even though the provider billed them for the tokens generated so far.
- Root cause: when the consumer (the turn loop) is dropped mid-stream, the pump task treats the failed channel send identically to a provider failure — terminal fail + error mirror — with no distinction between user-initiated cancellation and a real stream error. If the consumer exits right after a genuine stream error, the "consumer dropped" message can also mask the preceding error class in the log.
- What is actually lost: nothing already generated — the un-generated remainder is intentionally discarded, and partial output IS preserved (`record_interrupted_output` keeps partial text + tool calls with "not run" results; regression `mid_stream_interrupt_sanitizes_truncated_args_in_history` sanitizes truncated args in history). This is a measurement/hygiene bug, not a runtime data-loss bug.
- Suggested fix: a distinct Cancelled terminal class for the consumer-drop arm (excluded from provider-errors.jsonl or tagged `cancelled`), stamped from the trace record's existing timings; optionally emit a partial request_stats row (with a cancelled flag) so aborted requests stay countable in the latency/token aggregates.

**D2. LOW — compaction/tool-result truncation is the one true information-loss path; bounded and structured, but unrecoverable from context.**
- Location: src/agent/context.rs:238-415 (`summarize` — middle history replaced by an LLM summary; system prompt + keep_recent tail kept verbatim; tail cut at tool-call boundaries via `summary_cut_index` :437-448, so it can keep fewer than keep_recent — conservative, safe); :489-571 (`compact_old_tool_results` — tool results beyond keep_high=20 intact are truncated to summary_chars + "[… truncated for context efficiency]", idempotent via COMPACTED_MARKER, tool_call_id/name preserved); :640-676 (`build_summary_prompt` — structured summary format with identifier-preservation instructions).
- Loss paths: (a) the summarizer is itself an LLM call and can drop details (mitigated by the structured prompt + identifier-preservation instructions); (b) old tool results are truncated to ~500 chars — file contents and search results beyond the cap leave the context permanently (the agent must re-read; the files remain on disk, so this is context loss, not data loss); (c) reasoning-content retention is policy-driven per provider.
- Staleness check: the per-turn auto-recall cache (src/agent/turn.rs:1816-1911) is version-stamped and invalidated on compaction (`maybe_compact`, turn.rs:1530+) — no stale-recall path found.
- Suggested fix (optional): when truncating a tool result, append a one-line pointer (file + line range) so the agent can re-read cheaply instead of re-searching.

**Verified no-loss / solid designs (checked, no finding):**
- Fan-in channel (bounded, capacity 256): backpressure by design; the 50 `let _ = fanin_tx.send(...).await` sites in turn.rs only ignore errors after the receiver is gone (shutdown) — no silent drop in normal operation. The residual risk is the L2 stall, not loss.
- SSE pump → consume_stream channel: bounded; on consumer drop the pump stamps a terminal trace marker, so the LlmTraceView poll's is_complete predicate fires — no infinite polling.
- DeltaBatcher (src-tauri/src/ipc/events.rs:140-330): 16ms deadline / 64KiB cap / structural-boundary flush; ordering preserved; coalesced deltas concatenated — no loss; the frontend rAF-buffer hybrid matches the Rust-side batching.
- Run-all lane event routing: lanes share the main manager → the same forwarder; ownership routing (`owns_spawned_run`, events.rs:640-760) prevents cross-stamping between the main lane and spawned lanes; the headless console path (src-tauri/src/console.rs:800-929) drains its own fan-in. No routing loss found.
- TokenAccounting (src/agent/context.rs:709+): incremental head/tail accounting with in-place-replacement detection — no per-iteration full recount in the agent loop (the recount that exists is the provider-side estimate, L3).
- Polling hygiene: MemoryDebugView (2s overview poll with count-signature-piggybacked list refresh — MemoryDebugView.tsx:39,417-444) and BacklogView (push-based via backlog://changed, no polling) are fine; App.tsx 10s/60s and GraphView 1.5s/5s polls are lightweight; InflightBar's 1s tick is a local clock re-render.
