## Findings

### 1. HIGH (BUG, known OPEN) — Proxied DeepSeek/GLM reasoning leaks into the main chat; ThinkTagFilter gated to Local-kind endpoints only

- **Location:** `src/provider/openai.rs:722` (the gate), `src/provider/openai/sse.rs` (text-delta branch — filter applied only when enabled).
- **Symptom:** Reasoning tokens from proxy-served models (`deepseek-v4-flash-gcp`/`-aws`, `glm-5.3` via the the LiteLLM proxy) render in the **main chat window** as assistant text, including literal think-tag markers. Memory record `BUG: DeepSeek/GLM reasoning tokens in main chat` (id 2edb2989) — OPEN on main (e0ac5dd) as of 2027-01-09; the config-knob fix (plan 77278715) was rolled back 2027-01-09.
- **Root cause / precise leak path:** The gate is `let think_tags_enabled = matches!(self.config.kind, ProviderKind::Local);` (`openai.rs:722`). The inline comment justifies it: OpenAI-kind gateways "use proper reasoning fields", and for them a literal think-tag opener at answer position 0 must NOT be swallowed (false positive: the whole answer rerouted and echoed back as `reasoning_content` — review Low 3). That assumption fails for proxy deployments that do **not** map reasoning into the `reasoning_content`/`reasoning` delta field: when such a deployment (vLLM/SGLang serving DeepSeek/GLM without a reasoning-field adapter) emits reasoning inline in `choices[].delta.content` wrapped in think tags, the SSE parser routes those deltas to `TextDelta` (no reasoning field present to divert), the ThinkTagFilter is skipped (`think_tags_enabled == false` for `ProviderKind::Openai`), and the raw reasoning — tags included — accumulates into `response_text` and renders as the assistant's answer. The parser's `ReasoningDelta` diversion only fires on `reasoning_content`/`reasoning` delta fields, which these deployments never send.
- **Assessment of the current gate:** The conservative default is defensible for the false-positive risk, but it is the direct cause of the leak for any OpenAI-kind endpoint whose deployment inlines reasoning in `content`. The rolled-back per-model `think_tags` knob would have fixed it but was reverted over the false-positive concern; next direction TBD.
- **Suggested fix:** Replace the static kind gate with a **stream-level heuristic**: enable think-tag extraction for a given stream only when (a) the stream has emitted **zero** reasoning-field deltas (`reasoning_content`/`reasoning`) so far, and (b) the first content delta opens with a think tag. Models that use proper reasoning fields are then unaffected by construction (their reasoning arrives via `ReasoningDelta`, so the heuristic never arms — the literal-leading-tag false positive is eliminated), while inline-reasoning deployments get their tags stripped. Optionally require a closing tag within the same message before committing the strip. The existing boundary-token escaping (`⟦raw:…⟧`, `boundary.rs`) already prevents tool-result-borne tag tokens from triggering the heuristic.

### 2. LOW (BUG) — Anthropic cache usage fields never parsed; `cached_tokens` hardcoded 0 and `input_tokens` under-counts

- **Location:** `src/provider/anthropic.rs:731` (`cached_tokens: 0` hardcoded in the `Usage` event), `message_start` handler at `anthropic.rs:588`; same class on the Responses API path at `src/provider/openai/sse.rs:104`.
- **Symptom:** Anthropic cache activity is invisible — traces/usage always show `cached_tokens: 0` on the native Anthropic path, and the recorded `prompt_tokens` under-reports the true context size by the cached prefix (system head ~20K chars ≈ 5K tokens + tools).
- **Root cause:** `message_start.usage` carries `input_tokens`, `cache_read_input_tokens`, and `cache_creation_input_tokens` (verified against current docs.anthropic.com / platform.claude.com prompt-caching + Messages API reference); we parse only `input_tokens`. Per Anthropic semantics, `input_tokens` **excludes** cached tokens (total input = `cache_read_input_tokens` + `cache_creation_input_tokens` + `input_tokens`), so once the system+tools breakpoints are cached, every request reports ~5–10K fewer input tokens than the conversation actually contains. This is a semantic mismatch with the OpenAI path, where `prompt_tokens` **includes** cached tokens — the two paths feed different meanings into the same `Usage` accounting. The Responses API parser (`sse.rs:104`) likewise hardcodes `cached_tokens: 0` where OpenAI reports `usage.input_tokens_details.cached_tokens`.
- **Suggested fix:** In the `message_start` handler, parse `cache_read_input_tokens` (emit as `cached_tokens`) and `cache_creation_input_tokens`; for accounting parity with the OpenAI path, record `prompt_tokens = input_tokens + cache_read + cache_creation` (or document the divergence). Mirror the same for `input_tokens_details.cached_tokens` on the Responses API path.

### 3. LOW — Anthropic message history not cached: 2 of 4 breakpoints used, growing conversation re-billed at full input price

- **Location:** `src/provider/anthropic.rs:229-382` (`build_request_json` — `cache_control: {"type":"ephemeral"}` on `system[0]` and the last tool only).
- **Symptom:** On direct-Anthropic endpoints, every request re-pays full (uncached, 1x) input price for the entire message history; cached reads bill at 0.1x. For a 100K-token agent conversation that is a ~10x input-cost miss on that path.
- **Root cause:** Deliberate design — the in-code rationale says caching the message history "would pin the cache to a moving tail; the stable head (system + tools) is the high-value prefix". Current docs.anthropic.com prompt-caching guidance explicitly recommends the opposite for multi-turn/agentic conversations: put a breakpoint on the **last message** so the 20-block lookback window finds the prior request's write and caches the whole conversation prefix (consecutive `tool_use`/`tool_result` runs count as ONE position). We use 2 of the 4 allowed breakpoints; 2 slots are free. The docs also now offer **automatic caching** (top-level `cache_control`) as a simpler alternative to explicit breakpoints. Verified constraints we already satisfy: system head ≈ 5K tokens > the 1024-token minimum cacheable length; 2 ≤ 4 breakpoints; 5m default TTL fits agent cadence (1h TTL available if ever needed).
- **Suggested fix:** Add a third breakpoint on the last message of the **previous** turn (stable across the current turn's requests), and optionally a fourth on the final block — the docs' caveat that a turn adding >20 block-positions can push the prior write out of the lookback applies to us (an agent turn with N tool calls adds ~2N+ blocks), which is exactly why the docs recommend a second breakpoint closer to the write position. Alternatively adopt automatic caching. Note: thinking blocks cannot carry `cache_control` directly (docs) — place breakpoints on adjacent text/tool blocks.

### 4. LOW — `policy.rs` `template_kwargs` documented as must-send but never sent; field names absent from public vendor docs

- **Location:** `src/provider/policy.rs` (`ProviderPolicy::template_kwargs`: GLM `clear_thinking: false`, Qwen/Kimi `preserve_thinking: true`); no consumer in `src/provider/openai/request.rs`.
- **Symptom:** Doc comments assert vendor requirements — "Newer GLM clears thinking by default, so `clear_thinking: false` must be set explicitly", Qwen/Kimi "`preserve_thinking: true` must be sent" — but no request builder reads `template_kwargs`; the params never leave the process. Doc/code drift plus dead registry entries.
- **Root cause:** The registry predates the rolled-back config-driven policy layer; the wiring was never present at HEAD (the rollback removed the override layer, and the base registry's params were never merged into `build_request_json`'s extra-body). Additionally, neither `clear_thinking` nor `preserve_thinking` appears in current public vendor docs — Zhipu's documented core params are `do_sample`, `temperature`, `top_p`, `max_tokens`, `stream`, `thinking` (`{"type":"enabled"|"disabled"}`), `reasoning_effort` (verified 2027-01-09); no `clear_thinking`/`preserve_thinking`. The names are unverifiable against public sources (possibly proxy-internal, possibly invented by the spec).
- **Suggested fix:** Either wire `template_kwargs` into the extra-body merge (behind the TBD vendor-policy config direction) after verifying the field names against the proxy's actually-accepted params, or delete the fields and their doc comments to stop the drift. Do not ship them as-is: comments claiming must-send behavior the code does not perform is exactly the kind of stale claim this review round exists to catch.

### 5. LOW — `stop` sequence count not validated for direct-OpenAI endpoints (4-sequence cap; unsupported on latest reasoning models)

- **Location:** `src/provider/openai/request.rs` (stop assembly: boundary strings ride ahead of user stops), `src/config/endpoints.rs` (`stop_boundary_strings` config, no count check), `README.md:128` (example ships 6 boundary strings: 4 GLM role tags + 2 newline cascades).
- **Symptom:** A direct-OpenAI endpoint configured with more than 4 stop sequences returns 400 (`Invalid parameter: 'stop' ... up to 4 sequences`) — the README's own GLM example (6 strings) plus any user stops exceeds the cap. Separately, OpenAI's SDK docs state `stop` is "not supported with the latest reasoning models" (o3/o4-mini) — sending it there errors.
- **Root cause:** The boundary-string mechanism was designed for proxy/vLLM/SGLang backends, which do not enforce OpenAI's 4-sequence cap; nothing validates the count per endpoint kind.
- **Suggested fix:** Validate `stop` count ≤ 4 (and warn about reasoning models) for `ProviderKind::Openai` endpoints whose base URL is `api.openai.com`, or auto-drop boundary strings on direct-OpenAI endpoints; document the constraint in the endpoints.toml examples.

### 6. LOW — glm-5.3-flash* `cached_tokens=0` on every request: proxy model-group config, not our request shape (analysis conclusion)

- **Location:** parse site `src/provider/openai/sse.rs:194-205` (`usage.prompt_tokens_details.cached_tokens`); data: `.coding/analysis/cache-hit-5-aggregates.txt`.
- **Symptom:** ALL glm-5.3-flash* model groups (flash, flash-gcp, flash-gcp-h200-bf16-01, flash-gcp-h200-fp8-01, flash-gcp-h200-sglang-01 — 1,699 post-R12 rows) report `cached_tokens=0` on every request (0.0% hit, 100% "resets"), while glm-5.3-gcp* groups hit 76–92% on the same app.
- **Root cause / determination:** Our request shape does **not** differ per model in any cache-relevant way. The same `build_request_json` produces the body for every model; the only per-model differences are `model`, the R9-quantized `max_completion_tokens` (stable within a session by design), `stop`, and `reasoning_effort` — none of which are part of the prompt prefix that prefix caching keys on. The cache-stable context-footer sentinel and the boundary-token escaping keep the prefix byte-stable. The parse site reads `usage.prompt_tokens_details.cached_tokens`, which exactly matches Zhipu's documented usage shape (their response example: `"usage": {"prompt_tokens": 8, "prompt_tokens_details": {"cached_tokens": 0}, ...}`). Decisive comparison from the data: `glm-5.3-flash-gcp-h200-fp8-01` (245 rows, avgP 155K, single deployment) is 0% while `glm-5.3-gcp-h200-01` (658 rows, avgP 133K, same hardware family, same request shape) is 92% — same builder, same flags, opposite outcomes. Conclusion: **proxy-side model-group/deployment config** — the flash deployments either run with prefix caching disabled (e.g. vLLM without `--enable-prefix-caching` / SGLang radix cache off — a common throughput tuning for flash variants) or do not report `cached_tokens` in usage. Not an app-side issue.
- **Suggested fix:** Raise with the proxy admin: check the litellm_params / serving flags for the flash model groups (prefix-caching enablement and usage reporting). Optional app-side A/B: replay one conversation against a flash and a non-flash group and diff the raw usage frames.

### 7. LOW — `reasoning_effort` allow-list offers values GLM-5.3 rejects (only `max`/`high`/`low`)

- **Location:** `src/config/endpoints.rs` (per-model `reasoning_efforts` allow-list; default surface `none|minimal|low|medium|high|xhigh|max`), `src/provider/openai/request.rs` (emission + 400 self-healing retry-without-field fallback).
- **Symptom:** GLM-5.3 / GLM-5.3-FLASH accept only `max`, `high`, `low` — any other value returns 400 (verified against Zhipu's current core-params and deep-thinking docs). A user selecting `medium`/`minimal`/`none`/`xhigh` on a GLM-5.3 model gets a 400 on every request until the self-healing fallback silently drops the field — the user's choice is then ignored without a clear signal why.
- **Root cause:** The allow-list is config-driven per model, but the shipped default doesn't encode GLM-5.3's restriction. (For OpenAI the default is correct: the current SDK enum is exactly `none|minimal|low|medium|high|xhigh|max`.)
- **Suggested fix:** Preconfigure `reasoning_efforts = ["max", "high", "low"]` on GLM-5.3/flash model rows in the endpoints.toml examples and README; surface the restriction in Settings when the model is known to restrict the enum.

### 8. LOW — benign stream cancellations recorded as provider errors, skewing error stats

- **Location:** `src/provider/sse_util.rs` / `src/provider/openai.rs` abort path ("stream aborted — consumer dropped").
- **Symptom:** 45+ rows in provider-errors.jsonl are benign cancellations (user cancelled / turn superseded → consumer dropped → the pump aborts the upstream request). They are logged with HTTP 200 through the same error channel as real failures, inflating error counts and triage noise.
- **Root cause:** The abort path logs through the provider-error channel without a cancellation marker.
- **Suggested fix:** Tag cancellations distinctly (a `cancelled` flag or separate log level) so error aggregates can exclude them.

### 9. LOW — proxy 404 "model not found" bursts fail the turn instead of triggering the endpoint fallback

- **Location:** `src/error.rs` (`NotFound` → `is_non_retryable`), `src/agent/dispatch.rs:804` (fail fast), `src/agent/loop_impl.rs` (`try_429_fallback` fires only on rate-limit).
- **Symptom:** LiteLLM "No model configured for ..." 404 bursts (29×404 in 424s on glm-5.2 in the data window) kill the affected turns even when another endpoint serves the same model.
- **Root cause:** `NotFound` is correctly non-retryable for direct APIs (retrying won't make the model appear), but on a proxy these 404s are frequently transient deployment-cooldown / config-reload windows — community reports (LiteLLM issues #12691, #11330, #20867) show 404 / "No deployments available" with healthy endpoints. The 429-fallback machinery (switch endpoint + live-token-count viability check, merged e0ac5dd) is not invoked for 404.
- **Suggested fix:** Treat proxy-flavored 404s (body text matching "No model configured" / "No deployments available") as fallback-eligible like 429, reusing `try_429_fallback`'s viability check; keep plain 404s non-retryable.

**LiteLLM proxy layer — community cross-check vs our handling:**

- Virtual-key auth: our client sends `Authorization: Bearer <key>`; the 401 "LiteLLM Virtual Key expected ... expected to start with 'sk-'" rows (18, deepseek-v4-flash-gcp) are proxy-side key configuration (LiteLLM docs: virtual keys must be sk- prefixed). Not ours.
- 404 "No model configured" bursts — see finding 9 (fail-fast correct for direct APIs; fallback-eligible treatment suggested for proxy-flavored 404s).
- 502 BadGateway wrapping vertex errors ("No fallback model group found for original model_group=...") — LiteLLM wrapping upstream vertex failures; our retryable classification (server error → 3× backoff) is correct for transient upstream failures.
- 429 "No deployments available for selected model, Try again in 30 seconds ... pre-call-checks" — LiteLLM router cooldown; our `is_rate_limited` → immediate endpoint fallback with live-token-count viability (`AgentLoop::live_token_count`, `loop_impl.rs:116` + `try_429_fallback`, merged e0ac5dd) is the right response: retrying a cooling-down router within its 30s window is futile, and the viability check prevents falling back into a smaller context window than the live conversation needs. Verified correct.
- Context-overflow fail-fast: `is_non_retryable` patterns (`error.rs`) match the actual LiteLLM-wrapped error strings in the data ("litellm.ContextWindowExceededError ... maximum context length", "input length and `max_tokens` exceed context limit") — classified non-retryable, no 3× retry burn on a permanently-oversized prompt. Verified correct.
- SSE stall detection: 90s no-data read timeout → "stream stalled — no data for 90s (HTTP 200 OK)" → error → retry. 4 stalls in 28.5K requests — the bound works; the residual risk (a deployment thinking silently >90s with no reasoning deltas or pings) is empirically rare in the data. "stream aborted — consumer dropped" is our own cancellation cleanup working correctly (logged noisily — finding 8).
