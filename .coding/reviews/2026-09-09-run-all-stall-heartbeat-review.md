### Verified correct (with evidence)

**1. Heartbeat correctness — no double-dispatch hazard.** `run_all_dispatch_next` acquires `DISPATCH_LOCK` (run_all.rs:3575) and holds it across the entire selection→checkpoint→record window; the busy guard (3637–3668) re-checks `is_running || has_running_descendants` under the manager lock, and the exclude construction (3583–3605) skips current + spawned ids. A heartbeat dispatch racing a resolution-path dispatch therefore serializes on the lock; the loser either defers on the busy guard or picks a different item — never the same item twice. The only residual window (a just-started turn reading idle until the forwarder processes `Started`, 3761–3765) is pre-existing and documented as accepted; the heartbeat adds no new exposure class (the compact chain already races the resolution path the same way today).

**2. No fight with the between-items compact window.** `run_all_stalled` loads `state.backlog.compacting` (3388) and returns false while compacting (3392), so the heartbeat no-ops for the whole `AUTO_COMPACT_WAIT` (600s) wait; the compact chain sets/clears that same flag. The microscopic entry race (a heartbeat check landing between the turn resolution and `compacting=true`) is benign: the `Compact` command and the dispatched prompt serialize in the agent's command queue, compaction is best-effort by design, and the compact chain's post-wait dispatch then defers on the busy guard — eventually consistent, no corruption.

**3. No spin when only deferred items remain.** `next_pending_eligible_excluding` filters `!deferred` (src/backlog.rs:829), so a deferred-only queue reads not-stalled → the heartbeat no-ops; the run ends through the dispatch's no-eligible arm (3612–3624, `end_run` when no lane is in flight). The busy guard is only reachable after an item is selected, so a deferred-only queue can never wedge there.

**4. Self-termination; never ends runs.** The heartbeat breaks when `run_all` is None (3432–3434) and contains no `end_run` (3427–3443; pinned by `heartbeat_redispatches_a_stalled_run_without_turn_resolution`). `end_run` (242–259) clears `run_all`, so a normally-ended run kills the heartbeat at its next tick. Spawned lanes are parentless agents — not descendants of the main agent — so the heartbeat correctly dispatches to the main lane while spawned lanes run, matching the parallel design (the busy guard only guards the main agent).

**5. **LOW-2 — "every dispatch-chain arm writes here" is overstated: five arms remain eprintln-only.** run_all.rs:4249–4251 (`on_spawned_turn_resolved`, item-vanished arm), 4653–4655 (`on_spawned_turn_resolved`, terminal tail), 4796–4798 (`drain_spawned_on_exit`), 5423–5428 (`on_main_turn_resolved`, auto-compact else branch), and the became-busy-during-checkpoint deferral at 3789–3796. **LOW-3 — `run_all_stalled` ignores the run's stop flag.** 3362–3417 — the preconditions don't include `r.stop`. Every other dispatcher checks stop before dispatching: `on_main_turn_resolved` (5388–5398), `on_spawned_turn_resolved` (4637–4651), and the compact chain's post-wait re-check (3523–3545, the HIGH-2 guard). A stop requested while nothing is in flight (a between-items stall — the exact state the heartbeat heals) lets the heartbeat dispatch one more item despite the user's stop; the stop then takes effect at that item's resolution (bounded, self-correcting — the flag stays set). One-line fix: treat a stop-requested run as not stalled in `run_all_stalled`. Note the plan's own loop spec omitted the stop check too — the implementation matches the plan; the gap is in both.

**LOW-4 — Heartbeat lifetime binds to "any armed run", not this run.** 3427–3443 — the loop exits only when it observes `run_all == None` at a tick. If run A ends and run B starts within one 30s period (`backlog_run_all` refuses concurrent starts, so B starts only after A ended — but the None gap can be shorter than the heartbeat's sleep phase), heartbeat A survives into run B and serves alongside heartbeat B. Benign — dispatches serialize under `DISPATCH_LOCK`, the busy guard re-checks, each survivor is a 30s-period task with tiny lock checks, and all exit on the next observed None gap — but termination isn't deterministic across rapid restarts and duplicate heartbeat log lines are possible. A generation/run-id binding would close it.

**LOW-5 — Touched arms keep bare `eprintln!` next to the new `run_all_diag`.** 3643–3646 (busy-guard deferral), 3481–3483, 3490–3492, 3497–3499, 3529–3531, 3535–3537 (compact chain). `run_all_diag` already writes stderr via a swallowed `writeln!` (3322–3325), so the `eprintln!`s are now duplicate stderr output — and they carry the documented GUI-subsystem panic risk (events.rs:1046–1051: "NEVER eprintln! here: it PANICS when the stderr write fails"; a panic on the compact chain's spawned task kills the dispatch chain — the very stall class). Pre-existing lines, but the diff touched these arms; dropping the `eprintln!`s where `run_all_diag` now covers them closes both the duplication and the risk.

**LOW-6 — The zombie-descendant limitation is not documented, and the new docs overstate coverage.** The known limitation (a stale/zombie descendant keeping `has_running_descendants` true forever keeps the run "busy" → `run_all_stalled` false → the heartbeat never re-drives; identical to today's behavior) appears nowhere in the shipped artifacts — "zombie" occurs only in the heartbeat's self-termination comments (3431, 1705).
