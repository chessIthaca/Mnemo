### Finding 1 (LOW) — `clear()` updates `requests` state but not `requestsRef`, violating the new "always in lockstep" comment

- Location: frontend/src/components/views/LlmTraceView.tsx:1019-1029 (clear handler, `setRequests([])` at :1022) vs the list poll's paired update at :853-856 whose new comment says the ref is "kept beside the state so both are always in lockstep".
- The list poll feeds the ref beside every `setRequests(list)` (:853/:856), but the clear handler's `setRequests([])` (:1022) leaves `requestsRef.current` holding the pre-clear list for up to one poll cycle (≤1.5s) until the next list tick overwrites it. These are the only two `setRequests` call sites in the file (verified by search).
- Why it is currently harmless (verified, not assumed): the only readers of `requestsRef` are the two `load()` guards (:931, :977), and after clear() both polls are torn down by `setSelectedId(null)` in the same handler (the detail effect returns early on `selectedId === null`; the compare effect on `!compareOn || selectedId === null`). Even in the in-flight-tick race (a `listLlmRequests()` that resolved before the backend clear lands repopulates state + ref + selectedId with stale rows), the detail effect's effect-scoped `lastVersion = null` forces the first fetch, `getLlmRequest` then returns null (record gone), and the poll stops correctly — no wrong skip is possible in any interleaving. The drift self-heals on the next list tick.
- Why it is still a finding: the new comment claims lockstep, and the drift is a latent trap for any future reader of `requestsRef` outside the torn-down-poll window (a future refresh path, or a poll that survives clear). Fix: add `requestsRef.current = [];` beside `setRequests([])` in the clear handler; optionally extend the versionSkip source-contract test's "feeds requestsRef" case to pin the pairing at both call sites.

### Verified correct — the version-skip semantics ("can the skip ever hide a real change?")

Every scenario from the review brief was traced through the actual code (not just the diff):

- **Payload eviction**: `enforce_raw_budget` (trace.rs:1070-1094) bumps `r.version += 1` when it takes a payload (:1091). It is called from all three of its call sites — `start()` (:558), `with_record()` (:863), and `set_memory_budget()` (:886) — so a payload evicted by ring growth, by a mutation on another record, or by a budget shrink all bump the evicted record's version. The FE then sees listVersion ≠ lastVersion and re-fetches, so the UI can never keep showing an evicted body. Both regression tests pin this (arithmetic verified: shrink-eviction 1→2; growth-eviction bumps the OTHER record 1→2 while the appended record's own payload survives).
- **Ring eviction**: `start()`'s `pop_front()` (:553-555) removes the record entirely → it is absent from `list()` (which maps every ring record) → `listVersionOf` returns null → `shouldSkipRefetch(lastVersion, null)` is false → the fetch runs, observes the null, and `shouldStopPolling` stops the poll. The skip can never strand a ring-evicted record.
- **clear()**: `LlmRequestLog::clear()` (trace.rs:818-826) drops records but never resets `next_id` (AtomicU64, starts at 1, only `fetch_add`s) — ids are never reused, so the FE's standing invariant "a null can never become non-null" holds and the null path above applies. (The FE-side clear drift is Finding 1 — harmless there for the reasons given.)
- **Transient list-poll errors**: the list poll's catch only sets the error banner (LlmTraceView.tsx:862-864) — the `setInterval` is never cleared on error, so the poll retries every 1.5s indefinitely and `requestsRef` is stale only until the next successful tick. During an outage the detail may lag, but the outage is surfaced to the user (error banner) and self-heals; there is no permanent skip-forever scenario short of the backend being dead (in which case the detail fetch would fail too). The one theoretical gap — `listLlmRequests` persistently failing while `getLlmRequest` succeeds — is not plausible: both are Tauri commands over the same IPC reading the same mutex-guarded ring (src-tauri/src/ipc/trace.rs:37-59, types passed verbatim, no DTO mapping).
- **Compare effect's id-1**: the guard lookup and the fetch both use `selectedId - 1` consistently (:977/:980). Ids start at 1, so id-1 = 0 is never a valid id → listVersion null → fetch → null → stop. The effect depends on `[compareOn, selectedId]`, so a compare re-toggle or re-select restarts it with `lastVersion = null` → always re-fetches.
- **Effect-scoped lastVersion reset**: `let lastVersion: number | null = null` is declared inside each effect (:918/:966), so every selection change re-runs the effect and the first fetch always fires. Pinned by the source-contract test (exactly 2 occurrences asserted).
- **No-op mutations bump too** (conservative direction): `update_streaming_usage` on a terminal record and `append_response` on an evicted/truncated payload return early from their closures, but `with_record` bumps unconditionally after `f(r)` (:857). Worst case is one spurious re-fetch of identical content — the failure mode is over-fetching, never a missed change. Reads (`list`/`get`) take the lock but never route through `with_record`, so idle records stay stable (pinned by the idle test).
- **Completion/stop interplay**: finish/error is a mutation → version bump → the list carries it → the detail poll fetches → `is_complete` → `stopPolling`. The stop (and any post-mutation refresh) can lag by up to one poll cycle because the guard reads a ref fed by the previous list tick — bounded at ~1.5s extra on a poll that previously fetched every 1.5s anyway. An idle-but-incomplete record (TTFT window, stalled stream) now ticks without fetching — strictly better than the pre-change re-clone-per-tick, and the code comment documents it.
- **Overlapping loads** (fetch slower than POLL_MS): `lastVersion` is only written under `if (!cancelled)` after a fetch resolves; concurrent loads at worst both fetch (idempotent `setDetail`) and `lastVersion` ends at the latest fetched version — no stuck state.
- **Wire/IPC**: `LlmRequestDetail` is `pub type LlmRequestDetail = LlmRequestRecord` (trace.rs:282), so `get()` carries `version`; `From<&LlmRequestRecord>` copies it into the summary (:366); the Tauri commands return the Rust types verbatim (no field-by-field DTO that could drop it). u64 → JSON number is safe (no realistic overflow). The record derives only `Serialize` — the traces.jsonl mirror is write-only, so old mirror rows without `version` pose no deserialization-compat issue, and the added field is additive for the offline analysis consumers.
