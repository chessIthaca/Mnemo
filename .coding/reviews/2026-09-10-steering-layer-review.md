## Finding L1 (low) — rider awaited while holding the workflow guard, against the file's own documented rule

- **File/line:** src/tool/workflow/plan.rs:467-478 (the `recall_rider(...).await` call inside the `Ok(id)` arm, while the `wf` guard from :377 is live); contradicting rule at src/tool/workflow/plan.rs:1002-1006.
- **Why:** `abandon_plan` documents "the codebase rule: never hold a lock across an await; the supersede does store round-trips, and a concurrent workflow-lock acquirer must not stall behind SQLite latency" and deliberately drops the guard before its store round-trips. The rider does exactly what that rule forbids: up to two `recall_peek` store round-trips (embedding — potentially a REMOTE embedder call — plus SQLite reads on the blocking pool) under the workflow mutex. This is NOT a deadlock (store locks are independent, no lock-order inversion; the store never acquires the workflow mutex) and it matches the branch-prep precedent in the same function (awaiting `prepare_branch`/`ensure_work_branch` under the guard with the deliberate rationale at :383-387) — but unlike branch-prep, the rider does not NEED the lock at all: it reads only `args` + the store, and the plan is already persisted. A future maintainer reading the abandon_plan rule will find create_plan doing the opposite with no comment.
- **Suggested fix:** restructure the `Ok` arm so the success `ToolResult` is built (or the guard scoped/dropped) before the rider runs — e.g. bind the match result, `drop(wf)` (or end the lock's scope), then append the rider to the output and return. Alternatively, minimal fix: add a one-line comment at the call site documenting the deliberate exception (mirroring the :383-387 rationale). The plan's own claim "prepare_branch awaits under the same lock" is accurate; the gap is that the codebase's documented general rule for STORE round-trips (abandon_plan) points the other way.
