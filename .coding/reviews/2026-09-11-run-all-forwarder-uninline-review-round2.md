## LOW-1 (low) — continuation-side done-counter bumps are not gated on their transitions' success: one ordering of the LOW-1 race now double-counts

**Location**: src-tauri/src/ipc/run_all.rs:5630-5639 (`flip_done_if_linked`) and :4654-4662 (`on_spawned_turn_resolved`'s success arm).

Both continuation-side bumps fire on a status pre-check, not on the transition's result. `flip_done_if_linked` returns `true` unconditionally inside `if may_flip` — the transition's bool is discarded — and `commit_success` (a git add+commit subprocess, ~100ms+) sits between the `may_flip` check and the transition. `run_all_success_disposition` maps that `true` to `terminal_resolution: true` and `resolve_run_all_turn` bumps. The spawned success arm has the same shape (`terminal_resolution = true` inside `if still`, transition bool discarded), though its `still`→transition gap is a bare lock re-acquisition.

**The race**: in the main-lane variant of the LOW-1 scenario itself (main agent crashes/cancels right after its finishing turn, work landed), the drain's Done transition can land between the continuation's `may_flip` check and its transition — a window whose width is the `commit_success` duration, with the drain's own transition arriving after a comparable git-bound landed check, so the overlap is a plausible fraction of such events, not a contrived microsecond corner. In that ordering BOTH bump: the drain (its transition succeeded — correctly gated) and the continuation (its pre-check passed; its transition was refused, but its bump is not gated on that). The run's `done` counter double-counts the item.

**Why the spawned lane is effectively closed**: both the continuation's success arm and the drain's landed arm land the branch under LANDING_LOCK before their status check + transition; the landings serialize, so whichever lands second runs its check/transition well after the first's transition completed (microsecond check→transition gaps on both sides). The exposure is main-path-specific (`commit_success` has no such serialization).

**Impact**: display-only — `done` is read solely at backlog_cmds.rs:162 for the RunAllProgress payload (the UI progress line); run completion gates on `any_lane_in_flight` / eligibility, never on the counter, and the counter dies with the run state at `end_run`. Pre-fix this ordering produced a single correct bump (the continuation's); the LOW-1 drain bump is what turns it into a double — i.e. the fix's stated invariant "a blocked flip never double-counts" holds for the drain's flip but was never true for the continuation's (round 1's "the done-counter bump is gated on one's own successful transition" was accurate for the disposition wiring, not for `flip_done_if_linked`'s internal transition).

**Fix direction** (small, follow-up): mirror the drain-side gating this fix added — capture the transition's bool in `flip_done_if_linked` (return it instead of the unconditional `true`) and in the spawned success arm (gate `terminal_resolution` on it). One-line changes at two sites; no lock or ordering changes needed.
