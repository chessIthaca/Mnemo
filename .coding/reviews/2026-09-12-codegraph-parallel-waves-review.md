## Verification detail (checklist items 1–7)

**1. Concurrency correctness — PASS.**
- *No data races:* `extract_job` (mod.rs:922-1020) touches only `mtime_of`/`fs::read`/hashing/`extract_file_with` — zero store access. The `stored: HashMap<String, FileMeta>` is shared `&`-only across workers (immutable after the single `stored_file_meta()` load); `jobs` likewise `&`-shared; each worker owns its `ParserCache` and one `&mut Vec<(usize, UpsertEntry)>` from `outputs.iter_mut()` — exclusive by construction, joined before `outputs.into_iter()` consumes them (scope join precedes it).
- *Determinism:* job indices are unique within a wave and follow the walk's sorted order; `sort_unstable_by_key(|(i, _)| *i)` on unique keys is order-deterministic; waves apply in walk order. Final DB content is deterministic (only `indexed_at` timestamps vary — same as before).
- *Progress callback stays on the coordinator:* workers only `tx.send(())`; the drain loop (`for _ in rx`) runs inside the scope closure on the calling thread, so the non-`Send` `&dyn Fn` never crosses a thread boundary. Count is monotonic and exact: every file pulses exactly once (worker pulse per job, coordinator pulse per relpath-failure in the job-collection loop), so `done` ends at `total`.
- *Indexing-flag lifecycle:* `index_inner` still sets the flag + `IndexFlagGuard` first (mod.rs:369-370); a worker panic propagates out of `std::thread::scope` (which re-panics after joining), unwinds through `index_inner`, and the guard's `Drop` clears the flag. The wave's not-yet-committed transaction rolls back; earlier waves stay committed (incremental semantics self-heal on the next pass).
- *Panic cannot deadlock the drain:* a panicking worker's `Sender` clone drops during unwind; the drain ends when all senders drop, so the coordinator never blocks on a dead worker. `Ordering::Relaxed` on the work-index `fetch_add` is correct (unique-index assignment only; `jobs`/`stored` publication rides the spawn happens-before edge).
- *Concurrent-writer equivalence:* loading `stored` once up front is equivalent to the old per-file SELECTs — the only writers during a pass (`reindex_stale_files`, the watcher) coordinate via the indexing flag; `reindex_files_containing` may interleave but writes idempotent content-derived rows through the same store mutex (identical convergence window to the old code).

## Findings

### LOW-1: Two stale doc comments still claim the store lock is taken "per file"
The plan's detailed step (c) explicitly listed "update the store-lock doc comment (per wave, not per file)" — it was not done. Two sites now describe the pre-change behavior:
- `src/codegraph/mod.rs:89-90` (the `CodeGraph::store` field doc): "Short critical sections only: `index` takes the lock per file, and query snapshots load in two fast SELECTs."
- `src/codegraph/mod.rs:340-342` (the `CodeGraph::index` doc): "The store lock is acquired per file, so concurrent readers (agent tools, the Graph tab) stay responsive during a large index."

The new reality: one lock for the `stored_file_meta()` snapshot, one per wave for `upsert_files`, one for the final prune/stats block. The intent of both claims (readers stay responsive) still holds — even more so — but the factual mechanism is stale, and doc-comment accuracy is a review expectation for this project. While fixing, consider one clarifying word in the same `index` doc: `progress` is now called after each file's *extract* (the wave's store write follows the whole wave), so "called after each file" is still true in spirit but fires slightly earlier than the old post-upsert call — a half-sentence ("after each file is processed, before the wave's store write") removes the ambiguity.

Fix: reword both comments to the per-wave/per-snapshot locking (e.g. "the store lock is taken once for the metadata snapshot and once per wave of upserts, so concurrent readers … stay responsive between waves").

### LOW-2: Wave memory bound is file-count-based, not byte-based
`WAVE = 512` bounds the number of `UpsertEntry`s held between join and upsert, and each entry carries the file's full text (`content: String`) plus `FileData`. The walk admits files up to 1 MB (`should_search`'s cap), so a pathological tree (hundreds of ~1 MB searchable files not caught by the ignore rules) can hold roughly 0.5–1.5 GB transiently per wave — versus the old code's one-file-at-a-time peak. This is a deliberate, documented trade-off (the plan's invariants: "the wave size bounds memory for extracted results"), freed between waves, and realistic repos (this one: 2,913 mostly-small files) are nowhere near it — hence LOW, not a blocker. Suggested hardening for future work: pack waves by a byte budget (stop adding jobs to a wave once accumulated read bytes pass ~64–128 MB) or note the amplification in the module doc so the next person tuning `WAVE` knows it's a memory knob, not just a latency knob. Fixing now is optional; if skipped, record the justification (documented trade-off) in the plan.
