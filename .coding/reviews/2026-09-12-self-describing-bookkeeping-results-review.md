### Findings

**Finding 1 (LOW) — `update_plan`'s "steps replaced ({before} → {after} steps)" misstates the post-update step count whenever completed steps are preserved (the typical mid-flight replace).**
- Where: `src/tool/workflow/plan.rs:1071-1078` — the `else` branch pushes `format!("steps replaced ({before} → {new_steps_len} steps)")`, where `new_steps_len` is the count of steps *passed in the call*, not the resulting plan size.
- Evidence: the engine (src/workflow/mod.rs:721-771) preserves the completed prefix — the post-update total is `completed_prefix + passed_count`. Concrete case, straight from the existing test `update_plan_appends_steps_preserving_completed` (plan.rs:4528-4547): a 4-step plan with steps 1-2 done, replacing the remaining 2 with 2 new steps → the plan ends with **4** steps, but the new output reads "steps replaced (4 → 2 steps) — 2/4 done". The "→ 2" is false as a plan-size transition and is contradicted by the adjacent "2/4 done". The pair (total-before, passed-count-after) is incoherent under both natural readings: as a size transition the "after" should be the post-update total; as "remaining → new" the "before" should be the remaining count, not the total. The old format reported the true post-update total, and its own removed comment said the before→after form existed precisely to avoid "a misleading 'added' count" — this regresses that care for every replace with ≥1 completed step. No test pins the steps clause of the enumeration, which is how it slipped through (the new test only exercises context + regression_test).
- Fix: use the post-update `total` (already computed at plan.rs:1044) as the "after" — `format!("steps replaced ({before} → {total} steps)")` — or frame it as remaining→new (e.g. "steps replaced (2 remaining → 2 new)"). Add assertions pinning the enumeration: a replace-with-completed-steps case (e.g. extend `update_plan_appends_steps_preserving_completed` or the new test) and an append case asserting "steps appended (+K)" (that arm is already truthful — the engine adds exactly the passed steps after the remaining ones).
- Severity rationale: output-only, no state impact, the authoritative count is in the same line — but it violates the plan's own "the changes enumeration NEVER LIES" acceptance bar in the common case, so fix before landing.

**Finding 2 (LOW) — blank string fields are enumerated as changes the engine silently skipped.**
- Where: `src/tool/workflow/plan.rs:1052-1082` — the enumeration keys on `args.title.is_some()` / `args.goal.is_some()` / `if let Some(ctx) = &args.context` / `if let Some(rt) = &args.regression_test` alone.
- Evidence: the engine applies these fields only when non-blank (src/workflow/mod.rs:678-711 — `if !t.trim().is_empty()` etc.); blank means "keep current" per the schema's own parameter text ("omit or empty to keep current"). A mixed call such as `update_plan(title: "", context: "real text")` passes the tool-layer gate (blank context is filtered out of gating at plan.rs:1005; title/goal are ungated), succeeds via the context, and reports "title set, context replaced (…)" — but the title was NOT set. Same for goal/context/regression_test. `landed_design` (bool) has no blank concept and is fine. The no-op guard (workflow/mod.rs:773-779) means an all-blank call errors, so the overclaim only appears in mixed blank+real calls — degenerate, but the echo lies when it happens.
- Fix: mirror the engine's blank filter at the enumeration, e.g. `args.title.as_deref().is_some_and(|t| !t.trim().is_empty())` (likewise goal/context/regression_test).
- Severity rationale: degenerate-call edge; the engine does the right thing; only the echo overclaims.

**Finding 3 (LOW) — `complete_step`'s step text is read from the post-completion plan; after a sub-plan's last-step pop that is the PARENT plan, so the wrong step's text (or an empty string) is shown.**
- Where: `src/tool/workflow/plan.rs:1334-1346` — `plan.and_then(|p| p.steps.get(step_index as usize))` where `plan = wf.plan()` is taken AFTER `wf.complete_step` (plan.rs:1326).
- Evidence: the code itself documents the pop at plan.rs:1314-1316 ("a sub-plan's last step pops the stack, so plan_id() afterwards is the parent's") — which is exactly why `active_plan_id` is captured BEFORE the call. `step_text` (like title/completed/total) is read after, so in the pop case `p.steps.get(step_index)` yields the *parent's* step at that index — a work item that was NOT just completed — or `None` → `unwrap_or_default()` → "Complete Step 2 '' (…)". The title/counts quirk is pre-existing; the step text is NEW and specifically claims to be the completed step's text, so in this edge it names the wrong work item — the exact failure mode this feature exists to prevent.
- Fix: capture the step text BEFORE the `wf.complete_step` call (alongside `first_unchecked` at plan.rs:1321 and `active_plan_id` at :1316), from the pre-call plan.
- Severity rationale: edge case (last step of a stacked sub-plan only), pre-existing pattern for title, no state impact.
