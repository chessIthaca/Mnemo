## Findings

### HIGH 1 — `enforce_sendable`'s drop loop can orphan the newest tool result and can exit still over budget (violates its own documented invariant)
**Where:** `src/agent/context.rs:1086-1098` (guard at :1090, drain at :1098); doc claims at :1063-1066 and the module doc's "never splitting a tool batch".
**Failure mode:** the boundary walk `while drop_to < result.len() - 1 && result[drop_to].role == Role::Tool` has two exits. When the kept tail ends in an **open (parallel) tool batch** — `[sys, summary, …, assistant(call), tool, tool, …]` — and the loop consumes down to that batch, the walk stops at `len-1` on the guard (the newest message is a Tool result), and `result.drain(2..drop_to)` drops the assistant call **and every result except the newest**. The returned conversation permanently ends with an orphaned tool result: `validate_request_messages` (`src/provider/openai/request.rs:1256`, rejects dangling `tool_call_id`) then rejects **every** subsequent request; since the context is now under the summarize threshold, auto-compaction won't re-run to repair it — the session wedges until `/new`, which is precisely the symptom this plan set out to kill. The loop can also exit at `result.len() == 3` with `total > sendable_budget` (same guard), so the "compaction is total" post-condition is not "enforced by construction" as documented.
**Reachability:** requires the residual after the aggressive 2000-char cap (system head + summary + final batch) to still exceed `sendable_budget`. Unreachable for the built-in capability sets (openai 128K → budget 121,856; local 32K → 26,624; anthropic 200K → 165,856) but real for **user-configured small-window models** (`max_context` is a documented config field, PLAN.md:524; an 8–20K window gives budget 8,192–13,856 after the floor) combined with the app's ~5K-token system head plus a moderately wide final batch. The aggressive cap makes this *less* likely but cannot eliminate it.
**Fix direction:** treat the trailing tool batch as atomic with the newest message. Minimal change: when the walk exits on the guard with `result[drop_to].role == Role::Tool` (i.e. the newest is a Tool result), stop the loop instead of draining — the minimum kept tail becomes `[sys, summary, assistant(call), tool…]` (whole final batch), and document that totality yields when even the untouchable core exceeds the window (physically unavoidable). Then update the doc comment at :1063-1066 to match, and add a regression test: a fixture whose compacted+capped result still exceeds the budget with an open parallel batch as the final turn, asserting `assert_tool_pairing_intact` after `enforce_sendable` (the current fixtures never drive the loop to the final batch, so this hole is untested).

### LOW 2 — the mechanical fallback silently downgrades observability (R21 regression)
**Where:** `src/agent/context.rs` — summarize's overflow arm (~:330), summarize_with_interrupt's immediate (~:425) and mid-stream (~:480) overflow arms; consumer at `src/agent/turn.rs:1854-1905`.
**Failure mode:** pre-change, a size-rejected summarize request returned `Err`, which made `maybe_compact` record a `purpose='summarize'` `outcome='error'` request_stats row (R21, knowledge record 2027-01-07-request-stats…) and surface an Error event. Post-change the fallback returns `Ok`, so **no stats row is written and no transcript note marks the downgrade** — a chronically undersized summarizer (e.g. a cheap `[models.summarize]` slot mis-advertising its window) produces only normal-looking `Compacted` events whose summary is a mechanical note; there is no diagnostic trail.
**Fix direction:** at the three fallback return sites, either record a `purpose='summarize'` row (outcome `'error'` or a new `'mechanical'`) — the mechanical path has no Usage, so reuse the R21 estimate — and/or emit an `AgentEvent::Error { retrying: true }` note ("summarizer rejected the request for size — compacted mechanically") so the transcript explains the note-style summary. Non-size errors already keep the old Err behavior (tested).

### LOW 3 — latent slice panic if `budgeted_cut_index`'s defensive normalization ever yields `cut = 0`
**Where:** `src/agent/context.rs:1380` (`while cut > 0 && cut < messages.len() && messages[cut].role == Role::Tool { cut -= 1 }`) + the consumers' `&messages[1..cut]` in both summarize paths.
**Failure mode:** if `messages[1]` were ever a Tool message, the walk decrements to 0 (the guard checks `cut > 0` *before* decrementing), and `&messages[1..0]` panics one step later. Unreachable today — `summary_cut_index` (context.rs:591-602) always returns a non-Tool cut (it advances forward past tool results) and `messages[1]` can never be Tool in this app (messages[0] is the system message, which cannot carry tool_calls) — but the normalization exists to defend exactly this shape and then panics on it.
**Fix direction:** clamp the normalization at 1 (`while cut > 1 …`) and/or re-check `if cut <= 1 { return messages.to_vec() }` after budgeting in both summarize paths (mirroring the pre-budget `cut <= 1` skip). Cheap, makes the defensive code actually safe.

### LOW 4 — `prompt_text_tokens` doc overclaims the chunked sum as a proven upper bound
**Where:** `src/agent/context.rs:1229` (doc block) and the module doc's "conservative upper bound" bullet.
**Failure mode:** the argument "no BPE merge can span a chunk boundary, so the sum is an upper bound" is incomplete: chunking can also **split a pretoken** at the boundary, and greedy BPE is not globally optimal, so a contrived input could in theory measure the parts lower than the whole. In practice splits forfeit merges and over-count (the direction the budgets need), the residual risk is O(1) per boundary, `SUMMARY_BUDGET_SLACK_TOKENS = 16` absorbs it for short strings, and the mechanical fallback backstops any residual rejection — so no functional risk was identified. But the doc asserts more than is provable.
**Fix direction:** doc-only: soften to "over-counts in practice (a chunk split forfeits cross-boundary merges)" and note the residual theoretical risk is covered by the slack + the mechanical fallback. No code change required.

3. **`budgeted_cut_index` bail-out, both directions.** When one region turn exceeds `conv_budget`, the march returns the cut untouched; `budgeted_conv_text` then truncates that message in the **summary prompt only** with `SUMMARY_BUDGET_TRUNCATION` + `SUMMARY_BUDGET_NOTE` — after compaction the region is replaced by the summary, so the monster *leaves the conversation* (no lost coverage: the head + note tell the summarizer what was dropped; no re-wedging: the tail never contained the monster, and tail monsters are the aggressive cap's job). Coverage loss is confined to region content after the busting message, which is the documented design. Entry normalization preserves pairing: it walks the cut down to the batch's **assistant call**, moving the whole batch into the kept tail. The march itself can never reach cut=1 (post-bail-out a single-turn region always fits), and `summary_cut_index` guarantees a non-Tool incoming cut, so the normalization is defensive-only — see LOW 3 for its latent panic. The march is O(n): one seeding pass, O(1) subtraction per step, no re-serialization per iteration.

## Observations (non-finding)

- The oversize pass's `keep_chars + 100` slack is load-bearing for "an ingestion-capped result is not re-truncated": the ingestion trailer is ~97-106 chars depending on the dropped-count digits, so a very large dropped count (>~5 digits) pushes a capped result past `TOOL_RESULT_MAX_CHARS + 100` and the next compaction rewrites it to `COMPACTED_MARKER` + re-run pointer. Harmless (both truncations bound the size; idempotent after) but the magic +100 is fragile coupling between `cap_tool_result_text`'s trailer length and `truncate_tool_result_at`'s slack.
- `prompt_text_tokens`'s no-BPE path uses chars/4 while `count_message_tokens`'s no-BPE path uses bytes/4 — two different fallback ratios, both reachable only if the embedded tiktoken table fails to load (practically never).
- `context_budget`'s 8192 floor can exceed a genuinely tiny configured window (max_context < ~14K ⇒ budget > window). Documented as deliberate ("degenerate capabilities still get a minimal floor"); combined with HIGH 1's fix it may be worth an explicit doc note that totality yields when the untouchable core exceeds the window.
- The mid-stream overflow arm discards `buffered` commands (steers typed during a failed summarization); the pre-change Err path lost them identically — no regression.
- Housekeeping: do **not** commit the untracked `.coding/tmp/` scratch files (`buildQ.err`, `buildC.err` — intermediate build-error dumps) or `.coding/instance.json` with this change.
- `ContextManager::summarize` (plain) has no production callers (context.rs tests only, confirmed against the summarize-slot review) — the `sendable_budget` threading there is test-only, so no production site was missed. All three production call sites pass the correct window (swap = new model, auto = turn provider, manual = turn provider).
