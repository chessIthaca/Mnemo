**Code:** `src/agent/context.rs:1093-1132` (guard change at :1110, break at :1113-1124, drain at :1125-1130); doc at :1079-1086; test at :3990-4047.

- **Guard/break logic:** the walk changed from `drop_to < result.len() - 1 && role == Tool` to `drop_to < result.len() && role == Tool` (:1110), and the drain is now conditional: when the walk reaches `drop_to == result.len()` — i.e. every message from index 3 to the newest is a Tool result, so the surviving tail IS one open batch ending on the newest message — the loop `break`s and keeps the batch whole (:1113-1123, with a comment citing round-1 HIGH 1 and the `validate_request_messages` dangling-`tool_call_id` rejection). A non-Tool boundary anywhere in the tail still drains: the walk stops at the first non-Tool, so the new tail (`old result[drop_to]`) never starts on a tool result. Exactly the required semantics, and strictly safer than round-1's suggested minimal form (which keyed the break on the walk exiting *on* a Tool with the old `len-1` guard).
- **Drain cannot orphan by construction:** `drain(2..drop_to)` with `drop_to` = first non-Tool ≥ 3 removes the batch's call (index ≥ 2) together with every result that follows it contiguously — a tool result at index < drop_to always has its call in `[2, drop_to)` too (a call immediately precedes its results; indices 0-1 are system/summary and cannot carry `tool_calls`). Dropping a whole batch keeps pairing intact; the tail always restarts on a non-Tool message.
- **Termination still holds:** every iteration either breaks or drains `2..drop_to` with `drop_to ≥ 3` (≥1 message removed), and the while condition requires `result.len() > 3`; the inner walk is bounded by `result.len()`. The `dropped` subtraction and the exact-measure argument are unchanged from the round-1-reviewed shape (same `try_tiktoken_bpe()` instance as `count_tokens`, `saturating_sub`). The "totality yields to the untouchable core" outcome is now documented in the fn doc (:1082-1086) — the second half of round-1's fix direction.
