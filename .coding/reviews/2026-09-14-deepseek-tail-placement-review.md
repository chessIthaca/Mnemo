**R2 (low) — tests.rs:2508/2526/2533: stale CapturingProvider helper docs.** :2508 "the DeepSeek fold-volatile-tail path" and :2533 "DeepSeek's fold-volatile-tail" reference a removed mechanism; :2526 (`new_local_with_tails` doc) is factually false now — "tail folded into the leading system message, no footer" — the Local branch sends user-role tail+footer. **R3 (low) — request.rs:370–379: trailing-system exclusion is role-keyed; user-role tails are now inside the harness prefix-cache window, and the comment says otherwise.** `trailing_systems` counts only `Role::System` messages, so on DeepSeek/Local the volatile tail + footer are included in `cacheable_len` and in the fingerprint — contradicting both the comment ("excluded from the prefix cache and always serialized fresh") and the L3 design rationale (SPEC 7c8d90cd: excluded because "they disappear between iterations, so caching them would make the cache never hit" — still true, but the role-keyed count no longer implements it). Correctness is NOT affected: the cached entry is validated by recomputing `fingerprint_prefix` over the CURRENT `messages[0..c.len]` (role-hashed, request.rs:143), so a hit can only reuse bytes byte-identical to what a fresh build would emit. Effect is limited to the harness-side single-slot PrefixCache on DeepSeek/Local degrading to hit-only-on-byte-identical-retry (full rebuild per iteration otherwise — same cost class as the fold era, no regression; the provider-side cache, which this fix targets, is unaffected). Fix: count the trailing run regardless of role (take_while role is System OR the tail_as_user pair — simplest: exclude a trailing run of any non-tool role matching the two pushed messages, or explicitly take the policy into account), or at minimum correct the comment to state the role dependence.

**R4 (low) — turn.rs:1047: swap-path suggestion role keyed to `old_provider`, but the post-swap requests are served by the NEW provider.** In `handle_pending_swap`, the summarization runs on the old provider and the swap then completes; the provider snapshot taken after the call reflects the NEW provider (comment at :896–899), so subsequent requests in the same turn go to it. Swapping TO a DeepSeek-vendor/Local model from a non-user-role vendor injects the buffered text-only steer as a SYSTEM message into the conversation the new vendor will receive — a mid-conversation system block (not trailing — tail+footer always follow, so the echo invariant holds; same shape class as the pre-existing index-1 summary, and narrow: swap + oversize history + buffered steer). It nonetheless contradicts the helper's stated purpose at the one site where the provider identity is in transition. Fix: key the decision to the swap target, `pending.provider` (in scope at the re-injection site) — a user-role suggestion is universally acceptable, so the fix is safe even when the swap is interrupted and the old provider keeps serving.
