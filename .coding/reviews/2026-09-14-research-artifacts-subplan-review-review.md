## Findings

### F1 (HIGH) — `abandon_plan` never sets `review_required`: the same leak D closes is still reachable by ABANDONING the sub-plan

`src/workflow/mod.rs:1015-1027` (`abandon_plan`) pops the active frame and sets the state, and never touches `review_required`; the flag is set in exactly one place, the sub-plan POP branch of `complete_step` (`src/workflow/mod.rs:865-875`). So this sequence still ends unreviewed:

1. research root (Executing, filter = `ExecutingResearch`),
2. `create_plan` → implementation sub-plan pushed (`src/workflow/mod.rs:607-610` keeps the flag untouched on a push),
3. the sub-plan edits source (its own filter admits `file_write`/`file_edit`),
4. **`abandon_plan`** — e.g. the stale/wrong-approach case the tool's own doc names — pops it without setting the flag,
5. the root's final `complete_step` → `PlanKind::Research` + `review_required == false` → `WorkflowState::Complete`, `reviewed = true` (`src/workflow/mod.rs:888-896`).

The source edits on disk are then never reviewed — the exact defect class plan D exists to close, reached by a sibling call rather than the completion path. This is not a design question: the plan's own trap 6 asks for the conservative reading ("if the implementation sub-plan is later abandoned, the root still goes to Reviewing — a reviewer PASS on an (almost) empty diff is cheap and safe; do not add 'smart' clearing"), so the implementation diverges from the plan text here.

Suggested fix (3 lines, mirrors the completion path, keeps trap 6's "no smart clearing" stance): in `abandon_plan`, before the pop, mark `self.review_required = true` when `self.stack.len() > 1 && matches!(frame.plan.kind, PlanKind::Implementation | PlanKind::BugFixing)`. Note the intent is narrow — the ROOT's own abandonment while Reviewing stays the pre-existing sanctioned escape hatch (`abandon_plan`, "un-completable review"), which I am not asking to change.

Test to add: `abandoned_implementation_subplan_still_forces_review` — research root, push implementation sub-plan, `abandon_plan`, complete the root → state `Reviewing`, `reviewed == false` (fails without the fix).

### F2 (LOW) — the artifact judgment compares a re-written STRING, not the resolved path: two concrete mismatches

**(a) symlink/junction under `.coding/` → source is writable under a research plan, with nothing downstream catching it.** `is_research_artifact_write` resolves LEXICALLY only (`validate_for_creation`, no filesystem access — `src/agent/dispatch.rs:62-67`) and judges that; the file tool's ladder then canonicalizes the real target and re-checks protection on the CANONICAL path (`src/tool/agent/sandbox.rs:312-318`) but has no corresponding artifact re-check. With `.coding/link` a symlink (POSIX) or a directory junction (Windows — `mklink /J` needs no elevation) pointing at `src`, `file_write`/`file_edit` on `.coding/link/lib.rs` is granted at dispatch, and the ladder resolves it to `<root>/src/lib.rs` — inside the root, not protected — and writes it. The file tools are AutoRun on non-protected paths, so this is a silent source edit under a research plan, i.e. the invariant "research produces no source diff" broken with no approval prompt. The asymmetry is the tell: the protected check gets a canonical re-check in the ladder, the artifact boundary gets none. The doc claims at `src/agent/dispatch.rs:53-54` and `src/tool/agent/sandbox.rs:266-272` are correspondingly stronger than the enforcement.

Cheap hardening that keeps the lexical path for the not-yet-existing case: in `is_research_artifact_write`, when `sandbox.validate(Path::new(raw))` succeeds (target exists), ALSO require `is_artifact_write_target(&canonical)` — and/or canonicalize the parent when it exists. Test: a `.coding/<link-to-src>/x.rs` fixture must not be an artifact write.

Why LOW and not HIGH, stated honestly: the research filter is documented as a nudge, not a sandbox (`src/tool/mod.rs:1576-1578`), and `shell` can already write a file under a research plan — but shell is approval-gated while the file tools are AutoRun, so this is a silent route the change's own doc comment asserts cannot exist. It also requires the link to be planted (a committed symlink or a deliberate junction).

**(b) POSIX backslash spelling is granted while naming a non-artifact path.** `is_artifact_write_target` builds its comparison string with `replace('\\', "/")` (`src/tool/agent/sandbox.rs:279-282`). On macOS/Linux a backslash is a literal name character, so `file_write` with `.coding\x.md` (ONE component) is judged as `.coding/x.md` → granted, while the real target is `<root>/.coding\x.md` — a stray file in the repo ROOT, outside `.coding/`. Likewise `.coding\../src/lib.rs` resolves (POSIX) to components `.coding\..` / `src` / `lib.rs` → a stray subtree; no traversal is possible from a single component, so this is misplaced litter inside the root, not a source overwrite — hence LOW. But the error direction is wrong for a GRANTING predicate; the same idiom in `is_protected_write_target` is a REFUSAL, where a false positive is fail-safe. Fix: compare against the resolved relative path's components (`rel.components()` / `Path::starts_with(".coding")`) instead of a re-written string, or apply the `\`→`/` fold only under `cfg(windows)`. Test: `.coding\x.md` must not be an artifact write.

### F3 (LOW) — trailing dot/space evades the protected prefixes on Windows, and the new grant makes it reachable from a research plan

`is_protected_write_target` compares the `.coding/plans|reviews|knowledge/` prefixes literally (`src/tool/agent/sandbox.rs:232,236,239`) and the DB/backlog names exactly (`:221-231`), while the `.git` component check nine lines below trims trailing dots and spaces per component, with a comment stating exactly why — "Win32 path normalization strips them, so `mkdir(".git.")` creates the real `.git`" (`:246-252`). Windows sequence: `file_write` with `.coding/plans./sub/x.md` —

1. dispatch: rel_str `.coding/plans./sub/x.md` starts with `.coding/`, the protected prefix test misses → **GRANTED**;
2. the tool: `validate_for_write` step 1 fails (parent `.coding/plans./sub` does not exist), step 2 falls back to the LEXICAL `validate_for_creation`, step 3's protected check runs on that lexical path and misses again, step 4 `create_dir_all` creates the REAL `.coding/plans/sub` (Win32 strips the dot), step 5 writes the file inside the protected tree (`src/tool/agent/sandbox.rs:310-335`).

Overwriting existing protected files remains impossible — when the parent exists, step 1 canonicalizes and the protected check fires on the real path — so the impact is planting new files/subtrees inside a protected directory rather than corrupting live state (a planted plan doc is not picked up: `stack.json`, the thing that names plan files, is itself protected and cannot be overwritten). The root cause is pre-existing (an implementation plan can do the same today), but this change is what makes it reachable from a research plan, and focus point 2 asks for it explicitly. Fix: apply the existing `.git` idiom — trim trailing dots/spaces per component before the `.coding/...` prefix comparisons (one shared helper keeps the two checks consistent). Test: `.coding/plans./x.md` and `.coding/reviews./x.md` must be refused as protected targets.
