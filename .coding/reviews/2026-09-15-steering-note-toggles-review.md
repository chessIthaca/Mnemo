### LOW 1 — `search_nudge` misses the alternation-nudge emission shape (the checkbox does nothing for it)

- Registry: `frontend/src/lib/delegationNotes.ts:123-136`. Emission: `src/tool/agent/search.rs:659-667` (`symbol_nudge` delegates to `alternation_nudge`), text built at `search.rs:604-627`, wrapped as `note: …` by `with_note` (`search.rs:998`).
- The alternation note is a *documented* SearchNudge emission (the marker substring "is an indexed symbol" is in every resolved entry, so `steering_stats.rs` counts it — `SEARCH_NUDGE_MARK`), yet the frontend matcher set is `linePrefixes: ["AUTO-DELEGATED"]` plus two anchored patterns that require a leading `'name'` or `the symbol 'name' (from pattern '…')`. The real line begins `note: from the alternation pattern '…': …` → **no matcher fires**.
- Reproduced live during this review: my own `search` call with pattern `steering_notes|SteeringNotesPatch` returned exactly
  `note: from the alternation pattern 'steering_notes|SteeringNotesPatch': 'steering_notes' resolves to 'steering_notes_round_trips', an indexed symbol — graph_context(id=…) …; prefer the graph tools for symbol hunts (search is for text)`.
  With "Search symbol nudge" unchecked, that line stays visible in the ToolCard. Note also `search.rs:609`: inside the alternation note the `name == branch` entries are emitted **unquoted** (`{name} is an indexed symbol — …`), which no pattern covers either.
- The entry comment ("Three real shapes") is therefore also wrong — there are four.
- **Fix:** add the shape to the entry, e.g. `linePrefixes: ["AUTO-DELEGATED", "from the alternation pattern"]` (prefixes already match the `note: `-unwrapped text), or the narrower `linePatterns: [/^(?:note: |NOTE: )?from the alternation pattern '[^']*': .*is an indexed symbol/]`; extend the comment and add a `LINES`/strip case to `delegationNotes.test.ts`.

### LOW 2 — the collapsed card's error summary renders the stale-read note unfiltered

- `frontend/src/components/chat/Message.tsx:651-654` renders `toolErrorSummary(lastCall.result.output)` — the failed result's first non-empty line (`toolCardPaths.ts:607-615`) — with no steering filter, even though `hiddenSteeringNotes` is already in scope two dozen lines above (`Message.tsx:449`).
- A failed `file_edit`'s output *is* that line: `old_string not found in file — the content has likely drifted from your last read. Re-read the file (read_files, this exact path) …` (`src/agent/dispatch.rs:1568`, appended by `file_edit`'s `with_fresh_read_nudge`). So unchecking **Stale-read note** still shows the note in the un-expanded card header; only the expanded `<pre>` is filtered (`Message.tsx:812`). Same for any kind that leads a failed result.
- **Fix:** `const errSummary = filterSteeringNote(toolErrorSummary(lastCall.result.output), hiddenSteeringNotes) ?? "";` then use `errSummary !== ""` / `{errSummary}`; add a source-contract assertion next to the existing render-site pins.

### LOW 3 — an absent `steering_notes` ignores a legacy `show_delegation_notes = true`

- `frontend/src/App.tsx:344` hydrates with `hiddenKeysFromConfig(settings.ui.steering_notes)`; `delegationNotes.ts:381-386` returns `DEFAULT_HIDDEN_STEERING_NOTES` (`["auto_delegated"]`) when the object is missing. A user whose config says `[ui] show_delegation_notes = true` and whose backend predates the table (partial upgrade / stale binary) gets the delegation notes **hidden** — the legacy preference is silently dropped, and the same user's next Chat save then persists `auto_delegated: false`, making it permanent.
- Narrow (frontend and Rust ship in one binary), but the review asked for this path explicitly and the fix is one argument: `hiddenKeysFromConfig(cfg, legacyShowNotes)` where the legacy boolean seeds only the `auto_delegated` default (absent table + `true` → `[]`, else → `["auto_delegated"]`); `settings.ui.show_delegation_notes` is still on the DTO (`tauri.ts:466`).

### LOW 4 — the "first-line scoped … never hidden" doc claim is stronger than the implementation

- `docs/CONFIGURATION.md:9` and `docs/FEATURES.md:42` both assert: "the match is first-line scoped, so a file's content that merely quotes a note text is never hidden."
- True for the search/read paths (a match is anchored at line start and every result line carries a `path:line:` preface or a line number). Not true for the paths that filter a **whole output**: `stripSteeringNotes` runs over every line of the generic `<pre>` and of the shell stdout/stderr, so a `shell cat` of a markdown file whose line begins at column 0 with `TIP: for file-content search …` (or any echoed marker) *is* hidden; the `edit_stale_read` and `graph_miss` patterns are deliberately unanchored tail-chasers and can match a quoted file line containing the full drift clause.
- **Fix (docs):** reword to what the code does — "the match is anchored at the start of a line (or to the note's own marker shape); search/read results carry a path or line-number prefix, so file content that merely quotes a note is not hidden" — and, if you want the strong guarantee to be literally true, restrict the shell path to the leading note block instead of filtering the whole stream.
