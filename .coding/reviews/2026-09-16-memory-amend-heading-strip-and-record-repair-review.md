### LOW 1 — a stamp-shaped heading whose attribution group contains a colon is NOT stripped, so the doubled heading can still land (silently)

`src/memory/knowledge.rs:861-890` (`leading_self_heading`). The head is delimited by the **first colon on the line** (`let colon = line.find(':')?;` :863, `head = line[word_len..colon].trim()` :864), so a colon *inside* the parenthesized attribution group truncates the head before its closing paren and the stamp-shape test fails:

- `"Amended 2027-01-14 (review L1: the message was wrong): the wording changed"` → `colon` lands after `L1`; `head = "2027-01-14 (review L1"`; branch 2 → `tail = "-01-14 (review L1"`, `tail.find('(') == Some(6)`, `tail[6..].ends_with(')')` is **false** → `stamp_shaped = false` → `None` → nothing stripped.
- Same for `"Amendment (plan 987fef4c: the nudge fix): …"` (branch 1: `head = "(plan 987fef4c"` does not end with `)`).
- Second instance of the same root cause: a heading line with **no colon at all** (`"Amended 2027-01-14"` on its own line, text on the next) never reaches the shape test — `line.find(':')?` returns `None`.

Result: `amend` prefixes its own stamp and the record again carries two headings, one of them contradicting the tool's date — the exact defect this plan exists to kill — and the caller gets **no `NOTE: stripped …`**, so the strip is silent when it does not fire. The acceptance list's shapes (all colon-terminated, no interior colon) are all handled, so this is a gap outside the settled scope, not a regression; and the new repair path (b) makes the residual fixable in-tool, which is what keeps it LOW rather than HIGH. Suggested close (pick one): iterate successive `:` positions on the first line until one yields a stamp shape (or, when the head opens a `(` group, terminate at the colon following that group's `)`), plus a `strip_self_headings` case for `"(review L1: …)"`; **or** accept the residual explicitly in `strip_self_headings`' doc comment (it currently promises the shapes without naming this exclusion).

### LOW 2 — `replace_in_body`'s doc comment overstates the bypass: the digest shape IS reachable through the repair path (deliberately)

`src/memory/knowledge.rs:801-806`. The **primary** justification is sound and I verified it in code and test: `update()`'s guard fires on `candidate.trim().len() < current.trim().len()` (:992) plus a last-line `.coding/knowledge/` pointer tail, so the doubled-heading collapse — which shrinks the body while it still ends in a pointer tail — would be wrongly refused (`replace_in_body_repairs_record_text_without_digest_guard_interference` asserts exactly that refusal at :1650-1656). Keeping the repair path outside the guard is the right call.

The clause *"a unique-substring replacement cannot lose one"* is not literal, though: `replace_in_body(rel, "<the verbatim body minus the pointer tail>", "")` leaves a body that is **just the pointer tail** — the 2027-01-09 digest-collapse shape, smaller than the original, accepted by the code. So the guard's invariant ("a row digest must never replace the file's body") is deliberately not upheld here; what actually closes the *accident* is the verbatim-match rule (a condensed/paraphrased `find` returns 0 matches → `"not present"`), so only a caller that deliberately spells out the text it deletes can shrink a record toward a pointer. No behavior change is needed or possible without breaking the intended repair — suggested close: reword to "cannot *silently* replace a body — the caller must spell out the exact text it removes", so a future maintainer does not build on an absolute that the code does not enforce.
