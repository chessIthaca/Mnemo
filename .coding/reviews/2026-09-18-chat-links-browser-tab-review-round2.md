### LOW — the `mailto:` scheme case (`MarkdownLink.test.tsx:187-195`) still cannot fail for a widened allow-list

The round-1 LOW-1 remedy was applied verbatim — `async` + `await flushRouter()` (`:192`) and `rightPanelVisible: false` in the `beforeEach` (`:114`, with `pendingBrowserUrl: null` at `:116` and both mocks reset/re-armed at `:118-121`) — and it does its job for the sibling case: `:197-210` snapshots the store and asserts `pendingBrowserUrl === null`, so a `data:`/`file:` target wrongly handed to the tab now registers as a non-null store value after the flush and that case fails. The `mailto:` case asserts only `pendingFileOpen === null` and `openExternal` **not** called (`:193-194`).

Under the exact regression that case names (a non-openable scheme is no longer ignored), the wrongly-accepted target goes to the **Browser tab**, not to the OS browser: `openMarkdownTarget` → `openChatLink` → `requestBrowserOpen("mailto:a@b.c")` (`openChatLink.ts:83`) writes `pendingBrowserUrl` + `rightPanelTab: "browser"` + `rightPanelVisible: true` in one store write (`useAgentStore.ts:894-903`) and calls no `openExternal`; `pendingFileOpen` is untouched. So all of the case's assertions stay green while the click has produced exactly the visible side effect the case title forbids — panel revealed, tab switched, and (once the backend's `normalize_url` refuses the scheme) an error panel in the Browser view. The `await flushRouter()` added in this round is inert for this case: neither assertion observes the channel the regression would use.

Reachability, which is why this is low rather than higher: from the chat a `mailto:` href cannot even reach `openChatLink` unless `openMarkdownTarget`'s own `/^https?:\/\//i` gate (`MarkdownLink.tsx:41`) is *also* widened, so the regression is a two-place change; and that same widening is caught end-to-end by the sibling case in the same file and by the router-level suite (`openChatLink.test.ts:97-116`, which awaits `openChatLink` per target, `mailto:` included). No shipped behaviour is wrong — this is a test-strength gap only.

Fix (one line, mirroring the sibling case): snapshot the store after the flush and assert the tab channel too, e.g.
`const s = useAgentStore.getState(); expect(s.pendingBrowserUrl).toBeNull(); expect(s.rightPanelTab).toBe("plan");`

**LOW 3 (effect hygiene) — CLOSED.** `loadIntoChild` is `useCallback(async (target) => { … }, [])` (`BrowserView.tsx:111-144`). Its body captures only: `loadToken` (ref, `:61`), `setUrl`/`setLoadedUrl`/`setError` (useState setters, stable identities), `areaRef` (ref, `:58`), the module-scope imports (`browserNormalizeUrl`, `browserWebviewEnsure`, `browserWebviewNavigate`, `errMsg`) and `window.devicePixelRatio`, read at call time (`:125`). **LOW 4 (ordering) — CLOSED.** The token is taken after the empty-target guard (`:112-113`), so an empty URL-bar Open neither starts a chain nor supersedes an in-flight one. Guards follow every await: `:118` (after normalize), `:133` (after ensure, inside the `if (el)` block), `:136` (after navigate), `:141` (in the catch). Only the newest chain can act: a chain can dispatch `browserWebviewNavigate` only if at its last check no newer chain has started (a newer chain's `++loadToken.current` precedes all of its awaits, and there is no await between a chain's last check and the synchronous `invoke`), so the last-dispatched navigate always belongs to the newest-started chain — including the same-URL-twice case. `setLoadedUrl`/`setError(null)` sit immediately behind the `:136` guard with no await in between, and the catch is guarded: a superseded chain cannot write loaded state or an error, cannot clear the newest chain's error, cannot suppress its success, and the "newest fails while an older one succeeded" case resolves correctly (the older chain bails at its next guard and writes nothing; the newest writes `setError(errMsg(e))` and the error banner renders above its unchanged state). URL-bar Open/Enter behaves as before: same `onClick={() => void openUrl()}` (`:244`) / Enter (`:222`), same side-effect sequence; the only deltas are the intended ones (an Open now supersedes an in-flight chain instead of interleaving with it, and an empty Open is a true no-op — `loadIntoChild` returns before `setUrl`).
