### LOW 1 — the 60 ms throttle has no timer arm: a quiet stream is withheld, and the two marker-gated tests only pass on Windows by accident of PowerShell's startup latency

**Files:** `src/tool/agent/shell.rs:530-552` (the read loop), `:515-519` (the doc that implies a timer), `:1052-1055` (the shell-side marker-gated test), `src/agent/tests.rs:4517-4546` (the pin's watch), `docs/FEATURES.md:25`.

**What is wrong.** `emit_pending` is called from exactly one place — after a successful `pipe.read()` returns (`shell.rs:548-551`; grep confirms `last_emit` and `STREAM_FLUSH_INTERVAL` exist nowhere else). There is **no timer/sleep/`select!` arm**, so the elapsed-time check is only *evaluated when new bytes arrive*: a chunk that becomes pending less than 60 ms after the previous emit is not emitted until the next read returns or the pipe hits EOF. Two consequences:

1. **The two marker-gated tests depend on the child's first bytes arriving ≥ 60 ms after the reader task starts** (`last_emit = Instant::now()` is set at task start, `shell.rs:532`). On Windows that holds for free: `powershell -Command` takes hundreds of ms to boot, so by the time `one` reaches the pipe the condition is satisfied and the delta is emitted. On Unix the fixture runs `/bin/sh -c "echo one; while [ ! -f marker.txt ]; do sleep 0.05; done; echo two"` — `sh` fork/exec + a builtin `echo` land in single-digit milliseconds, the condition is false, the reader then blocks in `read()` waiting for output that only the marker can unblock, and the marker is only written after the first delta is received. The result: on macOS/Linux `streams_incremental_deltas_before_the_child_exits` fails after its 30 s timeout (`shell.rs:1052-1055`, `.expect("the child never produced its first line")`) and the pin fails after its 30 s timeout (`tests.rs:4557-4562`, `observed.unwrap_or_else(...)` → `panic!("no ToolOutputDelta reached the fan-in channel while the command ran")`). Both tests are new in this changeset and neither is `cfg`-gated, so the macOS suite fails (2 × 30 s burn, then failure) and the app-side behaviour is timing-luck even on Windows.
2. **User-visible variant of the same gap:** a command that prints a line and then works quietly (`echo start` + a long silent step, a build waiting on a lock) shows *nothing* on the card until the next output or exit — the exact "looks like a hang" symptom the feature exists to remove. `docs/FEATURES.md:25` sells a 60 ms cadence and `shell.rs:517` ("a short command must not wait the timer out") reads as if a timer existed.

**Why it matters.** Multi-platform neutrality is an explicit review gate for this project, and the round-1 report's claim that "both macOS and Windows take a working branch" was wrong: the non-Windows branch is not taken, the fixture deadlocks against its own gate until the timeout. The feature's latency bound is also weaker than documented.

**Concrete fix.** Give the loop a timer arm (the read path unchanged) so a pending chunk is flushed once the interval elapses with no new data:

```rust
loop {
    tokio::select! {
        res = pipe.read(&mut buf) => { /* existing Ok(0)/Err break + accumulate + emit check */ }
        _ = tokio::time::sleep_until(last_emit + STREAM_FLUSH_INTERVAL), if !pending.is_empty() => {
            emit_pending(&mut pending, false, stream, &sink, &streamed, &noted);
            last_emit = Instant::now();
        }
    }
}
```

That makes both tests deterministic on every platform (no reliance on process-start latency) and delivers the documented cadence. (Re-run the shell.rs streaming tests and the pin afterwards; the marker-gated ordering assertions should still hold unchanged.)

### LOW 2 — the clamp narrows but does not close the two-reader overshoot; the comment now claims the cap *is* a bound

**Files:** `src/tool/agent/shell.rs:591-604` (load → room → clamp → `fetch_add`), `:59-63` (const doc), `:594-597` (the claim), `:1147-1151` / `:1195-1199` (the `<= STREAM_CAP` assertions), `docs/FEATURES.md:25`.

**What is wrong.** `used = streamed.load(Relaxed)`, `room = STREAM_CAP - used` and the clamp are not atomic with the later `fetch_add` (`:606`): two readers racing can both read the same `used = U` and each clamp to the same `room = CAP − U`, so the live view can still reach `U + 2·room = CAP + room`. `room` is bounded by one pending chunk — at most `STREAM_FLUSH_BYTES` (8 KiB) plus one 4 KiB read, i.e. **< 12 KiB (≈4.7 % over 256 KiB)** — and the truncation note's own ~57 bytes are never counted at all. The round-1 finding said "soft budget, ±one chunk per racer"; the clamp roughly halves that, but the code comment at `:594-597` ("without the clamp each could add a full chunk and overshoot `STREAM_CAP` — the cap is documented as a bound") and the parent's fix summary ("a real byte bound even with two racing readers") overstate what was achieved. The `<= STREAM_CAP` assertion in the new multi-stream test can in principle fail on that race (~1e-4/run — negligible in practice, but it is not the invariant it claims to be).

**Why it matters.** Display-only and tiny in absolute terms, but it is exactly the kind of "documented guarantee the code does not give" that rounds 1 and 2 exist to catch; a later reader will trust the comment.

**Concrete fix.** Either reserve atomically, e.g. loop `compare_exchange` on `streamed` (compute `room` from the observed value, clamp, then `compare_exchange(used, used + emitted.len())`, retry on failure), or keep the clamp and reword to "past `STREAM_CAP` chunks are clamped to the remaining budget; under a two-reader race the live view can overshoot by at most one pending chunk (< 12 KiB)". If the assertion stays strict, keep the comment honest instead.

## Verified as unaffected by the fix round

## Residual risk accepted
