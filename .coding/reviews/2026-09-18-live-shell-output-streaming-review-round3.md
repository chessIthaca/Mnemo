### LOW 1 — CLOSED: the timer arm exists and delivers the cadence

**Evidence.** `src/tool/agent/shell.rs:559-572` — the new arm is
`_ = tokio::time::sleep_until(tokio::time::Instant::from_std(last_emit + STREAM_FLUSH_INTERVAL)), if live && !pending.is_empty() => { emit_pending(&mut pending, false, …); last_emit = Instant::now(); }` (guard `:569`, deadline `:567-569`, emit + reset `:570-571`); the read arm is unchanged (`:539-558`). The doc above `pump_stream` states the timer enforcement (`:517-519`).

**(a) Cadence — yes, ≤ one interval of becoming pending, read-independent.** `last_emit` is written only at task start (`:534`) and by a flush (read path `:556`, timer `:571`), so whenever `pending` becomes non-empty its `last_emit` is ≤ that moment: the read path either drains `pending` (resetting `last_emit` at that instant) or leaves it alone. The select then arms a deadline at `last_emit + 60 ms` ≤ arrival + 60 ms and the loop re-arms it identically if reads keep winning, so a pending chunk is flushed within ≤ one interval (+ scheduler jitter) with no dependence on further reads. No stale-past deadline can arise: a deadline already in the past implies `elapsed ≥ 60 ms`, which the read path flushes on the spot.

**(b) No busy-spin, no wakeup pathology.** (i) The `live && !pending.is_empty()` guard disables the timer whenever the sink is inactive or nothing is pending, so an idle read costs zero wakeups (matching the arm's own comment). (ii) The body resets `last_emit` **unconditionally** — including when `emit_pending` early-returns with `cut == 0` for an incomplete UTF-8 sequence (`:608-610`) — so the next wake is a full interval away; a dangling partial sequence costs at most one no-op wake per 60 ms, bounded, not a spin. (iii) Re-arming from the freshly reset `last_emit` (`:571`) is what prevents an immediate refire. (iv) If reads keep winning, either the byte rule or the elapsed check flushes on the read path, so the timer arm can never starve.

**(c) EOF / read error / `!live` still correct.** Read arm `:539-546`: `Ok(0) | Err(_) => break` (unchanged semantics; short-read bytes already collected stand). EOF exits the loop into the live-gated force flush `:575-580`, which drains the lossy remainder — no double emission, since `emit_pending` drains what it emits. `!live` continues before `pending.extend_from_slice` (`:548-550`), so nothing accumulates and the timer guard is permanently false (the sink-inactive path is byte-for-byte the old one).

**(d) macOS/Linux determinism — yes, and no longer by luck.** On Unix the fixture (`:1077`) lands its first bytes in single-digit ms; whether or not the read-path check (`:552-554`) happens to fire, the timer arm flushes the first delta within ≤ 60 ms, so the 30 s receives (`:1087-1090`) are not on the critical path and the ordering gate (marker written only after the first delta, `:1095`) holds. The Windows branch is unchanged and still deterministic (PowerShell's startup satisfies the elapsed check at the first read). **Honest limit:** I cannot exercise the Unix branch on this Windows box (read-only reviewer, no shell; the fixture is `cfg!(target_os = "windows")`-selected). That limitation does not weaken the argument, because the reasoning is timing-independent — it no longer assumes anything about process-start latency in either direction. The remaining Unix-side uncertainty is chunk *boundaries*, noted under residual risk.

### LOW 2 — CLOSED: the cap is now a real bound under two racing readers

**Evidence.** `src/tool/agent/shell.rs:613-640` (reservation loop), `:641-643` (emit after the successful CAS), `:644-648` (note gate `clamped && !noted.swap(…)`), const doc `:59-63`.

- **Reservation == emitted bytes.** The CAS writes `used + emit_text.len()` and the emit uses that same `emit_text`, untouched between the successful CAS and `sink.emit` (`:641-643`). `room = STREAM_CAP.saturating_sub(used)` (`:623`) and `truncate_to_boundary` only shortens (`read_files.rs:55-64`), so every successful CAS writes a value ≤ `STREAM_CAP`; `streamed` is monotone (each CAS moves `used` upward only), so the sum of all emissions over both readers — i.e. the final `streamed` — is ≤ `STREAM_CAP`. The only uncounted bytes are the one note (~57 B, gated once per call by the shared `noted`), exactly as the comment states (`:616-618`). The round-2 theoretical overshoot and the ~1e-4 flake in `emitted.len() <= STREAM_CAP` are gone: that assertion (`:1182-1186`, `:1230-1234`, note stripped first) is now a genuine invariant.
- **Termination.** `used` is non-decreasing across retries (a failed CAS installs the observed `actual` ≥ the value it held), so `room` is non-increasing and `emit_text` can only shrink; either the CAS succeeds or the chunk clamps to empty and breaks (`:628-630`). Once `used ≥ STREAM_CAP` every further chunk terminates on the empty branch, and a `compare_exchange_weak` spurious failure just re-runs the same CAS — the standard weak-CAS pattern, no livelock.
- **`clamped` ≡ the old `crossed`.** It is set exactly when the attempt's text exceeded the room (`:624-627`), and because `room` can only shrink on retry a later attempt cannot un-truncate — so `clamped` ⇔ the emitted slice was cut, the `room == 0` case included (empty ⇒ break, no emit, note still fires once). Tests that key on "one note when the budget truncated something" are unaffected.
