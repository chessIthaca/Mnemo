### L1 — The "every delta precedes its ToolResult" invariant is only enforced on the success path (0 high, low)

**Files:** `src/tool/agent/shell.rs:374-398`; `src/agent/dispatch.rs:481` (sink construction), `dispatch_with_interrupt`; `.coding/knowledge/spec/2027-01-11-live-shell-output-streaming-sink-at-dispatch-dis.md` ("the readers are joined BEFORE the result is returned, so every delta precedes the `ToolResult` on the same FIFO fan-in channel").

**What is wrong.** The success path is genuinely ordered: `out_task.await` / `err_task.await` (`shell.rs:396-399`) complete before `execute_streaming` returns, and the turn loop emits the `ToolResult` only after that, on the same FIFO mpsc — so every chunk is on the channel ahead of the result. Two paths do not have that property:

1. **Timeout** (`shell.rs:382-393`): `out_task.abort(); err_task.abort();` then `return ToolResult::error(...)`. `abort()` is *asynchronous and un-awaited*: on tokio's multi-thread runtime a reader can be mid-poll on another worker (its only awaits are the pipe reads, so a poll that already returned bytes runs `emit_pending` → `sink.emit` → `try_send` synchronously), so a chunk can be sent after the error result was emitted.
2. **Agent interrupt** (`dispatch_with_interrupt` drops the tool future): dropping a `JoinHandle` does **not** abort the task, so the two orphaned readers keep draining the (soon EOF'd) pipes and can emit after the call's synthetic result. Nothing in the tool can observe that drop.

**Why it matters.** Not user- or model-visible today — the console arm is silent, and *both* frontend consumers gate on `result === null` (`agentEventReducer.ts:668`, `useAgentStore.ts:1132`), which is exactly the defence the shell comment at 383-386 claims to be replacing. The risk is the documentation: `channels.rs` honestly documents the exception ("a timed-out or cancelled call can leave a reader emitting after its result was sent") while the SPEC record and the shell comment state the ordering as absolute. A future consumer keyed only on `tool_call_id` would inherit the bug this claim denies.

**Concrete fix.** Make the timeout path actually enforce it (the cancel lands at the reader's next await, so this returns quickly):

```rust
out_task.abort();
err_task.abort();
let _ = out_task.await;   // Err(cancelled) — returns once the task yields
let _ = err_task.await;
```

and, because the drop-for-interrupt path cannot be fixed that way, soften `shell.rs:383-386` and the SPEC record to "joined before returning on the success path; a timed-out or dropped call may leave a reader emitting after its result, which consumers must drop" (or wrap the readers in an abort-on-drop guard if hard ordering must hold for interrupts too).

### L2 — The "one-time" truncation note is once per *stream*, the 256 KiB budget is a soft cap under concurrency, and the frontend tail is capped in chars, not KiB (0 high, low)

**Files:** `src/tool/agent/shell.rs:50-63` (constants), `:487` (`noted`), `:521-551` (`emit_pending`); `docs/FEATURES.md:25`; `PLAN.md:350`; `.coding/knowledge/spec/2026-12-29-tool-call-echo-map-every-llm-tool-call-echoes-no.md:8`; `frontend/src/hooks/agentEventReducer.ts:631`.

**What is wrong.**
1. `let mut noted = false;` is a local of `pump_stream`, i.e. **per stream**, while `STREAM_CAP` is one shared `Arc<AtomicUsize>` **per call**. A call whose stdout fills the 256 KiB budget *and* whose stderr also crosses it emits a second truncation note (stderr's own `noted` is still false). The three doc sites say "a 256 KiB live budget per call with a one-time truncation note once it is reached" — `emit_pending`'s own doc (`shell.rs:521-523`) is the accurate one ("this stream's live view is truncated with a one-time note").
2. The budget check is a non-atomic check-then-add across the two readers (`:545-553`): both can read the same `used` and each add up to one 8 KiB chunk, so the live view can reach ~272 KiB. Harmless as a *soft* budget, but it is stated as a bound.
3. Unit mismatch: the docs (and the knowledge record) say the frontend keeps a "rolling 16 KiB tail"; `LIVE_OUTPUT_CAP` is `16 * 1024` **UTF-16 code units** ("in chars" per its own doc comment, and the new cap test asserts `live.length === LIVE_OUTPUT_CAP` in chars). For astral/CJK output that window is up to ~64 KiB of bytes — and it is a different unit from the Rust side's byte budget, so the two numbers are not comparable as written.

**Why it matters.** No behaviour breaks, but the shipped docs describe a guarantee the code does not give, and the tests cannot catch it: the `STREAM_CAP` test in `shell.rs` drives stdout only (`live.matches(note).count() == 1` would pass with a per-stream flag either way).

**Concrete fix.** Either (a) move the flag into the shared per-call state — pass an `Arc<AtomicBool>` into both `pump_stream` calls and set/check it in `emit_pending`, so the note is once per call as documented (preferred if "one-time" means the card says it once); or (b) keep the per-stream flag and reword `docs/FEATURES.md:25`, `PLAN.md:350` and the knowledge amendment to "a one-time note on the first stream to reach the cap". Add a stderr-side cap test (both streams over the budget) either way. For (2), either clamp the emitted slice to the remaining budget (`let room = STREAM_CAP.saturating_sub(used); emit(&text[..room])`) or state "soft budget, ±one 8 KiB chunk per stream" in the comment. For (3), say "16 K chars (UTF-16 code units)" or leave the Rust byte budget and the JS char window explicitly distinguished.

### L3 — `applyToolOutputDeltas` writes state even when no delta matched (the reducer's pinned no-op contract does not hold on the production path) (0 high, low)

**Files:** `frontend/src/hooks/useAgentStore.ts:1121-1151`; `frontend/src/hooks/agentEventReducer.ts:659-680`; `frontend/src/hooks/useAgentEvents.ts:542-559`; `frontend/src/hooks/useAgentStore.test.ts:836-842`.

**What is wrong.** The batched action unconditionally builds `const transcript = [...agent.transcript]` and returns `{ agents: { ...s.agents, [id]: { ...agent, transcript } } }`. When every delta in the batch is dropped by the `result === null` guard (`:1132`) — exactly the late-chunk case L1's timeout/interrupt races produce, and the case the dispatcher *does* forward because it flushes before dispatching the `tool_result` — the store still installs a **new transcript array and a new agent object**, so every subscriber selecting the transcript re-renders the list for no change. The reducer returns the agent untouched in that case (`agentEventReducer.ts:679`), and `useAgentStore.test.ts:836-842` pins that no-op ("not even a cloned transcript, so a stray chunk cannot cost a re-render") — but the dispatcher routes **every** `tool_output_delta` into `outputBuffers` (`useAgentEvents.ts:542`) and applies them only via `applyToolOutputDeltas` (`flush`, `:441-461`), so in the app the reducer arm is reachable only from a direct `handleAgentEvent` call (tests/replay). The two paths were specified to share "the same guards"; they share the *guard predicate* and the cap helper, but not the no-op discipline the test relies on.

**Why it matters.** A wasted transcript re-render per late chunk (rare, but the very case the third line of defence exists for), and a parity gap between the two implementations that a reader of the reducer test would not suspect.

**Concrete fix.** Track a match flag and skip the write entirely when nothing matched:

```ts
let matched = false;
for (const delta of deltas) { /* … existing search … */ matched = true; … }
if (!matched) return s;   // zustand keeps the previous state object
```

and extend the batched test with `const before = agent(ID); applyToolOutputDeltas(ID, [{ tool_call_id: "ghost", text: "x" }]); expect(agent(ID).transcript).toBe(before.transcript);` (or assert the whole agent object identity).

### L4 — New tests wrap every live-output assertion in an existence guard (vacuous-pass risk) (0 high, low)

**Files:** `frontend/src/hooks/useAgentStore.test.ts:817-824` (append), `:855-859` (late chunk), `:875-885` (cap), `:906-914` (batched action); `frontend/src/lib/ipc-contract.test.ts` (the new `tool_output_delta` fixture case, ~`:195-205`), alongside the pre-existing guarded cases at `:165`/`:175`/`:205`.

**What is wrong.** Each new test locates the entry with `const tool = agent(ID).transcript.find((e) => e.kind === "tool");` and then asserts **inside** `if (tool && tool.kind === "tool") { … }` (resp. `if (first && first.kind === "tool" && second && …)`). If the entry is missing, renamed, or its `kind` changed — e.g. `reduceToolCallStart` regressing so no `kind:"tool"` entry is pushed — the body is skipped and the test reports green. The `LIVE_OUTPUT_CAP` test at `:862` is the clearest case: it would pass with a completely broken live-output append as long as the card were absent.

**Why it matters.** These tests are the only behavioural guard on the new reducer/batched paths (the Rust side has its own pin), and a false green on exactly the code the review is asked to trust is worse than no test. The pattern is pre-existing in this file (and in `ipc-contract.test.ts`, which the new case copies), so this is not a new invention — but the new cases are in scope and the guard makes them non-probative.

**Concrete fix.** Assert existence first, then use the narrowed entry:

```ts
expect(tool?.kind).toBe("tool");
const calls = (tool as Extract<TranscriptEntry, { kind: "tool" }>).calls;
expect(calls[0].liveOutput).toBe("one\nwarn\n");
```

or throw on the miss (`if (!tool || tool.kind !== "tool") throw new Error("tool entry missing")`). Apply to the four new cases in `useAgentStore.test.ts` and the new fixture case in `ipc-contract.test.ts`.

### L5 — The integration pin's doc comment (and the step-5 SPEC record) name the wrong approval path, and the "cannot hang" claim has one unstated edge (0 high, low)

**Files:** `src/agent/tests.rs` (the `dispatch_streams_shell_output_deltas_before_the_result` doc comment: "runs the REAL funnel under Autonomous mode, where ShellTool's NeedsApproval never prompts … so the call takes the auto-approved streaming path"); `.coding/knowledge/spec/2027-01-11-shell-live-view-dispatch-sink-integration-pin-pl.md`.

**What is wrong.** With `safety_mode: Autonomous` (`src/agent/tests.rs:47`) `needs_approval` returns false (`src/agent/approval.rs:23`: "Autonomous — no approval prompts at all"), so the call takes the **no-approval** call site — the third one, which clones `output_sink` and calls `dispatch_with_interrupt` without any approval event — not the safety-rules *auto-approved* shortcut (the `if denial …` branch of `execute_tool_call`). Secondary edge on the comment's "writes the marker on both paths, so a failure cannot hang the suite": that holds for the failure it is designed for (marker written after the 30 s watch timeout ⇒ the blocked child always escapes; a non-streaming regression fails on `observed` instead of hanging). **Concrete fix.** Reword the doc comment (and the SPEC record) to "the no-approval path (Autonomous ⇒ `needs_approval` false)"; optionally make the pin fail fast on an unexpected approval — the loop already records `unexpected` into its panic message, so add `assert!(unexpected.is_none(), …)` and/or wrap the join in an overall `tokio::time::timeout` so an approval-wait regression fails instead of hanging CI.

## What I verified and how

**1. Ordering (Q1) — holds for a completing call, three layers deep; the two abort/drop paths are L1.** Traced `shell.rs:361-399` (spawn → join before return), the turn loop's post-return `ToolResult` emission, and the frontend chain: `useAgentEvents.ts:542-559` buffers `tool_output_delta` into `outputBuffers`; the final `else` at `:560-564` calls `flush()` **synchronously before** dispatching any structural event, and `flush()` (`:401-462`) applies the output buffers (`:441-461`) before `handleAgentEvent` ever sees the `tool_result`; the store action requires `c.result === null` (`useAgentStore.ts:1132`) and the reducer requires it too (`agentEventReducer.ts:668`). The sink itself uses `try_send` (never `send`), so a full fan-in channel drops a chunk instead of blocking the reader — a drop, not a reorder.

**2. The integration pin (Q2) — genuinely proves incremental streaming; not flake-prone in the way that matters; exercises the real funnel.** It cannot pass with a non-streaming implementation: the child prints `one`, then blocks on `Test-Path marker.txt`, and the test only writes that file **after** the watch future has resolved — so without a mid-run delta there is no `one` to observe (the 30 s watch timeout expires, then the panic assertion fires; the marker write happens on both paths, so the child always escapes and the suite cannot hang). `first.contains("one")` can therefore only come from output emitted **while** the child was still alive, which is the property under test. Real funnel confirmed: `agent.execute_tool_call(...)` with a real `ShellTool` inside a `tempdir` sandbox, driven into Executing by `create_plan`, on a real `mpsc` fan-in channel. Platform-aware: `cfg!(target_os = "windows")` chooses PowerShell (`[Console]::Out.WriteLine`, which bypasses the output formatter's buffering that `Write-Output` suffers) vs `/bin/sh` `echo`, so both macOS and Windows take a working branch. Bounded: 30 s watch timeout + the tool's own timeout. Coverage/description caveats → L5.

**3. Rust sanity (Q3).** `pump_stream` (`shell.rs:475-515`) drains to EOF and accumulates *all* bytes into the returned `Vec<u8>`; `child.wait()` is awaited under `tokio::time::timeout` with the child moved into the future, so the timeout, an interrupt-drop, and a normal exit all resolve (kill_on_drop kills the process, dropping the reader futures closes the pipes) — no join/wait deadlock. Non-UTF8: incremental decode keeps only the complete prefix (`valid_up_to`) and carries the partial tail over; the final forced flush is lossy, exactly as the result's `from_utf8_lossy` is — so the result bytes are unchanged (pinned by the `streaming_preserves_the_result_byte_for_byte`-class test in the same file). Interleaving: stdout and stderr are independent readers with their own pending buffers and throttle clocks, merging in arrival order into one tail (a deliberate design, documented in the test comment at `useAgentStore.test.ts:819-820`). Concurrent calls: the sink is built per dispatch and carries the call id, the `streamed` counter and the reader tasks are per call, and the store's `getOrCreate` keys by agent — no cross-call state. Budget: `STREAM_CAP` shared per call, emitted bytes counted, and the accumulator never consults it, so a capped live view still yields the complete result; the note/cap edges are L2. Result path unchanged: raw bytes → `from_utf8_lossy` → `shell_filter` shapes only the `output` field shown to the LLM → grep/redirect nudges → `DEFAULT_TOOL_OUTPUT_CAP`/`cap_tool_output` applied in the same order as before, with the raw stdout/stderr still riding `data`.

**4. Approval security (Q4) — no leak.** The sink is constructed at `src/agent/dispatch.rs:481`, *before* the approval gate, but it is inert: nothing can call it except a tool that actually runs, and every denial/never-run return (`:406-464` region, plus the reviewer/c5 and stop-signal paths) returns before the sink is ever handed to a running tool; the approved and auto-approved call sites pass `output_sink.clone()` only after the gate. No new auto-approval, no bypass, and the WIP commit adds no branch anywhere in `needs_approval` / `force_prompt` / `never_auto_for` — so a denied or never-run command emits no delta.

**5. Unexhaustive matches / missed consumers (Q5) — none.** Rust: `AgentEvent::ToolOutputDelta` defined at `channels.rs:196` with its serializable twin (`:537`) and the `into_serializable` arm (`:747`); console `render_event` handles it as Silent (`console.rs:257`); the Tauri forwarder's `DeltaBatcher` passes unknown kinds through as structural events and `watchdog_note`'s catch-all deliberately skips per-chunk deltas (the same treatment `TextDelta`/`ToolCallArgDelta` get) — both crates compile, so no non-exhaustive match can exist (`src-tauri` 299/0 and root 2409/0 per the parent's run). The golden fixture (`frontend/src/lib/ipc-fixtures/event-tool-output-delta.json`) carries exactly the twin's field set (`kind`/`stream`/`text`/`tool_call_id`).

**6. Frontend correctness (Q6).** Reducer search is newest-first, kind-guarded, and requires `result === null` — a late chunk returns the agent **unchanged** (`agentEventReducer.ts:659-680`); `reduceToolResult` sets `liveOutput: undefined` (`:741-745`), so the tail dies exactly when the result lands. `appendLiveOutputTail` (`:642-648`) head-drops past `LIVE_OUTPUT_CAP` (16 K chars) and drops a leading lone low surrogate (the DC00–DFFF guard). The batched action uses the same helper and the same predicate; its only divergence is L3.
