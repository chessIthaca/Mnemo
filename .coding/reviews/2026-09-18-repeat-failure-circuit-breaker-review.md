## Findings

### LOW 1 — The corrective user message hijacks the auto-recall query (src/agent/turn.rs)

`auto_recall` (turn.rs:2212-2217) builds its query from the **last User-role message**:

```rust
let query = messages.iter().rev().find(|m| m.role == Role::User)...
```

The breaker pushes its correction as `Message::user_text(...)` (turn.rs:1643) — a User-role message that is now the last user message for the **remainder of the turn** (tool results are Tool-role, assistant turns are Assistant-role). Consequences after a correction fires:

1. The per-turn recall cache key (`last_recalled_user_query`) changes from the user's actual prompt to the correction text → one spurious fresh recall (re-embed + rescan + a `MemoryRecalled` transcript event).
2. The memory context injected into the system prompt is scored against the correction text (error verbatim + schema) instead of the user's request — likely irrelevant memories for the rest of the turn.

The design comment in `TurnState` ("the recall query is just the latest User-role message text, which tool-result appends can never change") predates this change and no longer holds — the correction is exactly a user-role append that changes it. Self-heals next turn; corrections are rare; so LOW. Suggested fix: in the `auto_recall` query lookup, skip harness-attributed messages (e.g., `filter(|m| !m.content.as_text().starts_with("[harness tool-call correction"))`), or record the recall query before the batch.

### LOW 2 — Stale module doc comment contradicts the new required field (src/tool/agent/git.rs:50-51)

The module doc still reads: "`subcommand` is not required — `action` alone can name the subcommand." The schema now declares `"required": ["subcommand"]` (git.rs:505). The runtime-forgiveness half of the sentence is still true (`resolve_git_subcommand`, git.rs:136-160, is untouched and still resolves action-only calls), but "not required" is now false at the advertised-schema level. The HOW-record amendment shipped with this change explicitly says the old "no `required` array, by design" note "is superseded for `subcommand` only" — the in-code comment should have been updated to match (e.g., "the schema marks `subcommand` required, but the runtime still forgives an `action`-only call").

### LOW 3 — Plan step 5's promised README.md update not delivered

Plan step 5 (`.coding/plans/a9875b73.md`) explicitly promises: "Update README.md (git tool section: enriched per-subcommand errors, required subcommand)". Either add the README note or amend the plan/step record to record why README needed no change.

## Verification of the requested checks (all pass)

- **Detection correctness.** The scan (`repeated_tool_failure`, turn.rs:3462-3475) runs at turn.rs:1575-1581, BEFORE the current result is pushed (push at :1583) — a match is always against a prior failure, and same-batch duplicates count (earlier results of the batch are already in `messages`). Window is `rev().take(50)` — bounded, last-50-messages. No false positives: (a) user denials — the current result is excluded via `!is_user_denial_tool_output(&result.output)` on the raw output, and since a match requires byte-identical content, a prior denial can only match if the current output carries the same denial substring → excluded either way; (b) "interrupted: not run" synthetics (`synthesize_not_run_results`, turn.rs:3397-3416, content "interrupted: not run (turn stopped)") — same byte-identity argument, and the substring is in `is_user_denial_tool_output` (:3444-3450); (c) successful results are stored without the `[tool error]` prefix, so they cannot equal a failure's prefixed content (except a pathological success whose raw output literally begins `[tool error] ` — vanishingly unlikely and benign if it fires). Tool-name match (`m.name`) prevents cross-tool matches; the correction itself is User-role so it can never match.
- **After-batch push position.** Anthropic (`build_request_json`, anthropic.rs:282-312): adjacent Tool messages coalesce into ONE user carrier of `tool_result` blocks; the correction is a separate user text message after that carrier. Anthropic combines consecutive same-role turns, and this exact shape (user text after a tool-result carrier) already occurs today via the steer path (a steer carried as pending user message after a turn ending on tool results). The volatile tail/CONTEXT_FOOTER install after the correction next iteration; for Anthropic the system-role tail relocates into the final message's content (the correction) as trailing text blocks — valid. OpenAI (`validate_request_messages`, openai/request.rs:1274-1322): only checks non-empty assistant messages and tool_call_id↔tool-call references — a user text message after tool messages passes; the builder itself notes endpoints don't require strict alternation.
- **Cache stability.** No changes to `src/agent/prompt.rs` / `build_stable_head`. The correction is a tail append (prefix-cache-safe); the git schema change is a static deploy-time change, byte-stable within a session.
- **Schema vs strict providers.** `required: ["subcommand"]` matches the established codebase pattern (file_read `["path"]`, file_edit `["path"]`, shell `["command","purpose"]`, … — partial required arrays are the norm; only list_models sets `additionalProperties: false`). OpenAI-kind endpoints stamp `strict: Some(true)` on every schema (tool/mod.rs:1056-1061), and the git schema was already non-compliant with OpenAI structured-outputs rules before this change (no `required` key at all, no `additionalProperties: false`) — so this changes nothing material for strict endpoints while adding one unambiguous required field. `resolve_git_subcommand` (git.rs:136-160) is untouched — action-only calls still resolve at runtime.
- **MAX_RETRIES unchanged.** The `tool_error_count` logic (turn.rs:1459-1469) is untouched; the breaker is purely additive (queued correction + post-batch push + transient `retrying: true` event). The extended `max_retries_aborts_after_consecutive_tool_errors` test asserts the cap still aborts at 3 with both corrections landing in history.
- **Tests.** The 3 new breaker tests + extended max_retries test + `schema_requires_subcommand_and_maps_required_fields` + `prepare_edit_lines_one_bound_only_errors` + the enrichment assertions in the existing git tests all exercise the changed paths (verified by reading; I cannot execute cargo test as a read-only reviewer — the stated matrix, root 2415 passed / src-tauri 299, is consistent with the code).
- **Docs sync.** PLAN.md (error-recovery section) ✓, docs/FEATURES.md (git bullet) ✓, HOW-record amendment ✓ — README.md gap is Finding 3.
- **Multi-platform neutrality.** No platform-specific code, paths, or shell syntax in the diff. ✓
- **Warning-free.** By inspection: all new items are used (`REPEAT_FAILURE_SCAN_WINDOW`, `CORRECTION_SCHEMA_CAP`, the `ToolSchema` import, `truncate_for_display`); no dead code; doc comments present on the new pub(crate) items. ✓
- **Security.** The correction quotes only error text already in the transcript plus the tool's static schema; it is explicitly harness-attributed ("— not the user") so it never masquerades as human input; no new attack surface, no approval/safety bypass (the breaker only adds a message). ✓
