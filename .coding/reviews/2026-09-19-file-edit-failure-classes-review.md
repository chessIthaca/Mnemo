### HIGH 1 — `minItems`/`maxItems` on `lines` are not strict-mode-legal; every request to a strict-capable OpenAI-compatible endpoint would 400

- `file_edit` is in `STRICT_TOOLS` (`src/provider/strict.rs:251`), and the OpenAI provider kind defaults `supports_strict_schema: true` (`src/provider/mod.rs:69`), so `apply()` (`strict.rs:275-284`) sends its schema with `strict: Some(true)` on the default OpenAI path.
- The new `lines` property (`file_edit.rs:1513`) carries `"minItems": 2, "maxItems": 2`. `normalize_for_strict` (`strict.rs:76-193`) only widens optional types to nullable and forces `required` + `additionalProperties: false` — it does not strip other keywords, so `minItems`/`maxItems` reach the wire verbatim.
- OpenAI's strict mode supports a limited JSON-Schema subset; `minItems`/`maxItems` are not in it. The function-calling guide states strict mode "has a few limitations: Some features of JSON schema are not supported" and that a non-conforming schema + `strict: true` means "the request will be rejected with details about the missing constraints"; the well-known rejection is `Invalid schema for function 'file_edit': 'minItems' is not permitted in schema`. (I could not pull the live supported-schemas list verbatim — the docs pages truncate before that section — so confirm with one live request before/after the fix; the local facts above are all verified.)
- No precedent and no coverage: the codebase's only other `minItems` user, `ask_user` (`ask_user.rs:107`), is NOT a strict tool, so this is the first time these keywords reach a strict schema. The strict.rs tests use synthetic schemas; the file_edit tests cover deserialization (`strict_mode_shape_all_keys_null_optionals_deserializes`), not the advertised schema's strict-legality. This is exactly the class `cargo test` cannot catch.
- Impact: the tools array is sent on every agent request — a 400 here breaks the endpoint entirely, not just line-range edits.
- Fix (zero-cost): drop `"minItems": 2, "maxItems": 2` from the `lines` property. The runtime check in `prepare_edit_lines` (`bounds.len() != 2` → the exact-expected-arguments error) already enforces the tuple shape, and the description ("exactly [start, end] … One tuple, so the pair can never be half-filled") carries the contract — the keywords add nothing the tool doesn't already enforce. Optionally add a regression test asserting the advertised `file_edit` schema (post-`normalize_for_strict`) carries no keywords outside the strict-supported set (minimally: no `minItems`/`maxItems`).

### LOW 2 — batch no-op items still surface the generic error (the observed incident shape)

The backlog's cause (3) was a BATCH item with `old_string === new_string`; the new no-op guard covers single-mode only (`execute`: `edits.is_none() && !append && lines.is_none() && !use_regex`). A batch item with old==new still fails via the in-splice guard (`file_edit.rs:898-902`) wrapped as "edit N/M failed (anchor: '…'): old_string and new_string are identical" — item-scoped and reasonably clear, but not the new "no-op edit" message, and it fires after the file read. Plan step 2 explicitly scoped the guard to single-mode, so this is a completeness note rather than a plan violation: consider a per-item pre-check in `validate_batch_args` (old==new → the exact no-op message naming the item) so the observed batch shape gets the same clear rejection.

### LOW 3 — `near_miss_diagnostic` is unbounded O(n·m) on pathological content

The scan (`file_edit.rs:803-815`) gates on the first char, so typical content is near-O(n) — but a file with long runs of the needle's first char (minified/generated content) and a long needle degrades to O(n·m) with no work cap; a 10 MB file × 1 KB needle is minutes of blocking-pool time before the error returns. Acceptable for a miss-only path off the async runtime, but a cheap work budget (e.g. bail after ~10⁷ compared chars, or cap scanned positions) would bound the worst case. Indexing itself is panic-safe: `best_start + best_len ≤ hay.len()` by loop bounds, and `best_len < needle.len()` is guaranteed because the needle's absence is what reached the miss path (a full match would have been an exact/variant hit in `literal_splice`).

### LOW 4 — schema description overstates: "or the edit fails" vs the fallbacks that absorb misses

The description now says "old_string must match the file's exact content or the edit fails: …" while the landed fallbacks deliberately make several miss classes SUCCEED with a NOTE (escape variants, whitespace normalization). The module doc describes the fallback accurately; the model-facing description is now factually overstated. Defensible as steering (byte-exact is the contract; the fallback is a safety net), but a one-line softening ("…or the edit fails — escape/whitespace differences are auto-absorbed with a NOTE") would keep the doc surface honest about the NOTE the model may see on a fallback success.

### LOW 5 — single-path no-change error is now reachable with a misleading "not found" reason

`prepare_edit_literal`'s post-splice guard (`file_edit.rs:996-999`) returns "old_string not found in file" when `new_content == content`. Via the new Escaped variant this is now reachable in a case where the old_string WAS found: old=`it's`, new=`it\'s`, file=`it\'s` → the escaped variant matches, the replacement equals the matched text, content unchanged → "not found" (wrong reason; the batch path's equivalent arm says "the item produced no change" — accurate). Edge case, correctly rejected, cosmetic message accuracy: consider distinguishing "matched but produced no change".
