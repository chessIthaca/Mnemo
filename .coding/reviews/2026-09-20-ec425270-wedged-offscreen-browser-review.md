### Verified correct (the CHECK ESPECIALLY list)

1. **cdp wrapper async/lock interactions — no deadlock, by construction.** `tokio::time::timeout` drops the inner future *before* the `Err(Elapsed)` match arm runs, so any `MutexGuard` the future holds (list_pages' pruning lock, `src/browser/mod.rs:838`) is released synchronously at drop; a future still *waiting* on the lock is cancelled. `force_reap_wedged` (:531) then takes the lock cleanly — including the same-task case (the wrapper's own `cdp` call holds no lock; every op snapshots under a short lock and runs CDP lock-free, Review C1 preserved). The pruning lock inside the wrapped future is short and its mutations are cancel-safe (remove-then-continue; a dropped prune just leaves a zombie page that the force-reap clears anyway).

2. **force_reap_wedged idempotency.** `detach_browser` (:487) starts with `state.browser.take()?` — a second concurrent timeout finds `None` and returns `false` without spawning a second kill task. Two concurrent timeouts → exactly one detach + one kill task. The dead path (`reap_dead_browser`, :462) is unchanged in behavior: same gate, same clear-and-kill via the extracted helpers; aborting an already-finished handler is a no-op as documented.

3. **The watchdog probe cannot false-positive on a busy renderer.** The probe (:688-703) is `browser.version()` — a browser-process-level `Browser.getVersion` round-trip, not a per-page command, so a renderer stuck in an infinite JS loop does not block it (that case is handled by the op timeouts — the two detectors are complementary: op timeout = wedged renderer, probe = wedged browser process while idle). Strikes reset on any answer, any non-timeout error (connection closing — the next tick's `reap_dead_browser` handles the dying handler), and when no browser is spawned; only `Err(Elapsed)` strikes, 2 consecutive → force-reap. The probe clones the `Arc<Browser>` under the reap lock, drops the lock, then probes — a wedged browser being probed cannot block operations or the reap path. A stored browser has already completed the launch CDP handshake, so a >5s `getVersion` on a healthy browser (twice, 30s apart) is not realistic.

4. **The wedge regression test exercises the changed path.** `wedge_renderer_times_out_and_self_heals` (:2425-2471): healthy navigate under the 3s override (the browser *launch* lives in `ensure_browser`, outside the wrapper, so cold-start cannot false-fire the short budget — only the data:-URL round-trips are bounded); `eval(None, "while(true){}")` blocks the renderer main thread so the `Runtime.evaluate` response never arrives → the cdp wrapper times out → force-reap → the asserted error text ("unresponsive" + "restart"); the 10s outer guard is exactly the pre-fix failure mode (the hang); then navigate respawns a fresh browser and `list_pages` proves the clean slate (exactly 1 page, the new one). Pre-fix this test fails via the outer guard; post-fix it passes — a genuine regression test. The 3s override (vs the plan's sketched 250ms) is a wise deviation for CI robustness.

5. **Navigate listeners wrap.** On timeout the `Err(e)` arm (:770) propagates the cdp timeout message, not the subscribe error; on subscribe failure the `_` arm (:771-776) closes the page and returns before any state insertion — the active page is untouched, Review C3 preserved. On a timeout of the final `page_info` wrap, the already-inserted page/console task are cleared by the force-reap, consistent with the "re-navigate to reopen your pages" message.

6. **Root cause documented.** BUG memory exists (id 3a066101 + knowledge file) with symptom → root cause (no timeout on any launch-mode CDP round-trip; `reap_dead_browser` gated on a finished handler, which a wedge keeps alive) → fix + regression test name + re-run command. README.md and PLAN.md need nothing (verified: README's browser mentions are platform/feature-level only; PLAN.md has no browser-timeout claims).

**L2 (low, accepted-risk race) — a late-firing cdp timeout can force-reap a freshly respawned healthy browser.** `force_reap_wedged` detaches whatever browser is *currently* in state, not the one the timed-out op was talking to (ops hold `Page` clones, not the browser handle; there is no generation/epoch check). Interleaving: navigate B (60s budget) hangs on wedged browser X; eval A (30s) times out and reaps X; navigate C spawns fresh browser Y; B's timeout then fires and force-reaps Y — C fails with a spurious CDP connection error. The consequence stays bounded and self-healing (next op respawns), which is this feature's own accepted failure mode, so this is an accepted-risk candidate rather than a blocking defect; the window is narrow (staggered budgets + a respawn inside it). Fix if desired: tag `State` with a launch generation (`u64`, bumped by `ensure_browser`), have the `cdp` wrapper capture it at op start, and pass it to `force_reap_wedged` to no-op on mismatch. Skipping with that justification is also defensible.

**L3 (low, pre-existing + theoretical) — the navigate subscribe-failure cleanup's `page.close()` is an unbounded CDP round-trip (`src/browser/mod.rs:772`).** The plan goal says "every launch-mode CDP round-trip is bounded"; this one (the `_` match arm, carried over unchanged from before the diff) is not wrapped. Practically unreachable: the arm only runs when an `event_listener` returned `Err`, which implies a broken/closed connection (a wedged-but-open connection *hangs* the subscribe → the timeout arm, which is handled); on a broken connection `page.close()` errors immediately. Fix if desired: wrap it in the same `cdp()` (or a bare timeout) — one line — or skip with the pre-existing/unreachable justification.
