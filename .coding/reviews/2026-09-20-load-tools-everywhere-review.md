## Findings

### LOW 1 — Skill-arm comment rationale is wrong for browser/image (the real gap was MCP only)

`src/tool/mod.rs:867-873` (and the test doc at `:2532-2537`) says: "a skill whose allow-list names deferred tools (browser/image/mcp) needs the loader to reveal them — without it they stay deferred and unusable mid-skill."

That is inaccurate for browser/image. A skill whose allow-list NAMES a static deferred tool already got it without any loader, before this change: `ToolRegistry::schemas`'s explicit-allow-list bypass (`src/tool/mod.rs:1187-1191` — `!self.loaded_groups.contains(group) && !filter.explicitly_names(name)`) advertises a named deferred tool directly, and the Skill `_` arm's `allowed.iter().any(|n| n == name)` admits it at dispatch. So `Skill(["offscreen_browser_navigate"])` was already fully usable mid-skill pre-change.

The genuine gap the addition fixes is MCP only: an `mcp__<server>__<tool>` adapter does not exist in the registry until the `mcp.<server>` group is revealed, so the `explicitly_names` bypass cannot help — the loader was the only path to materialize the named tool, and it was denied in skills. (Secondary effect, fine as-is: a skill naming no deferred tools can now reveal/list a group's schemas, though non-named group tools stay filter-denied.)

Fix: reword the comment (and the test doc) to name the MCP case as the gap — e.g. "a skill whose allow-list names MCP tools needs the loader to materialize them (they don't exist in the registry until the group is revealed; named browser/image tools already bypass deferral via `explicitly_names`)". No code change. Worth fixing because this is the security-relevant filter arm and the comment is the rationale a future maintainer will trust.
