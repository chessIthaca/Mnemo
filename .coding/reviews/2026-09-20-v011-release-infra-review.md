### Findings

**LOW 1 — `package-lock.json` left at 0.1.0 (three entries) — the sixth version-bearing file was missed.**
`package-lock.json:3` (`"version": "0.1.0"` for root `mnemo`), `:9` (the `packages[""]` root entry), and `:17` (the `frontend` workspace entry) still say 0.1.0 while `package.json` and `frontend/package.json` say 0.1.1. **This does NOT break CI** — I verified it from npm's own source rather than assuming: `npm ci` (npm 11.19.1, `lib/commands/ci.js`) fails only when `validateLockfile(virtualInventory, idealTree.inventory)` reports version mismatches, and `@npmcli/arborist`'s `loadVirtual` (`lib/arborist/load-virtual.js`) builds the virtual tree's root manifest from the **on-disk** `package.json` (`#loadRoot` → `rpj(pj)`) and always re-reads workspace link targets' `package.json` from disk (`#resolveLinks`: "we always need to read the package.json for link targets outside node_modules because they can be changed by the local user"). So both inventories report 0.1.1 for root/workspace and `npm ci` passes — the tag push will build and publish fine. The residual costs are real though: (a) the lock is now self-inconsistent, and the next `npm install` (any dependency change) rewrites those three lines as a surprise diff unrelated to the change that triggered it; (b) the new_release skill's step 1 ("ALL FIVE files" + `cargo check`) re-creates this staleness on **every future release**, so the gap is baked into the reusable procedure this plan shipped. Fix: run `npm install --package-lock-only` and commit the refreshed lock (three-line diff), and amend `new_release.toml` step 1 to read "…Then `npm install --package-lock-only` to refresh package-lock.json and `cargo check` to refresh Cargo.lock, and commit everything on the working branch."

**LOW 2 — About-dialog fallback version is stale.**
`frontend/src/components/about/AboutDialog.tsx:42`: `const [version, setVersion] = useState<string>("0.1.0");` — the initial state (briefly shown every time the dialog opens, before `getVersion()` resolves) and the error fallback. The about-dialog review recorded the convention that this string "matches the manifests"; it now doesn't (a 0.1.1 app flashes 0.1.0). No test asserts the fallback value (verified — the only other `0.1.0` strings in frontend/src are unrelated shell-output test fixtures). Fix: bump the literal to `"0.1.1"` and re-run the frontend vitest suite.

**LOW 3 — the release job fails silent where the upload steps fail loud.**
The upload steps pin `if-no-files-found: error`, but `softprops/action-gh-release@v2` defaults `fail_on_unmatched_files` to false (confirmed in the action's `action.yml`). If any `files` glob matches nothing — e.g. a future tauri bundle-target change drops the nsis `.exe`, or the artifact's internal structure shifts — the release publishes silently missing that asset instead of failing the job. Fix: add `fail_on_unmatched_files: true` to the `with:` block, restoring the fail-loud symmetry with the uploads.

**LOW 4 — build.yml lost its trailing newline.**
The diff ends `\ No newline at end of file` after `generate_release_notes: true` — the previous file ended with a newline, the new one doesn't. Cosmetic (YAML and actionlint don't care), but it deviates from the LF-normalized tree (`.gitattributes` pins `* text=auto eol=lf`) and shows as noise in every future diff of the file's tail. Fix: restore the trailing newline.

**LOW 5 — the skill's inlined merge drops two of merge_to_main's hard-won rules.**
`new_release.toml` step 2 inlines the merge procedure but omits (a) the conflict-resolution rule — merge_to_main step 3's "Any conflict, in the pull or the merge: file_edit taking the UNION of both sides, `git add` + `git commit`; never drop a side, never `-X ours`/`-X theirs`" — a data-loss guard for exactly the plausible release-day case where main moved since the branch forked; and (b) the post-merge memory supersede (merge_to_main step 6), so stale branch-status memories linger after the release merge deletes the branch. Also, agent.md's branch policy says main receives merges "via the merge_to_main skill" — this skill's step 2 is now a second (identical-procedure) path, which the plan chose deliberately but agent.md doesn't acknowledge. Fix: add the two rules to step 2 (one line each), and optionally a parenthetical in agent.md's branch policy noting the new_release skill performs the same sanctioned merge inline.
