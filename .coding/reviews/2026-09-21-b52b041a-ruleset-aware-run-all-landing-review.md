## Findings

### L1 (low, bug — edge): empty PR title degrades the landing to the error path
`land_via_pull_request` takes the title from `git log -1 --pretty=%s <branch>` (src/project/worktrees.rs:428-431). A tip commit with an empty subject (git allows it via `--allow-empty-message`) yields `--title ""` → gh/GitHub rejects a blank title → create fails → `gh pr view` finds no PR → `LandError::Git`. The failure IS surfaced and actionable (the message names the manual command; branch + worktree kept; item Done with the note), so the acceptance criteria still hold — but a one-line fallback (e.g. `if title.is_empty() { title = branch.to_string() }`) makes the landing robust instead of degrading. Rare in practice (spawned agents always commit with messages).

### L2 (low, bug — edge): `parse_github_remote_url` fails open on three realistic URL shapes
Trailing slash (`https://github.com/o/r/` → repo `"r/"` contains `/` → None), ssh with port (`ssh://git@github.com:22/o/r` → no prefix match), mixed-case host (`https://GitHub.com/o/r`). All → None → `main_is_protected` false. This only matters when `gh repo view` fails while `gh api` would work (the fallback slug path); in that state on a protected repo the landing takes the direct path — the stranded-local-merge defect this change exists to fix. Suggest at least trimming a trailing `/` before the split (src/project/worktrees.rs:165-177).

### L3 (low, design residual): a detection false negative has no recovery hook, unlike the skill
The skill's direct path pushes main, so a ruleset-check miss surfaces as GH013 and recovers (reset main to origin/main, re-land via PR — merge_to_main.toml step 3). The app's direct path never pushes main, so a false negative (transient gh/api failure with gh otherwise working) silently strands the local merge with no later signal — and the next merge_to_main GH013 recovery would discard the landed work. The comments acknowledge the stranding but frame the false positive as "the worse failure" — debatable (a false positive costs a manual merge; a false negative costs the work). The direction is precedented and forced for gh-missing; suggest documenting the no-recovery residual explicitly in the module doc (src/project/worktrees.rs:193-197, 320-328), or queueing a follow-up.

### L4 (low, design gap — cosmetic): PR-path runall branches have no deletion sweeper
The docs promise "deletion happens after the human merges — a later session" (`remove_worktree_only` doc, src/project/worktrees.rs:131-134), but no code path deletes a merged `wt/runall-*` branch: the adoption sweep only removes requeued items' branches, and the skill deletes only its own branch. On a protected repo every PR-landed item leaves a permanent local branch — cosmetic, but it weakens agent.md's "no branches accumulate" topology goal. Suggest a follow-up sweeper (e.g. the adoption sweep could `git branch -d` fully-merged `wt/runall-*` refs) or a doc note softening the promise.

### L5 (low, deviation from the mirrored skill flow): the PR path skips the branch-build verification
The skill's PR path (step 4) verifies the branch builds first — "PRs get no CI: build.yml triggers only on tags/dispatch". The app's PR path pushes + creates the PR without building (src/project/worktrees.rs:416-478). Defensible: the app's direct path never verified builds either, and the spawned agent's own closing sequence ran the tests in the worktree before the plan completed — the producer-side guarantee the skill lacks. But it is a conscious deviation from the design being mirrored; a doc-comment line on `land_via_pull_request` stating the substituted guarantee would pin the decision.

### L6 (low, documentation sync / memory hygiene): stale DECISION record still describes the now-fixed breakage
`.coding/knowledge/decision/2027-01-11-merge-to-main-is-ruleset-aware-pr-flow-on-protec.md:18` still carries "KNOWN ADJACENT BREAKAGE (follow-up backlog item): … the app-managed run-all landing … pushes main directly and is equally blocked" — this change resolves that breakage (and the "pushes main directly" premise was inaccurate anyway). Amend the record at finish (memory_amend) so future sessions don't act on the stale claim; the BUG/SPEC digest written at finish should reference the resolution.
