**LOW 2 — the whitespace-only guard is only exercised on the macOS leg; Windows can never catch a regression in this predicate (hardening suggestion, non-blocking).**
The predicate and its tests live under `#[cfg(unix)]` / `#[cfg(all(test, unix))]` in `src-tauri/src/main.rs` (fn at :118–121, tests at :1860–1900). The gating itself is correct — the function does not exist on Windows (Windows GUI apps inherit the user PATH via the `#[cfg(not(unix))]` no-op at :124–125), so this defect genuinely could not compile on the Windows dev box. But the residual is real: the Windows dev box and the windows CI leg can never guard this predicate, and the workflow triggers ONLY on `workflow_dispatch` + `v*` tag pushes (no per-push CI at all) — so a future regression would first surface at release time. The BUG record itself flags this ("Consider whether the trimmed-empty guard deserves a platform-neutral unit test too, so Windows CI guards it"). Fix direction (optional): extract the pure predicate (`!value.trim().is_empty() && !value.chars().any(|c| c.is_control())`) into platform-neutral lib code (src/, pub fn with doc comment, tests running on all platforms) and have the `cfg(unix)` wrapper delegate — then both legs and the dev box guard it. Alternatively accept the residual and note it in the record.

**LOW 3 — the "Re-run failing tests" step name/comment mislabels its scope (cosmetic, build.yml :122–129).**
The comment says "Re-run only the failing tests with full stdout/stderr captured" and the step is named "Re-run failing tests with full output", but the command `cargo test --workspace --no-fail-fast -- --nocapture 2>&1 | tee -a macos-test-output.txt` re-runs the ENTIRE workspace (cargo has no "only the failed tests" mode without naming tests). Harmless at runtime (`continue-on-error: true`, appends to the same artifact) but the label can mislead a future maintainer into thinking it is scoped, and it doubles the macOS test time on failure (~6 min). Fix: reword the comment/step name to "Re-run the test suite with full output", or scope it to the failing test names if that precision is wanted.


### Detailed verification

**A. The `is_adoptable_path` fix — CORRECT, zero production-path regression.**
Exact hunk (from the PR #3 diff, confirmed against the working tree): predicate `!value.is_empty()` → `!value.trim().is_empty()` (main.rs:120); doc comment "non-empty" → "non-blank" plus the new "a whitespace-only value is not a usable PATH and must be rejected" sentence (:113–117); reject test extended with `"\t"`/`"\n"` cases and the new `adoptable_path_keeps_internal_spaces` test (:1883–1899).

- Intent coverage: empty ✓ (trimmed-empty), whitespace-only ✓ (the defect), control characters ✓ (unchanged `is_control` clause — covers `\t`, `\n`, `\r`, BEL, and any C0/C1), internal spaces preserved ✓ (`trim()` strips only leading/trailing Unicode whitespace; any value containing a non-whitespace char passes the first clause — `/Applications/Some App/bin` stays adoptable, pinned by both `adoptable_path_allows_spaces` and the new guard test).
- Would the tests fail without the fix? Yes — machine-proven, not argued: diagnostic run 35575972400's captured artifact shows `panicked at src-tauri/src/main.rs:1881:9: assertion failed: !is_adoptable_path("   ")`, `296 passed; 1 failed`; post-fix run 35578123470's macos job is green. The `adoptable_path_keeps_internal_spaces` test cannot fail on pre-fix code by design — it is an over-correction guard against a future blanket-whitespace rejection (the review-F5 failure class), a legitimate complement to the regression test.
- Production-path impact: NONE. `inherit_shell_path` (main.rs:99) does `String::from_utf8_lossy(&output.stdout).trim().to_string()` BEFORE calling the predicate, so a whitespace-only capture already arrived as `""` and was rejected by the OLD predicate too. The change hardens the standalone predicate's documented contract (defense in depth for any future un-trimmed caller). No legitimately-captured PATH is newly rejected: newline-only values were rejected before and after (control chars); leading/trailing whitespace is pre-trimmed at the call site and accepted by both predicates when non-blank; the only newly-rejected input class is entirely-non-control-whitespace strings (space, NBSP, U+2028/29) — never a usable PATH, and unreachable un-trimmed from the only caller. The `eprintln!` message ("PATH was empty or contained control characters", :103–106) stays accurate for every production-reachable rejection, because the pre-trimmed value arrives as empty in the whitespace-only case.
