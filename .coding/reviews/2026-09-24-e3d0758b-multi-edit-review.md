- Impact is contained: the inline `ApprovalPrompt` renders the combined diff correctly (`ApprovalPrompt.tsx:335-338`), so the approving user is not blind — but the diff-tab row of the docs is false and the touched file's multi_diff support is inert.

### L2 (low) — multi_edit's duplicate-path guard keys on the raw spelling: `"a.txt"` + `"./a.txt"` slip through, so the second entry's write silently discards the first entry's result while the combined preview claims both applied

- `src/tool/agent/multi_edit.rs:109-122` — `seen: HashSet<&str>` is keyed on `file.path` as sent. The guard's stated purpose (`:117-121`, "appears twice — merge its ops into one entry") is to stop a second entry's ops applying to the first entry's result.
- Equivalent spellings evade it: `Sandbox::validate` canonicalizes existing paths (`src/tool/agent/sandbox.rs:113-124`), so `"a.txt"` and `"./a.txt"` both validate to the same absolute canonical path. Both entries then prepare against the same on-disk original (`multi_edit.rs:146-182`) and the write loop (`:279-292`) writes each `new_content` in order — last write wins, the first entry's edit vanishes. `prepare_for_approval` (`:320-326`) also prepares each entry from the same base, so the approval preview shows BOTH edits applied while only the second lands.
- Fix: dedupe on the sandbox-validated `PathBuf` (validate each entry first, then `HashSet<PathBuf>`) and keep the existing "appears twice" message; or reject when any two validated targets compare equal.

### L3 (low) — The write-phase failure report lists the failed file under "not written (byte-identical)", which can be false for exactly that file

- `src/tool/agent/multi_edit.rs:279-290` — when the write for index `i` fails, `written.len() == i`, so `prepared[written.len()..]` starts AT the failed file: it is omitted from "written" and listed in `not written (byte-identical): [...]` together with the genuinely untouched tail. `std::fs::write` creates/truncates the target before writing, so a mid-write failure (e.g. disk full) can leave that file truncated or partially written — the "byte-identical" claim can be wrong for precisely the file named. The untouched tail is `prepared[i + 1..]`.
- The message is otherwise honest (it reports which files landed), and this is an error path only — but this message is the user's/agent's only account of a partial multi-file write, so the off-by-one matters.
- Fix: report the failed path in its own clause ("write failed — '<path>' may be truncated/partial") and list only `prepared[written.len() + 1..]` under "not written".

### L4 (low) — sandbox.rs's async-callers doc still says only `file_edit`/`file_write` override the inline approval-preview hook; multi_edit is now a third hook tool doing N validates + N reads

- `src/tool/agent/sandbox.rs:45-53` (module doc, the async-callers contract): "the **approval-preview hook** — `Tool::approval_preview` called inline from `dispatch::execute_tool_call` (no `spawn_blocking`) → `file_edit`/`file_write::prepare_for_approval`, which calls `validate` / `validate_for_creation` and then reads the file to build the diff. … Only those two tools override the trait default (`file_append` and `convert_line_endings` have no hook)…"
- Post-change, `MultiEditTool` overrides `approval_preview` (`src/tool/agent/multi_edit.rs:251-254`) → `prepare_for_approval` (`:316-327`) → `prepare_files` (`:146-184`): N `Sandbox::validate` calls + N file reads + N in-memory applies, invoked inline from `src/agent/dispatch.rs:536` (`tool.approval_preview(&parsed_call.arguments)` — no `spawn_blocking`). The doc's enumeration (which is the contract reviewers rely on for the blocking-I/O budget) is now stale, and multi_edit's hook is materially heavier than file_edit's one validate + one read.
- Fix: name multi_edit as the third inline-hook tool with its N-validates/N-reads note (same trade-off class as file_edit, one preview read per *prompted* call), or move the hook's work behind `spawn_blocking`.
