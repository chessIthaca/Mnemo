### Findings

- **HIGH-1 — bad-JSON site unimplemented, docs claim it shipped.** Plan 02deea7c Goal + DECISIONS(4) ("Bad-JSON: classify; confident permanent aborts early (<8 strikes)") was not implemented: `handle_bad_json` (src/agent/turn.rs:3388-3447, both the cap arm at :3408 and the retry arm) has zero triage integration, and `FailureSite::BadJsonRepair` / `TriageAction::AbortEarly` (src/agent/failure_triage.rs:432/:467) are referenced only by the label-stability tests (:927/:933) — their doc comments describe behavior that does not exist. Meanwhile the shipped docs claim the coverage: docs/FEATURES.md:48 ("at every failure-handling site (the tool-execution cap, **the bad-JSON repair loop**, and both provider retry layers)"), README.md:43 ("classifies every tool/provider failure"), PLAN.md consumer bullet ("the tool-execution cap + bad-JSON repair loop"), the failure_triage.rs module doc, the `LayaConfig::failure_triage` doc comment (src/config/general.rs:251-253), and the Settings toggle copy ("at every failure site"). Fix: either wire the site (classify once per repair-loop failure; confident permanent → `AbortEarly` row + abort before the 8-strike cap; else unchanged) or correct all six doc surfaces and mark the two enum variants reserved-for-follow-up. As shipped, the acceptance criterion "each class routes to the right action" cannot hold at that site and a user enabling the flag on the documented contract is misled.
- **LOW-1 — `restart_and_swap` can stomp a concurrent classifier-slot writer.** The status restore is only-if-own (`restore_status_if_ours`, src-tauri/src/ipc/finetune.rs:237-247) but the slot writes at :390-392 and :402-404 are unconditional. A Settings save landing between the fine-tune's success and the swap (rewire replaces the slot with the user's just-chosen external/managed classifier) is silently overwritten by the fine-tuned client. Narrow window, managed-mode only, self-corrects on the next save — but the swap should abort when the slot no longer holds the Arc the task observed at start (mirroring the status discipline).
- **LOW-2 — increment-only fine-tune dataset discards prior dispositions.** `finetune_decision` (src-tauri/src/ipc/finetune.rs:120-124) filters rows strictly newer than the marker and that filtered set *is* the exported dataset (:464); the runner passes no base/previous-artifact argument (`-m laya.finetune --dataset --out` only, :191-199). When a training surface appears, run N trains only on the newest ≥50 rows — every earlier labeled row is dropped from training, contradicting README/FEATURES ("retrain the checkpoint from that log … from real dispositions"). Latent today (laya 0.3.20 → Ineligible), but the plumbing bakes it in: use the marker only for the ≥50-new trigger and export the full resolved corpus (or chain the previous artifact, or document the incremental semantics in the user-facing docs).
- **LOW-3 — the fine-tune run blocks an async worker thread.** `run_finetune_process` calls `child.wait()` (src-tauri/src/ipc/finetune.rs:311) inside the spawned async task for the run's full duration (minutes-to-hours). The doc comment owns the tradeoff (one-shot startup task on the multi-thread runtime), but `tokio::task::spawn_blocking` + awaiting the handle is trivial and keeps the worker pool clean.
