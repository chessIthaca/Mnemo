## Findings

### L1 (LOW) — per-kind test survives a half-broken per-kind table
**Where**: frontend/src/components/views/DashboardView.test.tsx:105-109.
**Issue**: the "breaks the ledger down by kind" test asserts only `toContain("skeleton")` and `toContain("archive_expand")`. `"skeleton"` also appears in the recent-events fixture row (test.tsx:70, rendered at DashboardView.tsx:238), so the per-kind table's skeleton row could be dropped entirely — or its figures/columns scrambled — and the test still passes; only total absence of the table (losing "archive_expand" too) is caught. Nothing pins the per-kind figures (`fmtTokens(111_456)`), the biggest-first ordering, or the negative row's sign-preserving rendering (`fmtTokens(-4_000)` → "-4,000" — the display property that makes an `archive_expand` row read as a subtraction).
**Fix**: scope assertions to the per-kind card (e.g. add `data-testid="dashboard-per-kind"` to the card at DashboardView.tsx:180 and slice the markup), then assert the row contents and order: `fmtTokens(111_456)`, `fmtTokens(-4_000)`, and skeleton-before-archive_expand within that card.

### L2 (LOW) — the per-day section has no assertion; the epoch-days formatting contract is unpinned on the frontend
**Where**: DashboardView.test.tsx (missing coverage of the per-day card, DashboardView.tsx:202-227; `fmtDay` at :47-49).
**Issue**: no test renders or pins the per-day card at all — neither the epoch-DAYS → date formatting (`epochDay * 86_400_000`, DashboardView.tsx:48) nor the bar math (:148, :216). This is the one cross-layer unit mismatch in the app: `project_stats`/StatsView use day-start seconds × 1000 (mod.rs:2592 + StatsView.tsx:351) while `savings_stats`/DashboardView use epoch days × 86_400_000 — so this is exactly the contract a future "consistency" refactor would silently break: changing `fmtDay` to copy StatsView's `× 1000` shifts every date label by ~86× and fails ZERO tests. The backend unit is pinned (`per_day[0].day == day1 / 86_400`, tests.rs), but the frontend wiring is not.
**Fix**: add one assertion pinning the per-day row — give the per-day card a `data-testid` and assert the rendered label for the fixture day 19_675 (e.g. `toContain(new Date(19_675 * 86_400_000).toLocaleDateString())`) plus its saved-tokens figure, so the day-bucket → date rendering path is exercised.

### L3 (LOW) — `cached_not_null_requests` is documented as "the honest hit-rate denominator", but the displayed hit rate divides by ALL prompt tokens
**Where**: types.rs:649-653 and tauri.ts:1554 (docs) vs DashboardView.tsx:144-147 (the math).
**Issue**: both docs call the field "the honest denominator for a hit rate", but the rendered rate is `cached_tokens / prompt_tokens` (gated on `cached_not_null_requests > 0`), and `prompt_tokens` sums EVERY `request_stats` row — including error/cancelled rows that never reported usage (`cached_tokens` NULL, schema.rs:102-106). Concrete scenario: one reporting request (1M prompt, 400K cached) plus nine cancelled rows (100K prompt each, NULL cache) → the card shows 400K/1.9M = "21.1%" although every cache-reporting request hit 40%. The adjacent "requests reporting cache 1 / 10" row only partially discloses the dilution. The metric itself is a defensible "cached share of all prompt tokens", but the doc claim and the shipped math disagree — a doc-vs-behavior mismatch in exactly the section the plan's headline requirement lives.
**Fix** (cheapest, doc-only): reword both docs to "requests that reported a cache figure — the gate for showing a hit rate, and the numerator of the reporting ratio; the displayed rate is the cached share of all prompt tokens". (Alternative, if per-reporting-row honesty is preferred: add a `prompt_tokens`-over-reporting-rows sum to `CacheEfficiency` and divide by that; would need a backend + test change.)

### L4 (LOW) — pricing table non-empty but no model matches → "—" figures under a note claiming pricing-derived rates; untested
**Where**: DashboardView.tsx:290 (the note gate `pricing.length === 0`), :64-65 (`rateEstimate`'s no-match `continue`), :281/:287 (the "—" figures).
**Issue**: the honest-empty note only triggers when the pricing table is completely empty. With `[[pricing]]` entries present but NONE matching the models this project actually used, `rateEstimate` skips every `per_model` row → both rates 0 → both ESTIMATED figures render "—" — while the note still reads "Priced at this project's realized input/cached rates; never part of the metered totals above." (:292), claiming a derivation that didn't happen. Concrete scenario: user prices gpt-4o in `endpoints.toml`, the project ran on claude-sonnet → "estimated savings —" plus the misleading note. The empty-pricing test (test.tsx:142-146) only covers the fully-empty table.
**Fix**: have `rateEstimate` also return whether ANY per-model row matched (a `matched` count), gate the note on `pricing.length === 0 || matched === 0`, and use wording like "No [[pricing]] entries for the models this project used — dollar estimates are unavailable." Add the no-match test case.
