## Findings

### LOW 1 — `UnknownLabel` echoes endpoint-controlled text into the agent-visible message, unbounded (`src/tool/memory/mod.rs:393-396`, `src/memory/auto_typing.rs:196-199`)

The security ask was "no injection via classifier labels into messages/data". Labels that become types are safe (fixed six-way match → enum → static prefixes). But an unrecognized label is interpolated verbatim: `classifier kept the writer's prefix (unknown label '{label}')` — into the tool's result message AND the `auto_typed` data field. The label comes from the HTTP response's `choice` field (`classifier.rs:306`) with no length or character restriction, so a misbehaving or hostile endpoint can inject arbitrary-length text (control characters, newlines, prompt-injection phrasing) straight into the agent's tool-result stream, and blow up message size past the 4000-char cap the state text carefully enforces on the other side. The endpoint is localhost/user-chosen so the trust boundary is deliberate, but the same failure-protected contract that scrubs everything else should scrub this echo too. Fix: truncate (e.g. first ~40 chars) and strip non-printable characters before interpolating — one small helper or inline `label.chars().filter(..).take(..)` in `keep_writer_note`/`UnknownLabel` construction. Test: a stub returning a label with newlines/10k chars asserts the note stays single-line and bounded.

### LOW 2 — the seed set can train only 4 of the 6 retypable classes; the safety contract overstates it (`src/memory/auto_typing.rs:254-261` + docs)

`seed_dataset` walks only the four knowledge-dir-backed kinds (`spec`/`decision`/`bug`/`how`) because PLAN/REVIEW records have no knowledge home (`dir_for_record_type` ⇒ `None`, `knowledge.rs:227`). But `typing_question` asks over six labels and the 0.80 gate accepts any of the six — including the two the documented fine-tuning path cannot produce examples for. The user-facing contract ("enable only against a checkpoint fine-tuned on the shipped seed labeled set" — FEATURES.md, README, config doc) reads as sufficient validation for the whole feature, when a checkpoint trained on this set leaves PLAN/REVIEW near-chance/over-confident — precisely the failure mode the separate opt-in exists to guard. Nothing is wrong with the code (the label set honestly reflects the corpus); the gap is between the documented contract and the shipped data. Fix (docs-first): state in `seed_dataset`'s doc + FEATURES.md that PLAN/REVIEW have no seed examples, so a confident PLAN/REVIEW retype rides an untrained class — and either recommend keeping those two out of scope until plans/reviews corpora can be seeded, or note the follow-up. Optional hardening: treat PLAN/REVIEW answers as keeps until examples exist.

### LOW 3 — case-variant writer prefix survives inside the retitled title ("SPEC: spec: tabs lost") (`src/memory/auto_typing.rs:146-153` + `225-236`)

`strip_typed_prefix` is case-sensitive by design (mirroring `from_title`), so a writer's lowercase `"spec: tabs lost"` parses as `None`-kind. If the classifier then answers SPEC ≥ 0.80 (an agree-in-spirit answer), `retitle` cannot strip `"spec:"` and produces `"SPEC: spec: tabs lost"` — the final title carries the stale lowercase prefix as body text. `record_type`, the slug, and `bare_title` are all still correct (the outer prefix is stripped by `title_prefix`, leaving the writer's intended bare text), and a second pass agrees — so nothing corrupts; it is a cosmetic wart on exactly the mistyped-prefix inputs this feature targets (agents writing `bug:`/`spec:` lowercase are part of the stated problem). Fix options: in `strip_typed_prefix`, also strip a case-insensitive match of the same six prefixes at position 0 (keep `from_title` parity for parsing — only the STRIP side widens); or accept and document. A one-line regression test (`retitle("spec: x", Spec)` ⇒ `"SPEC: x"`) pins whichever choice is made.
