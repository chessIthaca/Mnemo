### Config-lock ordering / deadlock analysis (requested check) — SOUND

- The completion arm (laya.rs:774-777) holds **no other lock while awaiting** `config.lock()` — `run_setup` has finished, `end_setup()` has run, and the decision itself is pure. A task that holds nothing cannot close a lock cycle → no deadlock is possible from this side.
- The save path never holds the config lock across anything long: `save_settings` locks only around the pure patch application (settings.rs:962-965) and `persist_and_reload` locks only for the clone-and-swap after its synchronous disk I/O (config_io.rs:43-52). The rewire runs **lock-free** on the reloaded value, and its managed start is `tauri::async_runtime::spawn` fire-and-forget (rewire.rs:123-125) — so the 900 s probe never runs under the config lock. Worst case for the completion arm is brief serialization behind a save's microsecond-scale critical sections.
- Interleaving convergence: whether the completion arm reads the config before or after a concurrent save's swap, the final state matches the new config — the rewire is the last-writer authority (it unconditionally `laya.stop()`s and restarts), and every start path goes through the same child slot. Verified for all three mid-setup saves (disable / checkpoint switch / mode flip): each ends with the rewire's outcome and the setup completion deferring to it (or being torn down harmlessly via the generation gate).

### LOW 1 — A non-autostart setup leaves the shared status stuck at `Downloading ~99%` over a live, healthy classifier

- `src-tauri/src/ipc/laya.rs:663-667, 697-710, 469-478` — `run_setup` writes `Installing` and then `Downloading` ticks to the **shared** status, overwriting the live `Ready` of a serving classifier (managed + enabled + checkpoint X installed and running; user clicks Download on Y — the Download buttons of *other* cards stay enabled, ClassifierSection.tsx).
- `src-tauri/src/ipc/laya.rs:802-819` — on `Ok(())` without autostart, the completion arm writes a terminal status **only** when `laya_off`; the "leave any live classifier alone" branch writes nothing. But the status is no longer `Ready` to leave alone — the poller's last `Downloading {label: Y, progress ≈0.99}` sticks indefinitely.
- Self-heal paths only: the next `classify()` on the live classifier flips `Ready`/`Failed` (classifier.rs:332-336), or the next save's rewire rewrites it. In an idle session neither happens: Settings → Classifier shows a phantom ~99 % progress bar, and since `busy` is status-derived (`typeof status === "object"`, ClassifierSection.tsx:104-106) **every Download button stays disabled** until a classifier call or a save.

Status-only (the classifier slot and child are untouched and keep serving; the opt-in/disabled contracts hold), so LOW — but it is a terminal-state honesty bug of exactly the kind the status contract documents ("a terminal Ready/Failed always follows", classifier.rs:123-124). Fix: snapshot the pre-setup status when the setup starts and restore it in the no-autostart/no-off completion arm (or re-emit the status implied by the live slot).

### LOW 2 — The generation token guards only the probe-failure path; the spawn/record window and the success path remain unguarded (both pre-existing since 9de7e08)

- **(a) spawn/record window** — `src-tauri/src/ipc/laya.rs:401-427`: `spawn_server` takes and releases the child mutex at its top (`self.stop()`) and only re-acquires it for the final record; nothing holds it across `cmd.spawn()`. If a concurrent start (save-driven rewire) runs its *entire* spawn+record inside that gap, the slower task's record overwrites the newer `(child, gen)` — the winner's child becomes untracked and survives both the `RunEvent::Exit` stop (main.rs:959) and the `Drop` backstop, violating the documented "child must never outlive the app" invariant (laya.rs:430-433) and pinning ~1 GB of model RAM. Requires scheduler preemption of the spawning task for the competitor's full spawn_server (multiple syscalls) — a millisecond-scale theoretical window, not reachable without a concurrent save mid-spawn.
- **(b) success path** — `src-tauri/src/ipc/laya.rs:913-920`: the ready arm writes `Ready` and returns the port without confirming the generation still owns the slot. If a rewire's `laya.stop()` (rewire.rs:101) kills the child between probe success and the caller's slot swap (rewire.rs:116-121, laya.rs:797-800), the slot can briefly point at a dead port until the winner's start completes. Same family as (a).

Suggested fix for both: hold the child mutex across stop→spawn→record (extract a private unsynchronized kill helper so `stop()` stays callable), and re-check the generation before the `Ready` write/return. Given the windows, LOW is the honest severity — recorded so the residual is explicit rather than rediscovered.
