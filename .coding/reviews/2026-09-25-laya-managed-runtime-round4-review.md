### Requested bf6de80 regression checks

**1. Child lock held across `cmd.spawn()` + fs I/O — SOUND, no deadlock/stall risk.**
- `spawn_server` is a sync fn: no await under the lock, and it acquires **only** the child mutex — no status/classifier/config lock is taken beneath it, so no lock-order cycle can close (a task holding one lock cannot deadlock with itself or a peer that never nests).
- The kill+wait was *already* under the lock pre-bf6de80 (`self.stop()` at fn top held it across kill+reap); the newly-under-lock work (`is_file`, `create_dir_all`, `File::create`, `CreateProcess`/fork-exec) is millisecond-bounded syscall work. It runs on a tokio worker via `start_managed_server` (no await before it returns) — a bounded worker block, not a stall that can grow.
- `RunEvent::Exit`'s `stop()` (main.rs:959) and the `Drop` backstop (laya.rs:460-464) may wait milliseconds behind an in-flight critical section — that is the intended serialization, not a deadlock; and `Drop` cannot race the start task at all (the task holds an `Arc` clone of the manager, so `Drop` cannot run while it lives).
- Error paths (`serve` missing 424-429, `create_dir_all` 430, `File::create` 431, spawn failure 438-443) release the guard on return with the slot empty and the prior child killed — exactly the pre-bf6de80 semantics (`stop()` ran first there too), and the caller's `Err` arm writes `Failed`. Correct.
- A panicking task under the guard would poison the lock, but nothing in the section can panic (all failures are `Result`s). The code comment (412-417) documents the reasoning honestly.

**2. Pre-setup snapshot races + restore-vs-rewire clobber — the one residual LOW (below).** The setup guard (`begin_setup` CAS, laya.rs:1066-1068) prevents concurrent *setups* but not concurrent *server starts* (save-driven rewire / startup hook), which is exactly what opens the window.

**3. `owns_generation` residual TOCTOU — accepted, narrowed as intended.** Between the check (962) and the autostart arm's slot swap (833-836) there is no await (`build_managed_classifier` is sync), so the last-writer-wins window is microseconds; every interleaving converges to the rewire's outcome on the next `classify()`/save. This is precisely the narrowing round 3 asked for — not a finding. Likewise the superseded-probe `Downloading` ticks (926-929) over a winner's `Starting` reflect a *genuine* download (the HF dir is shared — it's the winner's), are self-limited, and pre-date bf6de80 — not a finding.

### LOW — The restore write is unguarded: a stale/transient snapshot can be restored over a concurrent writer's honest terminal status

- **(a) stale transient restored** — laya.rs:803-806 snapshots whatever the status holds at task start. If a save-driven rewire's `start_managed_server` is in flight at that moment, the snapshot captures `Starting` (laya.rs:947-948) or a probe `Downloading` tick (926-929). That start then finishes and writes `Ready` (963) while the (minutes-long) setup still runs; at completion the restore (849-856) writes the snapshotted `Starting` **over the winner's `Ready`** — a transient state with no remaining writer, violating the documented contract "A terminal `Ready`/`Failed` always follows" (classifier.rs:122-124). UI: a "Starting…" badge and `busy = true` (ClassifierSection.tsx:105-106) disables every Download button until the next `classify()` flips the status (classifier.rs:360-364) or a save rewires — the same phantom-busy shape as the original R3-LOW 1, in a narrower window (needs a start in flight exactly when Download is clicked).
- **(b) restore clobbers a rewire's honest terminal status** — the restore arm runs whenever the live config is enabled-but-not-autostart. A mid-setup save switching checkpoint X→Z (both installed) makes the rewire write `Starting` (rewire.rs:114-115) and spawn start(Z); if that start *fails* before the setup completes, its generation-gated `Failed` (laya.rs:983-993) is then overwritten by the restore's pre-setup `Ready` — stuck dishonest `Ready` until `classify()`/save. An external flip is worse in one sub-case: `build_classifier` writes `Disabled` (no endpoint, client_factory.rs:387) or `Failed` (unbuildable client, 401) and swaps the slot to `None` — the restore's stale `Ready` then has **no** `classify()` self-heal path at all (no client exists to flip it); only the next save or app restart clears it.
- **(c) second-setup interleave** — `end_setup()` (808) releases the guard *before* the completion arm runs, so a second setup's `Installing` (690) can be overwritten by the first task's restore write; the second setup's own next write (step-4 tick at 723, after a possibly tens-of-seconds `uv pip install`) is the only corrector. Cosmetic, seconds-scale, same root cause.
- Severity: **LOW** — status-only in every manifestation (the classifier slot and child are untouched; the opt-in/disabled contracts hold), self-healing via `classify()` or the next save in all but sub-case (b)'s `None`-slot variant, and each interleaving is strictly better than pre-bf6de80 (which *always* left the phantom progress bar in these same windows). Reachable only via a mid-setup save/start landing in a microsecond–seconds window.
- **Suggested fix:** condition the restore on the *current* status still being one of this setup's own progress states — `Installing`, or `Downloading { label }` with `label == checkpoint.id || label == "uv"` — and write nothing otherwise. That makes the restore immune to stale snapshots (a) and to any concurrent writer (b)/(c), and the predicate is a pure, unit-testable helper alongside `setup_autostart_decision`.
- Test note: the restore and the critical section remain untested (both need network/runtime — the standard round 3 already accepted, with the decision logic extracted and tested); if the fix lands as the suggested predicate, pin it with a unit test mirroring `setup_autostart_decision_follows_the_live_config` (laya.rs:1348-1365).
