## Risk-focus findings

**LOW — loop-top swap summarization skips `state.token_accounting.reset()`.** `TurnState::fresh()` is created once per TURN (turn.rs:325, before the loop), so the incremental accounting persists across iterations and its documented invariant (context.rs:1842–1850) says callers "must NOT insert or remove messages inside the already-counted prefix … call `reset` after any other rewrite (e.g. summarization)" — which `maybe_compact` does. The new loop-top `handle_pending_swap` has no access to `state`, so a mid-run smaller-context pick that summarizes rewrites `messages` with no reset. In practice `TokenAccounting::update`'s shrink guard (context.rs:1910–1915) detects the typical summarization (the summarized list is shorter: `len_new = len − cut + 2`, `cut ≥ 2`) and falls back to a full pass — the common case self-heals. The residual gap is the exact-length rewrite: when `cut == 2` (an 8-message conversation, `KEEP_RECENT_ON_SWAP = 6`) and `enforce_sendable`/`ensure_sendable_tail` leave the length unchanged, `len_new == counted_len` runs the delta path over an index-unstable rewrite (index 1 replaced inside the counted prefix; only the head replacement is detected) → stale per-role buckets for the rest of the turn: a wrong ContextUsage readout and possibly one spurious or missed summarize/preflight trigger, until the next reset (next turn, or the next compaction). No data loss, no crash, self-heals. Suggested fix: thread a reset at the loop-top call site (e.g. a "rewrote" flag from `handle_pending_swap` → `state.token_accounting.reset()`), matching `maybe_compact`. Before this change the swap completion only ran at turn top, before any accounting existed, so this exposure is new.
