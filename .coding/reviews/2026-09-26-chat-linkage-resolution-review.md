## Findings

### LOW-1: A chat item whose plan is abandoned never re-links to the successor plan — the same stranding, one branch deeper

- `chat_linkage_candidate` (run_all.rs:7204-7208) filters `item.plan_id.is_none()`, and `stamp_backlog_in_flight`'s fallback (run_all.rs:7294) fires only when the pointer is `None`. So once a chat-driven item is linked to plan P and P is abandoned mid-session, the successor plan's `Executing` entry cannot re-link it — the item is skipped by the fallback (it has a `plan_id`) and `resolve_linkage_target` will never match it against the successor plan id. The item strands `InFlight` linked to a dead plan, exactly the bug this plan fixes, in the abandonment sub-case.
- The dispatched path handles precisely this case by re-stamping the linkage "whenever a fresh plan replaces an abandoned one mid-dispatch, so the linkage always names the plan the item's status is derived from" (src/backlog.rs:706-710) — that doc claim is now shipped inaccurate for the chat path (documentation-sync angle of the same finding).
- Not a regression: pre-fix behaviour was identical (no arm, no linkage at all). Severity LOW because the targeted symptom (never-linked item) is fully fixed and this requires a chat session to abandon and replace a plan mid-item. Fix direction (if taken): let the fallback also claim a live `InFlight` item whose `plan_id` is a dead plan (e.g. plan file absent / abandoned), or extend the doc to name the residual.

### LOW-2: The stamp fallback can link a stale orphan from a dead session to an unrelated chat plan

- `chat_linkage_candidate` picks the unique live unlinked `InFlight` item at *every* pointer-less main-agent `Executing` entry — including one left `InFlight`+unlinked by a crashed/abandoned previous session, when the *current* session's agent never hand-stamps its own item (the user pastes item Y's text, the agent forgets `backlog_status`, the stale orphan X is the only candidate). X is then linked to the new plan, and at completion flips `Done` although the completed plan was not X's work — the wrong-item outcome the risk focus asked about.
- `adopt_orphaned_in_flight` does NOT narrow this window for chat sessions: it runs only at run-all start (backlog_cmds.rs:548), which a chat-driven session never executes. The helper's doc (run_all.rs:7196-7201 region) argues the zero/several-claimants refusals but not the stale-single-claimant case.
- Severity LOW: the window needs (stale unlinked `InFlight`) ∧ (no dispatch pointer) ∧ (current agent never stamps its item), and pre-fix the same orphan had *no* automatic recovery path at all — it just stranded forever. Recovery from a wrong `Done` is a legal `Done → Pending` requeue. Flagging per the risk focus; if accepted, the trade-off ("adopt the one stranded item into the next pointer-less plan") should at least be stated in `chat_linkage_candidate`'s doc.
