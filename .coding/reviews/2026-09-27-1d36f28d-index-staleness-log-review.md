### Findings

**LOW-1 — `factory.rs`: `with_staleness_log` was inserted between `with_skills` and its doc comment.** Lines 492–496 ("Wire in the [`SkillLibrary`] … When `None`, the skill tools are omitted (no skills available).") are `with_skills`' pre-existing doc comment; the new function was inserted directly between it and `pub fn with_skills` (line 505). Result: `with_staleness_log`'s rustdoc now begins with text describing the skill library, and `with_skills` — a public function — has no doc comment, violating the project's "all public functions must have doc comments" rule. Fix: move the SkillLibrary paragraph back onto `with_skills` and leave only the staleness-log paragraph on `with_staleness_log`.

**LOW-2 — `try_index` (search.rs:1063-1103, shared by `search` and `search_read`): a budget-spent-mid-set partial repair drops the reindexed files' records.** Attempt 0 reindexes with `refreshed > 0`, stores the full stale set in `last_stale`, and re-queries; if the re-query still finds stale files (budget ran out mid-set, or files re-edited), the flow returns `FtsOutcome::Stale` with only *attempt-1's* remaining stale set, discarding `last_stale`. The caller then logs just that remainder as SurfacedOnly — the files that WERE refreshed inline never get a record (neither `inline-reindex` nor `surfaced-only`). This narrows acceptance criterion 1 ("N edited files → N records") in that edge, and deviates from the plan's design ("log the whole set … BEFORE the cap branch: action = InlineReindex when it proceeds to reindex_stale_files"). Suggested fix: log (or return alongside `FtsOutcome::Stale`) the attempt-0 set as InlineReindex when `reindexed > 0`. Reachable only under the ~500 ms budget with a ≥1-file refresh, hence low.

**LOW-3 — `docs/CONFIGURATION.md` final paragraph: the `mtime-drift` clause "or the file is not content-indexed" is inaccurate.** A file with no index row always classifies `unindexed` — both with the probe (`classify` returns `Unindexed` when `stored_hash` is `None`, taking precedence over the disk probe) and without it (the no-probe arm maps `mtime_index == None` to `Unindexed`). `mtime-drift` occurs only above the inline-repair ceiling for a file that has a row. The extra alternative should be dropped (or reworded to "above the inline-repair ceiling only").
