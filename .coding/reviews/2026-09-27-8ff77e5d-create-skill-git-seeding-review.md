## Findings

### LOW 1 — A non-UTF-8 `.gitignore`/`.gitattributes` now hard-fails `Project::init` (src/project/scaffold.rs:106)

`ensure_managed_entries` uses `std::fs::read_to_string`, which errors with `InvalidData` on any non-UTF-8 byte. Git's ignore/attribute files are byte-oriented and may legally contain stray non-UTF-8 bytes (a Latin-1 comment, a mangled paste). For such a project — which initialized fine before this change — every init (and thus `create_project` and the CLI `--project` path, the only init callers) now fails with `Error::Project("failed to seed git files into …: stream did not contain valid UTF-8")`. No data is lost (the write never happens), but a previously-working project becomes un-openable until the user hunts down the offending byte. The same hard-fail applies to a read-only git file, though there failing loudly with the clear `Error::Project` message is arguably the right call.

**Fix suggestion:** read with `std::fs::read` and `String::from_utf8`; on an invalid-UTF-8 file, skip the merge for that file (leave it byte-untouched and return `Ok(false)` — the seeded entries are hygiene, not correctness-critical, and git itself tolerates the file). Keep the `NotFound` create path and the write-error propagation as-is.

### LOW 2 — The merge rewrite is not atomic: a crash mid-write is the one theoretical user-data-loss path (src/project/scaffold.rs:139)

`std::fs::write` truncates then writes, so a crash/power loss between truncate and write can destroy the user's existing `.gitignore` content — the exact content this change promises to never lose. The fresh-create path is harmless; only the merge path (which first reads the user's full content into memory, then rewrites file = old content + appended block) has the exposure. This matches the existing seeding precedent (`agent_md`, `seed_skills` also use `fs::write`), so it is a pre-existing pattern, but the merge path is the first that REWRITES a file the user may have hand-built.

**Fix suggestion:** for the append case write to `path.with_extension("gitignore-seed-tmp")`-style temp + `std::fs::rename` (same-dir rename is atomic on both Windows and macOS/Linux), e.g. `<name>.seed-tmp` beside the file. Keep it best-effort: on rename failure fall back to the direct write rather than erroring twice.

### LOW 3 — `*.db -text` is seeded repo-wide; the header comment understates the scope (src/project/scaffold.rs:66-85)

The three `*.db* -text` entries apply to EVERY `.db`/`.db-wal`/`.db-shm` file in the user's project, not just the app-owned caches under `.coding/` — the seeded header says "The SQLite caches under .coding/ are binary", which misdescribes the rule a user reading their new `.gitattributes` sees. Mirroring this repo's own repo-wide lines was a deliberate plan choice, but in a user project the app only owns `.coding/*.db`. `-text` is a safe default for databases, so the impact is small (it disables eol/encoding normalization on any user-owned `.db`, which they almost certainly want anyway), but the mismatch between comment and behavior is a documentation-accuracy issue and the scope is broader than "app-owned entries".

**Fix suggestion (either):** scope the seeded entries to `.coding/*.db -text`, `.coding/*.db-wal -text`, `.coding/*.db-shm -text` — which also keeps the dogfood test green via its leading-`/`-stripped normalized compare? NO — note: the dogfood test requires the REPO's files to carry each managed entry verbatim after normalization, and this repo carries `*.db -text` repo-wide, so scoping the seeded form breaks `repo_own_git_files_carry_every_managed_entry` unless the repo's own `.gitattributes` is changed too. The cheaper, self-consistent fix: amend the seeded header to say the `*.db` rules are repo-wide (they keep any SQLite file—app cache or user-owned—out of the eol machinery), e.g. "Any SQLite database (app caches under .coding/ and any user-owned .db) is binary — never text/eol-processed." A scope change should only be taken together with a matching change to this repo's own `.gitattributes` so the dogfood invariant stays honest.
