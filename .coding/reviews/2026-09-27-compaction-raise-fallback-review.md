## Finding (low)

**L1 — `raise_cap` equals the model's true window when `compact_headroom_tokens = 0`, contradicting the documented "capped below the window" invariant.**
- Where: `src/agent/context.rs` `raise_cap()` (~line 330: `self.hard_ceiling().max(self.effective_summarize_at())`), `docs/CONFIGURATION.md` line 7 ("never above the true window (`max_tokens - compact_headroom_tokens`)"), `PLAN.md` lines 838–839 ("so the provider's true window stays hard"), and the plan goal ("the raise is capped below it").
- `hard_ceiling()` is `max_tokens.saturating_sub(headroom)`; with headroom 0 that is `max_tokens`, so `raise_cap == max_tokens`. `compact_headroom_tokens` has **no config-load validation** (the clamp machinery at `src/config/general.rs` `clamped()` covers only `trace.memory_budget_mb`/`request_body_cap_kb`; `[context]` passes through verbatim), so a user writing `compact_headroom_tokens = 0` in `config.toml` reaches it. With `summarize_at_fill_rate >= 0.5` the full 10-step ladder (x2.0 of base) can then bring `effective_limit` to **exactly** the advertised window — zero output headroom — so the session can be driven into genuine provider 400s by the raise lever itself.
- Mitigations already in place: the provider length error still surfaces as a real error (the invariant that actually matters holds), and headroom 0 was already a degenerate config pre-change (the preflight keep_recent=3 selector never fires when ceiling == window) — so this is an edge extension, not a regression. Still, acceptance criterion (a) as phrased ("the cap must never let the effective limit reach the model's true window") is falsifiable.
- Suggested fix (scoped to the new code, no behavior change elsewhere): floor the subtraction in `raise_cap` — `self.max_tokens.saturating_sub(self.compact_headroom_tokens.max(1)).max(self.effective_summarize_at())` — or add a load-time clamp for `compact_headroom_tokens` alongside the trace clamps; or, minimally, document the headroom=0 edge in CONFIGURATION.md.
