## Findings

### L1 (low) — the pid guard is check-then-act; the docs claim the invariant categorically

**Location:** `src-tauri/src/instance_marker.rs` — `remove_marker_if_self` (module doc + the helper's doc comment).

The guard is `read_marker` → (pid match) → `remove_file`: non-atomic. If a newer instance writes its own marker inside the microseconds between this instance's read and its `remove_file`, this instance's exit deletes the newer incumbent's marker — exactly the outcome the docs promise cannot happen ("a newer incumbent's marker must survive our exit" / "last-writer-wins"). Impact is benign and advisory-class (a subsequent third launch would miss a warning; the dialog warns, never locks) and the window is tiny, but pid recycling — a residual of the same benign class — IS explicitly documented while this one is not, and the module doc plus the helper's doc comment state the invariant with no residual note.

**Recommended fix:** one doc-comment line (module doc and/or the helper's doc) noting the read→remove window as an accepted benign residual, same class as pid recycling. No code change is warranted: an atomic conditional delete is not expressible with `std::fs` on either platform without a lock file, which the single-slot advisory marker design does not merit. Alternatively, justify as factually-acceptable with this analysis.
