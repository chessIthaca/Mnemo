## Findings

**L1 (LOW) — byte position in the new positional error is line-relative and trim-shifted for rare payload shapes.** `parse_stringified_sequence` (mod.rs:304-311) parses the *trimmed* slice and reports `e.column().saturating_sub(1)`. serde_json's `column()` is 1-based and resets at every newline in the payload (it counts bytes within the *line*), and trimming shifts positions relative to the received string. For the pinned/observed shape (single-line stringified array, no leading whitespace) the pointer is exact — the test pins pos == 5. But both edge shapes are reachable (a JSON string can carry `\n` escapes that unescape to real newlines; leading whitespace is legal): for a multi-line stringified payload the message "JSON parse failed at byte {pos}" (read_files.rs:278, 291-292) can name a byte far from the actual defect, and leading whitespace shifts it further. Impact is confined to the pointer in an already-degraded error path — the reason, recovered/skipped counts, and expected native shape all remain correct. Minimal fix: parse the un-trimmed original (serde skips leading whitespace itself, keeping positions absolute) and render `line {e.line()}, byte {e.column()}` when `e.line() > 1` (or accept-with-justification: the shape is plan-inherent — step 2 prescribed `e.column()` — and the degraded payloads observed are single-line).
