### High

**H1 — `reduceToolResult` keys the lastDiff capture off the card's first-call name.** `agentEventReducer.ts:758` sets `completedToolName = entry.name` (the CARD-level name = the run's first call), while the doc comment at :788-790 and the gate at :800-805 (file_edit/file_write/file_append → `lastDiff`/`planDiffs` snapshot) clearly intend *the completed call's* name. In a mixed card led by another tool — e.g. the archetypal `read_files → file_edit` run — a completing `file_edit` yields `toolName = "read_files"`, so **no diff snapshot is captured**: the DiffViewer loses the post-approval diff (snaps back to empty) and the top plan's changed-file list misses the edit. Fix: `const completedToolName = calls[callIdx].name ?? entry.name` (the `?? entry.name` fallback covers legacy persisted cards whose calls predate the field). Add the regression test: mixed card `[read_files, file_edit]`, complete the `file_edit`, assert `lastDiff` is set — it fails today.

**H2 — loading a legacy saved conversation crashes the chat render.** `ToolInvocation.name` is now typed required (`types.ts`), but saved conversations written before this change carry calls without it, and `/load` (InputBar.tsx:520-547) applies only `stampEntryIds` — no per-call normalization. A restored tool card reaches `groupPhrase` → `actionPhrase(undefined, args)`, where `isBrowserToolName(undefined)` calls `undefined.startsWith("browser_")` (and `prettyToolName` would hit `undefined.split`) → **TypeError that takes down the whole Conversation render**, for every legacy saved conversation containing a tool card. The `startedAt` doc in types.ts already acknowledges "invocations restored from legacy saved conversations", so this path is a supported one. Fix: normalize on load (e.g. in `/load`, `calls.map(c => ({ ...c, name: c.name ?? entry.name }))` — entry.name is the correct per-card fallback since pre-bundling cards were single-tool), or make the phrase helpers tolerate a missing name; preferably both (belt and braces).

**H3 — `countGitMutations` keys off the card name, not the call's.** `gitLanes.ts:273` calls `isGitMutation(entry.name ?? "", call.args)` per call. With mixed cards, a completed mutation — a `git` commit/merge/checkout/branch, a shell-invoked git mutation, or `create_plan`'s branch fork — riding a card whose first call is another tool is **not counted**, so the Git tab's mutation-driven lane refresh misses it (and conversely, a card led by `git`/`shell` tests every bundled call's args against the git template). The per-call name now exists — pass `call.name` (and add `name?: string` to the structural call type `countGitMutations` declares). Add a mixed-card case to `gitLanes.test.ts`.

**H4 — `isKnowledgeActivityEntry` classifies mixed cards by their first call.** `agentState.ts:660` gates on `entry.name.startsWith("graph_")`. Since graph lookups now merge into runs led by other tools, a `graph_*` call bundled behind a `search`/`read_files` call is **hidden from the knowledge-activity view** (the `show_knowledge_activity` subset, consulted when `show_tool_activity` is off — Conversation.tsx:179-180); conversely a card led by a `graph_*` call but bundling shell/read legs shows the whole noisy card. Fix: `entry.kind === "tool" && entry.calls.some(c => (c.name ?? entry.name).startsWith("graph_"))`. Regression test in `agentState.test.ts`/`Conversation.test.ts`. (Impact is settings-gated — tool-activity OFF — but it silently loses a documented feature and is the exact per-call-name class this plan was obliged to sweep.)

The behavior is arguably better; either amend the plan note or leave it — not a code defect.
