### Findings

**1. LOW — post-fix check staleness: the merge precondition can be satisfied by checks that predate the fix commits.**
`agent.md:139` ("the worker's turn finished successfully and its checks passed") and `.coding/design/mnemo2.md:116` (§4: "When the review is closed and the worker's checks pass, the TeamManager merges…"), against design §3:91-102: a `review_fix` commit (lead's tiny fix, applied by the TeamManager at §3:94-95) or a fixer's fix commit (§3:99-102) lands on the worker branch *after* the worker's checks ran, and nothing re-runs checks on the new branch tip. The merge card therefore records checks for a commit that is no longer the tip being merged — the one path where the "reviewed + checked" guarantee can silently go stale.
*Fix:* in design §3/§4 (and optionally one clause in `agent.md:139`), state that the checks precondition binds to the **merge-time branch tip**: after any `review_fix` or fixer commit, the affected check scope must be re-run and pass (the fixer runs it as part of "commits the fix and reports"; for `review_fix` the TeamManager runs it in the worker worktree) before the merge card becomes mergeable; also define the check scope (for this repo: `cargo test --workspace`).

**2. LOW — `wt/agent-*` fork base is unspecified, so the conflict-halt rule may fire for avoidable reasons and workers may miss lead-side context.**
`agent.md:143` ("Worker branches are per-agent `wt/agent-*` worktrees") and `.coding/design/mnemo2.md:56-57` (§2: worker runs "in its own git worktree, on its own branch") never say what the branch is forked **from** — `main` or the lead's current working branch tip. This affects conflict probability against the merge target (the lead's local branch), whether workers build on unmerged lead work, and what "stale base" means when the lead branch advances while a worker runs.
*Fix:* add one sentence to design §4 (and/or `agent.md:143`): worker branches fork from the **lead's working branch tip at dispatch**; a base that has gone stale is never auto-rebased — the existing conflict-halt + route-back rule (§4:123-124) is the handling. Alternatively list it under §10 open decisions if the base is genuinely undecided — but currently it is neither specified nor listed as open.

**3. LOW — `git_diff` is named as an existing lead tool, but the current surface exposes no such tool.**
`.coding/design/mnemo2.md:36` (§2 lead belt: "`git_read` / `git_diff` and commits") and `:59` (worker belt: "`git_read`/`git_diff`"). The engine's actual surface is `git_read` with `diff` as an *op* (plus log/show/status) — there is no standalone `git_diff` tool (my own reviewer tool belt confirms: reads + `git_read` only). A design doc that otherwise names real symbols accurately should not imply a tool that doesn't exist.
*Fix:* either rename both to "`git_read` (diff/log/show/status ops)" or, if a dedicated diff tool is planned for Mnemo2, say so explicitly (e.g. add it to §11 phase 2's tool list).
