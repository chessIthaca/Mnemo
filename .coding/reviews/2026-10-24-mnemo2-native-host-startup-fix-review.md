### Findings

**F1 (HIGH) — the new regression test omits `test = true`; it breaks `cargo test --workspace` on macOS.**

`src-tauri/src/mnemo2/mod.rs:65-66` — `tauri::generate_context!("mnemo2-app/tauri.conf.json")` inside `#[cfg(test)]`. tauri-macros 2.7.0 — the pinned version — documents the `test` option for exactly this case: "skips code generation that misbehaves when the context is created inside a test binary — currently the `Info.plist` embedding performed on macOS development builds." On a macOS host in dev profile, every `generate_context!` without `test = true` emits `tauri::embed_plist::embed_info_plist!` (tauri-codegen context.rs: emitted when `target == Target::MacOS && dev && !running_tests`). The lib unit-test binary built by `cargo test` contains **both** invocations — `run()` (mod.rs:52, not cfg-gated) and the test — and embed_plist 1.2.2's reuse protection makes the second expansion a compile-time error (`_EMBED_INFO_PLIST` already defined). The mnemo-app test target therefore fails to build on macOS.

Impact: `.github/workflows/build.yml` runs `cargo test --workspace` on `macos-latest` ("Rust tests (workspace, macOS compile validation)"), on every `v*` tag and manual dispatch, and the release job `needs: [windows, macos]` — so the next tag build fails its macOS Rust-tests step and blocks the release. Windows is unaffected (the plist block is `#[cfg(target_os = "macos")]` inside codegen), which is why the local gates are green; the defect is invisible until macOS compiles it.

Fix (one line; `test = true` skips only the runtime-only plist embedding — `context.config().identifier` still comes from the parsed config, so the assertion is unaffected and Windows behavior is unchanged):

```rust
let context: tauri::Context<tauri::Wry> =
    tauri::generate_context!("mnemo2-app/tauri.conf.json", test = true);
```

**F2 (LOW; pre-existing since Phase 1, not introduced by this diff — surfaced for the upcoming real-team feature work) — macOS dev builds of the Mnemo1 main bin already double-embed `_EMBED_INFO_PLIST`.**

Since Phase 1, the main-bin target links the lib whose `run()` carries a second context expansion alongside `main.rs:1095`'s own `generate_context!()`; on macOS dev builds both emit `embed_info_plist!` into one link unit and collide in the main-bin test target the same way. Release builds are safe (`custom-protocol` ⇒ `dev = false` ⇒ no plist block; the CI `npx tauri build` steps are unaffected), and no macOS `cargo test --workspace` has run since Phase 1 (the build workflow triggers only on tags/manual dispatch), so it has never surfaced. Note: fixing F1 alone does not make macOS `cargo test --workspace` green — this sibling needs its own treatment (e.g. cfg/feature-gating the mnemo2 host context, or splitting the host into its own crate). Recommend folding it into the next feature plan rather than expanding this fix.
