The concern: could the soft-stop `Finished` arrive and be processed by the forwarder between `halt_run_all` and `send_cmd`?

No. The soft-stop `Finished` is generated by the agent task only AFTER it receives the `AgentCommand::Suggestion` (which `send_cmd` sends). Since `halt_run_all` is fully `await`ed — including `end_run` which sets `*run_all = None` (run_all.rs:79) — BEFORE `send_cmd` is called (agent.rs:248→250), `run_all` is guaranteed `None` by the time any soft-stop `Finished` can exist, let alone be processed. The forwarder processes events sequentially from the fan-in channel, so even a fast soft-stop `Finished` finds `run_all_active = false` (run_all.rs:672) → skips the Run-All branch → auto-feed branch → `auto_feed` is `false` (set at Run-All start, backlog_cmds.rs:356, never restored by `end_run`) → no dispatch. The steer's follow-up turn then runs as a normal interactive turn and resolves to a no-op (no `single_in_flight`, no `auto_feed`). ✓

### Edge cases (informational — non-blocking)

**E1 — Steer arriving just as the turn finishes may mark a successful item Failed.**
If the user steers in the narrow window between the agent's natural turn-end `Finished` being emitted and `on_main_turn_resolved` processing it, `halt_run_all` (which locks `run_all` first) can mark the in-flight item `Failed` before `on_main_turn_resolved` gets to commit it. `on_main_turn_resolved` then sees `run_all_active = false` → skips the Run-All branch → no commit, no rollback. The item is `Failed` with note "steer received during unattended run — halted" instead of `Done`. **Impact is limited:** work is preserved in the tree (no rollback), the note is clear, and the user can review/re-run. The window is milliseconds (between `Finished` channel-send and `on_main_turn_resolved`'s `run_all` lock acquisition). This is a conservative side effect of "halt on any main-agent steer during Run-All" — the simpler, safer choice over trying to detect whether the turn is already resolving (which would add its own races via the `is_running()` flag, set by the forwarder only when it *processes* the `Started` event). Noting for awareness; no change required.

**E2 — `halt_run_all` early-returns without `end_run` when `current_item` is None (pre-existing, now reachable from the steer path).**
At run_all.rs:939, `let Some(item_id) = &item_id else { return };` returns early if there's no in-flight item, but `stop` was already set to `true` (line 908) and `run_all` is NOT cleared (no `end_run` call). The run is left in a "stopped but not cleared" state. This is pre-existing (identical in `halt_run_all_for_approval`), but the new `send_suggestion` call site makes it reachable from a user steer. It self-heals in all realistic paths: `send_cmd` sends the steer → if the agent is idle it runs as a new turn; if mid-turn it queues → either way the resulting `Finished` → `on_main_turn_resolved` → Run-All branch (still `Some`) → `stopped == true` → `end_run` (run_all.rs:807-809). The only stuck scenario is: agent idle + `current_item` None + steer cancelled before injection — very unlikely. An optional robustness improvement would be to call `end_run` before the early return, but it is not blocking.

**E3 — Steer cancelled before injection leaves the run halted.**
If the user steers then cancels (via `cancel_suggestion`) before the steer is injected, `halt_run_all` has already run (run halted, item `Failed`). The cancel drains the queued steer → no soft-stop → no follow-up turn. The run stays halted. This is the **safe** behavior — a steer is a user intervention that stops the unattended run regardless of whether the steer is later cancelled. The user can manually re-start Run-All. Not a defect.
