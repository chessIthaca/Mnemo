## New findings (round-2 fresh pass)

### LOW A — an intervention turn's resolution can kill or zombie a *new* Run-All the user started mid-turn (run-identity ambiguity)

**Where:** `handle_user_intervention` run_all fallback + `end_run` (run_all.rs:1325-1332) and the closed-loop arm's early return (923-926); root cause is that the latch records only `item_id`, never *which* run it interrupted.

**Trace.** Steer lands on the main agent mid-turn → latch set, `halt_run_all(…, false)` ends run R1. While that steered turn is **still running**, the user clicks Run All — `backlog_run_all` (backlog_cmds.rs:345-378) has no busy gate, so fresh run R2 is created (dispatch defers; `current_item = None`). The steered turn then resolves:

- `!closed_loop` → `handle_user_intervention`: the old item is requeued correctly (that part is right), then `run_all_active` is true → `end_run` — **R2, a run the user started *after* the intervention, is killed** before dispatching anything.
- `closed_loop` + captured id → `finish_captured_item_done` returns without touching R2 → **R2 is left a zombie**: active, but nothing ever dispatches it (the resolution returned early), and the *user's next unrelated chat turn* resolves through the run-all branch and dispatches a backlog item uninvited.

**Impact:** no item is ever stranded or wrongly failed (all stay Pending / resolve correctly — the plan goal holds); the damage is run-lifecycle UX: the overnight run silently dies or revives unexpectedly. Window is narrow (start Run-All while a steered/interrupted turn is still running) but `backlog_run_all` deliberately allows starting while busy, so it's reachable by an ordinary "steer, then actually queue everything overnight" sequence. Note the designed paths are unaffected: interrupt-during-run R1 correctly ends R1 (R2 can't exist — `backlog_run_all` refuses while a run is active); only a run started *after* the halt is misidentified.

**Fix direction:** record run identity in the latch — e.g. a monotonically bumped `generation: u64` on `RunAllState` captured alongside `item_id` at halt/latch time; at resolution, only fall back to `run_all.current_item` / call `end_run` when the generation matches the live run. Alternatively (smaller): in `handle_user_intervention`, only `end_run` when the run's `current_item` resolves to the item being requeued, and have the closed-loop arm end a still-active run whose `current_item` is `None`. Either way, document the chosen rule in the module doc's intervention bullet. A source-contract test pinning "the intervention handler must not end a run whose in-flight pointer is empty" would hold the smaller variant.
