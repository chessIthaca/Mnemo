## Contract verification — all points confirmed

1. **`in_flight` ⇔ plan ACTIVE** — the stamp fires only on Executing *entry* (`should_stamp_in_flight`: X→Executing where X≠Executing); a sub-plan push stays Executing (no re-stamp, no abandonment); non-closing turn ends annotate only. The steer/intervention requeue (InFlight→Pending) is the documented escape hatch, matching PLAN.md.
2. **`done` ⇔ the plan-loop gate** — the gate arm `(Some(main_state), true) if plan_loop_allows_done(main_state, true)` → `commit_success` + `transition(Done)`, then falls through to the done-counter bump → stopped-flag check → `emit_backlog_changed` → next dispatch. Correct.
3. **`failed` ⇔ root-plan abandonment only** — the `_ if plan_abandoned` arm → `transition(Failed, "plan abandoned (abandon_plan)")`. The gate arm is matched FIRST in both the run-all and single-dispatch paths (and `else if plan_abandoned` in the failure path), so an abandon followed by a successor plan that finishes resolves Done, exactly per contract.
4. **Every other turn end → no transition** — run-all catch-all: `annotate(plan_open_note(...))` + `end_run` + return (`end_run` emits `backlog_changed`, so the UI still updates; the done counter is correctly NOT bumped for unresolved items). Single-dispatch: annotate + the pointer (already `take()`n) clears with the item untouched. No `rollback(` remains in `on_main_turn_resolved` (the source-contract test asserts the negative).
5. **Halt-for-approval stamps nothing, keeps the run state** — annotate-once via `already_halted`, `return` before `end_run`; the stop flag prevents the next dispatch; the post-approval turn resolution runs the run-all branch under the same rules.
6. **Checkpoint failure at dispatch → Pending** — annotate + `end_run` + `Err`, no stamp (`checkpoint_failure_leaves_the_item_pending` asserts no `BacklogStatus::Failed` in `run_all_dispatch_next`).
7. **Auto-feed gating (`resolved_terminally`)** — starts `true`, set `false` only when an in-flight item was NOT terminally resolved. No item in flight → feeds (normal auto-feed); terminal resolution → feeds; still-pending (no plan ran) or still-in-flight (plan active) → suppressed. No path skips a legitimate feed and no path can loop.
8. **Item↔plan linkage** — `BacklogItem.plan_id: Option<String>` with `#[serde(default)]` (old `backlog.jsonl` rows parse), `set_plan_id` guarded by `is_live`, refreshed on every Executing entry via `stamp_backlog_in_flight`.

## Findings

### LOW-1 — Stale doc/comment claims contradicting the new contract (doc sync, CHECK 7)

The task asked specifically for leftover rollback/CantResolve/approval-stamps-Failed claims; five remain (plus one minor):

1. `src-tauri/src/ipc/run_all.rs` module doc, "Safety model" section (lines 12-24): "On failure it `git reset --hard` back to the checkpoint and marks the item `CantResolve` for morning review" and "The item is stamped `Failed` at halt time and that stamp IS its final status: the halt clears the run state, so the turn's later resolution can no longer see the item" — both now false (no rollback, no harness-set CantResolve, approval halt stamps nothing and KEEPS the run state), and they directly contradict the new "Status ⇄ plan lifecycle" section added later in the same module doc (lines 58-103).
2. `halt_run_all` doc comment (lines ~1361-1391): "Approval halts (`stamp_failed = true`) mark the item `Failed` and clear the dispatcher … Because the run state is cleared, that stamp IS the item's final status — the later resolution can no longer see the item" and (line 1383) "`true` (approval halt) stamps it `Failed` — the sanctioned terminal state for an approval block, and load-bearing because the cleared run state means the later resolution can no longer see the item" — every clause is stale.
3. `RUN_ALL_STEER` rule (4) (lines 150-152): "ending the turn earlier fails the task and rolls its work back" — now false (ending early leaves the item in_flight and keeps the work; only abandonment fails). This is agent-facing prompt text embedded in every dispatched item, so it misstates the consequences to the unattended agent.
4. `src-tauri/src/ipc/backlog_cmds.rs` module doc (line 34): "and a commit/rollback on resolution" — the rollback half no longer exists.
5. `.coding/knowledge/spec/2026-09-01-backlog-item-resolution-paths-halt-stamping-is-t.md` — a living knowledge/spec file that still documents the old contract: "halt_run_all … stamps the in-flight item Failed AND calls end_run — an approval-halted item NEVER resolves later … halt's Failed stamp IS the terminal status for approvals." (Historical plan/review files under `.coding/plans/` and `.coding/reviews/` are point-in-time records and are fine as-is.)
6. Minor, same class: `backlog_retry`'s doc comment in backlog_cmds.rs still calls the checkpoint sha "the rollback/resume anchor" — automatic rollback is gone; "resume anchor" (manual) would be accurate.

**Fix:** rewrite the stale sections to the new contract — the Safety-model bullets (failure = annotate + halt, work kept; approval = annotate-only, run state kept for the post-approval resolution), the `halt_run_all` doc (both arms annotate; the approval arm returns without `end_run`), rule (4) wording (e.g. "ending the turn before the plan closes leaves the task in flight and halts the run — call finish before ending your turn"), drop "rollback" from the backlog_cmds doc, and supersede/update the knowledge spec file (memory_supersede + file rewrite).

### LOW-2 — Approval-arm drain hole: main-agent cancel/exit strands the run state (CHECK 2)

The two designed drain paths (post-approval Finished; interrupt → `handle_user_intervention`) are covered, but a third is not: if the main agent is **cancelled** (the `cancel` IPC command, agent.rs:347) or its task exits/crashes while blocked on the approval, the forwarder's `Exited` arm only removes the agent, calls `turn_resolve.on_exited`, and `try_flush_deferred_main_resolution` — and no deferred resolution is pending (the turn never emitted Finished/Error while blocked), so nothing resolves and nothing clears `run_all`. The run state stays `Some(stopped)` with `current_item` set:

- `backlog_run_all` then refuses to start ("run-all is already active") until app restart;
- the UI keeps showing the run active (`RunAllProgress.active = true`);
- the item stays `InFlight`, and the user-facing requeue refuses `InFlight` — no UI recovery (the stranding class flagged HIGH in the 2026-12-05 steer-intervention review).

Reachability is low — the UI's cancel button is subagent-only (MainPanel.tsx:149-151, "Close-x: only on subagent tabs (never the main agent)") — but the IPC surface allows cancelling the main agent and an agent-task crash has the same effect. This is a new regression surface: pre-change, the approval halt cleared the run state at halt time, so this path left nothing stranded. Recovery today: a steer on the main agent (`halt_run_all`'s steer arm runs `end_run`), app restart, or the agent's `backlog_status` tool (InFlight→Pending is legal via the transition table).

**Fix:** in the forwarder's `Exited` arm, when the exiting agent is the main agent and `run_all` is `Some`, call `end_run` and annotate the current item (e.g. "main agent exited while halted for approval — item left in flight"). A source-contract test pinning the Exited-arm cleanup would match the file's existing test style.

### LOW-3 — `plan_open_note` says "run halted" on the single-dispatch path

All three note variants end "run halted", which is accurate for Run-All but wrong for the single-dispatch/auto-feed path — there is no run to halt there; the pointer clears and the item keeps its status. Suggest a path-aware suffix or neutral wording ("no further items dispatched").
