The comment block above (1392-1420) documents the field-scoping with the Gemini rationale: "only for providers whose continuity field IS `reasoning_content`: Gemini also sets `reasoning_required`, but its contract is `thought_signature` and fabricating the key would break its Rule-1 byte-identical echo (review finding 2026-12-23)".

The conjunction `reasoning_required && reasoning_field == Some("reasoning_content")` is therefore satisfied by DeepSeek alone. Model resolution confirmed: `for_kind_and_model` (policy.rs:225-252) maps "deepseek-v4-flash" → deepseek() and "gemini-3-flash-preview" → gemini().
3. **No other call site fabricates the key for non-DeepSeek providers.** A sweep for `["reasoning_content"] =` finds exactly two writers: the raw-echo injection (openai.rs:1426, now field-scoped) and the synthetic path (openai.rs:1508). The synthetic path adds the key unconditionally for ANY synthetic assistant message (`if m.role == Role::Assistant`), so a Gemini request carrying a synthetic assistant message (e.g. a summarized turn) would still get the key. **Material note (not a finding):** this behavior is pre-existing — in commit b23463c the `if m.role == Role::Assistant { obj["reasoning_content"] = … }` lines are unchanged context; only the comment was rewritten (the old comment's false "every prior assistant message" premise is what the fix corrected).
