### Findings

**L1 — LOW — step_index mirror doesn't trim numeric strings; the tool does — a whitespace-padded FINAL step_index bypasses the descendant gate**

- Evidence: `src/agent/dispatch.rs:193` — `v.as_str().and_then(|s| s.parse::<u64>().ok())` (no trim). `src/tool/workflow/plan.rs:199-207` — `StepNumber::parse()` does `s.trim().parse::<u32>()`.
- Why it matters: the tool deliberately accepts `" 2"`, `"2 "`, `" 2\n"` (trim, then parse — the tolerant-shape precedent the tool itself documents at plan.rs:183-186). The dispatch mirror's parse fails on exactly those strings, so `exits_phase = false` and the call runs ungated. If such a call is the FINAL step of the root plan while descendants run, `Workflow::complete_step` fires the Executing→Reviewing/Complete transition with children still running — precisely the invariant this gate was rewritten to protect. The dispatch comment's justification ("Unparseable/zero args fall through ungated — the tool layer produces its own error for those", dispatch.rs:186-187) is false for this input class: the tool does not error, it succeeds. Harm is bounded — `finish` remains gated on descendants unconditionally, so the plan still cannot complete while children run — but the parent can enter Reviewing early and start the closing sequence (reviewer spawn, fixes, commit) while a parallel coder child still edits files. Hence LOW.
- Fix sketch: one word — `v.as_str().and_then(|s| s.trim().parse::<u64>().ok())`. Optionally pin it by extending `dispatch_blocks_final_complete_step_while_descendants_running` (or a sibling case) with `{"step_index":" 2 "}` → must be refused.

**L2 — LOW — the sub-plan branch of the finality query is untested; a documented design decision of this change is not pinned**

- Evidence: `src/workflow/mod.rs:715-719` — `if self.stack.len() != 1 { return false; }` (sub-plan completion and the empty-stack case both fall out ungated). The four new dispatch tests (`src/agent/tests.rs:3513` ff.) all run single-plan stacks; a project-wide search finds no other test touching `completing_step_exits_executing` or `step_completes_plan`.
- Why it matters: "Sub-plan completion is NOT gated (pops to parent, stays Executing)" is one of the change's core design decisions (backlog item, dispatch comment, and the query's own doc all state it), yet nothing fails if it regresses. A later refactor that gates any plan's last step — or drops/breaks the stack-length check — passes the entire suite silently. The root-plan paths (final blocked, non-final allowed) are well pinned; the len≠1 branch is not.
- Fix sketch: add one dispatch-level test — root plan + sub-plan pushed (`create_plan` twice), complete the SUB-plan's last step while `FixedDescendantTracker { running: true }` → succeeds, stack pops to the parent, state stays Executing — or a workflow-level unit test of `completing_step_exits_executing` covering stack depth 0/1/2 and (for depth 1) final / non-final / already-done / out-of-range indices.

### Verified correct (checked in depth, no finding)

1. **Finality query vs actual transition semantics** — `Workflow::complete_step` (mod.rs:668-705) transitions only when the ACTIVE plan becomes complete AND `stack.len() == 1` (root); sub-plans pop and stay Executing regardless of kind. `completing_step_exits_executing` (mod.rs:714-724) mirrors this exactly: len≠1 → false; len==1 → `step_completes_plan`. `PlanFile::step_completes_plan` (plan_file.rs:335-344) requires the step in range, not already done, and all OTHER steps done — so out-of-order completion is handled correctly (completing the lone undone step out of order is still detected as final; a done-prefix assumption would have missed it). Already-done step → false (and `PlanFile::complete_step` is idempotent — no transition). Out-of-range → false → the tool's own 1-indexed range error fires (plan.rs:805-813). Empty plans cannot be created (`create_plan` rejects; `steps.get` → None → false anyway). Kind-agnostic by design: research (→Complete) and implementation/bug_fixing (→Reviewing) final steps are both gated, per the backlog's explicit requirement. The `!is_complete()` guard is redundant-but-harmless defense (a complete root plan in Executing is unreachable via the state machine).
2. **Arg mirror otherwise matches the tool** — `step_index` is required in both the schema (`"required": ["step_index"]`, plan.rs:730) and `CompleteStepArgs` (no `#[serde(default)]`), so omitting the arg cannot bypass the gate — the tool errors on deserialization. 0 is rejected by the tool (plan.rs:753-758) and falls through ungated in dispatch (`Some(n) if n >= 1`) — consistent, no state change. Floats rejected by both (serde's u32 visitor + untagged string variant; `as_u64` returns None for floats). `"+2"` parses in both (Rust integer FromStr accepts a leading `+`). Values > u32::MAX: dispatch parses but `steps.get` → None → ungated; the tool errors on deserialization — no state change either way, only the error message differs. `plan_id` deliberately unchecked in dispatch — correct: a mismatch errors in the tool before any mutation (plan.rs:775-800), and the finality query operates on the same active plan the tool mutates, so gating on plan_id could only change the error message, never the outcome.
3. **Lock discipline** — the ToolFilter guard is dropped at the end of its block (dispatch.rs:99-129); the finality-query guard (dispatch.rs:196-200) is a temporary dropped no later than the end of the `let exits_phase` statement (line 205), which precedes the tracker await (line 209). No workflow lock is held across an await; the comment's claim is accurate.
4. **Gate completeness** — enumerated every workflow transition: Planning→Executing (create_plan — ungated per spec: entering a phase, not a review exit); Executing→Reviewing/Complete (final root complete_step — GATED); sub-plan push/pop (ungated per spec); Executing/Reviewing→Planning (abandon_plan — ungated as the designated failed-reviewer escape hatch, explicitly mandated by backlog 569b5922 with the hung-reviewer rationale, and documented in both the dispatch comment and the DescendantTracker doc); Reviewing→Complete (finish — GATED, with the non-empty-report gate as the second lock); skill_* overlays (ungated per spec — plan-stack-like, not review exits); `enter_planning_for_task` is IPC-only (Run-All dispatcher), not reachable through dispatch. Nothing is gated that shouldn't be; nothing the spec wanted gated is ungated.
5. **Test quality** — the four tests pin the new contract for root plans: create_plan + abandon_plan succeed AND actually transition (workflow state asserted, not just `result.success`); non-final complete_step succeeds, ticks the step (`completed_count == 1`), stays Executing; final complete_step is refused with the gate's message ("still running"), stays Executing AND the step is NOT ticked (`completed_count` stays 1 — no partial mutation); finish is refused with the descendant-gate message specifically (pinning that the descendant gate fires before the tool's report gate) and stays Reviewing. No coverage lost from the old blanket-gate test (it only asserted create_plan blocked — now intentionally allowed, with the inverse asserted). `make_registry` registering `AbandonPlanTool` is safe: no test expected abandon_plan to be an unknown tool (searched tests.rs), and the plan-mutations gate tests (tests.rs:556, 632) are unaffected.
