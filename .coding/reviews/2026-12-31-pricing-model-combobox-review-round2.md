### Findings

#### F1 (high) — L3's blur-close breaks mouse entry selection on macOS/WKWebView

Mechanism, step by step (all verified against the source):

1. Tauri renders the frontend in the system webview: WKWebView (WebKit) on macOS, WebView2 (Chromium) on Windows.
2. WebKit on macOS follows the platform focus convention: mousedown on a `<button>` does **not** move focus to it (text inputs do). With the input focused and the dropdown open — the primary flow, since focusing the input auto-opens it (onFocus → `setOpen(true)`, :96) — mousedown on an entry button therefore blurs the input, and the blur's relatedTarget is null/body, not contained in `rootRef`.
3. The root onBlur (:63-68) runs `setOpen(false)` during the mousedown's default-action focus change — before mouseup/click.
4. React 18 flushes discrete focus events synchronously: the dropdown (and the entry button being clicked) unmounts before the click event is dispatched.
5. The click hit-tests against the new DOM — the entry button is gone, so its onClick (:130-139) never fires. The value does not change; the user's click merely closes the dropdown.

Second symptom, same root cause: with the input focused and the dropdown open, clicking the chevron toggle to close it blurs the input (uncontained) → close, then the toggle's click toggles false → true → the dropdown reopens; only a second click (focus now on body, no blur) closes it.

Windows is unaffected — Chromium focuses buttons on mousedown, so relatedTarget is the contained entry/toggle button and the blur never fires prematurely. The implementer's vitest run on this Windows machine could not catch this, and the node-env source-contract tests do not model focus behavior. This is a regression introduced by the L3 fix (pre-fix there was no blur handler, so macOS mouse selection worked), and it breaks the feature's primary interaction on one of the two platforms the project constitution requires ("builds and behaves on both macOS and Windows"). The round-1 report's suggested fix carried the Windows-only assumption ("The option buttons live inside the root, so clicking an entry does not close before its click fires") — true only where mousedown-on-button focuses the button. This finding is static-analysis-based (no macOS run available here), but each step rests on well-established WebKit behavior, not speculation.

**Fix (cross-platform, minimal):** add `onMouseDown={(e) => e.preventDefault()}` to the entry buttons and the toggle button — the standard pattern for blur-closing dropdowns. Preventing the mousedown's default focus change keeps focus on the input (no blur, no premature close), so the click fires and selects normally on both platforms; keyboard focus (Tab) and Enter/Space activation are unaffected, and the cross-row close still works (another row's input still takes focus on mousedown on macOS). (Alternative: defer the blur-close by a tick and re-check `document.activeElement` containment — works, but adds timer/re-open races; the preventDefault approach is simpler.)

**Trap to avoid when fixing:** with preventDefault, at entry-click time the input is already focused, so `inputRef.current?.focus()` becomes a no-op that fires no focus event — the skipOpenRef flag would go stale and swallow the next genuine open. Guard the refocus: `if (document.activeElement !== inputRef.current) { skipOpenRef.current = true; inputRef.current?.focus(); }` — this keeps the existing test contract strings (`skipOpenRef.current = true;`, `inputRef.current?.focus();`) intact verbatim.

**Regression test (source-contract, node-env convention):** assert the entry buttons and the toggle carry `onMouseDown={(e) => e.preventDefault()}` — e.g. a "review round 2 — cross-platform mousedown guard" test in ModelCombobox.test.tsx.
