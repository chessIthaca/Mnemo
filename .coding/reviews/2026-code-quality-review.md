# Code Quality Review — myharness (2026 whole-codebase review)

**Perspective:** Code Quality (Rust + TypeScript)
**Reviewer:** read-only reviewer
**Date:** 2026-04-04
**Scope:** all of `src/` (Rust brain), `src-tauri/` (Tauri shell + IPC), `frontend/` (React/TS), `tests/`. Verified against current source; `cargo clippy` run captured. No project files edited except this report.

## Executive summary

myharness is a well-engineered codebase: typed errors (`thiserror`) at the library boundary, `anyhow` only in the binary shell, careful concurrency (lock-free agent↔UI channel decoupling, brief lock holds, no awaits across held locks in production code), exhaustive doc comments on nearly every public function, and strong test coverage of the workflow lifecycle, approval gate, IPC serialization, and multi-agent fan-in. The main quality debts are a cluster of **dead/legacy code** kept alive only by tests (an entire `async-openai` conversion layer superseded by a raw-JSON request builder), a **duplicated provider key-resolution block** in `main.rs`, **two TypeScript type drifts** at the IPC boundary that force `as never` escape casts, and a handful of clippy warnings. None are correctness bugs. The largest files (agent/mod.rs 2376, openai.rs 1554, memory/mod.rs 1211, commands.rs 1191) are long but coherent and well-commented; splitting is desirable but not urgent.

**Overall verdict: Good-with-debt.**

# Rust findings

## 1. Idioms & error handling

- **Good — typed errors throughout the library.** `src/error.rs:9-58` defines a single `thiserror::Error` enum (`Config`/`Project`/`Provider`/`Tool`/`Workflow`/`Memory`/`Safety`/`Runtime` + `#[from]` for io/json/toml/sqlite) and a `Result<T>` alias. `anyhow` appears only in `src-tauri/src/main.rs` (`build_brain`), exactly where the module doc (`error.rs:1-4`) says it should (binary boundary). This is the correct topology.
- **Low — `expect()` on std `Mutex` poisoning is the dominant lock pattern, which panics on poisoning.** Every `RwLock`/`Mutex` guard in `agent/mod.rs` uses `.expect("… lock poisoned")` (e.g. `provider` at `mod.rs:265,278`, `safety_mode` at `mod.rs:1023`, `session_id` at `mod.rs:238,244`, `agent_id` at `mod.rs:250,257`, `last_prompt_tokens` at `mod.rs:583,592`, `constitution` at `mod.rs:114`; factory at `factory.rs:145,156,160,213,217,232,292`; IPC `approval.rs:29,40,46,73`). This is a deliberate, consistent choice and is **safe in practice**: a poisoned mutex means a prior thread panicked mid-guard, and for an agent runtime there is no sensible recovery other than to stop. Documenting this as an intentional convention (one line in `error.rs`) would make the pattern self-explaining rather than look ad hoc. Not a bug.
- **Nitpick — one production `unwrap()` chain in `main.rs` fallback that is technically infallible.** `main.rs:315` `MemoryStore::open_in_memory(...).unwrap()` and `main.rs:339` `SafetyRules::new(":memory:").unwrap()` are in the failed-brain fallback path. `open_in_memory` can only fail on OOM/schema-apply failure (degenerate); the `unwrap_or_else` guard makes this a last resort. Acceptable, but a `let _ = … ` or logging path would be more robust if a future schema migration ever fails. Low priority.
- **Good — Result propagation is consistent.** Production code propagates via `?` and converts with `map_err(|e| Error::Provider(...))` at the reqwest boundary (`openai.rs:162,167`). The `complete_with_retry` fallback (`agent/mod.rs:1139-1143`) even handles the degenerate "loop bound changed" case with a sentinel error instead of a bare `unwrap()`.

## 2. Duplication & dead code

- **Medium — `convert_message` / `convert_tool_choice` + the entire `async-openai` conversion layer is dead production code, kept alive only by tests.** `src/provider/openai.rs:694` (`convert_message`) and `:772` (`convert_tool_choice`) build `async_openai::types::ChatCompletionRequestMessage` / `ChatCompletionToolChoiceOption`. They are **only** called from `#[cfg(test)]` code (`openai.rs:1181,1197,1214,1233,1246,1252,1258`). The real request path is `build_request_json` (`openai.rs:347-476`), which constructs raw `serde_json::Value` and never touches `convert_message`/`convert_tool_choice`. The `async-openai` dependency + ~90 lines of conversion + their tests therefore exist solely to test themselves.

  **Correction (acted on after the report-of-reviews audit):** an earlier version of this finding claimed the production path `build_request_json` had "no dedicated unit test" of message→JSON shape for the multimodal/tool-call/assistant cases. That is **false** — `build_request_json` is directly and extensively unit-tested: `build_request_json_sends_image_blocks_when_multimodal` (`openai.rs:1536`), `_strips_image_blocks_when_not_multimodal` (`:1577`), `_plain_text_unchanged_when_not_multimodal` (`:1618`), plus `_includes_strict_when_some`/`_omits_strict_when_none`/`_includes_reasoning_effort_when_set`/`_omits_reasoning_effort_when_none` (`:1376,1407,1435`). So the real serialization path is **not** under-tested; rather, the `convert_message`/`convert_tool_choice` tests are **redundant** with the existing `build_request_json` tests (they cover the same cases through a different, unused code path). The severity is accordingly **Medium, not High** — this is dead-code cleanup, not a coverage gap.

  Fix: delete `convert_message`/`convert_tool_choice` + their tests + the `async-openai` dependency (drop a transitive crate) — the existing `build_request_json` tests already cover the production shape. Alternatively, if `async-openai` types are wanted as the source of truth, route production through them. The current state is two parallel serialization paths, only one exercised in prod.
- **Medium — duplicated provider key-resolution + client-build block in `main.rs`.** The main provider build (`main.rs:271-304`) and the vision provider build (`main.rs:364-388`) repeat the same `config.key_for(...).or_else(OPENAI_API_KEY).or_else(ANTHROPIC_AUTH_TOKEN).unwrap_or("dummy")` + `match ep.kind {…}` + `OpenAiClientConfig {…}` block verbatim. A third copy lives in `set_model` (`commands.rs:446-466`, explicitly commented "Mirror the api-key fallback chain from build_brain"). Three copies of a security-sensitive credential-resolution chain is a drift hazard (e.g. a new env var added to one and forgotten in another). Extract a `fn build_client(config, endpoint, model, multimodal, reasoning_effort) -> Arc<dyn LlmClient>` shared by all three.
- **Low — `_dbg_test.rs` is a debug shim with no purpose.** `src/provider/_dbg_test.rs` (16 lines) is a `#[test] fn dbg_reqwest` that prints `reqwest::Client` debug info and asserts nothing. It's harmless (it's a test) but it's leftover scaffolding that clutters the provider module and runs on every `cargo test`. Delete it.
- **Low — `#[allow(unused_imports)]` masking a genuinely unused top-level import.** `openai.rs:20-21` `#[allow(unused_imports)] use futures::StreamExt;` — the top-level `StreamExt` is unused in production (the `tokio::spawn` block re-imports it locally at `openai.rs:188`); it's only referenced in tests. The `#[allow]` silences the real signal. Remove the top-level import (tests can import it themselves).

## 5. Concurrency correctness

- **Good — no `await` while holding a `Mutex` guard in production code.** Clippy's only `await_holding_lock` warning is `runtime/agent.rs:864` (`captured.lock().unwrap()` held across `cmd_tx.send(...).await` at `:877`) — this is in the `CapturingProvider` **mock inside `#[cfg(test)]`**, not production. Searched all `*.lock()`/`*.lock().await` sites in `src/`; production locks are released before any `.await` (e.g. `agent/mod.rs:465-473` locks the workflow, builds the prompt, drops the guard in the block, then awaits the stream; `commands.rs` consistently does `let mgr = manager.lock().await; … drop(mgr);` before sending/backlog-mutating awaits; `events.rs:246-248` reads parent id under lock then `drop(mgr)` before the send).
- **Good — `select!` honors interrupt/cancel at every streaming await point.** `agent/mod.rs:506-671` the streaming `select!` branches on `cmd_rx.recv()` for `Interrupt` (aborts stream), `Cancel` (returns immediately), and buffers `Suggestion`/`Prompt`. Summarization is interruptible via `summarize_with_interrupt` (`context.rs`, with buffered-command re-injection at `mod.rs:392-419`). Approval waiting is interruptible (`approval.rs:128-150`). The one subtlety: a `Cancel` mid-stream returns a `TurnOutcome` with empty text (drops in-flight deltas) — correct, but worth a test asserting no partial tool-call is left in `messages` after a mid-stream cancel (currently untested).
- **Good — `RwLock` vs `tokio::Mutex` choices are appropriate.** Provider/context-manager/safety-mode use `std::sync::RwLock` (read-heavy, never held across await — the loop snapshots into a local clone at turn start, `mod.rs:343-352`). The workflow uses `tokio::sync::Mutex` (held briefly, sometimes across the prompt-build but dropped before awaits). The manager + agent_loops + backlog use `tokio::sync::Mutex` (held across nothing that awaits long). The SQLite `Connection` uses `tokio::sync::Mutex` (serialized DB access — correct, rusqlite `Connection` is `!Sync`-for-concurrent-use). Safety-rules/constitution use `std::sync::Mutex` (mtime-check + cache, never across await). All sound.
- **Low — `tokio::spawn` fire-and-forget for stats recording.** `agent/mod.rs:615-617` spawns a task to `record_request_stats` so stats never block the turn. Correct intent. Minor: an unbounded sequence of these during a fast multi-tool turn could spawn many tasks before any completes (they're tiny DB writes, so this is fine in practice), but there's no backpressure. Acceptable.

# TypeScript / Frontend findings

## 8. Type safety at the IPC boundary

- **High — `WorkflowStateInfo` TS type drifts from Rust, forcing `as never` escape casts.** The Rust `WorkflowStateInfo` (`commands.rs:93-103`) has four fields: `state: String`, `plan`, `depth: usize`, `parents: Vec<String>`. The TS mirror (`lib/types.ts:140-143`) declares only `state: string` + `plan: PlanFile | null` — **`depth` and `parents` are missing**. Worse, `state` is typed `string` in TS, but the Rust value is `workflow.state().to_string()` (i.e. `"Planning"`/`"Executing"`/`"Complete"` — Display form, **capitalized**), while the store's `setWorkflowState` expects the `WorkflowState` union (`"planning"`/`"executing"`/`"complete"` — **lowercase**, the serde form). This mismatch is papered over with `wf.state as never` at `App.tsx:98` and `StatusBar.tsx:87`. Consequences: (a) `as never` silently accepts any string, so a Rust Display change or a new state variant produces a store value that doesn't match the `WorkflowState` union and won't be caught by `tsc`; (b) the cast is to `never` (the most permissive escape) rather than a narrowing function, so it defeats the type system entirely. Fix: make Rust serialize the state via the enum (serde lowercase) in `WorkflowStateInfo`, type `state: WorkflowState` in TS, add `depth` + `parents`, and drop the `as never` in favor of a direct assignment. Verify the casing actually matches at runtime (Display = capitalized vs serde = lowercase is the latent bug here).
- **Medium — `Approval` is typed `unknown` in `PendingApproval.args`.** `useAgentStore.ts:166-170` `PendingApproval.args: unknown`, populated from `event.args` (`SerializableAgentEvent.approval_request.args` is `unknown` in `types.ts:97`). The Rust `args: serde_json::Value` is a JSON value, so `unknown` is the honest TS type — but downstream the args are re-parsed with `JSON.parse(completedCall.args)` and field-accessed with `as string` casts (`useAgentStore.ts:979-982`: `parsedArgs.path as string`, `old_string as string | undefined`). These casts are unchecked. A `Record<string, unknown>` + a small `asFileEditArgs()` guard would make the diff-snapshot logic type-safe instead of stringly-cast.
- **Good — the event payload union mirrors Rust faithfully.** `SerializableAgentEvent` (`types.ts:87-128`) is a discriminated union with `kind` tags matching the Rust `#[serde(tag = "kind", rename_all = "snake_case")]` exactly (verified: `text_delta`, `tool_call_arg_delta`, `suggestion_injected`, `child_finished`, `workflow_state_changed` all match the snake_case rename). `BacklogItem`/`BacklogStatus`/`RunAllProgress`/`BacklogChangedPayload` match `backlog.rs`. `ToolResult`/`ApprovalPreview`/`PlanFile`/`PlanStep`/`FinishReason`/`AgentInfo` all mirror their Rust counterparts. `Approval = "approve" | "deny" | "deny_all"` matches the `rename_all = "snake_case"` serde. This is solid.
- **Good — no `any` leakage.** Searched all `frontend/src/**/*.{ts,tsx}`: zero `as any`, zero `any` type annotations in non-generic positions. The only escape casts are the two `as never` (above) and the `as string` arg casts (above). No `@ts-ignore` or `@ts-expect-error` anywhere.

## 9. Null/undefined handling & store ergonomics

- **Good — consistent optional-chaining and null guards.** `getOrCreate` (`useAgentStore.ts:423-428`) returns `agents[id] ?? emptyAgentState()` so no agent is ever accessed unguarded; `selectMainAgentId` (`:438-448`) handles empty maps; `mainAgentId()` (`:610`) and the `exited` handler (`:1102-1131`) guard `activeAgent === agent_id` before falling back to the main agent. The `setTimeout` steer cleanup (`:1071-1086`) re-reads `st.agents[agent_id]` and returns `st` if gone — no crash on a cleared agent.
- **Medium — `handleAgentEvent` is a 340-line switch with deeply nested mutation, in a single `set()` callback.** `useAgentStore.ts:821-1160` builds `next: AgentState = { ...agent }` then mutates `next.*` across ~12 cases, with several early `return { …s, agents: {…s.agents, [agent_id]: next}, … }` and several `break`s that fall through to a shared tail. The mix of early-returns and fall-through-breaks is hard to audit: e.g. the `tool_result` case (`:919-993`) returns early (skipping the tail), while `usage`/`context_usage`/`finished` break to the tail (`:1161` `return { …s, agents: {…s.agents, [agent_id]: next } };`). A reader must track which cases return vs break. Splitting each case into a pure `reduce(agent, event) => AgentState` function (tested independently) would make the reducer legible and unit-testable — right now it's only exercised through the live event stream.
- **Low — `agents[id]` indexed access in selectors can cause over-rendering.** Components selecting `useAgentStore((s) => s.agents[id])` re-render on every `agents` object identity change (every event creates a new `agents` map via spread). The `Message` component is memoized (`baseline` notes), and `appendStreamingText` batches via rAF (`useAgentEvents.ts`), which mitigates the hot path. But any selector returning `s.agents[activeId]?.transcript` re-runs on every agent's event (not just the active one) because the `agents` map reference changes for all. A per-agent subscription or `zustand`'s `useShallow` on the specific slice would reduce re-renders. Not a correctness issue; a perf-smell the rAF batching already mostly addresses.
- **Good — store state shape is flat and keyed by id.** `agents`/`agentNames`/`agentParents`/`workflowStates` are parallel `Record<AgentId, …>` maps, which is easier to reason about than nested `agents[id].workflowState`. The `exited` handler deletes from all four consistently (`:1108-1115`).

## 10. General TS quality

- **Low — `eslint-disable react-hooks/exhaustive-deps` used 11 times, all on intentionally-fire-once effects.** `App.tsx:140,164`, `StatusBar.tsx:100,111,117`, `PlanProgress.tsx:41,52,61`, `StatsView.tsx:367`, `useCountUp.ts:49`. Without the comment, a future reader can't tell a deliberate skip from a forgotten dep. The `useAgentEvents.ts:159` effect **correctly** lists `[handleAgentEvent, appendStreamingText]` as deps (no disable) — good model.
- **Good — `console.error` is used, not swallowed.** Every `try/catch` around an IPC call logs `console.error("failed to …", e)` (`App.tsx:90,101,107,131,137`, `useAgentEvents.ts:115,144`, `StatusBar.tsx:89`). Errors are surfaced to the user via `error` transcript entries (`useAgentStore.ts:1132-1155`).

# What's done well

- **Error topology is textbook:** `thiserror` typed errors in the library, `anyhow` only at the binary boundary, `Result<T>` alias, `?` propagation, `map_err` at the reqwest seam. The `error.rs` module doc states the convention.
- **Concurrency discipline:** no awaits across held locks in production (clippy confirms the only `await_holding_lock` is a test mock), brief lock holds, snapshot-then-release pattern for the swappable provider, lock-free `try_send` under the cleanup-subagents lock with a documented FIFO-correctness rationale (`events.rs:288-295`).
- **Doc-comment coverage is ~99%** on public functions across the largest files — the constitution rule is effectively honored; only `get_config` slipped through.
- **Test coverage is broad and meaningful:** workflow gate, full lifecycle, resume, multi-agent independence, approval matrix, SSE parsing, memory ranking/strength, consolidation, IPC round-trip. Tests are behavior-named (`planning_gate_hides_write_tools_until_a_plan_exists`, `between_turn_steer_is_converted_to_user_message_and_runs_turn`) and document intent.
- **The channel-decoupled `AgentEvent`/`SerializableAgentEvent` split** (non-serializable oneshot extracted at the IPC seam, `channels.rs:198-298`) is a clean, well-tested solution to "a `oneshot::Sender` can't cross Tauri IPC."
- **Frontend type fidelity is high** for the event union and backlog types; the discriminated-union approach gives exhaustive `switch` checking.
