### Findings

**LOW 1 — Cross-UTC-midnight chunked append with a bare name rejects a legitimate append chunk** (`src/tool/agent/write_review_report.rs:262-267`)

A reviewer that writes chunk 1 with a bare name (`"my-review.md"`) lands at `<today1>-my-review.md`. A follow-up `mode:"append"` with the same bare name after UTC midnight resolves the as-given path (not a file) → the normalized `<today2>-my-review.md` (also not a file) → the append-CREATE path → the verdict check rejects a legitimate verdict-less append chunk with "Received first line: …" — confusing feedback for an append, and retrying identically trips `REVIEW_REPORT_MAX_FAILURES` and aborts. The plan file and knowledge record claim "the chunked protocol survives … midnight rollover", but that holds only for date-prefixed names (as-given exists → reused), not bare names across a date change. Rare (a single UTC-midnight boundary must fall between two chunks of one report), loud, and recoverable (re-append using the dated basename from the first success message) — hence LOW. Fix direction: on the append path, when neither the as-given nor the today-normalized name exists, look for an existing `<any-date>-<stripped-name>` file (require exactly one match) before taking the create path.

**LOW 2 — The report-failure abort message overclaims** (`src/agent/turn.rs:669-674`)

"…No report was written." is false whenever a successful write preceded the failure streak (the counter resets on success — e.g. LOW 1's scenario, or a mid-report name change): a partial report exists and `last_review_report` is set, so the parent is told to read a partial report while the child's transcript says none was written. "verdict-line validation keeps rejecting it" also presumes the failure mode (IO errors and invalid-args failures count toward the same counter). Fix direction: hedge the wording ("the reviewer could not complete its review report"), or branch on `self.last_review_report()` to say "no COMPLETE report was written" when a partial one exists.

### Security

- **Path traversal: unchanged and sound.** `resolve_under_reviews` rejects absolute paths, any separator (both `/` and `\` and `MAIN_SEPARATOR`), and `..` before touching the filesystem, then enforces canonicalize+`starts_with` on the target; normalization cannot introduce separators (strip-only, on a validated bare name), so both resolution branches stay inside the sandbox. FinishTool's containment check runs on the RESOLVED path in both branches: an existing file outside reviews (absolute or `..`-relative) still fails `canonicalize().starts_with(reviews_dir)`; a non-existent outside path falls back to `reviews_dir/<basename>`, and `file_name()` can never contain separators or `..`, so the fallback cannot escape — it either finds the real report or fails the non-empty check. The `file_name() == None` edge (path ending in `..` or a separator) joins `""` → the reviews dir itself → `under_reviews` true but `read_to_string` fails → non-empty false → rejected. Symlinks inside reviews pointing outside are still resolved by `canonicalize` and rejected.
- **The 120-char first-line cap** is `chars()`-based (no char-boundary panic) and only echoes reviewer-authored content back to the reviewer — no injection surface, no sensitive data in notifications (the interpolated path is a validated bare filename).
- No new `#[allow]`, no unsafe, no Windows-only APIs; `\\?\` appears only in comments and in test assertions checking its absence.
