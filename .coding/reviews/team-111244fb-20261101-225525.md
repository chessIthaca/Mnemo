### HOW: Claude Code session identity for the external Mnemo lead (plan 111244fb step 3)

Design research for plan 111244fb step 3 (idle lead re-attaches from its own hooks).

VERIFIED (Claude Code docs, code.claude.com, 2027-01-15):
- Hooks receive `session_id` in the stdin JSON (common input field). The only place Claude Code exposes it.
- MCP stdio servers receive NO session identity: no env var carries it (env-vars reference page lists only behavior-control CLAUDE_* vars), the MCP protocol (initialize/tools/call) has no session field, and .mcp.json only substitutes ${CLAUDE_PLUGIN_ROOT}.
- So the bridge (mnemo2-mcp serve, spawned by Claude Code from mnemo2/plugin/.mcp.json) cannot learn Claude's session id. Parent-PID keying is not a session id, needs ancestor walking (no std API on Windows), and breaks under pid reuse / Agent-SDK multi-session processes — not reliable.
- RELIABLE channel that exists: the Stop hook knows its session_id on stdin and composes the waiter suggestion command the same session then runs → `mnemo2-mcp wait --session <id>` posts it to /lead/wait → server records it on ExternalLead. PostToolUse hooks then send their session_id on /lead/notices; the server re-attaches an idle lead only when the recorded id matches. No guessing anywhere ("letting the first hook win" is forbidden by the plan).
- Limitation: a lead that NEVER ran the waiter has no recorded id → hooks cannot re-attach it (it still re-attaches via an MCP tool call, today's behavior). The tools/call attach path records no id.

Key code pointers: attach flows mcp_server.rs `mcp()` (tools/call → self.attach) and `wait()` (/lead/wait → self.attach); idle release in `sweep_idle` = lead.release_external_lead() then team.mark_external_lead_idle(now_ms); notices() in mcp_server.rs:815; ExternalLead struct team.rs:553; hooks.rs notices()/wait(); Stop-check suggestion in hooks.rs NoticesMode::StopCheck.
