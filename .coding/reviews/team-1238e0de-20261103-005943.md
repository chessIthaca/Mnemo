### BUG: compact-then-switch failed Mnemo2 workers — root cause + the swap_needs_compaction rule (plan 1238e0de)

BUG root cause (plan 1238e0de, commit 593f84e1 on wt/agent-swapNoti), verified in src-tauri/src/mnemo2/team.rs worker pump:

- `CompactStarted` (emitted only from the deferred compact-then-switch path, turn.rs handle_pending_swap) sets `worker.compacting = true, busy = true, status = Working`.
- That path emits NO `Compacted` — the only `AgentEvent::Compacted` is turn.rs:3349 (regular maybe_compact). So the swap's paired end WAS the `Error { retrying: false }` it sent on completion, which the pump folded as: `if worker.compacting { clear badge; busy=false; status → Idle/NeedsYou; error = Some(msg) }` else `status = Failed`.
- Hence the 2026-11-02 symptom split in two: a switch that deferred but did NOT summarize (conversation fit) left compacting false → **Failed**; a switch that did summarize → Idle + error recorded. Both are wrong; the swap succeeded either way.
- Fix shape: kernel emits the new informational `AgentEvent::ModelSwapSummarized { model }` (serialized `model_swap_summarized`), gated on `rewrote`; the pump arm clears only the compacting badge (`changed |= worker.compacting; worker.compacting = false;`) and never touches status/busy/error.

Second, independent defect the same plan fixed: `set_explicit_provider` deferred whenever the new window was SMALLER, summarizing conversations that fit. Now the one shared rule is `AgentLoop::swap_needs_compaction(&new_context_manager)`: `live_token_count > 0 && live_token_count >= new_cm.effective_limit()` (the turn loop's own trigger, messages + tools overhead). `AgentSession::set_model` computes CompactsFirst/NextRequest from the same call, and handle_pending_swap's gate is `pending.context_manager.should_summarize(messages)`.

Test-harness gotcha for Mnemo2 end-to-end swap tests: the worker BRIEF is not in `messages` for token counting (it sits in the system/prompt scaffolding; a 120K-char brief left `count_tokens(messages)` tiny), so the pin's live count can stay under the new trigger and the swap lands WITHOUT deferral. Also a turn ends after 3 consecutive tool ERRORS (MAX_RETRIES), so growing a conversation by tool iterations must use SUCCESSFUL calls (e.g. `message_parent`, stub helper `stub_message_parent_turn`). And the new model's own compaction pass emits CompactStarted+Compacted (no-op, "too few messages"), whose pump arm sets busy=false/status Idle — so an end-to-end assertion should require "not Failed, error None", not "status == Working".
