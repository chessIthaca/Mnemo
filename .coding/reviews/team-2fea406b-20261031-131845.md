### HOW: accept Explorer-copied image-file pastes via clipboardData.files (empty-type items never carry image/*)

Durable clipboard-paste fact (plan 2fea406b): an image FILE copied in File Explorer and pasted into a web composer (Chromium/WebView2) does NOT announce itself through clipboardData.items as image/* — its file-kind DataTransferItem carries an EMPTY type; the real image File surfaces only in clipboardData.files. An items-only filter (kind === "file" && type.startsWith("image/")) therefore drops Explorer-copied image files entirely (no attach, no preview thumbnail), while screenshot/bitmap pastes DO produce image/* items.

Fix pattern (mnemo2 Composer.svelte imageFiles, commit 91cb611): when no image/* item is found, fall back to Array.from(data?.files ?? []).filter(f => f.type.startsWith("image/")); items keep precedence and are returned unchanged when present, so an ordinary screenshot paste (Chromium lists it in BOTH items and files) never double-attaches.

This supersedes the earlier per-session guess that an Explorer-file paste showing no preview was "by design, same as Mnemo1" — it was the actual defect.

Test pattern: hand-build a paste Event with Object.defineProperty(event, "clipboardData", { value: { items: [{ kind: "file", type: "", getAsFile: () => file }], files: [file] } }); prove red against the items-only filter, green after the fallback. Regressions live in mnemo2/src/components/Composer.test.ts ("an Explorer-copied PNG file renders its thumbnail before sending" and "a real pasted PNG renders its thumbnail before sending") — both wire the real frontend/src/lib/attachImages converter via vi.importActual so the file-wide vi.mock cannot hide the FileReader path.
