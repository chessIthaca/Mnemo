### BUG: Mnemo2 mnemo2.toml kept retired tier ids after the ladder upgrade (fixed dd812e42)

Root cause: `load_routing_settings` (src-tauri/src/mnemo2/dispatch_routing.rs) converted retired tier ids (average→routine, difficult→high, simple→trivial) in memory via `TierLadder::convert_old_id` but never wrote them back, so ~/.mnemo/mnemo2.toml kept `fallback_tier = "average"` until a routing save happened to run.

Fix (plan 5310e9bc, commit dd812e42 on wt/agent-routingI): the load now converts the RAW `[routing]` table (`fallback_tier` value + `[routing.effort]` keys — the only remaining tier-valued fields) and, when anything converted and the table still deserializes, rewrites mnemo2.toml once through a new `save_converted_routing_table` that mirrors `save_routing_settings`'s read-modify-write (replace only the `routing` key, keep other top-level tables). Failed write only logs; no conversion ⇒ no write (byte-identical file, asserted).

Key constraint discovered: `save_routing_settings` serializes `RoutingSettings`, which lost its `effort` field in plan 87932c46 step 3 — so routing through it DELETES the vestigial `[routing.effort]` table outright and cannot satisfy the plan's own test (effort key "difficult" must survive as "high"). Hence the raw-table helper (the plan's "or a small helper it calls"). Note the live file still carries an empty `[routing.effort]` on installs that have not loaded since.

Tests: `retired_tier_ids_are_rewritten_on_disk` (red-checked by disabling the write-back), `ladder_tier_ids_are_not_rewritten_on_load`. Verified: clippy --features mnemo2 --lib --tests --bins -D warnings exit 0; cargo test --features mnemo2 --lib --bins 535/319/166 passed, 0 failed.
