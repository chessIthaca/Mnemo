## Plan notes (retired at close)

### DECISION: Settings dialog unsaved guard is one context registry, per-page trackUnsaved()

mnemo2/src/lib/unsavedEdits.ts holds the settings dialog's single unsaved-edits guard (plan 5aac2023 step 1, commit 1e76be89, wt/agent-settings).

Shape: a Svelte context registry — `createUnsavedRegistry()` returns `{ register(check) -> unsubscribe, hasUnsaved() }` over a `Set<() => boolean>`; `provideUnsavedRegistry()` creates it and `setContext`s it (SettingsDialog, during init); `trackUnsaved(check)` (pages, during init) `getContext`s + `onDestroy(registry.register(check))`, and is a no-op when no registry exists (page rendered alone in a test/preview). Checks are plain closures over each page's deriveds, so they read fresh at question time — no runes in the lib.

Guard lives in SettingsDialog only: `requestLeave(action)` asks when `registry.hasUnsaved()`, else runs `action`; parked in `pendingLeave`, rendered as InlineConfirm.svelte ("Keep editing" / "Discard changes", role="alert", focus on Keep editing) at the top of `.settings-page`. Sheet's `onclose` is wrapped (`onclose={() => requestLeave(onclose)}`), so X / Escape / backdrop all funnel through one point without touching Sheet.svelte (shared with Composer, StartScreen, TopBar, WorkerDeleteSheet). Rail clicks go through `requestPage(next)`: current page is a no-op, a different page retargets the banner. `beforeunload` also lives here (Tauri's webview prompt on window close stays unverified).

Registered pages: Endpoints `() => dirty`, Tiers `hasUnsaved`, Models `compaction||vision||index||budget`, Savings `optimizer||pricing`, Safety `mode||rules`, Mcp `dirty || formOpen` (an open add/edit form holds typed values `dirty` misses), Specs `artifactDirtyNow || configDirty`. Project and Appearance apply immediately — never registered.

Removed: TiersPage's capture-phase window click/keydown + native `confirm("Discard unsaved Tiers edits?")` guard, its `pageEl` bind, and `leavesPage()` + its tests from lib/layaSettings.ts. Tiers' force-on gate `confirm()` is a different question and stays. Supersedes the React-era dialog-level dirty map and the Svelte rewrite's per-page guard (which existed only on Tiers).

### BUG: Svelte assignment_value_stale is dev-runtime, not a build warning (mnemo2)

Svelte 5's `assignment_value_stale` is a **dev-runtime client** warning, not a compile/build warning: it lives in node_modules/svelte/src/internal/client/dev/assign.js and fires only when a `$.assign(...)` dev call assigns a value whose post-assignment property value is a different object carrying STATE_SYMBOL (e.g. `obj.field = {...state.proxy}`). Consequences verified 2026-11-05 on mnemo2 (Svelte 5.57.3, worktree wt/agent-dialogSm, plan 5aac2023 step 2):
- `npx vite build` can never print it (production compile emits plain assignments), so a clean build is not evidence the warning is gone.
- Block-bodied vs expression-bodied arrow callbacks (`() => (a = b)` vs `() => { a = b; }`) compile to the SAME assignment; changing the arrow body cannot silence this warning.
- It did not reproduce in ModelsPage.test.ts (13 tests pass silently) nor in the vite build with the old expression bodies, so the Mnemo2 ModelsPage "assignment_value_stale" finding from the 2026-11-05 dialog review is not reproducible in the current tree; a real remedy would be assigning a plain snapshot rather than reading back a state proxy.
