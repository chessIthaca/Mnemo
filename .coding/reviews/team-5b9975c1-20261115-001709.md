### HOW: keep a Tauri sidecar out of a library crate's build script (TAURI_CONFIG externalBin race)

The Tauri CLI passes its merged config (e.g. `--config tauri.bundle.conf.json`) to EVERY crate's build script in the `TAURI_CONFIG` env var, so each `tauri_build::build()` resolves `bundle.externalBin` relative to its own manifest dir and copies the sidecar into `target/<profile>/`. In this repo the app package (src-tauri/mnemo2-app) and the host library mnemo-app (src-tauri) both ran tauri_build, so both copied `mnemo2-mcp.exe` concurrently — Windows refuses the second open: os error 32 (build.yml run 43648972717, tauri-build 2.7.4 lib.rs:163).
Fix pattern (step 7 of plan 5b9975c1, commit 5c5f2f84 on wt/agent-libStrip): the library's `src-tauri/build.rs` calls `strip_external_bin_from_tauri_config()` FIRST in `main()` — parse `TAURI_CONFIG` with serde_json (a `[build-dependencies]` entry), remove `bundle.externalBin`, `set_var` the result back — so only the app package copies the sidecar. Then the staging script only populates `src-tauri/mnemo2-app/binaries/`; `src-tauri/binaries/` is gone and `.gitignore` no longer covers it.
Red check: `$env:TAURI_CONFIG='{"bundle":{"externalBin":["binaries/mnemo2-mcp"]}}'; cargo build -p mnemo-app --features mnemo2` fails with `resource path binaries\mnemo2-mcp-x86_64-pc-windows-msvc.exe doesn't exist` without the strip and succeeds with it.
