### HOW: batched file_edit read-receipt cites go stale after an earlier line-shifting op

In file_edit/multi_edit `ops` arrays the read-receipt cite form ({from_read, lines, new_string}) is validated against the snapshot the receipt was minted from, NOT against the file as left by the preceding ops in the same array. So if an earlier op shifts lines (inserts/deletes), later cites land at stale positions and silently corrupt the file — observed 2026-11-02 on plan 7da65f3c step 1: three cites in one store.ts batch inserted the plan/file actions inside openTrace's object literal and inside dismissToast(), and similar batches mangled MemoryView.svelte, PlanTab.svelte and FilesTab.svelte. Symptom: svelte-check reports "'(' expected" / "Module '../lib/store' has no exported member 'actions'" cascades across every importer.

Rule: in a multi-op batch use verbatim content anchors ({old_string, new_string}) for every op, or do one read-receipt cite per call after a fresh read. Repair: read the git diff of the file, restore the clobbered region from HEAD plus the intended edit in ONE cite, then re-diff until the change set is pure additions. A full file_write from `git show HEAD:<path>` plus the intended edits is the safe rebuild when several regions are hit.
