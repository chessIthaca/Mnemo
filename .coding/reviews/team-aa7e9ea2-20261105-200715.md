### BUG: headless command-queue-full test races on macOS (agent drains cmd_rx mid-turn)

`tests/integration/headless.rs::close_and_wait_rejects_a_full_command_queue` cannot fill the queue deterministically on macOS; it is now `#[cfg_attr(target_os = "macos", ignore = ...)]`. Commit 1a6b093f on wt/agent-macTestF (plan aa7e9ea2, CI run 42037069902).

Root cause (no production bug): the agent command channel holds **64** slots (`src/host/runtime.rs:405`, `mpsc::channel(64)`), and the turn polls `cmd_rx.recv()` *beside* the pending provider future — the `select!` at `src/agent/turn.rs:4805-4828` (`let complete_fut = self.complete_with_retry(...)` … `select! { result = &mut complete_fut, cmd = cmd_rx.recv() }`) and the mid-stream loop at `:5196`; compaction matches via `context.rs::summarize_with_interrupt`. So the agent drains each queued `Compact` while the provider is still pending.

Which side wins is a real race: `Session::send` -> `agent_command` awaits the manager mutex (`sessions`/`parked` locks too) BEFORE reaching `AgentManager::send`'s `try_send`, and tokio mutex acquisition consumes coop budget (budget = 128, `tokio::task::coop`), so the sender yields and lets the consumer task run. On the multi-core macOS runner the consumer wins; on Windows the sender wins and `try_send` returns Full as the test expects.

Key consequence for future work: **no provider behaviour can wedge that `select!`** — a hanging `complete()` is itself a branch of it — so a test hook in production code is the only deterministic alternative. Don't try to "fix" this by making the provider hang.

Related: the browser tool-count expectations in `src/agent/factory.rs` are now platform-aware — the browser family is 10 offscreen tools everywhere + 6 on-screen WebView2 tools gated `#[cfg(windows)]`, i.e. 42/41 on Windows with `--features browser`, 36/35 on macOS, 26/25 without the feature.
