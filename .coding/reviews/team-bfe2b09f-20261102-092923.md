### BUG: Worker shell tool hung forever + leaked the process tree when a command left a child running (plan bfe2b09f)

Symptom: a shell command that started a process (backgrounded `npx vite`, dev server) never returned — the worker hung 50-90 minutes — and the process outlived the call, holding the `.worktrees/agent-*` folder open so team_merge could not remove the worktree ("file is in use by another process").

Root cause (plan bfe2b09f, src/tool/agent/shell.rs): after the shell itself exited, the success path joined the two pipe readers with NO bound — a grandchild that inherited the pipe handles keeps the pipes open, so the readers never saw EOF. `kill_on_drop` killed only the shell, not descendants, so they also survived the timeout path.

Fix (commit c5b5f07 on wt/agent-shellTre, 2026-11-02):
1. Bounded post-exit join: READER_JOIN_GRACE (3 s) after shell exit; on expiry the readers are stopped GRACEFULLY via a oneshot stop arm in pump_stream — breaking the loop normally returns the bytes captured so far (an abort would discard the task's stack) — and the output carries BACKGROUND_HOLD_NOTE ("a background process started by the command kept the output pipe open; it was stopped and the captured output may be truncated").
2. TreeKillGuard (drops on every exit path: success return, timeout error, agent interrupt): Windows assigns the shell to a Job Object with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE right after spawn (new windows-sys feature Win32_System_JobObjects; OwnedJobHandle newtype impls Send because HANDLE is a raw pointer); Unix spawns with process_group(0) and the guard kills the group at drop via the POSIX `kill` utility (no libc dep — same choice as the app crate's pid_alive). Documented accepted race: the microseconds between spawn() and AssignProcessToJobObject. Failure to create/assign the job degrades to the pre-fix behaviour (inert guard), never fails the call.

Intended policy: workers must not run dev servers — no shell command may leave one behind.

Regression tests (both in the shell tests module, red before green): `background_child_holding_the_pipes_does_not_hang_the_call` (outer 30 s tokio timeout so a regression fails instead of hangs; asserts <15 s return, the note, and the grandchild dead by pid — pid from `(Start-Process -NoNewWindow -PassThru ping ...).Id` / `sleep 60 & echo $!`); `timed_out_command_kills_the_background_grandchild` (tool timeout 10 s; grandchild pid via a file the command writes — the timeout path discards stdout; -PassThru REQUIRED or $p has no Id). pid liveness probed per-platform in tests: Windows OpenProcess+GetExitCodeProcess==STILL_ACTIVE (mirrors instance_marker::pid_alive), Unix `ps -p`.

Gotchas hit while testing: (a) under 60-way PowerShell saturation of the module run the pid write raced a 5 s tool timeout (empty file) — 10 s is the safe cut; (b) Start-Process without -PassThru returns nothing and Set-Content writes an empty pid file; (c) `cmd /c timeout /t N` exits immediately under redirected stdin (memory b860c7ed) — use `ping -n 60` as the long-lived Windows grandchild; (d) in the unfixed state the test binary lingered in teardown until the leaked ping's full 60 s lifetime expired — the fix removes the linger.
