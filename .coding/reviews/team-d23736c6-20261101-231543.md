### BUG: pid_alive read a held-open exited process as alive — stale instance.json blocked the project (d23736c6, fixed 5eb1b4b)

Symptom: after Stop-Process on a Mnemo2 (pid 48684) for a rebuild, the new build refused the project: "another Mnemo2 process (pid 48684) is using the project" while tasklist showed no such process; .coding/instance.json still named it. Removing the file by hand fixed it.

Root cause: on Windows an exited process keeps its kernel object while ANY process still holds a handle to it — the mnemo2-mcp launcher keeps the spawned Child — so instance_marker::pid_alive's bare OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION) probe returned true for the dead instance; it never consulted the exit code.

Fix (commit 5eb1b4b on wt/agent-pidAlive, plan d23736c6, file src-tauri/src/instance_marker.rs): after OpenProcess succeeds, GetExitCodeProcess; alive only when the code is STILL_ACTIVE (259, from windows_sys Win32::Foundation — typed NTSTATUS, cast as u32); CloseHandle on every path. Regression test an_exited_process_held_open_is_not_alive (spawn cmd /c exit 0, hold the Child, wait, assert !pid_alive) — FAILED before the fix (panic at the assert), green after. Companion test the_current_process_is_alive guards the probe against over-shrinking.

Accepted residuals: (1) a process that really exits with code 259 is indistinguishable from live (marker warns, never locks); (2) a pid recycled to an unrelated live process still reads as the marker's writer. The plan's optional guard for (2) — conflict_for comparing the marker's started_at with GetProcessTimes creation time (reused pid → marker stale) — was implemented and unit-tested, then REVERTED before commit: it makes mnemo2::project::tests::attach_requires_confirmation_for_a_live_incumbent fail, because that test's fixture marker {pid: live child, started_at: 1} is semantically a recycled-pid marker under the guard (child created ~2026 >> started_at 1 + slack), so the live-incumbent conflict disappears — violating acceptance scenario 2. Re-landing the guard requires making that fixture realistic (spawn the child, then write started_at = current epoch seconds — the child is created before the write, so the guard sees a consistent marker), an edit in project.rs outside the step's ownership (own: instance_marker.rs only). Reported to the lead for adjudication.
