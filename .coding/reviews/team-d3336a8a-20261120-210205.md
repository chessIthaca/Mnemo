## Plan notes (retired at close)

### HOW: Mnemo instances share one laya-serve via ~/.mnemo/run/laya leases

Mnemo2 shares one `laya-serve` per machine through the generic lease dir `src/host/shared_service.rs` (re-exported as `mnemo::shared_service`): `service.json` {pid, port, token, version, started_ms, models} written atomically, `lease-<instance pid>.json` per attached instance, dead-pid pruning via `mnemo::process_tree::pid_alive` (moved there from `src-tauri/src/instance_marker.rs`, which now delegates), a token `spawn.lock` (60 s stale takeover, 30 s wait then proceed unlocked), and a 2 s loopback HTTP probe.

`LayaManager` (`src/host/laya.rs`) entry points: `attach_shared` (probe + lease only, used by `Setup::attach_laya`'s fast attach leg), `acquire`/`acquire_on(models, Option<port>)` (spawn lock → attach or spawn), `finish_start` (post-fill task that re-checks the lock and re-points the classifier slot when another instance won), `await_ready`, `start_server_models`/`start_managed_server` (no port parameter any more — acquire allocates). `stop`/`Drop` only release the lease; a shared server is never killed by an instance.

Shared spawn = detached (Windows DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP, Unix process_group(0) — not setsid, no libc dep) and no KillOnCloseJob; only catalog checkpoint ids are shared (a fine-tuned artifact, a model mismatch, an unreachable descriptor or a missing watchdog binary all fall back to the private kill-on-close child). The watchdog is the hidden `mnemo2-mcp laya-watchdog --run-dir <dir> --server-pid <pid>` subcommand (`shared_service::run_watchdog_command`), spawned once per service under the spawn lock; it exits when service.json is gone or names a different pid and kills the tree after 60 s with no live lease. `MNEMO2_MCP_EXE` overrides the launcher lookup (sibling of the GUI exe otherwise).

Tests: `cargo test -p mnemo --lib host::shared_service` and `host::laya` (scripted processes, temp dirs, no Python). Commit 0af11a6a on wt/agent-sharedLa (plan d3336a8a step 1).

### HOW: one home for the detached-spawn flags — process_tree::detach_command

In the `mnemo` crate the detached-spawn flags (Windows `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`, Unix `process_group(0)`) are defined in exactly ONE place: `src/process_tree.rs::detach_command(&mut Command)`, with the public pins `process_tree::DETACHED_CREATION_FLAGS` / `DETACHED_PROCESS` (cfg(windows)).

- `process_tree::detached_command(program)` (plan d3336a8a step 7, sccache) = `Command::new(program)` + `detach_command`.
- `host::shared_service::detach` and its flag consts are pure re-exports of those items (`pub use crate::process_tree::detach_command as detach;`), so the laya spawn path in `src/host/laya.rs` keeps calling `shared_service::detach`.

Never `DETACHED_PROCESS`: a console-less child makes every console-subsystem grandchild pop a new Terminal window (user-reported swarm). Never put a shared service in a KillOnCloseJob either — surviving the spawn is the point.

Established by the plan d3336a8a step-1 replay commit 5420fad7 (wt/agent-layaRepl), which unified step 1's helper with step 7's.

### HOW: src-tauri code reaches kernel modules only through bare crate-root re-exports

`tests/boundary.rs::tauri_uses_only_public_api` scans ALL src-tauri production code (src-tauri/** and src-tauri/mnemo2-app/**, binaries included; only `#[cfg(test)]` modules are exempt) for the path tokens `mnemo::agent` / `mnemo::runtime` / `mnemo::host` and their `mnemo::{…}` grouped forms — a violation fails `cargo test --workspace` with "route via mnemo::headless / mnemo::app / the crate-root re-exports".

A new src-tauri binary/crate file that needs a kernel module must reach it via a BARE crate-root re-export added to the sanctioned block in `src/lib.rs` (~:56-103), which requires: a consumer-named comment (the block's stated contract), the same `#[cfg(feature = …)]` gate as the module it re-exports if it is feature-gated, and only module aliases/named items one name deep (no blanket re-exports). Example (plan d3336a8a step 2, commit 3a630d27): `#[cfg(feature = "embeddings")] pub use crate::host::models_host;` so `mnemo-models` uses `mnemo::models_host::serve`, which contains no banned substring.

Cost of missing it: the raw `mnemo::host::models_host` path only fails at the END of a full `cargo test --workspace` (~2 min per burn on a warm target); the fast narrow probe is `cargo test -p mnemo --test boundary` (~30 s).

### BUG: Mnemo's workspace cargo test flakes under machine load (shell.rs process/timing tests)

`cargo test --workspace` fails intermittently on a busy machine, always in `tool::agent::shell::tests` process/timing tests — never in logic. Root cause: the tests measure wall-clock bounds around PowerShell spawns and output streaming, and spawn latency explodes under load.

Evidence (2026-11-20, plan d3336a8a step 11 run, worktree pool-20): with 12 cargo + 68 rustc processes from other worktrees and CPU at 90-100%, a bare `powershell -NoProfile -Command "echo hi"` took 56.7 s inside a test while measuring 0.78 s idle; failures observed across runs were `chatty_command_outlives_the_silence_limit` (30 s silence timeout for a command that prints), `second_heavy_command_waits_for_the_slot` (same), `background_child_holding_the_pipes_does_not_hang_the_call` (16-19 s grace), `slot_wait_is_not_counted_as_silence` (SilenceTimeout at 4 s), `streams_incremental_deltas_before_the_child_exits`, `light_command_never_waits` (6.5-56.7 s). Each passes in isolation; the same lib suite passed 3799/3799 when the machine was quiet, and the shell module alone passed 55/57 at 90% load.

### BUG: one failed models-host request pinned 3-4 GB of in-process ONNX in a Mnemo2 window

In step 12 of plan d3336a8a (2026-11-20), the C:\Mnemo window reached a 3.7-4.6 GB working set while the FactoryGame window on the same shared mnemo-models host stayed at about 100 MB. Mechanism (measured by winMem01 with a counting-allocator probe):
- One transient embed request failure ("error sending request") made RemoteEmbedder build its lazy in-process fallback (BundledEmbedder for jina, about 0.6 GB). That fallback is cached for the process lifetime, so the ONNX session stays loaded even after the host recovers 60 s later.
- ONNX Runtime's CPU memory arena keeps one block per batch shape. fastembed pads each batch to its longest text, so one 17.5k-symbol pass grew the arena by about 2.9 GB, and it is never returned.
- The host's 5.2 GB has the same arena cause.
- Not the cause: the index re-parse (retains nothing), the find_code snapshot (about 60 MB) and the memory cosine pool (about 30 MB).
Fixes routed in plan d3336a8a: step 17 (no in-process ONNX for the code model while a host is serveable; one retry on a send error; drop the cached fallback once remote recovers) and step 15 (fixed-length padding or no arena on the host, 512-token cap, sub-batches of 16).

### BUG: a 3.7-4.6 GB Mnemo2 window = in-process ONNX embedder fallbacks + ORT arena growth, not the codegraph or the memory pool

A Mnemo2 window's 3.7-4.6 GB working set (plan d3336a8a step 17, measured 2026-11-20) was the ONNX Runtime side of in-process embedder fallbacks, not the codegraph or the memory pool. Numbers (mem_probe, counting global allocator + external WS sampler, fresh temp config dir, this repo): the index/re-parse pass retains nothing (0.2 MB Rust live, ≤85 MB WS peak, 18k symbols); the find_code snapshot +68 MB; the memory cosine pool +30 MB. The whale: one in-process jina-embeddings-v2-base-code session = 624 MB resident, and its ORT ARENA grows ~2.9 GB over one full pass — fastembed pads each batch of 64 to its longest text, so each distinct padded length allocates new arena blocks that ORT never returns. bge-base-en-v1.5 adds ~460 MB. Both in-process: 4,011 MB WS / 4,594 MB private peak — exactly the observed window (plus WebView2).

The trigger was structural: RemoteEmbedder's lazy in-process fallback (embedder.rs, "created at most once") cached the ONNX session FOREVER after ONE transient request failure — even while a healthy, leased host sat there serving; remote retried once a minute but the pinned session+arena were never freed (the observed failure class: "error sending request" against the one-request-per-connection host, likely a pooled-socket race; also the 10 s spawn-health-wait racing a slow cold host start).

Fix (step 17, wt/agent-winMem01): while a host is serveable (binary resolves or live descriptor — client_factory::host_is_serveable), the CODE embedder never loads in-process: build_code_embedder retries the acquire (2,4,8,16 s ≈ 30 s) then returns the not-ready signal (hash+Failed; the slot's retry gate skips the pass round; find_code falls back to text); RemoteEmbedder::embed_fallback returns zeros+Failed for the code model while serveable; embed_remote retries a transport-level send error once before arming the cooldown; a remote answer after a fallback drops the cached fallback (session+arena freed); the memory model keeps its in-process fallback (recall must work) and the deferred load (brain.rs) uses acquire_remote_embedder_with_retry. Verified before/after with mem_probe remote-mode + a mid-pass host kill: before 3,843-4,011 MB WS pinned; after 34-36 MB WS flat through the kill, the pass stopping at the not-ready signal, find_code falling back to text, and a fresh host respawning for the recall. The HOST's own 5.2 GB (same arena, server-side) is step 15's scope. Measurement evidence: %TEMP%\mnemo-memlab\logs; the throwaway probe is preserved in WIP commit 46144462 on wt/agent-winMem01.
