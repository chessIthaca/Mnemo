### HOW: multi_edit ops arrays — receipt-line cites shift when an earlier op in the same array changes line counts

Pitfall: in one multi_edit/file_edit ops array, a read-receipt line-range cite [s,e] is applied against the file AS LEFT BY THE PRECEDING OPS — an earlier op in the same array that inserts/deletes lines silently shifts every later line range, and the cite validates against the receipt's bytes so the mismatch only surfaces in the result. Burned 2027-02 in plan d6a64d60 step 1 (worktree agent-modelCmd): inserting `pub mod model_settings;` at mod.rs:53 (+5 lines) shifted the generate_handler! list, so a cite anchored at receipt-lines 414-415 (`ipc::settings_tiers,`/`ipc::settings_save_tiers,`) landed on post-shift 414-415 (`ipc::settings_remove_endpoint,`/`ipc::settings_set_api_key,`) — two registered commands were deleted and the tiers pair duplicated; the module still compiled (duplicate generate_handler! entries do not error), so only an unanchored `git diff` read caught it.

Safe patterns:
- Multiple ops in ONE array that each need line anchors: either use unique old_string anchors (no line numbers) for all later ops, or
- mint the receipt AFTER the preceding ops are already applied (separate call), or
- use line cites only for ranges that no earlier op in the same array can shift (all cites in top-of-file-independent regions), or
- apply shifting edits one op per call.
- ALWAYS do an unanchored `git_read op=diff` review of one's own whole diff before committing — the compile/test gate does NOT catch wrong-location registrations (duplicates compile).

### HOW: assert Svelte 5 state changes in vitest without flush-race false failures

Two vitest/jsdom pitfalls hit while testing the Mnemo2 Models/Savings settings pages (plan d6a64d60 step 2, commit d1d5d62):

1. Svelte 5 flush race: after fireEvent or after invoking a transport event handler directly, the DOM updates on the NEXT microtask flush. A synchronous getBy*/expect(...) right after races it (the call is recorded but the note/progress bar is not in the DOM yet). Assert with `await screen.findBy*` / `await waitFor(...)` after every state-changing action, even after a `waitFor` that already saw the mock called (the mock records at invoke time, before the await continuation mutated state).

2. getByLabelText matches SECTION aria-labels too: a `<section aria-label="Vision model">` wrapping an `<input aria-label="Vision model">` makes getByLabelText throw "multiple elements". Keep container aria-labels distinct from the label of the input inside (section "Vision", input "Vision model").

3. testing-library regex matchers are case-sensitive: /A fresh download.../ never matched "— a fresh download..." (lowercase a) — 5 failed runs looked like a render bug while the note was in the DOM all along. When a note "never renders", dump the section HTML to a file from inside the test before theorizing about reactivity.
