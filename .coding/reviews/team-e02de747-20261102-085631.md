### DECISION: Mnemo2 cannot call ipc::finetune — the module is Mnemo1-binary-only (plan e02de747)

Symptom: design .coding/design/mnemo2-laya.md (§4 "reuse unchanged") treats src-tauri/src/ipc/finetune.rs's spawn_startup_finetune as reachable from Mnemo2 — it is NOT. The `ipc` module tree is declared only in main.rs (the Mnemo1 BINARY target: `mod ipc;` at main.rs:23), while src-tauri/src/lib.rs compiles only webview_udf + instance_marker + #[cfg(feature="mnemo2")] mnemo2 into the LIB crate that the mnemo2 binary links (mnemo_app::mnemo2). From src-tauri/src/mnemo2/* (lib crate), `crate::ipc::finetune` fails to resolve (E0433); lib.rs:9-11 documents the split ("without pulling Mnemo1's larger IPC surface into the Mnemo2 binary").

Consequence (plan e02de747 step 3, commit ecdfc35 on wt/agent-layaRunt, 2027-01-15): Mnemo2's startup fine-tune spawn was left as a TODO at the attach site (runtime.rs attach_laya) — the step brief's sanctioned fallback ("only if it compiles cleanly … otherwise leave a TODO"). Spawning it needs the gate+runner lifted into the lib (or a Mnemo2-local twin): a crate-layout change (lib.rs + main.rs + ipc/mod.rs), not a single-file step. Until then Mnemo2 skips the startup fine-tune; the classifier serves whatever checkpoint is installed.

Related seam shipped in the same commit: LeadRuntime holds `laya: Mutex<Option<Arc<LayaManager>>>`, attach via engine-backed Setup::attach_laya at the end of start_engine, explicit stop in shutdown before the engine drops, and `pub fn laya_manager()` — the seam step 4's settings commands must reuse (a fresh for_engine Setup builds its own manager; only the held instance owns the running sidecar child). The accessor is `pub` not `pub(crate)` because dead_code under deny(warnings) fires on a pub(crate) method with no production caller yet.

### SPEC: Mnemo2 laya_settings commands (plan e02de747 step 4, commit 7732a6f)

Mnemo2's Laya settings backend (plan e02de747 step 4) lives in src-tauri/src/mnemo2/laya_settings.rs: commands `laya_status`, `laya_setup`, `laya_disable`, `save_laya_settings` (handlers directly after `ipc::lead_open,` in mod.rs). Event channel: `mnemo2://laya-event` (SetupEvent payloads). Manager lifetime: a laya-serve child lives inside the LayaManager that spawned it (last-Arc Drop = kill); the setup pipeline runs on the per-call Setup's OWN manager, held in laya_settings::HELD_SETUP_MANAGER (the IpcState role). Review finding heldManagerOrphan (fixed in commit be82192): a static is never dropped, so the hold now SETTLES — the forwarder forwards until the event stream CLOSES (the pipeline task's end: the autostart that runs after Done, inside the task, has landed or failed; a failed probe kills only the child this start spawned, so the manager's child state is final at close), then settle_held_manager_core: live sidecar (Starting/Ready/FineTuning) + open lead → LeadRuntime::set_laya_manager (pub setter, runtime.rs — stops the manager it replaces, its child superseded by the live-slot swap) so LeadRuntime::shutdown stops it like the attach-time manager; live + no lead → stop now (orphan; heals close-during-setup); not live → just clear the hold (the session's manager keeps serving the untouched slot). The settle only touches a hold still pointing at THIS manager (Arc::ptr_eq — a mid-flight laya_disable takes it, a newer laya_setup replaces it). mod.rs's RunEvent::ExitRequested handler calls laya_settings::stop_held_manager() right after state.shutdown() — the app-exit belt. The kernel's begin_setup guard is per-manager — hosts with per-call Setups serialize setups with their own flag (SETUP_IN_FLIGHT, released at the stream's close, so a second Install click fails fast while the sidecar comes up). laya_disable stops BOTH the lead's attach-time manager (LeadRuntime::laya_manager()) and the settings-side hold. Status mapping: FineTuning -> "ready"; enabled+installed+live-Disabled -> "disabled"; enabled+!installed -> "not_installed".
