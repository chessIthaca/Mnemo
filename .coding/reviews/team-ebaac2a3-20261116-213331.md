### HOW: a file restored with Copy-Item keeps its old mtime, so cargo reuses the stale test binary

When proving a Rust red-check by swapping files — `git restore --source=HEAD -- <path>`, run the test, then `Copy-Item backup <path>` — PowerShell's Copy-Item preserves the BACKUP's LastWriteTime on the destination, so the restored (fixed) source is older than the build fingerprint cargo just produced and cargo silently reuses the stale binary. Symptom: a test panics at line numbers that do not exist in the file on disk (e.g. panic at tests.rs:6663 while the assert sits at 6667), or an edited test keeps failing/passing exactly as before the edit. Fix: after copying back, stamp fresh mtimes — `$now = Get-Date; foreach ($p in @(...)) { (Get-Item $p).LastWriteTime = $now }` — before re-running cargo. Prefer file_edit/file_write for the swap-back: they write fresh mtimes. Seen 2026-11-16 in plan ebaac2a3 (worktree .worktrees/agent-auditRep).
