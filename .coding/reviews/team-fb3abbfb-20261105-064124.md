### SPEC: mnemo2-mcp helpers identify themselves with a per-process bridge id

The stdio helper (src-tauri/src/bin/mnemo2_mcp/serve.rs) mints one id per process — `uuid::Uuid::new_v4().simple().to_string()`, 32 lowercase hex — stored as `Bridge::id`. It is sent as header `X-Mnemo-Bridge: <id>` on every forwarded `/mcp` request and as `"bridge": <id>` (plus the usual `"root"`) in the `/lead/detach` body posted by `Bridge::finish` when stdin closes after a forwarded tools/call. A missing header/field means an anonymous/older helper (released as before). Server side (src-tauri/src/mnemo2/team.rs + mcp_server.rs) keeps the set of bridge ids that led and releases the external lead only when the last one detaches; the 10-minute idle sweep remains the crash fallback. Plan fb3abbfb; helper-side commit 0dbb2418 (branch wt/agent-helperBr), tests `forwarded_calls_carry_a_stable_bridge_id` and `detach_on_close_names_the_bridge` in serve_tests.rs.

### BUG: a closing helper released the external lead for every other helper — server side fixed (ffdd0016)

Symptom (2026-11-05, three times): a short-lived helper that made a tool call (e.g. one-off `mnemo2-mcp serve`) exited and Mnemo2 detached the external lead while the main Claude Code helper was still connected and leading; its waiter returned 'The Mnemo lead was detached'. Root cause: the helper's `Bridge::finish` posted a bare `/lead/detach` whenever it had forwarded a tools/call, and the server released the external lead unconditionally — tool calls attach anonymously, so the server could not tell one helper from another.

Fix (server side, commit ffdd0016 on wt/agent-leadBrid, plan fb3abbfb step 1; step 2 = helper side, pending): `ExternalLead` (src-tauri/src/mnemo2/team.rs) keeps `bridges: BTreeSet<String>` of helper ids that made a tools/call while attached (`note_external_bridge`/`forget_external_bridge`); every release path clears it. mcp_server.rs: `/mcp` tools/call reads header `X-Mnemo-Bridge` (valid id: trimmed, non-empty, <=64 chars of [0-9a-f]) and notes it; `/lead/detach` body `{"root", "bridge"}` forgets that id and releases only when none remain (reply `{"released": bool}`; helper ignores it); a detach without a valid bridge id is anonymous and releases exactly as before (existing tests unchanged). Idle sweep (10 min, no call, no waiter) still releases regardless of remembered helpers — the fallback for crashed helpers. Regression test: `a_closing_helper_keeps_the_lead_while_another_helper_led` (red 0 passed 1 failed before, green after); plus `detach_without_a_bridge_still_releases`, `idle_sweep_releases_even_with_bridges_left` (mcp_server) and `a_release_forgets_every_external_bridge` (team).
