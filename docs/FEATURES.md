# Mnemo — feature reference

The exhaustive detail behind the [README](../README.md)'s highlights — how the plan-first workflow is enforced, what the four memory tiers do, what the knowledge graph indexes, and the full surface of the agent's tools. Configuration (providers, models, MCP servers, per-project state) lives in [CONFIGURATION.md](./CONFIGURATION.md).

## Key ideas

- **The plan is the tool surface, not a suggestion.** A workflow state machine (Planning → Executing → Reviewing → Complete) decides which tools exist at any moment. In Planning there are no write tools; in Reviewing only the closing tools are callable (during a plan the advertised array is frozen for prefix-cache stability — one byte-identical surface for every plan kind, because a research plan's narrower array reset the cached prefix at the transition and re-billed the whole conversation; out-of-state and research-forbidden calls are still rejected at dispatch — a research plan's file tools pass only for its own `.coding/**` artifacts, and a completed or abandoned implementation/bug_fixing sub-plan forces its research root through review); the agent cannot skip ahead.
- **Memory is first-class infrastructure.** Every turn auto-recalls relevant memories; sessions consolidate into episodic summaries, distilled facts, and reusable procedures. The agent you talk to next week remembers this week's decisions — because a forgotten decision is a defect: the cost is not the retyping, it is the wrong call made confidently on a stale premise.
- **Tool usage is optimized.** Semantic code indexing and purpose-built tools replace grep archaeology — editing with a map, not a torch: the right file, first try.
- **Review is unskippable by construction.** An implementation plan cannot complete without a read-only reviewer subagent's report; its findings must all be fixed before commit. Review reports must open with a verdict line (`## Verdict: PASS` / `## Verdict: FINDINGS (n high, n low)`) — an unparseable verdict counts as FINDINGS (fail closed).
- **Bugs get their own plan kind.** `kind: "bug_fixing"` — for CONTAINED defect fixes — forces a locked reproduce → root-cause → fix → verify skeleton with a required `bug: <symptom>` param; a bug-triggered FEATURE (the fix adds capabilities, new dependencies, or spans multiple modules) belongs in `kind: "implementation"` with the bug documented as motivation in goal/context instead (2027-01-11, backlog 51ee41c1), and create_plan emits an advisory steering note when a bug_fixing payload looks feature-scale (more detailed steps than the locked skeleton AND spanning ≥3 modules); provided steps persist as CHECKABLE sub-items under `## Detailed steps` (the crash-resumption detail; text immutable like the skeleton, each sub-step's checkbox ticked via `complete_step detailed_step_index` so a restart shows exactly what shipped; escaped if they'd collide with plan-file structure); the verify step must record the regression test name (validated against the code graph at finish), a fix that turns out feature-scale mid-flight records `landed_design` + a "Landed design" context amendment (architecture, deviations from the sketch, measured numbers, invariants — the finish gate blocks the flag without the amendment; agent.md "Documentation expectations"), and finish auto-captures a BUG: memory digest.
- **Everything survives an interruption, even when context resets.** The spec is a file on disk, not a chat message: plans live on disk with per-step checkboxes, memory lives in SQLite, and step-granularity markers let a restarted session resume mid-plan.
- **Context is the scarce resource.** Shell/build noise never enters the window, occasional tool families stay deferred until wanted, and the tool array is byte-stable so provider prompt caches hit.

A chat window can suggest all of the above. **A harness enforces it.**

## Key features

**Workflow & safety**
- Enforced plan-first lifecycle with on-disk plans, sub-plan stacks (nested work pops back to the parent), and named *skills* — TOML files in `.coding/skills/` that overlay the workflow with a scoped tool allow-list + target state. The library is a live, reloadable `SkillLibrary`: `skill_reload` re-reads the dir into the running app (every workflow state, an active skill included — a hand-edited file never needs a restart) and `skill_create` authors a validated skill file, hot-added as startable (Executing only; never overwrites an existing file unless asked, never rewrites a skill shipped with the app such as `merge_to_main`, and its write is sandbox-mediated — a planted symlink or hardlink at the target is refused, and a link at the skills dir itself is refused when it leaves the project or resolves into a protected tree)
- Diff-based approval gate with three safety modes (approve-each / auto-approve-project / autonomous); git `merge` and `push` are always approval-gated
- Path sandbox confining all file tools to the project; protected `.coding/` live state and the `.git` control plane (planted hooks/`core.fsmonitor` can never be written by the file tools); refusals are hardlink-aware (a `.coding/**` file whose inode is shared with another name is refused) and re-run on the canonical path (a Win32 8.3 alias like `.coding/KNOWLE~1/…` cannot plant a subtree inside a protected tree), and the creation ladder fails closed on link components — a dangling link leaf included, with its one lexical fallback (a just-created parent) re-checked for link-freedom; API keys stored user-only (Windows DACL / `0o600`)
- Crash-safe resume: plans, workflow state, and memory markers persist across restarts
- Hang watchdog: if the main thread ever stalls >10 s (a Windows "Not responding" hang), the app writes an evidence report — `hang-<timestamp>.txt` in the project's `.coding/logs/` (or `%TEMP%\mnemo-hang-reports\` when no project is open) — with the stall duration, main-thread CPU busy-vs-blocked sample, a stack walk of the stalled main thread (module!symbol + file:line per frame), and a wait-chain summary naming the blocked-on object (all Windows-only enrichment), plus the agent's recent activity — so the next freeze names its exact line instead of being guessed at. The named stacks caught the recurring 2026-08-20 hang: a tao 0.35.3 keyboard self-deadlock, fixed by a vendored tao 0.35.4 backport of upstream PR #1215 (`vendor/tao/PATCHES.md`) plus Rust-side delta coalescing in the event forwarder
- Live shell output: while a `shell` call runs, its stdout/stderr stream into the chat card as they are produced — chunks throttled (>= 60 ms between emits per stream, or an 8 KiB batch), a 256 KiB live budget per call with a one-time truncation note once it is reached, and a rolling 16 K-char tail (UTF-16 code units) on the card that is cleared the moment the result lands — so a multi-minute build shows progress instead of looking like a hang. The preview block occupies a FIXED height (six lines), reserved from the first paint of the running card, so streaming chunks never change the card's height or jump the chat column — and it can be turned off entirely from Settings → Chat ("Stream shell output live in the tool card", persisted to localStorage, default on). The stream is display-only (`tool_output_delta`, keyed by `tool_call_id`, silent in the console); the final tool result stays byte-identical and is what the model consumes
- Command-aware shell-output filtering: `cargo`/`npm`/`git status` noise (Compiling…, passing tests, asset tables) is collapsed to errors, warnings, and summaries before it reaches the transcript — errors are never hidden, unknown commands pass through, and the raw unfiltered stdout/stderr remain in the tool result's `data` field. Configure via the `[shell_filter]` section of config.toml

**Memory**
- Four tiers: working (raw events), episodic (session summaries), semantic (durable facts), procedural (workflows)
- SQLite + FTS5 keyword search combined with bundled ONNX embeddings (fastembed; hash fallback) for semantic recall — no external service needed; keyword hits re-rank by cosine, and a zero-keyword query falls through to a capped semantic scan (200 most-recent) so paraphrases and stemming misses still surface; the cosine weight is embedder-aware (0.2 hash fallback / 0.35 real embedding models)
- Automatic consolidation pipeline plus manual maintenance (re-embed, vacuum, cleanup) in the UI
- Typed memory records: title prefixes `SPEC:`/`DECISION:`/`BUG:`/`PLAN:`/`HOW:`/`REVIEW:` classify records; the four knowledge types (SPEC/DECISION/BUG/HOW) live as **files** under `.coding/knowledge/<type>/` — git-tracked, wiki-linked (`[[spec/x]]`, `[[plan/<id>]]`, `[[src/...]]`), unbounded bodies with TOML front matter (title/status/supersedes/created); `memory_write`/`memory_supersede`/`memory_update`/`memory_delete` operate on the files (the truth), and the derived index holds budgeted digests with path+commit pointers (the derived index auto-truncates digests to stay compact; the file is complete). Supersede-not-delete keeps history (superseded files/records are excluded from recall by default, retrievable via `include_superseded`); superseding rewrites stale hand-written `File:` pointer lines in the successor body to the tool-chosen canonical path (the caller cannot know the deduped filename), and a targeted reindex of a successor knowledge file resolves its `supersedes` against the on-disk corpus (predecessor context + metadata reconciliation) so updates no longer error or leave stale digests; hygiene tools `memory_update`/`memory_amend`/`memory_supersede`/`memory_delete` (`memory_amend` appends a dated amendment paragraph to a knowledge record — the sanctioned `.coding/knowledge/**` addition writer, stripping a leading `Amended …:` heading the caller supplies so exactly one heading lands, dated by the tool; `memory_update` also carries a `find`/`replace_with` targeted-repair mode that fixes stray text in a record body in place, so record text is repairable in-tool rather than via the shell fallback), `memory_consolidate` for distillation, and the single retrieval tool `memory_search` (a ranked query, or a query-less browse narrowed by record_type/tier/prefix that replaces the former list-only tool) plus read-only `git_log`/`git_show`
- Derived index: `.coding/plans`, `.coding/reviews`, `.coding/knowledge/**`, and the pending backlog are indexed into budgeted PLAN:/REVIEW:/SPEC:/DECISION:/BUG:/HOW: digests with path pointers (incremental, idempotent; rebuild wipes only derived records — authored memories are sacred). **Startup reconciliation**: on project open the corpus is checked against the index state (content hashes); when the on-disk truth drifted — a git merge landed, a record was edited, or `memory.db` was deleted — the index is re-derived from the files in the background with a branded splash wait dialog (Mnemo logo + tagline over a network-motif band) and a live progress bar + counter; an in-sync startup stays silent. Settings → Memory shows counts + last-built and a Rebuild button with progress
- **The SQLite DBs are caches, the files are the truth**: `.coding/memory.db` and `.coding/codegraph.db` are gitignored rebuildable stores — deleting either forces a full rebuild from source (knowledge files, plans, reviews, source code). Git carries only the truth files
- **Working-branch topology**: one `wt/*` working branch per agent directory (worktree), reused across plans and landed into protected `main` via the `merge_to_main` skill — directly (sync `main` with `origin` first — `git fetch` + `git pull --no-rebase` — so the landed merge is immediately pushable instead of leaving `main` diverged, then delete the branch after landing it) on unprotected repos, or through a PR the skill opens and leaves for a human approving review where main is ruleset-protected (the branch is deleted after the human merges). `create_plan` auto-forks that branch from `main` when on `main` (no `branch` arg) and reuses the current branch otherwise — work never silently stays on `main`; the `branch` arg is reserved for an explicit user request. `.coding/` travels with git, so knowledge files, plans, reviews, and the backlog merge across instances — `backlog.jsonl` uses git's union merge driver (concurrent adds concatenate cleanly; UUID ids never collide), `plans/stack.json` is per-instance local state, and the memory index re-derives automatically at the next project open after a merge
- Merge hygiene: finish-captured digests carry a branch-only `unmerged` hint while work sits on a feature branch, and the `merge_to_main` skill supersedes those records once the branch lands in main — a feature/bug with no live marker is assumed to be in main
- Scale knobs in the `[memory]` config section (Settings → Memory): recency-decay half-life, per-query result cap, derived per-class cap, digest auto-truncation lengths — applied live on save, no restart

**Agents & interface**
- Multi-agent runtime: parallel sub-agents (`spawn_agent`), a strict read-only reviewer role (reads + `git_diff`/`git_log`/`git_show`, `web_fetch`, graph tools, and memory/backlog queries + `write_review_report` — it cannot ask questions, mutate memory/backlog, run plans, or finish; review reports can only ever be authored by a spawned reviewer — `write_review_report` is visible under no other filter and `.coding/reviews/` is protected from the file tools — the one residual is an approval-gated shell call, as with `.coding/plans/` — so the main agent can never review its own code; a spawned reviewer runs on the `[models.reviewing]` model — falling back `[models.executing]` → `[models.subagent]` → default; an explicit `model` on a reviewer spawn is dispatch-denied unless it is the user-sanctioned failed-reviewer retry (for non-reviewer spawns the arg still wins); the `[models.reviewing]` slot is reviewer-spawn-only: the main agent keeps its executing model through the Reviewing closing sequence), and per-workflow-state model routing (different models for planning vs. executing vs. complete; sub-agents skip the state tier — their workflow state is the Subagent role state, so they run `[models.subagent]` → default); if a reviewer fails without writing a report the parent must ask the user how to proceed (retry on another model / abandon the review — never self-review) instead of blindly respawning it; the status-bar model picker switches only the active agent — models are agent-specific, so other agents keep their models and newly spawned agents keep the configured default, and the picked model is a state-scoped pin: it beats per-state routing while the agent stays in the workflow state where it was picked, a configured `[models.*]` slot takes over when the workflow changes state (the pick goes dormant and resumes if the workflow returns), and with nothing configured for the new state the pick keeps serving
- Any OpenAI-compatible endpoint plus local providers (Ollama, LM Studio) and native Anthropic Messages API endpoints (Anthropic or any compatible gateway via a custom base URL); reasoning-effort and vision support (per endpoint, or per model — one endpoint can mix text-only and vision-capable models); full request tracing
- Reasoning-state continuity: each provider's assistant turn is stored **verbatim** in `Message::raw` (reassembled from streamed deltas) and echoed unchanged by the request builder — so reasoning fields (`thought_signature`, `reasoning_content`, thinking-block `signature`, `encrypted_content`) and any unknown keys round-trip byte-identical; a `ProviderPolicy` data object per provider (`src/provider/policy.rs`) captures each provider's reasoning contract and drives cross-vendor detection (full builder consultation of include/template/reasoning-field params is a follow-up); cross-vendor model switches strip reasoning + set `reasoning_stripped` (one-way — see `strip_cross_vendor_reasoning` doc); compaction never trims inside an open tool loop; serialization-bug 400s (missing `thought_signature`, `reasoning_content must be passed back`, `Expected thinking…found text`, `modified prior content`) fail loudly and are never retried; the OpenAI Responses API (`previous_response_id`) provides server-side stateful mode alongside the stateless raw-echo path
- Per-model endpoint config: each model within an endpoint can carry its own max input/output token caps and reasoning-effort allow-list; base URLs are forgiving (a missing trailing `/` is auto-added on save and load), and token caps discovered from the provider auto-fill the per-model entries in Settings
- Live turn-phase indicator: the inflight bar cycles sending (local prep only: token counting, recall, prompt build) → (compacting context while an auto-compaction summary call runs) → waiting (network-bound: TCP/TLS connect, POST upload, time-to-first-token, AND retry backoff sleeps — pre-first-byte only: a mid-stream stall keeps showing reasoning…/answering…, matching the trace graphs where stall is part of generate and renders as the red hatch overlay) → reasoning → answering → running tools — reasoning and the live answer both stream into the thinking box (reasoning dimmed gray, answer blue-gray), whose open/closed state is the USER's choice alone (it never opens itself — only the chevron click, or starting a drag on the handle, which opens it, changes it; the choice is remembered across restarts and a fresh install starts collapsed), and every failed provider attempt is surfaced as a transient "attempt N/3 failed, retrying" note in the activity log, so a multi-second "waiting" window is never a silent black box; non-retryable errors (context overflow, auth failure, model-not-found) fail immediately instead of burning the 3×3 retry stack, and a 429 (rate limit / out of quota) stops after a single attempt against that provider and automatically switches to the same model on a different endpoint if one is configured (retrying once on the alternate; the alternate stays sticky for that model id on later turns, but it is endpoint routing only — per-phase model overrides like [models.planning]→[models.executing] keep switching), surfacing an actionable "no alternate provider found" error only when no other endpoint serves the model or none can hold the live conversation (approval/question pauses get their own amber label), with a live elapsed timer ("1m 3s") and a tokens-received counter that climbs as the model streams; the streaming display updates independently of animation frames — a delta flushes immediately when it arrives ≥40ms after the last flush (sparse tokens appear one-by-one as they arrive), dense bursts batch per frame, and a fallback timer flushes within 40ms even when requestAnimationFrame stalls (RDP occlusion, WebView2 quirks)
- The LLM trace records per-request phase timings — prep (local prompt build: token counting, recall, prompt assembly), compact (auto-compaction call), backoff (retry sleeps before this attempt), connect (the POST in flight: TCP/TLS + upload + server ack), wait (TTFT: POST-send → first token — upload + server prefill/queue), reasoning (thinking time), generation (answer time), stall (byte-silence gaps inside the generation window), and tool-execution time — so you can see where each request's latency actually went; error records (connect timeout, stream stall, HTTP error) carry their elapsed time in the connect/wait/generation buckets too, so a 10s connect timeout or 30s dead-connection stall is attributed instead of lost; a user interrupt that drops a live stream mid-flight stamps the record **cancelled** (not failed) — no provider-errors row, and the aborted request still lands a `cancelled` row in request_stats so it stays countable; reasoning text is recognized from `reasoning_content`, `reasoning`, and inline thinking-tag blocks (Ollama / DeepSeek thinking mode)
- The Trace tab shows live stats in a resizable strip at the top (drag the splitter between the graphs and the request log): vertical per-request column charts — stacked phase times (prep/compact/backoff/connect/wait/reason/generate/tools, with a dithered red stall overlay inside the generate bar showing the stalled share), token stacks (prompt with a dithered cached overlay showing the cache-hit rate/completion/reasoning) — with the newest request always the rightmost column and a Fill/Relative scale toggle (Relative, the default: a 2-minute request's column is 4× taller than a 30-second one; Fill normalizes every column to full height); every legend chip is a click-toggle that hides/shows its series in that chart (persisted across sessions via localStorage), with column maxima recomputed over the visible series only so hiding a dominant segment zooms the rest — the `cached` chip toggles only the dithered overlay inside the prompt bar, and the `stall` chip only the overlay inside the generate bar; plus session aggregates (totals, tok/s, mean cache hit); hovering a chart column opens a multiline, tab-aligned tooltip (portal-rendered so the chart overflow can't clip it) with color-dotted rows matching the segments; request rows show model · provider; a request's response header can carry an amber `guard cut` marker (tooltip: the matched stop boundary and cut position) when the client-side stream guard terminated that turn early — distinguishing guard cuts from natural stops and empty completions
- Incremental token accounting: the turn loop re-tokenizes only messages appended since the last count (plus a head swap) instead of a full-history BPE pass per request, so context counting stays O(1) per loop iteration even as the conversation grows
- Context compaction that never wedges the conversation: the verbatim-kept tail is cut at a tool-call boundary (no orphaned tool results whose assistant call was summarized away), `/compact` (or the ctx-bar Compact button) announces start + result in the transcript on every path, and a mid-task compact resumes the interrupted work on the compacted conversation instead of stopping execution; past its remaining headroom toward a session's last tokens it automatically turns aggressive (`keep_recent=3`) so long sessions never fatal with `ContextWindowExceededError`; a turn whose context STILL stays over the threshold re-compacts at most 4 times (escalating `keep_recent` to 1) before aborting the turn with a clear error instead of re-compacting every iteration forever, and a turn-level repetition guard breaks the turn on 3 byte-identical consecutive assistant responses whose intervening tool batches had no error interaction (tool name+arguments keyed, provider-assigned ids ignored — the cross-iteration mirror of the in-stream R10 guard) so a pattern-continuing model can't re-execute the same tool call unboundedly — a response that follows a tool error is a repair attempt instead (the ring resets), and error loops are owned by the consecutive-error cap, which counts error INTERACTIONS: a batch of same-time failing calls is one interaction, giving the model a repair chance between interactions (backlog 7f72d3d7)
- The chat transcript stays responsive in long (run-all overnight) sessions: only the last 200 entries render by default (a "Show earlier messages (N hidden)" expander above the list reveals earlier batches stepwise), bounding the DOM size and per-frame reconciliation cost no matter how long the session grows

## The enforced workflow

<p align="center">
  <img src="../assets/workflow.svg" alt="Mnemo workflow: Planning → Executing → Reviewing → Complete, with back-edges for review findings and abandoning a plan">
</p>

1. **Planning** — read tools only. The agent explores the codebase and must call `create_plan` (a goal, context, and ordered steps) before it can touch anything.
2. **Executing** — all tools available, one step at a time (`complete_step` checks them off on disk). `create_plan` here pushes a *sub-plan*; finishing it pops back to the parent exactly where it left off. Skills temporarily narrow the tool set for focused work.
3. **Reviewing** — implementation plans only: the test matrix runs, a read-only reviewer subagent audits the full diff and writes a report, every finding is fixed, then the work is committed and `finish` closes the plan. Findings may not be deferred.
4. **Complete** — read-only again until the next plan. Research plans skip Reviewing by design (they produce no source changes).

Spec-driven and test-first development are not new ideas — everybody agrees with them, and everybody skips them at 2am under a deadline. A chat window can only ever *suggest* them; a harness makes them structural. In Planning no write tools exist — absent from the request schema, not discouraged. Bug plans are locked to the reproduce → root-cause → fix → verify skeleton. For bug plans, `finish` is blocked until the verify step names a regression test, validated against the code graph. If your guardrail is a sentence in a prompt, you cannot safely downshift the model. If your guardrail is the tool schema, you can — the rails are what make the smaller executor viable.
